## 🎯 Objectif du jour
Liste, détail, navigation sur ton API.

## 📖 Cours approfondi
**Modèle mental : le socle d'un projet, c'est le SQUELETTE MARCHANT — la plus petite version navigable de bout en bout qui PROUVE que l'architecture tient, avant d'ajouter la moindre fonctionnalité.** Tu ne commences pas BiblioApp par le formulaire le plus complexe ; tu commences par le chemin le plus fin qui traverse toutes les couches : afficher la liste des livres (depuis ton API via la couche api), cliquer sur un livre, voir son détail, revenir. Si ce squelette marche, tu as validé que le routing (jour 99), la couche api (jour 97) et l'architecture d'état (jour 104) fonctionnent ENSEMBLE — le reste n'est que du remplissage de ce cadre éprouvé.

Pourquoi commencer par le squelette marchant (« walking skeleton ») :
1. **Il valide l'assemblage tôt** : les bugs les plus coûteux sont ceux d'intégration entre couches (le front n'arrive pas à parler à l'API, le routing casse le chargement). Les découvrir sur un squelette de 50 lignes est trivial ; les découvrir après avoir codé dix écrans est un cauchemar.
2. **Il donne un fil de bout en bout** : chaque fonctionnalité suivante (CRUD, recherche) s'accroche à un squelette qui marche déjà, au lieu de flotter dans le vide.
3. **Il applique ton cadrage** (jour 104) : le socle est le premier incrément du backlog, celui qui met en place l'arbre de composants et le plan d'état décidés.

La discipline des COMMITS ATOMIQUES accompagne le socle : chaque commit est un pas COHÉRENT et réversible (« ajoute le routing », « branche la liste sur l'api », « ajoute la vue détail »), avec un message qui dit le POURQUOI. Un historique de commits atomiques raconte la construction du projet, permet de revenir en arrière proprement, et est LU par les recruteurs qui regardent ton GitHub. À l'inverse, un commit géant « BiblioApp » de 2000 lignes est impossible à relire et signale une absence de méthode.

La règle du jour : **construis d'abord le chemin le plus fin qui traverse toute l'architecture, commit par commit atomique — le socle marchant est la fondation sur laquelle tout le reste s'accroche**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : le socle navigable de BiblioApp — liste, détail, navigation, couche api — en commits atomiques.

**Exemple simple** : le squelette le plus fin tient en une phrase de code — la liste chargée depuis l'api et rendue. `const etat = useFetch<Livre[]>('/livres')` puis rendre les 3 états. Si ça marche, la couche api + le hook + le rendu sont validés ensemble.

**Raisonnement pas-à-pas** : mettre en place le routing → brancher la liste sur l'api (3 états) → ajouter la vue détail par id d'URL → vérifier la navigation aller-retour, un commit atomique par étape.

**Structure du socle** :
```tsx
// Commit 1 : "socle: routing liste/détail/404"
<Routes>
  <Route path="/livres" element={<Liste />} />
  <Route path="/livres/:id" element={<Detail />} />
  <Route path="*" element={<PageIntrouvable />} />
</Routes>
// Commit 2 : "socle: liste branchée sur l'API (3 états)"
function Liste() {
  const etat = useFetch<Livre[]>('/livres');                 // couche api (jour 97) + hook (jour 110)
  if (etat.s !== 'ok') return <EtatChargementOuErreur etat={etat} />;
  return <ul>{etat.data.map((l) => <li key={l.id}><Link to={`/livres/${l.id}`}>{l.titre}</Link></li>)}</ul>;
}
// Commit 3 : "socle: vue détail par id d'URL"
function Detail() { const { id } = useParams(); const etat = useFetch<Livre>(`/livres/${id}`); /* ... */ }
```

→ (a) pour découvrir tôt les bugs d'intégration entre couches, quand ils sont triviaux à corriger ; (b) un pas cohérent et réversible, avec un message qui dit le pourquoi ; (c) que routing + couche api + architecture d'état marchent ENSEMBLE.

## 🏢 Cas métier
Le « walking skeleton » est une pratique reconnue de démarrage de projet : construire d'abord le chemin le plus fin de bout en bout pour valider l'architecture avant d'investir dans les fonctionnalités. Les équipes qui le font découvrent les problèmes d'intégration (front↔API, configuration, déploiement) alors qu'ils sont faciles à régler ; celles qui construisent feature par feature sans squelette découvrent au pire moment que les couches ne s'assemblent pas. Couplé aux commits atomiques — lus par les recruteurs sur GitHub comme un récit de la construction —, cette approche signale une méthode de développement professionnelle, bien au-delà du « ça finit par marcher ».

Ça valide TÔT que le routing, la couche api et l'architecture d'état fonctionnent ensemble, quand les bugs d'intégration sont triviaux à corriger.
