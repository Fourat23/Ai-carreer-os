## 🎯 Objectif du jour
Orchestrer un traitement à l'échelle.

## 📖 Cours approfondi
**Modèle mental : orchestrer, c'est traiter des milliers d'unités de travail de façon FIABLE et ÉCONOME — le passage du prototype (10 documents) à l'échelle (500, 50 000) révèle des problèmes que le petit cas cachait.** Un workflow qui marche sur 10 documents ne « marche » pas forcément sur 500 : les appels LLM échouent parfois (rate limits, timeouts), le coût total devient significatif, la durée aussi, et un plantage au document 480 ne doit pas perdre les 479 précédents. L'orchestration est l'ingénierie de la FIABILITÉ et de l'EFFICACITÉ à l'échelle.

Les quatre préoccupations d'une orchestration à l'échelle :
1. **Le découpage** : diviser le travail en unités indépendantes (un document = une unité) qui peuvent être traitées, retentées et suivies séparément. C'est le sectionnement du jour 282, appliqué au volume.
2. **La parallélisation contrôlée** : traiter plusieurs unités à la fois pour la vitesse, MAIS avec une limite (un sémaphore) — 500 appels simultanés déclenchent les rate limits (429) et peuvent coûter cher d'un coup. La concurrence bornée est un réglage clé (trop bas : lent ; trop haut : 429 et instabilité).
3. **La reprise (idempotence + checkpointing)** : sauvegarder le résultat de chaque unité au fur et à mesure, et pouvoir REPRENDRE après un plantage sans retraiter (donc re-payer) ce qui est déjà fait. C'est l'idempotence de l'ETL (mois 6) et de la ré-ingestion (jour 223), appliquée à l'orchestration LLM — un traitement de 50 000 documents DOIT être reprenable, sinon un plantage à 90 % coûte tout.
4. **Le budget** : estimer le coût AVANT (nombre d'unités × coût par unité, jour 285), le PLAFONNER (arrêt si dépassement), et le SUIVRE pendant (coût cumulé loggé). Un traitement à l'échelle sans budget est une facture surprise qui attend.

La conception du jour — orchestrer « l'analyse de 500 documents » — n'est pas du code jetable mais une ARCHITECTURE : un schéma qui montre le découpage, la file de travail, la parallélisation bornée, le checkpointing pour la reprise, et le suivi de budget. C'est exactement le type de conception qu'on demande en entretien system design (« comment traiteriez-vous un million de documents ? ») — et la réponse mûre parle de reprise, de concurrence bornée et de budget, pas juste de « une boucle qui appelle le LLM ».

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : concevoir l'orchestration « analyse de 500 documents » (schéma + composants).

**Exemple simple** : le cœur de la reprise en une idée — avant de traiter un document, vérifier s'il est déjà dans les résultats sauvegardés ; si oui, sauter. Un plantage devient un non-événement.

**Raisonnement pas-à-pas** : découper en unités → file → parallélisation bornée → checkpoint par unité → budget suivi ; le schéma prime sur le code.

**L'architecture** :
```
[500 docs] → file de travail (unités indépendantes, id stable = hash)
     │
[pool de N workers] (concurrence BORNÉE, ex. N=5 → pas de 429)
     │  chaque worker : traiter(doc) → sauver_resultat(id, res)  ← checkpoint
     │  échec (429/timeout) → retry avec backoff (composant j.214)
     │  échec définitif → journal, on CONTINUE (un doc perdu ≠ tout perdu)
     ▼
[résultats partiels persistés]  → REPRISE : au relancement, sauter les id déjà faits
[budget] : coût estimé avant (500 × coût/doc) ; plafond ; coût cumulé loggé ; arrêt si dépassé
```
```python
async def orchestrer(docs, concurrence=5, budget_max=10.0):
    faits = charger_resultats()                        # REPRISE
    sem = asyncio.Semaphore(concurrence)               # parallélisation BORNÉE
    async def traiter_un(doc):
        if doc.id in faits: return                     # idempotence
        async with sem:
            res = await avec_retry(analyser, doc)      # retry/backoff (j.214)
            sauver_resultat(doc.id, res)               # CHECKPOINT immédiat
            if cout_cumule() > budget_max: raise BudgetDepasse()
    await gather(*[traiter_un(d) for d in docs])
```

**Mini-quiz** : (a) Pourquoi borner la concurrence ? (b) Que garantit le checkpoint par unité ? (c) Que se passe-t-il sans budget plafonné à l'échelle ?
→ (a) 500 appels simultanés → rate limits (429), coût d'un coup, instabilité ; (b) la reprise sans retraiter (donc sans re-payer) après un plantage ; (c) une facture surprise, potentiellement énorme, découverte trop tard.

**Variante** : estime le coût et la durée de ton orchestration AVANT de la lancer (500 × coût/doc, 500 / concurrence × latence/doc), lance sur 50 docs, extrapole, et compare au réel — c'est le réflexe de dimensionnement du jour 228.

## 🏢 Cas métier
Traiter un gros corpus avec des LLM (classifier 100 000 tickets, analyser tous les contrats d'une entreprise) est un besoin fréquent — et un champ de mines pour qui n'orchestre pas : sans reprise, un plantage à 95 % coûte tout ; sans concurrence bornée, les rate limits font échouer la moitié des appels ; sans budget, la facture surprend. Les équipes qui orchestrent proprement (découpage, reprise, concurrence bornée, budget) traitent des millions d'unités de façon fiable ; les autres relancent sans cesse en priant. Cette compétence — la fiabilité à l'échelle — est ce qui sépare un script de démo d'un système de production.

## 🎤 Question d'entretien
**« Comment traiterais-tu 500 000 documents avec un LLM ? »** → Par une orchestration, pas une boucle : découper en unités indépendantes à id stable, un pool de workers à concurrence BORNÉE (sinon rate limits et coût d'un coup), un checkpoint par unité pour la REPRISE (un plantage à 90 % ne doit pas tout perdre — idempotence : sauter les unités déjà faites), retry avec backoff sur les erreurs transitoires, un journal pour les échecs définitifs (on continue), et un budget estimé avant / plafonné / suivi pendant. La réponse mûre parle de reprise, concurrence bornée et budget — pas juste d'appeler le LLM en boucle.
