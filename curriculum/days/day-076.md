# Jour 76 — Modularité et API design : concevoir des interfaces propres

## 🎯 Objectif du jour
Concevoir des modules à interfaces claires, comprendre couplage/cohésion, préparer la pensée architecturale.

## 📖 Cours approfondi
**Concepts abordés :** Module et interface · Couplage faible / cohésion forte · Cacher l'implémentation · API design (contrat) · Dépendances.

Deux mesures gouvernent la qualité d'un découpage en modules : le COUPLAGE (à quel point les modules dépendent les uns des autres — à minimiser) et la COHÉSION (à quel point le contenu d'un module va ensemble — à maximiser). Le symptôme du couplage fort : changer une chose oblige à toucher cinq fichiers.

Un bon module CACHE son implémentation derrière une interface minimale : le reste du monde connaît le contrat (les fonctions exposées), jamais les détails (la structure interne, la lib utilisée). Ton interface Store (jour 44), ton module api.ts : même principe. Ce qui est caché peut changer librement ; ce qui est exposé est un engagement.

Le graphe de dépendances rend le design VISIBLE : les flèches doivent aller dans un sens (vers le bas, vers le stable), jamais en cercle (A→B→A = les deux modules n'en sont qu'un, déguisé).

## ✍️ Pratique autonome
> **D'abord sans IA.** Tente seul au moins 30 minutes. Ne copie-colle jamais une réponse d'IA : lis, ferme, réécris de mémoire.

### Exercice principal
Prends un projet et découpe-le en modules à interfaces explicites : chaque module expose un contrat minimal et cache son implémentation. Dessine le graphe de dépendances. Réduis le couplage là où c'est possible.

## 📦 Livrable attendu
Un projet remodularisé + graphe de dépendances avant/après.

## ✅ Critères de validation
- [ ] Le graphe de dépendances avant/après est dessiné et le couplage a diminué (moins de flèches, pas de cycle)
- [ ] Chaque module expose une interface minimale documentée
- [ ] Le test : changer l'implémentation d'un module ne casse aucun autre (essayé sur un cas)

## ⚠️ Erreurs fréquentes
- Modules qui exposent tout (pas d'encapsulation).
- Dépendances circulaires (A→B→A).

## 🎤 Question d'entretien
**« Conçois un système pour {besoin} — monolithe ou microservices ? »** → Clarifier les besoins/volumes AVANT ; par défaut monolithe modulaire (le distribué coûte cher en complexité) ; isoler ce qui change derrière des interfaces ; anticiper échelle et pannes. Justifier en trade-offs, pas en mode.
