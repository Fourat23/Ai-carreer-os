# Jour 292 — Design patterns dans ton code

[← Dashboard](../../) · [Semaine 42](../week-42.md) · [Mois 10](../month-10.md) · [Correction](../solutions/day-292-solution.md)

## 🎯 Objectif du jour
Reconnaître les patterns.

## 📖 Cours approfondi
**Modèle mental : les design patterns sont un VOCABULAIRE partagé pour des solutions récurrentes — les reconnaître dans TON code te fait passer de « j'ai bricolé ça » à « c'est une Strategy », et nommer un problème est le premier pas pour en parler et l'améliorer.** Après les grandes structures (hexagonal, monolithe), tu descends au niveau du code : quels patterns as-tu déjà utilisés sans les nommer, et quels ANTI-patterns as-tu introduits sans t'en rendre compte ? Ce jour développe l'œil qui reconnaît les structures — une compétence de communication (parler d'architecture avec des mots partagés) autant que de conception.

Les patterns que tu as PROBABLEMENT déjà utilisés (à identifier dans ton code) :
1. **Strategy** : encapsuler des algorithmes interchangeables derrière une interface commune. Tes adapters (jour 289) en sont : `StockageVecteurs` avec Chroma vs mémoire est une Strategy. Tes stratégies de chunking (jour 240) aussi.
2. **Adapter** : convertir une interface en une autre attendue. Littéralement tes ports & adapters (289).
3. **Factory** : centraliser la création d'objets (ta racine de composition qui câble les adapters).
4. **Decorator** : envelopper un objet pour ajouter un comportement. Ton `llm_call` avec cache (284) ou retry (214) DÉCORE l'appel de base.
5. **Repository** : abstraire l'accès aux données derrière une interface métier (ton port de stockage).

Les ANTI-patterns à traquer chez toi :
1. **God object/function** : une classe ou fonction qui fait trop (un `main` de 300 lignes, un module qui touche à tout). Symptôme : impossible à tester en isolation, difficile à nommer.
2. **Couplage fort** : un module qui importe les détails d'un autre (le cœur qui importe chromadb — la contamination du jour 288).
3. **Duplication non factorisée**, **nombres magiques**, **conditions imbriquées profondes**, **primitive obsession**...

Pourquoi c'est utile et pas académique : nommer un pattern permet d'en PARLER (« ici j'ai mis une Strategy pour rendre le chunking interchangeable » est instantanément compris en revue de code) et nommer un anti-pattern permet de le CIBLER (« ce God object devrait être décomposé »). La compétence n'est pas de mémoriser les 23 patterns du GoF mais de RECONNAÎTRE les structures dans du vrai code — le tien d'abord. Un ingénieur qui dit « c'est un Decorator » ou « c'est un God object à décomposer » communique en architecture ; celui qui n'a pas le vocabulaire décrit laborieusement sans se faire comprendre.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : identifier 5 patterns dans ton propre code et 2 anti-patterns, les nommer.

**Exemple simple** : ouvre ton `llm_call` avec cache (jour 284) — l'appel de base est enveloppé pour ajouter le cache SANS changer sa signature. C'est un Decorator. Tu l'avais fait sans le nommer.

**Raisonnement pas-à-pas** : parcourir ton code réel, reconnaître les structures récurrentes, les nommer, et traquer honnêtement les anti-patterns.

**La grille (livrable)** :
```
PATTERNS chez moi (fichier → pattern → ce qu'il apporte) :
  adapters vector store (j.289)    → Strategy/Adapter → interchangeabilité
  racine de composition (j.289)    → Factory → création centralisée
  llm_call + cache/retry (j.214/284)→ Decorator → comportement ajouté sans modif
  port de stockage (j.288)         → Repository → accès données abstrait
  routage de workflow (j.282)      → Strategy → traitement selon la catégorie
ANTI-PATTERNS chez moi (honnête !) :
  1. [ex. un module orchestrateur de 250 lignes qui fait tout] → God object
     → à décomposer en responsabilités séparées
  2. [ex. une valeur 0.45 (seuil de refus) en dur à 3 endroits] → nombre magique
     → à extraire en constante nommée configurable
```

**Mini-quiz** : (a) À quoi sert de NOMMER un pattern qu'on a déjà utilisé ? (b) Ton cache autour de llm_call, quel pattern ? (c) Quel est le symptôme d'un God object ?
→ (a) à en PARLER (vocabulaire partagé en revue) et à raisonner dessus ; (b) Decorator (enveloppe pour ajouter un comportement) ; (c) il fait trop, impossible à tester en isolation, difficile à nommer d'un mot.

**Variante** : pour chaque anti-pattern identifié, écris la refactorisation (décomposer le God object, extraire le nombre magique) — reconnaître sans corriger ne rend pas le code meilleur. Corrige au moins un.

## ⚠️ Erreurs fréquentes
- Réciter les 23 patterns du GoF sans exemple : la compétence est de les RECONNAÎTRE dans du vrai code, à commencer par le tien.
- Forcer un pattern là où il n'y en a pas (« pattern-itis ») : tout n'est pas un pattern, et sur-appliquer les patterns crée de la complexité gratuite.
- Identifier les anti-patterns sans les corriger : reconnaître un God object sans le décomposer ne rend pas le code meilleur.
- Confondre pattern et framework : un pattern est une STRUCTURE de code, pas une bibliothèque à importer.

## 🏢 Cas métier
Le vocabulaire des design patterns est l'outil de communication des équipes de développement : en revue de code, « extrais une Strategy ici » ou « ce God object doit être décomposé » transmet une intention complexe en trois mots, instantanément compris. Un développeur sans ce vocabulaire décrit laborieusement (« euh, tu pourrais faire une classe qui... et une autre qui... ») et se fait mal comprendre. Reconnaître les patterns dans le code existant (et les anti-patterns dans le sien) est une compétence de collaboration directement observable en entretien technique et en revue — elle signale que tu penses en structures, pas en lignes.

## 🎤 Question d'entretien
**« Quels design patterns utilises-tu, et peux-tu en citer dans ton propre code ? »** → Je préfère les reconnaître dans du vrai code plutôt que réciter le GoF : mes adapters de vector store sont une Strategy/Adapter (interchangeabilité), mon llm_call avec cache est un Decorator (comportement ajouté sans modifier l'appel), ma racine de composition est une Factory, mon port de stockage un Repository. Et je traque mes propres anti-patterns : un orchestrateur qui faisait trop (God object, à décomposer), un seuil en dur répété (nombre magique, à extraire). Nommer un pattern permet d'en PARLER en revue ; nommer un anti-pattern permet de le CIBLER. La compétence est l'œil qui reconnaît les structures, pas la mémorisation.
