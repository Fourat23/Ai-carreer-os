## 🎯 Objectif du jour
Ingérer la source.

## 📖 Cours approfondi
**Modèle mental : extraire, c'est capturer la source TELLE QUELLE en gérant ses défaillances PROPRES (fichier absent, API qui limite ou tombe, format inattendu, encodage) — une extraction robuste ne suppose JAMAIS que la source est disponible et bien formée, parce qu'en réalité elle ne l'est pas toujours.** C'est l'étape « E » du pipeline (jour 138) appliquée à ta vraie source DataPulse. Sa seule responsabilité : ramener les données brutes, fidèlement, en survivant aux problèmes de source — sans nettoyer (ça, c'est le transform).

Ce que l'extraction doit gérer (le réel) :
1. **La disponibilité** : la source peut être absente (fichier déplacé) ou injoignable (API en panne, réseau coupé). On gère avec les exceptions spécifiques (jour 122) : `FileNotFoundError`, timeout, erreur HTTP — et on échoue avec un message clair, pas une trace obscure.
2. **Les limites d'API** : une API publique impose souvent un débit (rate limit) ou une pagination. Extraire proprement, c'est respecter ces limites (attendre, paginer) et gérer le cas où l'API renvoie une erreur temporaire (un retry avec backoff pour les erreurs transitoires — pas pour un 404).
3. **Le format et l'encodage** : un CSV peut avoir un séparateur inattendu, un encodage non-UTF-8, des colonnes en trop ou manquantes. On capture le brut et on vérifie sa FORME minimale (les colonnes attendues sont-elles là ?) — la validation approfondie viendra au transform, mais un contrôle de forme à l'extraction attrape tôt une source qui a changé.
4. **La fidélité** : on extrait SANS transformer. Mélanger extraction et nettoyage empêche de rejouer le traitement sans re-télécharger (jour 138) — d'où l'intérêt de matérialiser le brut (staging) pour développer le transform sans rappeler la source.

Le piège du « ça marche sur ma source du jour » : une extraction testée une fois sur un fichier parfait cassera dès que la source réelle aura un jour sans données, une ligne malformée, ou une API qui expire. Concevoir l'extraction, c'est anticiper ces défaillances.

La règle du jour : **extrais la source fidèlement (sans transformer), gère ses défaillances propres (indisponibilité, limites d'API, format), échoue clairement, et matérialise le brut pour rejouer la suite sans re-télécharger**. Une extraction robuste transforme une source capricieuse en une entrée fiable pour le reste du pipeline.

**Énoncé** : implémenter l'extraction de DataPulse (CSV/API) avec gestion des erreurs de source.

**Exemple simple** : le contrôle de forme minimal, tôt — après lecture, `assert set(ATTENDUES) <= set(df.columns), "la source a changé de schéma"`. Il attrape immédiatement une source dont les colonnes ont bougé, avant que le pipeline ne parte de travers.

**Raisonnement pas-à-pas** : tenter la lecture/l'appel → rattraper les défaillances de source spécifiques → vérifier la forme minimale → matérialiser le brut (staging).

**Implémentation** :
```python
import pandas as pd, requests, time, logging
from pathlib import Path

def extract_api(url: str, essais: int = 3) -> list[dict]:
    for i in range(essais):
        try:
            r = requests.get(url, timeout=10)
            if r.status_code == 429:                      # rate limit : attendre et réessayer
                time.sleep(2 ** i); continue              # backoff exponentiel
            r.raise_for_status()                          # 4xx/5xx → exception
            return r.json()
        except requests.Timeout:
            logging.warning("Timeout, essai %d/%d", i + 1, essais)
    raise RuntimeError(f"Source injoignable après {essais} essais : {url}")

def extract_csv(chemin: str) -> pd.DataFrame:
    try:
        df = pd.read_csv(chemin, encoding="utf-8")
    except FileNotFoundError:
        raise RuntimeError(f"Source absente : {chemin}")   # message clair (jour 122)
    ATTENDUES = {"date", "station", "valeur"}
    if not ATTENDUES <= set(df.columns):                  # contrôle de FORME tôt
        raise ValueError(f"Colonnes manquantes : {ATTENDUES - set(df.columns)}")
    df.to_parquet("staging/brut.parquet")                 # staging : rejouer transform sans re-DL
    return df
```

**Mini-quiz** : (a) L'extraction doit-elle nettoyer les données ? (b) Comment gérer une API qui renvoie 429 (rate limit) ? (c) Pourquoi matérialiser le brut ?
→ (a) non — elle capture le brut fidèlement ; le nettoyage est le rôle du transform ; (b) attendre (backoff) et réessayer, car c'est une erreur transitoire (contrairement à un 404, définitif) ; (c) pour rejouer le transform sans re-télécharger, et développer/déboguer sans dépendre de la source.

**Variante** : coupe le réseau (ou pointe vers une URL invalide) et vérifie que ton extraction échoue avec un message CLAIR (« source injoignable »), pas une trace obscure — c'est la preuve qu'elle gère l'indisponibilité réelle.

## 🏢 Cas métier
L'extraction est le point de contact avec le monde extérieur, donc le plus exposé aux défaillances : en production, les sources tombent, les API limitent le débit ou changent de schéma, les fichiers arrivent malformés. Une extraction naïve qui suppose la source parfaite casse au premier incident et laisse le pipeline sans diagnostic. Les data engineers conçoivent l'extraction pour l'échec — retry sur erreurs transitoires, respect des rate limits, contrôle de forme tôt, message clair sur indisponibilité, staging pour rejouer. Cette robustesse à la frontière est ce qui rend un pipeline exploitable au quotidien, et sa gestion des erreurs de source est directement évaluée : elle montre qu'on a anticipé le réel, pas seulement le cas idéal du fichier de démo.

## 🎤 Question d'entretien
**« Comment rends-tu robuste l'extraction d'un pipeline ? »** → Sa responsabilité unique est de capturer la source TELLE QUELLE, sans transformer, en survivant à ses défaillances propres. Je gère la disponibilité (fichier absent, API injoignable) avec des exceptions spécifiques et un message clair, pas une trace obscure. Pour une API, je respecte les rate limits et je fais un retry avec backoff sur les erreurs TRANSITOIRES (429, timeout) mais pas sur un 404 définitif. Je contrôle la FORME minimale tôt (les colonnes attendues sont-elles là ?) pour attraper une source qui a changé de schéma. Et je matérialise le brut dans un staging pour rejouer le transform sans re-télécharger. Le piège que j'évite : l'extraction testée une fois sur un fichier parfait, qui casse dès que la source réelle a un jour vide ou une ligne malformée. Je conçois pour l'échec, pas pour le cas idéal.
