## 🎯 Objectif du jour
Ne jamais casser l'UI.

## 📖 Cours approfondi
**Modèle mental : une UI robuste ne se contente pas d'afficher les données — elle prévoit CHAQUE façon dont ça peut rater et dégrade PROPREMENT au lieu de montrer un écran blanc. Et il existe deux familles d'erreurs distinctes qui demandent deux parades différentes.** Depuis le jour 95 tu gères l'erreur d'un fetch (état 'error'). Aujourd'hui tu généralises : une application entière ne doit JAMAIS casser sans rien dire. Un écran blanc est le pire échec UX — l'utilisateur ne sait ni ce qui s'est passé ni quoi faire.

Les deux familles d'erreurs et leurs parades :
1. **Les erreurs ATTENDUES (asynchrones)** : un appel réseau échoue (500, timeout, hors ligne). Elles se gèrent avec l'état 'error' (jour 95) et un message + un bouton « réessayer ». Elles sont prévisibles : tu SAIS que le réseau peut tomber, donc tu codes le chemin d'erreur explicitement. Un `try/catch` autour de l'appel suffit.
2. **Les erreurs INATTENDUES (exceptions de rendu)** : un composant lève une exception pendant son rendu (une propriété `undefined` lue, un bug). Un `try/catch` ne peut PAS les attraper — elles surviennent DANS le rendu de React, hors de ton flux d'exécution. C'est le rôle de l'**error boundary** : un composant spécial qui ENVELOPPE une partie de l'arbre, attrape toute exception de rendu de ses enfants, et affiche une UI de repli au lieu de laisser toute l'app planter en écran blanc.

Les principes d'une app résiliente :
- **Chaque zone risquée est enveloppée** d'une error boundary, avec une granularité réfléchie : une boundary par section importante (pas une seule pour toute l'app, sinon une erreur dans un widget tue tout l'écran).
- **Chaque état non-heureux est traité** : loading, error, empty — partout, pas seulement sur l'écran principal.
- **L'erreur offre une SORTIE** : réessayer, revenir, contacter — jamais un cul-de-sac.
- **On PROVOQUE les erreurs pour tester la résilience** : casser volontairement (couper le réseau, forcer une exception) et vérifier que l'app dégrade proprement — la même démarche que le red teaming ou le sabotage des tests (jour 106).

La règle du jour : **une UI professionnelle ne peut pas montrer d'écran blanc ; toute erreur, attendue ou non, mène à un état lisible avec une issue**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : rendre l'app résiliente — error boundary + états d'erreur soignés + retry, prouvé en cassant l'app.

**Exemple simple** : l'error boundary attrape ce qu'un try/catch ne peut pas — une exception PENDANT le rendu. `<ErrorBoundary fallback={<Repli/>}><SectionRisquée/></ErrorBoundary>` : si `SectionRisquée` plante, l'utilisateur voit `Repli`, pas un écran blanc.

**Raisonnement pas-à-pas** : distinguer erreur async (try/catch + état error) et exception de rendu (error boundary) → envelopper chaque section → offrir une sortie (réessayer) → PROVOQUER les deux pour vérifier.

**Solution** :
```tsx
class ErrorBoundary extends React.Component<{ fallback: React.ReactNode; children: React.ReactNode }, { crash: boolean }> {
  state = { crash: false };
  static getDerivedStateFromError() { return { crash: true }; }   // attrape l'exception de rendu
  componentDidCatch(err: Error) { console.error('Crash UI :', err); } // journalise (jour 111 → prod)
  render() { return this.state.crash ? this.props.fallback : this.props.children; }
}

// Erreur ATTENDUE (async) : état 'error' + retry (jour 95)
function Section() {
  const etat = useFetch<Livre[]>('/livres');                       // hook du jour 110
  if (etat.s === 'err') return <MessageErreur onRetry={/* relance */ () => {}} />;
  /* ... */
}
// Erreur INATTENDUE (rendu) : enveloppée par la boundary
// <ErrorBoundary fallback={<Repli/>}><Section/></ErrorBoundary>
```

**Mini-quiz** : (a) Pourquoi un try/catch ne suffit-il pas pour toutes les erreurs React ? (b) Quelle granularité pour les error boundaries ? (c) Comment prouver que l'app est résiliente ?
→ (a) il n'attrape pas les exceptions levées PENDANT le rendu de React — c'est le rôle de l'error boundary ; (b) une par section importante, pas une seule pour toute l'app (sinon un widget cassé tue tout l'écran) ; (c) en cassant volontairement (couper le réseau, forcer une exception) et en vérifiant la dégradation propre.

**Variante** : ajoute un composant qui lève une exception au clic (`throw new Error()`) dans une section, et vérifie que SEULE cette section montre le repli, le reste de l'app restant utilisable — la preuve d'une bonne granularité.

## ⚠️ Erreurs fréquentes
- Croire qu'un try/catch attrape les exceptions de rendu : il ne le fait pas — c'est le rôle des error boundaries.
- Une seule error boundary pour toute l'app : un widget cassé fait tomber tout l'écran — une par section.
- Laisser des culs-de-sac (erreur sans bouton réessayer/retour) : l'utilisateur est bloqué.
- Ne pas provoquer les erreurs : sans les tester volontairement, on ne sait pas si la dégradation est réellement propre.

## 🏢 Cas métier
L'écran blanc — l'app qui plante entièrement à cause d'une exception dans un composant — est un incident de production classique et coûteux : une seule propriété `undefined` non prévue peut rendre toute l'interface inutilisable. Les error boundaries, placées par section, contiennent le dégât : un widget cassé affiche un repli local, le reste de l'app continue de fonctionner. Les équipes sérieuses journalisent aussi ces crashs (componentDidCatch → outil de suivi) pour les corriger. Combiné au traitement systématique des états loading/error/empty et à une sortie sur chaque erreur, cela distingue une app « qui marche en démo » d'une app « qui tient en production ». Cette robustesse est directement observable et valorisée.

## 🎤 Question d'entretien
**« Comment rends-tu une application React robuste aux erreurs ? »** → Je distingue deux familles. Les erreurs ATTENDUES (async : réseau qui échoue) se gèrent avec un état 'error' explicite, un message et un bouton réessayer — je code le chemin d'erreur car je SAIS que le réseau peut tomber. Les erreurs INATTENDUES (exceptions levées pendant le rendu) ne peuvent PAS être attrapées par un try/catch ; j'utilise des error boundaries — des composants qui enveloppent une section, attrapent l'exception de ses enfants et affichent un repli au lieu d'un écran blanc. Je place une boundary par section importante (granularité) pour qu'un widget cassé ne tue pas tout l'écran, je journalise les crashs, et je PROUVE la résilience en cassant volontairement l'app. Règle : jamais d'écran blanc, toute erreur mène à un état lisible avec une issue.
