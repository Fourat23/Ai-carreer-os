## 🎯 Objectif du jour
Jointures de données.

## 📖 Cours approfondi
**Modèle mental : un `merge` JOINT deux tables sur une CLÉ commune, et le TYPE de jointure (inner/left/right/outer) décide QUOI FAIRE des lignes sans correspondance — le vrai risque n'est pas la syntaxe mais les lignes qu'on PERD ou qu'on DUPLIQUE silencieusement.** Joindre deux sources (des ventes + un référentiel produits, des utilisateurs + leurs commandes) est une opération de tous les jours. La difficulté n'est pas d'écrire `pd.merge` : c'est de comprendre ce qu'il advient des lignes qui n'ont PAS de correspondance, et de VÉRIFIER que le résultat a le nombre de lignes attendu.

Les types de jointure — la décision centrale :
1. **`inner` (défaut)** : ne garde que les lignes présentes des DEUX côtés. Les lignes sans correspondance sont SILENCIEUSEMENT perdues — un piège si tu ne l'attends pas (des ventes dont le produit n'est pas dans le référentiel disparaissent).
2. **`left`** : garde TOUTES les lignes de gauche, complète avec la droite quand possible (NaN sinon). C'est le choix quand la table de gauche est la référence à préserver (toutes les ventes, enrichies du produit si connu).
3. **`outer`** : garde toutes les lignes des deux côtés. Utile pour un audit de correspondance (qui n'a pas de match ?).
4. **`right`** : symétrique de left, rarement nécessaire (on inverse les tables).

Les deux pièges qui coûtent cher :
- **La perte silencieuse** : un `inner` qui élimine des lignes attendues. TOUJOURS comparer `len` avant/après et se demander « ai-je perdu des lignes, et est-ce normal ? ».
- **La duplication (one-to-many mal maîtrisé)** : si la clé n'est pas unique du côté droit, chaque ligne de gauche est DUPLIQUÉE pour chaque correspondance — le nombre de lignes EXPLOSE. Le paramètre `validate="many_to_one"` fait ÉCHOUER le merge si la relation n'est pas celle attendue : un garde-fou qui attrape ce bug tôt.

La clé doit aussi être PROPRE : mêmes types des deux côtés (un id en `int` d'un côté, en `str` de l'autre ne matchera jamais), casse et espaces normalisés (jour 128). Une clé sale = zéro correspondance sans erreur.

La règle du jour : **choisis le type de jointure selon ce que tu veux faire des non-correspondances, VÉRIFIE le nombre de lignes avant/après, et protège la cardinalité avec `validate` ; une clé doit être propre et de même type des deux côtés**. Le merge est facile à écrire et facile à se tromper silencieusement — la vérification EST le travail.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : merger 2+ sources, gérer les clés manquantes, et VALIDER le résultat.

**Exemple simple** : le garde-fou de cardinalité — `pd.merge(ventes, produits, on="produit_id", validate="many_to_one")`. Il fait échouer le merge si un `produit_id` apparaît plusieurs fois côté produits (ce qui dupliquerait les ventes). Un merge sans `validate` est un merge à surveiller.

**Raisonnement pas-à-pas** : vérifier les clés (types, propreté) → choisir le type de jointure selon les non-correspondances voulues → merger avec `validate` → COMPARER les tailles avant/après.

**Implémentation** :
```python
import pandas as pd
ventes = pd.read_csv("ventes.csv")
produits = pd.read_csv("produits.csv")

# 1. Clés propres et de MÊME type des deux côtés (sinon zéro match silencieux)
ventes["produit_id"] = ventes["produit_id"].astype(str).str.strip()
produits["produit_id"] = produits["produit_id"].astype(str).str.strip()

# 2. left : garder TOUTES les ventes, enrichir du produit si connu
enrichi = pd.merge(ventes, produits, on="produit_id", how="left",
                   validate="many_to_one")   # garde-fou : 1 produit par vente max

# 3. VALIDER : ai-je perdu ou dupliqué des lignes ?
assert len(enrichi) == len(ventes), "le merge a changé le nombre de ventes !"
sans_produit = enrichi["nom_produit"].isna().sum()   # ventes sans produit référencé
print(f"{sans_produit} ventes sans produit correspondant (à investiguer)")
```

**Mini-quiz** : (a) Que deviennent les lignes sans correspondance avec un `inner` ? (b) Comment un merge peut-il faire EXPLOSER le nombre de lignes ? (c) À quoi sert `validate` ?
→ (a) elles sont silencieusement supprimées — piège si non attendu ; (b) si la clé n'est pas unique côté droit, chaque ligne de gauche est dupliquée par correspondance (one-to-many) ; (c) faire échouer le merge si la cardinalité réelle n'est pas celle attendue (garde-fou contre la duplication).

**Variante** : fais volontairement un merge sur une clé de types différents (int vs str) et observe que le résultat est vide malgré des valeurs identiques à l'œil — la preuve qu'une clé doit être de même type des deux côtés.

## 🏢 Cas métier
Joindre des sources est au cœur de tout travail data (enrichir des transactions avec un référentiel, croiser des utilisateurs et leur activité), et les bugs de merge sont parmi les plus insidieux car ILS NE PLANTENT PAS : un `inner` qui perd 15% des lignes attendues, ou une clé dupliquée qui triple le chiffre d'affaires par duplication. Une analyse ou un rapport bâti sur un merge mal maîtrisé donne des chiffres FAUX qui paraissent plausibles. Les data engineers expérimentés vérifient systématiquement la cardinalité (`validate`) et le nombre de lignes avant/après, précisément parce que l'erreur est silencieuse. ## 🎤 Question d'entretien
**« Quels sont les pièges d'un merge en pandas, et comment les évites-tu ? »** → Deux pièges, tous deux SILENCIEUX. D'abord la perte de lignes : un `inner` (le défaut) ne garde que ce qui matche des deux côtés, donc élimine sans avertir les lignes sans correspondance — je choisis `left` quand je veux préserver la table de référence. Ensuite la DUPLICATION : si la clé n'est pas unique côté droit, chaque ligne de gauche est dupliquée par correspondance (one-to-many), et le nombre de lignes explose — un CA qui triple silencieusement. Je m'en protège avec `validate="many_to_one"` qui fait échouer le merge si la cardinalité n'est pas celle attendue, et je COMPARE toujours `len` avant/après. Enfin, je m'assure que la clé est propre et de même type des deux côtés, sinon zéro correspondance sans erreur. La vérification EST le travail.
