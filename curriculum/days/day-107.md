## 🎯 Objectif du jour
Tester le comportement, pas l'implémentation.

## 📖 Cours approfondi
**Modèle mental : on teste ce que l'UTILISATEUR voit et fait (un texte à l'écran, un clic sur un bouton, un rôle accessible) — PAS l'implémentation interne (le nom du state, la structure des composants). Un test couplé à l'implémentation casse à chaque refactor sans détecter aucun vrai bug.** C'est le principe fondateur de Testing Library : « plus tes tests ressemblent à la façon dont l'utilisateur se sert de ton app, plus ils te donnent confiance ». Tu ne vérifies pas « le state `ouvert` vaut `true` » ; tu vérifies « le menu est visible à l'écran ».

Les trois gestes du test de composant :
1. **Rendre** le composant dans un DOM virtuel (`render(<X/>)`).
2. **Trouver** les éléments comme un utilisateur : par leur rôle, leur label, leur texte (`getByRole('button', { name: 'Ajouter' })`, `getByText`) — PAS par une classe CSS ou un id technique. Chercher par rôle pousse en prime vers un HTML accessible (jour 103).
3. **Interagir et vérifier** : simuler un clic ou une saisie (`userEvent.click`), puis affirmer sur ce qui a CHANGÉ à l'écran (`expect(screen.getByText('Ajouté')).toBeVisible()`).

Pourquoi ce principe est décisif : un test couplé à l'implémentation (« le composant `<Modal>` a un state `isOpen`») se casse dès que tu renommes le state ou restructures les composants — alors même que l'app fonctionne parfaitement pour l'utilisateur. Il génère du bruit et décourage le refactor. À l'inverse, un test orienté COMPORTEMENT (« après le clic, la modale apparaît ») survit aux refactors internes et n'échoue que si le comportement RÉEL casse — ce qui est exactement ce qu'on veut d'un test.

La règle du jour : **teste le comportement observable, jamais les détails d'implémentation ; cherche les éléments comme le fait un utilisateur (rôle, label, texte)**. Ce qui teste le comportement résiste au refactor et attrape les vrais bugs ; ce qui teste l'implémentation casse pour rien. C'est la même philosophie que le test d'API par son contrat (mois 3) : on teste l'interface publique, pas la plomberie interne.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : tester trois composants clés par leur comportement, pas leur implémentation.

**Exemple simple** : un test orienté utilisateur — `render(<Compteur/>); await userEvent.click(screen.getByRole('button', { name: '+' })); expect(screen.getByText('1')).toBeVisible();`. On clique comme un humain, on vérifie ce qu'il verrait.

**Raisonnement pas-à-pas** : rendre → trouver par rôle/label/texte → interagir → affirmer sur le DOM visible, jamais sur le state interne.

**Solution** :
```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('le formulaire affiche une erreur si le titre est vide', async () => {
  render(<AjoutLivre onCreer={async () => {}} />);
  await userEvent.click(screen.getByRole('button', { name: /ajouter/i }));
  expect(screen.getByText(/titre est requis/i)).toBeVisible();   // comportement visible
});

test('appelle onCreer avec les valeurs saisies', async () => {
  const onCreer = vi.fn();
  render(<AjoutLivre onCreer={onCreer} />);
  await userEvent.type(screen.getByLabelText(/titre/i), 'React');  // trouvé par LABEL (a11y)
  await userEvent.type(screen.getByLabelText(/auteur/i), 'Dan');
  await userEvent.click(screen.getByRole('button', { name: /ajouter/i }));
  expect(onCreer).toHaveBeenCalledWith({ titre: 'React', auteur: 'Dan' });
});
```

**Mini-quiz** : (a) Pourquoi chercher par rôle/label plutôt que par classe CSS ? (b) Que teste-t-on : le state interne ou le DOM visible ? (c) Pourquoi un test couplé à l'implémentation est-il un problème ?
→ (a) c'est ce que voit l'utilisateur, et ça résiste au refactor tout en poussant vers un HTML accessible ; (b) le DOM visible / le comportement observable ; (c) il casse à chaque refactor interne sans détecter de vrai bug — du bruit qui décourage le refactor.

**Variante** : après avoir écrit ces tests, RENOMME un state interne ou restructure un sous-composant sans changer le comportement — tes tests doivent rester VERTS. S'ils cassent, c'est qu'ils testaient l'implémentation.

## ⚠️ Erreurs fréquentes
- Chercher par classe CSS ou id technique : le test casse dès qu'on change le style ou la structure, sans vrai bug.
- Affirmer sur le state interne au lieu du DOM visible : couplage à l'implémentation, tests fragiles.
- Tester des détails de rendu sans valeur (nombre de divs) plutôt que le comportement utilisateur.
- Oublier d'attendre les interactions asynchrones (userEvent/await) : assertions sur un DOM pas encore à jour.

## 🏢 Cas métier
Le passage d'Enzyme (qui testait l'implémentation : instances, state) à Testing Library (qui teste le comportement) dans l'écosystème React illustre exactement ce principe à l'échelle de l'industrie : les équipes ont adopté « teste comme l'utilisateur » parce que les tests couplés à l'implémentation coûtaient plus qu'ils ne rapportaient — ils cassaient à chaque refactor sans attraper de bugs. Aujourd'hui, tester par rôle/label/texte est le standard, et c'est ce qu'un employeur attend. Bonus notable : comme on cherche les éléments par leur rôle accessible, écrire de bons tests POUSSE naturellement vers une UI accessible — les deux compétences se renforcent.

## 🎤 Question d'entretien
**« Comment testes-tu un composant React, et que veut dire 'tester le comportement pas l'implémentation' ? »** → Je rends le composant, je trouve les éléments comme un UTILISATEUR le ferait (par rôle, label ou texte — pas par classe CSS ni id technique), j'interagis (clic, saisie) et j'affirme sur ce qui change À L'ÉCRAN. « Tester le comportement » signifie vérifier ce que l'utilisateur voit et fait (« après le clic, la modale apparaît »), pas les détails internes (« le state `isOpen` vaut true »). Un test couplé à l'implémentation casse à chaque refactor sans détecter de vrai bug ; un test orienté comportement survit aux refactors et n'échoue que si le comportement réel casse. Effet de bord vertueux : chercher par rôle pousse vers un HTML accessible.
