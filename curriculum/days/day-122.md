## 🎯 Objectif du jour

## 📖 Cours approfondi
**Modèle mental : en Python, on demande PARDON plutôt que la permission (EAFP : « Easier to Ask Forgiveness than Permission ») — on TENTE l'opération et on rattrape l'exception SPÉCIFIQUE, au lieu de tout vérifier avant (LBYL, « Look Before You Leap »). Une exception non rattrapée n'est pas un bug, c'est un signal ; le vrai danger, c'est de rattraper trop large et de masquer les vrais bugs.** Rendre un programme robuste, ce n'est pas empêcher toute erreur, c'est prévoir COMMENT il réagit quand une opération prévisible échoue (fichier absent, JSON corrompu, entrée invalide).

Les mécanismes des exceptions Python :
1. **`try / except SpécifiqueError`** : on rattrape le TYPE précis d'erreur attendu (`FileNotFoundError`, `json.JSONDecodeError`, `ValueError`), jamais un `except:` nu qui avale TOUT — y compris les bugs de programmation et l'interruption clavier. Rattraper spécifiquement, c'est traiter le cas qu'on a prévu et laisser remonter ce qu'on n'a pas prévu.
2. **`else` et `finally`** : `else` s'exécute si AUCUNE exception (le chemin heureux, séparé du try), `finally` s'exécute TOUJOURS (nettoyage). C'est plus expressif que le `try/catch` de JS, qui n'a pas de `else`.
3. **`raise`** : lever une exception soi-même quand une précondition est violée (`raise ValueError("le montant doit être positif")`). On échoue TÔT et FORT plutôt que de propager une donnée invalide.
4. **Les exceptions personnalisées** : `class NoteInvalideError(Exception)` pour les erreurs MÉTIER, distinctes des erreurs techniques. L'appelant peut alors rattraper précisément « erreur métier » sans confondre avec un bug.

La hiérarchie compte : toutes les exceptions héritent de `Exception`. Rattraper `Exception` est parfois légitime (à une frontière, pour journaliser et re-lever), mais rattraper le type le plus SPÉCIFIQUE possible est la règle : ça documente ce qu'on attend et laisse les surprises remonter.

La règle du jour : **tente, rattrape le type SPÉCIFIQUE, échoue tôt avec `raise` sur une précondition violée, et ne masque jamais un bug avec un `except` trop large**. Un programme robuste transforme chaque échec prévisible en message clair pour l'utilisateur, et laisse les vrais bugs remonter pour être corrigés — jamais l'inverse.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : ajouter une gestion d'exceptions complète à la CLI `notes` (fichier absent, JSON corrompu, entrées invalides).

**Exemple simple** : le contraste EAFP vs LBYL — au lieu de `if FICHIER.exists(): ... else: ...` (LBYL, sujet aux courses), on écrit `try: with open(...): ... except FileNotFoundError: return []` (EAFP). On tente, on rattrape le cas précis.

**Raisonnement pas-à-pas** : identifier chaque opération faillible (lire, parser, valider) → rattraper le type SPÉCIFIQUE de chacune → traduire en message clair → lever soi-même sur une précondition métier violée.

**Implémentation** :
```python
import json
from pathlib import Path

class NoteInvalideError(Exception):   # erreur MÉTIER, distincte des erreurs techniques
    pass

def charger(fichier: Path) -> list[dict]:
    try:
        with fichier.open(encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError:                 # cas prévu 1 : première utilisation
        return []
    except json.JSONDecodeError as e:         # cas prévu 2 : fichier corrompu
        raise NoteInvalideError(f"Fichier de notes corrompu : {e}") from e

def ajouter(notes: list[dict], texte: str) -> list[dict]:
    if not texte.strip():                     # précondition métier
        raise NoteInvalideError("Une note ne peut pas être vide")  # échoue TÔT
    return [*notes, {"id": len(notes) + 1, "texte": texte}]

def main() -> None:
    try:
        notes = charger(Path("notes.json"))
        # ... action ...
    except NoteInvalideError as e:            # frontière : message clair à l'utilisateur
        print(f"Erreur : {e}")
        raise SystemExit(1)                   # code de sortie non nul
```

**Mini-quiz** : (a) Pourquoi éviter un `except:` nu ? (b) Que fait le bloc `else` d'un try ? (c) Quand lever une exception soi-même avec `raise` ?
→ (a) il avale TOUT, y compris les bugs et l'interruption clavier, masquant les vrais problèmes ; (b) il s'exécute si aucune exception n'a été levée (le chemin heureux, séparé du try) ; (c) quand une précondition est violée, pour échouer tôt plutôt que propager une donnée invalide.

**Variante** : ajoute le `raise ... from e` (chaînage d'exceptions) partout où tu retransformes une erreur — la trace conserve alors la cause d'origine, ce qui rend le débogage bien plus facile.

## 🏢 Cas métier
La gestion d'exceptions distingue un script fragile (qui plante avec une trace incompréhensible au premier fichier manquant) d'un outil robuste (qui dit « fichier introuvable, création d'un nouveau »). En entreprise, le bug le plus dangereux est le `except` trop large qui avale silencieusement les erreurs : un pipeline qui « marche » mais produit des données fausses parce qu'il a rattrapé et ignoré une exception qu'il n'aurait pas dû. Les revues de code Python traquent les `except:` nus précisément pour cette raison. Savoir rattraper le type spécifique, échouer tôt avec `raise` sur une précondition, et distinguer erreurs métier et techniques est une compétence de fiabilité directement valorisée — surtout pour des pipelines de données où une erreur masquée corrompt tout en aval.

## 🎤 Question d'entretien
**« Comment gères-tu les erreurs en Python, et pourquoi éviter un `except` trop large ? »** → Je suis le style EAFP : je TENTE l'opération et je rattrape le type SPÉCIFIQUE d'exception attendu (`FileNotFoundError`, `json.JSONDecodeError`, `ValueError`), plutôt que de tout vérifier avant. Un `except:` nu ou un `except Exception` trop large est dangereux : il avale TOUT, y compris les bugs de programmation et l'interruption clavier, ce qui masque les vrais problèmes — le pire cas étant un pipeline qui « marche » mais produit des données fausses. Je rattrape le plus spécifique possible, je laisse remonter ce que je n'ai pas prévu, j'échoue tôt avec `raise` sur une précondition violée, et je distingue les erreurs métier (exceptions personnalisées) des erreurs techniques. J'utilise aussi `raise ... from e` pour conserver la cause d'origine.
