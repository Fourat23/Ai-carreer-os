## 🎯 Objectif du jour
Figer la référence.

## 📖 Cours approfondi
**Modèle mental : la baseline officielle est le POINT ZÉRO immuable de DocSense — le chiffre contre lequel toutes les améliorations du dernier mois se compareront ; sans elle, « v1 est meilleur » n'a aucun sens.** Après le golden set (316), le harnais (317) et le dashboard (318), tu FIGES la référence : une baseline v0 chiffrée, enregistrée, datée, qui capture l'état actuel de DocSense sur toutes les dimensions. C'est le geste méthodologique qui rend tout le travail d'amélioration mesurable et défendable.

Ce qu'une baseline officielle exige (le rappel du jour 267, appliqué à DocSense) :
1. **Le système figé** : la version actuelle de DocSense (config du mois 9 appliquée, retrieval hybride, génération citée), rien ne bouge pendant la mesure. C'est l'état « avant » de référence.
2. **La mesure multidimensionnelle complète** : le harnais sur le golden set → retrieval (rappel@k, MRR), génération (fidélité, pertinence, exactitude) par type, plus latence et coût. La baseline est multidimensionnelle car une amélioration future peut gagner sur une dimension et dégrader une autre — il faut le point de départ sur TOUTES.
3. **L'enregistrement immuable** : la baseline est sauvegardée (config + golden version + date + tous les scores), affichée sur le dashboard comme la première version. Elle ne se retouche JAMAIS — c'est la référence contre laquelle tout se compare. Une baseline mouvante invaliderait toutes les comparaisons.

Pourquoi c'est le geste qui donne du sens à tout le reste : sans baseline, chaque amélioration est une impression (« ça a l'air mieux ») ; avec baseline, chaque amélioration est une mesure (« +4 points de fidélité vs la baseline v0 »). La baseline transforme le travail de qualité en progrès DÉMONTRABLE. Elle est aussi le fondement du rapport final (jour 334) : « voici la baseline, voici les améliorations, voici la trajectoire » est un récit de valeur que seul un point de départ chiffré rend possible. Le piège à éviter absolument : « corriger un petit truc » pendant qu'on établit la baseline — chaque correction invalide le point de comparaison. On mesure l'état existant intact ; on améliore APRÈS.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : la baseline officielle v0 de DocSense, chiffrée, multidimensionnelle, enregistrée.

**Exemple simple** : la baseline est juste un rapport du harnais (jour 317) sur le système ACTUEL, sauvegardé et étiqueté « v0 — référence ». La discipline est de ne plus jamais y toucher.

**Raisonnement pas-à-pas** : figer le système, lancer le harnais complet, enregistrer immuablement, sans rien corriger.

**La baseline (livrable)** :
```
=== BASELINE DocSense v0 — [date] — golden-v1 — config mois 9 ===
RETRIEVAL   rappel@3 0,84 · MRR 0,78
GÉNÉRATION  fidélité 0,86 · pertinence 0,90 · exactitude 0,82
  par type  factuelles 0,90 · reformulées 0,84 · synthèses 0,55 ← point faible
REFUS       hors corpus : refus correct sur X/Y
PERF        p95 2,6s · coût/question 0,007€
→ enregistrée, affichée sur le dashboard comme v0, JAMAIS retouchée
→ chantiers priorisés par faiblesse (synthèses) pour les améliorations (j.334)
```

**Mini-quiz** : (a) Pourquoi la baseline doit-elle être multidimensionnelle ? (b) Pourquoi ne jamais la retoucher ? (c) Quel piège éviter en l'établissant ?
→ (a) une amélioration peut gagner sur une dimension et dégrader une autre — il faut le départ sur toutes ; (b) une baseline mouvante invalide toutes les comparaisons ; (c) « corriger un petit truc » pendant la mesure — chaque correction invalide le point de comparaison.

**Variante** : à partir de la baseline, identifie les 2-3 chantiers d'amélioration prioritaires (les dimensions/types les plus faibles) — la baseline sert autant à mesurer le progrès qu'à PRIORISER où améliorer (jour 334).

## ⚠️ Erreurs fréquentes
- Corriger « un petit truc » pendant la mesure : chaque correction invalide le point de comparaison — mesurer l'état intact.
- Baseline unidimensionnelle (un score) : une amélioration peut gagner ici et dégrader là — mesurer toutes les dimensions.
- Retoucher la baseline plus tard : elle devient mouvante et toutes les comparaisons perdent leur sens — immuable.
- Ne pas enregistrer config/version : une baseline sans contexte n'est pas reproductible ni comparable.

## 🏢 Cas métier
La baseline officielle est le geste méthodologique qui rend un projet ML défendable : sans elle, impossible de justifier le temps investi (« on a amélioré, mais de combien par rapport à quoi ? ») ; avec elle, chaque gain est chiffré et démontrable. En entreprise, un data scientist qui présente « baseline v0 à 0,82, version finale à 0,92, voici la trajectoire » obtient la reconnaissance de son travail ; celui qui dit « c'est mieux maintenant » ne convainc personne. Pour DocSense, la baseline v0 est le point zéro contre lequel tout le mois de qualité se mesurera — et le fondement du rapport final qui prouvera la valeur du projet à un recruteur.

## 🎤 Question d'entretien
**« Avant d'améliorer un système, que fais-tu ? »** → J'établis une baseline officielle : je fige le système actuel et je le mesure sur TOUTES les dimensions (retrieval, génération par type, latence, coût) via le harnais sur le golden set, puis j'enregistre immuablement (config + version + date + scores). Elle est multidimensionnelle car une amélioration peut gagner sur un axe et dégrader un autre. Je ne la retouche JAMAIS (une baseline mouvante invalide les comparaisons), et je ne corrige RIEN pendant la mesure (chaque correction fausse le point de départ). La baseline transforme chaque amélioration d'une impression en une mesure — et elle priorise les chantiers par faiblesse.
