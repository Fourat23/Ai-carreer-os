## 🎯 Objectif du jour
Gérer l'état local sans le muter.

## 📖 Cours approfondi
**Modèle mental : le state n'est pas une variable que tu MODIFIES, c'est une valeur que tu REMPLACES — et c'est ce remplacement qui déclenche un nouveau rendu.** `useState` te donne deux choses : la valeur actuelle et une fonction pour la remplacer. Tu n'écris jamais `compteur = compteur + 1` ; tu appelles `setCompteur(compteur + 1)`. La différence est fondamentale : React ne « surveille » pas tes variables — il re-rend uniquement quand tu l'INFORMES via un setter qu'une nouvelle valeur existe.

Les trois lois du state :
1. **Immutabilité** : pour un objet ou un tableau, tu ne modifies pas l'ancien, tu en crées un NOUVEAU. `liste.push(x)` ne re-rend PAS (même référence) ; `setListe([...liste, x])` re-rend (nouvelle référence). C'est le piège valeur/référence de JS (mois 1) qui devient une règle React : React compare les références pour décider s'il re-rend.
2. **Le state est une capture** : à chaque rendu, la valeur du state est FIGÉE pour ce rendu. D'où le setter fonctionnel `setCompteur(c => c + 1)` quand la nouvelle valeur dépend de l'ancienne — indispensable si tu fais plusieurs mises à jour d'affilée.
3. **Le bon niveau de granularité** : plusieurs `useState` pour des valeurs indépendantes, un seul state-objet quand les valeurs bougent ensemble (comme la machine à 3 états loading/error/data du jour 95).

La règle qui gouverne l'interactivité React : **un événement met à jour le state (immuablement), et le nouveau state produit un nouveau rendu**. L'UI est toujours une fonction du state courant — tu ne manipules jamais l'affichage directement, tu changes le state et laisses React recalculer l'écran. C'est la boucle événement → setState → rendu, le cœur de toute app interactive.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : un compteur borné et une liste de courses, avec un state 100 % immuable.

**Exemple simple** : la mise à jour immuable la plus courante — ajouter à une liste : `setItems([...items, nouvel])`. Jamais `items.push(nouvel)`. Retiens ce spread : 90 % des bugs de state viennent d'une mutation oubliée.

**Raisonnement pas-à-pas** : identifier ce qui change (le state) → le mettre à jour via le setter avec une NOUVELLE référence → laisser React re-rendre.

**Solution** :
```tsx
function Compteur({ min = 0, max = 10 }: { min?: number; max?: number }) {
  const [n, setN] = useState(min);
  return (
    <div>
      <button onClick={() => setN((c) => Math.max(min, c - 1))}>-</button>
      <span>{n}</span>
      <button onClick={() => setN((c) => Math.min(max, c + 1))}>+</button>
    </div>
  );
}

function Courses() {
  const [items, setItems] = useState<{ id: number; nom: string; pris: boolean }[]>([]);
  const ajouter = (nom: string) =>
    setItems((xs) => [...xs, { id: Date.now(), nom, pris: false }]);   // NOUVEAU tableau
  const cocher = (id: number) =>
    setItems((xs) => xs.map((x) => x.id === id ? { ...x, pris: !x.pris } : x)); // NOUVEAUX objets
  return /* ... rendu de la liste ... */;
}
```

**Mini-quiz** : (a) Pourquoi `items.push(x)` ne déclenche-t-il pas de rendu ? (b) Quand utiliser `setN(c => c + 1)` plutôt que `setN(n + 1)` ? (c) Que compare React pour décider de re-rendre ?
→ (a) parce que c'est la MÊME référence de tableau — React ne voit pas de changement ; (b) quand la nouvelle valeur dépend de l'ancienne, surtout en cas de mises à jour multiples ; (c) la référence (identité) de la valeur, pas son contenu.

**Variante** : ajoute un bouton « reset » et un compteur d'articles cochés DÉRIVÉ du state (`items.filter(x => x.pris).length`) — n'en fais PAS un state séparé : ce qui se calcule ne se stocke pas.

## 🏢 Cas métier
Le bug le plus fréquent des juniors React en production : « j'ai modifié le tableau mais l'écran ne bouge pas ». La cause est toujours la même — une mutation (`push`, `sort`, `obj.champ = x`) au lieu d'un remplacement immuable. Les équipes imposent l'immutabilité (lint, revues) parce qu'elle rend le state prévisible et débuggable. Maîtriser l'immutabilité n'est pas de la coquetterie : c'est ce qui fait qu'une UI interactive se comporte de façon fiable, et c'est directement transférable à Redux, à la gestion d'état de toute app, et au raisonnement sur les données immuables en général.

## 🎤 Question d'entretien
**« Pourquoi ne faut-il jamais muter le state directement en React ? »** → Parce que React décide de re-rendre en comparant les RÉFÉRENCES, pas le contenu. Si je fais `liste.push(x)`, la référence du tableau ne change pas : React ne voit rien, l'UI ne se met pas à jour. Je dois créer une NOUVELLE référence (`[...liste, x]` ou `.map(...)`), passée au setter. C'est le comportement valeur/référence de JavaScript qui devient une règle : l'immutabilité rend le state prévisible et permet à React d'optimiser les rendus. Corollaire : ce qui se calcule à partir du state (un total, un filtre) ne se stocke pas en state, on le dérive.
