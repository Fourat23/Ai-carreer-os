## 🎯 Objectif du jour
Une commande, un rapport.

## 📖 Cours approfondi
**Modèle mental : un harnais d'évaluation transforme l'évaluation d'un ÉVÉNEMENT (que tu refais à la main, rarement) en une COMMANDE (que tu lances à chaque changement, sans friction).** Tu as les instruments : golden set (253), métriques de retrieval (254), juges de génération (255-256). Éparpillés, ils ne servent qu'aux jours où tu as le courage de les rejouer. Assemblés en `rag eval`, ils deviennent le réflexe qui pilote toute amélioration — la boucle mesurée des jours 211 et 235, industrialisée pour le système entier.

Ce qu'un harnais digne de ce nom produit :
1. **Une commande, un rapport** : `rag eval --config retrieval-v2` fait tourner TOUT le golden set et sort un rapport structuré — scores agrégés (rappel@k, MRR, fidélité, pertinence, exactitude), scores PAR TYPE de question, et le détail PAR QUESTION (pour aller voir les échecs). Agrégats pour décider, détail pour diagnostiquer.
2. **Reproductible et daté** : température 0 partout, golden set versionné, config d'évaluation enregistrée — deux exécutions sur le même système donnent le même rapport. Un harnais non déterministe ne permet aucune comparaison.
3. **Comparable entre versions** : le rapport s'enregistre (JSON horodaté + config), et un mode `rag eval --compare v2 v3` montre les DELTAS par métrique et par question — ce qui a gagné, ce qui a régressé. C'est ce qui rend « v3 est-il meilleur que v2 ? » répondable en une commande.
4. **Économe** : l'évaluation coûte (les juges LLM sont des appels) — le harnais met en cache les jugements par (question, réponse) identiques, ne re-juge que ce qui a changé, et affiche le coût de la campagne. Une évaluation qu'on hésite à lancer à cause du coût n'est pas lancée.

Le harnais est l'INFRASTRUCTURE qui rend le mois d'évaluation opérationnel : sans lui, chaque mesure est une corvée manuelle ; avec lui, tu mesures à chaque commit. C'est exactement le rôle des frameworks d'éval (Ragas, promptfoo, DeepEval) que tu comprendras de l'intérieur pour les avoir construits.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : le harnais `rag eval` — une commande, un rapport reproductible et comparable.

**Raisonnement** : orchestrer les évaluateurs existants, structurer le rapport (agrégats + par type + par question), rendre reproductible, comparable et économe.

**Architecture** :
```python
def rag_eval(config_name: str, golden_path: str) -> Rapport:
    golden = charger(golden_path)                 # versionné
    systeme = construire_systeme(config_name)     # retrieval-v2 + génération
    lignes = []
    for q in golden["questions"]:
        rep, extraits = systeme.repondre(q["question"])   # réponse + sources
        ligne = {
            "id": q["id"], "type": q["type"],
            **evaluer_retrieval_1(systeme, q),        # rappel@k, RR (j.254)
            **evaluer_generation(q["question"], rep, extraits, q),  # 3 axes (j.256)
        }
        lignes.append(ligne)
    return Rapport(
        config=config_name, golden_version=golden["version"], date=now(),
        agregats=agreger(lignes),          # global + PAR TYPE
        detail=lignes,                     # PAR QUESTION
        cout=cout_campagne(), duree=...,
    )   # sérialisé en JSON horodaté pour comparaison future
```

**Le rapport (structure)** :
```
=== rag eval — retrieval-v2 — golden v1.1 — 2026-XX-XX ===
AGRÉGATS   rappel@3 0,85 · MRR 0,79 · fidélité 0,88 · pertinence 0,92 · exact. 0,81
PAR TYPE   factuelles: exact 0,92 | synthèse: exact 0,50 <- point faible
COÛT       0,31 € · DURÉE 48 s · 26 questions
ÉCHECS     [gs-09 synthèse: fidèle mais inexact] [gs-17 reformulée: rappel@3=0]...
```

**Explication** : le rapport à trois niveaux (agrégats -> par type -> par question avec échecs listés) est ce qui rend le harnais utile pour DÉCIDER *et* DIAGNOSTIQUER — la plupart des harnais bâclés ne donnent que l'agrégat, inexploitable pour réparer. **Variante** : implémente `rag eval --compare` qui charge deux rapports JSON et affiche les deltas + la liste des questions BASCULÉES (gagnées/perdues) — l'outil qui rendra les jours 267-268 (améliorations pilotées) triviaux.

## 🏢 Cas métier
La différence entre une équipe qui améliore son RAG vite et une qui stagne tient souvent à ça : la première a une commande d'évaluation qu'elle lance à chaque changement (30 secondes, un rapport), la seconde « évalue quand elle a le temps » (donc jamais vraiment). Le harnais rend l'évaluation SANS FRICTION, et ce qui est sans friction se fait. C'est le même principe que les tests automatisés (mois 5) : ce qui n'est pas automatisé n'est pas fait. En entretien, « j'évalue à chaque commit via mon harnais » est le signal d'une culture d'ingénierie mûre.

## 🎤 Question d'entretien
**« Comment industrialises-tu l'évaluation d'un RAG ? »** → Un harnais : une commande fait tourner le golden set et sort un rapport à trois niveaux — agrégats pour décider, par type pour cibler, par question pour diagnostiquer. Reproductible (température 0, golden versionné, config enregistrée), comparable entre versions (rapports horodatés + mode compare qui montre les deltas et les questions basculées), et économe (cache des jugements, coût affiché). Sans harnais, l'évaluation est une corvée qu'on saute ; avec, c'est un réflexe à chaque commit — le principe des tests automatisés appliqué à la qualité RAG.
