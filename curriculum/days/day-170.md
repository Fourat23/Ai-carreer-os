## 🎯 Objectif du jour
Traiter les variables catégorielles.

## 📖 Cours approfondi
**Modèle mental : un modèle ne mange que des NOMBRES — les variables catégorielles doivent être ENCODÉES (one-hot pour le non-ordonné, jamais un label-encoding qui invente un ordre faux), et les échelles NORMALISÉES pour les modèles sensibles à la distance ; le tout appris DANS un pipeline sur le train seul pour éviter le leakage.** Le préprocessing n'est pas une formalité : un mauvais encodage introduit un ordre fictif qui trompe le modèle, et une normalisation mal placée fait fuir l'information du test. C'est une source majeure d'erreurs subtiles.

Les transformations et leurs raisons, depuis les fondations :
1. **Encoder les catégories** : un modèle ne comprend pas « rouge/vert/bleu ». Deux options :
   - **One-hot encoding** : une colonne binaire par catégorie (`couleur_rouge`, `couleur_vert`…). Correct pour les catégories NON ordonnées, car il n'impose aucun ordre. Coût : beaucoup de colonnes si nombreuses modalités.
   - **Label encoding** (0, 1, 2…) : à réserver aux catégories ORDONNÉES (petit < moyen < grand). L'appliquer à du non-ordonné (rouge=0, vert=1, bleu=2) INVENTE un ordre faux (« bleu > rouge ») que les modèles linéaires interprètent à tort — erreur classique.
2. **Normaliser les échelles** : les modèles basés sur la DISTANCE (k-NN, k-means, SVM) ou le gradient sont sensibles à l'échelle : une feature en milliers (revenu) écrase une feature en unités (âge). `StandardScaler` (centrer-réduire) ou `MinMaxScaler` remettent les features sur une échelle comparable. Les arbres/forêts, eux, sont insensibles à l'échelle (ils splittent par seuils).
3. **Imputer les manquants** : remplacer les valeurs manquantes (médiane, mode, ou valeur dédiée) — décision à justifier (jour 128), et à apprendre sur le train seul.

Le fil conducteur — TOUT dans un pipeline, sur le train seul : chaque transformation (encodage, normalisation, imputation) APPREND des paramètres (les catégories vues, la moyenne/écart-type, la médiane). Si on les apprend sur l'ensemble complet avant le split, l'information du test fuit (jour 157). La parade structurelle est le Pipeline (jour 171) avec un ColumnTransformer qui applique le bon traitement à chaque type de colonne, ré-appris à chaque fold.

La règle du jour : **encode les catégories selon leur nature (one-hot pour le non-ordonné, jamais un ordre fictif), normalise pour les modèles sensibles à la distance, impute les manquants — et apprends tout le préprocessing sur le train seul (via pipeline) pour éviter le leakage. Un mauvais encodage trompe le modèle, un préprocessing mal placé fait fuir le test**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : construire un préprocessing complet (one-hot vs label, normalisation) dans un Pipeline anti-leakage.

**Exemple simple** : l'erreur d'encodage à éviter — encoder `ville` (non ordonnée) en 0,1,2,3 fait croire au modèle que « ville 3 > ville 0 ». Le one-hot (une colonne par ville) évite cet ordre fictif. La nature de la variable dicte l'encodage.

**Raisonnement pas-à-pas** : séparer colonnes numériques et catégorielles → normaliser les numériques, one-hot pour les catégorielles → tout dans un ColumnTransformer + Pipeline (ré-appris à chaque fold).

**Implémentation** :
```python
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.pipeline import Pipeline
from sklearn.linear_model import LogisticRegression

num = ["age", "revenu", "anciennete_mois"]
cat = ["ville", "forfait"]                         # catégories NON ordonnées -> one-hot

pre = ColumnTransformer([
    ("num", StandardScaler(), num),                # normaliser (sensible à la distance)
    ("cat", OneHotEncoder(handle_unknown="ignore"), cat),   # one-hot, pas d'ordre fictif
])

pipe = Pipeline([("pre", pre), ("clf", LogisticRegression(max_iter=1000))])
# En CV, tout le préprocessing est ré-appris sur le train de chaque fold -> pas de leakage.
```

**Mini-quiz** : (a) Pourquoi ne pas label-encoder une catégorie non ordonnée ? (b) Quels modèles nécessitent une normalisation, lesquels non ? (c) Pourquoi mettre le préprocessing dans un Pipeline ?
→ (a) label-encoder (0,1,2…) invente un ORDRE (« 2 > 0 ») que les modèles linéaires interprètent à tort ; le one-hot n'impose aucun ordre ; (b) les modèles à base de distance/gradient (k-NN, k-means, SVM, régressions) en ont besoin ; les arbres/forêts sont insensibles à l'échelle ; (c) pour que le préprocessing soit appris sur le train de chaque fold seulement — sinon l'info du test fuit (leakage).

**Variante** : compare le score d'un modèle linéaire avec label-encoding vs one-hot sur une catégorie non ordonnée. Le one-hot est meilleur : tu vois concrètement le tort d'un ordre fictif.

## ⚠️ Erreurs fréquentes
- Label-encoder une catégorie non ordonnée : ordre fictif qui trompe les modèles linéaires — utiliser le one-hot.
- Normaliser sur tout le dataset avant le split : l'info du test fuit — l'encapsuler dans un Pipeline.
- Normaliser pour des arbres/forêts : inutile (ils sont insensibles à l'échelle).
- One-hot sur une variable à très nombreuses modalités : explosion de colonnes — envisager d'autres encodages.

## 🏢 Cas métier
Le préprocessing est une source majeure de bugs subtils en ML appliqué : un label-encoding sur des catégories non ordonnées introduit un ordre fictif qui dégrade silencieusement les modèles linéaires ; une normalisation ajustée sur tout le dataset fait fuir l'information du test et gonfle les scores. Les data scientists rigoureux encodent selon la nature de la variable, normalisent pour les modèles sensibles à l'échelle, et encapsulent TOUT dans un pipeline avec ColumnTransformer pour garantir l'absence de leakage à chaque fold. C'est ce qui rend un projet reproductible et déployable : le même préprocessing s'applique en production, appris exactement comme en entraînement. Maîtriser l'encodage et le préprocessing anti-leakage est un attendu de base, et les erreurs ici invalident des projets entiers.
