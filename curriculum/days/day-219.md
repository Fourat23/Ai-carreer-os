## 🎯 Objectif du jour
Retrouver les chunks pertinents.

## 📖 Cours approfondi
**Modèle mental : la similarité cosinus mesure si deux flèches pointent dans la même direction.** Deux vecteurs d'embedding sont deux flèches dans un espace à N dimensions ; le cosinus de leur angle vaut 1 (même direction = même sens sémantique), 0 (orthogonaux = sans rapport), -1 (opposés — rare avec les embeddings modernes). La formule : `cos(a, b) = (a·b) / (‖a‖ × ‖b‖)` — le produit scalaire, normalisé par les longueurs pour que seule la DIRECTION compte, pas la magnitude.

La recherche top-k est alors d'une simplicité désarmante : embedder la question, calculer son cosinus avec CHAQUE chunk, trier, garder les k meilleurs. C'est une recherche EXHAUSTIVE (brute force) — parfaitement exacte, et parfaitement suffisante pour des milliers de chunks (quelques millisecondes en NumPy vectorisé). Les vector DB n'accélèrent ce calcul (index approximatifs ANN) que quand les millions de vecteurs rendent l'exhaustif trop lent — en échange d'une EXACTITUDE légèrement dégradée. Tu implémentes aujourd'hui la version exacte : c'est ta référence de vérité pour toujours.

Deux subtilités qui font la différence :
1. **Les scores se regardent.** Un top-1 à 0.83 et un top-1 à 0.41 ne racontent pas la même histoire — le second dit « je n'ai rien trouvé de vraiment proche ». Afficher les scores (et envisager un seuil plancher) prépare le diagnostic des échecs (jour 226).
2. **k est un paramètre de conception** : k=1 est fragile (le bon chunk est parfois 2e ou 3e), k=10 noie la génération sous le bruit et gonfle le coût. k=3-5 est le point de départ standard — à mesurer plus tard, comme toujours.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : la recherche par similarité maison, vectorisée, avec scores affichés.

**Raisonnement** : d'abord la fonction cosinus (testée sur des cas connus), puis le top-k vectorisé, puis l'inspection des résultats sur tes questions types.

**Implémentation** :
```python
import numpy as np

M = np.array([c["vecteur"] for c in chunks])          # matrice (n_chunks, dim)
M_norm = M / np.linalg.norm(M, axis=1, keepdims=True)  # pré-normalisée UNE fois

def top_k(question: str, k=3) -> list[tuple[float, dict]]:
    q = np.array(api_embeddings([question])[0])
    q = q / np.linalg.norm(q)
    scores = M_norm @ q                                 # tous les cosinus d'un coup
    idx = np.argsort(scores)[::-1][:k]
    return [(float(scores[i]), chunks[i]) for i in idx]

# Tests de la fonction cosinus elle-même :
# cos(v, v) == 1.0 ; cos(v, -v) == -1.0 ; cos([1,0], [0,1]) == 0.0
```

**Explication** : pré-normaliser la matrice transforme le cosinus en simple produit matriciel `M @ q` — toute la recherche tient en une ligne NumPy (tes acquis du jour 183 ressurgissent). **Variante** : chronomètre sur ton corpus (probablement < 5 ms) puis extrapole : à combien de chunks la recherche exhaustive dépasserait-elle 100 ms ? C'est TON seuil chiffré de « il me faudrait une vector DB ».

## 🎤 Question d'entretien
**« Pourquoi le cosinus plutôt que la distance euclidienne pour les embeddings ? Et que fait une vector DB de plus que ton implémentation ? »** → Le cosinus ne compare que la direction (le sens), en neutralisant la magnitude des vecteurs. Ma version exhaustive est exacte et suffit jusqu'à ~10⁵ chunks ; une vector DB ajoute des index approximatifs (ANN) pour rester rapide à des millions de vecteurs — en acceptant une légère perte d'exactitude — plus le filtrage par métadonnées et la persistance concurrente.
