## 🎯 Objectif du jour
Appliquer REST pour des endpoints cohérents et prévisibles.

## 📖 Cours approfondi
**Concepts abordés :** Ressources/collections · Verbes = actions, URLs = noms · Statuts par cas · Pagination · Cohérence.

REST modélise l'API en RESSOURCES (des noms au pluriel : /livres, /livres/42) manipulées par les verbes HTTP. La règle d'or : l'URL dit QUOI, le verbe dit COMMENT — jamais de verbe dans l'URL (/getLivres est un anti-pattern).

Une bonne API est PRÉVISIBLE : qui a vu GET /livres devine POST /livres (créer), DELETE /livres/42 (supprimer), GET /livres/42/emprunts (sous-ressource). La cohérence des statuts complète le contrat : 201 + l'objet créé sur un POST réussi, 204 sur un DELETE, 404 sur un id inconnu, 400 avec les détails sur une entrée invalide.

Pagination, filtres et recherche passent en query string (?page=2&genre=sf) : ils raffinent la ressource, ils ne la changent pas.

**Modèle mental : REST modélise une API en RESSOURCES (des noms au pluriel : `/livres`, `/livres/42`) manipulées par les verbes HTTP. La règle d'or : l'URL dit QUOI (la ressource), le verbe dit COMMENT (l'action) — jamais de verbe dans l'URL. Le critère de qualité ultime : une API bien conçue est PRÉVISIBLE, on devine ses endpoints sans lire la doc. Qui a vu `GET /livres` devine `POST /livres`, `DELETE /livres/42`, `GET /livres/42/emprunts`.** Concevoir une API REST, c'est offrir un contrat si cohérent qu'il se lit comme du langage naturel.

Pourquoi REST existe. Avant une convention partagée, chaque API inventait ses noms (`/getLivres`, `/livre_delete`, `/nouveauLivre`) : impossible à deviner, coûteux à apprendre. REST propose une CONVENTION universelle bâtie sur HTTP (jour 50) : les données sont des ressources, les verbes HTTP sont les actions. Le bénéfice n'est pas technique mais HUMAIN : un développeur qui connaît REST comprend n'importe quelle API REST sans réapprendre.

Les principes, depuis les fondations. **Ressources = noms, au pluriel** : `/livres` (collection), `/livres/42` (élément). **Verbes = actions** : `GET /livres` liste, `GET /livres/42` lit un, `POST /livres` crée, `PUT /livres/42` remplace, `PATCH /livres/42` modifie, `DELETE /livres/42` supprime. **Sous-ressources** pour les relations : `GET /livres/42/emprunts`. **Statuts cohérents** (jour 50) : 201 + l'objet créé sur un POST, 204 sur un DELETE, 404 sur un id inconnu, 400 + détails sur une entrée invalide. **Query string pour raffiner** : `?page=2&genre=sf&tri=titre` — pagination, filtres et recherche RAFFINENT la ressource sans la changer (ils restent des GET).

La différence verbe-dans-l'URL vs REST. `GET /getLivres` ou `POST /deleteLivre/42` sont des anti-patterns : ils dupliquent dans l'URL l'information que porte déjà le verbe HTTP, et cassent la prévisibilité (faut-il `/getLivres` ou `/livresList` ou `/allLivres` ?). En REST, l'URL nomme une CHOSE, le verbe dit ce qu'on en fait — une seule façon logique, donc devinable.

La cohérence, valeur centrale. Une API où `/livres` est au pluriel mais `/auteur` au singulier, où certaines erreurs sont des 200 et d'autres des 400, où la pagination change de nom selon l'endpoint, force à lire la doc à chaque appel. La cohérence (pluriels partout, mêmes statuts pour les mêmes cas, mêmes conventions de query) est ce qui rend l'API prévisible — elle vaut plus qu'une doc exhaustive.

Limites et compromis. REST pur n'est pas toujours idéal : certaines actions ne sont pas de simples CRUD (`POST /livres/42/emprunter` — une action métier — est un compromis pragmatique accepté). GraphQL ou RPC répondent à d'autres besoins (requêtes flexibles, appels de procédures). Et la pagination par OFFSET a ses limites sur gros volumes (jour 64). REST est un excellent défaut, pas un dogme absolu — on assume les entorses pragmatiques en les gardant cohérentes.

La règle du jour : **conçois des ressources (noms pluriels), laisse les verbes HTTP porter les actions (jamais de verbe dans l'URL), sois COHÉRENT (mêmes statuts pour les mêmes cas, query string pour raffiner), et vise la PRÉVISIBILITÉ : une bonne API se devine sans doc. Spécifie les cas d'erreur, pas seulement les succès.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : concevoir (en markdown, sans code) le contrat REST d'une ressource `livres`, et vérifier qu'il se devine sans doc.

**Exemple simple** : le test de prévisibilité. Si je montre `GET /livres` à un développeur, il doit deviner sans hésiter : créer = `POST /livres`, lire un = `GET /livres/{id}`, supprimer = `DELETE /livres/{id}`. S'il hésite (`/livres/create` ? `/newLivre` ?), le design a échoué.

**Raisonnement pas-à-pas** : (1) j'identifie la ressource (livres) au pluriel ; (2) je mappe chaque opération CRUD sur un verbe + une URL ; (3) j'attribue le statut précis de chaque cas (succès ET erreur) ; (4) je mets pagination/filtres en query string ; (5) je vérifie la cohérence (pluriels, statuts).

**Contrat (api-design.md)** :
```text
RESSOURCE : livres

GET    /livres              -> 200 + [ {id,titre,auteur}, ... ]   (liste)
       ?page=2&genre=sf&tri=titre  (pagination + filtres + tri en query)
GET    /livres/{id}         -> 200 + {id,...}   |  404 si absent
POST   /livres              -> 201 + {id,...}   |  400 + détails si invalide
PUT    /livres/{id}         -> 200 + {id,...}   |  404 absent | 400 invalide
PATCH  /livres/{id}         -> 200 + {id,...}   |  404 | 400
DELETE /livres/{id}         -> 204 (pas de corps) |  404 si absent

SOUS-RESSOURCE : les emprunts d'un livre
GET    /livres/{id}/emprunts -> 200 + [ ... ]

Erreurs (toujours) : 400 {erreurs:[...]}, 404 {message}, 409 conflit métier.
```
Le contrat est ENTIÈREMENT devinable : pluriels cohérents, verbes HTTP pour les actions, statuts précis par cas, query string pour raffiner. Aucun verbe dans les URLs.

## ⚠️ Erreurs fréquentes
- Mettre des verbes dans les URLs (`/getLivres`, `/deleteLivre`) : anti-REST, casse la prévisibilité.
- Répondre 200 pour tout, y compris les erreurs : prive les clients du langage des statuts.
- Incohérences (pluriel/singulier mélangés, statuts variables pour un même cas) qui forcent à lire la doc.
- Ne spécifier que les succès : les cas d'erreur (400, 404, 409) font partie du contrat.

## 🏢 Cas métier
La conception d'API REST cohérente est un enjeu de PRODUCTIVITÉ d'équipe et d'écosystème. Une API prévisible réduit drastiquement le coût d'intégration : les équipes front, mobile et les partenaires externes la consomment sans harceler l'équipe back de questions, les outils (générateurs de clients, documentation automatique type OpenAPI) fonctionnent mieux sur des conventions respectées, et les nouveaux développeurs sont productifs plus vite. À l'inverse, une API incohérente (verbes dans les URLs, statuts anarchiques, pluriels mélangés) génère des tickets, des bugs d'intégration et de la frustration durable — et elle est difficile à corriger une fois publiée (casser le contrat casse les clients). C'est pourquoi la conception d'API est souvent revue collectivement et fait l'objet de questions d'entretien back précises : « conçois-moi l'API REST de X » teste directement si tu penses ressources, verbes, statuts et cohérence.

## 🎤 Question d'entretien
**« Conçois l'API REST d'une bibliothèque : comment structures-tu les endpoints ? »** → Je modélise les DONNÉES en ressources nommées au pluriel (`/livres`, `/auteurs`, `/emprunts`) et je laisse les verbes HTTP porter les actions : `GET /livres` liste, `GET /livres/42` lit un livre, `POST /livres` crée, `PUT/PATCH /livres/42` modifient, `DELETE /livres/42` supprime. Jamais de verbe dans l'URL — `/getLivres` est un anti-pattern qui duplique le verbe HTTP et casse la prévisibilité. Les relations deviennent des sous-ressources : `GET /livres/42/emprunts`. J'attribue des statuts précis à chaque cas, succès ET erreur : 201 + l'objet sur un POST, 204 sur un DELETE, 404 sur un id inconnu, 400 + détails sur une entrée invalide, 409 sur un conflit métier (double emprunt). La pagination, les filtres et la recherche passent en query string (`?page=2&genre=sf`) car ils raffinent la ressource sans la changer. Mon critère de qualité est la PRÉVISIBILITÉ : un développeur doit deviner mes endpoints sans doc, grâce à la cohérence (pluriels partout, mêmes statuts pour les mêmes cas). **Relance possible** : « et une action qui n'est pas un simple CRUD, comme emprunter ? » → j'assume un compromis pragmatique, `POST /livres/42/emprunter`, en le gardant cohérent : REST est un excellent défaut, pas un dogme, et une action métier peut être une sous-ressource verbale documentée.
