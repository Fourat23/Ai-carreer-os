### Synthèse de la semaine
La semaine 13 a clôturé le mois 3 avec le Projet 2 (LivreAPI) : une API REST complète avec ses routes CRUD, sa validation, ses codes HTTP corrects, sa collection Postman documentée et une revue mensuelle. Le fil rouge du mois : une API n'est pas « du code qui répond », c'est un CONTRAT — des routes prévisibles, des statuts qui disent la vérité (200/201/400/404/500), des erreurs structurées, et une documentation exécutable (Postman) qui prouve qu'elle marche. Tu entres maintenant dans le mois 4 (React) avec un back-end réel à consommer : ton front des semaines suivantes se branchera sur CETTE API. La bascule mentale à réussir : tu passes de « je produis des réponses JSON » à « je consomme un contrat et j'en affiche les trois états (chargement, erreur, données) ».

### Plan de remédiation (si un critère échoue)
- **Routes incohérentes ou verbes mal choisis** (GET qui modifie, POST pour lire) : reprends la conception REST — une ressource au pluriel, le verbe HTTP porte l'action. Une API dont on ne devine pas les routes n'est pas consommable.
- **Codes de statut approximatifs** (tout en 200, même les erreurs) : le statut est la PREMIÈRE information que ton front React lira pour choisir entre les 3 états. Réaligne 201 (créé), 400 (entrée invalide), 404 (absent), 500 (bug serveur).
- **Pas de validation** : une entrée non validée = un plantage 500 au lieu d'un 400 explicite. Ajoute la validation en entrée de chaque route qui reçoit un corps.
- **Collection Postman absente ou non rejouable** : sans elle, tu ne peux pas PROUVER que l'API marche ni t'y brancher méthodiquement. Reconstruis-la, une requête par route, avec un exemple de corps et la réponse attendue.

### Questions d'entretien de la semaine
1. **« Qu'est-ce qui fait qu'une API REST est bien conçue ? »** Attendu : des ressources nommées clairement, les bons verbes HTTP, des codes de statut qui disent la vérité, des erreurs structurées, une documentation qui permet de la consommer sans lire le code.
2. **« Pourquoi un code de statut HTTP compte-t-il autant pour le client ? »** Attendu : c'est le premier signal que le client lit pour décider quoi faire (afficher, réessayer, montrer une erreur) ; tout renvoyer en 200 force le client à deviner.
3. **« Quels sont les trois états qu'un front doit gérer face à une API ? »** Attendu : chargement, erreur, données — un fetch a TOUJOURS ces trois états, et on ne peut jamais afficher « données » sans données.
4. **« Que prouve une collection Postman ? »** Attendu : que l'API marche vraiment, route par route ; c'est une documentation exécutable, pas une promesse.
