## 🎯 Objectif du jour
POO Python et idiomes.

## 📖 Cours approfondi
**Modèle mental : en Python, la POO est OPTIONNELLE et LÉGÈRE — une classe regroupe des données ET le comportement qui les manipule, mais le style pythonique préfère les `dataclass` pour les données, la COMPOSITION à l'héritage, et le duck typing aux hiérarchies rigides. La question n'est pas « comment faire une classe » mais « ai-je vraiment besoin d'une classe ici ? ».** Beaucoup de code Python n'a pas besoin de POO : une fonction sur un `dict` suffit souvent. On introduit une classe quand des données et des comportements vont ENSEMBLE et bénéficient d'être encapsulés.

Ce qu'il faut maîtriser :
1. **La classe et `self`** : `class Compte:`, `def __init__(self, solde)` (le constructeur), `self` est la référence explicite à l'instance (là où JS a un `this` implicite et piégeux). Chaque méthode reçoit `self` en premier paramètre.
2. **La `dataclass`** : pour une classe qui porte surtout des DONNÉES, `@dataclass` génère automatiquement `__init__`, `__repr__` (affichage lisible) et l'égalité. `@dataclass\nclass Livre:\n    titre: str\n    auteur: str` remplace 15 lignes de code répétitif. C'est l'idiome pythonique pour les structures de données.
3. **`__repr__` et les méthodes spéciales** : `__repr__` donne une représentation lisible pour le débogage ; les « dunder methods » (`__eq__`, `__len__`...) intègrent tes objets aux idiomes du langage.
4. **Composition > héritage** : plutôt qu'une hiérarchie profonde (`ClientPremium(Client)`), on COMPOSE (un `Client` a une `Adresse`, une `Facturation`). L'héritage crée un couplage rigide ; la composition reste souple. On n'hérite que pour une vraie relation « est-un ».
5. **Duck typing** : « si ça marche comme un canard et cancane comme un canard, c'est un canard ». Python ne vérifie pas le TYPE mais le COMPORTEMENT : n'importe quel objet ayant une méthode `.lire()` peut être utilisé là où on attend un « lecteur », sans hiérarchie commune.

Quand NE PAS utiliser de classe : si tu as une classe avec un seul `__init__` et une seule méthode, c'est probablement une FONCTION déguisée. Si tu n'as que des données sans comportement, une `dataclass` (ou un simple `dict`) suffit.

La règle du jour : **une classe pour regrouper données + comportement quand ça a du sens ; une `dataclass` pour les données ; la composition par défaut, l'héritage seulement pour un vrai « est-un » ; et pas de classe quand une fonction suffit**. Le style pythonique privilégie la simplicité — la POO est un outil, pas une obligation.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : modéliser un système simple en classes Python idiomatiques (`dataclass`, style pythonique).

**Exemple simple** : la `dataclass` qui remplace le code répétitif — `@dataclass\nclass Livre:\n    titre: str\n    auteur: str\n    dispo: bool = True`. Trois lignes te donnent constructeur, affichage lisible et égalité. C'est l'idiome à réflexe pour toute structure de données.

**Raisonnement pas-à-pas** : distinguer ce qui est DONNÉE (dataclass) de ce qui est COMPORTEMENT (méthodes) → composer plutôt qu'hériter → n'ajouter une classe que si données et comportement vont ensemble.

**Implémentation** :
```python
from dataclasses import dataclass, field

@dataclass
class Livre:                      # DONNÉES : dataclass (init/repr/eq générés)
    titre: str
    auteur: str
    dispo: bool = True

@dataclass
class Bibliotheque:               # DONNÉES + COMPORTEMENT : classe justifiée
    livres: list[Livre] = field(default_factory=list)   # (pas [] mutable partagé !)
    def ajouter(self, livre: Livre) -> None:
        self.livres.append(livre)
    def disponibles(self) -> list[Livre]:
        return [l for l in self.livres if l.dispo]        # comprehension
    def __len__(self) -> int:      # dunder : len(biblio) fonctionne
        return len(self.livres)

biblio = Bibliotheque()
biblio.ajouter(Livre("React", "Dan"))
print(len(biblio), biblio.disponibles())   # repr lisible gratuit
```

**Mini-quiz** : (a) Quand préférer une `dataclass` à une classe classique ? (b) Pourquoi `field(default_factory=list)` et pas `= []` ? (c) Composition ou héritage par défaut ?
→ (a) quand la classe porte surtout des données : `@dataclass` génère init/repr/eq ; (b) une valeur par défaut mutable (`[]`) est PARTAGÉE entre toutes les instances — piège classique ; `default_factory` crée une liste neuve à chaque fois ; (c) composition par défaut ; l'héritage seulement pour un vrai « est-un ».

**Variante** : prends une de tes classes et demande-toi si elle a plus d'un `__init__` et une seule méthode — si oui, réécris-la en fonction. Savoir SUPPRIMER une classe inutile est aussi pythonique que savoir en écrire une.

## 🏢 Cas métier
Le style POO pythonique — dataclasses pour les données, composition, pas de classe superflue — produit du code plus court et plus lisible que la POO « à la Java » (hiérarchies profondes, getters/setters partout) que les développeurs venus d'autres langages ont tendance à écrire. Dans les bases de code Python data/ML, les dataclasses structurent les configurations, les enregistrements et les résultats d'analyse ; l'over-engineering POO (une classe pour ce qui devrait être une fonction) est un anti-pattern que les revues signalent. Le piège de la valeur par défaut mutable (`= []`) est un bug réel et fréquent qui partage un état entre instances. Savoir quand une classe est justifiée — et quand une fonction ou une dataclass suffit — est un marqueur de maturité Python valorisé.

## 🎤 Question d'entretien
**« Quand utilises-tu une classe en Python, et qu'est-ce que le style pythonique ? »** → Une classe quand des DONNÉES et le COMPORTEMENT qui les manipule vont ensemble et bénéficient d'être encapsulés — pas par défaut. Pour des données surtout, j'utilise une `@dataclass` qui génère `__init__`, `__repr__` et l'égalité automatiquement. Je préfère la COMPOSITION à l'héritage (l'héritage crée un couplage rigide, réservé aux vraies relations « est-un ») et je m'appuie sur le duck typing : Python vérifie le comportement, pas le type, donc pas besoin de hiérarchie commune. Le style pythonique privilégie la simplicité : si une classe n'a qu'un `__init__` et une méthode, c'est une fonction déguisée. Attention au piège de la valeur par défaut mutable (`= []`), partagée entre instances — j'utilise `field(default_factory=list)`.
