## 🎯 Objectif du jour
Rendre le pipeline robuste.

## 📖 Cours approfondi
**Modèle mental : un pipeline ROBUSTE est REJOUABLE (idempotent : le relancer ne duplique ni ne corrompt rien) et SURVIT aux échecs PARTIELS (reprise possible, logs pour diagnostiquer, écriture transactionnelle) — car « ça a tourné une fois sur mon poste » n'est pas « ça tourne en production », où les sources tombent, les jobs s'interrompent et les données arrivent sales.** Un pipeline conçu (jour 138) doit maintenant être fiable dans le monde réel. Les deux propriétés qui le rendent déployable sont l'idempotence et la survie aux échecs.

L'IDEMPOTENCE — pouvoir relancer sans dégât :
- Le problème : un pipeline qui INSÈRE des lignes à chaque exécution DUPLIQUE les données si on le relance (après un échec, ou pour rattraper). Un pipeline idempotent produit le MÊME état final qu'on le lance une ou dix fois.
- Les techniques : le `UPSERT` (insérer ou mettre à jour selon une clé, `INSERT ... ON CONFLICT DO UPDATE`) plutôt qu'un INSERT aveugle ; le remplacement complet d'une partition (`replace` d'une table/période) ; une clé naturelle qui identifie une ligne pour éviter les doublons. L'idempotence est ce qui rend un pipeline REJOUABLE en confiance.

La SURVIE aux échecs partiels :
- **Les logs** : à chaque étape, journaliser ce qui se passe (combien de lignes extraites, transformées, chargées ; les erreurs). Sans logs, un pipeline qui échoue la nuit est un mystère au matin — les logs sont les traces (jour 274 côté agents) appliquées à l'ETL.
- **Le chargement transactionnel** (jour 136) : le load réussit ENTIÈREMENT ou est annulé — jamais une base à moitié chargée.
- **La reprise / le point de contrôle** : pouvoir relancer après un échec sans tout refaire (grâce au staging, jour 138, et à l'idempotence). Un pipeline qui doit tout recommencer depuis zéro à chaque échec est fragile.
- **La gestion des erreurs de données** : décider quoi faire d'une ligne invalide — la rejeter dans un « bac à rejets » (dead-letter) avec sa raison, plutôt que planter tout le pipeline ou l'ignorer silencieusement.

La règle du jour : **rends le pipeline idempotent (relançable sans duplication) et résilient (logs à chaque étape, load transactionnel, reprise après échec, rejets tracés) ; conçois pour l'interruption, pas seulement pour le chemin heureux**. Un pipeline de production n'est pas un script qui a marché une fois — c'est un script qui survit à la nuit où la source tombe à mi-parcours.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : rendre le pipeline robuste — logs, échec partiel, idempotence — et prouver la survie à une interruption.

**Exemple simple** : le cœur de l'idempotence — l'upsert. `INSERT INTO ventes(...) VALUES(...) ON CONFLICT(id) DO UPDATE SET ...`. Relancer le pipeline met à jour les lignes existantes au lieu de les dupliquer. C'est ce qui rend « relancer » sûr.

**Raisonnement pas-à-pas** : rendre le load idempotent (upsert/replace par clé) → journaliser chaque étape → charger transactionnellement → tracer les rejets → prouver en interrompant.

**Implémentation** :
```python
import logging
logging.basicConfig(level=logging.INFO)

def run() -> None:
    sources = extract()
    logging.info("Extract : %d lignes", len(sources["ventes"]))

    df, rejets = transform_avec_rejets(sources)         # rejets tracés, pas ignorés
    logging.info("Transform : %d valides, %d rejetées", len(df), len(rejets))
    if rejets: rejets.to_csv("rejets.csv", index=False)  # dead-letter avec raisons

    with sqlite3.connect("entrepot.db") as con:          # LOAD transactionnel (jour 136)
        for _, r in df.iterrows():
            con.execute("""INSERT INTO ventes(id, montant) VALUES(?, ?)
                           ON CONFLICT(id) DO UPDATE SET montant=excluded.montant""",  # UPSERT idempotent
                        (r["id"], r["montant"]))
    logging.info("Load : %d lignes chargées (rejouable)", len(df))
```
Preuve d'idempotence : lancer `run()` deux fois de suite laisse la table dans le MÊME état (pas de doublons) grâce à l'upsert. Preuve de survie : interrompre pendant le load, relancer → la transaction annule le load partiel, et l'upsert évite les doublons au redémarrage.

**Mini-quiz** : (a) Qu'est-ce qu'un pipeline idempotent ? (b) Pourquoi tracer les lignes rejetées plutôt que les ignorer ? (c) À quoi servent les logs par étape ?
→ (a) le relancer produit le même état final (une ou dix fois) — pas de duplication ; (b) pour ne pas perdre silencieusement des données et pouvoir diagnostiquer/corriger la cause ; (c) diagnostiquer un échec après coup (combien extrait/transformé/chargé, où ça a cassé) — sans eux, un échec nocturne est un mystère.

**Variante** : simule une coupure en levant une exception au milieu du load, puis relance — vérifie qu'il n'y a NI doublon (idempotence) NI chargement partiel (transaction). C'est la preuve concrète que ton pipeline survit à l'interruption.

## ⚠️ Erreurs fréquentes
- INSERT aveugle non idempotent : relancer duplique les données — utiliser un upsert ou un remplacement par clé.
- Aucun log : un échec nocturne est indiagnosticable au matin.
- Load non transactionnel : une interruption laisse la base à moitié chargée.
- Ignorer ou planter sur une ligne invalide : perte silencieuse ou pipeline fragile — la router vers un dead-letter avec sa raison.

## 🏢 Cas métier
La robustesse d'un pipeline est ce qui sépare un script de démo d'un pipeline de production : en réel, les sources tombent, les API expirent, les jobs sont tués, les données arrivent sales — et un pipeline non idempotent qui duplique à chaque relance ou plante sans logs devient un cauchemar opérationnel (données corrompues, débogage à l'aveugle, réconciliations manuelles). Les data engineers conçoivent POUR l'échec : idempotence pour rejouer sans risque, logs pour diagnostiquer, transactions pour ne jamais laisser un état partiel, dead-letter pour tracer les rejets. Cette maturité — « je conçois pour la nuit où la source tombe à mi-parcours » — est exactement ce qui est attendu d'un rôle data engineer, et directement démontrable dans le projet DataPulse (pipeline rejouable en une commande).

## 🎤 Question d'entretien
**« Comment rends-tu un pipeline ETL robuste et rejouable ? »** → Deux propriétés. L'IDEMPOTENCE : le relancer produit le même état final, sans duplication — j'utilise des UPSERT (`ON CONFLICT DO UPDATE`) ou un remplacement de partition plutôt que des INSERT aveugles, avec une clé qui identifie chaque ligne. C'est ce qui rend « relancer après un échec » sûr. La SURVIE aux échecs partiels : des logs à chaque étape (combien extrait/transformé/chargé, les erreurs) pour diagnostiquer après coup ; un load TRANSACTIONNEL (tout ou rien, jamais une base à moitié chargée) ; la reprise après échec grâce au staging ; et un « bac à rejets » (dead-letter) où j'envoie les lignes invalides avec leur raison, au lieu de planter ou d'ignorer silencieusement. Je conçois pour l'interruption, pas seulement pour le chemin heureux — « ça a tourné une fois » n'est pas « ça tient en production ».
