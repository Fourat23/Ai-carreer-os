## 🔁 Revue hebdomadaire

**Thème de la semaine :** Express complet : middlewares, erreurs, validation, structure

### Bilan
La différence entre une API de tutoriel et une API pro : gestion d'erreurs, validation, structure en couches, logs.

### Test pratique
75 min : ajoute à l'API citations — middleware d'erreurs centralisé, validation stricte des entrées (sans lib, à la main), erreurs 400 détaillées, 404 propres, logs avec timestamp. Casse ton API avec Postman (10 requêtes malveillantes) et vérifie chaque réponse.

### Test théorique
Pourquoi centraliser la gestion d'erreurs ; différence erreur opérationnelle vs bug ; qu'est-ce que l'injection (intuition) et pourquoi valider TOUTES les entrées ; que logger et que ne JAMAIS logger.

### Mini-projet / livrable
Squelette d'API réutilisable : structure routes/services/data + erreurs + validation + logs, qui servira de base au projet 2.

### Exercice de réflexion architecturale
Liste 5 choses qui peuvent mal se passer entre un client et ta base de données (réseau, entrée invalide, ressource absente, panne, bug). Pour chacune : qui détecte, qui répond quoi, avec quel statut.

### Synthèse de la semaine
La semaine 11 a bâti la culture d'ingénieur au-delà du code applicatif. Le réseau (jour 71) : la pile sous HTTP — DNS → TCP → TLS → HTTP, ce que HTTPS protège (confidentialité, intégrité, identité du serveur) et ne cache pas (le domaine), et la distinction latence (aller-retour, distance) vs bande passante. Linux avancé (jour 72) : un script encode un savoir-faire répétable (set -e, config par environnement, permissions) — le germe du DevOps. Git avancé (jour 73) : le rebase réécrit l'historique pour le rendre lisible, jamais sur du partagé ; un historique propre est une documentation. Documentation technique (jour 74) : écrire pour un lecteur précis, avec la bonne hiérarchie (README, docstrings-contrat, ADR, diagramme), le pourquoi pas le quoi. Lecture de code (jour 75) : la compétence n°1 en poste — jamais linéairement, mais point d'entrée → carte → un flux → hypothèses vérifiées. Modularité (jour 76) : couplage faible, cohésion forte, implémentation cachée derrière une interface minimale. Le fil rouge : **un bon ingénieur ne se juge pas qu'à son code — mais à sa compréhension des systèmes (réseau), à son outillage (Linux, Git), à sa communication (doc), à sa capacité à lire l'existant, et à son sens de la structure (modularité).** Ces compétences transversales sont ce qui distingue un développeur employable d'un simple codeur.

### Questions d'entretien de la semaine
1. **« Que se passe-t-il quand tu tapes une URL ? »** Attendu : DNS → TCP → TLS → HTTP, ce que TLS protège (confidentialité, intégrité, identité serveur), latence vs bande passante, le domaine fuite via SNI/DNS.
2. **« Comment écris-tu un script d'automatisation robuste ? »** Attendu : set -e, codes de sortie, config par environnement (tourne partout), permissions ; germe de la CI.
3. **« Rebase ou merge, et la règle de sécurité ? »** Attendu : rebase réécrit (linéaire, avant partage), merge fusionne (fidèle, après) ; jamais rebaser du partagé ; historique = documentation.
4. **« Comment documentes-tu pour être compris ? »** Attendu : écrire pour un lecteur précis, hiérarchie (README/docstrings-contrat/ADR/diagramme), le pourquoi pas le quoi, doc testée.
5. **« Comment abordes-tu un codebase inconnu, et qu'est-ce qu'un bon module ? »** Attendu : point d'entrée → carte → flux → hypothèses ; couplage faible/cohésion forte, interface minimale, pas de cycle.
