# Correction — Jour 340 : Polish GitHub

[← Retour au jour 340](../days/day-340.md)

> ⛔ **Ne lis cette correction qu'après avoir vraiment tenté seul.** Une correction n'est pas une réponse à copier : c'est un outil pour comprendre ta démarche.

## 🧠 La logique attendue
Solution simple : ajouter un README aux repos. Solution améliorée : polir CHAQUE repo (description, topics, README à jour, licence) et créer un README de profil GitHub (page d'accueil : qui tu es, projets clés, contact). GitHub étant le portfolio de facto, la propreté des dépôts est un proxy de la qualité du travail — le polish change la première impression de tous les projets pour un coût faible.

## ⚠️ Erreurs probables et points à vérifier
- Repos sans description ni topics : invisibles et incompréhensibles en un coup d'œil — chaque repo en a.
- READMEs obsolètes ou « TODO » : signalent l'abandon — les mettre à jour, proportionnés au projet.
- Pas de licence : flou juridique, projet non réutilisable — MIT typiquement.
- Pas de README de profil : la page d'accueil GitHub est vide — c'est ta vitrine, la soigner.

## 🔍 Comment vérifier ta solution
- Les 7 repos ont description, topics, README à jour, licence.
- Le README de profil GitHub existe (qui tu es, projets clés, contact).
- Aucun repo ne semble abandonné (README vide, pas de description).
- Les commits/repos donnent une impression professionnelle.
- Le test « regard de recruteur » sur le GitHub est passé (variante).

## 🎤 À savoir expliquer à l'oral
Explique GitHub comme portfolio de facto : « un recruteur regarde mon GitHub avant l'entretien, et la propreté de mes repos est un proxy de la qualité de mon travail — donc chaque repo a description, README et licence, et mon profil a une page d'accueil ». Puis le ratio : « le polish prend une journée mais change la première impression de tous mes projets ». Soigner la présentation est un impact élevé pour un coût faible.
