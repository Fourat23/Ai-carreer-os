## 🎯 Objectif du jour
Gérer les secrets proprement.

## 📖 Cours approfondi
**Modèle mental : un secret (clé API, mot de passe, token) n'a qu'une règle absolue — il ne doit JAMAIS toucher le code source ni l'historique git ; une fois committé, il est compromis pour toujours, même après suppression.** Tu connais la base (clé en .env, mois 4) ; aujourd'hui tu AUDITES tous tes repos et professionnalises la gestion des secrets. Pour une app IA, l'enjeu est aigu : les clés d'API LLM sont des secrets à valeur MONÉTAIRE DIRECTE — une clé fuitée peut être utilisée pour des milliers d'euros d'appels avant que tu ne t'en aperçoives.

Les principes d'une gestion de secrets professionnelle :
1. **Jamais dans le code ni git** : les secrets vivent dans des variables d'environnement (.env local, jamais committé — .gitignore), ou un gestionnaire de secrets (vault, secrets managers cloud) en production. La règle est absolue car git a une MÉMOIRE : un secret committé puis « supprimé » reste dans l'historique, accessible à quiconque clone le repo. Suppression ≠ effacement.
2. **La rotation** : un secret doit pouvoir être RÉVOQUÉ et REMPLACÉ rapidement (en cas de fuite, de départ d'un collaborateur, ou par hygiène périodique). Une architecture où changer une clé demande de modifier 10 fichiers rend la rotation impossible en urgence — d'où la centralisation (une seule source de vérité pour chaque secret).
3. **La gestion par environnement** : des secrets DIFFÉRENTS pour dev, staging, production — jamais la clé de production sur une machine de dev. Une fuite en dev ne doit pas compromettre la production.
4. **La détection** : scanner les repos et l'historique pour les secrets committés par erreur (des outils existent), et surveiller l'usage des clés (une clé API LLM dont la consommation explose signale une fuite).

L'audit du jour : parcourir TOUS tes repos — chercher les secrets dans le code ET l'historique git, vérifier les .gitignore, identifier les clés à faire tourner, mettre en place la gestion par environnement. Si tu trouves une clé committée (même ancienne), la RÉVOQUER (pas juste la supprimer — elle est déjà compromise) et en générer une nouvelle. C'est un travail d'hygiène peu glamour mais critique : une fuite de secret est l'une des causes les plus fréquentes et les plus coûteuses d'incidents de sécurité, et pour une app IA, c'est ta facture LLM qui est directement en jeu.

**La chaîne d'approvisionnement logicielle (fondation V24).** Ton application n'est pas faite que de TON code : elle embarque des dizaines à des milliers de **dépendances** (directes et **transitives** — les dépendances de tes dépendances). Chacune est une porte d'entrée potentielle : c'est la **supply chain**. Trois piliers d'hygiène. **Verrouiller** : un **lockfile** (package-lock, etc.) fige les versions EXACTES (y compris transitives) pour que tout le monde — toi, la CI, la prod — installe la même chose ; une plage (`^1.2.0`) laisse arriver une version non prévue, potentiellement compromise. **Épingler** (pinning) : préférer une version exacte, et pour les images de conteneur, un **digest** immuable (`@sha256:…`) plutôt qu'un tag mobile comme `latest`. **Vérifier la provenance** : savoir d'où vient un artefact et qu'il n'a pas été altéré — d'où la **signature** d'artefacts et le **SBOM** (Software Bill of Materials : l'inventaire exact des composants, qui permet de répondre en minutes à « suis-je affecté par cette vulnérabilité ? »).

**Les attaques de supply chain.** Le **typosquatting** publie un paquet malveillant au nom très proche d'un paquet populaire (`expresss` pour `express`) en pariant sur une faute de frappe. La **dependency confusion** exploite un paquet censé être interne : un attaquant publie un homonyme sur le registre PUBLIC, et l'outil, mal configuré, tire la version publique malveillante. Un **changement de lockfile inattendu** (une dépendance transitive qui saute de version sans raison) est un signal à investiguer. Enfin, une **dépendance vulnérable** (une CVE connue) doit être mise à jour ou mitigée — encore faut-il savoir qu'on l'utilise (SBOM).

**Que faire dans ce cas ? (dépendance compromise)** : (1) évaluer l'**exposition** (où la dépendance est-elle utilisée ? SBOM) ; (2) **geler les déploiements** pour ne pas propager ; (3) **épingler/retirer** la version compromise, vérifier le lockfile ; (4) **remplacer** par une version saine ou **isoler** ; (5) **reconstruire** depuis un lockfile vérifié ; (6) **surveiller** les indicateurs de compromission ; (7) **post-mortem** : renforcer verrouillage, provenance et revue des mises à jour. Le **Security & Incident Lab** analyse un lockfile factice (dépendance non verrouillée, vulnérable via une base CVE **factice** locale, typosquatting) — sans aucun accès réseau ni scanner réel.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : audit des secrets sur TOUS tes repos, rotation, gestion par environnement.

**Exemple simple** : le test le plus important — chercher dans l'HISTORIQUE git, pas juste le code actuel : `git log -p | grep -i "api_key\|secret\|password"`. Un secret supprimé du code mais présent dans l'historique est TOUJOURS compromis.

**Raisonnement pas-à-pas** : scanner code + historique, révoquer ce qui a fuité, centraliser, séparer par environnement.

**La démarche d'audit** :
```
1. SCANNER chaque repo : code actuel ET historique git (les secrets committés
   restent dans l'historique même après suppression).
   → outils de détection de secrets, ou grep sur l'historique.
2. Pour chaque secret trouvé dans git : le RÉVOQUER (il est compromis) et
   en générer un nouveau. Supprimer du code NE SUFFIT PAS.
3. Vérifier les .gitignore : .env et fichiers de secrets exclus PARTOUT.
4. CENTRALISER : chaque secret a une seule source (.env / secrets manager),
   le code le lit par variable d'environnement — rotation = changer UN endroit.
5. SÉPARER par environnement : clés distinctes dev / staging / prod.
6. Pour les clés API LLM : surveiller la consommation (une hausse anormale = fuite).
```

**Mini-quiz** : (a) Un secret committé puis supprimé du code est-il sûr ? (b) Pourquoi centraliser les secrets ? (c) Pourquoi les clés API LLM sont-elles des secrets particulièrement sensibles ?
→ (a) NON — il reste dans l'historique git, il faut le RÉVOQUER ; (b) pour rendre la rotation possible en urgence (changer un seul endroit) ; (c) valeur monétaire directe — une clé fuitée peut générer des milliers d'euros d'appels.

**Variante** : mets en place une détection automatique (un hook de pre-commit qui refuse un commit contenant un motif de secret) — la meilleure gestion de secret est celle qui EMPÊCHE la fuite avant qu'elle n'arrive.

## ⚠️ Erreurs fréquentes
- Croire qu'un secret supprimé du code est sûr : il reste dans l'historique git — il faut le RÉVOQUER, la suppression ne l'efface pas.
- Secrets dispersés dans plusieurs fichiers : la rotation d'urgence devient impossible — centraliser (une source par secret).
- Même clé pour dev et prod : une fuite en dev compromet la prod — séparer par environnement.
- Ignorer la surveillance de consommation des clés LLM : une clé fuitée peut générer des milliers d'euros avant détection — surveiller les hausses anormales.

## 🏢 Cas métier
Les fuites de secrets sont l'une des causes les plus fréquentes et coûteuses d'incidents : des clés API committées sur des repos publics sont scannées et exploitées par des bots en MINUTES — et pour une clé LLM, cela signifie des milliers d'euros d'appels frauduleux avant détection. Des entreprises ont subi des factures cloud catastrophiques à cause d'une seule clé fuitée. La gestion professionnelle des secrets (jamais dans git, rotation, séparation par environnement, détection) est une hygiène de sécurité non négociable. Un ingénieur qui audite ses repos, révoque les clés compromises et met en place la détection démontre une rigueur de sécurité que les employeurs exigent — surtout quand des clés à valeur monétaire sont en jeu.

## 🎤 Question d'entretien
**« Comment gères-tu les secrets, et que fais-tu si une clé a été committée ? »** → Règle absolue : jamais dans le code ni l'historique git — variables d'environnement en local (.env gitignoré), gestionnaire de secrets en production. Si une clé a été committée, même supprimée depuis, elle est COMPROMISE (git a une mémoire) : je la RÉVOQUE et j'en génère une nouvelle — supprimer du code ne suffit pas. Je centralise (une source par secret pour rendre la rotation possible en urgence), je sépare par environnement (jamais la clé de prod en dev), et je détecte (scan de l'historique, hook pre-commit, surveillance de la consommation des clés LLM). Pour l'IA, l'enjeu est aigu : une clé LLM fuitée a une valeur monétaire directe.
