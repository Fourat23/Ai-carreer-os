## 🎯 Objectif du jour
Tester du code qui appelle un LLM.

## 📖 Cours approfondi
**Modèle mental : tester du code qui appelle un LLM exige de CONTRÔLER le LLM — on le remplace par un mock (réponse programmée) ou un replay (réponse enregistrée), pour que les tests soient rapides, déterministes et gratuits.** Le LLM est non déterministe (jour 199), coûteux et lent — trois propriétés incompatibles avec des tests (qui doivent être rapides, reproductibles, gratuits). La solution, standard, est de ne pas appeler le vrai LLM dans les tests : on injecte un DOUBLE de test. C'est le pattern d'injection de dépendance (jour 214, hexagonal jour 289) appliqué au LLM.

Les deux techniques et leurs usages :
1. **Le mock** : remplacer l'appel LLM par une fonction qui retourne une réponse PROGRAMMÉE. Utile pour tester la LOGIQUE autour de l'appel — que fait ton code si le LLM retourne tel format ? tel refus ? une erreur ? un JSON invalide ? Le mock permet de simuler tous ces cas (y compris les cas d'erreur difficiles à provoquer avec le vrai LLM) et de vérifier que ton code réagit correctement. C'est ainsi qu'on teste le workflow d'analyse (jour 323), le parsing, le retry (jour 214), la gestion d'erreur.
2. **Le replay** : enregistrer les VRAIES réponses du LLM une fois, puis les rejouer dans les tests. Utile pour tester avec des réponses RÉALISTES sans payer ni attendre à chaque exécution. On capture les réponses lors d'un run réel, on les stocke, et les tests les rejouent — déterministes et gratuits, mais réalistes. C'est un compromis entre le mock (totalement contrôlé mais artificiel) et le vrai appel (réaliste mais coûteux/non déterministe).

Ce qu'on teste ainsi : le workflow d'analyse (les étapes s'enchaînent correctement), le parsing des sorties structurées (jour 205), la gestion d'erreur (LLM down, JSON invalide → comportement correct), le retry/fallback (jour 214). Ce qu'on NE teste PAS ainsi : la qualité des réponses du LLM (ça, c'est l'évaluation avec le harnais, jour 317 — un problème différent).

Pourquoi c'est une compétence spécifique et différenciante : « on ne peut pas tester du code qui appelle un LLM parce que c'est non déterministe » est une idée reçue répandue — et fausse. On teste la LOGIQUE autour de l'appel en contrôlant le LLM (mock/replay) ; on évalue la QUALITÉ séparément (harnais). Distinguer ces deux problèmes (tester le code vs évaluer le modèle) et savoir mocker/rejouer les appels LLM est une compétence de test IA que peu de développeurs maîtrisent. Elle rend le code qui entoure le LLM aussi testable que n'importe quel code — et donc fiable, refactorable, protégé par la CI (jour 326).

## 🧭 Exemple guidé

**Énoncé** : mock/replay des appels LLM dans les tests, tests du workflow d'analyse.

**Exemple simple** : le mock en une idée — injecter un faux générateur qui retourne une réponse fixe, et vérifier que ton workflow la traite correctement. `MoteurRAG(generateur=GenerateurMock(reponse="..."))` — le cœur est testé sans vrai appel.

**Raisonnement pas-à-pas** : injecter un double de test (mock pour la logique/les cas d'erreur, replay pour le réalisme), tester le workflow et ses cas limites.

**Implémentation** :
```python
# MOCK : réponse programmée, pour tester la logique et les cas d'erreur
class GenerateurMock:
    def __init__(self, reponse): self.reponse = reponse
    def generer(self, q, chunks): return self.reponse   # contrôlé

def test_workflow_analyse():
    moteur = analyser_document  # avec générateur mocké
    # cas nominal : le workflow enchaîne résumé → points clés → questions
    # cas d'erreur : LLM retourne un JSON invalide → gestion d'erreur (j.205)
    # cas refus : scores faibles → refus (j.263)

# REPLAY : vraies réponses enregistrées une fois, rejouées (réaliste, gratuit)
class GenerateurReplay:
    def generer(self, q, chunks): return self.enregistrements[hash(q)]  # rejoué
```

**Mini-quiz** : (a) Pourquoi ne pas appeler le vrai LLM dans les tests ? (b) Quelle est la différence entre mock et replay ? (c) Que teste-t-on avec mock/replay, et que ne teste-t-on PAS ?
→ (a) le vrai LLM est non déterministe, coûteux et lent — incompatible avec des tests ; (b) le mock retourne une réponse programmée (contrôle total, cas d'erreur), le replay rejoue de vraies réponses enregistrées (réaliste, gratuit) ; (c) on teste la LOGIQUE autour de l'appel (workflow, parsing, erreurs), PAS la qualité des réponses (ça, c'est l'évaluation).

**Variante** : teste un cas d'erreur difficile à provoquer avec le vrai LLM — un JSON malformé, un timeout, un refus. Le mock permet de simuler ces cas et de vérifier que ton code les gère (jour 214) — c'est un avantage majeur du mock sur le vrai appel.

## 🏢 Cas métier
« On ne peut pas tester du code qui appelle un LLM » est une idée reçue qui laisse des pans entiers de code IA non testés (et donc fragiles) dans beaucoup de projets. Les équipes matures savent que c'est faux : elles mockent/rejouent les appels pour tester la logique (workflows, parsing, gestion d'erreur) comme n'importe quel code, et évaluent la qualité séparément avec un harnais. Cette distinction — tester le CODE vs évaluer le MODÈLE — est ce qui rend une base de code IA fiable et refactorable. Pour DocSense, des tests du workflow d'analyse avec mock/replay signifient que le code autour du LLM est protégé par la CI (jour 326), aussi robuste que le reste. « Je teste mon code LLM avec des mocks, et j'évalue la qualité séparément » démontre une compétence de test IA que peu maîtrisent.

## 🎤 Question d'entretien
**« Comment testes-tu du code qui appelle un LLM ? »** → En contrôlant le LLM : je l'injecte comme dépendance (hexagonal) et je le remplace par un mock (réponse programmée, pour tester la logique et les cas d'erreur — JSON invalide, timeout, refus, difficiles à provoquer avec le vrai LLM) ou un replay (vraies réponses enregistrées puis rejouées, pour le réalisme sans coût ni non-déterminisme). Je teste ainsi la LOGIQUE autour de l'appel (workflow, parsing, gestion d'erreur, retry) — comme n'importe quel code. Ce que je ne teste PAS ainsi, c'est la QUALITÉ des réponses : ça, c'est l'évaluation avec le harnais, un problème séparé. « On ne peut pas tester du code LLM » est une idée reçue fausse : on teste le code, on évalue le modèle.
