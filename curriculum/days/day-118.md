## 📖 Cours approfondi
**Modèle mental : un projet non documenté et non démontrable n'existe pas pour un recruteur — le README, le schéma, l'ADR et la démo sont l'INTERFACE entre ton travail et le marché. BiblioApp est fini ; aujourd'hui tu le rends LISIBLE en trois minutes par quelqu'un qui ne l'a jamais vu.** Tu as déjà rendu un projet présentable pour LivreAPI (mois 3) ; ici tu le fais pour une app front full-stack, avec des livrables adaptés à ce type de projet. C'est la dernière ligne droite qui transforme du code en PIÈCE DE PORTFOLIO.

Les quatre livrables et leur rôle DISTINCT pour BiblioApp :
1. **Le README** raconte l'histoire : le problème (gérer une bibliothèque de livres), ce que fait l'app (avec un GIF de démo qui vaut mille mots), comment la lancer en une commande, et les limites. Il commence par le POURQUOI, pas par « BiblioApp utilise React et Vite ». Un recruteur le lit en 90 secondes et décide s'il creuse.
2. **Le schéma d'architecture 3-tiers** : le trait distinctif d'un projet full-stack — montrer visuellement les trois couches (le front React ↔ l'API REST ↔ la base de données) et comment une requête les traverse. Ce schéma prouve que tu comprends l'ARCHITECTURE, pas seulement le code d'un écran.
3. **L'ADR n°3 : « état global (Context) vs état local »** : une décision d'architecture RÉELLE de BiblioApp, figée avec son pourquoi — pourquoi le thème est en Context mais l'état d'un formulaire reste local (jours 100-101), les options écartées, les conséquences. Une ADR montre que tu as ARBITRÉ, le signal recherché au-dessus du niveau junior.
4. **La démo de 2 minutes** montre l'app VIVANTE : lister, créer, rechercher, supprimer — un parcours fluide qui prouve que « ça marche » là où le README l'affirme.

La règle qui gouverne les quatre : ils s'adressent à un lecteur EXTÉRIEUR pressé, pas à toi. Le test du regard neuf : quelqu'un qui n'a jamais vu BiblioApp comprend-il, via le README et la démo, ce que fait l'app, comment elle est construite (le schéma), pourquoi tu as fait tes choix (l'ADR), et comment la lancer — SANS te parler ? Si oui, ton projet est présentable et vendable. Sinon, c'est un projet que seul toi comprends, donc invisible sur le marché.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : rendre BiblioApp présentable — README + schéma 3-tiers + ADR n°3 + démo 2 min.

**Exemple simple** : la première ligne du README n'est pas « BiblioApp est une app React/Vite » mais « BiblioApp permet de gérer une bibliothèque : lister, ajouter, rechercher et supprimer des livres, avec une interface soignée et testée ». Le POURQUOI et la valeur avant la stack.

**Raisonnement pas-à-pas** : écrire pour un lecteur extérieur pressé — histoire (README + GIF), architecture (schéma 3-tiers), décision arbitrée (ADR), preuve vivante (démo) — puis TEST du regard neuf.

**Structure** :
```
README.md
  1. Le problème + ce que fait BiblioApp (2 phrases) + GIF de démo
  2. Fonctionnalités : liste, CRUD, recherche/filtres, états soignés, tests
  3. Lancer en 1 commande (npm install && npm run dev)
  4. Architecture → lien vers le schéma 3-tiers
  5. Décisions → lien vers les ADR · 6. Limites assumées
schéma 3-tiers (image) :
  [Front React] --HTTP/JSON--> [API REST] --SQL--> [Base de données]
  (une requête "créer un livre" traverse les trois : formulaire → POST → INSERT)
ADR-003 : état global (Context) vs local
  contexte → options (tout en Context / tout local / mixte) → décision (mixte :
  thème en Context, formulaires en local) → conséquences → révision si
démo 2 min : lister → créer un livre → le rechercher → le supprimer (parcours fluide)
```

**Mini-quiz** : (a) Par quoi commence un bon README ? (b) Que prouve un schéma 3-tiers qu'un écran de code ne prouve pas ? (c) Que montre l'ADR « Context vs local » ?
→ (a) le problème et la valeur, pas la stack ; (b) que tu comprends l'ARCHITECTURE (comment front, API et base collaborent), pas juste un composant ; (c) que tu as ARBITRÉ une vraie décision (thème global, formulaire local) avec son pourquoi et ses options écartées.

**Variante** : fais lire ton README à quelqu'un qui ne connaît pas BiblioApp et chronomètre — comprend-il en 90 secondes ce que fait l'app, comment elle est construite et comment la lancer ? Ses questions sont tes trous à combler.

## ⚠️ Erreurs fréquentes
- README qui commence par la stack (« React + Vite ») au lieu du problème et de la valeur : le lecteur ne sait pas pourquoi le projet existe.
- Pas de schéma d'architecture : sur un projet full-stack, on ne prouve pas qu'on comprend comment les couches collaborent.
- ADR qui ne liste que la décision sans les options écartées : sans l'arbitrage, elle ne prouve pas la pensée d'architecte.
- Démo hésitante ou absente : « ça marche sur ma machine » ne convainc pas — un parcours CRUD fluide de 2 min, oui.

## 🏢 Cas métier
Les recruteurs techniques passent 30 à 90 secondes sur un repo GitHub avant de décider s'ils creusent : un README qui commence par le problème et montre un GIF de démo capte cette fenêtre ; un README « TODO » ou noyé dans la config la gâche. Pour un projet full-stack, le schéma 3-tiers est décisif — il prouve en un coup d'œil que le candidat comprend comment le front, l'API et la base collaborent, ce que beaucoup de juniors ne savent pas expliquer. Et l'ADR distingue celui qui a « fait des choix » de celui qui « a suivi un tuto ». À compétence égale, le candidat dont le projet se comprend en deux minutes obtient l'entretien que l'autre n'obtient pas : le README, le schéma et la démo ne sont pas de la cosmétique, ils sont l'interface entre ton travail et le marché.

Un README qui commence par le pourquoi, un schéma qui montre que je comprends l'architecture, une démo qui prouve que ça marche — pour que la valeur soit comprise sans que j'aie tout à expliquer.
