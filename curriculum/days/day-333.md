## 🎯 Objectif du jour
Tester les chemins critiques.

## 📖 Cours approfondi
**Modèle mental : la couverture de tests ne vise pas 100% — elle vise les CHEMINS CRITIQUES, ceux dont une régression casserait la valeur du système.** Après la gestion d'erreur (331) et l'observabilité (332), tu assures la testabilité du cœur : une couverture RAISONNABLE, ciblée sur les chemins critiques (le RAG core, le refus, la génération citée, le workflow d'analyse), plutôt qu'une course au pourcentage. Tester intelligemment, c'est protéger ce qui compte, pas cocher une métrique.

La philosophie d'une couverture de tests utile :
1. **Les chemins critiques d'abord** : quels sont les comportements dont une régression serait GRAVE ? Pour DocSense : le retrieval retourne les bons chunks, la génération cite ses sources, le refus se déclenche quand il faut, le workflow d'analyse enchaîne ses étapes, la gestion d'erreur ne casse pas. Ce sont eux qu'il faut tester en priorité — une régression dessus détruit la valeur.
2. **La couverture raisonnable, pas maximale** : viser 100% de couverture est contre-productif (on teste du code trivial, on écrit des tests fragiles, on perd du temps). Une couverture raisonnable du CŒUR (la logique métier, testable en isolation grâce à l'hexagonal, jour 310) avec des mocks/replay pour le LLM (jour 327) protège l'essentiel. Le pourcentage est un indicateur, pas un objectif — 70% sur les chemins critiques vaut mieux que 95% incluant du code trivial.
3. **Les tests comme filet de refactoring** : les tests du cœur permettent de refactorer sans peur (si les tests passent, le comportement est préservé) et sont exécutés par la CI (jour 326) à chaque commit. Ils transforment DocSense en un système qu'on peut faire évoluer en confiance.

Pourquoi « chemins critiques » plutôt que « 100% » : la couverture à 100% est un piège — elle donne une fausse sécurité (du code trivial testé, des bugs dans la logique complexe manqués) et coûte cher (tests fragiles, maintenance). La bonne question n'est pas « quel pourcentage ? » mais « si ce test manquait, quelle régression passerait ? ». Tester les chemins critiques (ceux dont la casse détruit la valeur) est ce qui protège efficacement. C'est un jugement d'ingénieur : savoir OÙ mettre l'effort de test. « Je teste les chemins critiques de mon cœur, pas 100% pour le chiffre » démontre une maturité de test que la course au pourcentage ne montre pas.

**Mini-quiz** : (a) Pourquoi ne pas viser 100% de couverture ? (b) Quelle est la bonne question pour décider quoi tester ? (c) À quoi servent les tests au-delà d'attraper des bugs ?
→ (a) fausse sécurité (trivial testé, logique complexe manquée) + coût (tests fragiles) — viser les chemins critiques ; (b) « si ce test manquait, quelle régression passerait ? » ; (c) filet de refactoring (refactorer sans peur) + protection en CI à chaque commit.

**Variante** : pour chaque chemin critique testé, imagine la régression que le test attraperait (« si quelqu'un casse le refus, ce test le voit ») — un test dont tu ne peux pas nommer la régression qu'il protège est peut-être un test inutile.

## ⚠️ Erreurs fréquentes
- Viser 100% de couverture : fausse sécurité (trivial testé, logique complexe manquée) + coût de maintenance — cibler les chemins critiques.
- Tester des getters/setters triviaux pour le chiffre : du temps perdu qui gonfle le pourcentage sans protéger la valeur.
- Tests fragiles couplés à l'implémentation : ils cassent à chaque refactoring — tester le comportement, pas les détails.
- Ne pas intégrer les tests à la CI : un test non exécuté automatiquement ne protège pas — le filet doit tourner à chaque commit.

## 🏢 Cas métier
La course à la couverture à 100% est un anti-pattern classique : elle donne une fausse sécurité (on teste des getters triviaux pendant que la logique complexe reste sous-testée) et coûte cher en maintenance (tests fragiles qui cassent à chaque refactoring). Les équipes matures ciblent les chemins critiques — ceux dont une régression casserait la valeur — et acceptent une couverture raisonnable plutôt que maximale. En entreprise, « nous testons nos chemins critiques » est un signe de maturité ; « nous avons 100% de couverture » est souvent un signe de tests superficiels. Pour DocSense, tester le cœur (retrieval, génération citée, refus, workflow, gestion d'erreur) avec des mocks LLM protège l'essentiel et sert de filet de refactoring — et « je teste les chemins critiques, pas le pourcentage » démontre le jugement d'ingénieur de savoir où mettre l'effort.
