## 🎯 Objectif du jour
Structurer extract/transform/load.

## 📖 Cours approfondi
**Modèle mental : un pipeline ETL sépare TROIS responsabilités — EXTRACT (lire les sources telles quelles), TRANSFORM (nettoyer/normaliser/joindre en mémoire), LOAD (écrire dans la cible) — chacune isolée pour être testée, remplacée et débuggée INDÉPENDAMMENT. Le E, le T et le L ne se mélangent jamais.** Amener des données brutes et éparses (des CSV, une API) jusqu'à une base propre et interrogeable est un besoin universel. La tentation du débutant est de tout faire dans une grosse fonction ; le pipeline professionnel sépare les étapes, car chacune a des raisons d'échouer et d'évoluer différentes.

Les trois étapes et leur responsabilité stricte :
1. **Extract** : récupérer les données de chaque source SANS les transformer — lire le CSV, appeler l'API, télécharger. On capture le brut, on gère les erreurs de SOURCE (fichier absent, API en panne), et on s'arrête là. Mélanger extraction et nettoyage empêche de rejouer une transformation sans re-télécharger.
2. **Transform** : tout le travail EN MÉMOIRE — nettoyer (jour 128), valider (jour 132), normaliser, joindre les sources (jour 131), calculer les colonnes dérivées. C'est le cœur métier, fait de fonctions pures testables (jour 132). Aucune écriture en base ici.
3. **Load** : écrire le résultat propre dans la cible (SQLite), dans un schéma pensé (jour 134), transactionnellement (jour 136). On sépare l'écriture car la cible peut changer (SQLite → Postgres) sans toucher au reste.

Pourquoi cette séparation est décisive : elle permet de TESTER chaque étape isolément (transform sans base ni réseau), de REMPLACER une source ou une cible sans réécrire le pipeline, et de DÉBUGGER en localisant l'étape fautive. C'est l'architecture propre (responsabilités isolées) appliquée aux données — le pendant du découpage stockage/métier/interface du jour 121.

La notion de STAGING : entre les étapes, on matérialise parfois les données intermédiaires (fichier ou table de staging) pour rejouer une étape sans refaire les précédentes, et pour inspecter ce qui se passe entre E, T et L.

La règle du jour : **conçois le pipeline en trois étapes strictement séparées (extract lit, transform traite en mémoire, load écrit), chacune testable et remplaçable ; le brut ne se mélange jamais au traitement ni à l'écriture**. Un ETL bien conçu se lit étape par étape et se débogue en localisant laquelle a échoué.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : concevoir (papier + code) un pipeline extract (CSV+API) → transform → load (SQLite).

**Exemple simple** : la signature qui matérialise la séparation — `extract() -> dict[str, DataFrame]`, `transform(sources) -> DataFrame`, `load(df) -> None`. Trois fonctions, trois responsabilités ; `load(transform(extract()))` compose le tout. Chaque étape se teste seule.

**Raisonnement pas-à-pas** : dessiner le flux (sources → étapes → cible) → une fonction par étape, sans chevauchement → transform en fonctions pures → load transactionnel dans un schéma pensé.

**Conception + code** :
```
FLUX :  ([CSV ventes] + [API taux])  →  EXTRACT  →  TRANSFORM (nettoie, joint, convertit)  →  LOAD  →  [SQLite]
```
```python
def extract() -> dict:                                  # E : lire le BRUT, gérer erreurs de source
    ventes = pd.read_csv("ventes.csv")
    taux = requests.get(URL_TAUX, timeout=10).json()    # (try/except sur la source)
    return {"ventes": ventes, "taux": taux}

def transform(sources: dict) -> pd.DataFrame:           # T : tout en MÉMOIRE, fonctions pures
    df = clean(sources["ventes"])                        # jour 132
    df = valider(df)
    df["montant_eur"] = df["montant"] * sources["taux"]["eur"]
    return df                                            # aucune écriture ici

def load(df: pd.DataFrame, con) -> None:                # L : écrire, transactionnel (jour 136)
    with con:                                            # transaction implicite
        df.to_sql("ventes", con, if_exists="replace", index=False)

load(transform(extract()), sqlite3.connect("entrepot.db"))   # composition
```

**Mini-quiz** : (a) Pourquoi ne pas nettoyer pendant l'extraction ? (b) Que contient l'étape transform, jamais ? (c) Pourquoi séparer le load ?
→ (a) pour pouvoir rejouer une transformation sans re-télécharger, et isoler les erreurs de source des erreurs de traitement ; (b) aucune écriture en base — c'est le rôle du load ; (c) pour changer de cible (SQLite → Postgres) sans toucher au reste, et tester le traitement sans base.

**Variante** : matérialise le résultat de `extract` dans un fichier de staging (`brut.parquet`) — tu peux alors rejouer `transform` autant de fois que tu veux sans rappeler l'API, ce qui accélère énormément le développement.

## 🏢 Cas métier
L'ETL est l'ossature de toute infrastructure de données : amener des sources hétérogènes (fichiers, API, bases) vers un entrepôt propre est le travail quotidien des data engineers. La séparation extract/transform/load n'est pas académique : elle permet de rejouer une transformation sans re-télécharger (crucial quand une source est lente ou limitée en appels), de remplacer une source ou une cible sans tout réécrire, et de localiser une panne (est-ce l'extraction, le traitement ou l'écriture ?). Les pipelines qui mélangent tout dans une fonction fourre-tout deviennent impossibles à tester, à rejouer et à maintenir. Concevoir un ETL en étapes séparées est une compétence de data engineering fondamentale, directement mise en œuvre dans le projet DataPulse (jours 141-144) et valorisée sur le marché.

## 🎤 Question d'entretien
**« Comment conçois-tu un pipeline ETL ? »** → En trois étapes strictement séparées. EXTRACT : lire les sources telles quelles (CSV, API), gérer les erreurs de SOURCE, sans rien transformer — pour pouvoir rejouer la suite sans re-télécharger. TRANSFORM : tout le traitement EN MÉMOIRE (nettoyer, valider, normaliser, joindre, dériver), en fonctions pures testables, sans aucune écriture en base. LOAD : écrire le résultat propre dans la cible, dans un schéma pensé et transactionnellement. Cette séparation permet de tester chaque étape isolément (transform sans base ni réseau), de remplacer une source ou une cible sans réécrire le pipeline, et de localiser une panne à l'étape fautive. C'est l'architecture propre appliquée aux données. J'ajoute souvent un staging entre les étapes pour rejouer une étape sans refaire les précédentes.
