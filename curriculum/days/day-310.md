## 🎯 Objectif du jour
Le moteur avec la bonne config.

## 📖 Cours approfondi
**Modèle mental : construire le RAG core « en architecture cible dès le départ » signifie appliquer TOUT ce que tu as appris (la config optimale du mois 9, l'architecture hexagonale du mois 10) directement, au lieu de bricoler puis refactorer — tu ne réapprends pas, tu ASSEMBLES tes acquis en un système propre.** Le RAG core est le moteur de DocSense : le pipeline question → retrieval → génération citée. Le point clé du jour n'est pas de redécouvrir le RAG (tu l'as construit et évalué au mois 9) mais de le RECONSTRUIRE PROPREMENT, avec la bonne configuration et la bonne architecture d'emblée.

Ce que « architecture cible dès le départ » implique :
1. **La config optimale du mois 9** : tu as MESURÉ la meilleure stratégie de chunking (jour 241), le meilleur modèle d'embedding (243), la config de retrieval consolidée (251). Tu ne repars pas de zéro ni de valeurs par défaut — tu appliques directement la config JUSTIFIÉE par tes mesures. C'est le bénéfice d'avoir évalué : tu construis sur des décisions chiffrées.
2. **L'architecture hexagonale d'emblée** (jour 289) : le cœur (logique RAG) derrière des ports, les détails (vector DB, LLM) dans des adapters. Construire hexagonal DÈS LE DÉPART évite le refactoring douloureux — et rend le cœur testable en isolation (avec des stubs) dès la première fonctionnalité.
3. **Le pont vers les fonctionnalités à venir** : le RAG core est la fondation sur laquelle s'ajouteront le retrieval hybride (jour 311), les citations (312), le workflow d'analyse (323). Le construire proprement rend ces ajouts naturels ; le bricoler les rendrait pénibles.

Pourquoi « propre dès le départ » plutôt que « bricoler puis refactorer » : le refactoring d'un système qui marche est coûteux et risqué (on casse ce qui marchait). Construire propre d'emblée, quand on SAIT déjà la bonne architecture et la bonne config (grâce au mois 9-10), est plus rapide au total. C'est le privilège de l'expérience : la première fois (mois 9) tu explorais et mesurais ; maintenant tu appliques ce que tu as appris. C'est aussi ce qui distingue un projet final abouti d'un énième prototype : DocSense n'est pas un exercice d'apprentissage du RAG, c'est la DÉMONSTRATION que tu sais construire un RAG de qualité, directement.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : le RAG core de DocSense avec la config optimale du mois 9, en architecture hexagonale.

**Exemple simple** : le cœur reçoit des PORTS, pas des technos — `MoteurRAG(stockage: StockageVecteurs, generateur: Generateur)` ; Chroma et l'API LLM sont injectés à la racine. Le cœur est testable avec des stubs dès aujourd'hui.

**Raisonnement pas-à-pas** : poser le cœur hexagonal, y brancher la config mesurée du mois 9, valider sur le corpus DocSense.

**Implémentation** :
```python
# Cœur (domaine) — reçoit des ports, applique la config JUSTIFIÉE du mois 9
class MoteurRAG:
    def __init__(self, stockage: StockageVecteurs, generateur: Generateur,
                 config: ConfigRAG):        # config du mois 9 : chunking structurel,
        self.config = config                #   modèle d'embedding choisi, k=3...
    def repondre(self, question: str) -> ReponseCitee:
        chunks = self.stockage.chercher(embed(question), self.config.k)
        return self.generateur.generer(question, chunks)   # génération citée (j.312)

# Racine de composition : les adapters concrets + la config mesurée
moteur = MoteurRAG(ChromaAdapter(), LLMAdapter(),
                   config=CONFIG_MOIS9)     # PAS des valeurs par défaut
```

**Mini-quiz** : (a) Pourquoi appliquer la config du mois 9 plutôt que des valeurs par défaut ? (b) Pourquoi construire hexagonal DÈS LE DÉPART ? (c) Que démontre DocSense qu'un énième prototype ne démontre pas ?
→ (a) elle est JUSTIFIÉE par des mesures — construire sur des décisions chiffrées, pas au hasard ; (b) éviter le refactoring douloureux et rendre le cœur testable dès la première fonctionnalité ; (c) que tu sais construire un RAG de QUALITÉ directement, pas juste apprendre le RAG.

**Variante** : écris un test du cœur (MoteurRAG) avec un StockageVecteurs stub et un Générateur stub — il tourne sans Chroma ni appel LLM réel. La testabilité en isolation est le bénéfice immédiat de l'hexagonal (jour 289), à exploiter dès maintenant.
