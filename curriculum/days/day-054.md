## 🎯 Objectif du jour
Rendre une API robuste : valider toutes les entrées, centraliser les erreurs, ne jamais crasher ni fuiter.

## 📖 Cours approfondi
**Concepts abordés :** Validation des entrées · Middleware d'erreurs central · Erreur opérationnelle vs bug · Logs sans fuite.

Une API robuste part d'un principe : TOUTE entrée est hostile jusqu'à validation. Chaque champ est vérifié (présence, type, bornes, format) à l'entrée, et le refus est précis : 400 avec la liste des problèmes (ton pattern collecteur du jour 5).

La gestion d'erreurs se CENTRALISE : un middleware d'erreurs final attrape tout, distingue l'erreur OPÉRATIONNELLE (attendue : ressource absente → 404, entrée invalide → 400, on informe le client) du BUG (inattendu : on log les détails en interne, on répond un 500 générique — les détails internes ne fuient JAMAIS au client, c'est une règle de sécurité).

Le test d'une API robuste : l'attaquer soi-même. Dix requêtes malveillantes (types faux, champs manquants, ids absurdes, corps géant, JSON invalide) — chacune doit recevoir une réponse propre, jamais un crash ni une stack trace.

**Modèle mental : une API robuste part d'un principe non négociable — TOUTE entrée est HOSTILE jusqu'à validation. Chaque champ est vérifié à l'ENTRÉE (présence, type, bornes, format) et un refus est PRÉCIS (400 + la liste des problèmes). Les erreurs se CENTRALISENT dans un middleware final qui distingue l'erreur OPÉRATIONNELLE (attendue : 404, 400 — on informe le client) du BUG (inattendu : 500 générique, détails loggés en interne, jamais fuités). Le test d'une API robuste, c'est de l'ATTAQUER soi-même.** La robustesse n'est pas un ajout : c'est la différence entre une API qu'on peut exposer et une bombe à retardement.

Pourquoi valider aux frontières. L'entrée d'une API (corps, paramètres, query) vient du DEHORS : un client bogué, un utilisateur maladroit, un attaquant. Si on lui fait confiance, un champ manquant plante le traitement, un type inattendu propage un `NaN`, une valeur hors bornes corrompt les données, une injection compromet la base (jour 57). Valider À LA FRONTIÈRE (le point d'entrée) permet à tout l'intérieur de faire CONFIANCE aux données — la validation est le poste de douane de l'API.

La validation précise, depuis les fondations. Pour chaque champ : est-il PRÉSENT (obligatoire) ? du bon TYPE ? dans les BORNES (longueur, min/max) ? au bon FORMAT (email, date) ? Le refus ne dit pas juste « invalide » : il RENVOIE LA LISTE des problèmes (400 + `{erreurs: [...]}`), en utilisant le pattern collecteur (jour 5) — on accumule toutes les erreurs plutôt que de s'arrêter à la première, pour que le client corrige tout d'un coup.

La centralisation des erreurs, depuis les fondations. Plutôt que de gérer les erreurs dans chaque route (duplication, oublis, fuites), un MIDDLEWARE D'ERREURS FINAL (à 4 arguments : `(err, req, res, next)`) attrape tout. Il distingue deux natures : l'erreur OPÉRATIONNELLE (attendue, fait partie du fonctionnement : ressource absente → 404, entrée invalide → 400) qu'on communique clairement au client ; et le BUG (inattendu, une exception non prévue) qu'on LOGGE en interne avec les détails, mais auquel on répond un 500 GÉNÉRIQUE. Règle de sécurité absolue : les détails internes (stack trace, requête SQL, chemin de fichier) ne FUITENT JAMAIS au client — ils renseignent un attaquant.

La différence erreur opérationnelle vs bug. L'erreur OPÉRATIONNELLE est prévue et normale (un 404 n'est pas un dysfonctionnement, c'est une réponse) : on informe. Le BUG est une défaillance imprévue : on protège (500 générique au client) et on diagnostique (log interne détaillé). Les confondre mène soit à exposer des détails sensibles, soit à masquer des erreurs légitimes derrière des 500 opaques.

Le test par l'attaque. Une API se prouve robuste en l'ATTAQUANT : dix requêtes malveillantes (types faux, champs manquants, ids absurdes, corps géant, JSON invalide, injection) — chacune doit recevoir une réponse PROPRE (statut adapté + message utile), jamais un crash ni une stack trace. Si une seule fait tomber le process, l'API n'est pas prête.

Limites et compromis. La validation exhaustive est un travail ingrat mais décisif ; des bibliothèques (Zod, Joi) l'allègent, mais comprendre le raisonnement à la main d'abord est formateur. Trop de validation peut rigidifier une API ; trop peu la fragilise — le bon niveau valide ce qui entre dans la logique. Et distinguer opérationnel/bug demande de la discipline à chaque throw.

La règle du jour : **traite toute entrée comme hostile jusqu'à validation (présence/type/bornes/format, 400 + liste des problèmes), centralise les erreurs dans un middleware final qui distingue l'opérationnel (404/400, on informe) du bug (500 générique, détails loggés en interne, jamais fuités), et PROUVE la robustesse en attaquant ta propre API.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : valider une entrée en collectant TOUTES les erreurs, et centraliser la gestion dans un middleware qui ne fuite jamais les détails internes.

**Exemple simple** : validation qui collecte vs qui s'arrête. S'arrêter à la première erreur force le client à corriger un problème à la fois. Collecter toutes les erreurs (`{erreurs: ['titre requis', 'note doit être 1-5']}`) lui permet de tout corriger d'un coup — le pattern collecteur du jour 5.

**Raisonnement pas-à-pas** : (1) je vérifie chaque champ (présence, type, bornes) en ACCUMULANT les erreurs ; (2) si la liste n'est pas vide → 400 + la liste ; (3) sinon, la logique fait confiance aux données ; (4) le middleware d'erreurs final distingue opérationnel (statut informatif) et bug (500 générique, log interne).

**Implémentation** :
```ts
// Validation qui COLLECTE toutes les erreurs (pattern collecteur, jour 5)
function validerCitation(body: any): string[] {
  const erreurs: string[] = [];
  if (typeof body?.texte !== 'string' || !body.texte.trim()) erreurs.push('texte requis (string non vide)');
  if (body.note !== undefined && (typeof body.note !== 'number' || body.note < 1 || body.note > 5))
    erreurs.push('note doit être un nombre entre 1 et 5');
  return erreurs;                       // vide = valide
}

app.post('/citations', (req, res, next) => {
  const erreurs = validerCitation(req.body);
  if (erreurs.length) return res.status(400).json({ erreurs });   // refus PRÉCIS
  try {
    res.status(201).json(serviceCitations.ajouter(req.body));
  } catch (e) { next(e); }             // délègue au middleware d'erreurs
});

// MIDDLEWARE D'ERREURS CENTRAL (4 arguments), en DERNIER
class ErreurOperationnelle extends Error { constructor(msg: string, public statut: number) { super(msg); } }

app.use((err: Error, _req: Request, res: Response, _next: NextFunction) => {
  if (err instanceof ErreurOperationnelle) {
    return res.status(err.statut).json({ message: err.message });   // attendu : on INFORME
  }
  console.error('BUG interne :', err);                              // log détaillé EN INTERNE
  res.status(500).json({ message: 'Erreur interne' });              // au client : GÉNÉRIQUE, zéro détail
});
```
Le client reçoit un 400 avec toutes les erreurs (utile) ou un 500 générique (sûr) ; les détails d'un bug sont loggés côté serveur, jamais renvoyés. Le process ne crashe sur aucune entrée.

## ⚠️ Erreurs fréquentes
- Valider à une porte et en oublier une autre : une entrée non validée s'infiltre.
- Renvoyer la stack trace ou le détail d'un 500 au client : fuite d'information exploitable par un attaquant.
- Confondre erreur opérationnelle et bug : exposer des détails sensibles ou masquer des erreurs légitimes derrière des 500 opaques.
- S'arrêter à la première erreur de validation au lieu de collecter toutes les erreurs pour le client.

## 🏢 Cas métier
La validation aux frontières et la gestion d'erreurs centralisée sont la première ligne de défense de tout service exposé, et leur absence est la source n°1 des incidents et des failles en production. Une entrée non validée cause des crashs (champ manquant), des corruptions de données (type ou bornes non vérifiés) et des vulnérabilités (injection). Une gestion d'erreurs qui fuit des détails internes (stack trace, requête SQL) offre une carte à un attaquant — c'est un défaut de sécurité classique relevé en audit. À l'inverse, une API qui valide tout, distingue proprement l'attendu de l'imprévu et ne fuite rien inspire confiance et résiste aux abus. Les équipes matures utilisent des schémas de validation (Zod, Joi) et un middleware d'erreurs central systématique. Savoir durcir une API et l'attaquer soi-même est une compétence directement valorisée (sécurité, fiabilité) et un sujet d'entretien récurrent (« comment rends-tu une API robuste ? »).

## 🎤 Question d'entretien
**« Comment rends-tu une API robuste face à des entrées malveillantes ou inattendues ? »** → Je pars du principe que TOUTE entrée est hostile jusqu'à validation. À la frontière, je vérifie chaque champ — présence, type, bornes, format — et je renvoie un refus PRÉCIS : un 400 avec la LISTE de tous les problèmes, pas juste le premier, pour que le client corrige tout d'un coup. Ensuite, tout l'intérieur peut faire confiance aux données. Pour les erreurs, je CENTRALISE dans un middleware final (4 arguments) qui distingue deux natures : l'erreur OPÉRATIONNELLE, attendue et normale (404 pour une ressource absente, 400 pour une entrée invalide), que je communique clairement ; et le BUG, une défaillance imprévue, auquel je réponds un 500 GÉNÉRIQUE tout en loggant les détails EN INTERNE. Règle de sécurité absolue : les détails internes — stack trace, requête SQL — ne fuient JAMAIS au client, car ils renseignent un attaquant. Enfin, je PROUVE la robustesse en attaquant ma propre API : une dizaine de requêtes malveillantes (types faux, champs manquants, corps géant, JSON invalide), chacune devant recevoir une réponse propre sans jamais faire crasher le process. **Relance possible** : « qu'est-ce qui peut mal tourner entre le client et la base, et qui répond quoi ? » → entrée invalide → 400 (validation) ; ressource absente → 404 ; conflit métier → 409 ; base indisponible ou exception imprévue → 500 générique loggé en interne. Chaque cas a un responsable et un statut.
