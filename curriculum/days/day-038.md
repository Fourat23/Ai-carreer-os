## 🎯 Objectif du jour
Maîtriser les 4 piliers POO en TS et savoir quand une classe est le bon outil.

## 📖 Cours approfondi
**Concepts abordés :** Classe, constructeur · private/readonly · Héritage / super · Polymorphisme via interface · Composition > héritage.

La POO regroupe données + comportements dans des objets. Les 4 piliers : encapsulation (cacher l'état interne — `private`), abstraction (exposer un contrat simple), héritage (une classe en étend une autre — à utiliser avec parcimonie), polymorphisme (traiter des objets différents via un contrat commun).

Le polymorphisme par interface est le pilier le plus utile : `alerter(notifieurs: Notifieur[])` ne connaît que le contrat `envoyer()` — ajouter Slack demain = une classe de plus, ZÉRO modification d'alerter. C'est le principe open/closed, et le germe de l'inversion de dépendance (ton interface Store au jour 44).

La règle moderne : composition > héritage. Un héritage profond (A extends B extends C) est fragile ; assembler des comportements est plus souple. Et une fonction pure + closure fait souvent le même travail qu'une petite classe : compare honnêtement.

**Modèle mental : les quatre piliers de la POO (encapsulation, abstraction, héritage, polymorphisme) servent UN seul but pratique — programmer contre une INTERFACE (un contrat) plutôt que contre une implémentation. Le polymorphisme est le cœur : une fonction `alerter(notifieurs: Notifieur[])` ne connaît QUE le contrat `envoyer()`, jamais les classes concrètes ; ajouter un canal Slack demain = une classe de plus, ZÉRO modification ailleurs. C'est le principe ouvert/fermé, et le germe de l'inversion de dépendance.** La POO bien comprise n'est pas « tout mettre en classes » : c'est isoler ce qui varie derrière un contrat stable.

Pourquoi la POO existe. À mesure qu'un programme grandit, le vrai défi est le COUPLAGE : quand ajouter une fonctionnalité oblige à modifier dix endroits, le code devient fragile. La POO propose de regrouper données + comportements dans des objets, de CACHER l'état interne (pour que personne ne dépende des détails), et d'exposer des contrats stables. Le bénéfice : on peut faire évoluer les implémentations derrière un contrat sans casser le reste.

Les quatre piliers, depuis les fondations. **Encapsulation** : cacher l'état (`private`, `readonly`) et n'exposer que des méthodes — l'objet garantit ses propres invariants, personne ne le met dans un état incohérent de l'extérieur. **Abstraction** : exposer un contrat simple (`envoyer(msg)`) en masquant la complexité (l'API SMTP derrière Email). **Héritage** : une classe étend une autre (`extends`, `super`) pour réutiliser — puissant mais à manier avec parcimonie. **Polymorphisme** : traiter des objets de types différents via un contrat commun — le pilier qui donne la souplesse.

Le polymorphisme par interface, en détail. On définit `interface Notifieur { envoyer(msg: string): void }`. Email, SMS, Push l'implémentent chacun à sa façon. `alerter(notifieurs: Notifieur[], msg)` itère et appelle `envoyer` sans savoir laquelle : c'est le CONTRAT qui garantit que l'appel a un sens. Ajouter Slack = écrire `class Slack implements Notifieur` — `alerter` n'est pas touchée. C'est l'open/closed (ouvert à l'extension, fermé à la modification) et l'inversion de dépendance (dépendre de l'abstraction, pas du concret — exactement ton interface `Store` du jour 44).

La différence héritage vs composition, et vs fonctionnel. L'**héritage** crée un lien fort « est-un » : un héritage profond (A extends B extends C) est FRAGILE, car un changement dans B casse A. La **composition** (« a-un » : assembler des comportements) est plus souple et souvent préférable — d'où la règle « composition > héritage ». Et une **fonction pure + closure** (jour 22) fait souvent le travail d'une petite classe : la classe se justifie quand on a un ÉTAT encapsulé avec des méthodes qui l'opèrent ; sinon, une fonction suffit.

Limites et compromis. La POO ajoute de la CÉRÉMONIE (classes, interfaces) : sur-appliquée, elle noie une logique simple sous des couches inutiles. Tout mettre en classe par réflexe est un anti-pattern. Le bon jugement : classe pour un état + comportements liés ou pour du polymorphisme ; fonction pour une transformation sans état.

La règle du jour : **programme contre des contrats (interfaces), pas contre des implémentations. Encapsule l'état, exploite le polymorphisme pour être ouvert à l'extension et fermé à la modification, préfère la composition à l'héritage, et n'utilise une classe que quand un état encapsulé le justifie — sinon une fonction suffit.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : construire un système de notifications polymorphe — une interface `Notifieur`, plusieurs implémentations, une fonction `alerter` qui ne dépend que du contrat.

**Exemple simple** : la puissance du contrat. `alerter` écrite une fois pour toutes ne mentionne JAMAIS Email ni SMS ; elle appelle `envoyer` sur des `Notifieur`. C'est ce découplage qui rend l'ajout d'un canal indolore.

**Raisonnement pas-à-pas** : (1) je définis le CONTRAT (`interface Notifieur`) ; (2) chaque canal l'implémente à sa manière ; (3) `alerter` prend une liste de `Notifieur` et appelle le contrat, sans connaître les classes ; (4) je PROUVE l'open/closed en ajoutant un canal sans toucher `alerter`.

**Implémentation** :
```ts
interface Notifieur { envoyer(msg: string): void; }

class Email implements Notifieur {
  constructor(private readonly adresse: string) {}   // état encapsulé
  envoyer(msg: string): void { console.log(`[Email->${this.adresse}] ${msg}`); }
}
class SMS implements Notifieur {
  constructor(private readonly numero: string) {}
  envoyer(msg: string): void { console.log(`[SMS->${this.numero}] ${msg}`); }
}

// Polymorphe : ne connaît QUE le contrat 'envoyer'
function alerter(notifieurs: Notifieur[], msg: string): void {
  for (const n of notifieurs) n.envoyer(msg);
}

alerter([new Email('a@ex.fr'), new SMS('0600')], 'Serveur down !');

// OUVERT à l'extension : ajouter Slack ne modifie PAS alerter
class Slack implements Notifieur {
  constructor(private readonly canal: string) {}
  envoyer(msg: string): void { console.log(`[Slack#${this.canal}] ${msg}`); }
}
alerter([new Slack('ops')], 'Nouveau canal, zéro modif ailleurs.');
```

**La version fonctionnelle, pour comparer** :
```ts
type Notifier = (msg: string) => void;
const email = (adr: string): Notifier => msg => console.log(`[Email->${adr}] ${msg}`);
const alerterFn = (ns: Notifier[], msg: string) => ns.forEach(n => n(msg));
// Même découplage avec une fonction + closure : la classe se justifie surtout
// quand l'objet porte PLUSIEURS méthodes et un état riche.
```

## ⚠️ Erreurs fréquentes
- Recourir à un héritage profond fragile là où la composition (ou une interface) suffirait.
- Tout mettre en classe par réflexe : une fonction pure convient souvent mieux qu'une classe sans état.
- Écrire `alerter` avec des `if canal === …` au lieu du polymorphisme : chaque ajout force une modification et une régression possible.
- Exposer l'état interne (pas de private) : d'autres finissent par en dépendre, ce qui casse l'encapsulation.

## 🏢 Cas métier
Le polymorphisme par interface est le mécanisme qui rend les systèmes d'entreprise EXTENSIBLES. Un service de paiement définit une interface `MoyenPaiement` ; Carte, PayPal, Virement l'implémentent ; le moteur de commande ne connaît que le contrat. Ajouter Apple Pay = une classe, sans toucher le moteur ni risquer de régression sur les moyens existants. Même schéma pour les exporteurs (PDF/CSV/Excel), les stratégies de tarification, les fournisseurs de stockage (S3/local/GCS). Ce découplage réduit le coût et le risque de chaque évolution — la valeur business directe d'une bonne conception objet. À l'inverse, un code où `alerter` contiendrait un `if canal === 'email' … else if … ` doit être modifié (et re-testé) à chaque nouveau canal. Savoir concevoir contre des interfaces, et arbitrer classe vs fonction vs héritage vs composition, est évalué en entretien back et lors des revues de code.

## 🎤 Question d'entretien
**« Explique le polymorphisme avec un exemple, et pourquoi il rend le code extensible. »** → Le polymorphisme, c'est traiter des objets de types différents via un CONTRAT commun. Exemple : une interface `Notifieur { envoyer(msg) }` implémentée par Email, SMS, Push. Une fonction `alerter(notifieurs: Notifieur[])` itère et appelle `envoyer` sans jamais connaître les classes concrètes — c'est le contrat qui garantit que l'appel a un sens. Le bénéfice : ajouter un canal Slack = écrire `class Slack implements Notifieur`, ZÉRO modification d'`alerter`. C'est le principe ouvert/fermé (ouvert à l'extension, fermé à la modification) et le germe de l'inversion de dépendance : on dépend de l'abstraction, pas du concret. Sans polymorphisme, `alerter` serait une cascade de `if canal === …` à modifier et re-tester à chaque ajout. **Relance possible** : « faut-il tout mettre en classes ? » → non : la classe se justifie pour un état encapsulé avec des méthodes liées ou pour du polymorphisme ; une simple transformation sans état se fait mieux avec une fonction pure. Et je préfère la composition à l'héritage profond, plus fragile.
