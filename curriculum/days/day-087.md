## 📖 Cours approfondi
**Concepts abordés :** Composant · JSX · props/state · useState · Rendu déclaratif · Immutabilité (jour 26).

Le modèle mental de React tient en une équation : UI = f(state). Tu ne modifies JAMAIS l'interface directement (pas de « trouve cet élément et change son texte ») — tu décris à quoi l'UI DOIT ressembler pour chaque état possible, et React recalcule le rendu quand l'état change.

Le state se modifie exclusivement via son setter (`setCompteur(n + 1)`), et de façon IMMUABLE : `setListe([...liste, nouvelItem])`, jamais `liste.push(...)`. Pourquoi ? React détecte les changements par comparaison de RÉFÉRENCES — une mutation garde la même référence, React ne voit rien, l'écran ne bouge pas. Ta discipline d'immutabilité du jour 26 n'était pas un dogme : c'était l'entraînement pour aujourd'hui.

Un composant est une FONCTION qui reçoit des props et retourne du JSX : la composition de fonctions (jour 22), appliquée à l'interface.

**Modèle mental : React tient en une équation — UI = f(state). Tu ne modifies JAMAIS l'interface directement (pas de « trouve cet élément et change son texte ») : tu DÉCRIS à quoi l'UI doit ressembler pour chaque état possible, et React recalcule le rendu quand l'état change. Le state se modifie exclusivement via son setter et de façon IMMUABLE (`setListe([...liste, item])`, jamais `liste.push()`) — parce que React détecte les changements par comparaison de RÉFÉRENCES : une mutation garde la même référence, React ne voit rien, l'écran ne bouge pas.** Les premiers pas React, c'est adopter le rendu déclaratif et comprendre pourquoi l'immutabilité (jour 26) y est OBLIGATOIRE.

Pourquoi le rendu déclaratif. En manipulation directe du DOM (jQuery, vanilla), on décrit COMMENT changer l'UI étape par étape (« trouve ce div, change son texte, ajoute cette classe ») — fragile et vite ingérable quand l'état se complexifie. React inverse : on décrit CE QUE l'UI doit être pour un état donné (déclaratif), et React se charge du COMMENT (calculer les changements du DOM). On raisonne sur des ÉTATS, pas sur des transitions — bien plus simple à mesure que l'application grandit.

L'équation UI = f(state), depuis les fondations. Un composant est une FONCTION qui, à partir de son état (et de ses props), retourne à quoi l'UI doit ressembler (en JSX). Quand l'état change, React RÉ-EXÉCUTE la fonction et met à jour le DOM pour correspondre au nouveau rendu. Tu ne touches jamais le DOM toi-même : tu changes l'état, React re-rend. C'est un changement de mentalité fondamental par rapport à la manipulation directe.

Le state et son setter, depuis les fondations. Le state (`useState`) est la mémoire d'un composant entre les rendus. On ne le modifie QUE via son setter (`setCompteur(n + 1)`), jamais par affectation directe (`compteur = n + 1` ne déclenche aucun rendu). Le setter dit à React « l'état a changé, re-rends » — c'est le signal qui déclenche la mise à jour de l'UI.

Pourquoi l'immutabilité est OBLIGATOIRE, depuis les fondations. React détecte un changement d'état en comparant les RÉFÉRENCES (l'ancienne valeur === la nouvelle ?). Si tu MUTES (`liste.push(item)`), la référence de `liste` reste la MÊME : React compare, voit « identique », et NE re-rend PAS — l'écran ne bouge pas alors que les données ont changé. Si tu crées une NOUVELLE référence (`setListe([...liste, item])`), React voit une valeur différente et re-rend. L'immutabilité (jour 26) n'est donc pas un style en React : c'est une CONDITION de fonctionnement.

La différence état vs dérivé. On stocke dans le state ce qui est une VRAIE donnée d'état (la liste des tâches) ; ce qui se CALCULE à partir du state (le nombre de tâches non finies) ne se stocke PAS — on le dérive au rendu. Stocker un dérivé crée des risques de désynchronisation (le dérivé et sa source divergent). La règle : minimiser le state, dériver le reste.

Limites et compromis. Le rendu déclaratif a une courbe d'apprentissage (renoncer à la manipulation directe). L'immutabilité par copie a un léger coût (négligeable ici). Et sur-découper en composants ou tout mettre en state complique — l'équilibre vient avec la pratique. Le modèle UI = f(state) est puissant mais demande d'adopter sa mentalité pour ne pas « se battre contre React ».

La règle du jour : **React, c'est UI = f(state) : tu décris l'UI pour chaque état, tu ne touches jamais le DOM directement. Modifie le state UNIQUEMENT via son setter et de façon IMMUABLE (nouvelle référence) — une mutation ne re-rend pas, car React compare les références. Minimise le state, dérive le reste.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : construire une liste de tâches React où l'ajout est IMMUABLE, et comprendre pourquoi une mutation ne re-rend pas.

**Exemple simple** : mutation vs immutabilité. `taches.push(nouvelle); setTaches(taches)` NE re-rend PAS (même référence, React ne voit rien). `setTaches([...taches, nouvelle])` re-rend (nouvelle référence). La différence tient à la comparaison de références de React.

**Raisonnement pas-à-pas** : (1) le state contient la liste (vraie donnée) ; (2) le nombre de tâches finies est DÉRIVÉ (pas stocké) ; (3) l'ajout crée une NOUVELLE liste (immuable) ; (4) je ne touche jamais le DOM, je change le state.

**Implémentation (Vite + React + TS)** :
```tsx
import { useState } from 'react';

interface Tache { id: number; titre: string; fait: boolean; }

export function ListeTaches() {
  const [taches, setTaches] = useState<Tache[]>([]);   // STATE : vraie donnée
  const nbFaites = taches.filter(t => t.fait).length;  // DÉRIVÉ : calculé, pas stocké

  function ajouter(titre: string) {
    // IMMUABLE : nouvelle référence -> React re-rend
    setTaches([...taches, { id: Date.now(), titre, fait: false }]);
    // taches.push(...) ; setTaches(taches)  // NE re-rendrait PAS (même référence)
  }
  function basculer(id: number) {
    // mise à jour immuable ciblée (map, jour 26) -> nouvelle référence
    setTaches(taches.map(t => t.id === id ? { ...t, fait: !t.fait } : t));
  }

  // UI = f(state) : on DÉCRIT l'UI pour l'état courant, React s'occupe du DOM
  return (
    <div>
      <p>{nbFaites} / {taches.length} faites</p>
      <ul>{taches.map(t => (
        <li key={t.id} onClick={() => basculer(t.id)}
            style={{ textDecoration: t.fait ? 'line-through' : 'none' }}>
          {t.titre}
        </li>
      ))}</ul>
    </div>
  );
}
```
Le state ne contient que la vraie donnée (la liste) ; le nombre de faites est dérivé ; les mises à jour créent de NOUVELLES références (immuables), ce qui déclenche le re-rendu. On décrit l'UI pour l'état courant sans jamais toucher le DOM — c'est UI = f(state).

## ⚠️ Erreurs fréquentes
- Muter le state (state.push, affectation directe) : React ne détecte rien, l'UI ne se met pas à jour.
- Stocker une valeur dérivée dans le state : risque de désynchronisation avec sa source.
- Toucher le DOM directement au lieu de changer le state : on se bat contre le modèle de React.
- Modifier le state par affectation au lieu du setter : aucun rendu déclenché.

## 🏢 Cas métier

Comprendre ce modèle est un prérequis pour tout poste full-stack ou front en entreprise. La règle de l'immutabilité du state est LA source de bugs des débutants React : une mutation qui ne re-rend pas produit une UI « bloquée » incompréhensible tant qu'on n'a pas compris la comparaison de références — c'est exactement pourquoi l'immutabilité travaillée au jour 26 devient ici une condition de fonctionnement, pas un style. Le rendu déclaratif rend les interfaces complexes gérables : on raisonne sur des états plutôt que sur des séquences de manipulations du DOM, ce qui réduit drastiquement les bugs d'UI. ## 🎤 Question d'entretien
**« Pourquoi ne faut-il jamais muter le state en React ? »** → Parce que React détecte les changements d'état en comparant les RÉFÉRENCES. Le modèle mental de React est UI = f(state) : je ne touche jamais le DOM directement, je décris à quoi l'UI doit ressembler pour un état donné, et React recalcule le rendu quand l'état change. Pour savoir QUAND recalculer, React compare l'ancienne valeur du state et la nouvelle par référence. Si je MUTE — par exemple `liste.push(item)` — la référence de `liste` reste la même : React compare, voit « identique », et ne re-rend PAS, alors que les données ont pourtant changé. L'écran reste bloqué, ce qui est le bug classique du débutant. Il faut au contraire créer une NOUVELLE référence : `setListe([...liste, item])` pour un ajout, ou `map` pour une mise à jour ciblée. React voit alors une valeur différente et re-rend. C'est exactement pourquoi l'immutabilité n'est pas un style en React mais une CONDITION de fonctionnement. Et je modifie le state uniquement via son setter, jamais par affectation directe, car le setter est le signal qui déclenche le rendu. **Relance possible** : « faut-il tout mettre dans le state ? » → non : je minimise le state à la vraie donnée, et je DÉRIVE au rendu ce qui se calcule (le nombre d'éléments cochés, par exemple) ; stocker un dérivé crée des risques de désynchronisation avec sa source.
