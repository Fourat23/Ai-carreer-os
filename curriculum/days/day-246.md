## 🎯 Objectif du jour
Ajouter la recherche par mots-clés.

## 📖 Cours approfondi
**Modèle mental : le vectoriel comprend le SENS, le lexical retrouve les MOTS — et certaines questions sont des questions de mots.** Ton retrieval vectoriel rapproche « congés » et « vacances » : magique pour les reformulations. Mais demande-lui « erreur E1027 », « article L1234-5 » ou « fonction \`parse_invoice\` » : l'embedding DILUE ces identifiants exacts dans le sens général de la phrase — et le chunk contenant exactement « E1027 » peut perdre contre un chunk qui « parle d'erreurs en général ». C'est la famille d'échecs « vocabulaire » de ton autopsie (jour 226) vue à l'envers : le vectoriel rate aussi des matchs EXACTS.

**BM25** est l'algorithme canonique de la recherche lexicale (celui des moteurs de recherche depuis 30 ans). Son intuition en trois morceaux :
1. **TF (term frequency)** : un document qui répète le terme de la requête est plus pertinent — avec SATURATION (la 10e occurrence vaut moins que la 2e : paramètre k1).
2. **IDF (inverse document frequency)** : un terme RARE dans le corpus (« E1027 ») pèse beaucoup plus qu'un terme banal (« erreur ») — c'est l'IDF qui rend BM25 redoutable sur les identifiants.
3. **Normalisation de longueur** : un long document a mécaniquement plus d'occurrences ; on corrige (paramètre b).

En pratique, tu n'implémentes pas BM25 : **SQLite FTS5** te le donne (tes acquis SQL du mois 5 ressurgissent) — une table virtuelle, tes chunks indexés, \`ORDER BY bm25(table)\`. Les subtilités françaises : la tokenisation (unicode61, accents), et les limites assumées (pas de stemming natif décent en français dans FTS5 : « résiliation » ne matchera pas « résilier » — c'est un cas où le VECTORIEL sauve le lexical, exactement l'inverse d'E1027). Aujourd'hui : construire l'index lexical, et surtout CARTOGRAPHIER sur ton golden set qui gagne où — la carte des forces complémentaires est l'argument du hybrid search de demain.

**Énoncé** : index FTS5 sur tes chunks + cartographie lexical vs vectoriel.

**Raisonnement** : indexer les MÊMES chunks (comparabilité), exposer la même interface top-k, puis confronter les deux moteurs question par question.

**Implémentation** :
```python
import sqlite3
con = sqlite3.connect("lexical.db")
con.execute("""CREATE VIRTUAL TABLE chunks_fts USING fts5(
    chunk_id UNINDEXED, texte, source UNINDEXED,
    tokenize='unicode61 remove_diacritics 2')""")   # accents gérés
con.executemany("INSERT INTO chunks_fts VALUES (?, ?, ?)",
    [(c["id"], c["texte"], c["meta"]["source"]) for c in chunks])

def top_k_lexical(question: str, k=3):
    requete = nettoyer_fts(question)     # échapper les opérateurs FTS5 !
    rows = con.execute(
        """SELECT chunk_id, texte, bm25(chunks_fts) AS score
           FROM chunks_fts WHERE chunks_fts MATCH ?
           ORDER BY score LIMIT ?""", (requete, k)).fetchall()
    return rows                           # NB : bm25() est un COÛT (plus bas = mieux)
```

## 🏢 Cas métier
Les moteurs de recherche d'entreprise (support, juridique, e-commerce) sont TOUS hybrides, et la raison est celle de ta cartographie : les utilisateurs alternent requêtes sémantiques (« comment annuler ma commande ») et requêtes exactes (« commande #48213 », « article 700 CPC »). Un RAG purement vectoriel qui rate les références exactes perd la confiance des juristes et des devs — les deux publics qui vérifient. Savoir POURQUOI (dilution des identifiants dans l'embedding vs IDF) te distingue de ceux qui ajoutent BM25 « parce que tout le monde le fait ».

## 🎤 Question d'entretien
**« Pourquoi ajouter une recherche lexicale à un RAG vectoriel ? »** → Parce que les deux échouent sur des questions différentes : le vectoriel gagne sur les reformulations (synonymes, paraphrases) mais dilue les identifiants exacts (codes d'erreur, références, noms rares) que BM25 attrape via l'IDF des termes rares. Sur mon golden set : le vectoriel écrase sur les reformulées, le lexical fait 4/4 sur les identifiants — l'union des réussites dépasse chaque moteur seul, c'est l'argument mesuré de l'hybride.
