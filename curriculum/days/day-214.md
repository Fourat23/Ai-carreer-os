## 🎯 Objectif du jour
Encapsuler la faillibilité.

## 📖 Cours approfondi
**Modèle mental : tu construis le disjoncteur, pas l'ampoule.** Depuis deux semaines, chaque projet réécrit les mêmes protections : retry, validation, logs, timeout. Aujourd'hui tu les factorises UNE FOIS dans un composant `llm_call()` — la seule porte par laquelle ton code parlera désormais à un LLM. C'est un exercice d'ARCHITECTURE : encapsuler la faillibilité derrière une interface simple.

Les cinq responsabilités du composant :
1. **Validation de sortie** : le composant prend un schéma attendu (ou un validateur) et retourne du VALIDÉ ou une erreur claire — jamais du texte brut à charge du code appelant.
2. **Retry intelligent** : sur erreur transitoire (429, timeout réseau) → backoff exponentiel ; sur sortie invalide → renvoi de l'erreur au modèle (jour 205) ; sur erreur permanente (clé invalide) → échec immédiat. TROIS stratégies selon la nature de l'échec.
3. **Fallback** : au bout des retries, une stratégie déclarée par l'appelant : valeur par défaut, modèle de secours moins cher, ou propagation propre de l'échec.
4. **Observabilité** : chaque appel émet un enregistrement structuré — timestamp, prompt (ou son hash), modèle, tokens in/out, coût, latence, nombre de retries, statut final. C'est la matière première du debugging et du suivi de coûts.
5. **Cache optionnel** : même prompt + même modèle + temp 0 → réponse cachée. Trivial à implémenter (dict/fichier), gains réels en dev et sur les appels répétitifs.

Et la règle qui rend le composant crédible : il est TESTÉ. Les pannes se simulent (mock du client API qui renvoie 429, du JSON cassé, une exception réseau) — tu prouves chaque comportement au lieu de l'espérer.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : le module `llm_call` réutilisable, testé avec des pannes simulées.

**Raisonnement** : définir l'interface d'abord (ce que voit l'appelant), implémenter les couches ensuite, tester chaque comportement avec un client mocké.

**Interface cible** :
```python
resultat = llm_call(
    prompt=PROMPT_EXTRACTION.format(texte=t),
    schema=Conge,                  # validation intégrée (Pydantic)
    max_retries=2,
    fallback=None,                 # ou valeur par défaut, ou modele="petit"
)
# → LlmResult(ok=True, data=Conge(...), cout=0.0021, latence_ms=840, retries=0)
# → LlmResult(ok=False, erreur="validation après 2 retries", ...)
```

**Tests avec pannes simulées (l'essentiel)** :
```python
def test_retry_sur_429(client_mock):
    client_mock.reponses = [Erreur429(), Erreur429(), reponse_valide]
    r = llm_call(..., client=client_mock)
    assert r.ok and r.retries == 2      # backoff appliqué, succès au 3e

def test_fallback_apres_echecs(client_mock):
    client_mock.reponses = [json_casse] * 3
    r = llm_call(..., fallback=CONGE_INCONNU)
    assert r.ok and r.data == CONGE_INCONNU and r.degrade
```

**Explication** : l'injection du client (paramètre `client`) rend tout testable sans réseau ni coût — le pattern d'injection de dépendance du mois 5, appliqué au LLM. **Variante** : branche ton extracteur du jour 205 et ton app du jour 208 sur ce composant — la migration doit SUPPRIMER du code chez les appelants, c'est le signe que la factorisation est bonne.

## ⚠️ Erreurs fréquentes
- Retry uniforme sur tout (y compris clé invalide ou requête malformée) : tu retardes l'échec inévitable et tu masques le vrai problème.
- Logger le prompt complet avec données personnelles : le log de production se réfléchit (hash ou troncature) — réflexe RGPD.
- Cacher des réponses à température > 0 : tu figes UN tirage aléatoire comme s'il était LA réponse.
- Interface qui fuit (l'appelant doit encore parser/valider) : la factorisation a échoué si les appelants gardent leur plomberie.

## 🏢 Cas métier
Dans les équipes matures, ce composant existe toujours — wrapper maison ou gateway LLM — parce que 5 features qui appellent l'API chacune à sa façon = 5 gestions d'erreurs divergentes, des coûts intraçables et des incidents impossibles à diagnostiquer. Arriver en entretien avec « j'ai construit ce composant, voici son interface et ses tests de panne » = démontrer de l'architecture, pas juste de l'intégration.

## 🎤 Question d'entretien
**« Conçois-moi une couche d'appel LLM pour une app de production. »** → Une seule porte d'entrée : validation de sortie par schéma, trois stratégies de retry selon la nature de l'erreur (transitoire → backoff, sortie invalide → renvoi de l'erreur au modèle, permanente → échec immédiat), fallback déclaré par l'appelant, log structuré par appel (tokens, coût, latence, retries), cache optionnel à temp 0. Le tout testé avec un client mocké qui simule les pannes.
