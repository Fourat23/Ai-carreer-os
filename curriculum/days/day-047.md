## 📖 Cours approfondi
**Concepts abordés :** Agrégations (reduce) · Tests (node:test ou Vitest) · README de qualité · ADR.

La dernière ligne droite d'un projet est ce qui sépare « ça marche » de « c'est fini » : les stats (un reduce par statut/priorité), le verrouillage des cas d'erreur UN PAR UN, le README qui rend le projet utilisable par un inconnu en 5 minutes, et l'ADR qui documente ta décision de stockage.

Un ADR (Architecture Decision Record) capture : le contexte, les options considérées, la décision, ses conséquences, et ce qui te ferait changer d'avis. C'est un document d'une page qui vaut de l'or en entretien : il PROUVE que tu arbitres consciemment au lieu de suivre des recettes.

La section « Ce que j'ai appris » du README : 3-5 puces honnêtes. Les recruteurs la lisent — l'honnêteté et la lucidité y sont des signaux forts.

**Modèle mental : la finition est ce qui sépare « ça marche sur ma machine » de « c'est FINI ». Un projet livré, ce sont des stats utiles, des cas d'erreur verrouillés UN PAR UN, des tests sur la logique pure, un README qui rend le projet utilisable par un inconnu en 5 minutes, et un ADR qui PROUVE que tu as arbitré consciemment. Le code qui marche est la moitié du travail ; l'autre moitié — celle qui rend le projet crédible et ré-employable — est la documentation, les tests et les décisions tracées.** Cette ligne droite est précisément ce qu'un recruteur inspecte.

Pourquoi la finition compte autant que le code. Un projet dont la logique fonctionne mais sans README est INVISIBLE : personne ne sait l'installer, l'utiliser, ni ce qu'il démontre. Un projet sans tests est FRAGILE : chaque modification risque une régression silencieuse. Un projet sans décisions tracées paraît suivre des recettes sans comprendre. La finition transforme un tas de code en un ARTEFACT professionnel — c'est ce qui fait la différence entre un exercice et une pièce de portfolio.

Les tests sur la logique pure, depuis les fondations. Grâce à l'immutabilité (jour 46), les opérations (add, done, filtrer, stats) sont des fonctions pures : mêmes entrées → mêmes sorties, sans fichiers. On peut donc les tester en isolation, rapidement, sans montage. Un test vérifie un comportement précis (« done marque la bonne tâche sans toucher les autres ») ET les cas limites (id inexistant, liste vide). Verrouiller les cas d'erreur UN PAR UN — écrire un test par cas — garantit qu'ils sont tous couverts, pas juste supposés.

Le README qui rend utilisable en 5 minutes. Il doit contenir : à quoi sert le projet, comment l'INSTALLER (commandes exactes), comment l'UTILISER (exemples concrets), l'ARCHITECTURE (le contrat Store, l'inversion de dépendance), et « ce que ça prouve » / « ce que j'ai appris » (3-5 puces honnêtes). Le test : un inconnu clone le dépôt et, en 5 minutes, installe, lance et comprend. Un README bâclé rend le meilleur code invisible.

L'ADR (Architecture Decision Record). Un document d'UNE page qui capture : le CONTEXTE, les OPTIONS considérées, la DÉCISION prise, ses CONSÉQUENCES, et ce qui te ferait CHANGER d'avis (révision). Pour TaskFlow : « JSON vs SQLite pour le stockage ». L'ADR PROUVE que tu arbitres consciemment — c'est une pièce maîtresse en entretien, parce qu'elle montre ton RAISONNEMENT, pas seulement ton résultat. La stats (`reduce` par statut/priorité, jour 24) complète l'outil.

Limites et compromis. Tout tester est irréaliste et contre-productif : on teste la LOGIQUE (pure, à valeur) plutôt que le câblage trivial. Un README trop long dilue l'essentiel ; trop court, il n'aide pas — viser l'utilisabilité en 5 minutes. Un ADR ne se justifie que pour les décisions STRUCTURANTES (pas pour chaque choix mineur). La finition prend du temps qu'on est tenté de zapper — c'est justement ce qui distingue les projets finis des projets abandonnés à 90 %.

La règle du jour : **finis vraiment — stats utiles, tests sur la logique pure, cas d'erreur verrouillés un par un, README qui rend le projet utilisable et compréhensible par un inconnu en 5 minutes, et un ADR qui trace ta décision structurante. La finition est la moitié du travail, et celle que le recruteur regarde.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire un test qui verrouille le comportement de `done` (bonne tâche modifiée, autres intactes, id inexistant sans effet) et esquisser l'ADR JSON vs SQLite.

**Exemple simple** : ce qu'un bon test capture. `done([t1, t2], t1.id)` doit renvoyer une liste où `t1` est `done` ET `t2` est INCHANGÉE ET l'original n'est pas muté. Trois assertions, un comportement verrouillé.

**Raisonnement pas-à-pas** : (1) je teste la logique pure (pas les fichiers) grâce à l'immutabilité ; (2) une assertion par comportement, plus les cas limites (id inexistant, liste vide) un par un ; (3) l'ADR trace le POURQUOI de la décision de stockage.

**Implémentation (tests avec node:test)** :
```ts
import { test } from 'node:test';
import assert from 'node:assert/strict';

test('done marque la bonne tâche sans toucher les autres ni muter l\'original', () => {
  const t1: Task = { id: 1, titre: 'A', statut: 'todo', priorite: 'moyenne', creeLe: '' };
  const t2: Task = { id: 2, titre: 'B', statut: 'todo', priorite: 'haute', creeLe: '' };
  const avant = [t1, t2];
  const apres = done(avant, 1);
  assert.equal(apres.find(t => t.id === 1)!.statut, 'done');   // bonne tâche
  assert.equal(apres.find(t => t.id === 2)!.statut, 'todo');   // autre intacte
  assert.equal(t1.statut, 'todo');                             // original NON muté
});

test('done sur un id inexistant ne change rien', () => {
  const taches: Task[] = [{ id: 1, titre: 'A', statut: 'todo', priorite: 'basse', creeLe: '' }];
  assert.deepEqual(done(taches, 999), taches);   // cas limite verrouillé
});
```

**L'ADR n°1 (squelette)** :
```md
# ADR 1 — Stockage : JSON vs SQLite
## Contexte : TaskFlow doit persister des tâches, CLI mono-utilisateur.
## Options : (a) fichier JSON — simple, lisible, zéro dépendance ;
##           (b) SQLite — requêtes, transactions, monte en charge.
## Décision : JSON pour la v1 (simplicité, boucle de feedback rapide).
## Conséquences : réécriture totale du fichier à chaque save ; pas de concurrence.
## Révision : passer à SQLite si volume/concurrence/requêtes le justifient (prévu jour 57).
```
Le test verrouille un comportement précis et ses cas limites ; l'ADR prouve que le choix de stockage est RAISONNÉ, pas subi.

## ⚠️ Erreurs fréquentes
- README bâclé : le projet devient invisible et inutilisable par un tiers, quel que soit le code.
- Cas d'erreur non testés un par un : on suppose la couverture au lieu de la garantir.
- Vouloir tout tester (câblage trivial) au lieu de cibler la logique à valeur.
- ADR absent ou réduit à une phrase : la décision de stockage paraît subie, pas raisonnée.

## 🏢 Cas métier
La finition distingue le développeur professionnel de l'amateur, et c'est mesurable en entreprise. Les tests sur la logique métier attrapent les régressions avant les utilisateurs — indispensable dès qu'une équipe modifie un code commun. Un README de qualité réduit le temps d'onboarding et rend un service maintenable par d'autres que son auteur. Les ADR sont une pratique répandue dans les équipes matures : ils tracent POURQUOI une décision a été prise, évitant que six mois plus tard personne ne se souvienne du contexte (et défasse un bon choix par ignorance). Pour un portfolio, ces éléments sont décisifs : un recruteur qui clone ton projet juge d'abord le README (peut-il l'utiliser ?), puis l'historique de commits et les tests (est-ce rigoureux ?), puis les ADR (raisonne-t-il ?). Un projet « fini » à ce niveau vaut plus que trois projets abandonnés à 90 % — c'est la preuve concrète que tu livres.

## 🎤 Question d'entretien
**« Qu'est-ce qui fait qu'un projet est vraiment "fini" au-delà du code qui marche ? »** → La moitié du travail est le code ; l'autre moitié est ce qui rend le projet crédible et ré-employable. D'abord des TESTS sur la logique pure — grâce à l'immutabilité, mes opérations sont des fonctions pures, donc testables sans fichiers ; je verrouille les cas d'erreur UN PAR UN (id inexistant, liste vide), pas seulement le chemin heureux. Ensuite un README qui rend le projet utilisable par un inconnu en 5 minutes : à quoi ça sert, installation, usage, architecture, et « ce que j'ai appris ». Sans README, le meilleur code est invisible. Enfin un ADR — un document d'une page qui trace une décision structurante (ici JSON vs SQLite pour le stockage) avec contexte, options, décision, conséquences et révision : il prouve que j'arbitre consciemment, ce qui vaut de l'or en entretien parce qu'il montre mon raisonnement. Je ne teste pas TOUT (le câblage trivial n'a pas de valeur), je teste la logique ; je ne documente pas chaque choix mineur, je trace les décisions structurantes. **Relance possible** : « pourquoi un ADR plutôt qu'un commentaire dans le code ? » → parce qu'une décision d'architecture dépasse un fichier : l'ADR est un document dédié, retrouvable, qui explique le POURQUOI à toute l'équipe, présente et future.
