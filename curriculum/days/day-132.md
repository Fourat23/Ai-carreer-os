## 🎯 Objectif du jour
Sortir du notebook vers du code réutilisable.

## 📖 Cours approfondi
**Modèle mental : sortir du notebook, c'est transformer une analyse JETABLE en un PIPELINE de fonctions PURES et testables (load → validate → clean → report) — un notebook prouve une idée une fois, une fonction pure la rend RÉUTILISABLE, TESTABLE et REJOUABLE.** Un notebook est parfait pour EXPLORER (jours 127-131) : on essaie, on voit, on ajuste. Mais un nettoyage qui doit tourner chaque semaine sur de nouvelles données ne peut pas rester une suite de cellules exécutées dans le désordre, dépendant d'un état caché. On le PROMEUT en code : des fonctions à responsabilité unique (jour 121), pures (mêmes entrées → mêmes sorties, sans effet de bord caché), et testées (jour 124).

Pourquoi une fonction pure change tout :
1. **Réutilisable** : `nettoyer(df)` s'applique à n'importe quel DataFrame de même forme, pas seulement à celui chargé dans la cellule 3.
2. **Testable** : une fonction pure se teste avec pytest (jour 124) — on lui donne un petit DataFrame sale connu et on vérifie la sortie. Un notebook ne se teste pas.
3. **Rejouable et déterministe** : relancer le pipeline sur les mêmes données donne le même résultat, sans dépendre de l'ordre d'exécution des cellules ni d'un état résiduel.
4. **Composable** : `report(clean(validate(load(chemin))))` — chaque étape isolée, on peut en remplacer une sans casser les autres.

Les étapes canoniques d'un pipeline de qualité :
- **load** : lire la source (et rien d'autre).
- **validate** : vérifier les invariants attendus (colonnes présentes, types, plages) et ÉCHOUER TÔT (jour 122) si les données ne sont pas celles attendues — un pipeline qui traite des données invalides produit des résultats invalides.
- **clean** : appliquer les décisions de nettoyage (jour 128), chacune justifiée.
- **report** : produire le rapport avant/après (jour 128) et les métriques de qualité.

Le piège à éviter : une fonction `clean` qui MUTE son entrée ou lit un état global. Une fonction pure prend un DataFrame et en RENVOIE un nouveau (`df.copy()` au besoin), sans surprise pour l'appelant.

La règle du jour : **promeus ton nettoyage exploratoire en fonctions pures à responsabilité unique (load/validate/clean/report), testées et composables ; le notebook explore, le module PRODUIT**. C'est la transition de « j'ai fait marcher une analyse » à « j'ai un outil de qualité réutilisable » — exactement ce qui sépare un débutant d'un data engineer.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : transformer ton nettoyage (jour 128) en fonctions pures Python testables (load/validate/clean/report).

**Exemple simple** : la signature d'une fonction pure de nettoyage — `def clean(df: pd.DataFrame) -> pd.DataFrame:`. Elle prend un DataFrame, en renvoie un NOUVEAU (jamais ne mute l'entrée), ne lit aucun état global. Cette pureté est ce qui la rend testable.

**Raisonnement pas-à-pas** : découper le nettoyage en étapes à responsabilité unique → chacune pure (entrée → nouvelle sortie) → valider tôt → tester chaque fonction avec un petit cas connu.

**Implémentation** :
```python
import pandas as pd

def load(chemin: str) -> pd.DataFrame:
    return pd.read_csv(chemin)                       # responsabilité unique : lire

def validate(df: pd.DataFrame) -> pd.DataFrame:
    attendues = {"date", "produit", "prix"}
    manquantes = attendues - set(df.columns)
    if manquantes:                                    # échoue TÔT (jour 122)
        raise ValueError(f"Colonnes manquantes : {manquantes}")
    return df

def clean(df: pd.DataFrame) -> pd.DataFrame:
    df = df.copy()                                    # PUR : ne mute pas l'entrée
    df["produit"] = df["produit"].str.lower().str.strip()
    df = df[df["prix"] >= 0]
    df["prix"] = df["prix"].fillna(df["prix"].median())
    return df

def report(avant: pd.DataFrame, apres: pd.DataFrame) -> dict:
    return {"lignes_avant": len(avant), "lignes_apres": len(apres),
            "lignes_retirees": len(avant) - len(apres)}

# Composition : chaque étape isolée, remplaçable, testable
brut = load("ventes.csv"); valide = validate(brut); propre = clean(valide)

# Test pytest (jour 124) — une fonction pure se teste avec un cas connu :
def test_clean_retire_prix_negatif():
    entree = pd.DataFrame({"produit": ["A"], "prix": [-5], "date": ["2024-01-01"]})
    assert len(clean(entree)) == 0
```

**Mini-quiz** : (a) Pourquoi `df.copy()` dans `clean` ? (b) Que teste-t-on plus facilement dans une fonction que dans un notebook ? (c) Pourquoi `validate` échoue-t-il tôt ?
→ (a) pour rester PUR : ne pas muter l'entrée, éviter les surprises pour l'appelant ; (b) le comportement — on donne un cas connu et on vérifie la sortie (un notebook ne se teste pas) ; (c) un pipeline qui traite des données invalides produit des résultats invalides — mieux vaut échouer clairement à l'entrée.

**Variante** : écris un test qui donne à `validate` un DataFrame SANS la colonne `prix` et vérifie qu'il lève `ValueError` — tu prouves que ton garde-fou de validation fonctionne, pas seulement le chemin heureux.

## ⚠️ Erreurs fréquentes
- Fonction qui mute son entrée ou lit un état global : impure, source de surprises — utiliser `df.copy()` et ne dépendre que des paramètres.
- Tout garder dans le notebook : non testable, non rejouable, dépendant de l'ordre d'exécution des cellules.
- Sauter la validation : un pipeline qui traite des données invalides produit des résultats invalides sans le signaler.
- Une fonction fourre-tout qui load + clean + report : impossible à tester ou remplacer par morceau — une responsabilité par fonction.

## 🏢 Cas métier
La promotion d'un nettoyage exploratoire en fonctions pures testées est exactement la transition « notebook → production » que font les équipes data : un notebook est excellent pour explorer mais ingérable en production (état caché, ordre d'exécution, non testable, non rejouable). Les pipelines de données d'entreprise sont faits de fonctions pures composables, précisément pour être testées, rejouées et maintenues. Un data analyst qui reste au notebook plafonne ; celui qui sait transformer son analyse en module de qualité réutilisable accède aux rôles de data engineer. Cette compétence — code pur, testé, composable — est directement visible dans un repo et attendue dès qu'un traitement doit tourner plus d'une fois.

## 🎤 Question d'entretien
**« Comment passes-tu d'un nettoyage en notebook à du code de production ? »** → Je PROMEUS le nettoyage en fonctions PURES à responsabilité unique : load (lire), validate (vérifier les invariants et échouer tôt si les données ne sont pas celles attendues), clean (appliquer les décisions justifiées), report (métriques avant/après). Pures signifie : mêmes entrées → mêmes sorties, sans effet de bord ni état global, et sans muter l'entrée (`df.copy()`). Ça change tout : c'est réutilisable (sur n'importe quel DataFrame de même forme), testable avec pytest (un petit cas sale connu → sortie vérifiée), rejouable (déterministe, indépendant de l'ordre des cellules) et composable (`report(clean(validate(load(x))))`). Le notebook explore, le module produit — c'est la transition de « une analyse qui a marché » à « un outil de qualité réutilisable ».
