**Modèle mental : un projet réel commence par le SQUELETTE QUI MARCHE, pas par la fonctionnalité parfaite. Un CLI qui répond « commande inconnue » et persiste une liste vide est un meilleur point de départ qu'une commande `add` brillante dans un programme qui ne se lance pas — parce que la boucle de feedback (coder → lancer → constater) doit rester sous 10 secondes pour que tu progresses vite. On construit un tube qui traverse tout, puis on l'épaissit.** Implémenter `JsonStore` derrière l'interface du jour 44, c'est donner corps au contrat sans jamais y coupler la logique.

Pourquoi le squelette d'abord. Un programme qui ne démarre pas ne donne aucun retour : on code à l'aveugle, les erreurs s'accumulent. Un squelette qui tourne (même minimal) établit la boucle de feedback : chaque ajout se teste immédiatement. C'est le principe du « walking skeleton » : faire traverser une fonctionnalité de bout en bout (CLI → logique → Store → fichier → retour) le plus tôt possible, puis enrichir. La vitesse de la boucle de feedback est le premier facteur de productivité.

La persistance robuste, depuis les fondations. `JsonStore` implémente `Store` (jour 44) et recycle le pattern de lecture/écriture du jour 12. Le point délicat est `charger()` : il doit DISTINGUER trois cas — fichier ABSENT (premier lancement : normal, on part d'une liste vide), JSON VALIDE (on parse), JSON CORROMPU (erreur : on s'ARRÊTE sans écraser, pour ne pas détruire des données). Confondre « absent » et « corrompu » mène soit à planter au premier lancement, soit à écraser silencieusement des données.

Les identifiants uniques : max+1, jamais length+1. Générer un id avec `length + 1` crée des DOUBLONS après suppression : si on a les ids [1,2,3], qu'on supprime le 2 (reste [1,3], length=2), le prochain id serait 3 → collision avec l'existant. `max(ids) + 1` (ici 4) garantit l'unicité indépendamment des suppressions. C'est un bug classique et instructif : l'id doit dériver du MAXIMUM existant, pas du nombre d'éléments.

La différence parsing robuste vs naïf. Un `JSON.parse` non protégé plante sur un fichier corrompu et peut, mal géré, mener à écraser. Un parsing robuste enveloppe la lecture, distingue les cas, et échoue de façon SÛRE (on préfère s'arrêter avec un message clair plutôt que corrompre davantage). Tout ce qui entre (fichier, arguments) est hostile jusqu'à validation.

Limites et compromis. Un stockage JSON complet réécrit tout le fichier à chaque sauvegarde : simple et parfait pour un CLI personnel, inadapté à de gros volumes ou à la concurrence (d'où SQLite au jour 57). Les commits atomiques par fonctionnalité racontent la construction — un historique propre est une vitrine pour le recruteur, au prix d'une discipline de commit.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : implémenter `JsonStore` (chargement robuste, ids en max+1) et la commande `add`, en gérant les trois cas de fichier.

**Exemple simple** : le bug d'id à éviter. Avec `length+1` : ids [1,2,3], on supprime le 2 → [1,3] (length 2) → prochain id = 3 → DOUBLON. Avec `max+1` : max([1,3]) + 1 = 4 → unique. L'id dérive du maximum, pas du compte.

**Raisonnement pas-à-pas** : (1) `charger()` distingue fichier absent (→ []), valide (→ parse), corrompu (→ on s'arrête sans écraser) ; (2) `sauver()` crée le dossier si besoin puis écrit ; (3) `add` calcule l'id en max+1 et persiste une NOUVELLE liste (immuable).

**Implémentation** :
```ts
import { readFileSync, writeFileSync, existsSync, mkdirSync } from 'node:fs';
import { dirname } from 'node:path';

class JsonStore implements Store {
  constructor(private readonly chemin: string) {}

  load(): Task[] {
    if (!existsSync(this.chemin)) return [];          // ABSENT : premier lancement, normal
    const brut = readFileSync(this.chemin, 'utf8');
    try {
      return JSON.parse(brut) as Task[];              // VALIDE
    } catch {
      throw new Error(`Fichier corrompu : ${this.chemin} (arrêt pour ne pas écraser).`); // CORROMPU
    }
  }
  save(taches: Task[]): void {
    mkdirSync(dirname(this.chemin), { recursive: true });   // crée data/ si absent
    writeFileSync(this.chemin, JSON.stringify(taches, null, 2));
  }
  all(): Task[] { return this.load(); }
}

function add(store: Store, titre: string): Task {
  const taches = store.load();
  const id = taches.length ? Math.max(...taches.map(t => t.id)) + 1 : 1;   // max+1, PAS length+1
  const t: Task = { id, titre, statut: 'todo', priorite: 'moyenne', creeLe: new Date().toISOString() };
  store.save([...taches, t]);   // nouvelle liste, pas de mutation
  return t;
}
```
Le fichier absent ne plante pas, le corrompu arrête proprement, et `max+1` évite les doublons — trois pièges désamorcés avant qu'ils ne deviennent des bugs de production.

## 🎤 Question d'entretien
**« Comment gères-tu le chargement d'un fichier de données de façon robuste, et comment génères-tu des identifiants uniques ? »** → Pour le chargement, je distingue explicitement trois cas. Fichier ABSENT : c'est un premier lancement normal, je pars d'une liste vide — pas une erreur. JSON VALIDE : je parse. JSON CORROMPU : je m'ARRÊTE avec un message clair sans écraser le fichier, pour ne pas détruire davantage de données. Confondre « absent » et « corrompu » mène soit à planter au démarrage, soit à écraser silencieusement — deux incidents classiques. L'id doit dériver du MAXIMUM existant, pas du nombre d'éléments.
