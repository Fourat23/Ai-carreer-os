# Jour 213 — Function calling avancé

[← Dashboard](../../) · [Semaine 31](../week-31.md) · [Mois 8](../month-08.md) · [Correction](../solutions/day-213-solution.md)

## 🎯 Objectif du jour
Plusieurs outils, gestion d'erreur.

## 📖 Cours approfondi
**Modèle mental : à trois outils, ton assistant devient un système distribué miniature — et il en attrape toutes les maladies.** Au jour 207, la boucle à 2 outils tenait dans un happy path. À 3+ outils, les cas non nominaux dominent : un outil LENT (timeout ?), un outil qui ÉCHOUE (on réessaie ? on le dit ?), une requête qui n'a besoin d'AUCUN outil, une requête qui en enchaîne PLUSIEURS (météo → conversion → comparaison), et le modèle qui choisit le MAUVAIS outil parce que deux descriptions se ressemblent.

Les règles d'ingénierie qui émergent :
1. **Chaque outil expose son contrat d'échec** : il retourne soit un résultat, soit une erreur STRUCTURÉE (`{error: "timeout", tool: "meteo"}`) — jamais une exception qui tue la boucle. L'erreur repart au modèle, qui doit la dire à l'utilisateur.
2. **Timeout par outil** : un outil qui pend ne doit pas geler l'assistant. Le timeout EST un des cas d'échec du contrat.
3. **Les descriptions sont des frontières de décision** : si le modèle confond deux outils, la correction est dans les DESCRIPTIONS (« à utiliser uniquement si... », contre-exemples), pas dans des if de rattrapage.
4. **Budget d'itérations et d'appels** : une limite dure sur la boucle (déjà vue) + un compteur d'appels d'outils par requête — un assistant qui appelle 14 fois la météo est un bug de conception, pas un comportement à logger silencieusement.

Le test de vérité du jour : la MATRICE de cas. Chaque outil × (succès, échec, timeout) + les cas transverses (aucun outil, multi-outils, outil ambigu). C'est elle qui distingue « ça a marché quand j'ai essayé » de « c'est robuste ».

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : assistant 3 outils (météo mockée, calcul, recherche de contacts mockée) avec matrice de robustesse.

**Raisonnement** : d'abord le contrat d'échec uniforme, ensuite les outils, enfin la matrice de tests.

**Le contrat uniforme** :
```python
def executer_outil(nom, args, timeout_s=3):
    try:
        resultat = OUTILS_IMPL[nom](**args)      # exécution réelle
        return {"ok": True, "resultat": resultat}
    except TimeoutError:
        return {"ok": False, "erreur": f"{nom} n'a pas répondu en {timeout_s}s"}
    except Exception as e:
        return {"ok": False, "erreur": f"{nom} a échoué : {type(e).__name__}"}
# Le dict repart TOUJOURS au modèle comme tool_result — ok ou pas.
```

**La matrice (l'essentiel du travail)** :
```
            succès   échec forcé   timeout forcé
meteo         ✓          ✓             ✓
calcul        ✓          ✓             —
contacts      ✓          ✓             ✓
+ « quelle heure est-il ? »       → aucun outil, réponse honnête
+ « météo à Paris ET à Lyon »     → deux appels, réponse consolidée
+ « cherche paris » (ville ou contact ?) → le modèle demande OU choisit
  justifiablement — observe et ajuste les DESCRIPTIONS
```

**Explication** : forcer les échecs (un flag `FORCER_ECHEC=meteo`) fait partie du livrable — tu ne peux pas attendre qu'un mock échoue naturellement. **Variante** : ajoute le compteur d'appels par requête et fais échouer le test si > 5 — ton premier budget d'agent.

## ⚠️ Erreurs fréquentes
- Laisser une exception d'outil tuer la boucle : l'assistant entier tombe pour une météo en panne.
- Cacher l'échec au modèle (renvoyer un résultat vide) : il invente alors une réponse plausible — pire que l'erreur.
- Corriger un mauvais choix d'outil par du code de rattrapage au lieu d'améliorer les descriptions : tu combats le mécanisme au lieu de le piloter.
- Tester la matrice à la main sans l'automatiser : elle ne sera jamais rejouée après la prochaine modification.

## 🏢 Cas métier
Les frameworks d'agents (LangChain, etc.) cachent cette boucle — jusqu'au jour où l'agent tourne en rond ou gèle en production, et où il faut débugger À TRAVERS le framework. Le dev qui a construit la boucle à nu diagnostique en minutes (« c'est un outil sans timeout » / « deux descriptions se chevauchent ») là où les autres regardent des logs opaques. C'est l'argument : je sais ce que le framework fait pour moi.

## 🎤 Question d'entretien
**« Qu'est-ce qui devient difficile quand on passe de 1 à N outils ? »** → Le choix (les descriptions deviennent des frontières de décision à concevoir), les échecs (contrat d'erreur structuré par outil, timeouts, l'erreur remonte au modèle qui doit la dire), et le contrôle (budget d'itérations et d'appels). La robustesse se prouve par une matrice outil × {succès, échec, timeout} + cas transverses, pas par une démo.

## 🚀 Pourquoi ça comptera plus tard
- **Bankable** : la matrice de robustesse est un artefact d'entretien concret — peu de candidats juniors peuvent montrer un tableau de cas d'échec TESTÉS sur un assistant à outils.
- C'est la brique des agents du mois 10 : un agent = cette boucle + planification ; si la base gère mal les échecs, l'agent amplifie le chaos.
- Le réflexe « contrat d'échec uniforme » vaut pour toute intégration (APIs, jobs, micro-services) — compétence transversale backend.

## 🧩 Questions de réflexion (à faire seul)
- Tu passes de 1 à 5 outils : pourquoi le CHOIX du bon outil devient-il le problème principal, et de quoi ce choix dépend-il directement ?
- Un de tes outils met trente secondes à répondre ou échoue : que doit faire la boucle pour ne ni se bloquer ni mentir à l'utilisateur sur le résultat ?
- Deux outils ont des descriptions qui se ressemblent : pourquoi le modèle risque-t-il d'hésiter ou de se tromper d'outil, et que révèle ce problème sur le rôle des descriptions ?
