## 🎯 Objectif du jour
S'entraîner au design système.

## 📖 Cours approfondi
**Modèle mental : un exercice de design système est un test de RAISONNEMENT sous contraintes, pas une recherche de la « bonne » réponse — l'évaluateur regarde comment tu poses les questions, arbitres les trade-offs et justifies tes choix, pas si tu tombes sur une architecture canonique.** Après avoir appris les briques (hexagonal, événementiel, styles, patterns), tu t'entraînes à l'exercice le plus fréquent des entretiens d'ingénieur : concevoir un système à l'échelle en 45 minutes, à voix haute, en dessinant. Aujourd'hui : un système de traitement de documents à l'échelle (le cousin de DocSense).

La méthode d'un design système réussi (le processus compte plus que le résultat) :
1. **Clarifier les exigences AVANT de dessiner** : combien de documents ? quel débit (uploads/jour) ? quelle latence acceptable pour l'ingestion ? pour la recherche ? quelles garanties (fraîcheur, disponibilité) ? Un candidat qui saute cette étape et dessine tout de suite échoue — les exigences DÉTERMINENT l'architecture. Poser les bonnes questions est la première compétence évaluée.
2. **Estimer les ordres de grandeur** : volume de données (N docs × taille), débit (requêtes/s), stockage (vecteurs : N chunks × dims × octets, ton calcul du jour 228), coût (jour 285). Les chiffres orientent les choix (une vector DB managée à 10M de vecteurs, un fichier JSON à 10k).
3. **Dessiner le flux de haut niveau** : ingestion (upload → queue → workers → index, l'événementiel du jour 290) et requête (question → retrieval → génération). Les composants, pas les détails.
4. **Approfondir 2-3 points critiques** : là où c'est dur — la reprise de l'ingestion (jour 283), la fraîcheur de l'index (jour 242), le budget de coût/latence. L'évaluateur creuse ; tu montres la profondeur.
5. **Énoncer les TRADE-OFFS** : chaque choix a un coût. « Vector DB managée : simple mais coûteuse et dépendance ; auto-hébergée : moins chère mais ops. Je choisis X parce que [contrainte] ». C'est le cœur de l'exercice — un design sans trade-offs énoncés est suspect.

Ce qui distingue un bon candidat : il DIRIGE l'exercice (clarifie, estime, structure, approfondit, arbitre) au lieu de subir ; il pense à voix haute (l'évaluateur suit son raisonnement) ; il assume les limites (« à cette échelle, ceci deviendrait un problème »). Le but n'est pas de mémoriser une architecture mais de dérouler une MÉTHODE — et tu as toutes les briques du mois pour le faire.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : designer un système de traitement de documents à l'échelle (schéma + trade-offs), 45 min.

**Exemple simple** : commence TOUJOURS par une question, jamais par un dessin — « combien de documents, quel débit d'upload, quelle latence acceptable ? ». Les réponses changent tout (10k docs vs 10M ne donnent pas la même architecture).

**Raisonnement pas-à-pas** : clarifier → estimer → dessiner le flux → approfondir 2-3 points → énoncer les trade-offs, à voix haute.

**Le déroulé type (45 min)** :
```
1. CLARIFIER (5 min) : volume ? débit ? latence ingestion/recherche ? fraîcheur ?
   disponibilité ? → disons 1M docs, 10k uploads/jour, recherche < 2s, MàJ quotidienne
2. ESTIMER (5 min) : ~20M chunks × 1024 dims × 4o ≈ 80 Go de vecteurs → vector DB
   managée ; débit d'ingestion → workers + queue ; coût mensuel (j.285)
3. FLUX (10 min) :
   ingestion : upload → API → queue → workers (extract/chunk/embed) → vector DB
               (événementiel j.290, orchestration j.283)
   requête  : question → hybride+rerank → génération citée (ton pipeline)
4. APPROFONDIR (15 min) : reprise de l'ingestion (checkpoint), fraîcheur
   (versioning d'index j.242), budget latence par étage (j.250)
5. TRADE-OFFS (10 min) : vector DB managée vs auto-hébergée ; sync vs async ;
   monolithe modulaire vs services (j.291) — chaque choix justifié par une contrainte
```

**Mini-quiz** : (a) Par quoi commence un design système, jamais par quoi ? (b) Qu'est-ce que l'évaluateur regarde vraiment ? (c) Qu'est-ce qui rend un design suspect ?
→ (a) par CLARIFIER les exigences ; jamais par dessiner tout de suite ; (b) le RAISONNEMENT (questions, estimations, arbitrages), pas la « bonne » architecture ; (c) l'absence de trade-offs énoncés (chaque choix a un coût).

**Variante** : fais l'exercice CHRONOMÉTRÉ (45 min, à voix haute, en dessinant) et enregistre-toi — réécoute : as-tu clarifié avant de dessiner ? estimé les ordres de grandeur ? énoncé les trade-offs ? C'est l'entraînement exact de l'entretien.

## ⚠️ Erreurs fréquentes
- Dessiner avant de clarifier les exigences : l'architecture dépend du volume/débit/latence — sauter cette étape produit un design hors sol.
- Oublier d'estimer les ordres de grandeur : sans chiffres, impossible de justifier vector DB managée vs fichier, sync vs async.
- Ne pas énoncer les trade-offs : un design présenté comme « la » solution sans coûts est suspect — chaque choix a un prix.
- Rester muet ou dérouler en silence : l'évaluateur note le RAISONNEMENT — penser à voix haute est la moitié de l'exercice.

## 🏢 Cas métier
Le design système est l'épreuve reine des entretiens d'ingénieur (surtout à partir du niveau intermédiaire) — et un domaine où beaucoup de candidats techniquement solides échouent, faute de MÉTHODE : ils dessinent avant de clarifier, oublient d'estimer, ne verbalisent pas leurs trade-offs. Ceux qui réussissent dirigent l'exercice (clarifier → estimer → structurer → approfondir → arbitrer) et pensent à voix haute. Pour un profil IA, savoir designer un système de traitement de documents à l'échelle — en mobilisant retrieval, orchestration, événementiel, coûts — est une démonstration complète. C'est aussi la répétition générale du cadrage de DocSense (mois 11).
