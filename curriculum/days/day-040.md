## 📖 Cours approfondi
**Concepts abordés :** Nommage révélateur · Fonctions courtes · Niveau d'abstraction cohérent · Commentaire = POURQUOI · DRY sans excès.

Le clean code repose sur un fait : le code est LU 10 fois plus qu'il n'est écrit. Optimiser la lecture est donc rentable. Les leviers principaux : des noms qui révèlent l'INTENTION (calculerRemiseFidelite > calcRem > x), des fonctions courtes à UNE responsabilité, un niveau d'abstraction cohérent par fonction (ne pas mélanger logique métier et détails techniques dans le même bloc).

Les commentaires : ils doivent dire POURQUOI (la décision, la contrainte invisible), jamais QUOI (la ligne suivante se lit toute seule). Un commentaire qui paraphrase le code est du bruit qui se périme.

DRY (Don't Repeat Yourself) avec discernement : factoriser deux duplications identiques oui, mais forcer une abstraction sur deux choses juste RESSEMBLANTES crée un couplage pire que la duplication.

**Modèle mental : le code est LU dix fois plus qu'il n'est écrit — par tes collègues, et par TOI dans six mois. Le clean code optimise donc pour le LECTEUR, pas pour l'écrivain. Un bon nom rend un commentaire inutile ; une fonction courte tient dans la tête ; un commentaire dit POURQUOI (la décision, la contrainte invisible), jamais QUOI (la ligne se lit toute seule). L'objectif n'est pas l'esthétique : c'est de réduire le coût de COMPRÉHENSION future, qui est le vrai coût d'un logiciel.** Écrire clairement est un acte d'empathie envers le prochain lecteur — souvent soi-même.

Pourquoi le clean code existe. Un logiciel vit des années et change constamment. Le temps dominant n'est pas l'écriture initiale, mais la LECTURE lors de chaque correction, ajout, débogage. Du code obscur taxe chacune de ces lectures : il faut re-déchiffrer, deviner l'intention, craindre de casser. Le clean code est un investissement qui se rembourse à chaque relecture — c'est de l'économie, pas de la coquetterie.

Les leviers principaux, depuis les fondations. **Le nommage révélateur** : le nom doit dire l'INTENTION (`calculerRemiseFidelite` > `calc` > `x`). Un bon nom élimine le besoin d'un commentaire explicatif : le code se lit comme une phrase. **Les fonctions courtes à une seule responsabilité** : une fonction qui tient à l'écran, qui fait UNE chose, se comprend et se teste d'un coup d'œil. **Le niveau d'abstraction cohérent** : ne pas mélanger, dans un même bloc, la logique métier de haut niveau et les détails techniques de bas niveau — le lecteur perd le fil. **Le commentaire = POURQUOI** : documenter la décision non évidente (« on trie ici parce que l'API l'exige »), la contrainte cachée, le piège — jamais paraphraser le code.

La différence commentaire utile vs bruit. Un commentaire qui répète le code (`i++; // incrémente i`) est du BRUIT : il n'ajoute rien et se PÉRIME (le code change, le commentaire ment). Un commentaire utile capture une information ABSENTE du code : le pourquoi d'un choix, un lien vers un ticket, un avertissement (« ne pas paralléliser : l'API limite à 1 req/s »). Règle : si tu ressens le besoin de commenter QUOI fait le code, essaie d'abord de mieux le NOMMER.

Le DRY avec discernement. « Don't Repeat Yourself » dit de factoriser les duplications VRAIES (deux morceaux identiques qui évoluent ensemble). Mais forcer une abstraction sur deux choses qui se RESSEMBLENT sans être liées crée un couplage pire que la duplication : quand elles divergent, l'abstraction devient un nœud. La bonne question : « ces deux bouts changeront-ils toujours ENSEMBLE ? » — si non, laisse-les séparés.

Limites et compromis. Le clean code est affaire de JUGEMENT, pas de règles absolues : des fonctions trop découpées fragmentent la lecture ; un nom trop long nuit autant qu'un trop court. Refactorer sans TESTS risque de casser en silence (d'où les tests, jour 47). Et « propre » dépend du contexte d'équipe : la cohérence avec le code existant prime souvent sur la préférence personnelle.

La règle du jour : **écris pour le lecteur futur (souvent toi) : des noms qui révèlent l'intention, des fonctions courtes à une responsabilité, un niveau d'abstraction cohérent, des commentaires qui disent POURQUOI. Applique DRY avec discernement, et souviens-toi qu'un bon nom rend un commentaire inutile.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : refactorer un fragment obscur en appliquant nommage, fonctions courtes et « commentaire = pourquoi », et mesurer le gain de lisibilité.

**Exemple simple** : le AVANT — correct mais illisible.
```ts
// AVANT : que fait ce code ?
function p(a: any[]): number {
  let x = 0;
  for (let i = 0; i < a.length; i++) {
    if (a[i].t === 1 && a[i].q > 0) x += a[i].pr * a[i].q; // ???
  }
  return x * 1.2; // 1.2 ?
}
```

**Raisonnement pas-à-pas** : (1) je NOMME ce que le code calcule (un total TTC de lignes actives) ; (2) je remplace les champs cryptiques par des noms d'intention ; (3) j'extrais la condition en une fonction au nom parlant ; (4) je remplace le `1.2` magique par une constante nommée ; (5) je garde UN commentaire, sur le POURQUOI d'un choix non évident.

**Implémentation (APRÈS)** :
```ts
const TAUX_TVA = 0.2;

interface Ligne { type: 'produit' | 'service'; quantite: number; prixUnitaire: number; }

function estLigneFacturable(ligne: Ligne): boolean {
  return ligne.type === 'produit' && ligne.quantite > 0;
}

function totalTTC(lignes: Ligne[]): number {
  const totalHT = lignes
    .filter(estLigneFacturable)                          // intention claire
    .reduce((somme, l) => somme + l.prixUnitaire * l.quantite, 0);
  // POURQUOI : la TVA est appliquée au total, pas ligne à ligne,
  // pour éviter les écarts d'arrondi cumulés (exigence comptable).
  return totalHT * (1 + TAUX_TVA);
}
```
Le AVANT et le APRÈS produisent le MÊME résultat, mais le second se lit sans effort : les noms portent l'intention, la constante remplace le nombre magique, et le seul commentaire capture une décision INVISIBLE dans le code (l'ordre d'application de la TVA).

## ⚠️ Erreurs fréquentes
- Sur-commenter l'évident (`i++ // incrémente`) au lieu de documenter la seule décision non triviale.
- Refactorer sans tests : on casse le comportement en silence — d'où l'intérêt des tests (jour 47).
- Sur-découper en fonctions atomiques : la lecture se fragmente autant qu'avec une fonction trop longue.
- Forcer DRY sur deux bouts juste ressemblants : couplage plus coûteux que la duplication quand ils divergent.

## 🏢 Cas métier
La lisibilité du code est un enjeu économique majeur en entreprise, où une base est maintenue des années par des équipes qui tournent. Du code clair réduit le temps d'onboarding d'un nouvel arrivant, accélère chaque correction de bug (on comprend avant de modifier), et diminue le risque de régression (on voit ce qu'on touche). À l'inverse, du code obscur crée une « dette » : chaque évolution coûte plus cher et fait plus peur. C'est pourquoi les revues de code portent autant sur la clarté (noms, découpage, commentaires) que sur la correction. Un développeur qui livre du code lisible, testable et bien nommé fait gagner du temps à toute l'équipe — une valeur directe et mesurée. Savoir refactorer un fragment obscur en expliquant CHAQUE choix (pourquoi ce nom, pourquoi extraire cette fonction) est exactement ce qu'on évalue en entretien et en période d'essai.

## 🎤 Question d'entretien
**« Qu'est-ce que du code propre pour toi, et comment refactorerais-tu une fonction obscure ? »** → Du code propre optimise pour le LECTEUR, parce que le code est lu dix fois plus qu'il n'est écrit — par l'équipe et par moi-même dans six mois. Concrètement : des noms qui révèlent l'INTENTION (un bon nom rend un commentaire inutile), des fonctions courtes à UNE responsabilité qui tiennent à l'écran, un niveau d'abstraction cohérent (ne pas mêler métier de haut niveau et détails techniques), et des commentaires qui disent POURQUOI un choix a été fait, jamais QUOI fait le code. Pour refactorer une fonction obscure : je la renomme d'après ce qu'elle calcule vraiment, je remplace les variables et nombres magiques par des noms/constantes parlants, j'extrais les conditions complexes en fonctions au nom explicite, et je ne garde que les commentaires qui capturent une décision invisible dans le code. Le tout à comportement CONSTANT, idéalement sous couverture de tests pour ne rien casser. **Relance possible** : « ne risque-t-on pas de trop découper ? » → si : le clean code est du jugement, pas des règles absolues. Des fonctions atomisées fragmentent la lecture, et DRY appliqué sans discernement (factoriser deux choses juste ressemblantes) crée un couplage pire que la duplication.
