## 🎯 Objectif du jour
Le LLM comme composant faillible.

## 📖 Cours approfondi
**Modèle mental : intègre le LLM comme tu intégrerais un service tiers lent, cher et parfois faux.** Dans ton app, l'appel LLM n'est pas une fonction locale : c'est une dépendance externe avec quatre propriétés hostiles — latence en secondes, coût par appel, non-déterminisme, et échecs (réseau, rate limit, sortie invalide). L'architecture d'intégration découle de ces quatre propriétés :

- **Latence** → jamais d'appel bloquant dans le chemin critique : streaming pour l'UX, état de chargement honnête, timeout explicite.
- **Coût** → chaque appel logge tokens in/out et coût calculé ; un plafond (par utilisateur/jour, par exemple) protège des dérives.
- **Non-déterminisme** → la sortie est validée (jour 205) avant d'atteindre l'utilisateur ou la base.
- **Échecs** → try/except sur chaque appel, retry avec backoff sur les erreurs transitoires (429), et surtout la **dégradation gracieuse** : si le LLM est indisponible, l'app reste UTILISABLE — la fonctionnalité IA s'efface (message honnête, valeur par défaut, file d'attente), elle n'entraîne pas l'app dans sa chute.

La question d'architecte à te poser AVANT de coder : « si l'API LLM disparaît pendant une heure, que vit mon utilisateur ? ». Si la réponse est « rien de grave », ton intégration est bien pensée. C'est le critère qui sépare la feature IA collée au scotch de la feature IA de production.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : intégrer un appel LLM utile dans UNE de tes apps existantes (ex. suggestion de description dans ton app du mois 5).

**Raisonnement** : choisir une intégration NON critique (l'app doit vivre sans), puis construire les quatre protections.

**Architecture** :
```
1. Un module llm.py/llm.ts UNIQUE (pas d'appels éparpillés) :
   - appel + timeout + retry (2 essais, backoff) + validation de sortie
   - log par appel : timestamp, tokens in/out, coût, latence, succès/échec
2. Le point d'intégration :
   - UI : bouton « Suggérer » → état de chargement → résultat ÉDITABLE
     (l'utilisateur garde la main sur la sortie IA)
3. La dégradation :
   - échec/timeout → message « suggestion indisponible, réessayez » ;
     le formulaire reste 100 % fonctionnel à la main
4. Le test de la panne : coupe la clé API et vérifie le parcours complet.
```

**Explication** : le module unique centralise logs, retries et coûts — quand tu ajouteras un 2e usage LLM, tout est déjà en place. **Variante** : ajoute un compteur de coût cumulé du jour et un plafond au-delà duquel la feature se désactive proprement.

## ⚠️ Erreurs fréquentes
- Appel LLM dans le chemin critique d'une page : la latence du tiers devient TA latence perçue.
- Pas de timeout : un appel qui pend gèle l'expérience entière.
- Afficher la sortie LLM brute sans validation ni possibilité d'édition : l'hallucination part chez l'utilisateur avec TON logo dessus.
- Tester uniquement le cas nominal : la panne se teste EXPRÈS, en coupant la clé.

## 🏢 Cas métier
Post-mortem classique : une app dont la page d'accueil attendait un appel LLM synchrone — le jour où l'API a eu 30 minutes d'incident, TOUTE l'app était morte. La feature IA était accessoire, la panne était totale. La dégradation gracieuse n'est pas du polish : c'est ce qui borne le rayon d'explosion d'une dépendance externe.

## 🎤 Question d'entretien
**« Comment intègres-tu un LLM dans une app de production ? »** → Comme un service tiers faillible : module d'appel centralisé avec timeout, retry/backoff, validation de sortie, log tokens/coût/latence par appel, plafonds de dépense, et dégradation gracieuse — l'app reste utilisable si le LLM tombe. Je teste le parcours de panne, pas seulement le parcours nominal.
