# Jour 227 — Décisions de conception du RAG

> **Mois 8** · **Semaine 33** · Compétence : **RAG** · Difficulté : Intermédiaire/5 · Durée : 4.5 h

[← Dashboard](../../) · [Semaine 33](../week-33.md) · [Mois 8](../month-08.md) · [Correction](../solutions/day-227-solution.md)

## 🎯 Objectif du jour
Rendre les choix explicites.

## 📖 Cours approfondi
**Modèle mental : une décision non écrite est une décision par défaut — et le défaut n'a pas de critère d'échec.** Ton RAG incarne six décisions que tu as prises, parfois sans les formuler : taille de chunk, overlap, k, modèle d'embedding, prompt de génération, seuil de refus. Aujourd'hui tu les rends EXPLICITES, avec pour chacune trois choses : la valeur choisie, le POURQUOI (même si c'est « valeur de départ standard »), et surtout **le critère d'échec** — le signal observable qui dira que cette décision est mauvaise.

Le critère d'échec est l'idée clé du jour. « Chunks de 400 tokens » n'est ni bon ni mauvais dans l'absolu ; ce qui compte est : « cette décision échoue si l'autopsie montre des réponses coupées en deux (jour 226 : 2 cas déjà) ou si des chunks multi-sujets polluent le top-k ». Une décision avec critère d'échec devient TESTABLE ; sans critère, elle devient un dogme qu'on n'ose plus toucher — ou qu'on change au hasard.

Pourquoi documenter maintenant : (1) l'autopsie d'hier alimente les critères avec des cas RÉELS ; (2) le mois 9 va tester ces décisions une à une (chunking jour 241, embeddings jour 243, k et seuils via le golden set) — le document d'aujourd'hui est le PLAN de ces expériences ; (3) c'est un artefact d'ingénieur : le tableau des six décisions est exactement ce qu'un tech lead demande en design review (« qu'as-tu choisi, pourquoi, comment on saura que c'était faux ? »).

Format : léger. Six blocs d'un tiers de page — pas un rapport. La valeur est dans la précision des critères, pas dans le volume.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : documenter les 6 décisions avec valeur, justification, critère d'échec.

**Raisonnement** : partir des données réelles (autopsies d'hier) pour ancrer chaque critère dans un symptôme observable.

**Gabarit (à répéter 6 fois)** :
```
## Décision 3 : k = 3
Valeur     : top-3 chunks injectés dans la génération.
Pourquoi   : point de départ standard ; limite le bruit et le coût
             (~1 200 tokens de contexte par question).
Échoue si  : des échecs « rang 4-7 » s'accumulent (jour 226 : déjà 4 cas —
             k=5 en a récupéré 3 au re-test) ; OU si la génération cite des
             chunks non pertinents (bruit → k trop grand).
Re-test    : golden set du mois 9, k ∈ {3, 5, 8}, courbe précision/coût.
Statut     : SOUS SURVEILLANCE (données d'hier défavorables).
```

**Les 6 décisions à couvrir** :
```
1. Taille de chunk (400 tk)   → échoue si : réponses coupées, chunks multi-sujets
2. Overlap (15 %)             → échoue si : idées frontières perdues malgré tout
3. k (3)                      → voir gabarit ci-dessus
4. Modèle d'embedding         → échoue si : échecs « vocabulaire » persistants
                                 (jour 243 : comparaison mesurée)
5. Prompt de génération       → échoue si : réponses hors sources, citations
                                 décoratives, refus injustifiés
6. Seuil de refus (score min) → échoue si : réponses forcées sur top-k faibles
                                 OU refus de questions légitimes
```

**Explication** : le champ « Statut » (OK / sous surveillance / à re-tester) relie le document au réel — trois décisions ont déjà des données contre elles grâce à l'autopsie. **Variante** : ajoute pour chaque décision « ce que ça coûterait de changer » (re-ingestion complète pour 1-2-4, un fichier pour 3-5-6) — la matrice coût-du-changement × probabilité-d'échec est un raisonnement d'architecte.

## 🏢 Cas métier
Six mois après le lancement, un nouveau dev rejoint le projet RAG : « pourquoi k=3 ? pourquoi 400 tokens ? » — sans document, les réponses sont « c'était comme ça », et personne n'ose toucher. Avec tes six blocs, il lit, comprend, et sait QUOI mesurer avant de changer. Ce document est aussi la half du sujet « ADR » (jour 230) : tu documentes des décisions réversibles ici, tu trancheras une décision structurante là-bas.

## 🎤 Question d'entretien
**« Quels sont les principaux paramètres d'un RAG et comment les règles-tu ? »** → Six décisions : taille de chunk, overlap, k, modèle d'embedding, prompt de génération, seuil de refus. Ma méthode : chaque décision est documentée avec sa justification ET son critère d'échec observable, reliée aux échecs réels diagnostiqués, puis re-testée sur un jeu d'évaluation quand les données l'accusent. On ne règle pas au feeling — on instrumente.
