## 🎯 Objectif du jour
Apprendre à documenter : README, docstrings, ADR, diagrammes — la communication technique évaluée en entretien.

## 📖 Cours approfondi
**Concepts abordés :** README structuré · Docstrings/JSDoc · ADR · Diagrammes (quand/comment) · Écrire pour son lecteur.

On documente pour un LECTEUR précis, jamais « en général » : le recruteur (30 secondes, il veut quoi/démo/preuve), le collègue (comment lancer, comment contribuer), le futur toi (pourquoi cette décision). Chaque document a UN lecteur cible et répond à SES questions dans SON ordre.

La hiérarchie de la documentation : le README (la porte d'entrée), les docstrings/JSDoc (le contrat des fonctions publiques : paramètres, retour, erreurs possibles), les ADRs (le pourquoi des décisions), le diagramme (la vue d'ensemble qu'aucun texte ne remplace — mais UN diagramme simple et à jour vaut mieux que cinq diagrammes périmés).

Le test de qualité : lire son propre document À VOIX HAUTE en suivant ses instructions à la lettre, sur un environnement propre. Chaque friction rencontrée est un bug de documentation.

**Modèle mental : on documente toujours pour un LECTEUR PRÉCIS, jamais « en général ». Le recruteur (30 secondes : quoi, démo, preuve), le collègue (comment lancer, comment contribuer), le futur toi (pourquoi cette décision). Chaque document a UN lecteur cible et répond à SES questions dans SON ordre. La hiérarchie de la doc : le README (la porte d'entrée), les docstrings/JSDoc (le CONTRAT des fonctions publiques — paramètres, retour, erreurs possibles), les ADR (le POURQUOI des décisions), le diagramme (la vue d'ensemble qu'aucun texte ne remplace).** Documenter, c'est de la communication technique — TA compétence, évaluée en entretien, pas celle de l'IA.

Pourquoi écrire pour un lecteur précis. Une documentation « générale » ne sert personne : elle est trop technique pour le recruteur, trop superficielle pour le collègue qui doit contribuer, sans le contexte que cherche le futur toi. En identifiant le LECTEUR (qui va lire ? que cherche-t-il ? dans quel ordre ?), on écrit ce qui l'aide RÉELLEMENT. C'est le même principe que le clean code (jour 40) : optimiser pour le lecteur, pas pour l'écrivain — appliqué à la prose cette fois.

La hiérarchie de la documentation, depuis les fondations. **Le README** est la porte d'entrée (jour 66) : quoi, comment lancer, comment tester, architecture, limites. **Les docstrings/JSDoc** documentent le CONTRAT des fonctions publiques : ce que la fonction attend (paramètres et leurs types), ce qu'elle retourne, et les erreurs qu'elle peut lever — pour qu'on l'utilise sans lire son implémentation. **Les ADR** capturent le POURQUOI des décisions structurantes (jours 47, 66). **Le diagramme** donne la vue d'ensemble qu'aucun texte ne remplace : un schéma d'architecture simple montre en un coup d'œil les composants et leurs relations.

Les docstrings comme contrat, depuis les fondations. Une docstring/un JSDoc sur une fonction publique dit son CONTRAT : `@param` (ce qu'elle attend), `@returns` (ce qu'elle rend), et les erreurs possibles. Bénéfice : on utilise la fonction en lisant son contrat, sans plonger dans son code — comme les types (jour 36) mais avec l'intention et les cas d'erreur en prose. Le contrat documenté est ce qui rend une API de code utilisable.

La règle « documenter le POURQUOI, pas le QUOI ». Le code montre déjà CE QU'IL fait (visible) ; la documentation doit capturer ce qui est INVISIBLE dans le code : le pourquoi d'une décision (ADR), le contrat attendu (docstring), la vue d'ensemble (diagramme), le contexte. Documenter ce que le code fait déjà voir (paraphraser) est du bruit qui se périme (jour 40).

La règle du diagramme : simple et à jour. UN diagramme simple et juste vaut mieux que dix diagrammes complexes et périmés. Un schéma d'architecture (Mermaid, ou même une photo de papier) qui montre les grandes zones et leurs relations aide plus qu'un texte long. Mais un diagramme faux ou périmé TROMPE — mieux vaut pas de diagramme qu'un diagramme mensonger.

Limites et compromis. La documentation a un coût de MAINTENANCE : une doc périmée est pire qu'une absence de doc (elle ment). D'où : documenter ce qui change peu (contrats, décisions, architecture) plus que les détails volatils, et TESTER sa doc (suivre ses instructions sur un clone frais, jour 66). Trop documenter noie l'essentiel ; le bon niveau répond aux questions du lecteur cible.

La règle du jour : **documente pour un LECTEUR PRÉCIS (recruteur / collègue / futur toi), dans SON ordre de questions. Utilise la bonne hiérarchie : README (entrée), docstrings/JSDoc (contrat des fonctions publiques), ADR (pourquoi des décisions), diagramme simple et à jour (vue d'ensemble). Documente le POURQUOI, pas le QUOI — et teste ta doc.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire une docstring qui documente le CONTRAT d'une fonction publique (params, retour, erreurs), puis un diagramme d'architecture simple.

**Exemple simple** : une docstring qui documente le contrat, pas le code. Mauvais : « incrémente i » (paraphrase le code). Bon : « emprunte un livre ; lève ConflitMetier si déjà emprunté » (le contrat et les erreurs, invisibles dans la signature seule).

**Raisonnement pas-à-pas** : (1) j'identifie le lecteur (un collègue qui utilisera la fonction sans lire son code) ; (2) je documente ce qu'elle ATTEND, RETOURNE et les ERREURS ; (3) je ne paraphrase pas le code ; (4) j'ajoute un diagramme simple des couches.

**Implémentation (JSDoc = contrat)** :
```ts
/**
 * Emprunte un livre pour un membre, de façon atomique (transaction).
 * @param livreId - identifiant du livre à emprunter
 * @param membreId - identifiant du membre emprunteur
 * @returns l'emprunt créé (avec sa date)
 * @throws {ConflitMetier} si le livre est déjà emprunté (-> 409 côté route)
 * @throws {Error} si le livre est introuvable (-> 404 côté route)
 */
function emprunter(livreId: number, membreId: number): Emprunt { /* ... */ }
```
Un collègue utilise `emprunter` en lisant CE contrat, sans plonger dans son implémentation : il sait quoi passer, ce qu'il reçoit, et quelles erreurs gérer.

**Un diagramme d'architecture simple (Mermaid)** :
```text
flowchart LR
  Client -->|HTTP| Routes
  Routes -->|appelle| Services
  Services -->|SQL paramétré| Data
  Data -->|lit/écrit| SQLite[(SQLite)]
```
Le diagramme montre en un coup d'œil les couches et leur sens de dépendance — la vue d'ensemble qu'aucun paragraphe ne remplace. Simple et juste : il aide ; complexe et périmé, il tromperait.

## ⚠️ Erreurs fréquentes
- Documenter ce que fait le code (visible) au lieu du pourquoi et du contrat (invisibles) : bruit qui se périme.
- README générique qui pourrait décrire n'importe quel projet, écrit sans lecteur cible.
- Diagramme complexe et périmé qui trompe : mieux vaut un schéma simple et à jour, ou pas de diagramme.
- Docstrings qui paraphrasent la signature sans dire les erreurs possibles ni l'intention.

## 🏢 Cas métier
La documentation technique est une compétence de communication directement évaluée en entreprise et en entretien, souvent sous-estimée par les développeurs. Une bonne documentation réduit le coût de tout : onboarding d'un nouvel arrivant, contribution d'un collègue, maintenance six mois plus tard, intégration par une autre équipe. Les docstrings/JSDoc qui documentent les contrats permettent d'utiliser une API de code sans lire son implémentation — indispensable dans une base partagée. Les ADR préservent le pourquoi des décisions, évitant qu'elles soient défaites par ignorance. Les diagrammes d'architecture donnent la vue d'ensemble aux nouveaux venus. À l'inverse, une documentation absente ou périmée coûte cher (temps perdu, décisions mal comprises, doc qui ment). Pour un portfolio, une documentation claire (écrite pour le recruteur qui lira en 30 secondes) est décisive. Et la capacité à COMMUNIQUER techniquement — à l'écrit comme à l'oral — est ce qui distingue un développeur qu'on veut dans une équipe : « documente cette fonction/ce projet » et « explique-moi ton architecture » sont des exercices d'entretien fréquents.

## 🎤 Question d'entretien
**« Comment abordes-tu la documentation d'un projet ? »** → Je pars toujours du LECTEUR, jamais « en général » : le recruteur qui lit 30 secondes veut quoi/démo/preuve ; le collègue qui contribue veut comment lancer et comment le code s'organise ; le futur moi veut le pourquoi des décisions. Chaque document a un lecteur cible et répond à ses questions dans son ordre. J'utilise une hiérarchie : le README est la porte d'entrée (quoi, lancer, tester, architecture, limites) ; les docstrings/JSDoc documentent le CONTRAT des fonctions publiques — ce qu'elles attendent, retournent, et les erreurs qu'elles lèvent — pour qu'on les utilise sans lire leur code ; les ADR capturent le pourquoi des décisions structurantes ; et un diagramme simple donne la vue d'ensemble qu'aucun texte ne remplace. Ma règle : je documente le POURQUOI et le contrat (invisibles dans le code), jamais le QUOI que le code montre déjà — paraphraser le code est du bruit qui se périme. Et je teste ma doc : je suis mes propres instructions sur un clone frais. **Relance possible** : « et les diagrammes ? » → un diagramme simple et À JOUR vaut mieux que dix complexes et périmés : un schéma faux trompe le lecteur, donc mieux vaut pas de diagramme qu'un diagramme mensonger ; je garde un schéma d'architecture minimal et je le mets à jour quand la structure change.
