## 🎯 Objectif du jour
Structurer le pipeline.

## 📖 Cours approfondi
**Modèle mental : un pipeline est une chaîne de contrats, pas un script qui marche.** Ton RAG fonctionne — en un seul fichier où tout se touche. Le refactoring du jour le découpe en cinq modules aux frontières nettes : `ingest` (documents → textes), `chunk` (textes → chunks), `embed` (chunks → index), `search` (question → top-k), `answer` (top-k + question → réponse citée). Chaque module a UN contrat : ce qu'il prend, ce qu'il rend, ce qu'il ne fait pas.

Pourquoi c'est le bon moment : la semaine prochaine tu vas ITÉRER (changer le chunking, comparer des embeddings, ajouter du filtrage). Sur un monolithe, chaque expérience casse tout ; sur des modules, tu remplaces UNE pièce et le reste ne bouge pas. Le découpage d'aujourd'hui est ce qui rend les mesures du mois 9 possibles — c'est de l'infrastructure d'expérimentation, pas de l'esthétique.

Les règles du refactoring sûr (acquises au mois 5, appliquées ici) :
1. **Comportement constant** : mêmes questions → mêmes réponses avant/après. Tes 10 questions types sont ton harnais de tests — lance-les AVANT, garde les sorties, relance APRÈS, compare.
2. **Les formats intermédiaires sont documentés** : le format des chunks, de l'index, du top-k — écrits dans le README, parce que ce sont les points de branchement des futures expériences.
3. **Une CLI par étape ET une CLI bout-en-bout** : pouvoir relancer SEULEMENT l'ingestion, ou SEULEMENT la recherche, est exactement ce dont le débogage du jour 226 aura besoin.

Le README qui explique chaque étape n'est pas un bonus : c'est le document que tu ouvriras en entretien pour dérouler l'architecture — schéma, contrats, décisions.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : refactorer rag-from-scratch en 5 modules + CLI + README.

**Raisonnement** : harnais d'abord, découpage ensuite, vérification à la fin — jamais de refactoring sans filet.

**Structure cible** :
```
rag/
  ingest.py     # charge les documents → [{doc_id, texte, meta}]
  chunk.py      # → [{id, texte, source, position}]
  embed.py      # → index.json (+ méta : modèle, date, n)
  search.py     # (question, k) → [(score, chunk)]
  answer.py     # (question, top_k) → réponse citée (via llm_call)
  cli.py        # rag ingest / rag ask "..." / rag search "..." --k 5
tests/
  test_harnais.py   # les 10 questions types, sorties attendues figées
README.md           # schéma du pipeline + contrat de chaque module
```

**Protocole** :
```
1. AVANT : lance les 10 questions, sauvegarde les réponses (harnais).
2. Découpe module par module, en commençant par le plus indépendant (chunk).
3. APRÈS chaque module déplacé : relance le harnais. Un écart = stop, diagnostic.
4. À la fin : `rag ask` bout-en-bout + `rag search` seul fonctionnent.
```

**Explication** : `search` séparé de `answer` est LE découpage qui paiera le plus — le diagnostic du jour 226 doit pouvoir regarder le retrieval SANS payer la génération. **Variante** : ajoute `rag search --k 10 --scores` qui affiche les chunks et leurs scores — ton futur outil de débogage n°1.

## ⚠️ Erreurs fréquentes
- Refactorer sans harnais : tu ne sauras pas si les réponses ont changé — et avec un LLM à temp 0, elles DOIVENT être stables.
- Des modules qui s'importent en cascade (answer importe chunk) : les frontières sont décoratives si tout dépend de tout.
- Cacher les formats intermédiaires « pour encapsuler » : le mois 9 a BESOIN de brancher des mesures entre les étapes.
- README qui décrit les fichiers au lieu des contrats : « chunk.py découpe les textes » n'aide personne ; le format d'entrée/sortie, si.

## 🏢 Cas métier
Différence visible en entretien technique : le candidat A montre un notebook de 400 lignes « qui marche » ; le candidat B montre 5 modules, une CLI, un README avec le schéma et les contrats. Le second peut répondre à « et si on voulait changer le modèle d'embedding ? » en pointant UN fichier. C'est le même RAG — mais un seul des deux ressemble à du travail d'équipe.

## 🎤 Question d'entretien
**« Comment structures-tu un pipeline RAG pour pouvoir l'améliorer ensuite ? »** → Cinq modules aux contrats nets (ingest, chunk, embed, search, answer), formats intermédiaires documentés, CLI par étape pour déboguer chaque maillon isolément, et un harnais de questions types qui verrouille le comportement pendant les refactorings. L'itération sur un monolithe casse tout ; sur des modules, on remplace une pièce.
