## 🔁 Revue hebdomadaire

**Thème de la semaine :** Full-stack réel : front + API + auth simple, tests unitaires

### Bilan
Assembler les deux mondes proprement, protéger des routes avec un token simple, et écrire tes premiers vrais tests automatisés.

### Test pratique
90 min : ajoute à l'ensemble citations — un token d'API simple (header vérifié par middleware), le front qui l'envoie, et 6 tests Vitest sur la logique métier (validation, formatage, filtres).

### Test théorique
Pourquoi l'auth par header et pas dans l'URL ; qu'est-ce que CORS et pourquoi ton front le déclenche ; que teste un test unitaire vs un test d'intégration ; qu'est-ce qu'un mock ?

### Mini-projet / livrable
Suite de tests du squelette d'API (semaine 11) : au moins 10 tests couvrant validation et services.

### Exercice de réflexion architecturale
Pourquoi la logique métier dans les routes Express est-elle difficile à tester ? Refactore UNE route pour extraire la logique en fonction pure testée. Mesure : nombre de lignes de test nécessaires avant/après.

### Synthèse de la semaine
La semaine 16 a transformé « du code qui marche » en « du code de qualité, prouvé et maintenable » : tests unitaires Vitest qui rougissent quand on sabote le code (jour 106), tests de composants orientés comportement et non implémentation (107), mocks de la frontière réseau et tests d'intégration des flux (108), refactor de composants trop gros par extraction à responsabilité unique (109), hooks personnalisés pour partager la logique à état (110), et gestion d'erreur robuste sans écran blanc — error boundaries et états dégradés (111). Le fil rouge : **un front professionnel se PROUVE (des tests qui peuvent échouer), se LIT (des pièces à responsabilité unique) et ne CASSE jamais silencieusement (toute erreur mène à un état lisible)**. Tu abordes la semaine 17 (Projet 3, BiblioApp) avec de quoi construire une app testée, propre et résiliente — pas seulement fonctionnelle.

### Plan de remédiation (si un critère échoue)
- **Tests décoratifs** (qui ne peuvent pas rougir) : rejoue le jour 106 — sabote le code pour prouver que chaque test échoue ; couvre les cas limites, pas seulement le cas heureux.
- **Tests couplés à l'implémentation** : jour 107 — cherche par rôle/label/texte, affirme sur le DOM visible ; un refactor interne ne doit pas casser tes tests.
- **Sur-mock ou vrais appels réseau** : jour 108 — mocke uniquement la frontière externe ; teste en vrai ton code interne ; un test d'intégration attrape les bugs d'assemblage.
- **Composants fourre-tout** : jour 109 — extrais logique (hooks) et sections (sous-composants), une responsabilité nommable par pièce, sous protection des tests.
- **Logique dupliquée** : jour 110 — extrais un hook custom (partage la logique, pas les données), testé isolément.
- **Écran blanc possible** : jour 111 — error boundaries par section (try/catch n'attrape pas les exceptions de rendu), états d'erreur avec sortie ; prouve en cassant l'app.

### Questions d'entretien de la semaine
1. **« Qu'est-ce qui prouve la valeur d'un test unitaire ? »** Attendu : sa capacité à ROUGIR quand on sabote le code ; AAA, déterminisme, couverture des cas limites ; un test toujours vert ne protège rien.
2. **« Tester le comportement vs l'implémentation ? »** Attendu : chercher par rôle/label/texte, affirmer sur le DOM visible ; un test d'implémentation casse au refactor sans attraper de bug.
3. **« Que mockes-tu, que laisses-tu réel ? »** Attendu : mocker la frontière externe (réseau, temps) pour le déterminisme et les cas d'erreur rares ; ne jamais mocker le code testé ; l'intégration attrape les bugs d'assemblage.
4. **« Quand extraire un hook personnalisé ? »** Attendu : dès qu'une logique à état se répète ou alourdit un composant ; il partage la logique pas les données ; testé isolément.
5. **« Comment évites-tu l'écran blanc ? »** Attendu : error boundaries par section pour les exceptions de rendu (try/catch ne les attrape pas), états d'erreur avec sortie, résilience prouvée en cassant l'app.
