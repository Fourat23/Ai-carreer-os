## 🎯 Objectif du jour
Comprendre et poser des index.

## 📖 Cours approfondi
**Modèle mental : un index est une STRUCTURE DE RECHERCHE (un arbre trié, le plus souvent un B-tree) qui transforme un BALAYAGE COMPLET de la table (O(n), lire chaque ligne) en une recherche directe (O(log n)) — mais il a un COÛT (espace disque + ralentissement des écritures), donc on n'indexe QUE les colonnes vraiment interrogées, et on MESURE avant/après.** C'est l'application directe de la pensée algorithmique (complexité) et du réflexe « mesurer avant d'optimiser » (jour 102) au monde des bases. Sans index, chercher `WHERE email = 'x'` oblige la base à lire TOUTE la table ; avec un index sur `email`, elle va droit au but.

Comment ça marche et pourquoi c'est rapide :
1. **Le B-tree** : l'index maintient les valeurs d'une colonne TRIÉES dans une structure d'arbre équilibré. Chercher une valeur = descendre l'arbre (quelques sauts) au lieu de balayer n lignes. C'est pourquoi un index accélère les recherches d'égalité, de plage (`BETWEEN`, `>`) et les `ORDER BY` sur la colonne indexée.
2. **Où indexer** : les colonnes des `WHERE` fréquents, les colonnes de JOIN (clés étrangères), les colonnes de tri fréquent. Un index composite `(a, b)` sert les requêtes filtrant sur `a` puis `b` (l'ordre compte).
3. **Le coût — pourquoi ne pas tout indexer** : chaque index occupe de l'espace et doit être MIS À JOUR à chaque INSERT/UPDATE/DELETE (l'arbre se rééquilibre). Trop d'index ralentit les écritures et gaspille de l'espace. Un index sur une colonne jamais interrogée est un pur coût.

L'outil de décision — `EXPLAIN` (ou `EXPLAIN QUERY PLAN`) : il montre le PLAN d'exécution — la base fait-elle un « scan » complet (lent) ou un « index seek » (rapide) ? C'est ce qui permet de DIAGNOSTIQUER une requête lente et de VÉRIFIER qu'un index est réellement utilisé. On ne devine pas : on lit le plan.

La démarche professionnelle (identique au jour 102) : MESURER la requête lente (temps + plan), ajouter un index JUSTIFIÉ, REMESURER pour prouver le gain. Un index ajouté « au cas où » sans mesure est de l'optimisation à l'aveugle.

La règle du jour : **indexe les colonnes réellement interrogées (WHERE/JOIN/ORDER BY), diagnostique avec `EXPLAIN`, mesure avant/après, et n'indexe jamais par principe — chaque index accélère les lectures mais coûte en écritures et en espace**. L'index est un arbitrage lecture/écriture qu'on décide sur des mesures, pas des impressions.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : sur une base peuplée, mesurer une requête lente, ajouter un index justifié, remesurer.

**Exemple simple** : le diagnostic avant tout — `EXPLAIN QUERY PLAN SELECT * FROM commandes WHERE client_id = 42;`. S'il affiche « SCAN commandes » (balayage complet), un index sur `client_id` le transformera en « SEARCH ... USING INDEX ». On LIT le plan, on ne devine pas.

**Raisonnement pas-à-pas** : identifier la requête lente → lire son plan (`EXPLAIN`) → si scan complet sur une colonne filtrée, ajouter l'index → remesurer temps ET plan.

**Implémentation** :
```sql
-- 1. MESURER : plan AVANT (scan complet = lent sur grande table)
EXPLAIN QUERY PLAN
SELECT * FROM commandes WHERE client_id = 42;      -- "SCAN commandes"

-- 2. INDEXER la colonne réellement filtrée (justifié : WHERE fréquent sur client_id)
CREATE INDEX idx_commandes_client ON commandes(client_id);

-- 3. REMESURER : plan APRÈS
EXPLAIN QUERY PLAN
SELECT * FROM commandes WHERE client_id = 42;      -- "SEARCH ... USING INDEX idx_commandes_client"

-- Index composite pour un filtre à deux colonnes (l'ordre suit le WHERE) :
CREATE INDEX idx_ventes_date_produit ON ventes(date, produit_id);
-- Sert WHERE date = ? [AND produit_id = ?], mais PAS un filtre sur produit_id seul.
```

**Mini-quiz** : (a) Pourquoi un index accélère-t-il la recherche ? (b) Pourquoi ne pas indexer toutes les colonnes ? (c) À quoi sert `EXPLAIN` ?
→ (a) il maintient les valeurs triées dans un arbre : recherche en O(log n) au lieu d'un balayage O(n) ; (b) chaque index coûte de l'espace et ralentit les écritures (mise à jour de l'arbre à chaque INSERT/UPDATE) ; un index jamais interrogé est un pur coût ; (c) montrer le plan d'exécution — scan complet vs utilisation d'index — pour diagnostiquer et vérifier.

**Variante** : sur la même table, ajoute un index sur une colonne JAMAIS filtrée et mesure le ralentissement d'un gros INSERT en lot — tu vois concrètement le coût en écriture d'un index inutile.

## 🏢 Cas métier
Les index sont le premier levier de performance des bases en production : une requête qui balaie des millions de lignes (secondes ou minutes) devient instantanée avec le bon index. Mais l'excès d'index est un problème réel et courant — chaque index ralentit les écritures et gonfle la base, si bien qu'une table sur-indexée devient lente à alimenter. Les DBA et data engineers diagnostiquent avec `EXPLAIN`, ajoutent des index ciblés sur des requêtes mesurées, et suppriment les index inutilisés. Cette discipline « mesurer, indexer le prouvé, remesurer » est identique au réflexe de performance front (jour 102) et directement évaluée : savoir lire un plan d'exécution et justifier un index distingue quelqu'un qui comprend les bases de quelqu'un qui « ajoute des index au hasard ».

## 🎤 Question d'entretien
**« Comment optimises-tu une requête SQL lente ? »** → Je ne devine pas, je DIAGNOSTIQUE avec `EXPLAIN` (le plan d'exécution) : la base fait-elle un balayage complet de la table (`SCAN`, lent) ou une recherche par index (`SEARCH ... USING INDEX`, rapide) ? Un index est une structure triée (B-tree) qui transforme une recherche O(n) en O(log n) ; j'en ajoute un sur les colonnes réellement interrogées — celles des `WHERE`, `JOIN` et `ORDER BY` fréquents. Puis je REMESURE (temps + plan) pour prouver le gain. Je n'indexe jamais par principe : chaque index coûte de l'espace et ralentit les écritures (l'arbre se met à jour à chaque INSERT/UPDATE), donc un index sur une colonne jamais filtrée est un pur coût. C'est un arbitrage lecture/écriture décidé sur des mesures — exactement comme « mesurer avant d'optimiser » au front.
