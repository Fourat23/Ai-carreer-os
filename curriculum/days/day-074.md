# Jour 74 — Documentation technique : écrire pour être compris

## 🎯 Objectif du jour
Apprendre à documenter : README, docstrings, ADR, diagrammes — la communication technique évaluée en entretien.

## 📖 Cours approfondi
**Concepts abordés :** README structuré · Docstrings/JSDoc · ADR · Diagrammes (quand/comment) · Écrire pour son lecteur.

On documente pour un LECTEUR précis, jamais « en général » : le recruteur (30 secondes, il veut quoi/démo/preuve), le collègue (comment lancer, comment contribuer), le futur toi (pourquoi cette décision). Chaque document a UN lecteur cible et répond à SES questions dans SON ordre.

La hiérarchie de la documentation : le README (la porte d'entrée), les docstrings/JSDoc (le contrat des fonctions publiques : paramètres, retour, erreurs possibles), les ADRs (le pourquoi des décisions), le diagramme (la vue d'ensemble qu'aucun texte ne remplace — mais UN diagramme simple et à jour vaut mieux que cinq diagrammes périmés).

Le test de qualité : lire son propre document À VOIX HAUTE en suivant ses instructions à la lettre, sur un environnement propre. Chaque friction rencontrée est un bug de documentation.

**Leçon(s) de fond à lire/relire :**
- [Storytelling technique](/doc/lessons/technical-storytelling)
- [Clean code](/doc/lessons/clean-code)

## ✍️ Pratique autonome
> **D'abord sans IA.** Tente seul au moins 30 minutes. Ne copie-colle jamais une réponse d'IA : lis, ferme, réécris de mémoire.

### Exercice principal
Reprends un projet et écris : un README exemplaire, des docstrings sur les fonctions clés, un ADR complet, un diagramme d'architecture simple (Mermaid ou papier). Fais relire (à voix haute).

## 📦 Livrable attendu
Documentation complète d'un projet (README + docstrings + ADR + diagramme).

## ✅ Critères de validation
- [ ] README refondu et TESTÉ (instructions suivies sur clone frais)
- [ ] Docstrings sur les fonctions publiques clés (contrat complet : params, retour, erreurs)
- [ ] Un diagramme d'architecture simple et juste (Mermaid ou photo de papier)

## ⚠️ Erreurs fréquentes
- Documenter ce que fait le code (visible) au lieu du pourquoi (invisible).
- README générique qui pourrait décrire n'importe quel projet.

## 🔗 Ressources
- Guide "How to write a good README" ; adr.github.io

## 🤖 Consigne d'utilisation de l'IA
Écris SEUL : la communication technique est TA compétence, pas celle de l'IA.

## 🎤 Question d'entretien
**« Parle-moi d'un de tes projets. »** → Structure STAR : le problème et pour qui, tes DÉCISIONS (avec les trade-offs / ADRs), les résultats CHIFFRÉS, un obstacle réel et sa résolution. Raconter les décisions, pas la liste des features.

## 🧠 À retenir
- Concepts clés du jour : README structuré, Docstrings/JSDoc, ADR, Diagrammes (quand/comment), Écrire pour son lecteur.
- Approfondis via la leçon de fond : Storytelling technique, Clean code.
- Je dois pouvoir REFAIRE l'exercice seul demain et l'EXPLIQUER à l'oral — sinon ce n'est pas encore acquis.

## 🚀 Pourquoi ça comptera plus tard
- **En carrière** : un projet non racontable n'existe pas — le storytelling (STAR, décisions, chiffres) transforme ton travail en offres d'entretien.
- **En équipe** : READMEs, ADRs et démos sont la communication asynchrone qui fait fonctionner les équipes techniques.
- **En entretien** : la clarté d'explication est évaluée dans TOUS les entretiens — c'est la compétence transversale n°1.
