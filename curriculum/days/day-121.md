## 📖 Cours approfondi
**Modèle mental : un module Python est un NAMESPACE dans un fichier — organiser un projet, ce n'est pas empiler des fonctions dans un seul script, c'est découper le code en modules à responsabilité unique qu'on IMPORTE.** Tu sais écrire du Python idiomatique (jour 120) ; aujourd'hui tu structures un vrai projet. La brique de base est la fonction ; l'unité d'organisation est le module (un fichier `.py`) ; et un dossier de modules devient un package.

Ce qu'il faut maîtriser :
1. **La fonction bien conçue** : `def nom(params) -> type:`, un `return` explicite (une fonction Python sans return renvoie `None`), des arguments par défaut (`def f(x, sep=", ")`), et les arguments nommés (`f(x, sep="; ")`) qui rendent l'appel lisible. Une fonction fait UNE chose, nommée d'après ce qu'elle fait.
2. **Le module et l'import** : chaque fichier `.py` est un module dont le nom est le nom de fichier. `from notes.stockage import charger` importe une fonction précise. Contrairement au `<script>` global du navigateur, rien n'est global entre fichiers : on importe explicitement ce dont on a besoin — c'est le cousin des modules ESM de JS, mais l'unité EST le fichier.
3. **Le garde `if __name__ == "__main__":`** : il sépare « ce qui s'exécute quand je lance le fichier » de « ce qui est disponible quand je l'importe ». Sans lui, importer un module exécuterait tout son code — un piège classique. C'est ce qui fait qu'un module peut être À LA FOIS une bibliothèque et un point d'entrée.
4. **Les fichiers** : `with open(chemin) as f:` (le `with` ferme le fichier automatiquement, même en cas d'erreur — l'équivalent du `try/finally`), et `pathlib.Path` pour manipuler les chemins proprement (`Path("data") / "notes.json"`). Pour la persistance structurée : le module `json` (`json.load`/`json.dump`).

La règle du jour : **découpe en modules à responsabilité unique, importe explicitement, protège le point d'entrée avec `__main__`, et gère les fichiers avec `with`**. Un projet bien organisé se lit module par module ; un script de 500 lignes où tout se touche est le contraire de ce qu'on attend d'un développeur Python. C'est le clean code (mois 2) appliqué à la structure d'un projet Python.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : une CLI `notes` (ajouter/lister/chercher, persistée en JSON) découpée en modules propres avec `argparse`.

**Exemple simple** : le garde de point d'entrée, à connaître par cœur — `if __name__ == "__main__": main()`. Il fait que lancer `python cli.py` exécute `main()`, mais `import cli` ne l'exécute PAS. C'est la frontière entre bibliothèque et programme.

**Raisonnement pas-à-pas** : séparer le stockage (I/O JSON), la logique métier (ajouter/chercher) et l'interface (argparse) en modules distincts → chacun testable isolément → un point d'entrée qui les assemble.

**Implémentation** :
```python
# notes/stockage.py — responsabilité : lire/écrire le fichier JSON
import json
from pathlib import Path
FICHIER = Path("notes.json")
def charger() -> list[dict]:
    if not FICHIER.exists():
        return []
    with FICHIER.open(encoding="utf-8") as f:   # with : fermeture garantie
        return json.load(f)
def sauver(notes: list[dict]) -> None:
    with FICHIER.open("w", encoding="utf-8") as f:
        json.dump(notes, f, ensure_ascii=False, indent=2)

# notes/metier.py — responsabilité : la logique, sans I/O ni CLI
def ajouter(notes: list[dict], texte: str) -> list[dict]:
    return [*notes, {"id": len(notes) + 1, "texte": texte}]   # immuable
def chercher(notes: list[dict], mot: str) -> list[dict]:
    return [n for n in notes if mot.lower() in n["texte"].lower()]

# cli.py — responsabilité : l'interface
import argparse
from notes import stockage, metier
def main() -> None:
    p = argparse.ArgumentParser()
    p.add_argument("action", choices=["ajouter", "lister", "chercher"])
    p.add_argument("valeur", nargs="?", default="")
    args = p.parse_args()
    notes = stockage.charger()
    if args.action == "ajouter":
        stockage.sauver(metier.ajouter(notes, args.valeur))
    elif args.action == "chercher":
        for n in metier.chercher(notes, args.valeur): print(n["texte"])
    else:
        for n in notes: print(n["texte"])
if __name__ == "__main__":   # point d'entrée protégé
    main()
```

**Mini-quiz** (réponds sans regarder) : (a) Que renvoie une fonction Python sans `return` ? (b) À quoi sert `if __name__ == "__main__"` ? (c) Pourquoi ouvrir un fichier avec `with` ?
→ (a) `None` ; (b) séparer le code exécuté au lancement du code disponible à l'import ; (c) le fichier se ferme automatiquement même en cas d'erreur (comme un try/finally).

**Variante** : ajoute une commande `supprimer <id>` — tu dois pouvoir le faire en ajoutant UNE fonction dans `metier.py` et un `choices` dans la CLI, sans toucher au stockage. Si ça t'oblige à tout modifier, tes modules sont mal découpés.

## 🏢 Cas métier
Tout outil ou service Python d'entreprise est organisé en modules à responsabilité unique : la couche d'accès aux données séparée de la logique métier, elle-même séparée de l'interface (CLI, API). Cette séparation permet de tester la logique sans fichier ni réseau, de remplacer le stockage (JSON → base de données) sans toucher au métier, et de faire évoluer chaque partie indépendamment. Le contre-exemple coûteux, courant chez les débutants venus de scripts, est le fichier unique de plusieurs centaines de lignes où l'I/O, la logique et l'affichage sont entremêlés : impossible à tester, à réutiliser ou à faire évoluer. Savoir structurer un projet Python en modules est un prérequis pour toute base de code partagée — et directement visible dans un repo.

## 🎤 Question d'entretien
**« Comment organises-tu un projet Python, et à quoi sert `if __name__ == "__main__"` ? »** → Je découpe en modules à responsabilité unique — typiquement la couche d'accès aux données (I/O), la logique métier pure (sans I/O), et l'interface (CLI/API) — que j'importe explicitement. Rien n'est partagé implicitement entre fichiers : chaque module est un namespace, on importe ce dont on a besoin. Le garde `if __name__ == "__main__":` sépare le code exécuté quand on LANCE le fichier de celui disponible quand on l'IMPORTE — sans lui, importer un module exécuterait tout son code. Ça permet à un module d'être à la fois une bibliothèque et un point d'entrée. Pour les fichiers, j'utilise `with open(...)` qui garantit la fermeture, et `pathlib` pour les chemins.
