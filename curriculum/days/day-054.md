# Jour 54 — Validation, erreurs centralisées, robustesse d'API

## 🎯 Objectif du jour
Rendre une API robuste : valider toutes les entrées, centraliser les erreurs, ne jamais crasher ni fuiter.

## 📖 Cours approfondi
**Concepts abordés :** Validation des entrées · Middleware d'erreurs central · Erreur opérationnelle vs bug · Logs sans fuite.

Une API robuste part d'un principe : TOUTE entrée est hostile jusqu'à validation. Chaque champ est vérifié (présence, type, bornes, format) à l'entrée, et le refus est précis : 400 avec la liste des problèmes (ton pattern collecteur du jour 5).

La gestion d'erreurs se CENTRALISE : un middleware d'erreurs final attrape tout, distingue l'erreur OPÉRATIONNELLE (attendue : ressource absente → 404, entrée invalide → 400, on informe le client) du BUG (inattendu : on log les détails en interne, on répond un 500 générique — les détails internes ne fuient JAMAIS au client, c'est une règle de sécurité).

Le test d'une API robuste : l'attaquer soi-même. Dix requêtes malveillantes (types faux, champs manquants, ids absurdes, corps géant, JSON invalide) — chacune doit recevoir une réponse propre, jamais un crash ni une stack trace.

### Exercice principal
Durcis l'API citations : validation stricte à la main, middleware d'erreurs central, 400 détaillés, 404 propres. Attaque-la avec 10 requêtes malveillantes et vérifie chaque réponse.

## 📦 Livrable attendu
API durcie + 10 requêtes malveillantes et leurs réponses correctes.

## ✅ Critères de validation
- [ ] Les 10 requêtes malveillantes reçoivent chacune une réponse correcte (statut + message utile)
- [ ] Le middleware d'erreurs central distingue 400/404 (informatif) de 500 (générique, loggé en interne)
- [ ] Le process ne crashe sur AUCUNE entrée

## ⚠️ Erreurs fréquentes
- Valider à une seule porte, en oublier une autre.
- 500 qui fuite la stack trace au client.
