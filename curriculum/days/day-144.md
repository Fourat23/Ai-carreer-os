## 🎯 Objectif du jour
Charger en base transactionnellement.

## 📖 Cours approfondi
**Modèle mental : charger, c'est écrire les données propres dans un SCHÉMA PENSÉ, de façon TRANSACTIONNELLE et REJOUABLE EN UNE COMMANDE — le load de DataPulse combine le schéma sain (jour 134), la transaction atomique (136) et l'idempotence (139) en un seul point d'entrée reproductible. « Rejouable en une commande » est le critère de réussite.** Le load est l'étape « L » (jour 138) appliquée à DataPulse : il prend le résultat propre du transform (jour 143) et l'écrit dans SQLite, prêt à alimenter le dashboard. Sa qualité se mesure à une chose : peut-on relancer tout le pipeline d'une commande et obtenir un état correct, à chaque fois ?

Ce que le load de DataPulse assemble :
1. **Un schéma pensé** (jour 134) : les tables cibles avec les bons types, contraintes (NOT NULL, CHECK) et clés — pas un `to_sql` brut sans réflexion. Le schéma reflète les entités et sert les requêtes du dashboard.
2. **Une écriture transactionnelle** (jour 136) : le chargement réussit ENTIÈREMENT ou est annulé — jamais une base à moitié chargée qui donnerait un dashboard faux. Si l'écriture échoue à mi-chemin, rollback.
3. **L'idempotence** (jour 139) : relancer le pipeline ne DUPLIQUE pas les données. Selon le cas : remplacer entièrement la table (`if_exists="replace"` pour un rechargement complet) ou upsert par clé (pour un chargement incrémental). Le critère « rejouable en une commande » EXIGE l'idempotence.
4. **Un point d'entrée unique** : une commande (`python -m datapulse` ou `make run`) qui enchaîne extract → transform → load et laisse la base prête. La reproductibilité (jour 125) rendue concrète : un tiers clone, lance une commande, obtient le même résultat.

Pourquoi « une commande » est le bon critère : un pipeline qui exige dix étapes manuelles dans le bon ordre n'est ni reproductible, ni démontrable, ni fiable. Réduire tout le pipeline à une commande rejouable force à automatiser proprement, à gérer l'ordre des étapes, et à rendre le tout idempotent. C'est ce qui transforme un ensemble de scripts en un OUTIL.

La règle du jour : **charge dans un schéma pensé, transactionnellement et idempotemment, derrière un point d'entrée unique ; le pipeline entier doit se rejouer en une commande et produire un état correct à chaque fois**. Le load bien fait est ce qui rend DataPulse reproductible et démontrable — la condition d'un vrai projet.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : charger DataPulse en SQLite transactionnellement, avec un schéma propre, rejouable en une commande.

**Exemple simple** : le critère de réussite en une ligne de shell — `python -m datapulse` recrée la base complète à partir de zéro, à chaque exécution, sans doublon. Si ça demande plus d'une commande ou casse au deuxième lancement, le load n'est pas fini.

**Raisonnement pas-à-pas** : créer le schéma pensé → charger transactionnellement → garantir l'idempotence (replace ou upsert) → tout enchaîner derrière un point d'entrée unique.

**Implémentation** :
```python
import sqlite3

SCHEMA = """
CREATE TABLE IF NOT EXISTS trafic (
  date TEXT NOT NULL, mois TEXT NOT NULL, station TEXT NOT NULL,
  valeur INTEGER NOT NULL CHECK (valeur >= 0));
"""  # schéma pensé (types, contraintes) — jour 134

def load(df, chemin="datapulse.db") -> None:
    with sqlite3.connect(chemin) as con:                 # transaction (jour 136) : tout ou rien
        con.executescript(SCHEMA)
        df.to_sql("trafic", con, if_exists="replace",    # idempotent : recharge complète, pas de doublon
                  index=False)
    # le `with` commit si tout va bien, rollback sur exception

def run() -> None:                                        # POINT D'ENTRÉE unique
    brut = extract()                                      # jour 142
    propre, rapport = transform(brut)                     # jour 143
    load(propre)                                          # ce jour
    print(rapport)
if __name__ == "__main__":
    run()   # → `python -m datapulse` : tout le pipeline en UNE commande, rejouable
```

**Mini-quiz** : (a) Pourquoi « rejouable en une commande » est-il le bon critère ? (b) Pourquoi charger transactionnellement ? (c) Comment éviter les doublons au rechargement ?
→ (a) un pipeline à dix étapes manuelles n'est ni reproductible ni démontrable ; une commande force l'automatisation propre et l'idempotence ; (b) pour ne jamais laisser une base à moitié chargée qui donnerait un dashboard faux ; (c) idempotence — remplacer la table (recharge complète) ou upsert par clé (incrémental).

**Variante** : lance ton pipeline DEUX fois de suite et vérifie que la base contient exactement les mêmes données (pas de doublons) — c'est la preuve d'idempotence, le cœur du « rejouable en une commande ».

## 🏢 Cas métier
La reproductibilité « en une commande » est ce qui sépare un projet data démontrable d'un tas de scripts : un pipeline qui exige de lancer manuellement dix cellules dans le bon ordre n'est ni fiable, ni partageable, ni présentable — et casse dès qu'on oublie une étape. En entreprise, les pipelines de production tournent sur commande ou planifiés, de façon idempotente, transactionnelle, dans un schéma pensé, précisément pour être rejouables sans surveillance. Pour un portfolio, un DataPulse qui se relance d'une seule commande et reconstruit une base cohérente à chaque fois prouve une maîtrise de la reproductibilité que les recruteurs reconnaissent immédiatement. Le load bien fait — schéma, transaction, idempotence, point d'entrée unique — est la charnière qui rend le projet réel.

## 🎤 Question d'entretien
**« Qu'est-ce qui fait un bon chargement (load) dans un pipeline ? »** → Il assemble trois choses en un point d'entrée unique. Un SCHÉMA pensé (types, contraintes, clés — pas un `to_sql` brut), qui reflète les entités et sert les requêtes en aval. Une écriture TRANSACTIONNELLE : tout ou rien, jamais une base à moitié chargée qui donnerait un dashboard faux. Et l'IDEMPOTENCE : relancer ne duplique pas — soit je remplace la table (rechargement complet), soit j'upsert par clé (incrémental). Le critère de réussite que je vise est « rejouable en UNE commande » : tout le pipeline (extract → transform → load) derrière un seul point d'entrée qui reconstruit un état correct à chaque exécution. C'est ce qui rend le projet reproductible et démontrable — un pipeline à dix étapes manuelles n'est ni fiable ni présentable.
