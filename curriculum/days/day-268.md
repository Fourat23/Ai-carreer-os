## 🎯 Objectif du jour
Améliorer par les mesures.

## 📖 Cours approfondi
**Modèle mental : une amélioration pilotée est une expérience à hypothèse — on prédit, on change UNE chose, on mesure contre la baseline, on garde ou on jette.** C'est la boucle des jours 211 et 235, appliquée au projet entier avec toute la rigueur acquise au mois d'évaluation. La différence avec « bricoler jusqu'à ce que ça semble mieux » : chaque amélioration part d'une HYPOTHÈSE issue de la baseline (jour 267), et se juge par une comparaison chiffrée MULTIDIMENSIONNELLE — pas seulement sur la métrique visée, mais sur TOUTES (pour attraper les régressions).

Le protocole d'une amélioration pilotée :
1. **L'hypothèse, écrite avant** : « la faiblesse est X (mesurée à la baseline) ; je pense que le changement C l'améliorera de ~Δ, sans dégrader le reste ». Exemple : « les synthèses sont à 0,50 d'exactitude alors que leur rappel@k est bon → c'est la génération multi-chunks ; un prompt de synthèse qui demande d'intégrer explicitement plusieurs sources devrait faire gagner ~0,20, sans toucher aux factuelles ».
2. **Le changement isolé** : UNE modification (le prompt de synthèse, ou le chunking, ou k — pas trois). Si plusieurs changent, un gain devient inattribuable et une régression se cache.
3. **La mesure complète** : `rag eval --compare baseline amelioration1` — le delta sur la métrique visée ET sur toutes les autres. C'est la comparaison multidimensionnelle qui distingue un vrai gain d'un déplacement de problème.
4. **La décision et la trace** : garder (si gain net sans régression inacceptable), jeter (si régression), ou nuancer (gain sur la cible, petite régression tolérée — décision explicite). Chaque amélioration est versionnée (jour 211) avec son rapport de comparaison.

Le cas le plus instructif — et le plus fréquent : l'amélioration qui MARCHE sur sa cible mais RÉGRESSE ailleurs. Le nouveau prompt de synthèse gagne 0,20 sur les synthèses mais rend les factuelles plus verbeuses (−0,05 sur leur pertinence). Est-ce un bon échange ? La réponse dépend de la distribution d'usage (le golden set représentatif, jour 253) — et c'est une DÉCISION documentée, pas un réflexe. Savoir refuser une amélioration qui déplace le problème est aussi important que savoir en garder une qui le résout.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : la première amélioration pilotée, de l'hypothèse à la décision tracée.

**Raisonnement** : hypothèse issue de la baseline, changement isolé, comparaison multidimensionnelle, décision documentée.

**Le cycle complet (exemple : synthèses)** :
```
HYPOTHÈSE (écrite avant) :
  Faiblesse baseline : synthèses exactitude 0,50, rappel@k bon (0,83)
  → diagnostic : génération multi-chunks défaillante (jours 244/249/267)
  → changement : prompt de synthèse demandant d'INTÉGRER explicitement
    les sources multiples et de signaler les points non couverts
  → prédiction : synthèses 0,50 → ~0,70, autres types stables

CHANGEMENT ISOLÉ : uniquement le prompt de génération pour les synthèses
  (détecté par type de question ; le reste du pipeline inchangé)

MESURE : rag eval --compare baseline amelioration1
                        baseline   amélioration1   delta
  synthèse (exactitude)   0,50        0,72         +0,22 ✓ (hypothèse validée)
  factuelles (pertinence) 0,92        0,88         -0,04  ← régression légère
  fidélité globale        0,88        0,89         +0,01
  latence p95             1,1 s       1,1 s         stable

DÉCISION : GARDÉ. Le gain synthèse (+0,22) domine la régression factuelle
  (-0,04) ; les synthèses sont 15% du golden set (usage réel), le gain net
  est positif. Régression factuelle notée pour l'amélioration 2 (jour 269).
  Versionné : prompt-generation-v3, rapport de comparaison archivé.
```

**Explication** : la comparaison multidimensionnelle est ce qui révèle la régression factuelle qu'une mesure ciblée aurait manquée — et la décision de garder est EXPLICITE, fondée sur la distribution d'usage, pas sur le seul score cible. **Variante** : si ton hypothèse est RÉFUTÉE (le prompt de synthèse ne gagne rien, ou dégrade), c'est un résultat AUSSI précieux — documente pourquoi (peut-être le problème n'est pas le prompt mais le chunking des passages à synthétiser) et ré-oriente. Une hypothèse réfutée proprement vaut mieux qu'un bricolage qui « marche » sans qu'on sache pourquoi.

## 🏢 Cas métier
L'amélioration pilotée par les métriques est le quotidien des équipes ML matures : on ne pousse JAMAIS une amélioration sans son rapport de comparaison avant/après sur toutes les métriques. La raison est douloureusement apprise : les améliorations qui « déplacent le problème » (gain visible, régression cachée) sont la première cause de dégradation silencieuse des systèmes. « Amélioration 1 : +0,22 sur les synthèses, −0,04 sur les factuelles, gardée car les synthèses dominent l'usage » est exactement le type de décision tracée qu'un lead attend — et que peu de juniors savent produire.

## 🎤 Question d'entretien
**« Comment améliores-tu un système sans casser ce qui marche ? »** → Amélioration pilotée : une hypothèse écrite avant (issue de la baseline), UN changement isolé, une mesure MULTIDIMENSIONNELLE contre la baseline (pas seulement la métrique visée — c'est elle qui attrape les régressions), puis une décision tracée (garder/jeter/nuancer). Le cas clé : l'amélioration qui gagne sur sa cible mais régresse ailleurs — la garder ou non dépend de la distribution d'usage, et c'est une décision documentée. Savoir refuser une amélioration qui déplace le problème vaut autant que savoir en garder une bonne.
