## 🎯 Objectif du jour
Comprendre les données, établir la baseline.

## 📖 Cours approfondi
**Modèle mental : avant tout modèle, on COMPREND les données (EDA) et on pose une BASELINE — le premier livrable d'un projet ML n'est pas un modèle sophistiqué mais une baseline honnête qui donne le SEUIL à battre et révèle les pièges (déséquilibre, fuites, features douteuses). Un projet qui saute l'EDA et la baseline construit sur du sable.** Le Projet 5 (ChurnScope) commence ici : pas par entraîner le meilleur modèle, mais par comprendre à quoi on a affaire et fixer un point de départ mesurable. C'est l'application du cadrage (jour 174) aux vraies données.

Ce que l'EDA + baseline doit accomplir, depuis les fondations :
1. **L'analyse exploratoire (EDA)** appliquée à la cible métier : distribution de la CIBLE (quel taux de churn ? le déséquilibre confirmé, jour 152), qualité des features (manquants, aberrants, types), corrélations avec la cible (quelles features semblent porter du signal ?), et surtout la chasse aux FUITES potentielles (une feature calculée après l'événement de churn ?). C'est l'inspection (jours 127, 149) orientée vers la question métier.
2. **La confirmation du cadrage** : la cible définie (jour 174) est-elle bien construite dans les données ? Le déséquilibre est-il celui attendu ? Les features nécessaires sont-elles disponibles au moment de la prédiction ?
3. **La baseline honnête** : le modèle trivial (classe majoritaire, ou règle métier simple) sur la métrique choisie. Il donne le SEUIL sous lequel tout modèle est inutile. Sur du churn à 6 %, prédire « pas de churn » donne 94 % d'accuracy — d'où l'importance d'avoir choisi la bonne métrique au cadrage (rappel/précision, pas accuracy).
4. **Le split propre dès le départ** : réserver un jeu de test qui ne sera PAS touché avant l'évaluation finale (jour 179), et travailler en validation croisée sur le reste. Fixer cette discipline dès l'EDA évite le leakage plus tard.

Pourquoi commencer par là : sauter l'EDA fait rater les pièges (une fuite, un déséquilibre extrême, des features inutilisables) qui invalideront tout le travail en aval. Et sans baseline, on n'a aucun repère pour juger un modèle — « AUC 0,72 » ne veut rien dire sans savoir que la baseline est à 0,50. L'EDA + baseline est le socle honnête sur lequel tout le projet se construit.

La règle du jour : **commence ChurnScope par l'EDA (distribution de la cible, qualité, fuites potentielles) et une baseline honnête sur la bonne métrique ; le premier livrable est ce socle, pas un modèle sophistiqué. Sans EDA on rate les pièges, sans baseline on n'a aucun repère**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : EDA complète de ChurnScope, question métier confirmée, split, baseline établie.

**Exemple simple** : la première chose à regarder — la distribution de la cible. `df["churn"].value_counts(normalize=True)` révèle le taux de churn (ex. 6 %) et donc le déséquilibre, qui conditionne le choix de métrique et la baseline. On ne modélise rien avant de connaître ce chiffre.

**Raisonnement pas-à-pas** : inspecter la cible et les features → chasser les fuites → split (test réservé) → baseline sur la métrique choisie.

**Implémentation** :
```python
import pandas as pd
from sklearn.model_selection import train_test_split
from sklearn.dummy import DummyClassifier
from sklearn.metrics import roc_auc_score, recall_score

df = pd.read_csv("churn.csv")
print(df["churn"].value_counts(normalize=True))     # déséquilibre : ex. 6 % de churn
print(df.isna().mean().sort_values(ascending=False).head())   # manquants
print(df.corr(numeric_only=True)["churn"].sort_values())      # signal apparent + FUITES ?
# -> une feature parfaitement corrélée à churn est suspecte (fuite : calculée après l'événement).

X, y = df.drop(columns=["churn"]), df["churn"]
X_dev, X_test, y_dev, y_test = train_test_split(X, y, test_size=0.2,
    stratify=y, random_state=42)   # stratify : garder le taux de churn dans chaque part

base = DummyClassifier(strategy="most_frequent").fit(X_dev, y_dev)
print("baseline recall:", recall_score(y_test, base.predict(X_test)))   # ~0 : elle rate tout churn
# -> le futur modèle devra clairement battre ce seuil sur la métrique métier.
```

**Mini-quiz** : (a) Quelle est la première chose à regarder dans les données ? (b) Comment repère-t-on une fuite pendant l'EDA ? (c) Pourquoi établir une baseline avant tout modèle ?
→ (a) la distribution de la CIBLE (taux de churn, déséquilibre) — elle conditionne métrique et baseline ; (b) une feature anormalement corrélée à la cible, ou calculée après l'événement de churn, est suspecte ; (c) elle donne le seuil sous lequel tout modèle est inutile ; sans repère, « AUC 0,72 » ne veut rien dire.

**Variante** : stratifie le split (`stratify=y`) pour conserver le taux de churn dans le train ET le test. Sur une cible rare, un split non stratifié peut mettre trop peu de positifs dans le test et rendre l'évaluation instable — un détail qui compte sur les données déséquilibrées.

## 🏢 Cas métier
L'EDA et la baseline sont le socle de tout projet ML sérieux, et les sauter est une cause majeure d'échec : un data scientist qui fonce sur un modèle complexe sans EDA rate la fuite qui invalidera tout, ou le déséquilibre qui rend son accuracy trompeuse ; sans baseline, il ne sait pas si son « AUC 0,72 » est bon ou catastrophique. En entreprise, un premier livrable « EDA + baseline » est attendu et VALORISÉ : il montre qu'on a compris le problème et posé un repère honnête avant d'investir dans la modélisation. C'est aussi ce qui permet au métier de calibrer ses attentes tôt. Pour un projet de portfolio, une EDA rigoureuse qui révèle les pièges et une baseline honnête démontrent une maturité que les recruteurs valorisent bien plus qu'un modèle « impressionnant » sans fondations.
