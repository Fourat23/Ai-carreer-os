## 🎯 Objectif du jour
Implémenter Stack (LIFO) et Queue (FIFO) génériques, comprendre leurs coûts O(1), les appliquer.

## 📖 Cours approfondi
**Concepts abordés :** LIFO / FIFO · Opérations O(1) · Classe générique · Applications : undo, parenthèses, files.

Une Stack (pile) est LIFO : dernier entré, premier sorti — comme une pile d'assiettes. Une Queue (file) est FIFO : premier entré, premier sorti — comme une file d'attente. Les deux offrent des opérations O(1) aux extrémités.

Cas d'usage réels : la Stack porte l'historique undo/redo, la call stack de la récursion, la vérification de parenthèses ; la Queue porte les files de traitement, le BFS, les files de messages (mois 10).

En TypeScript, la classe générique `Stack<T>` fonctionne pour tout type sans perdre le typage : c'est exactement le cas d'usage des génériques vus au jour 37.

**Modèle mental : une Stack et une Queue ne sont pas des « conteneurs » de plus — ce sont des DISCIPLINES D'ACCÈS. La Stack impose LIFO (dernier entré, premier sorti, comme une pile d'assiettes) ; la Queue impose FIFO (premier entré, premier sorti, comme une file d'attente). Choisir la bonne discipline rend un problème trivial ; choisir la mauvaise le rend inextricable. Leur valeur tient à ce qu'elles INTERDISENT (l'accès arbitraire), pas à ce qu'elles offrent.** Un tableau permet tout ; une Stack ne permet QUE d'empiler et dépiler au sommet — cette contrainte est exactement ce qui modélise l'imbrication, l'historique et l'ordre de traitement.

Pourquoi ces structures existent, depuis les fondations. Certains problèmes ont une structure d'IMBRICATION (parenthèses, appels de fonctions, undo/redo) où « le dernier ouvert doit se fermer en premier » : c'est LIFO, une pile. D'autres ont une structure d'ORDONNANCEMENT équitable (tâches à traiter dans l'ordre d'arrivée, parcours en largeur) : c'est FIFO, une file. Plutôt que de re-coder cette logique à la main, on encapsule la discipline dans un type dont l'interface elle-même empêche de tricher.

Comment elles fonctionnent et pourquoi O(1). Sur un tableau, `push`/`pop` en FIN sont O(1) (on touche le sommet). La Stack s'implémente donc directement sur un tableau. La Queue naïve utilise `push` (enfiler en fin) + `shift` (défiler en tête) — mais `shift` est O(n) car il DÉCALE tous les éléments ! La vraie Queue O(1) garde deux index (tête et queue) ou une liste chaînée, pour ne jamais décaler. Cette nuance est un piège d'entretien fréquent.

La différence avec les concepts proches. Un **tableau** offre l'accès indexé O(1) mais n'impose aucune discipline. Une **Deque** (double-ended queue) autorise les deux bouts — plus souple mais moins « parlante » sur l'intention. Le **Set/Map** vise l'appartenance/l'association, pas l'ordre de traitement. Choisir Stack ou Queue, c'est DÉCLARER la sémantique du problème dans le type — un lecteur comprend immédiatement « ici l'ordre d'imbrication compte » ou « ici l'ordre d'arrivée compte ».

Les applications qui rendent le concept concret. Stack : historique undo/redo, vérification de parenthèses `()[]{}`, évaluation d'expressions, et… la CALL STACK de la récursion (chaque appel empile son contexte, le retour dépile — la récursion EST une pile déguisée). Queue : files de tâches, buffers de messages (mois 10), et le parcours en largeur BFS (jour 34).

Limites et compromis. Une Stack/Queue générique ajoute une indirection (méthodes) sur un simple tableau : négligeable en lisibilité gagnée, mais inutile si le besoin est ponctuel. Piège `shift` O(n) déjà cité. Et sur une Stack, oublier de tester la vacuité avant `pop`/`peek` renvoie `undefined` silencieux — d'où l'intérêt d'un `isEmpty()` explicite.

La règle du jour : **quand un problème parle d'imbrication ou de « le dernier compte d'abord », pense Stack (LIFO) ; quand il parle d'ordre d'arrivée ou de traitement équitable, pense Queue (FIFO). La bonne discipline d'accès transforme la difficulté — et méfie-toi du `shift` O(n) pour une file.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : implémenter `parenthesesValides(str)` avec une Stack — vérifier que `()`, `[]`, `{}` sont correctement imbriqués. C'est l'application canonique de LIFO.

**Exemple simple** : pourquoi une pile ? Dans `([])`, la dernière ouvrante `[` doit se fermer AVANT la première `(`. « Le dernier ouvert se ferme en premier » = LIFO exactement. J'empile chaque ouvrante ; sur une fermante, je vérifie qu'elle correspond au sommet (le dernier ouvert).

**Raisonnement pas-à-pas** : (1) je parcours les caractères ; (2) ouvrante → je l'empile ; (3) fermante → si la pile est vide, il y a une fermante orpheline → invalide ; sinon je dépile et vérifie la correspondance ; (4) à la fin, la pile doit être VIDE (sinon des ouvrantes n'ont jamais été fermées).

**Implémentation** (avec une Stack générique) :
```ts
class Stack<T> {
  private items: T[] = [];
  push(x: T): void { this.items.push(x); }          // O(1)
  pop(): T | undefined { return this.items.pop(); }  // O(1)
  peek(): T | undefined { return this.items[this.items.length - 1]; }
  isEmpty(): boolean { return this.items.length === 0; }
  size(): number { return this.items.length; }
}

function parenthesesValides(str: string): boolean {
  const pile = new Stack<string>();
  const paires: Record<string, string> = { ')': '(', ']': '[', '}': '{' };
  for (const c of str) {
    if (c === '(' || c === '[' || c === '{') {
      pile.push(c);                       // ouvrante : empiler
    } else if (c in paires) {
      if (pile.pop() !== paires[c]) return false;  // fermante : le sommet doit correspondre
    }
  }
  return pile.isEmpty();                   // reste-t-il des ouvrantes non fermées ?
}

console.log(parenthesesValides('([]{})'));  // true
console.log(parenthesesValides('([)]'));    // false : mauvais imbriquement
console.log(parenthesesValides('(('));      // false : ouvrantes en trop
console.log(parenthesesValides('))'));      // false : fermante orpheline
```

**Le piège Queue à connaître** : une file naïve sur `shift()` est O(n) par défilement. Version O(1) à deux index :
```ts
class Queue<T> {
  private items: T[] = [];
  private tete = 0;                          // on n'utilise JAMAIS shift()
  enqueue(x: T): void { this.items.push(x); }        // O(1)
  dequeue(): T | undefined { return this.items[this.tete++]; }  // O(1) amorti
  isEmpty(): boolean { return this.tete >= this.items.length; }
}
```

## ⚠️ Erreurs fréquentes
- Implémenter la Queue avec shift() : O(n) par défilement, quadratique sur gros volume — mentionner la version à deux index.
- Oublier le cas « ouvrantes en trop » : ne pas tester que la pile est vide à la fin déclare `((` valide à tort.
- Oublier le cas « fermante orpheline » : dépiler une pile vide (pop → undefined) sans le traiter.
- Ne pas tester isEmpty avant pop/peek : renvoie undefined silencieusement au lieu de signaler l'erreur.

## 🏢 Cas métier
Stacks et Queues structurent des mécanismes qu'on utilise tous les jours sans les nommer. Stack : la fonction annuler/rétablir de tout éditeur (chaque action empilée, undo = dépiler), l'historique de navigation « précédent » d'un navigateur, l'évaluation des expressions dans un interpréteur, la pile d'exécution qui trace tes erreurs. Queue : les files de messages (RabbitMQ, SQS) qui découplent producteurs et consommateurs, les files de tâches d'un worker asynchrone, l'ordonnancement équitable des requêtes d'un serveur. Choisir la bonne discipline est un acte de conception : un système de tâches qui traiterait le DERNIER arrivé d'abord (Stack au lieu de Queue) affamerait les premières tâches. En entretien, « valide ces parenthèses » ou « implémente une file avec deux piles » testent la maîtrise fine de ces disciplines et de leurs coûts.

## 🎤 Question d'entretien
**« Implémente une fonction qui vérifie qu'une chaîne de parenthèses `()[]{}` est bien équilibrée. »** → C'est l'application canonique d'une pile (LIFO), parce que la règle « la dernière parenthèse ouverte doit se fermer en premier » EST du dernier-entré-premier-sorti. Je parcours la chaîne : chaque ouvrante, je l'empile ; chaque fermante, je dépile et je vérifie que l'ouvrante dépilée correspond bien — sinon la chaîne est invalide (mauvais imbriquement ou fermante orpheline si la pile est vide). À la fin, la pile doit être VIDE ; sinon des ouvrantes n'ont jamais été fermées. C'est O(n) en temps et O(n) en mémoire dans le pire cas (que des ouvrantes). **Relance possible** : « et si je te demande d'implémenter une Queue avec deux Stacks ? » → j'empile les entrées sur une pile « in » ; pour défiler, si la pile « out » est vide je transvide « in » dedans (ce qui inverse l'ordre → FIFO), puis je dépile « out ». Chaque élément est transvidé au plus une fois → O(1) amorti par opération, ce qui montre que je maîtrise le coût réel, pas juste l'API.
