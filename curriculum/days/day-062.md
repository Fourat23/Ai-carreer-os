## 🎯 Objectif du jour
Implémenter les relations (auteurs, emprunts) et la logique métier d'emprunt/retour.

## 📖 Cours approfondi
**Concepts abordés :** JOIN dans l'API · Logique métier · Règles (disponibilité) · Transactions.

La logique MÉTIER est ce qui distingue une vraie API d'un CRUD généré : « on ne peut emprunter qu'un livre disponible » est une RÈGLE, et les règles vivent dans la couche service (pas dans les routes, pas dans la base seule).

L'emprunt est une opération à étapes multiples (vérifier la disponibilité → créer l'emprunt → marquer indisponible) : c'est exactement le cas d'usage des TRANSACTIONS du jour 58. Sans elle, une panne au milieu laisse un livre fantôme. Le conflit métier (déjà emprunté) mérite son statut précis : 409 Conflict — pas 400, pas 500.

Les JOIN entrent dans l'API : GET /livres/42 ramène le livre AVEC son auteur (un JOIN), pas un id opaque que le client devrait résoudre par une seconde requête.

## ✅ Critères de validation
- [ ] Le double emprunt est refusé avec un 409 (testé)
- [ ] L'opération emprunt est transactionnelle (interruption simulée → rien n'est à moitié fait)
- [ ] La règle métier vit dans le service (pas dans la route) — vérifiable en lisant le code

## ⚠️ Erreurs fréquentes
- Emprunter un livre déjà emprunté (règle non vérifiée).
- Pas de transaction (état incohérent si échec).

## 🏢 Cas métier
Cas typique : appeler un LLM (POST + header d'auth + corps JSON + streaming), exposer ton système RAG comme une API (`POST /questions`), ou consommer une API tierce — comprendre HTTP, c'est comprendre comment les systèmes IA se parlent.

## 🎤 Question d'entretien
**« Décris le trajet d'une requête HTTP et le rôle des statuts. »** → DNS → TCP → TLS → HTTP ; requête (méthode + URL + headers + corps) / réponse (statut + corps) ; sans état ; 2xx succès, 4xx faute client, 5xx faute serveur ; idempotence de GET/PUT/DELETE pour les retries.
