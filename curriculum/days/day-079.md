## 🎯 Objectif du jour
Rendre une application observable : logs structurés, métriques, correlation id — indispensable en production.

## 📖 Cours approfondi
**Concepts abordés :** Logs structurés (JSON) · Niveaux de log · Métriques · Traces / correlation id · Que logger, que ne jamais logger.

L'observabilité répond à UNE question : « que s'est-il passé en production ? » — sans elle, tu es aveugle. Trois piliers : les LOGS (des événements horodatés — ce qui s'est passé), les MÉTRIQUES (des agrégats — combien, à quelle vitesse), les TRACES (le parcours d'UNE requête à travers le système).

Les logs STRUCTURÉS (JSON : {timestamp, level, message, requestId, ...}) sont interrogeables mécaniquement, là où le texte libre exige des yeux humains. Les NIVEAUX (debug/info/warn/error) permettent de filtrer. Le CORRELATION ID — un identifiant unique généré à l'entrée de chaque requête et propagé partout — relie tous les logs d'une même requête : c'est lui qui permet de « rejouer » une session.

Ce qu'on ne logge JAMAIS : mots de passe, tokens, données personnelles sensibles. Un log est une base de données que tout le monde lit.

### Exercice principal
Ajoute à LivreAPI : des logs structurés (JSON) avec correlation id par requête, des niveaux (info/warn/error), et un endpoint de métriques simples (compteur de requêtes, latences). Rejoue une session complète depuis les logs.

## 📦 Livrable attendu
LivreAPI observable + preuve qu'on peut rejouer une session depuis les logs.

## ✅ Critères de validation
- [ ] Logs JSON structurés avec niveaux et correlation id sur chaque requête
- [ ] Une session complète reconstituée à partir des seuls logs (preuve)
- [ ] Relecture : aucun secret ni donnée sensible dans les logs

## ⚠️ Erreurs fréquentes
- Logs en texte non structuré (ingrep-able).
- Logger des secrets/mots de passe/tokens.
