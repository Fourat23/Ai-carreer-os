C'est le jalon qui atteste que DocSense a une culture de qualité opérationnelle, pas juste un moteur qui répond.

Ce que ce jalon démontre :
1. **L'évaluation en une commande** : `docsense eval` (jour 317) produit le rapport complet sur le golden set. La qualité de DocSense est mesurable à tout moment, par quiconque.
2. **Le dashboard opérationnel** : les scores s'affichent en tendance (jour 318), racontant l'état de qualité. La baseline v0 (jour 319) y figure comme référence.
3. **Docker up sur machine propre** : `docker compose up` (jour 320) fait tourner tout DocSense depuis un clone frais. La reproductibilité est prouvée, pas supposée.
4. **La revue d'architecture hebdomadaire** : l'architecture tient-elle après l'ajout de toute l'infrastructure d'évaluation ? Le cœur est-il resté pur (hexagonal), l'évaluation branchée par les ports sans le contaminer ?

Pourquoi ce jalon est un tournant : à la fin de la semaine 46, DocSense n'est plus seulement fonctionnel — il est MESURABLE (on connaît sa qualité chiffrée), REPRODUCTIBLE (il tourne partout en une commande), et SUIVI (le dashboard montre la tendance). C'est le socle qui rend les 6 dernières semaines d'amélioration PILOTABLES : chaque changement se mesurera contre la baseline, se visualisera sur le dashboard, se démontrera sur machine propre. Un projet qui atteint ce niveau d'infrastructure de qualité à mi-parcours est un projet qui finira solide. C'est aussi un signal fort en entretien : « mon projet s'évalue en une commande, se lance en une commande, et j'ai un dashboard qui montre sa qualité progresser » démontre une maturité d'ingénierie que peu de projets de portfolio atteignent.

**Exploiter un service orchestré (fondation V23).** Déclarer un Deployment ne suffit pas : il faut le rendre OBSERVABLE et RÉSILIENT. Trois sondes le pilotent. La **readiness probe** répond « prêt à recevoir du trafic ? » — tant qu'elle est rouge, le Service ne route PAS vers le pod (indispensable au démarrage, cache froid, dépendance non prête). La **liveness probe** répond « encore vivant ? » — si elle échoue, le conteneur est redémarré. La **startup probe** protège les démarrages lents en désactivant les deux autres le temps du boot. Erreur fréquente : une liveness trop agressive (`initialDelaySeconds` trop court) qui tue le conteneur avant qu'il ait démarré → **CrashLoopBackOff** dû à la sonde, pas à l'application. Les **requests** réservent des ressources (l'ordonnanceur en a besoin pour placer) ; les **limits** plafonnent (sans limite mémoire, une fuite fait tomber le voisinage). Une limite mémoire dépassée provoque un **OOMKilled**.

**Livrer et revenir en arrière.** Un Deployment se met à jour par **rolling update** (stratégie **RollingUpdate**) : les pods sont remplacés progressivement, sans coupure, réglé par `maxUnavailable`/`maxSurge` — mais deux versions coexistent un temps, donc la nouvelle doit rester compatible avec l'ancienne. La stratégie **Recreate** arrête tout puis redémarre (coupure) ; on l'évite sauf incompatibilité. Un **rollout** qui bloque (nouveaux pods jamais prêts) se **rollback** vers la révision précédente d'une commande — à condition que le retour soit possible (une migration de schéma non rétrocompatible peut l'empêcher : il faut alors **roll-forward**).

**Les états d'un pod à savoir lire.** **Pending** (pas encore planifié : ressources insuffisantes, PVC non lié) ; **Running** (en cours) ; **Failed**/**Succeeded** (Jobs). Les incidents caractéristiques : **CrashLoopBackOff** (le conteneur démarre puis meurt en boucle — bug de démarrage, mauvaise config, liveness trop stricte) ; **ImagePullBackOff** (image introuvable : mauvais nom/tag ou accès registre) ; **OOMKilled** (mémoire dépassée) ; **Evicted** (le nœud manque de ressources). Diagnostiquer, c'est LIRE ces états et les **événements**/**logs**, pas modifier au hasard.

### Que faire dans ce cas ? (méthode d'intervention)

Une méthode professionnelle, réutilisable, pour tout incident de déploiement — **pas une recette magique, une démarche** :

1. **Symptômes observés** : lire l'état réel (états de pods, événements, logs, métriques). Décrire les faits, pas les hypothèses.
2. **Risque immédiat** : qui/quoi est impacté maintenant (blast radius) ? production ou pré-prod ?
3. **Ce qu'il ne faut PAS faire** : redéployer à l'aveugle, supprimer des ressources sans comprendre, modifier plusieurs choses à la fois, désactiver les probes « pour que ça passe ».
4. **Vérifications initiales** : état des pods, du Service (a-t-il des endpoints ?), de l'image, des ressources, des dépendances.
5. **Hypothèses classées** de la plus probable à la moins probable, avec un test pour chacune.
6. **Données à collecter** : `describe` du pod, événements, logs du conteneur, métriques mémoire/CPU — de quoi trancher entre les hypothèses.
7. **Décision** : continuer, interrompre, **rollback** (retour à la version stable, si réversible), **roll-forward** (correctif en avant, si le retour est impossible), **hotfix** (correctif urgent), **désactivation par feature flag**, ou **mitigation** (réduire l'impact sans régler la cause).
8. **Validation après correctif** : readiness verte, endpoints présents, erreurs retombées, smoke test — la preuve, pas la foi.
9. **Communication** : un message d'incident court et honnête (impact, action, prochaine étape).
10. **Documentation et prévention** : **runbook** (la procédure rejouable), **post-mortem sans blâme** (cause racine, facteurs contributifs), **action corrective** (règle le problème) et **action préventive** (empêche la récurrence : test de non-régression, alerte, garde-fou).

**Cas types à savoir traiter** : Pod en **CrashLoopBackOff** ; **OOMKilled** (augmenter la limite ou corriger la fuite) ; **Service inaccessible** (selector orphelin → aligner labels) ; **rollout bloqué** (readiness/image → rollback) ; **régression** après nouvelle image ; migration qui **empêche le rollback** (→ roll-forward) ; **secret exposé** (rotation + coffre) ; **probe mal configurée** ; **mauvaise image** ; montée de charge (HPA/replicas).

**Terminologie de reprise (précise).** **bugfix** = correction normale d'un défaut ; **hotfix** = correction urgente en production ; **patch** = livraison corrective limitée ; **rollback** = retour à la version précédente ; **roll-forward** = correction vers une nouvelle version ; **mitigation** = réduire l'impact sans supprimer la cause ; **workaround** = contournement temporaire ; **emergency change** = changement d'urgence encadré ; **post-mortem** = analyse a posteriori sans blâme ; **action corrective** vs **action préventive**. Ces mots ne sont pas interchangeables : la clarté du vocabulaire est la clarté de la décision.

**Persistance, mise à l'échelle, permissions (introduction).** Un **volume** attache du stockage à un pod ; un **PersistentVolumeClaim (PVC)** demande un stockage durable (un StatefulSet en réclame un par instance). Le **Horizontal Pod Autoscaler (HPA)** ajuste le nombre de replicas selon une métrique — au niveau conceptuel ici. Le **RBAC** (avec **ServiceAccount**, **Role**, **RoleBinding**) applique le moindre privilège aux identités du cluster. Rappel d'honnêteté : rien de tout cela n'est un vrai cluster ici — le Manifest Lab **analyse et simule** de façon déterministe, sans jamais déployer.

## ⚠️ Erreurs fréquentes
- Démontrer sur sa propre machine configurée : le test qui compte est sur machine PROPRE (clone + up).
- Infrastructure de qualité incomplète (dashboard sans baseline, éval non reproductible) : elle ne pilotera pas les améliorations — la compléter avant d'avancer.
- Sauter la revue d'architecture : l'ajout de l'infrastructure d'évaluation peut avoir contaminé le cœur — vérifier.
- Une infrastructure lente/pénible : si évaluer ou lancer prend trop de friction, elle ne sera pas utilisée — la rendre fluide.
