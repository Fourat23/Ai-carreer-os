## 🎯 Objectif du jour
La fonctionnalité différenciante.

## 📖 Cours approfondi
**Modèle mental : le workflow d'analyse est la fonctionnalité DIFFÉRENCIANTE de DocSense — au-delà de répondre à des questions (ce que fait tout RAG), il ANALYSE un document (résumé structuré, points clés, questions ouvertes), et c'est un WORKFLOW explicite, pas un agent.** Après l'infrastructure de qualité, tu construis ce qui distingue DocSense d'un simple chatbot documentaire : une capacité d'analyse. Et le choix d'architecture est délibéré — un workflow explicite (jour 281), pas un agent, parce que le flux d'analyse est FIXE (les étapes sont connues), donc prévisible, testable et économe.

Pourquoi un workflow et pas un agent (la doctrine du jour 278 appliquée) :
1. **Le flux est fixe** : analyser un document = résumer → extraire les points clés → identifier les questions ouvertes. Ces étapes sont connues d'avance, dans un ordre fixe. Pas besoin de l'autonomie coûteuse d'un agent (qui déciderait du flux) — un workflow qui orchestre ces étapes suffit.
2. **Les patterns de workflow** (jour 282) : l'analyse combine du chaînage (les étapes séquentielles) et potentiellement de la parallélisation (analyser plusieurs aspects en même temps). Le LLM fait le travail cognitif de chaque étape ; ton code orchestre.
3. **Les bénéfices** : coût borné (nombre d'appels connu), prévisible, testable étape par étape (jour 327), pas de modes d'échec d'agent (boucle, dérive). Exactement ce qu'on veut pour une fonctionnalité de production.

Ce que l'analyse produit (le livrable de valeur) : pour un document donné, un résumé structuré (pas un pavé, une structure claire), les points clés extraits, et les questions ouvertes (ce que le document soulève mais ne résout pas). C'est une fonctionnalité à VALEUR AJOUTÉE réelle — elle fait un travail qu'un humain ferait lentement, sur un document que personne n'a le temps de lire en entier.

Pourquoi c'est différenciant : un RAG qui répond à des questions est devenu banal ; un DocSense qui ANALYSE des documents (résume, extrait, questionne) apporte une valeur supplémentaire visible. En construisant cette analyse comme un workflow explicite (et en sachant expliquer POURQUOI workflow et pas agent), tu démontres à la fois une fonctionnalité de valeur et un jugement d'architecture — le combo qui distingue un projet de portfolio mémorable.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : le workflow d'analyse de DocSense — résumé structuré, points clés, questions ouvertes d'un document.

**Exemple simple** : le workflow en une chaîne — `analyse = {resume: resumer(doc), points_cles: extraire_points(doc), questions: identifier_ouvertes(doc)}`. Trois étapes fixes, un appel LLM chacune, orchestrées par ton code.

**Raisonnement pas-à-pas** : décomposer l'analyse en étapes fixes (workflow, pas agent), orchestrer, structurer la sortie.

**Implémentation** :
```python
def analyser_document(doc: str) -> Analyse:
    # Workflow EXPLICITE : étapes fixes, flux connu (pas d'agent — j.278)
    resume = llm_call(PROMPT_RESUME_STRUCTURE, doc, temp=0)      # étape 1
    points_cles = llm_call(PROMPT_POINTS_CLES, doc, temp=0)      # étape 2
    questions = llm_call(PROMPT_QUESTIONS_OUVERTES, doc, temp=0) # étape 3
    return Analyse(resume=resume, points_cles=points_cles, questions=questions)
# Nombre d'appels CONNU (3) → coût et latence bornés et estimables
# Testable étape par étape (j.327) ; pas de boucle/dérive possible (pas d'agent)
```

**Mini-quiz** : (a) Pourquoi un workflow et pas un agent pour l'analyse ? (b) Qu'est-ce qui rend l'analyse différenciante ? (c) Quels bénéfices le workflow apporte-t-il vs l'agent ?
→ (a) le flux est FIXE (résumé → points clés → questions), pas besoin de l'autonomie coûteuse d'un agent ; (b) elle apporte une valeur au-delà de répondre — elle fait un travail (résumer, extraire) qu'un humain ferait lentement ; (c) coût borné, prévisible, testable étape par étape, pas de modes d'échec d'agent.

**Variante** : demande-toi si UNE étape de l'analyse mériterait de l'autonomie (ex. « creuser un point clé jusqu'à épuisement ») — presque toujours non ; le flux fixe suffit, et c'est la démonstration que tu sais choisir workflow vs agent à bon escient.

## ⚠️ Erreurs fréquentes
- Construire l'analyse comme un agent : le flux est fixe, l'autonomie d'un agent serait coûteuse et fragile pour rien — un workflow suffit.
- Un résumé en pavé non structuré : la valeur est dans la STRUCTURE (résumé + points clés + questions), pas dans un bloc de texte.
- Ne pas savoir justifier workflow vs agent : le jugement d'architecture est aussi important que la fonctionnalité — savoir dire pourquoi workflow.
- Flux non testable : structurer en étapes permet de tester chacune (jour 327) — un mégaprompt monolithique perd cet avantage.

## 🏢 Cas métier
L'analyse de documents (résumé, extraction de points clés, identification de questions) est une fonctionnalité à forte valeur en entreprise : personne n'a le temps de lire tous les documents en entier, et un outil qui les analyse fiablement fait gagner un temps considérable. Construire cette analyse comme un workflow explicite (plutôt qu'un agent) est le bon choix d'ingénierie — flux fixe, coût borné, testable — et démontre le jugement du jour 278. Pour DocSense, c'est la fonctionnalité qui le fait passer de « RAG qui répond » (banal) à « assistant qui analyse » (différenciant), tout en prouvant que tu sais choisir l'architecture adaptée. « Ma fonctionnalité d'analyse est un workflow, pas un agent, parce que le flux est fixe » est exactement le type de décision justifiée qu'un lead valorise.
