## 🎯 Objectif du jour
Garantir l'atomicité.

## 📖 Cours approfondi
**Modèle mental : une transaction rend un GROUPE d'opérations ATOMIQUE — soit TOUT réussit et est validé (`COMMIT`), soit une erreur annule TOUT (`ROLLBACK`) et la base revient à son état d'avant. ACID garantit qu'une panne au milieu ne laisse JAMAIS la base dans un état incohérent — comme un stock décrémenté sans commande créée.** Certaines opérations métier n'ont de sens qu'ENSEMBLE : débiter un compte ET créditer un autre, créer une commande ET décrémenter le stock. Si la première réussit et la seconde échoue (panne, erreur), un état partiel corrompt les données. La transaction interdit cet entre-deux.

ACID — les quatre garanties (le POURQUOI) :
- **A — Atomicité** : tout ou rien. Les opérations d'une transaction forment un bloc indivisible ; un échec au milieu annule tout ce qui précède.
- **C — Cohérence** : la transaction fait passer la base d'un état valide à un autre état valide (les contraintes — clés étrangères, CHECK — restent respectées).
- **I — Isolation** : deux transactions concurrentes ne se marchent pas dessus ; chacune voit une base cohérente, comme si elles s'exécutaient l'une après l'autre.
- **D — Durabilité** : une fois `COMMIT`, les données survivent même à une coupure de courant.

Le mécanisme : `BEGIN` ouvre la transaction, on exécute les opérations, `COMMIT` valide TOUT d'un coup, `ROLLBACK` annule TOUT en cas d'erreur. En pratique, on englobe les opérations dans un `try` : succès → commit, exception → rollback. C'est l'atomicité du CRUD front (jour 114 « l'UI ne ment pas ») portée au niveau des données : la base ne reste jamais à moitié modifiée.

Quand une transaction est NÉCESSAIRE : dès que PLUSIEURS écritures doivent réussir ou échouer ENSEMBLE pour que les données restent cohérentes (transfert, commande+stock, écritures liées d'un pipeline). Quand elle est superflue : une seule écriture indépendante est déjà atomique en elle-même.

L'isolation, en bref : plusieurs niveaux existent (des lectures plus ou moins strictes) ; l'essentiel à retenir est que sans isolation, des transactions concurrentes peuvent lire des états intermédiaires et produire des incohérences (double dépense, survente). Le niveau se choisit selon le compromis cohérence/performance.

La règle du jour : **englobe dans une transaction toute suite d'écritures qui doivent réussir ou échouer ENSEMBLE ; commit sur succès, rollback sur erreur ; ACID garantit qu'aucune panne ne laisse la base à moitié modifiée**. Une transaction, c'est la promesse « tout ou rien » qui protège l'intégrité des données.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire une transaction (commande + décrément de stock) et PROUVER le rollback en cas d'échec.

**Exemple simple** : la structure tout-ou-rien — `BEGIN; ...opérations...; COMMIT;` et `ROLLBACK` si une opération échoue. Les deux écritures (commande, stock) vivent dans le même bloc : impossible d'en valider une sans l'autre.

**Raisonnement pas-à-pas** : ouvrir la transaction → exécuter les écritures liées → si toutes réussissent, commit → si l'une échoue (stock insuffisant), rollback → vérifier que la base est intacte.

**Implémentation** :
```python
import sqlite3
con = sqlite3.connect("boutique.db")
try:
    con.execute("BEGIN")                                    # début de transaction
    con.execute("INSERT INTO commandes(produit_id, qte) VALUES (?, ?)", (42, 3))
    cur = con.execute("UPDATE produits SET stock = stock - 3 "
                      "WHERE id = 42 AND stock >= 3")        # échoue si stock insuffisant
    if cur.rowcount == 0:
        raise ValueError("Stock insuffisant")                # déclenche le rollback
    con.commit()                                             # TOUT validé d'un coup
except Exception as e:
    con.rollback()                                           # TOUT annulé : base intacte
    print(f"Transaction annulée : {e}")
```
Preuve du rollback : après un échec de stock, ni la commande n'est créée, ni le stock n'est décrémenté — la base est exactement comme avant. Sans transaction, la commande aurait été insérée puis l'échec du stock aurait laissé un état incohérent (commande fantôme).

**Mini-quiz** : (a) Que garantit l'atomicité ? (b) Pourquoi cette opération a-t-elle besoin d'une transaction ? (c) Que se passe-t-il sur `ROLLBACK` ?
→ (a) tout ou rien : un échec au milieu annule tout ce qui précède ; (b) commande et décrément de stock doivent réussir ou échouer ENSEMBLE, sinon état incohérent (stock décrémenté sans commande, ou l'inverse) ; (c) toutes les opérations depuis `BEGIN` sont annulées, la base revient à son état d'avant.

**Variante** : provoque volontairement une erreur APRÈS l'INSERT mais AVANT le COMMIT (ex. une contrainte violée) et vérifie qu'AUCUNE des deux écritures ne subsiste — c'est la démonstration concrète de l'atomicité.

## 🏢 Cas métier
Les transactions sont indispensables dès qu'une opération métier touche plusieurs écritures liées : transfert bancaire (débit + crédit), commande e-commerce (commande + stock + paiement), écritures groupées d'un pipeline. Sans transaction, une panne au mauvais moment laisse un état incohérent — de l'argent débité sans être crédité, un stock décrémenté sans vente — qui exige une réconciliation manuelle coûteuse et mine la confiance. ACID est précisément ce qui permet aux systèmes financiers et transactionnels d'être fiables malgré les pannes. Savoir identifier quand une transaction est nécessaire, l'implémenter avec commit/rollback, et prouver l'atomicité est une compétence de fiabilité de données essentielle — et directement pertinente pour le chargement transactionnel de DataPulse (jour 144).

## 🎤 Question d'entretien
**« Qu'est-ce qu'une transaction et que garantit ACID ? »** → Une transaction rend un groupe d'opérations ATOMIQUE : soit tout réussit et est validé (`COMMIT`), soit une erreur annule tout (`ROLLBACK`) et la base revient à son état d'avant. C'est nécessaire dès que plusieurs écritures doivent réussir ou échouer ENSEMBLE — une commande et son décrément de stock, un débit et un crédit — sinon une panne au milieu laisse un état incohérent. ACID : Atomicité (tout ou rien), Cohérence (on passe d'un état valide à un autre, contraintes respectées), Isolation (les transactions concurrentes ne se corrompent pas), Durabilité (après commit, ça survit à une panne). En pratique, j'englobe les écritures dans un `try` : succès → commit, exception → rollback. La garantie clé : la base n'est jamais laissée à moitié modifiée.
