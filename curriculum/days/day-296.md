## 🎯 Objectif du jour
Protéger les données.

## 📖 Cours approfondi
**Modèle mental : une politique de données répond à quatre questions simples mais cruciales — qu'est-ce qui ENTRE, où ça TRANSITE, ce qui PART vers l'extérieur, et combien de temps on le GARDE — et pour une app IA, la troisième question (les APIs LLM externes) est la plus sensible.** Après l'audit sécurité (jour 295), tu formalises la gouvernance des données de DocSense. Ce n'est pas de la paperasse : c'est ce qui détermine si ton app est déployable dans un contexte réel (entreprise, RGPD, données clients) — et c'est une question que tout recruteur produit-IA posera.

Les quatre questions de la politique de données :
1. **Ce qui ENTRE** : quelles données l'utilisateur fournit (documents, questions), leur nature (publiques ? personnelles ? confidentielles ?), et leur classification. Une donnée personnelle (RGPD) ou un secret d'entreprise n'a pas le même traitement qu'un document public.
2. **Où ça TRANSITE et est STOCKÉ** : le chemin des données dans ton système (upload → stockage → index → contexte LLM), où elles reposent (chiffrées ? où ?), qui y a accès. Le moindre privilège du jour 295 appliqué au stockage.
3. **Ce qui PART vers l'extérieur — LA question IA critique** : quand tu appelles une API LLM (OpenAI, Anthropic), tu ENVOIES le contexte (question + extraits de documents) à un tiers. Que deviennent ces données ? Sont-elles utilisées pour l'entraînement ? Conservées ? C'est LE point que les entreprises redoutent : envoyer leurs documents confidentiels à un LLM externe. Les parades : lire les conditions du fournisseur (certains offrent le no-training et la non-rétention), anonymiser/masquer les données sensibles avant l'envoi, ou héberger un modèle en local pour les données ultra-sensibles.
4. **La RÉTENTION** : combien de temps garde-t-on chaque type de donnée, et comment on la supprime (le droit à l'effacement du RGPD). Une politique de rétention explicite (les logs 30 jours, les documents jusqu'à suppression par l'utilisateur, etc.) est une exigence légale et de confiance.

Pourquoi c'est déterminant : une app IA qui envoie des données clients à un LLM externe sans politique claire est INDÉPLOYABLE en entreprise (risque juridique, perte de confiance). Savoir tracer le chemin des données, identifier ce qui part vers l'extérieur, et définir une politique de rétention est ce qui rend une app IA acceptable par un DPO, un RSSI, un client. C'est une compétence de gouvernance qui vaut autant que la technique — et qui manque cruellement à la plupart des développeurs IA.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : la politique de données de DocSense (entrée, transit, sortie externe, rétention).

**Exemple simple** : la question qui révèle le risque IA — « quand j'appelle l'API LLM, quelles données de l'utilisateur j'envoie à un tiers ? ». La réponse (question + extraits de documents) est exactement ce qu'une entreprise veut contrôler.

**Raisonnement pas-à-pas** : tracer le chemin des données, classifier, identifier le point de sortie externe (l'API LLM), définir la rétention.

**La politique (livrable)** :
```
# Politique de données DocSense
## 1. Ce qui ENTRE
  - documents utilisateur (classification : peuvent être confidentiels)
  - questions (peuvent contenir des données personnelles)
## 2. Transit & stockage
  - upload → stockage chiffré → index vectoriel → contexte LLM
  - accès : moindre privilège (un utilisateur ne voit que SES documents)
## 3. Ce qui PART vers l'extérieur (LE point sensible)
  - appel API LLM : on envoie question + extraits à [fournisseur]
  - garanties : conditions no-training + non-rétention vérifiées ? OUI/NON
  - parade données sensibles : masquage avant envoi OU modèle local
## 4. Rétention
  - documents : jusqu'à suppression par l'utilisateur (droit à l'effacement)
  - logs : 30 jours (avec données personnelles masquées)
  - index : reconstruit, pas de données brutes résiduelles
```

**Mini-quiz** : (a) Quelle est la question de données la plus sensible pour une app IA ? (b) Que peut-on faire des données sensibles avant de les envoyer à un LLM externe ? (c) Pourquoi une politique de rétention est-elle nécessaire ?
→ (a) ce qui PART vers l'extérieur (les données envoyées aux APIs LLM tierces) ; (b) les masquer/anonymiser, ou utiliser un modèle local pour l'ultra-sensible ; (c) exigence légale (droit à l'effacement RGPD) et de confiance.

**Variante** : identifie dans DocSense un type de donnée qui NE devrait PAS partir vers un LLM externe (un document marqué confidentiel) et conçois le traitement (masquage, ou refus d'ingestion vers l'API externe) — c'est le cas concret qui rend la politique opérationnelle.

## 🏢 Cas métier
« Est-ce que nos documents partent chez OpenAI ? » est LA question qui bloque (ou débloque) l'adoption d'une app IA en entreprise — un DPO ou un RSSI refusera le déploiement tant que le chemin des données et les garanties du fournisseur ne sont pas clairs. Les startups IA qui réussissent en B2B ont toutes une politique de données explicite (no-training vérifié, masquage des données sensibles, option de modèle local pour les clients régulés). Un ingénieur qui pense « quand j'appelle le LLM, j'envoie ces données à un tiers, voici comment je les protège » est immédiatement plus déployable — cette conscience de gouvernance des données manque à la plupart des développeurs IA et fait la différence sur le marché.

## 🎤 Question d'entretien
**« Quelles données de tes utilisateurs partent vers des services externes, et comment les protèges-tu ? »** → C'est LA question de gouvernance d'une app IA : quand j'appelle une API LLM, j'envoie le contexte (question + extraits de documents) à un tiers. Ma politique répond à quatre questions : ce qui entre (classification des données), où ça transite (stockage chiffré, moindre privilège d'accès), ce qui PART vers l'extérieur (les garanties du fournisseur — no-training, non-rétention — vérifiées ; masquage des données sensibles avant envoi ; modèle local pour l'ultra-sensible), et la rétention (droit à l'effacement RGPD, logs limités). Une app qui envoie des données clients sans politique claire est indéployable en entreprise.
