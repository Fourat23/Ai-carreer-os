## 🎯 Objectif du jour
Nommer et appliquer 5 patterns concrets et reconnaître qu'ils formalisent tes réflexes.

## 📖 Cours approfondi
**Concepts abordés :** Factory · Strategy · Adapter · Observer · Singleton · Sur-ingénierie.

Un design pattern est une solution NOMMÉE à un problème récurrent — un vocabulaire partagé entre ingénieurs. Strategy : injecter un comportement interchangeable (tes callbacks du jour 22 en sont). Factory : centraliser la création d'objets (créer le bon Notifieur selon une config). Adapter : uniformiser deux interfaces incompatibles (ton module api.ts). Observer : notifier des abonnés d'un changement (les événements du DOM). Singleton : une instance unique (la connexion DB — mais attention, c'est un état global déguisé).

Le piège : appliquer un pattern sans avoir le problème correspondant. La sur-ingénierie EST un anti-pattern. Le bon usage : reconnaître le problème quand il arrive, et nommer la solution qu'on a souvent déjà réinventée.

**Modèle mental : un design pattern est un NOM donné à une solution que tu réinventes déjà. Ce n'est ni une bibliothèque à importer ni une obligation : c'est un VOCABULAIRE partagé qui permet à deux ingénieurs de dire « ici, une Strategy » et de se comprendre instantanément. La compétence n'est pas de mémoriser 23 patterns, mais de RECONNAÎTRE le problème récurrent et de nommer la solution — et de résister à la tentation de les appliquer sans le problème correspondant.** Un pattern appliqué sans besoin est de la sur-ingénierie, un anti-pattern.

Pourquoi les patterns existent. Dans les années 90, des ingénieurs ont remarqué que les mêmes solutions revenaient d'un projet à l'autre pour les mêmes problèmes de conception. Les nommer et les cataloguer a créé un langage commun : au lieu de décrire « une classe qui décide quelle sous-classe instancier selon une config », on dit « une Factory ». Le pattern capture aussi le CONTEXTE (quand l'utiliser) et les CONSÉQUENCES (ses compromis), pas seulement le code.

Les cinq patterns du jour, depuis leur problème. **Strategy** : injecter un comportement interchangeable — tes callbacks d'ordre supérieur (jour 22) EN SONT ; on passe la « stratégie » de calcul (tarif, tri) en paramètre pour la changer sans toucher l'appelant. **Factory** : centraliser la création d'objets quand le choix du type dépend d'une donnée (créer le bon `Notifieur` selon une config) — l'appelant demande un produit sans connaître la classe concrète. **Adapter** : uniformiser deux interfaces incompatibles (envelopper deux API tierces derrière une interface commune, ton module `api.ts`). **Observer** : notifier des abonnés d'un changement (les écouteurs d'événements du DOM sont des observers). **Singleton** : garantir une instance unique (une connexion DB) — mais c'est un ÉTAT GLOBAL déguisé, à limiter car il complique les tests et couple tout à cette instance.

La différence à saisir : pattern vs réflexe nommé. Tu utilises déjà Strategy quand tu passes une fonction de comparaison à un tri, Factory quand une fonction décide quel objet créer, Observer quand tu ajoutes un `addEventListener`. Les patterns ne t'apprennent pas à coder autrement : ils METTENT UN NOM sur ce que tu fais, ce qui rend le code plus lisible (l'intention est déclarée) et les discussions plus rapides.

Le piège central : la sur-ingénierie. Le plus difficile n'est pas d'appliquer un pattern, c'est de SAVOIR NE PAS l'appliquer. Introduire une Factory abstraite pour deux cas triviaux, un Observer là où un appel direct suffit, un Singleton par confort d'accès global : chaque pattern non justifié ajoute de la complexité sans bénéfice. La règle : le pattern doit RÉSOUDRE un problème que tu as réellement, pas anticiper un problème hypothétique.

Limites et compromis. Les patterns sont issus de langages orientés objet classiques ; en JS/TS, certains sont natifs (les fonctions de première classe rendent Strategy trivial) ou moins nécessaires. Sur-utiliser les patterns rend le code « astronaute » (abstrait sans raison). Le bon usage : reconnaître, nommer, appliquer avec parcimonie.

La règle du jour : **un pattern est un nom pour une solution récurrente, un outil de communication — reconnais le problème AVANT de nommer la solution, applique avec parcimonie, et rappelle-toi que le vrai savoir-faire est aussi de savoir NE PAS appliquer un pattern (la sur-ingénierie est un anti-pattern).**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : illustrer le pattern Strategy EN CONTEXTE de ton propre code (le calcul de tarif du jour 5), puis nommer le problème qu'il résout.

**Exemple simple** : sans Strategy, une fonction `prix` truffée de `if typeClient === 'vip' … else if 'pro' …` doit être MODIFIÉE à chaque nouveau type de client. Avec Strategy, on INJECTE la règle de calcul : ajouter un type = passer une nouvelle fonction, sans toucher l'appelant.

**Raisonnement pas-à-pas** : (1) j'identifie ce qui VARIE (la règle de calcul du prix) ; (2) je l'extrais derrière un contrat (une fonction `(base) => number`) ; (3) l'appelant reçoit la stratégie en paramètre ; (4) ajouter une stratégie ne modifie plus l'appelant — c'est Strategy, et c'est exactement l'open/closed du jour 38.

**Implémentation** :
```ts
// Le comportement qui VARIE, extrait derrière un contrat
type Tarif = (base: number) => number;

const tarifs: Record<string, Tarif> = {
  standard: base => base,
  vip:      base => base * 0.8,      // -20 %
  pro:      base => base * 0.9,      // -10 %
};

// L'appelant ne connaît que le CONTRAT Tarif : il ne change jamais
function prixFinal(base: number, strategie: Tarif): number {
  return Math.round(strategie(base) * 100) / 100;
}

console.log(prixFinal(100, tarifs.vip));   // 80
console.log(prixFinal(100, tarifs.pro));   // 90

// Ajouter 'partenaire' = une entrée de plus, prixFinal N'EST PAS touchée (open/closed)
tarifs.partenaire = base => base * 0.7;
console.log(prixFinal(100, tarifs.partenaire));  // 70
```
Le même code montre que Strategy n'est que le nom de « injecter un comportement » — que tu faisais déjà avec les fonctions d'ordre supérieur (jour 22).

**Une Factory, en une image** :
```ts
interface Notifieur { envoyer(m: string): void; }
function creerNotifieur(type: 'email' | 'sms'): Notifieur {
  // l'appelant demande un produit sans connaître la classe concrète
  return type === 'email' ? new Email() : new SMS();
}
```

## 🏢 Cas métier
Les design patterns structurent le code d'entreprise et, surtout, les CONVERSATIONS entre développeurs. En revue de code, « remplace ce switch par une Strategy » ou « ce couplage appelle un Adapter » transmet une intention complète en trois mots — c'est un gain de communication réel dans une équipe. Concrètement : les frameworks eux-mêmes sont bâtis sur des patterns (les middlewares Express sont une Chain of Responsibility, les hooks React relèvent de l'Observer, un ORM cache un Factory/Repository). Savoir les reconnaître aide à comprendre les bibliothèques qu'on utilise. Mais la maturité se voit surtout dans la RETENUE : un candidat qui plaque une AbstractFactory sur un problème trivial inquiète autant qu'un candidat qui ne connaît aucun pattern. Les recruteurs valorisent celui qui reconnaît le problème, nomme la bonne solution, et sait dire « ici, pas besoin de pattern ».

## 🎤 Question d'entretien
**« Cite un design pattern que tu as déjà utilisé sans le savoir, et explique le problème qu'il résout. »** → La Strategy. Dès qu'on passe une fonction de comparaison à un tri, ou une règle de calcul de tarif en paramètre, on fait du Strategy : on INJECTE le comportement qui varie derrière un contrat, au lieu de le coder en dur dans une cascade de `if`. Le problème résolu : faire évoluer ce comportement sans modifier l'appelant — ajouter un type de tarif devient « une fonction de plus », l'appelant reste intact. C'est exactement le principe ouvert/fermé. Un pattern n'est pas une bibliothèque, c'est un NOM sur une solution récurrente : ça rend le code lisible (l'intention est déclarée) et les discussions d'équipe rapides. Je connais aussi Factory (créer le bon objet selon une config), Adapter (uniformiser deux API incompatibles), Observer (les écouteurs d'événements), Singleton (instance unique, mais état global déguisé à limiter). **Relance possible** : « quand NE faut-il PAS utiliser de pattern ? » → quand le problème correspondant n'existe pas : plaquer une Factory abstraite sur deux cas triviaux ajoute de la complexité sans bénéfice — la sur-ingénierie est elle-même un anti-pattern.
