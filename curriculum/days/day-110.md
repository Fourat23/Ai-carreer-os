## 🎯 Objectif du jour
Extraire la logique réutilisable.

## 📖 Cours approfondi
**Modèle mental : un hook personnalisé extrait une LOGIQUE À ÉTAT réutilisable (pas du JSX) — c'est la fonction réutilisable du clean code appliquée à la logique stateful de React.** Quand plusieurs composants répètent la même mécanique — charger des données avec les 3 états, lire/écrire dans le localStorage, gérer un formulaire — cette logique n'a pas sa place dupliquée dans chacun. Un hook custom (une fonction dont le nom commence par `use`) l'encapsule une fois, et chaque composant l'APPELLE. Le composant se recentre sur le rendu ; la logique vit dans le hook, testable et partagée.

Ce qu'un hook custom est et n'est pas :
1. **C'est une fonction qui appelle d'autres hooks** (`useState`, `useEffect`) et renvoie ce dont le composant a besoin (des valeurs, des fonctions). `useFetch(url)` renvoie `{ data, erreur, chargement }` ; `useLocalStorage(cle, defaut)` renvoie `[valeur, setValeur]`.
2. **Ce n'est PAS du partage de state** : deux composants qui appellent `useFetch` ont chacun leur PROPRE état — le hook partage la LOGIQUE, pas les données. (Pour partager des données, c'est Context, jour 101.)
3. **Il obéit aux règles des hooks** : appelé au niveau racine du composant/hook (jamais dans une condition ou une boucle), et son nom commence par `use` pour que React et l'outillage le reconnaissent.

Le bénéfice en cascade : un hook custom bien fait rend les composants MAIGRES (jour 109 : logique hors du rendu), TESTABLES (on teste le hook isolément, la logique n'est plus enfouie dans le JSX), et COHÉRENTS (tous les fetchs de l'app passent par le même `useFetch`, donc gèrent les 3 états de la même façon). C'est la même valeur qu'une bonne fonction utilitaire : écrite une fois, correcte partout.

La règle du jour : **extrais en hook custom une logique à état DÈS qu'elle se répète ou qu'elle alourdit un composant — nomme-le `useX`, fais-lui renvoyer une interface claire, et teste-le isolément**. Attention au sur-abstraction inverse : n'extrais pas un hook pour une logique utilisée à un seul endroit et triviale ; comme toute abstraction, un hook se justifie par la réutilisation ou la clarté gagnée, pas par principe.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : créer deux hooks custom typés et testés — `useFetch` et `useLocalStorage`.

**Exemple simple** : l'interface d'un hook AVANT son corps — `function useFetch<T>(url: string): { data?: T; erreur?: string; chargement: boolean }`. Décider ce que le hook RENVOIE (son contrat) avant de l'implémenter guide tout le reste.

**Raisonnement pas-à-pas** : identifier la logique répétée → l'extraire dans une fonction `useX` qui appelle les hooks de base → renvoyer une interface claire → tester le hook isolément.

**Solution** :
```tsx
function useFetch<T>(url: string) {
  const [etat, setEtat] = useState<{ s: 'load' | 'err' | 'ok'; data?: T }>({ s: 'load' });
  useEffect(() => {
    let annule = false;
    setEtat({ s: 'load' });
    api.get<T>(url).then((d) => !annule && setEtat({ s: 'ok', data: d }))
                   .catch(() => !annule && setEtat({ s: 'err' }));
    return () => { annule = true; };                        // logique du jour 95, écrite UNE fois
  }, [url]);
  return etat;                                              // chaque appelant a SON propre état
}

function useLocalStorage<T>(cle: string, defaut: T) {
  const [val, setVal] = useState<T>(() => {
    const brut = localStorage.getItem(cle);
    return brut ? JSON.parse(brut) : defaut;                // initialisation paresseuse
  });
  useEffect(() => { localStorage.setItem(cle, JSON.stringify(val)); }, [cle, val]);
  return [val, setVal] as const;
}
```

**Mini-quiz** : (a) Deux composants qui appellent `useFetch` partagent-ils leur data ? (b) Pourquoi le nom doit-il commencer par `use` ? (c) Quand extraire un hook custom ?
→ (a) non — chacun a son propre état ; le hook partage la LOGIQUE, pas les données (ça, c'est Context) ; (b) pour que React et le linter appliquent les règles des hooks et le reconnaissent ; (c) dès qu'une logique à état se répète ou alourdit un composant — pas pour du trivial à usage unique.

**Variante** : écris un test du hook `useLocalStorage` (avec un localStorage mocké, jour 108) qui vérifie qu'il relit la valeur au montage — tu testes la LOGIQUE sans aucun composant autour, ce qui prouve qu'elle est bien isolée.

## 🏢 Cas métier
Les hooks personnalisés sont la façon standard de partager de la logique en React moderne, et toute base de code React d'entreprise en contient : `useFetch`, `useAuth`, `useForm`, `useDebounce`. Leur intérêt est double : ils suppriment la duplication (la logique de fetch écrite une fois, correcte partout) et rendent les composants maigres et testables. Les bibliothèques les plus populaires de l'écosystème (React Query, etc.) sont essentiellement des hooks custom sophistiqués. Savoir extraire un hook propre, typé et testé — et savoir quand NE pas sur-abstraire — est une compétence React attendue au-delà du niveau débutant, immédiatement visible dans la qualité d'un repo.

## 🎤 Question d'entretien
**« Qu'est-ce qu'un hook personnalisé et quand en crées-tu un ? »** → C'est une fonction dont le nom commence par `use`, qui appelle d'autres hooks et encapsule une LOGIQUE À ÉTAT réutilisable — `useFetch`, `useLocalStorage`. J'en crée un dès qu'une logique stateful se répète entre composants ou alourdit un composant : je l'extrais, elle est écrite une fois et testable isolément, et le composant se recentre sur le rendu. Point clé : un hook partage la LOGIQUE, pas les données — deux composants qui appellent `useFetch` ont chacun leur propre état (pour partager des données, c'est Context). Il obéit aux règles des hooks (appelé au niveau racine, pas dans une condition). Comme toute abstraction, il se justifie par la réutilisation ou la clarté gagnée, pas par principe.
