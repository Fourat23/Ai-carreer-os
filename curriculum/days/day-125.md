## 🎯 Objectif du jour
Maîtriser venv, pip, requirements, linters.

## 📖 Cours approfondi
**Modèle mental : un projet Python REPRODUCTIBLE tient sur trois piliers — un `venv` qui ISOLE les dépendances, un fichier qui les FIGE (requirements/pyproject), et un linter/formateur (ruff/black) qui rend le style NON négociable et AUTOMATIQUE. Sans ces trois, « ça marche sur ma machine » est la norme, pas l'exception.** Tu as croisé le venv au jour 120 ; aujourd'hui tu montes l'outillage complet d'un projet Python professionnel. Ces outils ne sont pas de la bureaucratie : ils garantissent qu'un collègue (ou toi dans six mois) peut installer et faire tourner ton projet à l'identique.

Les trois piliers en détail :
1. **L'isolation — `venv`** : Python installe les paquets GLOBALEMENT par défaut, donc deux projets qui veulent des versions différentes d'une bibliothèque entrent en conflit. `python -m venv .venv` crée un environnement isolé par projet ; `source .venv/bin/activate` l'active. Chaque projet a SES dépendances, sans polluer le système ni les autres projets.
2. **Le figeage — `requirements.txt` / `pyproject.toml`** : lister les dépendances AVEC leurs versions (`pandas==2.2.0`) pour que l'installation soit reproductible. `pip freeze > requirements.txt` capture l'état exact ; `pip install -r requirements.txt` le restaure. `pyproject.toml` est le standard moderne qui regroupe dépendances, métadonnées et config des outils.
3. **Le style automatique — linter + formateur** : `black` (ou `ruff format`) FORMATE le code de façon déterministe (fini les débats sur les espaces) ; `ruff` (linter) DÉTECTE les problèmes (imports inutilisés, variables non définies, anti-patterns) avant l'exécution. Le style devient une propriété de l'outil, pas une discipline manuelle — comme ESLint/Prettier au front.

Pourquoi c'est décisif : un projet sans isolation casse dès qu'une dépendance change ailleurs ; un projet sans figeage n'est pas installable à l'identique ; un projet sans linter/formateur accumule les incohérences de style et les bugs triviaux. Ces outils sont le premier réflexe d'hygiène que TOUTE équipe Python exige.

La règle du jour : **un projet Python = venv isolé + dépendances figées + linter/formateur configurés, le tout documenté**. C'est ce qui rend ton code installable, reproductible et propre — les conditions de base pour travailler à plusieurs ou montrer un projet.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : configurer un projet Python propre (venv, requirements, ruff/black, structure) et documenter 5 conventions.

**Exemple simple** : la séquence d'isolation à connaître — `python -m venv .venv && source .venv/bin/activate && pip install pandas`. À partir de là, `pandas` n'existe que dans CE projet. `deactivate` en sort. C'est le point de départ de tout projet Python.

**Raisonnement pas-à-pas** : créer et activer le venv → installer et figer les dépendances → configurer ruff/black → structurer le projet → documenter les conventions.

**Mise en place** :
```bash
python -m venv .venv && source .venv/bin/activate   # 1. isolation
pip install pandas pytest ruff                       # 2. dépendances du projet
pip freeze > requirements.txt                        # 3. figeage reproductible
ruff check . && ruff format .                         # 4. lint + format automatiques
```
```toml
# pyproject.toml — configuration centralisée (standard moderne)
[project]
name = "datapulse"
dependencies = ["pandas>=2.2", "pytest>=8.0"]
[tool.ruff]
line-length = 100
```
```
Structure :  datapulse/  (code)   tests/  (tests)   pyproject.toml   README.md   .gitignore (dont .venv/)
Mes 5 conventions : snake_case · type hints partout · docstrings sur les fonctions publiques ·
                    ruff format avant chaque commit · tests dans tests/ miroir du code
```

**Mini-quiz** : (a) Pourquoi un venv par projet ? (b) Que capture `pip freeze` ? (c) Quelle différence entre `black`/`ruff format` et `ruff check` ?
→ (a) Python installe globalement par défaut ; le venv isole les dépendances pour éviter les conflits de versions entre projets ; (b) l'état exact des dépendances installées avec leurs versions, pour une installation reproductible ; (c) le formateur (black/ruff format) réécrit le style de façon déterministe ; le linter (ruff check) détecte les problèmes (imports inutiles, bugs) sans réécrire.

**Variante** : ajoute `.venv/` à ton `.gitignore` et vérifie que `git status` ne propose plus de committer des milliers de fichiers de dépendances — un venv ne se commite JAMAIS, seul le `requirements.txt`/`pyproject.toml` le fait.

## ⚠️ Erreurs fréquentes
- Installer globalement sans venv : conflits de versions entre projets, « ça marche sur ma machine ».
- Ne pas figer les versions (requirements sans numéros) : l'installation n'est pas reproductible.
- Committer le dossier `.venv/` : des milliers de fichiers inutiles dans le repo — l'exclure via `.gitignore`.
- Compter sur la discipline manuelle pour le style au lieu d'un formateur : incohérences et débats stériles.

## 🏢 Cas métier
L'outillage (venv + dépendances figées + linter/formateur) est le premier réflexe d'hygiène qu'exige toute équipe Python, et son absence est la cause n°1 du « ça marche sur ma machine » : un projet sans venv casse quand une dépendance change ailleurs, un projet sans requirements n'est pas installable à l'identique, un projet sans formateur accumule les incohérences et les bugs triviaux. En entreprise, la CI refuse un code non formaté ou qui échoue au linter, et un projet non reproductible est un risque. Pour un portfolio, un projet avec un venv propre, un `requirements.txt`/`pyproject.toml`, une config ruff et un `.gitignore` correct signale immédiatement un développeur qui connaît les standards — bien avant même de lire le code métier.

## 🎤 Question d'entretien
**« Comment mets-tu en place un projet Python reproductible ? »** → Trois piliers. L'ISOLATION : un `venv` par projet (`python -m venv .venv`), parce que Python installe globalement par défaut et que deux projets peuvent vouloir des versions différentes d'une bibliothèque. Le FIGEAGE : `requirements.txt` (via `pip freeze`) ou `pyproject.toml` qui liste les dépendances avec leurs versions, pour une installation à l'identique. Le STYLE AUTOMATIQUE : un formateur (`black` ou `ruff format`) qui rend le style déterministe et un linter (`ruff`) qui détecte imports inutiles et bugs avant l'exécution — l'équivalent de Prettier/ESLint. J'ajoute un `.gitignore` (le venv ne se commite jamais, seul le fichier de dépendances). Sans ces trois, « ça marche sur ma machine » devient la norme.
