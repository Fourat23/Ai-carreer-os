## 🎯 Objectif du jour
Rendre reproductible.

## 📖 Cours approfondi
**Modèle mental : dockeriser DocSense, c'est rendre « ça marche chez moi » universel — n'importe qui, sur n'importe quelle machine, lance `docker compose up` et TOUT tourne, sans installer quoi que ce soit d'autre.** La reproductibilité (jour 181) atteint ici son aboutissement : Docker empaquette l'application, ses dépendances et sa configuration dans un environnement isolé et reproductible. Un projet dockerisé est un projet qu'on peut faire tourner, démontrer et déployer sans galère d'installation — un standard de production et un signal de professionnalisme.

Ce que la dockerisation apporte :
1. **La reproductibilité totale** : le Dockerfile décrit l'environnement exact (version de Python, dépendances, configuration) ; l'image construite est identique partout. Fini « ça marche chez moi mais pas chez toi » — l'environnement EST le même. C'est la reproductibilité du jour 181, industrialisée.
2. **`docker compose up` = tout tourne** : le compose orchestre les services (l'app DocSense, la vector DB, éventuellement un cache) en une commande. Un évaluateur (ou toi sur une machine neuve) clone le repo, lance une commande, et DocSense fonctionne. C'est ce qui rend la démo sur machine propre (jour 314) triviale.
3. **Les secrets par environnement** : les clés API (jour 298) ne sont JAMAIS dans l'image — elles sont injectées par variables d'environnement au lancement. Le `.dockerignore` exclut les secrets, le `.env`, les fichiers inutiles de l'image. La sécurité des secrets s'applique à la dockerisation.

Pourquoi c'est un standard non négociable : un projet non dockerisé impose à quiconque veut le lancer de reproduire manuellement l'environnement (versions, dépendances, config) — source de galères et de « ça ne marche pas ». Un projet dockerisé se lance en une commande, ce qui le rend démontrable (un recruteur peut le faire tourner), déployable (le même conteneur va en production) et reproductible (l'environnement est figé). En entreprise, la dockerisation est la norme pour livrer une application. Pour DocSense, `docker compose up` qui fait tout tourner sur une machine propre est à la fois une preuve de professionnalisme et l'assurance que ton projet est réellement livrable, pas juste fonctionnel sur ta machine.

**Fondations Docker approfondies (à maîtriser au-delà de « ça marche »).**

**Image vs conteneur vs couche.** Une IMAGE est un modèle immuable, empilé en COUCHES (chaque instruction du Dockerfile ajoute une couche, mise en cache). Un CONTENEUR est une instance en cours d'exécution d'une image (un processus isolé, pas une VM : il PARTAGE le noyau de l'hôte). Un REGISTRY stocke les images ; un TAG (`node:20-alpine`) est un pointeur MUTABLE, tandis qu'un DIGEST (`@sha256:…`) identifie un contenu EXACT et reproductible. Épingler un digest garantit le même build demain ; `latest` ne garantit rien.

**Cache de couches et ordre des instructions.** Docker réutilise une couche tant que son instruction et ses entrées n'ont pas changé. D'où la règle : copier d'abord le manifeste de dépendances et les installer (`COPY package.json` puis `RUN npm ci`), PUIS copier le code (`COPY . .`). Ainsi une simple modification de code ne réinvalide pas l'installation des dépendances — builds bien plus rapides. Un `.dockerignore` (excluant `.git`, `node_modules`, `.env`, tests) réduit le build context envoyé au démon et la taille de l'image.

**CMD vs ENTRYPOINT.** `ENTRYPOINT` fixe l'exécutable du conteneur ; `CMD` fournit les arguments PAR DÉFAUT (surchargeables à l'exécution). En forme « exec » (`["node","server.js"]`, pas la forme shell), le processus reçoit les signaux directement — crucial pour un arrêt propre. `EXPOSE` documente un port sans le publier ; c'est `-p 8080:80` qui publie réellement.

**Multi-stage builds & taille.** Un build multi-étapes compile dans une image lourde (avec le toolchain) puis ne copie que l'artefact final dans une image d'exécution minimale (base `-alpine`/distroless). Résultat : image plus petite, surface d'attaque réduite, démarrage plus rapide. L'"image bloat" (couches inutiles, dépendances de build embarquées) est une dette technique mesurable.

**Durcissement (sécurité d'exploitation).** Un conteneur pédagogique/production sûr : utilisateur NON-ROOT (`USER 1000`), système de fichiers en LECTURE SEULE (`--read-only` + `--tmpfs` pour l'éphémère), `--network none` quand aucun réseau n'est requis, `--cap-drop ALL`, `--security-opt no-new-privileges`, limites `--memory`/`--cpus`/`--pids-limit`. Jamais de secret dans une couche (il reste dans l'historique de l'image), jamais de montage du socket Docker dans un conteneur, jamais `--privileged`. **Limite honnête : un conteneur RÉDUIT la surface mais PARTAGE le noyau hôte — ce n'est PAS une isolation OS absolue** (contrairement à une VM).

**PID 1, signaux et healthcheck.** Le processus principal du conteneur est PID 1 : s'il n'intercepte pas `SIGTERM`, `docker stop` attend puis le tue brutalement (`SIGKILL`) — d'où la forme exec et, si besoin, un init léger pour récolter les zombies. Un `HEALTHCHECK` (ou une sonde côté orchestrateur) vérifie périodiquement que le service répond vraiment, pas seulement que le processus tourne. Le CODE DE SORTIE du conteneur (celui de PID 1) dit s'il s'est arrêté proprement (0) ou en erreur.

**Diagnostic d'un conteneur qui « démarre puis s'arrête ».** Méthode : lire les LOGS (`docker logs`), regarder le CODE DE SORTIE et le dernier message, distinguer les causes classiques — commande/ENTRYPOINT erroné, variable d'environnement MANQUANTE, PORT non publié ou mauvais mapping, PERMISSION refusée (droits/utilisateur), VOLUME mal monté, HEALTHCHECK en échec. Comme pour le réseau (jour 71), on remonte par couches et on isole la cause, on ne devine pas.

**Énoncé** : dockeriser DocSense — Dockerfile + compose (up = tout tourne), secrets par env, .dockerignore.

**Exemple simple** : le test qui prouve la dockerisation — sur une machine SANS Python ni dépendances installées, `docker compose up` fait tourner DocSense. Si ça marche, la reproductibilité est atteinte.

**Raisonnement pas-à-pas** : décrire l'environnement (Dockerfile), orchestrer les services (compose), gérer les secrets par env, exclure l'inutile (.dockerignore).

**Les fichiers** :
```
Dockerfile :
  FROM python:3.x-slim → installer les dépendances → copier le code → commande de lancement
docker-compose.yml :
  services:
    docsense : build . , ports, env_file (secrets injectés, PAS dans l'image)
    vectordb : image Chroma, volume persistant
  → docker compose up = app + vector DB tournent ensemble
.dockerignore :
  .env, secrets, .git, __pycache__, tests, docs → image légère et sûre
.env (gitignoré, jour 298) : ANTHROPIC_API_KEY=... (injecté au lancement)
```

**Mini-quiz** : (a) Que résout la dockerisation par rapport à « ça marche chez moi » ? (b) Où vivent les secrets dans un projet dockerisé ? (c) À quoi sert le .dockerignore ?
→ (a) l'environnement est identique partout (versions, dépendances, config figées) ; (b) injectés par variables d'environnement au lancement, JAMAIS dans l'image ; (c) exclure les secrets et l'inutile de l'image (image légère et sûre).

## ⚠️ Erreurs fréquentes
- Secrets dans l'image Docker : une image avec une clé API est compromise si partagée — injecter par variables d'environnement au lancement.
- Pas de .dockerignore : l'image embarque .git, .env, tests — lourde et potentiellement dangereuse (secrets).
- Tester seulement sur sa machine (déjà configurée) : le test qui compte est sur une machine PROPRE (git clone + compose up).
- Compose incomplet (oublier la vector DB) : `up` doit faire tourner TOUT le système, pas seulement l'app.

## 🏢 Cas métier
La dockerisation est un standard de production non négociable : en entreprise, une application se livre en conteneur (le même qui tourne en dev, en test et en production), ce qui élimine les « ça marche chez moi » et rend le déploiement reproductible. Un projet non dockerisé impose une reproduction manuelle de l'environnement — source de friction et d'erreurs. Pour un portfolio, un projet qui se lance en `docker compose up` sur une machine propre signale immédiatement un niveau de professionnalisme : le recruteur peut le faire tourner sans galère, et sait que le candidat maîtrise les standards de livraison. « DocSense se lance en une commande sur n'importe quelle machine » est une preuve de livrabilité que les projets « fonctionnels mais impossibles à installer » n'ont pas.
