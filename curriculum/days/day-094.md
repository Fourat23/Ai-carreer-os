## 🎯 Objectif du jour
Afficher conditionnellement et mapper des listes avec key.

## 📖 Cours approfondi
**Modèle mental : afficher une liste, c'est PROJETER des données en JSX (`map`), et la `key` est l'IDENTITÉ stable que React utilise pour savoir quel élément est lequel entre deux rendus — ce n'est pas une décoration.** Deux mécanismes s'assemblent aujourd'hui : le rendu conditionnel (montrer un morceau d'UI selon une condition) et le rendu de listes (transformer un tableau de données en tableau d'éléments). Tous deux découlent du même principe : le JSX est du JavaScript, donc tu utilises les outils JS (`&&`, ternaire, `.map`, `.filter`) pour construire l'UI.

Les points à maîtriser :
1. **Le rendu conditionnel** : `{condition && <X/>}` (afficher si vrai), `{cond ? <A/> : <B/>}` (l'un ou l'autre). Piège classique : `{liste.length && <Liste/>}` affiche `0` quand la liste est vide (car `0` est falsy mais rendu) — écris `{liste.length > 0 && ...}`.
2. **Le rendu de listes** : `{items.map((it) => <Ligne key={it.id} {...it} />)}`. La `key` DOIT être un identifiant STABLE et unique (l'id métier), jamais l'index du tableau si la liste peut être réordonnée, filtrée ou modifiée. Une key = index provoque des bugs subtils : React réutilise le mauvais composant, un champ de formulaire garde la valeur du voisin supprimé.
3. **Les états edge** : une liste a toujours au moins trois cas à rendre — vide (« aucun résultat »), en chargement (squelette/spinner), et rempli. Une UI professionnelle traite le cas vide EXPLICITEMENT, pas comme un oubli.

La règle qui gouverne le jour : **une liste rendue est une fonction pure de ses données, et son identité passe par des keys stables**. Pourquoi la key compte tant : React « réconcilie » l'ancien et le nouveau rendu en appariant les éléments par leur key. Une key stable = React sait qu'un élément a bougé/changé/disparu et met à jour le minimum. Une mauvaise key = React se trompe d'élément, avec des bugs d'affichage et d'état invisibles à la lecture.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : une liste filtrable avec ses états vide et chargement, et des keys correctes.

**Exemple simple** : le cas vide, souvent oublié — `{resultats.length === 0 && <p>Aucun résultat</p>}`. Toujours prévoir ce que l'écran montre quand il n'y a RIEN à montrer.

**Raisonnement pas-à-pas** : gérer d'abord chargement, puis vide, puis la liste ; mapper avec une key stable ; dériver la liste filtrée du state (jour 93).

**Solution** :
```tsx
function Livres({ livres, chargement }: { livres: Livre[]; chargement: boolean }) {
  const [q, setQ] = useState('');
  const filtres = livres.filter((l) => l.titre.toLowerCase().includes(q.toLowerCase()));

  if (chargement) return <Spinner />;                       // état 1 : chargement
  return (
    <>
      <input value={q} onChange={(e) => setQ(e.target.value)} placeholder="Rechercher" />
      {filtres.length === 0                                   // état 2 : vide (explicite)
        ? <p>Aucun livre ne correspond.</p>
        : <ul>{filtres.map((l) => <li key={l.id}>{l.titre}</li>)}</ul>  // état 3 : key stable
      }
    </>
  );
}
```

**Mini-quiz** : (a) Pourquoi ne pas utiliser l'index du tableau comme key sur une liste filtrable ? (b) Que rend `{liste.length && <X/>}` quand la liste est vide ? (c) Où vient la liste filtrée — state ou dérivée ?
→ (a) l'index change quand on filtre/réordonne, React apparie les mauvais éléments (bugs d'état) ; (b) `0` s'affiche à l'écran (0 est falsy mais rendu) — utilise `length > 0` ; (c) dérivée du state `q`, jamais stockée (jour 93).

**Variante** : sur chaque ligne, ajoute un bouton supprimer ; vérifie qu'avec des keys = id, supprimer le 2e élément ne « décale » aucune valeur — puis teste avec key = index pour VOIR le bug.

## 🏢 Cas métier
Le bug « key=index » est un classique des revues de code : une liste avec des champs éditables où supprimer une ligne fait apparaître la valeur d'une autre. La cause est toujours la même — React apparie les éléments par leur key, et un index n'est pas une identité stable. Les équipes front l'attrapent en revue parce que c'est une source de bugs coûteux et difficiles à reproduire. Savoir choisir une key stable et traiter le cas vide explicitement est un signe de maturité front : ça montre que tu penses aux données réelles (vides, filtrées, réordonnées), pas seulement au cas idéal.

## 🎤 Question d'entretien
**« À quoi sert la prop `key` dans une liste React, et pourquoi éviter l'index ? »** → La `key` donne à chaque élément une IDENTITÉ stable que React utilise pour réconcilier l'ancien et le nouveau rendu : il sait ainsi quel élément a bougé, changé ou disparu, et met à jour le minimum. Si j'utilise l'index du tableau, l'identité change dès que la liste est filtrée ou réordonnée — React apparie les mauvais éléments, ce qui provoque des bugs d'état invisibles (un champ qui garde la valeur du voisin supprimé). Il faut une key issue des données (un id métier unique et stable).
