### Synthèse de la semaine
La semaine 18 a transformé « je connais la syntaxe Python » en « je sais construire un projet Python propre » : syntaxe et structures idiomatiques (jour 120), fonctions/modules/fichiers et organisation en responsabilités uniques (121), gestion d'exceptions robuste avec rattrapage spécifique et échec tôt (122), POO pythonique légère — dataclasses, composition, pas de classe superflue (123), tests pytest minimalistes avec fixtures et paramétrisation (124), et outillage reproductible — venv, dépendances figées, ruff/black (125). Le fil rouge : **du Python professionnel n'est pas du code qui marche une fois, c'est du code ORGANISÉ (modules), ROBUSTE (exceptions spécifiques), TESTÉ (pytest) et REPRODUCTIBLE (venv + outils)**. Tu entres dans la semaine 19 (pandas) avec les fondations pour écrire du code data propre, pas seulement des notebooks jetables.

### Plan de remédiation (si un critère échoue)
- **Script monolithique** (tout dans un fichier) : rejoue le jour 121 — découpe en modules (I/O, métier pur, interface), protège le point d'entrée avec `__main__`, logique testable sans fichier.
- **Exceptions mal gérées** (`except:` large, plantages) : jour 122 — rattrape le type spécifique, échoue tôt avec `raise`, ne masque jamais un bug ; distingue erreurs métier et techniques.
- **POO plaquée d'un autre langage** (hiérarchies, getters/setters) : jour 123 — dataclass pour les données, composition, pas de classe quand une fonction suffit ; attention à la valeur par défaut mutable.
- **Pas de tests ou tests fragiles** : jour 124 — pytest (assert, fixtures `tmp_path`, parametrize), prouve le rougissement.
- **Projet non reproductible** : jour 125 — venv, dépendances figées, ruff/black, .gitignore ; un collègue doit pouvoir installer et lancer à l'identique.

### Questions d'entretien de la semaine
1. **« Comment organises-tu un projet Python ? »** Attendu : modules à responsabilité unique (I/O, métier pur, interface), import explicite, `__main__` pour séparer bibliothèque et point d'entrée.
2. **« Pourquoi éviter un `except` trop large ? »** Attendu : il avale bugs et interruptions, masque les vrais problèmes (données fausses silencieuses) ; rattraper le type spécifique, échouer tôt avec `raise`.
3. **« Quand une classe en Python, et le style pythonique ? »** Attendu : classe si données + comportement ensemble ; dataclass pour les données ; composition > héritage ; pas de classe pour une fonction ; piège de la valeur par défaut mutable.
4. **« Comment testes-tu avec pytest ? »** Attendu : fonctions `test_*` + assert, fixtures (`tmp_path`) pour l'I/O, parametrize pour les cas limites, prouver le rougissement.
5. **« Comment rends-tu un projet Python reproductible ? »** Attendu : venv isolé, dépendances figées (requirements/pyproject), linter/formateur, venv jamais commité.
