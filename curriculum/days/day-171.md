## 📖 Cours approfondi
**Modèle mental : un Pipeline scikit-learn ENCHAÎNE le préprocessing et le modèle en UN seul objet qui n'apprend que sur le train à chaque étape — c'est la garantie ANTI-LEAKAGE structurelle : il devient IMPOSSIBLE d'ajuster un scaler sur des données de test par accident, et tout le traitement devient reproductible et déployable en une ligne.** Après avoir compris le leakage (jour 157) et le préprocessing (jour 170), le Pipeline est l'outil qui rend l'anti-leakage automatique plutôt que dépendant de la discipline. C'est la différence entre « je fais attention à ne pas fuiter » et « la structure m'en empêche ».

Ce qu'un Pipeline apporte, depuis les fondations :
1. **L'enchaînement en un objet** : `Pipeline([("pre", preprocessing), ("clf", modèle)])` se comporte comme un modèle unique avec `.fit`/`.predict`/`.score`. Appeler `.fit(X_train, y_train)` ajuste le préprocessing PUIS le modèle sur le train ; `.predict(X_test)` applique le préprocessing appris (sans le ré-ajuster) puis prédit.
2. **L'anti-leakage automatique** : c'est le point crucial. En validation croisée, le Pipeline ré-apprend le préprocessing sur le train de CHAQUE fold — jamais sur le fold de test. Sans Pipeline, on est tenté d'ajuster le scaler une fois sur tout, ce qui fait fuir l'info du test. Le Pipeline rend ce bug structurellement impossible.
3. **Le ColumnTransformer** : pour appliquer des traitements DIFFÉRENTS selon les colonnes (normaliser les numériques, one-hot les catégorielles), on l'intègre dans le Pipeline (jour 170). Tout le préprocessing hétérogène est ainsi encapsulé proprement.
4. **La reproductibilité et le déploiement** : un Pipeline entraîné se sérialise (joblib) et se déploie tel quel — le préprocessing part avec le modèle, appris exactement comme en entraînement. Fini le « j'ai oublié de normaliser en production » : le Pipeline garantit que l'inférence applique le même traitement que l'entraînement.

Pourquoi c'est un standard non négociable : la majorité des bugs de leakage viennent d'un préprocessing mal séparé du modèle. Le Pipeline élimine cette classe entière d'erreurs par construction, rend le code plus lisible (un objet au lieu de plusieurs étapes manuelles), et rend le modèle déployable. Un projet ML professionnel encapsule TOUJOURS préprocessing + modèle dans un Pipeline.

La règle du jour : **encapsule préprocessing + modèle dans un Pipeline — il garantit l'anti-leakage par construction (préprocessing ré-appris sur le train de chaque fold), rend le traitement reproductible et déployable, et se comporte comme un modèle unique. Le Pipeline transforme l'anti-leakage d'une discipline en une garantie structurelle**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : refactorer un modèle en Pipeline complet (préprocessing + modèle), sans leakage, reproductible.

**Exemple simple** : le Pipeline se comporte comme un modèle — `pipe.fit(X_tr, y_tr)` ajuste préprocessing PUIS modèle sur le train ; `pipe.predict(X_te)` applique le préprocessing appris puis prédit. Un seul objet, aucun risque d'oublier une étape.

**Raisonnement pas-à-pas** : encapsuler le préprocessing (ColumnTransformer) et le modèle dans un Pipeline → l'utiliser en CV (préprocessing ré-appris à chaque fold) → sérialiser pour le déploiement.

**Implémentation** :
```python
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.pipeline import Pipeline
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import cross_val_score
import joblib

pre = ColumnTransformer([
    ("num", StandardScaler(), num_cols),
    ("cat", OneHotEncoder(handle_unknown="ignore"), cat_cols),
])
pipe = Pipeline([("pre", pre), ("clf", RandomForestClassifier(random_state=42))])

# En CV : le préprocessing est ré-appris sur le train de CHAQUE fold -> zéro leakage
print(cross_val_score(pipe, X, y, cv=5, scoring="roc_auc").mean())

pipe.fit(X_tr, y_tr)
joblib.dump(pipe, "modele.joblib")     # déployable tel quel : préproc + modèle ensemble
```

**Mini-quiz** : (a) Pourquoi un Pipeline évite-t-il le leakage automatiquement ? (b) Que se passe-t-il quand on appelle `.predict` sur un Pipeline ? (c) Pourquoi est-ce utile au déploiement ?
→ (a) en CV, il ré-apprend le préprocessing sur le train de chaque fold seulement, jamais sur le test — le bug du scaler ajusté sur tout devient impossible ; (b) il applique le préprocessing DÉJÀ appris (sans le ré-ajuster) puis prédit ; (c) le préprocessing part avec le modèle, appris comme à l'entraînement — fini le « j'ai oublié de normaliser en prod ».

**Variante** : compare une CV avec préprocessing fait AVANT (à la main, sur tout X) vs le même dans un Pipeline. Le score du Pipeline est légèrement plus bas — c'est le score HONNÊTE, sans le leakage que le préprocessing global introduisait.

## 🏢 Cas métier
Le Pipeline est un standard non négociable du ML professionnel : il élimine par construction la classe d'erreurs la plus coûteuse (le leakage par préprocessing mal séparé) et rend le modèle déployable — le préprocessing voyage avec le modèle, garantissant qu'en production l'inférence applique exactement le traitement de l'entraînement. Sans Pipeline, les équipes accumulent des bugs subtils (scaler ajusté sur tout, préprocessing oublié en prod, incohérence train/serving) qui invalident des projets. Les revues de code ML exigent l'encapsulation en Pipeline précisément pour ces raisons. ## 🎤 Question d'entretien
**« Pourquoi encapsuler préprocessing et modèle dans un Pipeline scikit-learn ? »** → Pour trois raisons. D'abord l'ANTI-LEAKAGE par construction : en validation croisée, le Pipeline ré-apprend le préprocessing sur le train de CHAQUE fold, jamais sur le fold de test — le bug classique du scaler ajusté sur tout le dataset devient structurellement impossible. Ensuite la REPRODUCTIBILITÉ et le déploiement : le Pipeline se comporte comme un modèle unique (`fit`/`predict`) et se sérialise avec son préprocessing, donc en production l'inférence applique exactement le traitement de l'entraînement — fini les incohérences train/serving. Enfin la LISIBILITÉ : un objet au lieu d'étapes manuelles dispersées. J'y intègre un ColumnTransformer pour traiter différemment numériques (normalisation) et catégorielles (one-hot). Un projet ML sérieux encapsule toujours préprocessing + modèle dans un Pipeline : ça transforme l'anti-leakage d'une discipline fragile en garantie structurelle.
