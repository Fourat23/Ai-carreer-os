## 🎯 Objectif du jour
Ajout, édition, suppression.

## 📖 Cours approfondi
**Modèle mental : le CRUD, c'est le cycle de vie complet d'une ressource (Créer, Lire, Modifier, Supprimer) — et chaque ÉCRITURE combine trois réflexes déjà acquis : formulaire contrôlé validé (jour 96), mise à jour d'état IMMUABLE (jour 93), appel via la couche api (jour 97). Tu n'apprends rien de neuf ; tu ASSEMBLES.** Sur le socle marchant (jour 113, le « R » de lire), tu ajoutes maintenant les trois opérations d'écriture. Chacune suit le même patron : l'utilisateur agit (formulaire ou bouton) → validation → appel api → mise à jour immuable de l'état local → l'UI reflète le changement.

Ce que chaque écriture exige de spécifique :
1. **Créer (C)** : un formulaire contrôlé validé (jour 96) qui POST vers l'api ; à la réussite, ajouter le nouvel élément à l'état (`[...livres, nouveau]`) et rediriger ou confirmer.
2. **Modifier (U)** : le MÊME formulaire, pré-rempli avec les valeurs existantes (initialiser le state du formulaire depuis la ressource) ; un PUT/PATCH ; à la réussite, remplacer l'élément dans l'état (`livres.map(l => l.id === id ? modifié : l)`). Réutiliser le formulaire pour créer ET modifier est un signe de bonne conception.
3. **Supprimer (D)** : une action DESTRUCTRICE, donc à CONFIRMER (« Confirmer la suppression ? ») — jamais un clic direct qui détruit sans filet ; un DELETE ; à la réussite, retirer l'élément (`livres.filter(l => l.id !== id)`).

Le point de vigilance transversal : **garder l'état local COHÉRENT avec le serveur après chaque écriture, immuablement**. Deux stratégies — soit re-fetcher la liste après l'écriture (simple, sûr, un aller-retour de plus), soit mettre à jour l'état local en miroir de ce que le serveur a fait (plus réactif, mais il faut gérer l'échec : si l'api rejette, ne pas laisser l'UI mentir). Le débutant oublie souvent ce cas : l'UI affiche « supprimé » alors que le serveur a refusé.

La règle du jour : **chaque opération d'écriture valide, appelle l'api, met à jour l'état immuablement, et gère son échec ; la suppression se confirme toujours**. Le CRUD complet est le cœur fonctionnel de BiblioApp — et le patron de la quasi-totalité des applications de gestion.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : le CRUD complet de BiblioApp — ajout/édition validés, suppression confirmée, état immuable.

**Exemple simple** : les trois écritures immuables tiennent en trois expressions — ajouter `[...livres, n]`, modifier `livres.map(l => l.id===id?m:l)`, supprimer `livres.filter(l => l.id!==id)`. Le CRUD d'état, c'est ces trois lignes appliquées après chaque appel api réussi.

**Raisonnement pas-à-pas** : réutiliser le formulaire contrôlé pour créer ET modifier → appeler l'api → mettre à jour l'état immuablement à la réussite → confirmer avant de supprimer → gérer l'échec.

**Solution** :
```tsx
async function creer(l: NouveauLivre) {
  const cree = await api.creerLivre(l);                     // POST (jour 97)
  setLivres((xs) => [...xs, cree]);                         // ajout IMMUABLE
}
async function modifier(id: number, patch: Partial<Livre>) {
  const maj = await api.majLivre(id, patch);                // PUT
  setLivres((xs) => xs.map((l) => (l.id === id ? maj : l))); // remplacement IMMUABLE
}
async function supprimer(id: number) {
  if (!confirm('Confirmer la suppression ?')) return;        // action destructrice → CONFIRMÉE
  try {
    await api.supprimerLivre(id);                            // DELETE
    setLivres((xs) => xs.filter((l) => l.id !== id));        // retrait IMMUABLE
  } catch { alert('Suppression refusée par le serveur'); }  // l'UI ne ment pas si l'api rejette
}
```

**Mini-quiz** : (a) Pourquoi réutiliser le même formulaire pour créer et modifier ? (b) Pourquoi confirmer une suppression ? (c) Que se passe-t-il si on met à jour l'UI sans gérer l'échec de l'api ?
→ (a) c'est le même formulaire de saisie validé, seule l'initialisation et le verbe HTTP changent — moins de code, cohérence ; (b) c'est destructeur et irréversible côté utilisateur — jamais un clic direct sans filet ; (c) l'UI « ment » : elle affiche un changement que le serveur a refusé.

**Variante** : pré-remplis le formulaire d'édition en initialisant son state depuis la ressource chargée (`useState(livre)`) — le même composant sert alors à l'ajout (state vide) et à l'édition (state pré-rempli).

## ⚠️ Erreurs fréquentes
- UI qui « ment » : mettre à jour l'état sans gérer l'échec de l'api affiche un changement que le serveur a refusé.
- Suppression sans confirmation : destruction de données par un clic accidentel.
- Muter l'état après écriture (push/splice) au lieu de spread/map/filter : désynchronisation de l'affichage.
- Dupliquer deux formulaires quasi identiques pour créer et modifier au lieu d'en réutiliser un seul : plus de code, incohérences.

## 🏢 Cas métier
Le CRUD est le cœur de la quasi-totalité des applications de gestion en entreprise (clients, commandes, stocks, utilisateurs) : maîtriser ce patron — formulaire réutilisé, écriture immuable, suppression confirmée, échec géré — c'est savoir construire la brique la plus répandue du métier. Les bugs récurrents que les revues attrapent : l'UI qui « ment » (affiche un changement que le serveur a rejeté), la suppression sans confirmation qui détruit des données par mégarde, et l'état muté qui désynchronise l'affichage. Un CRUD propre, cohérent avec le serveur et sûr pour les actions destructrices, est un livrable que tout recruteur sait évaluer — et qui prouve que tu sais assembler des acquis en une fonctionnalité complète.

## 🎤 Question d'entretien
**« Comment implémentes-tu un CRUD complet côté front ? »** → Chaque opération assemble trois réflexes : formulaire contrôlé validé, mise à jour d'état IMMUABLE, appel via la couche api. Créer : POST puis ajout immuable (`[...xs, cree]`). Modifier : le MÊME formulaire pré-rempli, PUT, puis remplacement (`map`). Supprimer : une CONFIRMATION obligatoire (action destructrice), DELETE, puis retrait (`filter`). Le point de vigilance : garder l'état local cohérent avec le serveur — soit re-fetcher, soit mettre à jour en miroir en gérant l'ÉCHEC (si l'api rejette, ne pas laisser l'UI afficher un changement qui n'a pas eu lieu). Réutiliser le formulaire pour créer et modifier est un signe de bonne conception.
