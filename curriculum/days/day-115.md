## 🎯 Objectif du jour
Recherche et filtrage côté UI.

## 📖 Cours approfondi
**Modèle mental : la recherche et les filtres sont de l'état DÉRIVÉ — on ne stocke JAMAIS la liste filtrée, on la CALCULE à partir des données brutes + des critères courants ; et des filtres combinables ne sont qu'une COMPOSITION de prédicats.** C'est l'application directe de « ce qui se calcule ne se stocke pas » (jour 93) à un cas riche. Le state contient les CRITÈRES (le texte recherché, les filtres actifs) ; la liste affichée se dérive à chaque rendu en appliquant ces critères aux données. Stocker la liste filtrée en state serait une seconde source de vérité à resynchroniser sans cesse — la garantie de bugs.

La structure d'une recherche/filtres propre :
1. **Le state = les critères, pas les résultats** : `q` (texte), `filtres` (genre, disponibilité...). Ce sont les seules choses qui « changent » ; le reste se déduit.
2. **Les résultats = une dérivation** : `livres.filter(l => matchTexte(l, q) && matchFiltres(l, filtres))`. Des filtres COMBINABLES = un ET de prédicats indépendants ; ajouter un filtre = ajouter un prédicat, sans toucher aux autres. Cette composition rend le système extensible.
3. **Les états edge de la recherche** : le cas VIDE (« aucun résultat pour 'xyz' ») est différent du cas « aucune donnée » — une recherche qui ne trouve rien doit le dire clairement, avec le terme cherché, et idéalement offrir de réinitialiser les filtres.

La performance, avec mesure (jour 102) : sur de grandes listes, filtrer à chaque frappe peut ramer. La parade mesurée est le DEBOUNCE (attendre que l'utilisateur arrête de taper avant de filtrer) — mais on ne l'ajoute que si le Profiler montre un vrai problème ; sur une petite liste, filtrer en direct est parfait et le debounce serait de la complexité inutile.

La règle du jour : **stocke les critères, dérive les résultats ; compose les filtres comme des prédicats indépendants ; traite le cas 'aucun résultat' explicitement**. Cette approche garde la recherche prévisible (une seule source de vérité), extensible (un filtre de plus = un prédicat de plus) et lisible.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : barre de recherche + filtres combinables + états vides soignés, en état dérivé.

**Exemple simple** : la dérivation est le cœur — `const resultats = livres.filter(l => l.titre.toLowerCase().includes(q.toLowerCase()))`. La liste affichée n'existe pas en state : elle se recalcule à chaque frappe. Ajouter un filtre, c'est ajouter une condition à ce `filter`.

**Raisonnement pas-à-pas** : stocker les critères en state → dériver les résultats en composant des prédicats → gérer le cas « aucun résultat » distinct du cas « aucune donnée » → mesurer avant d'optimiser.

**Solution** :
```tsx
function Catalogue({ livres }: { livres: Livre[] }) {
  const [q, setQ] = useState('');
  const [dispoSeule, setDispoSeule] = useState(false);       // critères en STATE

  const matchTexte = (l: Livre) => l.titre.toLowerCase().includes(q.toLowerCase());
  const matchDispo = (l: Livre) => (dispoSeule ? l.dispo : true);
  const resultats = livres.filter((l) => matchTexte(l) && matchDispo(l)); // DÉRIVÉ : prédicats composés

  return (
    <>
      <input value={q} onChange={(e) => setQ(e.target.value)} placeholder="Rechercher un titre" />
      <label><input type="checkbox" checked={dispoSeule} onChange={(e) => setDispoSeule(e.target.checked)} /> Disponibles seulement</label>
      {resultats.length === 0
        ? <p>Aucun livre ne correspond à « {q || 'ces filtres'} ». <button onClick={() => { setQ(''); setDispoSeule(false); }}>Réinitialiser</button></p>
        : <ListeLivres livres={resultats} />}
    </>
  );
}
```

**Mini-quiz** : (a) Pourquoi ne pas stocker la liste filtrée en state ? (b) Comment rend-on des filtres combinables ? (c) Quand ajouter un debounce ?
→ (a) ce serait une seconde source de vérité à resynchroniser — on la dérive des critères ; (b) en composant des prédicats indépendants par un ET (`match1 && match2`) ; (c) seulement si le Profiler montre un vrai ralentissement sur une grande liste — sinon c'est de la complexité inutile.

**Variante** : ajoute un troisième filtre (par genre) — tu dois pouvoir le faire en ajoutant UN prédicat au `filter`, sans toucher aux autres. Si ça t'oblige à réécrire la logique, c'est que tes filtres ne sont pas bien composés.

## 🏢 Cas métier
La recherche et le filtrage sont attendus dans presque toute application affichant des données (catalogues, back-offices, tableaux de bord), et la façon de les implémenter distingue immédiatement le niveau : stocker la liste filtrée en state (et la resynchroniser à la main) est le bug de conception classique du débutant, source de désynchronisations ; dériver les résultats des critères est l'approche propre et extensible. La composition en prédicats indépendants permet d'ajouter des filtres sans casser l'existant — exactement ce qu'exige une fonctionnalité qui grossit avec le temps. Savoir dériver plutôt que stocker, et composer des filtres, est un marqueur de conception d'état sain que les revues valorisent.

## 🎤 Question d'entretien
**« Comment implémentes-tu une recherche avec filtres combinables ? »** → Je stocke les CRITÈRES en state (le texte, les filtres actifs), jamais la liste filtrée : celle-ci est de l'état DÉRIVÉ, recalculé à chaque rendu en appliquant les critères aux données. Stocker les résultats créerait une seconde source de vérité à resynchroniser — un nid à bugs. Les filtres combinables sont une COMPOSITION de prédicats indépendants reliés par un ET : ajouter un filtre = ajouter un prédicat, sans toucher aux autres, donc le système reste extensible. Je traite le cas « aucun résultat » explicitement (avec le terme cherché et un moyen de réinitialiser), distinct du cas « aucune donnée ». Le debounce, je ne l'ajoute que si le Profiler prouve un ralentissement — pas par principe.
