## 🎯 Objectif du jour
Comprendre et limiter les re-renders inutiles.

## 📖 Cours approfondi
**Modèle mental : React re-rend un composant quand son state ou ses props changent, ET re-rend ses enfants par défaut — la performance, ce n'est pas empêcher TOUS les re-rendus, c'est éliminer les re-rendus INUTILES, et seulement après les avoir MESURÉS.** Un re-rendu n'est pas mauvais en soi : recalculer du JSX est rapide. Le problème survient quand un composant coûteux (grande liste, calcul lourd) se re-rend alors que rien de ce qui l'affecte n'a changé. L'optimisation prématurée (mémoïser partout « au cas où ») ajoute de la complexité pour un gain nul, voire négatif.

La démarche correcte, dans l'ordre :
1. **MESURER d'abord** : le React DevTools Profiler montre quels composants se re-rendent et combien de temps ils prennent. Sans mesure, tu optimises à l'aveugle. « Mesurer avant d'optimiser » est la règle d'or, identique côté back-end.
2. **Comprendre la cause** : un re-rendu inutile vient souvent d'une nouvelle RÉFÉRENCE créée à chaque rendu du parent — un objet, un tableau ou une fonction recréés en ligne (`onClick={() => ...}`, `style={{...}}`) qui changent l'identité des props de l'enfant à chaque fois.
3. **Appliquer le bon outil** : `React.memo` (ne re-rend l'enfant que si ses props changent réellement), `useMemo` (mémoïse une VALEUR calculée coûteuse), `useCallback` (mémoïse une FONCTION pour garder son identité stable entre rendus). Ces trois outils reposent sur la stabilité des références — la même notion que l'immutabilité (jour 93).

La règle qui évite le sur-usage : **on mémoïse un composant/valeur/fonction quand un profil PROUVE un re-rendu coûteux inutile — pas par principe**. Mémoïser a un coût (mémoire, comparaison des props, code plus complexe) qui ne se justifie que face à un vrai problème mesuré. Un `useMemo` sur un calcul trivial est du bruit qui dégrade la lisibilité sans rien gagner. La compétence n'est pas « connaître memo/useMemo/useCallback », c'est savoir QUAND ils valent leur coût — ce qui suppose d'avoir mesuré.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : identifier un re-rendu coûteux au Profiler et le corriger avec le bon outil.

**Exemple simple** : la cause n°1 d'un re-rendu inutile — une fonction recréée en ligne — `<Enfant onClic={() => faire(id)} />`. À chaque rendu du parent, `onClic` a une nouvelle identité, donc `React.memo(Enfant)` ne sert à rien tant qu'on ne stabilise pas la fonction avec `useCallback`.

**Raisonnement pas-à-pas** : profiler → repérer le composant coûteux qui se re-rend sans raison → identifier la référence instable → stabiliser (memo + useCallback/useMemo) → RE-profiler pour prouver le gain.

**Solution** :
```tsx
const LigneLourde = React.memo(function LigneLourde(
  { livre, onSelect }: { livre: Livre; onSelect: (id: number) => void }) {
  return <li onClick={() => onSelect(livre.id)}>{livre.titre}</li>;
}); // ne re-rend QUE si livre ou onSelect changent d'identité

function Liste({ livres }: { livres: Livre[] }) {
  const [sel, setSel] = useState<number | null>(null);
  const onSelect = useCallback((id: number) => setSel(id), []); // identité STABLE
  const tri = useMemo(() => [...livres].sort((a, b) =>              // calcul coûteux mémoïsé
    a.titre.localeCompare(b.titre)), [livres]);
  return <ul>{tri.map((l) => <LigneLourde key={l.id} livre={l} onSelect={onSelect} />)}</ul>;
}
```

**Mini-quiz** : (a) Que faut-il faire AVANT de mémoïser quoi que ce soit ? (b) Pourquoi `React.memo` seul ne suffit-il pas si on passe `onClick={() => ...}` ? (c) Un `useMemo` sur `a + b` est-il utile ?
→ (a) mesurer avec le Profiler pour prouver un re-rendu coûteux inutile ; (b) la fonction en ligne a une nouvelle identité à chaque rendu, donc les props changent — il faut useCallback ; (c) non, calcul trivial : du bruit qui dégrade la lisibilité sans gain.

**Variante** : retire le `useCallback` et re-profile — observe que `React.memo` cesse d'agir (l'enfant re-rend à nouveau). Tu PROUVES la dépendance entre stabilité de référence et mémoïsation.

## 🏢 Cas métier
Les problèmes de performance React en production sont presque toujours des re-rendus inutiles d'une grande liste ou d'un composant lourd, déclenchés par des références instables (fonctions/objets recréés). Les équipes matures traitent cela par la MESURE (Profiler) puis une mémoïsation ciblée — jamais par une mémoïsation systématique qui alourdit le code sans preuve. Le contre-exemple fréquent : un junior sème des `useMemo`/`useCallback` partout « pour la performance », rendant le code illisible sans gain mesurable. Savoir mesurer, diagnostiquer la référence instable, et n'optimiser que le prouvé est exactement le jugement recherché — et « mesurer avant d'optimiser » se transfère à toute optimisation, front comme back.

## 🎤 Question d'entretien
**« Comment optimises-tu les performances d'un composant React ? »** → D'abord je MESURE avec le React DevTools Profiler : je ne devine pas, je repère quels composants se re-rendent inutilement et combien ça coûte. La cause est souvent une RÉFÉRENCE instable — un objet, un tableau ou une fonction recréés en ligne à chaque rendu du parent, qui changent l'identité des props de l'enfant. Je corrige avec le bon outil : `React.memo` pour ne re-rendre un enfant que si ses props changent vraiment, `useCallback` pour stabiliser une fonction, `useMemo` pour un calcul coûteux. Puis je RE-profile pour prouver le gain. Je ne mémoïse jamais par principe : ça a un coût qui ne se justifie que face à un problème mesuré.
