## 🎯 Objectif du jour
Robustesse et versioning.

## 📖 Cours approfondi
**Modèle mental : un prompt en production est un artefact logiciel avec un cycle de vie.** Au jour 204 tu as appris que le prompt est une spécification ; aujourd'hui tu le traites comme du code DÉPLOYÉ : versionné, testé, mesuré, avec un processus de changement. La différence entre les deux : en production, un prompt qui régresse casse une fonctionnalité pour de vrais utilisateurs — et sans mesures, la régression est INVISIBLE (pas de stacktrace, juste des sorties un peu pires).

Le système minimal viable :
1. **Un prompt = un fichier versionné** (`prompts/extracteur-v3.md`), jamais une chaîne dans le code. Le code référence la version ; le git log raconte l'évolution.
2. **Un jeu de cas de test par prompt** : des entrées de référence avec sorties attendues (exactes pour l'extraction, critères pour le généré). C'est ton filet de sécurité — l'équivalent des tests unitaires.
3. **Un taux de réussite mesuré** : avant TOUT changement de prompt, le score sur le jeu de test ; après le changement, le même score. Un changement qui fait passer le taux de 92 % à 84 % est un REVERT, pas un débat d'opinion.
4. **Un journal des changements** : quel changement, pourquoi, quel effet mesuré — trois lignes par version suffisent.

La boucle est identique à celle du développement classique (tests → changement → tests → commit), appliquée à un artefact que la plupart des équipes modifient encore « au feeling ». C'est précisément pour ça que la discipline est différenciante.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : un système de prompts versionnés avec mesure du taux de réussite.

**Raisonnement** : structurer d'abord (fichiers + jeu de test), mesurer ensuite, améliorer en dernier — jamais l'inverse.

**Structure** :
```
prompts/
  extraction-conges/
    prompt.md            # la version courante
    cas-de-test.json     # [{entree, sortie_attendue}, ...] ≥ 10 cas
    CHANGELOG.md         # v1→v2 : ajout cas limite « texte vide », 82→94 %
run_tests.py             # rejoue tous les cas → taux de réussite par prompt
```

**Le runner (cœur du système)** :
```python
def tester_prompt(prompt: str, cas: list) -> float:
    reussites = 0
    for c in cas:
        sortie = appel_llm(prompt.format(entree=c["entree"]), temp=0)
        if valide(sortie, c["sortie_attendue"]):   # exact ou critères
            reussites += 1
    return reussites / len(cas)
```

**Explication** : temp 0 pour la répétabilité ; la fonction `valide` est exacte pour le structurel (JSON identique) et par critères pour le généré (contient/ne contient pas, longueur, format). **Variante** : casse volontairement ton meilleur prompt (retire les exemples) et vérifie que le runner DÉTECTE la chute — un filet qui n'attrape rien n'est pas un filet.

## 🏢 Cas métier
Une fintech utilise un LLM pour pré-classifier les réclamations. Un dev « améliore » le prompt un vendredi ; lundi, le taux de bonne classification est passé de 91 % à 78 % et personne ne sait pourquoi ni comment revenir en arrière. Avec des prompts versionnés + jeu de test, l'incident devient : diff git, score avant/après, revert en 2 minutes. C'est exactement l'argumentaire à dérouler en entretien.

## 🎤 Question d'entretien
**« Comment gères-tu les prompts dans une app en production ? »** → Comme du code : fichiers versionnés (jamais de chaînes en dur), un jeu de cas de test par prompt, taux de réussite mesuré avant/après chaque modification, changelog. Un changement qui fait baisser le score est reverté. Le prompt « au feeling » en production est l'équivalent du déploiement sans tests.
