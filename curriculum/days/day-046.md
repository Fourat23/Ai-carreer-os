## 📖 Cours approfondi
**Concepts abordés :** CRUD complet · Filtres/tri · Immutabilité (jour 26) · Validation.

Le CRUD complet d'un vrai outil gère l'ÉTAT en style immuable : done/edit ne modifient pas la tâche, ils retournent une copie modifiée que le Store persiste (ton pattern mettreAJourParId du jour 26). Bénéfice concret : chaque opération est une fonction pure testable sans fichiers.

Les filtres combinables (--done --priority high) reprennent le pattern « filtre conditionnel » du jour 23 : chaque critère absent laisse tout passer. Attention au piège falsy : un filtre « priorité 0 » ou une chaîne vide ne doit pas être confondu avec « pas de filtre ».

La validation aux frontières : tout argument CLI est hostile jusqu'à preuve du contraire (id non numérique, priorité inconnue → message clair, exit 1).

**Modèle mental : le CRUD d'un vrai outil gère l'ÉTAT en style IMMUABLE — `done`/`edit` ne MODIFIENT pas une tâche, ils retournent une COPIE modifiée que le Store persiste (ton pattern `mettreAJourParId` du jour 26). Bénéfice concret : chaque opération devient une fonction PURE, testable sans fichiers ni montage. Et les filtres combinables (`--done --priority haute`) suivent le pattern « filtre conditionnel » — chaque critère ABSENT laisse tout passer — avec un piège `falsy` à désamorcer.** Compléter le CRUD, c'est appliquer immutabilité, filtrage et validation aux frontières sur un cas réel.

Pourquoi l'immutabilité pour le CRUD. Muter une tâche en place (`tache.statut = 'done'`) crée des effets de bord : si plusieurs parties du code partagent la référence, elles changent toutes (le bug de référence partagée du jour 41). En retournant une COPIE modifiée (`{ ...tache, statut: 'done' }`), l'original reste intact, l'opération est une fonction pure (mêmes entrées → même sortie), et on peut la tester sans fichiers. `mettreAJourParId` (jour 26) applique une transformation à la tâche ciblée et renvoie une nouvelle liste : c'est le cœur réutilisable de done/edit/rm.

Les filtres combinables, depuis les fondations. Chaque filtre est un prédicat ; les combiner, c'est composer des `filter` (jour 23). Le principe clé : un critère NON FOURNI ne doit rien filtrer (laisser tout passer). D'où le piège `falsy` : tester `if (priorite)` échoue si une priorité légitime est une valeur falsy (chaîne vide, 0) — on confond « pas de filtre » et « filtre sur une valeur falsy ». Il faut tester la PRÉSENCE (`priorite !== undefined`), pas la véracité (le piège du jour 5).

La validation aux frontières. Tout argument CLI est HOSTILE jusqu'à preuve du contraire : un id non numérique, une priorité inconnue, une commande mal formée doivent produire un MESSAGE CLAIR et un `exit 1`, jamais une stack trace brute (qui fait peur et n'aide pas l'utilisateur). La frontière (l'entrée utilisateur) est l'endroit où l'on valide ; l'intérieur du programme peut alors faire confiance aux données.

La différence mise à jour immuable vs mutation. La MUTATION change l'objet existant : rapide mais source d'effets de bord et de bugs de partage. L'IMMUABILITÉ crée un nouvel objet : un léger coût mémoire contre la prévisibilité et la testabilité. Pour un CRUD d'outil, l'immutabilité est le bon choix — les volumes sont petits, la sûreté prime.

Limites et compromis. L'immutabilité par copie a un coût sur de très gros volumes (rare ici). Multiplier les filtres peut compliquer la lisibilité — les composer proprement (une liste de prédicats appliqués en chaîne) garde le code clair. Et la validation exhaustive de chaque entrée est un travail ingrat mais décisif pour l'expérience : un outil qui plante avec une stack trace sur une faute de frappe paraît non fini.

La règle du jour : **gère le CRUD en immuable (retourne des copies modifiées, réutilise mettreAJourParId), compose les filtres en laissant passer les critères absents (attention au piège falsy : teste la présence, pas la véracité), et valide tout argument aux frontières avec un message clair plutôt qu'une stack trace.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : implémenter `done` (marquer terminé) en IMMUABLE et un filtrage combinable, en évitant le piège falsy.

**Exemple simple** : le piège falsy sur un filtre. Si je filtre `if (opts.priorite) garder(...)`, une priorité légitime `''` (ou un filtre « toutes ») serait ignorée. Je dois tester `opts.priorite !== undefined` : la PRÉSENCE du critère, pas sa véracité.

**Raisonnement pas-à-pas** : (1) `done` renvoie une NOUVELLE liste où seule la tâche ciblée est copiée-modifiée (mettreAJourParId) ; (2) le filtrage compose des prédicats ; (3) un critère absent (undefined) laisse tout passer ; (4) chaque argument invalide produit un message clair, pas une stack trace.

**Implémentation** :
```ts
// mise à jour IMMUABLE ciblée (pattern du jour 26)
function mettreAJourParId(taches: Task[], id: number, maj: (t: Task) => Task): Task[] {
  return taches.map(t => (t.id === id ? maj(t) : t));   // copie ciblée, original intact
}
function done(taches: Task[], id: number): Task[] {
  return mettreAJourParId(taches, id, t => ({ ...t, statut: 'done' }));  // COPIE modifiée
}

// filtres COMBINABLES : un critère absent (undefined) laisse tout passer
interface Filtres { statut?: Statut; priorite?: Priorite; }
function filtrer(taches: Task[], f: Filtres): Task[] {
  return taches.filter(t =>
    (f.statut === undefined || t.statut === f.statut) &&          // présence, pas véracité
    (f.priorite === undefined || t.priorite === f.priorite));
}

// validation à la frontière : message clair, jamais de stack trace
function parseId(arg: string): number {
  const id = Number(arg);
  if (!Number.isInteger(id) || id <= 0) {
    console.error(`Id invalide : "${arg}" (attendu : entier positif).`);
    process.exit(1);
  }
  return id;
}
```
L'original n'est jamais muté, les filtres se combinent sans le piège falsy, et une entrée invalide échoue proprement — un CRUD prévisible et testable.

- Muter les tâches en place au lieu de retourner des copies : effets de bord et bugs de référence partagée.
- Piège falsy : filtres qui ignorent une valeur légitime falsy (chaîne vide, priorité 0) faute de tester la présence.
- Filtres qui ne se combinent pas correctement (un critère absent qui filtre au lieu de tout laisser passer).
- Laisser une entrée invalide produire une stack trace brute au lieu d'un message clair et d'un exit 1.

## 🏢 Cas métier
L'immutabilité et la validation aux frontières sont des piliers du logiciel fiable en entreprise. La mise à jour immuable de l'état est LE modèle de la gestion d'état moderne côté front (Redux, React) : ne jamais muter, toujours retourner un nouvel état, ce qui rend les changements traçables et le débogage possible (time-travel). Côté back, valider chaque entrée à la frontière (API, CLI, message de file) est la première ligne de défense : une entrée non validée est la source n°1 des bugs et des failles (injection, crash). Le piège falsy est une source récurrente de bugs subtils dans le code réel (une quantité 0, une chaîne vide traitées comme « absentes »). Un CRUD propre — immuable, filtres combinables sans piège, validation claire — est exactement ce qu'un recruteur veut voir dans un projet portfolio : il démontre que tu écris du code prévisible et défensif, pas seulement fonctionnel.

## 🎤 Question d'entretien
**« Pourquoi mettre à jour l'état de façon immuable, et quel piège guette les filtres conditionnels ? »** → Muter une tâche en place (`tache.statut = 'done'`) crée des effets de bord : si une référence est partagée, plusieurs endroits changent ensemble — le bug de référence partagée. En retournant une COPIE modifiée (`{ ...tache, statut: 'done' }`), l'original reste intact, l'opération devient une fonction pure, donc testable sans fichiers ni montage. C'est le modèle de la gestion d'état moderne (Redux, React) : jamais muter, toujours un nouvel état, ce qui rend les changements traçables. Pour les filtres combinables, le piège est le `falsy` : si je teste `if (critere)`, une valeur légitime mais falsy (chaîne vide, 0) est ignorée à tort ; je dois tester la PRÉSENCE du critère (`critere !== undefined`), pas sa véracité, pour distinguer « pas de filtre » de « filtre sur une valeur falsy ». Un critère absent doit laisser tout passer. **Relance possible** : « et la robustesse face aux entrées utilisateur ? » → je valide tout argument à la frontière (un id non numérique, une priorité inconnue) avec un message clair et exit 1, jamais une stack trace brute : la frontière valide, l'intérieur fait confiance.
