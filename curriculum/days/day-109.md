## 🎯 Objectif du jour
Refactorer pour la lisibilité.

## 📖 Cours approfondi
**Modèle mental : un composant se refactore comme une fonction — quand il fait trop de choses, on EXTRAIT (sous-composants, hooks custom, fonctions nommées) ; la lisibilité se mesure au temps qu'il faut pour comprendre ce composant.** Le clean code du mois 2 (noms clairs, fonctions courtes, une responsabilité) s'applique directement au front. Un composant de 300 lignes qui gère l'état, le fetch, la validation, le rendu et le formatage est le pendant React de la fonction fourre-tout : illisible, non testable, source de bugs. Le refactor front, c'est le découper en pièces qui font chacune UNE chose.

Les signaux qu'un composant a besoin de refactor (les « code smells » front) :
1. **Il est trop long** : on doit scroller pour le comprendre. Extrait des sous-composants (une section = un composant nommé).
2. **Il mélange logique et affichage** : du fetch, des calculs et du JSX entremêlés. Extrait la logique à état dans un hook custom (jour 110) ; le composant ne garde que le rendu.
3. **Il a des noms vagues** : `data`, `handleClick`, `temp`. Renomme d'après l'intention (`livres`, `supprimerLivre`). Un bon nom est la première documentation.
4. **Il répète du JSX** : trois cartes copiées-collées → un composant `Carte` mappé. La duplication est le signal le plus fiable qu'une abstraction manque.
5. **Il a des props en cascade ou des conditions imbriquées** : simplifie, extrait, aplatis.

La règle qui guide chaque extraction : **une pièce (composant, hook, fonction) doit avoir UNE responsabilité qu'on peut nommer d'une phrase**. Si tu ne peux pas nommer ce que fait un composant sans « et » (« il affiche la liste ET gère le formulaire ET fetch »), il en fait trop. Le refactor n'ajoute AUCUNE fonctionnalité — il réorganise pour la lisibilité et la testabilité, et se fait sous la protection des tests (jours 106-108) qui garantissent qu'on n'a rien cassé.

La bascule : le code est lu bien plus souvent qu'écrit. Un composant clair fait gagner du temps à chaque personne qui le relira — toi dans un mois, un collègue, un recruteur qui lit ton repo. Refactorer pour la lisibilité n'est pas cosmétique : c'est un investissement mesurable.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : refactorer un composant trop gros — avant/après — par extraction.

**Exemple simple** : la première extraction évidente — une section répétée devient un composant nommé. `{livres.map(l => <CarteLivre key={l.id} livre={l} />)}` remplace trois blocs de JSX copiés. Moins de lignes, un nom, réutilisable.

**Raisonnement pas-à-pas** : repérer les smells (long, mélange logique/rendu, noms vagues, duplication) → extraire une pièce à la fois → renommer d'après l'intention → vérifier que les tests restent verts.

**Avant / après** :
```tsx
// AVANT : <Catalogue> fait TOUT (fetch, filtre, rendu, formatage) — 120 lignes, intestable.
// APRÈS : responsabilités séparées, chaque pièce nommée et testable.
function Catalogue() {
  const { livres, erreur, chargement } = useLivres();        // logique à état → hook custom (jour 110)
  const [q, setQ] = useState('');
  const filtres = livres.filter((l) => matchTitre(l, q));     // fonction pure nommée
  if (chargement) return <Spinner />;
  if (erreur) return <MessageErreur erreur={erreur} />;       // sous-composant nommé
  return (
    <>
      <BarreRecherche q={q} onChange={setQ} />                {/* une section = un composant */}
      <ListeLivres livres={filtres} />
    </>
  );
}
```

**Mini-quiz** : (a) Quel est le signal le plus fiable qu'une abstraction manque ? (b) Où va la logique à état quand on refactore un gros composant ? (c) Un refactor doit-il ajouter des fonctionnalités ?
→ (a) la duplication (JSX copié-collé) ; (b) dans un hook custom, pour que le composant ne garde que le rendu ; (c) non — il réorganise pour la lisibilité/testabilité sans changer le comportement, sous protection des tests.

**Variante** : après refactor, chronométre le temps qu'un camarade (ou toi, à froid demain) met à comprendre le composant — la lisibilité se MESURE en temps de compréhension, pas en impression.

## 🏢 Cas métier
Le refactor pour la lisibilité est un travail quotidien en entreprise, car le code est lu bien plus qu'il n'est écrit : un composant clair fait gagner du temps à chaque développeur qui le touche, un composant fourre-tout en fait perdre à tout le monde et concentre les bugs. Les revues de code front rejettent régulièrement les composants de plusieurs centaines de lignes qui mélangent tout, précisément parce qu'ils sont impossibles à tester et à faire évoluer sans risque. Savoir découper un gros composant en pièces à responsabilité unique — et le faire sous la protection des tests — est une compétence d'ingénierie directement observable dans un repo, et donc évaluée par les recruteurs.

## 🎤 Question d'entretien
**« Comment refactores-tu un composant devenu trop gros ? »** → Je le traite comme une fonction fourre-tout : je repère les signaux (trop long, mélange logique/rendu, noms vagues, JSX dupliqué) et j'EXTRAIS une pièce à la fois. La logique à état part dans un hook custom pour que le composant ne garde que le rendu ; les sections répétées ou distinctes deviennent des sous-composants nommés ; je renomme d'après l'intention. La règle : chaque pièce doit avoir UNE responsabilité nommable d'une phrase sans « et ». Le refactor n'ajoute aucune fonctionnalité — il réorganise pour la lisibilité et la testabilité, sous la protection des tests qui garantissent que le comportement n'a pas changé. Je le fais parce que le code est lu bien plus souvent qu'écrit.
