## 🎯 Objectif du jour
Écrire des tests d'intégration de l'API (au-delà de Postman) et sécuriser les cas limites.

## 📖 Cours approfondi
**Concepts abordés :** Tests d'intégration · Base de test isolée · Cas limites métier · Assertions sur réponses.

Un test d'INTÉGRATION vérifie le système assemblé : une vraie requête HTTP traverse routes → services → base, et on vérifie la réponse ET l'état de la base. Complémentaire du test unitaire (une fonction isolée) : l'unitaire localise précisément les bugs de logique, l'intégration attrape les bugs de CÂBLAGE (mauvaise route, mauvaise colonne, transaction oubliée).

La règle d'or : une base de TEST isolée, réinitialisée avant chaque suite (jamais la base de dev — les tests doivent être rejouables à l'infini et indépendants de l'ordre).

Que tester en priorité : les RÈGLES MÉTIER (le double emprunt → 409), les cas d'erreur (id inconnu, entrée invalide), et un flux complet (créer → emprunter → rendre). Les chemins heureux triviaux (GET qui liste) rapportent moins par test.

**Modèle mental : un test d'INTÉGRATION vérifie le système ASSEMBLÉ — une vraie requête HTTP traverse routes → services → base, et on vérifie la RÉPONSE ET l'ÉTAT de la base. Il est complémentaire du test unitaire (une fonction isolée, jour 47) : l'unitaire LOCALISE précisément les bugs de logique, l'intégration attrape les bugs de CÂBLAGE (mauvaise route, mauvaise colonne, transaction oubliée) qu'aucun test unitaire ne voit. La règle d'or : une base de TEST isolée, réinitialisée, JAMAIS la base de dev.** Tester l'API de bout en bout, c'est prouver que les pièces fonctionnent ENSEMBLE, pas seulement séparément.

Pourquoi l'intégration en plus de l'unitaire. Un test unitaire vérifie une fonction pure (la logique d'emprunt décide bien « indisponible → conflit »). Mais il ne voit pas si la route est bien branchée, si la requête SQL vise la bonne colonne, si la transaction est réellement appliquée. Ces bugs de CÂBLAGE n'apparaissent qu'en assemblant le système. Les deux niveaux sont complémentaires : l'unitaire est rapide et localise (« CETTE fonction est fausse »), l'intégration est plus lent mais réaliste (« le PARCOURS complet est faux »). La pyramide des tests : beaucoup d'unitaires, moins d'intégration.

Comment ça fonctionne, depuis les fondations. Un test d'intégration ENVOIE une vraie requête HTTP à l'API (via `fetch` sur un serveur de test, ou `supertest`), puis vérifie deux choses : la RÉPONSE (statut, corps) ET souvent l'ÉTAT de la base (la ligne a-t-elle bien été créée/modifiée ?). Il exerce le vrai chemin routes → services → data → SQL, exactement comme un client réel.

La base de test isolée, règle non négociable. Les tests s'exécutent sur une base de TEST séparée, RÉINITIALISÉE avant chaque suite (ou chaque test). Deux raisons : ne jamais POLLUER ni détruire la base de dev ; et rendre les tests REJOUABLES à l'infini et INDÉPENDANTS de l'ordre (un test ne doit pas dépendre des données laissées par un autre). Une base réinitialisée garantit un état de départ connu.

La différence unitaire vs intégration. L'UNITAIRE isole (une fonction, pas de base, pas de réseau) : rapide, précis sur la localisation, mais aveugle au câblage. L'INTÉGRATION assemble (HTTP + logique + base réelle de test) : plus lent, mais attrape les erreurs de branchement et prouve que le système fonctionne pour de vrai. On teste en priorité les RÈGLES MÉTIER (le double emprunt → 409) et les cas d'erreur, pas seulement les chemins heureux.

Limites et compromis. Les tests d'intégration sont plus lents et plus fragiles (dépendent de la base, du montage) que les unitaires — d'où la pyramide : peu d'intégration, beaucoup d'unitaire. Réinitialiser la base a un coût (temps) mais garantit l'indépendance. Et tester TOUS les chemins d'intégration est irréaliste : on cible les parcours critiques et les règles métier.

La règle du jour : **écris des tests d'INTÉGRATION qui envoient de vraies requêtes HTTP et vérifient réponse ET état de la base, sur une base de TEST isolée et réinitialisée (jamais la base de dev). Ils attrapent les bugs de câblage que l'unitaire ne voit pas — cible les règles métier et les cas d'erreur, pas seulement les chemins heureux.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire un test d'intégration qui vérifie la règle du double emprunt (409) de bout en bout, sur une base de test réinitialisée.

**Exemple simple** : ce qu'un test d'intégration voit et pas l'unitaire. L'unitaire vérifie que la fonction `emprunter` renvoie « conflit » si indisponible. L'intégration vérifie que `POST /livres/1/emprunter` répète deux fois renvoie 201 puis 409 — donc que la route, le service, la transaction et la base sont tous bien branchés.

**Raisonnement pas-à-pas** : (1) j'utilise une base de TEST réinitialisée avant la suite ; (2) j'envoie une vraie requête HTTP ; (3) je vérifie le statut ET l'état résultant ; (4) je cible la règle métier (double emprunt → 409), pas juste le chemin heureux.

**Implémentation (node:test + fetch)** :
```ts
import { test, before, beforeEach } from 'node:test';
import assert from 'node:assert/strict';

beforeEach(() => {
  // base de TEST isolée, réinitialisée -> tests rejouables et indépendants de l'ordre
  db.exec('DELETE FROM emprunts; DELETE FROM livres;');
  db.prepare('INSERT INTO livres (id, titre, disponible) VALUES (1, ?, 1)').run('Test');
});

test('emprunter deux fois le même livre : 201 puis 409', async () => {
  const url = 'http://localhost:3000/livres/1/emprunter';
  const body = { method: 'POST', headers: { 'Content-Type': 'application/json' },
                 body: JSON.stringify({ membreId: 1 }) };

  const r1 = await fetch(url, body);
  assert.equal(r1.status, 201);                       // 1er emprunt réussit

  const r2 = await fetch(url, body);
  assert.equal(r2.status, 409);                       // 2e refusé : CONFLIT métier

  // vérifier aussi l'ÉTAT de la base : le livre est bien indisponible
  const livre = db.prepare('SELECT disponible FROM livres WHERE id = 1').get();
  assert.equal(livre.disponible, 0);
});

test('emprunter un livre inexistant : 404', async () => {
  const r = await fetch('http://localhost:3000/livres/999/emprunter',
    { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: '{"membreId":1}' });
  assert.equal(r.status, 404);                          // cas d'erreur, pas juste le heureux
});
```
Le test exerce le vrai parcours HTTP → service → transaction → base, vérifie réponse ET état, cible la règle métier (409) et un cas d'erreur (404), et tourne sur une base réinitialisée — rejouable à l'infini.

## ⚠️ Erreurs fréquentes
- Tester sur la base de dev : pollution et destruction de données réelles.
- Ne tester que les chemins heureux : les bugs se cachent dans les règles métier et les cas d'erreur.
- Tests dépendants de l'ordre ou d'un état laissé par un autre : faux positifs, flakiness.
- Vérifier seulement la réponse HTTP sans l'état de la base : on rate une transaction non appliquée.

## 🏢 Cas métier
Les tests d'intégration sont ce qui donne confiance pour livrer et modifier une API en entreprise. Ils attrapent une classe de bugs invisibles aux tests unitaires : une route mal branchée, une requête qui vise la mauvaise colonne, une transaction oubliée, un statut incorrect — des erreurs de CÂBLAGE qui passent tous les tests de logique mais cassent le système réel. Sur une base modifiée par plusieurs développeurs, une suite d'intégration verte est le filet qui permet de refactorer et d'ajouter des fonctionnalités sans casser l'existant en silence. La règle de la base de test isolée est fondamentale : des tests qui polluent la base de dev, ou qui dépendent de l'ordre d'exécution, sont pires que pas de tests (faux positifs, flakiness). Les équipes matures exécutent la suite d'intégration en CI à chaque push. Savoir écrire des tests d'intégration qui vérifient réponse ET état, sur une base réinitialisée, en ciblant les règles métier, démontre une culture de qualité directement valorisée — et « comment testes-tu une API ? » est une question d'entretien récurrente.

## 🎤 Question d'entretien
**« Quelle est la différence entre un test unitaire et un test d'intégration, et lequel écris-tu pour une API ? »** → Un test UNITAIRE isole une fonction (la logique d'emprunt décide-t-elle bien « indisponible → conflit ? ») : rapide, sans base ni réseau, il localise précisément un bug de logique. Un test d'INTÉGRATION vérifie le système ASSEMBLÉ : il envoie une vraie requête HTTP qui traverse routes → services → base, et vérifie la RÉPONSE ET l'ÉTAT de la base. Il attrape les bugs de CÂBLAGE qu'aucun unitaire ne voit : route mal branchée, requête sur la mauvaise colonne, transaction oubliée, mauvais statut. Pour une API, j'écris les deux, selon la pyramide : beaucoup d'unitaires pour la logique, moins d'intégration pour les parcours critiques et les règles métier — par exemple emprunter deux fois le même livre doit renvoyer 201 puis 409, et je vérifie aussi que le livre est bien devenu indisponible en base. Règle non négociable : les tests tournent sur une base de TEST isolée, réinitialisée avant chaque suite, jamais la base de dev — pour qu'ils soient rejouables à l'infini et indépendants de l'ordre. Je cible les règles métier et les cas d'erreur, pas seulement les chemins heureux. **Relance possible** : « pourquoi ne pas tout tester en intégration ? » → parce que c'est plus lent et plus fragile ; l'unitaire localise mieux et coûte moins — d'où la pyramide.
