## 🎯 Objectif du jour
Appliquer les principes du code lisible et refactorer un de tes fichiers du mois 1.

## 📖 Cours approfondi
**Concepts abordés :** Nommage révélateur · Fonctions courtes · Niveau d'abstraction cohérent · Commentaire = POURQUOI · DRY sans excès.

Le clean code repose sur un fait : le code est LU 10 fois plus qu'il n'est écrit. Optimiser la lecture est donc rentable. Les leviers principaux : des noms qui révèlent l'INTENTION (calculerRemiseFidelite > calcRem > x), des fonctions courtes à UNE responsabilité, un niveau d'abstraction cohérent par fonction (ne pas mélanger logique métier et détails techniques dans le même bloc).

Les commentaires : ils doivent dire POURQUOI (la décision, la contrainte invisible), jamais QUOI (la ligne suivante se lit toute seule). Un commentaire qui paraphrase le code est du bruit qui se périme.

DRY (Don't Repeat Yourself) avec discernement : factoriser deux duplications identiques oui, mais forcer une abstraction sur deux choses juste RESSEMBLANTES crée un couplage pire que la duplication.

### Exercice principal
Écris ta 'code smell checklist' (10 points) SEUL, puis refactore un fichier du mois 1 avec, en documentant avant/après.

## 📦 Livrable attendu
Ta checklist clean code (10 points) + un fichier refactoré (avant/après).

## ✅ Critères de validation
- [ ] Ta checklist de 10 code smells est écrite AVANT consultation de ressources
- [ ] Un fichier du mois 1 refactoré avec diff avant/après commenté
- [ ] Chaque renommage/découpage du refactor est justifiable en une phrase

## ⚠️ Erreurs fréquentes
- Sur-commenter l'évident vs sous-commenter une décision non triviale.
- Refactorer sans tests (on casse) — d'où les tests plus tard.

## 🔗 Ressources
- Résumés de "Clean Code" (Robert Martin) — nommage et fonctions

## 🤖 Consigne d'utilisation de l'IA

## 🎤 Question d'entretien
**« Comment testes-tu ce code, et comment sais-tu qu'un test est utile ? »** → Arrange/Act/Assert sur la logique pure ; un test doit pouvoir ÉCHOUER (on sabote pour le prouver) ; isoler l'extérieur par des mocks ; tester les cas limites et d'erreur, pas seulement le chemin heureux.

## 🚀 Pourquoi ça comptera plus tard
- **En architecture** : tests, gestion d'erreurs et refactoring sont ce qui rend une architecture VIVABLE — sans eux, tout design s'effondre à la première évolution.
- **En IA** : tester un composant qui appelle un LLM (mock, replay, éval — mois 11) est une extension directe des tests d'aujourd'hui.
- **En entretien** : la qualité de ton code sous pression (nommage, découpage, cas limites) est évaluée dans CHAQUE exercice, même quand on ne le dit pas.
