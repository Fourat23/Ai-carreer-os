## 🎯 Objectif du jour
Construire une API Express structurée en 3 couches, comprendre la chaîne de middlewares.

## 📖 Cours approfondi
**Concepts abordés :** Routes · Middlewares (chaîne) · routes/services/data · Middleware de log.

Un middleware Express est une fonction (req, res, next) dans une CHAÎNE : chaque maillon traite (log, auth, parsing, validation) puis passe la main avec next(), ou court-circuite en répondant. Comprendre la chaîne = comprendre Express : l'ordre de déclaration EST l'ordre d'exécution.

La structure en 3 couches sépare les responsabilités : routes (traduire HTTP ↔ appels de fonctions), services (la logique métier, PURE autant que possible — testable sans serveur), data (la persistance). Chaque couche ne connaît que celle du dessous.

Bénéfice immédiat : la logique métier dans les services se teste comme n'importe quelle fonction (jour 62). La logique enfouie dans les routes est intestable sans lancer un serveur — c'est LE code smell des APIs de débutant.

**Modèle mental : un middleware Express est un MAILLON `(req, res, next)` dans une CHAÎNE. Chaque maillon traite (log, auth, parsing, validation) puis passe la main avec `next()`, ou court-circuite en répondant. Comprendre la chaîne, c'est comprendre Express : l'ordre de déclaration EST l'ordre d'exécution. Et la structure en 3 COUCHES (routes → services → data) sépare les responsabilités pour que la logique métier soit TESTABLE sans lancer de serveur.** Une API bien structurée n'est pas un tas de routes : c'est une chaîne de traitement et un empilement de couches aux rôles nets.

Pourquoi les middlewares existent. Beaucoup de traitements sont TRANSVERSAUX : logger chaque requête, vérifier l'authentification, parser le corps, valider les entrées, gérer les erreurs. Les répéter dans chaque route serait redondant et fragile. Le middleware factorise ces traitements en maillons réutilisables placés dans la chaîne : ils s'appliquent à toutes les routes qui les traversent. C'est la Chain of Responsibility (jour 39) appliquée au HTTP.

Comment fonctionne la chaîne, depuis les fondations. À chaque requête, Express fait passer `(req, res)` à travers les middlewares DANS L'ORDRE DE DÉCLARATION. Chaque middleware reçoit aussi `next` : il fait son travail, modifie éventuellement `req` (ex. `req.user` après auth), puis appelle `next()` pour passer au suivant — OU répond directement (ex. `res.status(401)`) pour court-circuiter la chaîne. Oublier `next()` sans répondre BLOQUE la requête (elle reste pendante). L'ordre compte : un middleware d'auth doit venir AVANT les routes protégées ; le middleware d'erreurs (à 4 arguments) vient EN DERNIER.

La structure en 3 couches, depuis les fondations. **Routes** : traduisent HTTP ↔ appels de fonctions (extraire les paramètres, appeler un service, renvoyer le statut). **Services** : la logique métier, aussi PURE que possible — testable sans serveur ni HTTP. **Data** : la persistance (SQL, fichier). Chaque couche ne connaît que celle du DESSOUS : les routes appellent les services, les services appellent la data. Le bénéfice décisif : la logique métier (services) se teste comme n'importe quelle fonction, sans monter un serveur.

La différence logique-dans-les-routes vs en couches. Mettre toute la logique dans les routes (`app.post('/x', (req,res) => { /* 50 lignes de métier + SQL */ })`) est LE code smell des API de débutant : c'est INTESTABLE sans lancer un serveur et envoyer des requêtes, ça mélange HTTP et métier, et ça se duplique. Extraire la logique dans des services purs la rend testable, réutilisable et lisible — la route redevient un simple aiguillage.

Limites et compromis. Le découpage en couches a un coût (plus de fichiers, indirection) qui ne se justifie que passé une certaine taille — pour un script jetable, c'est excessif. Trop de middlewares ou un ordre mal pensé rend le flux difficile à suivre. Et « service pur » est un idéal : certains services doivent parler à la data (effet de bord assumé) — on garde la logique DÉCISIONNELLE pure et on isole les effets.

La règle du jour : **structure l'API en middlewares (chaîne `(req,res,next)`, l'ordre de déclaration = l'ordre d'exécution, toujours next() ou répondre) et en 3 couches (routes → services → data). Sors la logique métier des routes vers des services testables sans serveur — la logique dans les routes est le code smell à éviter.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire un middleware de log maison et une route CRUD structurée en 3 couches, où la logique vit dans un service testable.

**Exemple simple** : le smell à éviter vs le bon découpage. Une route qui contient 40 lignes de métier + SQL est intestable sans serveur. Une route qui appelle `serviceCitations.ajouter(...)` délègue à une fonction pure testable en isolation. La route ne fait qu'aiguiller.

**Raisonnement pas-à-pas** : (1) le middleware de log traite (méthode, chemin, durée) puis appelle `next()` ; (2) la route extrait les paramètres et DÉLÈGUE au service ; (3) le service porte la logique (pur autant que possible) ; (4) la data persiste. Chaque couche ne connaît que celle du dessous.

**Implémentation (3 couches + middleware)** :
```ts
import express, { Request, Response, NextFunction } from 'express';

// MIDDLEWARE : un maillon (req,res,next) -> traite puis next()
function logger(req: Request, res: Response, next: NextFunction): void {
  const debut = Date.now();
  res.on('finish', () => {
    console.log(`${req.method} ${req.path} -> ${res.statusCode} (${Date.now() - debut}ms)`);
  });
  next();                              // sans next() : requête bloquée
}

// COUCHE DATA : persistance (ici en mémoire)
const db: Citation[] = [];
const dataCitations = {
  all: () => db,
  add: (c: Citation) => { db.push(c); return c; },
};

// COUCHE SERVICE : logique métier, testable SANS serveur
const serviceCitations = {
  lister: () => dataCitations.all(),
  ajouter: (texte: string): Citation => {
    if (!texte?.trim()) throw new Error('texte requis');   // règle métier
    const id = dataCitations.all().length + 1;
    return dataCitations.add({ id, texte });
  },
};

// COUCHE ROUTES : traduit HTTP <-> service, aucune logique métier
const app = express();
app.use(express.json());
app.use(logger);                                    // l'ordre compte
app.get('/citations', (_req, res) => res.json(serviceCitations.lister()));
app.post('/citations', (req, res) => {
  const c = serviceCitations.ajouter(req.body.texte); // DÉLÈGUE au service
  res.status(201).json(c);
});
```
Le service `ajouter` se teste comme une fonction pure (`serviceCitations.ajouter('x')`), sans lancer le serveur — impossible si la logique était dans la route.

## ⚠️ Erreurs fréquentes
- Mettre toute la logique dans les routes : intestable sans serveur, mélange HTTP et métier, duplication.
- Oublier next() dans un middleware sans répondre : la requête reste bloquée.
- Mal ordonner les middlewares (auth après la route protégée, erreurs pas en dernier) : comportement incorrect.
- Coupler les couches à contre-sens (un service qui connaît le req/res HTTP) : perte de testabilité.

## 🏢 Cas métier
La structure en couches et la maîtrise des middlewares sont des marqueurs de maturité back directement évalués en entreprise. Une API où la logique métier est isolée dans des services purs est TESTABLE (tests unitaires rapides sans serveur ni base), MAINTENABLE (on change la persistance sans toucher le métier, on modifie une règle sans risquer les routes) et LISIBLE (chaque couche a un rôle net). À l'inverse, l'API « spaghetti » où tout est dans les routes est le cauchemar récurrent des équipes : impossible à tester unitairement, chaque modification est risquée, la duplication prolifère. Les middlewares transversaux (log, auth, gestion d'erreurs centralisée, rate limiting) sont la façon standard de gérer les préoccupations communes proprement. Savoir structurer une API en couches et expliquer la chaîne de middlewares (ordre, next, court-circuit) est un attendu des postes back et un sujet d'entretien fréquent (« comment organises-tu une API Express ? »).

## 🎤 Question d'entretien
**« Comment organises-tu une API Express, et comment fonctionne la chaîne de middlewares ? »** → Je la structure en 3 couches. Les ROUTES traduisent HTTP ↔ appels de fonctions : elles extraient les paramètres, appellent un service, renvoient le statut — aucune logique métier. Les SERVICES portent la logique, aussi PURE que possible, ce qui les rend testables sans serveur ni HTTP. La couche DATA gère la persistance. Chaque couche ne connaît que celle du dessous. Le bénéfice clé : je teste ma logique métier comme n'importe quelle fonction, sans monter un serveur — alors que la logique enfouie dans les routes est le code smell classique, intestable et dupliqué. Pour les middlewares : chacun est une fonction `(req, res, next)`, maillon d'une chaîne. Il traite (log, auth, validation), modifie éventuellement `req`, puis appelle `next()` pour passer au suivant, ou répond pour court-circuiter. L'ORDRE de déclaration est l'ordre d'exécution : l'auth doit venir avant les routes protégées, le middleware d'erreurs (4 arguments) vient en dernier. Oublier `next()` sans répondre bloque la requête. **Relance possible** : « où mets-tu la validation et l'authentification ? » → dans des middlewares dédiés, placés avant les routes concernées : ils factorisent ces préoccupations transversales au lieu de les répéter dans chaque route.
