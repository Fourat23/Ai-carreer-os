## 🎯 Objectif du jour
Comprendre requête/réponse, méthodes, statuts, headers, avec curl et les DevTools.

## 📖 Cours approfondi
**Concepts abordés :** Requête/réponse · GET/POST/PUT/PATCH/DELETE · Statuts 2xx/3xx/4xx/5xx · Headers · Idempotence · DNS→TCP→TLS→HTTP.

HTTP est un protocole texte requête/réponse SANS ÉTAT : chaque requête est autonome et contient tout (méthode, URL, headers, corps). Le serveur répond un statut + headers + corps, et oublie tout.

Les méthodes portent une SÉMANTIQUE : GET lit (sans effet de bord — jamais de modification sur un GET), POST crée, PUT remplace, PATCH modifie partiellement, DELETE supprime. GET/PUT/DELETE sont IDEMPOTENTES : les rejouer ne change rien de plus — propriété cruciale pour les retries réseau.

Les statuts sont un langage : 2xx succès (200 ok, 201 créé, 204 sans contenu), 3xx redirection, 4xx erreur du CLIENT (400 requête invalide, 401 non authentifié, 403 interdit, 404 absent, 409 conflit), 5xx erreur du SERVEUR. Choisir le bon statut EST de la conception d'API.

**Modèle mental : HTTP est un protocole texte REQUÊTE/RÉPONSE SANS ÉTAT. « Sans état » signifie que chaque requête est AUTONOME et contient TOUT ce qu'il faut pour être traitée (méthode, URL, headers, corps) — le serveur répond puis OUBLIE tout. Les méthodes (GET/POST/PUT/PATCH/DELETE) portent une SÉMANTIQUE, et les statuts (2xx/3xx/4xx/5xx) forment un LANGAGE : choisir le bon statut et la bonne méthode EST de la conception d'API, pas un détail.** Comprendre HTTP en profondeur, c'est parler la langue de tout le web — chaque API, chaque page, chaque appel réseau.

Pourquoi HTTP est sans état, et ce que ça implique. Rendre chaque requête autonome permet de faire PASSER À L'ÉCHELLE : n'importe quel serveur peut traiter n'importe quelle requête, sans mémoire partagée, donc on peut en ajouter à volonté (répartition de charge). Le prix : l'état (qui suis-je, mon panier) doit être TRANSPORTÉ à chaque requête — via un token d'authentification, un cookie, un identifiant. C'est pourquoi l'authentification se rejoue à chaque appel : le serveur ne « se souvient » de rien.

Les méthodes et leur sémantique, depuis les fondations. GET LIT (jamais d'effet de bord — un GET ne doit RIEN modifier). POST CRÉE (ou déclenche une action). PUT REMPLACE une ressource entière. PATCH MODIFIE partiellement. DELETE SUPPRIME. Cette sémantique est un CONTRAT : un client, un cache, un proxy s'y fient. Un GET qui modifierait des données casserait les caches et les attentes de tout l'écosystème.

L'idempotence, un concept clé. Une méthode est IDEMPOTENTE si la rejouer produit le même effet que l'appeler une fois. GET, PUT, DELETE le sont (relire, re-remplacer, re-supprimer ne change rien de plus) ; POST ne l'est PAS (deux POST créent deux ressources). C'est CRUCIAL pour les RETRIES réseau : si une réponse se perd, on peut rejouer sans risque une requête idempotente, pas un POST (d'où les mécanismes d'idempotency-key pour les paiements).

Les statuts comme langage, et les distinctions à ne pas rater. 2xx SUCCÈS (200 ok, 201 créé, 204 sans contenu). 3xx REDIRECTION. 4xx erreur du CLIENT (400 requête invalide, 401 NON AUTHENTIFIÉ — « je ne sais pas qui tu es », 403 INTERDIT — « je sais qui tu es mais tu n'as pas le droit », 404 absent, 409 conflit). 5xx erreur du SERVEUR. La confusion classique 401 vs 403 trahit une compréhension superficielle ; renvoyer 200 pour tout (avec un « error » dans le corps) prive les clients et les outils du langage des statuts.

Le cycle complet, pour situer. Taper une URL déclenche : DNS (nom → IP) → TCP (connexion) → TLS (chiffrement en HTTPS) → HTTP (requête/réponse). Savoir dessiner cette chaîne montre qu'on comprend ce qui se passe « sous » l'API.

Limites et compromis. Le sans-état simplifie la montée en charge mais reporte la gestion de l'état sur le client/token. Choisir le bon statut demande de la rigueur (la tentation du 200-pour-tout est réelle). HTTP/1.1 vs HTTP/2 (multiplexage) sont des raffinements de performance à connaître de nom. Et un statut mal choisi n'empêche pas le fonctionnement — il dégrade l'interopérabilité, silencieusement.

La règle du jour : **HTTP est sans état (chaque requête autonome porte tout, le serveur oublie), les méthodes portent une sémantique (GET lit sans effet de bord, POST crée…), l'idempotence (GET/PUT/DELETE) sécurise les retries, et les statuts sont un langage (distingue 401 « non authentifié » de 403 « interdit »). Choisir méthode et statut EST de la conception d'API.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : explorer une API avec `curl` — un GET, un POST JSON, et l'observation des statuts — pour voir HTTP « en vrai ».

**Exemple simple** : la différence de statuts qui parle. Un GET sur une ressource existante → 200. Un GET sur une ressource absente → 404. Un POST qui crée → 201. Une requête sans jeton → 401 ; avec jeton mais sans droit → 403. Le statut RÉSUME le résultat sans lire le corps.

**Raisonnement pas-à-pas** : (1) un GET lit (aucun effet de bord) et renvoie 200 + un corps ; (2) un POST envoie un corps JSON (header `Content-Type`) et renvoie 201 + la ressource créée ; (3) j'observe le statut et les headers avec `-i` ; (4) je distingue 401 (non authentifié) de 403 (interdit).

**Exploration curl** :
```bash
# GET : lire (idempotent, sans effet de bord). -i affiche statut + headers
curl -i https://api.exemple.dev/taches/1
# -> HTTP/1.1 200 OK ... { "id": 1, "titre": "..." }

# GET absent -> 404 (le statut dit "pas trouvé", pas besoin de lire le corps)
curl -i https://api.exemple.dev/taches/9999      # -> 404 Not Found

# POST : créer. Content-Type + corps JSON. Non idempotent (2 POST = 2 créations)
curl -i -X POST https://api.exemple.dev/taches \
     -H "Content-Type: application/json" \
     -d '{ "titre": "Apprendre HTTP" }'
# -> HTTP/1.1 201 Created ... { "id": 42, "titre": "Apprendre HTTP" }

# Sans jeton -> 401 (non authentifié) ; avec jeton sans droit -> 403 (interdit)
curl -i https://api.exemple.dev/admin              # -> 401 Unauthorized
curl -i -H "Authorization: Bearer TOKEN_USER" https://api.exemple.dev/admin  # -> 403 Forbidden
```
Chaque statut est une information exploitable par le client ; répondre 200 partout la détruirait. Rejouer le GET est sûr (idempotent) ; rejouer le POST créerait un doublon.

## ⚠️ Erreurs fréquentes
- Répondre 200 pour tout : les statuts sont de l'information exploitable par les clients et les outils.
- Confondre 401 (non authentifié) et 403 (interdit) : distinction sémantique essentielle.
- Croire qu'un GET peut modifier des données : il doit être sans effet de bord (contrat des caches/proxies).
- Ignorer l'idempotence : rejouer un POST après une réponse perdue crée un doublon.

## 🏢 Cas métier
HTTP est le protocole de TOUT le web : chaque appel d'API, chaque page chargée, chaque intégration entre services passe par lui. Maîtriser sa sémantique est un prérequis absolu pour le développement back et l'intégration. Concrètement : le caractère sans état fonde l'architecture des services scalables (on ajoute des serveurs derrière un répartiteur de charge parce qu'aucun ne détient d'état) ; l'idempotence est vitale pour la fiabilité (les systèmes de paiement utilisent des idempotency-keys pour qu'un retry après une réponse perdue ne débite pas deux fois) ; le choix des statuts détermine si une API est correctement consommable par d'autres équipes et outils (monitoring, caches, clients générés). La confusion 401/403 ou le « 200 pour tout » sont des red flags en revue de code et en entretien back. Savoir dessiner le cycle DNS→TCP→TLS→HTTP montre qu'on comprend l'infrastructure sous l'API, pas seulement l'API.

## 🎤 Question d'entretien
**« Explique ce que "HTTP est sans état" implique, et la différence entre 401 et 403. »** → Sans état signifie que chaque requête est AUTONOME : elle contient tout ce qu'il faut (méthode, URL, headers, corps), le serveur la traite puis OUBLIE tout. La conséquence pratique est double : d'un côté ça permet de passer à l'échelle — n'importe quel serveur peut traiter n'importe quelle requête, donc on en ajoute derrière un répartiteur de charge ; de l'autre, l'état (mon identité, mon panier) doit être TRANSPORTÉ à chaque requête, via un token ou un cookie, et l'authentification se rejoue à chaque appel. Pour 401 vs 403 : 401 veut dire « non AUTHENTIFIÉ » — le serveur ne sait pas qui tu es (jeton absent ou invalide) ; 403 veut dire « INTERDIT » — il sait qui tu es, mais tu n'as pas le droit d'accéder à cette ressource. Plus largement, les statuts sont un langage (2xx succès, 4xx erreur client, 5xx erreur serveur) et choisir le bon EST de la conception d'API — répondre 200 pour tout prive les clients et les outils de cette information. **Relance possible** : « pourquoi l'idempotence compte-t-elle ? » → parce qu'une méthode idempotente (GET/PUT/DELETE) peut être rejouée sans risque après une réponse réseau perdue, contrairement à POST qui créerait un doublon — d'où les idempotency-keys pour les paiements.
