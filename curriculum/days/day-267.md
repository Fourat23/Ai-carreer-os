## 🎯 Objectif du jour
Établir la référence.

## 📖 Cours approfondi
**Modèle mental : la baseline chiffrée est le point zéro d'un projet évalué — sans elle, « j'ai amélioré » est une opinion, avec elle, c'est une mesure.** Le Projet 6 (DocQA évalué) est ta pièce maîtresse RAG, et il commence non par du code mais par une PHOTO chiffrée de l'état actuel. Tout ce que tu construis cette semaine (deux améliorations pilotées, guardrails, rapport) se mesurera CONTRE cette baseline. Un projet évalué sans baseline est un projet qui raconte une histoire non vérifiable.

Ce que « établir la baseline » signifie rigoureusement :
1. **Le système figé** : la configuration actuelle (retrieval-v2 du jour 251, prompt de génération actuel, guardrails actuels) — rien ne bouge pendant la mesure. C'est l'état « avant ».
2. **Le harnais complet** : `rag eval` (jour 257) sur le golden set (jour 253), produisant TOUTES les métriques — retrieval (rappel@k, MRR), génération (fidélité, pertinence, exactitude), sécurité (suite adverse, jour 264), plus latence et coût. La baseline est multidimensionnelle : une amélioration qui gagne en exactitude mais dégrade la latence ou la sécurité doit être VISIBLE.
3. **L'enregistrement daté et versionné** : le rapport de baseline est sauvegardé (config + golden version + date + tous les scores) — c'est la référence immuable contre laquelle les jours 268-269 se compareront via `rag eval --compare`.
4. **La lecture diagnostique** : la baseline ne sert pas qu'à mesurer le progrès, elle IDENTIFIE les chantiers. Où sont les points faibles ? (Tes découvertes récurrentes : les synthèses résistent — jours 244, 249 ; certains types ont un rappel@k bas.) La baseline priorise les deux améliorations à venir — on attaque ce qui est faible ET mesurable, pas ce qui est amusant.

Le piège méthodologique central : la tentation de « corriger un petit truc » pendant qu'on établit la baseline. NON — la baseline mesure l'état existant, intact. Chaque correction pendant la mesure invalide le point de comparaison. On observe d'abord (comme au jour 225), on améliore ensuite (jours 268-269), et le contraste avant/après raconte l'histoire chiffrée du projet.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : la baseline chiffrée multidimensionnelle de DocQA, enregistrée et lue.

**Raisonnement** : figer le système, passer le harnais complet, enregistrer, diagnostiquer les chantiers — sans rien corriger.

**Le protocole** :
```
1. Fige la config actuelle (retrieval-v2 + prompt actuel + guardrails).
2. rag eval --config baseline --adversarial → rapport complet :
```
```
=== BASELINE DocQA — 2026-XX-XX — golden v1.1 — config retrieval-v2 ===
RETRIEVAL   rappel@3 0,85 · MRR 0,79
GÉNÉRATION  fidélité 0,88 · pertinence 0,92 · exactitude 0,81
  par type  factuelles 0,92 · reformulées 0,83 · SYNTHÈSE 0,50 ← faible
SÉCURITÉ    14/15 attaques neutralisées (adv-15 ancrage : à traiter)
PERF        p95 1,1 s · coût/question 0,0081 €

CHANTIERS PRIORISÉS (par faiblesse mesurée) :
  1. Synthèses à 0,50 (exactitude) — rappel@k correct dessus → c'est la
     GÉNÉRATION multi-chunks, pas le retrieval (confirmé jours 244/249)
     → amélioration 1 : prompt de génération pour les synthèses (jour 268)
  2. adv-15 (une injection d'ancrage passe) → amélioration sécurité (jour 268/270)
  3. reformulées à 0,83 — marge de retrieval → amélioration 2 candidate (jour 269)
```

**Explication** : la lecture diagnostique transforme la baseline en FEUILLE DE ROUTE — les deux améliorations des jours 268-269 sortent des faiblesses MESURÉES, pas d'une envie. La confirmation « synthèses = génération, pas retrieval » vient de trois sources concordantes (jours 244, 249, et maintenant la baseline). **Variante** : formule pour chaque chantier une HYPOTHÈSE testable (« améliorer le prompt de synthèse fera passer l'exactitude synthèse de 0,50 à ~0,70 sans dégrader les autres types ») — tu valideras ou réfuteras demain, c'est la démarche scientifique.

## 🏢 Cas métier
Tout projet ML sérieux en entreprise commence par une baseline : sans point de départ chiffré, impossible de justifier le temps investi (« on a passé deux semaines, pour quel gain ? »). La baseline est ce qui rend le travail d'amélioration DÉFENDABLE devant un manager — « exactitude sur les synthèses passée de 0,50 à 0,72, sécurité de 14/15 à 15/15, latence stable » est un bilan qui se présente. Les développeurs qui savent établir et présenter une baseline transforment leur travail technique en valeur démontrable — une compétence de communication autant que d'ingénierie.

## 🎤 Question d'entretien
**« Tu dois améliorer un système existant : par quoi commences-tu ? »** → Par une baseline chiffrée multidimensionnelle : je fige le système actuel et je passe le harnais complet — retrieval, génération par type, sécurité, latence, coût — enregistré et daté. Elle sert deux fonctions : le point de comparaison immuable pour prouver le progrès, et le diagnostic qui PRIORISE les chantiers (on attaque ce qui est faible et mesurable). Et je ne corrige RIEN pendant la mesure — chaque correction invalide le point de comparaison. On observe d'abord, on améliore ensuite, le contraste raconte l'histoire.
