## 🎯 Objectif du jour
Finaliser la pièce maîtresse.

## 📖 Cours approfondi
**Modèle mental : un projet non documenté et non démontrable n'existe pas pour un recruteur — le README, les ADR et la démo sont ce qui rend ton travail LISIBLE de l'extérieur.** Tu as construit et évalué DocQA ; aujourd'hui tu le rends présentable en 3 minutes à quelqu'un qui ne l'a jamais vu. C'est la dernière ligne droite qui transforme du code en PIÈCE DE PORTFOLIO — et c'est souvent ce qui distingue deux candidats à compétence égale : celui dont on comprend le projet en 2 minutes, et celui dont le repo est illisible.

Les trois livrables et leur rôle distinct :
1. **Le README** raconte l'HISTOIRE : quel problème, quelle approche, quels RÉSULTATS CHIFFRÉS (le rapport du jour 271 en résumé), comment lancer en une commande, quelles limites. Un recruteur lit le README en 90 secondes et décide s'il creuse. Il commence par le POURQUOI (le problème métier), pas par la stack technique.
2. **Les ADR** (Architecture Decision Records) figent les DÉCISIONS et leur pourquoi : stockage vectoriel, stratégie de chunking, modèle, approche d'évaluation. Tu en as déjà (ADR-006, jour 230) ; ici tu consolides les 3 décisions les plus structurantes. Une ADR montre que tu as ARBITRÉ, pas juste codé — c'est ce que cherche un lead.
3. **La démo de 3 minutes** montre le système VIVANT : une question normale (réponse + citations vérifiables), une question piège (refus honnête), l'état du corpus. Enregistrée, fluide, sans hésitation. La démo prouve que « ça marche » là où le README l'affirme.

La règle qui gouverne les trois : ils s'adressent à un lecteur EXTÉRIEUR pressé, pas à toi. Le test : quelqu'un qui n'a jamais vu DocQA comprend-il, en lisant le README et regardant la démo, ce que fait le système, à quel point il est bon, et comment le lancer — SANS te parler ? Si oui, ton projet est présentable. Sinon, c'est un projet que seul toi comprends, donc invisible sur le marché.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : README + 3 ADR + démo 3 min qui rendent DocQA présentable à froid.

**Exemple simple** : la première ligne du README n'est pas « DocQA utilise Chroma et FTS5 » mais « DocQA répond à des questions sur VOS documents en citant ses sources, et refuse honnêtement quand il ne sait pas ». Le POURQUOI avant la stack.

**Raisonnement pas-à-pas** : écrire pour un lecteur extérieur pressé — histoire d'abord (README), décisions ensuite (ADR), preuve vivante enfin (démo), puis TEST du regard neuf.

**Structure** :
```
README.md
  1. Le problème (métier, en 2 phrases)
  2. Ce que fait DocQA (+ 1 capture ou GIF de la démo)
  3. Résultats chiffrés (exactitude 0,87, sécurité 15/15 — résumé du rapport j.271)
  4. Lancer en 1 commande (make run / python docqa.py)
  5. Architecture (schéma) + liens vers les ADR
  6. Limites assumées
docs/adr/
  ADR-006 stockage vecteurs · ADR-007 chunking · ADR-008 évaluation
  (chaque ADR : contexte → options → décision → conséquences → révision si)
demo (3 min, enregistrée) :
  question normale → réponse citée → clic sur une source (vérifiable)
  question hors corpus → refus honnête
  rag status → état du corpus
```

**Mini-quiz** : (a) Par quoi commence un bon README ? (b) Que prouve une ADR qu'un commit ne prouve pas ? (c) Quel est le test de qualité du README ?
→ (a) le problème métier, pas la stack ; (b) que tu as ARBITRÉ entre des options (le pourquoi), pas juste choisi ; (c) un inconnu comprend le projet sans te parler.

**Variante** : fais lire ton README à quelqu'un qui ne connaît pas le projet et chronomètre — comprend-il en 90 secondes quoi, à quel point c'est bon, et comment lancer ? Ses questions sont tes trous à combler.

## ⚠️ Erreurs fréquentes
- README qui commence par la stack technique : le lecteur ne sait pas POURQUOI le projet existe — commence par le problème métier.
- ADR qui ne liste que la décision sans les options écartées : sans l'arbitrage, elle ne prouve pas la pensée d'architecte.
- Démo non enregistrée ou hésitante : « ça marche sur ma machine » ne convainc pas — une démo fluide de 3 min, oui.
- Pas de résultats chiffrés dans le README : le lecteur ne peut pas juger à quel point le système est bon.

## 🏢 Cas métier
Les recruteurs techniques passent 30 à 90 secondes sur un repo GitHub avant de décider s'ils creusent : un README qui commence par le problème et montre des résultats chiffrés capte cette fenêtre ; un README « TODO » ou noyé dans la config la gâche. À compétence égale, le candidat dont le projet se comprend en 2 minutes passe l'entretien technique que l'autre n'obtient pas. Le README et la démo ne sont pas de la cosmétique : ils sont l'INTERFACE entre ton travail et le marché.

## 🎤 Question d'entretien
**« Montre-moi un projet dont tu es fier. »** → Je déroule DocQA en 3 minutes : le problème (répondre sur des documents en citant, refuser quand on ne sait pas), la démo vivante (réponse citée vérifiable, refus honnête sur une question piège), les résultats chiffrés (exactitude 0,87, sécurité 15/15, rapport reproductible), et 2-3 décisions d'architecture justifiées (ADR). Un README qui commence par le pourquoi, une démo enregistrée fluide, des ADR qui montrent que j'ai arbitré. L'objectif : que tu comprennes la valeur SANS que j'aie à tout expliquer.
