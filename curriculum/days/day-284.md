## 🎯 Objectif du jour
Réduire coûts et latence.

## 📖 Cours approfondi
**Modèle mental : le cache exploite une propriété simple — beaucoup d'appels LLM sont IDENTIQUES, et re-payer la même réponse est un gaspillage pur.** En développement (tu relances 50 fois le même workflow), en production (des utilisateurs posent les mêmes questions, un système réutilise le même prompt système), une part significative des appels reproduit un couple (prompt, modèle) déjà calculé. Le cache stocke la réponse la première fois et la ressert instantanément et gratuitement les suivantes. C'est le levier coût/latence le plus simple et le plus rentable — quand il est applicable.

Le mécanisme :
1. **La clé** : `hash(prompt + modèle + paramètres)`. Deux appels sont « identiques » s'ils ont le MÊME prompt complet (system + messages), le même modèle, les mêmes paramètres. Le hash est la clé de cache ; la réponse est la valeur.
2. **Le stockage** : un dictionnaire en mémoire (durée de vie du process), un fichier/SQLite (persiste entre les runs — précieux en dev), ou un cache distribué (production multi-instances). Le choix suit le besoin ; SQLite suffit largement pour commencer (tes acquis SQL, mois 5).
3. **La condition de validité — CRUCIALE** : le cache n'est correct QUE si le même prompt DOIT donner la même réponse. Cela impose **température 0** (jour 199) : à température élevée, la variabilité est VOULUE, et cacher fige un tirage aléatoire comme s'il était LA réponse — bug subtil. On ne cache que le déterministe (extraction, classification, réponses factuelles à temp 0), jamais le créatif où la diversité est le but.
4. **La mesure — le taux de hit** : la fraction d'appels servis par le cache. C'est l'indicateur qui dit si le cache VAUT le coup : un taux de hit de 40 % signifie 40 % d'appels en moins (coût et latence). Un cache avec 2 % de hit ne sert à rien ; à 40 %, c'est un levier majeur.

Les limites à connaître : le cache n'aide QUE sur les appels répétés (un système où chaque prompt est unique — car il contient une question différente — a un faible taux de hit, sauf sur les sous-parties communes) ; l'invalidation (si le corpus change, une réponse cachée peut devenir obsolète — d'où lier la clé à la version de l'index) ; et le prompt caching côté fournisseur (certains APIs cachent le PRÉFIXE commun d'un prompt, ex. un long system prompt — un mécanisme complémentaire, géré côté serveur). Mesurer le taux de hit AVANT de conclure que le cache aide est le réflexe d'ingénieur.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : un cache d'appels LLM (fichier/SQLite), clé = hash(prompt+modèle), taux de hit mesuré.

**Exemple simple** : le cache le plus simple est un dict — `if cle in cache: return cache[cle]` avant l'appel, `cache[cle] = reponse` après. Tout le reste (persistance, mesure) est du raffinement.

**Raisonnement pas-à-pas** : envelopper l'appel LLM d'un cache clé-valeur, persister, mesurer le taux de hit, et RESTREINDRE à température 0.

**Implémentation** :
```python
import hashlib, sqlite3, json

def cle_cache(prompt, modele, params):
    brut = json.dumps({"p": prompt, "m": modele, **params}, sort_keys=True)
    return hashlib.sha256(brut.encode()).hexdigest()

_hits, _miss = 0, 0
def llm_call_cache(prompt, modele="...", temp=0, **params):
    assert temp == 0, "Cache valide uniquement à température 0 !"   # garde-fou
    cle = cle_cache(prompt, modele, {"temp": temp, **params})
    if (cached := cache_lire(cle)) is not None:
        global _hits; _hits += 1
        return cached                                  # HIT : gratuit, instantané
    reponse = appel_llm_reel(prompt, modele, temp, **params)
    cache_ecrire(cle, reponse)                         # MISS : on stocke
    global _miss; _miss += 1
    return reponse

def taux_hit(): return _hits / (_hits + _miss)         # l'indicateur clé
```

**Mini-quiz** : (a) Pourquoi le cache impose-t-il la température 0 ? (b) Que mesure le taux de hit et pourquoi est-il crucial ? (c) Sur quel type d'appels le cache est-il inutile ?
→ (a) sinon la variabilité voulue est figée sur un tirage aléatoire — bug ; (b) la fraction d'appels évités : il dit si le cache vaut le coup (40 % = levier, 2 % = inutile) ; (c) les appels uniques (chaque prompt différent) et le créatif (diversité voulue).

**Variante** : mesure le taux de hit de ton cache sur un workflow relancé 3 fois en dev, puis sur un ensemble de questions utilisateur variées — le taux de hit diffère radicalement (élevé en dev, faible sur des questions uniques). Tu VOIS quand le cache aide.

## ⚠️ Erreurs fréquentes
- Cacher à température > 0 : on fige un tirage aléatoire comme s'il était LA réponse — la variabilité voulue disparaît, bug subtil.
- Ne pas mesurer le taux de hit : un cache à 2 % de hit ne sert à rien ; sans la mesure, on croit optimiser sans effet.
- Clé incomplète (oublier le modèle ou les paramètres) : deux appels réellement différents partagent une entrée → mauvaise réponse servie.
- Ignorer l'invalidation : une réponse cachée devient obsolète si le corpus change — lier la clé à la version de l'index quand c'est pertinent.

## 🏢 Cas métier
Le cache LLM est un levier de coût standard : en développement, il rend les itérations gratuites et instantanées (relancer un workflow de test ne re-paie pas) ; en production, sur les systèmes à requêtes répétitives (FAQ, classifications récurrentes), il coupe une fraction significative de la facture. Les équipes qui cachent le déterministe économisent sans effort ; celles qui re-paient chaque appel identique gaspillent. Mais la nuance qui distingue l'ingénieur : savoir que le cache n'aide QUE sur le répété et le déterministe — mesurer le taux de hit avant de conclure, plutôt que de supposer que « le cache aide toujours ».
