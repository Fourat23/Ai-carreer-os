## 🎯 Objectif du jour
Le LLM qui agit.

## 📖 Cours approfondi
**Modèle mental : le LLM ne fait rien — il DEMANDE.** Le function calling ne donne aucun pouvoir au modèle : il lui permet d'émettre une demande structurée (« appelle `meteo(ville="Paris")` »), que TON code exécute (ou refuse), avant de renvoyer le résultat au modèle pour qu'il formule la réponse. Le modèle propose des actions ; ton code garde le monopole de l'exécution. Cette frontière est LE concept du jour — et la base de sécurité de tout agent.

La boucle canonique :
1. Tu déclares les outils (nom, description, schéma des paramètres — la DESCRIPTION est cruciale : c'est elle que le modèle lit pour choisir).
2. Le modèle répond soit du texte, soit une demande d'appel d'outil avec ses arguments.
3. Ton code VALIDE les arguments (schéma, bornes — le jour 205 ressert : un argument d'outil est une sortie structurée comme une autre), exécute, et renvoie le résultat.
4. Le modèle intègre le résultat et répond — ou redemande un outil (d'où : boucle avec LIMITE d'itérations).

Les cas qui séparent le POC du système sérieux : la question qui ne nécessite AUCUN outil (le modèle doit savoir ne pas appeler), l'outil qui échoue (le résultat d'erreur repart au modèle, qui doit le dire à l'utilisateur au lieu d'inventer), les arguments invalides (validés, refusés, redemandés). Un « assistant à outils » sans ces trois cas gérés est une démo, pas un composant.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : assistant à 2 outils (météo mockée, calculatrice), boucle complète.

**Raisonnement** : la boucle requête→tool_call→exécution→réponse, avec validation et limite d'itérations.

**Squelette** :
```python
OUTILS = [
  {"name": "meteo", "description": "Météo actuelle d'une ville. À utiliser UNIQUEMENT si l'utilisateur demande la météo.",
   "input_schema": {"type": "object", "properties": {"ville": {"type": "string"}}, "required": ["ville"]}},
  {"name": "calcul", "description": "Évalue une expression arithmétique simple.",
   "input_schema": {"type": "object", "properties": {"expression": {"type": "string"}}, "required": ["expression"]}},
]
def executer(nom, args):            # TON code : valide puis exécute
    if nom == "meteo":  return meteo_mock(args["ville"])       # dict figé
    if nom == "calcul": return calcul_sur(args["expression"])   # PAS eval() !

messages = [{"role": "user", "content": question}]
for _ in range(5):                   # limite anti-boucle-infinie
    rep = client.messages.create(model=..., tools=OUTILS, messages=messages, max_tokens=500)
    if rep.stop_reason != "tool_use":
        break                        # réponse finale en texte
    # sinon : extraire le tool_call, exécuter, renvoyer le tool_result
```

**Explication** : `stop_reason == "tool_use"` signale la demande d'outil ; le résultat repart dans messages comme `tool_result`. Le calcul n'utilise JAMAIS `eval()` sur une chaîne issue du LLM (exécuter du code proposé par le modèle = la faille classique) — un petit parseur ou une lib sûre. **Variante** : pose « quelle heure est-il ? » (aucun outil ne convient) — l'assistant doit répondre qu'il ne peut pas, pas appeler la météo au hasard.

## 🏢 Cas métier
Tous les produits « assistant qui agit » (réserver, chercher, commander) sont cette boucle avec plus d'outils. Et l'actualité sécurité 2024-2025 (agents manipulés par injection de prompt) rend la frontière « le modèle demande, mon code valide et exécute » CENTRALE en entretien : savoir dire où passe la frontière de confiance te distingue immédiatement.

## 🎤 Question d'entretien
**« Explique le function calling, et où est la frontière de sécurité. »** → Je déclare des outils avec schémas ; le modèle émet une DEMANDE d'appel structurée ; mon code valide les arguments, exécute et renvoie le résultat ; le modèle formule la réponse. La frontière : le modèle ne touche jamais l'exécution — tout ce qu'il propose est validé côté code, avec limite d'itérations et gestion des échecs d'outil.
