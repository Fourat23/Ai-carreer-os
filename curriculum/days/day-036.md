## 🎯 Objectif du jour
Installer TS, comprendre pourquoi typer, annoter les types de base, lire les erreurs du compilateur comme des alliées.

## 📖 Cours approfondi
**Concepts abordés :** tsc / tsconfig · Types primitifs · Inférence · any (à fuir) vs unknown · strict mode.

TypeScript ajoute un vérificateur de types AU-DESSUS de JavaScript : le code s'exécute pareil, mais un compilateur (tsc) relit tout avant et signale les incohérences (appeler une fonction avec le mauvais type, accéder à une propriété qui n'existe pas, oublier un cas null).

Le typage est une DOCUMENTATION VÉRIFIÉE : la signature `function payer(montant: number): Recu` dit le contrat, et le compilateur garantit qu'il est respecté partout, pour toujours. En mode strict, les null/undefined implicites deviennent des erreurs : la moitié des bugs du mois 1 auraient été attrapés à la compilation.

`any` désactive la vérification (à bannir) ; `unknown` dit « je ne sais pas encore » et FORCE une validation avant usage — c'est la bonne réponse aux données externes.

**Modèle mental : TypeScript ne change RIEN à ce que ton code fait — il ajoute un CONTRAT vérifié À LA COMPILATION, par-dessus JavaScript. Le compilateur `tsc` est un relecteur infatigable qui lit tout ton code AVANT exécution et signale les incohérences (mauvais type d'argument, propriété inexistante, cas `null` oublié). Le typage est une documentation qui ne peut pas mentir, parce que la machine la vérifie partout, pour toujours. Les erreurs `tsc` ne sont pas des obstacles : ce sont des bugs futurs attrapés gratuitement.** Apprendre à LIRE ces erreurs est la vraie compétence — plus que la syntaxe des annotations.

Pourquoi le typage statique existe. JavaScript est dynamiquement typé : une variable peut être un nombre puis une chaîne, et une faute (appeler `.toUpperCase()` sur un nombre) n'explose qu'À L'EXÉCUTION, parfois en production chez l'utilisateur. Le coût d'un bug croît avec le temps avant sa détection. Le typage statique DÉPLACE la détection au plus tôt — pendant que tu écris, dans l'éditeur — là où corriger coûte quelques secondes. C'est la même logique que les tests, mais gratuite et permanente.

Comment ça fonctionne, depuis les fondations. Tu ANNOTES les contrats aux frontières (signatures de fonctions, formes d'objets) : `function payer(montant: number): Recu`. Le compilateur PROPAGE ces types par INFÉRENCE : tu n'écris pas `const total: number = a + b`, il déduit `number` seul. Puis il VÉRIFIE la cohérence de tout le graphe d'appels. À l'exécution, tout ce typage DISPARAÎT (transpilation en JS) : c'est un filet de sécurité au développement, à coût zéro à l'exécution.

La différence entre les acteurs, pour ne pas confondre. `tsc` VÉRIFIE et transpile ; `node` (ou `tsx`) EXÉCUTE. Une erreur `tsc` n'est PAS une erreur d'exécution : c'est un avertissement anticipé. `any` DÉSACTIVE le vérificateur pour une valeur — c'est renoncer à l'outil, à bannir. `unknown` dit « type inconnu pour l'instant » et FORCE une vérification (narrowing) avant tout usage : c'est la bonne réponse aux données externes (JSON d'une API, saisie utilisateur) dont on ne connaît pas la forme à la compilation.

Le mode strict et son intérêt. `strict: true` active notamment `strictNullChecks` : `null` et `undefined` ne sont plus assignables implicitement partout. Résultat : le compilateur t'OBLIGE à traiter le cas « la valeur pourrait être absente » — exactement la classe de bugs (`Cannot read property of undefined`) qui hante le JavaScript. La moitié des bugs du mois 1 auraient été attrapés à la compilation.

Limites et compromis. Le typage a un COÛT d'écriture (annotations, batailles avec le compilateur au début) et une COURBE d'apprentissage. Il ne garantit pas la CORRECTION logique (un type juste peut cacher une mauvaise formule) : il élimine une CLASSE de bugs (les incohérences de type), pas tous. Et les types peuvent devenir complexes au point de nuire à la lisibilité — le bon dosage est de typer les frontières et laisser l'inférence faire le reste.

La règle du jour : **type les CONTRATS aux frontières, laisse l'inférence propager, active `strict`, bannis `any` au profit de `unknown` + validation, et surtout apprends à LIRE les erreurs du compilateur comme des bugs futurs attrapés gratuitement — c'est la compétence, pas la syntaxe.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : convertir une petite fonction JavaScript en TypeScript strict et observer un bug RÉVÉLÉ par le typage.

**Exemple simple** : une fonction JS qui « marche »… parfois.
```js
// version JS : aucun garde-fou
function prixTTC(prixHT, taux) {
  return prixHT * (1 + taux);
}
prixTTC(100, 0.2);      // 120  ✅
prixTTC("100", 0.2);    // "1001.2"  ❌ concaténation silencieuse !
```

**Raisonnement pas-à-pas** : (1) j'annote les paramètres et le retour avec les types attendus ; (2) je compile en strict ; (3) le compilateur REFUSE l'appel fautif AVANT toute exécution ; (4) je lis l'erreur, qui pointe la ligne et la cause exacte.

**Implémentation** :
```ts
function prixTTC(prixHT: number, taux: number): number {
  return prixHT * (1 + taux);
}

prixTTC(100, 0.2);       // 120  ✅
prixTTC("100", 0.2);     // ❌ tsc : Argument of type 'string' is not
                         //    assignable to parameter of type 'number'.
```
Le bug de concaténation (`"100" * ...`) qui aurait produit un prix faux en production est attrapé à la compilation, avec un message qui DÉSIGNE le coupable.

**any vs unknown sur une donnée externe** :
```ts
function traiter(donnee: unknown): number {
  // interdit d'utiliser 'donnee' sans vérifier : le compilateur FORCE le narrowing
  if (typeof donnee === 'number') return donnee * 2;   // ici donnee est number
  throw new Error('attendu: number');
}
// avec 'any' à la place de 'unknown', donnee * 2 passerait SANS vérification -> bug latent
```

## ⚠️ Erreurs fréquentes
- Mettre `any` pour faire taire le compilateur : c'est désactiver l'outil et réintroduire les bugs du JS non typé.
- Croire que tsc exécute le code : il VÉRIFIE puis transpile ; c'est node (ou tsx) qui exécute.
- Sur-annoter en dupliquant ce que l'inférence déduit déjà (`const x: number = 2`) : bruit inutile.
- Croire qu'un code qui compile est forcément correct : le typage n'attrape pas les erreurs de logique.

## 🏢 Cas métier
L'adoption massive de TypeScript en entreprise (front comme back Node) tient à une raison économique : sur une base de code de plusieurs dizaines de milliers de lignes maintenue par une équipe, le typage attrape à la compilation des régressions qui, sinon, ne se révéleraient qu'en production. Renommer un champ, changer une signature, supprimer une propriété : le compilateur liste INSTANTANÉMENT tous les endroits à corriger, là où en JS il faudrait une couverture de tests parfaite (illusoire) ou des bugs découverts par les utilisateurs. C'est aussi une documentation vivante : un nouveau développeur lit les types pour comprendre les contrats sans deviner. Concrètement, savoir écrire du TypeScript strict, lire ses erreurs et manier `unknown` aux frontières est aujourd'hui une exigence de base sur la plupart des offres front et back JS — pas un plus.

## 🎤 Question d'entretien
**« Pourquoi typer du JavaScript avec TypeScript, et quelle est la différence entre `any` et `unknown` ? »** → Le typage ajoute un contrat vérifié À LA COMPILATION, sans rien changer à l'exécution : il déplace la détection des bugs de type au plus tôt (dans l'éditeur, où corriger coûte quelques secondes) au lieu de la laisser exploser en production. C'est une documentation qui ne peut pas mentir, parce que le compilateur la vérifie partout. En mode strict, il attrape notamment les `null`/`undefined` oubliés — la classe de bugs la plus fréquente en JS. Pour `any` vs `unknown` : `any` DÉSACTIVE le vérificateur pour une valeur, on retombe dans les risques du JS non typé — à bannir. `unknown` dit « type inconnu » et FORCE une vérification (narrowing) avant tout usage : c'est la réponse correcte aux données externes (JSON d'API, saisie) dont on ignore la forme à la compilation. **Relance possible** : « le typage garantit-il un code correct ? » → non : il élimine les incohérences de type, pas les erreurs de logique ; un type juste peut cacher une formule fausse — le typage complète les tests, il ne les remplace pas.
