## 📖 Cours approfondi
**Concepts abordés :** Sous-ensembles · Permutations · Arbre de décision · Backtracking (intro) · Complexité exponentielle assumée.

Générer toutes les combinaisons revient à explorer un arbre de décisions : pour chaque élément, deux branches — le prendre ou non. 2 choix × n éléments = 2^n feuilles (les sous-ensembles). Pour les permutations : n choix, puis n-1, puis n-2… = n! feuilles.

Le backtracking est la technique d'exploration : on descend dans une branche (on « essaie »), on note le résultat au fond, puis on REMONTE en défaisant le choix (on « backtrack ») pour essayer l'autre branche. Le squelette : choisir → explorer récursivement → défaire.

Ici l'exponentiel est inévitable : c'est la TAILLE DU RÉSULTAT qui l'impose, pas ta solution. Savoir distinguer « problème exponentiel » de « solution maladroite » (fib naïf) est une compétence d'analyse.

**Modèle mental : générer toutes les combinaisons, c'est PARCOURIR un arbre de décisions. À chaque élément, deux branches — « je le prends » ou « je ne le prends pas ». La récursion DESCEND dans une branche, atteint une feuille (une solution complète), puis REMONTE en défaisant le dernier choix pour explorer l'autre branche : c'est le backtracking. Le nombre de feuilles (2ⁿ pour les sous-ensembles, n! pour les permutations) EST la taille du résultat, donc le coût exponentiel vient du PROBLÈME, pas d'une maladresse.** Distinguer « exponentiel inévitable » (générer 2ⁿ sous-ensembles) de « exponentiel évitable » (fib naïf qui recalcule) est une compétence d'analyse cruciale.

Pourquoi le backtracking existe. Beaucoup de problèmes demandent d'ÉNUMÉRER ou de CHERCHER parmi toutes les configurations possibles : tous les sous-ensembles, toutes les permutations, tous les placements valides (Sudoku, N-reines). On ne peut pas les lister « à plat » : leur nombre dépend de n. Le backtracking les construit INCRÉMENTALEMENT — un choix à la fois — et abandonne (« élague ») une branche dès qu'elle ne peut plus mener à une solution, ce qui évite d'explorer des configurations mortes.

Le squelette universel, depuis les fondations. Trois gestes : **choisir** (ajouter un élément à la solution partielle), **explorer** (appel récursif sur le reste), **défaire** (retirer l'élément pour tester l'autre branche). Le cas de base : « plus de décisions à prendre » → on enregistre une COPIE de la solution partielle. Le « défaire » est ce qui distingue le backtracking d'une simple récursion : on RÉUTILISE le même accumulateur en le remettant dans son état d'avant, au lieu d'en créer un à chaque nœud.

La différence avec les concepts proches. La **récursion simple** (factorielle, somme) fait UN appel par niveau et remonte une valeur ; le backtracking fait PLUSIEURS appels par niveau (une par branche) et construit un ensemble de résultats. La **programmation dynamique** s'attaque aux problèmes où les sous-problèmes se RÉPÈTENT (fib) : on mémorise pour ne pas recalculer — inutile ici, car chaque sous-ensemble est unique. Le backtracking et la DP répondent donc à des besoins opposés : énumérer/chercher vs optimiser en réutilisant.

Limites et compromis. L'exponentiel plafonne l'usage : générer les sous-ensembles de 30 éléments = un milliard de feuilles, impraticable. On ne backtrack en pratique que si n est petit OU si l'élagage coupe la majorité de l'arbre (contraintes fortes). Piège mémoire classique : muter l'accumulateur PARTAGÉ sans en enregistrer une COPIE au fond — toutes les « solutions » finissent identiques (des références au même tableau vidé au retour).

La règle du jour : **quand un problème demande « toutes les » configurations ou « existe-t-il une » configuration valide, pense arbre de décisions + backtracking (choisir → explorer → défaire), enregistre une COPIE au cas de base, et sache dire si l'exponentiel est imposé par le problème ou par ta solution.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : générer tous les sous-ensembles de `[1, 2, 3]` (il y en a 2³ = 8) par récursion à choix binaire, en observant la descente et la remontée.

**Exemple simple** : l'arbre de décision pour `[1, 2]`. Racine : rien de choisi. Niveau 1 (élément 1) : branche « avec 1 » / branche « sans 1 ». Niveau 2 (élément 2) : chaque branche se re-divise. Feuilles : `{1,2}, {1}, {2}, {}` = 2² = 4. Ajouter l'élément 3 double chaque feuille → 8.

**Raisonnement pas-à-pas** : (1) je traite les éléments dans l'ordre, un « index de décision » qui avance ; (2) à chaque index, deux appels : un où je PRENDS l'élément (je le `push`), un où je ne le prends pas ; (3) quand l'index dépasse le dernier élément → cas de base → j'enregistre une COPIE de la solution partielle ; (4) après l'appel « je prends », je `pop` pour DÉFAIRE et laisser la branche « je ne prends pas » repartir d'un état propre.

**Implémentation** :
```ts
function sousEnsembles<T>(arr: T[]): T[][] {
  const resultats: T[][] = [];
  const partiel: T[] = [];

  function explorer(i: number): void {
    if (i === arr.length) {          // cas de base : plus de décision
      resultats.push([...partiel]);  // COPIE, sinon on pousse une référence mutée
      return;
    }
    partiel.push(arr[i]);            // CHOISIR : je prends arr[i]
    explorer(i + 1);                 // EXPLORER la branche "avec"
    partiel.pop();                   // DÉFAIRE (backtrack)
    explorer(i + 1);                 // EXPLORER la branche "sans"
  }

  explorer(0);
  return resultats;
}

console.log(sousEnsembles([1, 2, 3]));
// [[1,2,3],[1,2],[1,3],[1],[2,3],[2],[3],[]]  -> 8 sous-ensembles
```

**La même mécanique, permutations** : au lieu de « prendre/ne pas prendre », on choisit à chaque niveau UN élément non encore utilisé (n choix, puis n-1…), d'où n! feuilles.
```ts
function permutations<T>(arr: T[]): T[][] {
  const res: T[][] = [], partiel: T[] = [], utilise = new Set<number>();
  function explorer(): void {
    if (partiel.length === arr.length) { res.push([...partiel]); return; }
    for (let i = 0; i < arr.length; i++) {
      if (utilise.has(i)) continue;      // on ne réutilise pas un élément
      utilise.add(i); partiel.push(arr[i]);      // choisir
      explorer();                                 // explorer
      partiel.pop(); utilise.delete(i);           // défaire
    }
  }
  explorer();
  return res;
}
console.log(permutations([1, 2, 3]).length);   // 6 = 3!
```

## ⚠️ Erreurs fréquentes
- Muter l'accumulateur partagé sans en enregistrer une COPIE au cas de base : tous les résultats deviennent identiques.
- Oublier le « défaire » (pop) entre deux branches : les choix d'une branche polluent la suivante.
- Manquer le cas de base (plus d'éléments à décider) : récursion infinie ou dépassement de pile.
- Confondre l'exponentiel inévitable (2ⁿ résultats) avec un exponentiel dû à une mauvaise solution (recalcul redondant).

## 🏢 Cas métier
Le backtracking résout les problèmes de configuration et de contrainte omniprésents en ingénierie : générer les combinaisons d'options d'un produit, résoudre un solveur de contraintes (planning, placement), explorer les coups possibles d'un moteur de jeu, énumérer les chemins valides d'un routeur. Un moteur de règles métier qui doit trouver « une affectation valide de tâches à des créneaux » est un backtracking déguisé. La clé en production : l'élagage. Un développeur qui génère toutes les configurations PUIS filtre fait exploser le temps ; celui qui abandonne une branche dès qu'une contrainte est violée rend le problème traitable. En entretien, « génère toutes les combinaisons/permutations » ou « résous ce Sudoku » teste précisément si tu sais structurer choisir → explorer → défaire et raisonner sur la complexité.

## 🎤 Question d'entretien
**« Écris une fonction qui génère tous les sous-ensembles d'un tableau, et donne sa complexité. »** → C'est un parcours d'arbre de décisions : chaque élément a deux branches (le prendre ou non), donc 2ⁿ feuilles = 2ⁿ sous-ensembles. J'utilise le squelette du backtracking : une fonction récursive avec un index de décision, qui à chaque niveau fait deux appels (« avec » et « sans » l'élément), et au cas de base (index au bout) enregistre une COPIE de la solution partielle. Le geste crucial est le « défaire » (`pop`) entre les deux branches, pour que l'accumulateur partagé reparte propre — et la copie au cas de base, sinon tous les résultats pointent vers le même tableau muté. La complexité est O(2ⁿ) en temps, imposée par la taille du résultat, pas par une maladresse — c'est un exponentiel INÉVITABLE, à distinguer de celui de fib naïf qui, lui, se corrige par mémoïsation. **Relance possible** : « et pour les permutations ? » → même mécanique, mais à chaque niveau on choisit un élément NON ENCORE UTILISÉ (n puis n-1…), d'où n! feuilles.
