## 🎯 Objectif du jour
Connecter un front à TON API : fetch, états loading/error/data, module api réutilisable.

## 📖 Cours approfondi
**Concepts abordés :** fetch · useEffect · 3 états async · Module api.ts · Gestion d'erreur affichée.

useEffect synchronise ton composant avec l'EXTÉRIEUR (un fetch, un abonnement) : il s'exécute APRÈS le rendu, et son tableau de dépendances dit quand le rejouer. Le contrat des données async ne change pas : chaque fetch a TROIS états (loading, error, data) et l'UI doit décrire les trois — l'oublier donne les pages blanches et les spinners éternels.

En StrictMode (dev), React monte chaque composant DEUX fois exprès : si ton effet casse au double appel, c'est qu'il lui manque un cleanup ou qu'il n'est pas idempotent — c'est une feature de détection, pas un bug.

Le module api.ts unique (l'Adapter du jour 39) centralise les appels : types partagés avec le backend, gestion d'erreur commune, un seul endroit à modifier si l'API change. Un fetch dispersé dans chaque composant est le code smell frontend n°1.

**Modèle mental : `useEffect` SYNCHRONISE ton composant avec l'EXTÉRIEUR (un fetch, un abonnement) — il s'exécute APRÈS le rendu, et son tableau de DÉPENDANCES dit quand le rejouer. Le contrat des données async ne change jamais : chaque fetch a TROIS états — loading, error, data — et l'UI doit décrire les TROIS, sinon on obtient les pages blanches et les spinners éternels. Tous les appels passent par un module `api.ts` UNIQUE et typé : c'est l'Adapter (jour 39) qui centralise la gestion d'erreur et partage les types.** Brancher le front sur TON API, c'est gérer proprement l'asynchrone et centraliser les appels.

Pourquoi useEffect existe. Un composant React est une fonction pure du state (UI = f(state), jour 87). Mais parfois il faut interagir avec l'EXTÉRIEUR : appeler une API, s'abonner à un événement, lire le stockage. Ces effets de bord ne peuvent pas vivre dans le corps du rendu (qui doit rester pur et peut s'exécuter plusieurs fois). `useEffect` est l'endroit prévu pour ça : il s'exécute APRÈS le rendu, une fois le DOM à jour, et se REJOUE selon ses dépendances. Il SYNCHRONISE le composant avec une source externe.

Les trois états de l'async, depuis les fondations. Toute donnée récupérée par le réseau passe par trois états que l'UI DOIT gérer explicitement : **LOADING** (la requête est en cours — afficher un indicateur), **ERROR** (la requête a échoué — afficher un message, permettre de réessayer), **DATA** (la requête a réussi — afficher les données). Oublier LOADING donne une UI figée sans retour ; oublier ERROR donne une page blanche sur réseau lent ou serveur éteint. Décrire les trois états est le contrat non négociable de tout fetch.

Le tableau de dépendances, depuis les fondations. `useEffect(fn, [deps])` : l'effet se rejoue quand une dépendance change. Un tableau VIDE `[]` = l'effet s'exécute une seule fois (au montage) — typique d'un fetch initial. Des dépendances `[id]` = l'effet se rejoue quand `id` change (recharger quand on change de ressource). Un tableau de dépendances mal renseigné cause des bugs : effet qui ne se rejoue pas quand il faut, ou qui boucle.

Le module api.ts, l'Adapter, depuis les fondations. Plutôt que d'éparpiller des `fetch` dans chaque composant (duplication, gestion d'erreur incohérente, types non partagés), on centralise TOUS les appels dans un module `api.ts` unique et typé. Bénéfices : la gestion d'erreur est COMMUNE (un seul endroit pour traiter les statuts), les TYPES sont partagés (le front et l'API parlent le même contrat), et changer l'URL de base ou la façon d'appeler ne touche qu'un fichier. C'est l'Adapter du jour 39 : une interface uniforme devant les détails du réseau.

Le StrictMode et le double montage. En développement, React monte chaque composant DEUX fois exprès (StrictMode) : si ton effet casse au double appel, c'est qu'il lui manque un CLEANUP ou qu'il n'est pas idempotent. C'est une FEATURE de détection (pas un bug) qui révèle les effets mal écrits — à comprendre pour ne pas s'en effrayer.

Limites et compromis. Gérer les trois états à la main est verbeux ; les vraies applications utilisent des bibliothèques (React Query, SWR) qui encapsulent loading/error/data, le cache et le rafraîchissement — mais comprendre le contrat à la main d'abord est formateur. `useEffect` a des subtilités (dépendances, cleanup, races) qui en font un hook souvent mal utilisé — d'où l'importance du modèle « synchroniser avec l'extérieur ».

La règle du jour : **`useEffect` synchronise avec l'extérieur (s'exécute après le rendu, se rejoue selon ses dépendances). Chaque fetch a TROIS états — loading, error, data — que l'UI doit TOUS décrire (sinon pages blanches et spinners éternels). Centralise les appels dans un module `api.ts` unique et typé (l'Adapter) : gestion d'erreur commune et types partagés.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : charger la liste des livres depuis LivreAPI en gérant explicitement les trois états async, via un module api.ts.

**Exemple simple** : les 3 états. Sans eux, l'UI casse : réseau lent → figée (pas de loading), serveur éteint → page blanche (pas d'error). Avec les trois : « Chargement… » puis soit la liste, soit « Erreur : réessayer ». L'utilisateur sait toujours où il en est.

**Raisonnement pas-à-pas** : (1) le module api.ts centralise l'appel typé ; (2) useEffect lance le fetch APRÈS le rendu (dépendances `[]` = au montage) ; (3) je gère loading, error, data explicitement ; (4) l'erreur réseau est AFFICHÉE, pas avalée.

**Implémentation** :
```ts
// api.ts — module UNIQUE et typé (l'Adapter, jour 39)
const BASE = 'http://localhost:3000';
export async function getLivres(): Promise<Livre[]> {
  const r = await fetch(`${BASE}/livres`);
  if (!r.ok) throw new Error(`API ${r.status}`);   // gestion d'erreur COMMUNE
  return r.json() as Promise<Livre[]>;
}
```
```tsx
import { useEffect, useState } from 'react';
import { getLivres } from './api';

export function Livres() {
  const [data, setData] = useState<Livre[] | null>(null);
  const [error, setError] = useState<string | null>(null);
  const [loading, setLoading] = useState(true);          // les 3 ÉTATS async

  useEffect(() => {                                       // SYNCHRONISE avec l'API
    getLivres()
      .then(setData)
      .catch(e => setError(e.message))                   // l'erreur est CAPTURÉE
      .finally(() => setLoading(false));
  }, []);                                                 // [] = une fois, au montage

  if (loading) return <p>Chargement…</p>;                 // état LOADING décrit
  if (error)   return <p>Erreur : {error} <button onClick={() => location.reload()}>Réessayer</button></p>; // ERROR affiché
  return <ul>{data!.map(l => <li key={l.id}>{l.titre}</li>)}</ul>;   // état DATA
}
```
Tous les appels passent par api.ts (typé, gestion d'erreur commune), useEffect synchronise le composant avec l'API après le rendu, et les TROIS états sont décrits — donc l'UI ne casse ni sur réseau lent (loading) ni serveur éteint (error affiché avec un bouton réessayer).

## ⚠️ Erreurs fréquentes
- États async oubliés : UI figée sur réseau lent (pas de loading) ou page blanche sur erreur (pas d'error).
- fetch dupliqué hors du module api : gestion d'erreur incohérente, types non partagés.
- Erreur réseau avalée (catch vide) au lieu d'être affichée à l'utilisateur.
- Tableau de dépendances de useEffect mal renseigné : effet qui ne se rejoue pas quand il faut, ou qui boucle.

## 🏢 Cas métier
Connecter un front à une API en gérant proprement l'asynchrone est le cœur du développement full-stack en entreprise, et la source des bugs d'UI les plus fréquents. Les trois états async (loading, error, data) sont un contrat universel : les applications qui les négligent offrent une expérience cassée (spinners éternels, pages blanches sur erreur réseau, données qui n'arrivent jamais) — un défaut immédiatement visible et pénalisant. La centralisation des appels dans un module API (l'Adapter) est une pratique standard : elle évite la duplication, uniformise la gestion d'erreur et l'authentification, et partage les types entre front et back (surtout en TypeScript de bout en bout). Les bibliothèques modernes (React Query, SWR) sont bâties précisément pour gérer ce contrat async (états, cache, rafraîchissement) — comprendre le contrat à la main est le prérequis pour les utiliser à bon escient. Savoir gérer les états async, centraliser les appels et afficher les erreurs à l'utilisateur démontre une maîtrise full-stack concrète, très valorisée. « Comment gères-tu le chargement et les erreurs d'un appel API ? » est une question d'entretien front récurrente.

## 🎤 Question d'entretien
**« Comment gères-tu un appel API dans un composant React ? »** → J'utilise `useEffect`, qui SYNCHRONISE le composant avec l'extérieur : il s'exécute APRÈS le rendu et se rejoue selon son tableau de dépendances — un tableau vide pour un fetch initial au montage, ou des dépendances comme `[id]` pour recharger quand la ressource change. Le point crucial, c'est que tout appel async a TROIS états que l'UI doit décrire explicitement : LOADING (requête en cours, j'affiche un indicateur), ERROR (échec, j'affiche un message et je permets de réessayer), et DATA (succès, j'affiche les données). Oublier loading fige l'UI, oublier error donne une page blanche quand le serveur est éteint — donc je gère toujours les trois. Et je centralise TOUS les appels dans un module `api.ts` unique et typé : c'est l'Adapter, qui me donne une gestion d'erreur commune, des types partagés entre le front et l'API, et un seul endroit à changer si l'URL de base bouge — plutôt que d'éparpiller des fetch dans chaque composant. **Relance possible** : « pourquoi React exécute-t-il ton effet deux fois en développement ? » → c'est le StrictMode, qui monte les composants deux fois exprès pour révéler les effets mal écrits : si mon effet casse au double appel, c'est qu'il lui manque un cleanup ou qu'il n'est pas idempotent. C'est une feature de détection, pas un bug — en production, l'effet ne s'exécute qu'une fois.
