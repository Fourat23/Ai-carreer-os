## 🎯 Objectif du jour
Comprendre le pipeline ML.

## 📖 Cours approfondi
**Modèle mental : le machine learning supervisé est un WORKFLOW standard et répétable — on apprend des paramètres sur des données d'entraînement (fit), on applique le modèle à des données neuves (predict), on évalue la qualité (score) — et scikit-learn impose cette API uniforme à TOUS les modèles, si bien que changer d'algorithme ne change qu'une seule ligne (l'instanciation).** Le ML n'est pas une collection d'algorithmes exotiques : c'est un PROCESSUS qu'on répète, où l'algorithme est un composant interchangeable. Comprendre le workflow d'abord, les algorithmes ensuite, évite de se noyer dans les détails.

Les concepts fondateurs :
1. **Apprentissage supervisé** : on dispose d'exemples ÉTIQUETÉS (des `X` = features, et un `y` = cible connue). Le modèle apprend la relation `X → y` pour PRÉDIRE `y` sur de nouveaux `X`. Régression si `y` est un nombre, classification si `y` est une catégorie.
2. **L'API estimator de scikit-learn** : chaque modèle est un objet avec `.fit(X, y)` (apprendre), `.predict(X)` (prédire), et `.score(X, y)` (évaluer). Cette uniformité est la grande force de scikit-learn : `LinearRegression()`, `DecisionTreeClassifier()`, `RandomForestClassifier()` s'utilisent EXACTEMENT pareil.
3. **Le workflow standard** : charger et inspecter → séparer `X`/`y` → SPLIT train/test (jour 157) → `fit` sur le train → `predict`/`score` sur le test → interpréter. Ce squelette ne change JAMAIS ; seuls le modèle et les métriques varient.
4. **fit ≠ predict** : `fit` APPREND les paramètres (les coefficients, les seuils des arbres) à partir des données d'entraînement ; `predict` les APPLIQUE. Confondre les deux (ou fit sur le test) est la source du data leakage (jour 157).

Pourquoi cette abstraction est décisive : elle rend le ML MODULAIRE et EXPÉRIMENTAL. Tu écris le workflow une fois, puis tu essaies dix modèles en changeant une ligne, tu compares leurs scores, tu choisis. La compétence n'est pas de connaître les maths de chaque algorithme par cœur, mais de maîtriser le PROCESSUS d'expérimentation rigoureux (split, fit, évaluer, comparer, sans leakage). C'est le prolongement direct de la pensée « pipeline reproductible » de la data (jours 132, 138).

La règle du jour : **maîtrise le workflow (charger → split → fit → predict → évaluer) et l'API fit/predict/score AVANT les algorithmes ; scikit-learn rend les modèles interchangeables, donc l'important est le PROCESSUS rigoureux, pas la connaissance encyclopédique de chaque algorithme**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : faire tourner un pipeline ML minimal complet avec scikit-learn (fit/predict/score).

**Exemple simple** : le cœur du ML en trois lignes — `modele.fit(X_train, y_train)` (apprendre), `preds = modele.predict(X_test)` (prédire), `modele.score(X_test, y_test)` (évaluer). Tout le reste (quel modèle, quelles métriques) s'articule autour de ces trois gestes.

**Raisonnement pas-à-pas** : charger un dataset intégré → séparer features/cible → split train/test → instancier un modèle → fit sur train → predict/score sur test.

**Implémentation** :
```python
from sklearn.datasets import load_diabetes
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LinearRegression

X, y = load_diabetes(return_X_y=True)                 # features (X), cible (y)
X_train, X_test, y_train, y_test = train_test_split(  # on RÉSERVE un test jamais vu
    X, y, test_size=0.2, random_state=42)

modele = LinearRegression()          # changer d'algo = changer CETTE ligne uniquement
modele.fit(X_train, y_train)         # APPREND les paramètres sur le train
preds = modele.predict(X_test)       # APPLIQUE le modèle à des données neuves
print(modele.score(X_test, y_test))  # évalue (R² par défaut pour une régression)
```

**Mini-quiz** : (a) Que fait `fit` et que fait `predict` ? (b) Pourquoi évalue-t-on sur le test et pas sur le train ? (c) Combien de lignes changent pour essayer un autre modèle ?
→ (a) `fit` apprend les paramètres sur les données d'entraînement ; `predict` les applique à de nouvelles données ; (b) évaluer sur le train mesure la mémorisation, pas la généralisation — le test jamais vu mesure la vraie performance ; (c) une seule (l'instanciation), grâce à l'API uniforme de scikit-learn.

**Variante** : remplace `LinearRegression()` par `DecisionTreeRegressor()` (une ligne) et compare les scores. Tu vérifies concrètement que le workflow est identique et que seul le modèle change — c'est ce qui rend l'expérimentation rapide.

## 🏢 Cas métier
Le workflow scikit-learn est le standard de fait du ML classique en entreprise : sa cohérence (fit/predict/score identiques pour tous les modèles) permet aux data scientists d'expérimenter vite et de collaborer sur une base commune. Ce qui distingue un praticien fiable n'est pas de connaître les maths de chaque algorithme, mais de maîtriser le PROCESSUS : split rigoureux, absence de leakage, comparaison équitable, reproductibilité. Un modèle « impressionnant » évalué sur ses données d'entraînement (leakage) est inutile ; un modèle simple évalué proprement est déployable. Les recruteurs testent cette rigueur de workflow (« comment évalues-tu un modèle ? ») bien plus que la théorie de tel ou tel algorithme.

## 🎤 Question d'entretien
**« Décris le workflow d'un projet de ML supervisé avec scikit-learn. »** → On dispose d'exemples étiquetés (X features, y cible). Le workflow standard : charger et inspecter les données, séparer X et y, faire un SPLIT train/test pour réserver des données jamais vues, instancier un modèle, l'entraîner avec `.fit(X_train, y_train)` (qui apprend les paramètres sur le train), prédire avec `.predict(X_test)` et évaluer avec `.score(X_test, y_test)`. La force de scikit-learn est son API uniforme : `fit`/`predict`/`score` sont identiques pour tous les modèles, donc changer d'algorithme ne change qu'une ligne. Le point crucial est d'évaluer sur le TEST (généralisation), jamais sur le train (mémorisation), et de ne jamais laisser d'information du test fuir vers l'entraînement (leakage). L'important est la rigueur du processus, pas la connaissance encyclopédique des algorithmes.
