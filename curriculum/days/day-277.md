## 🎯 Objectif du jour
Gérer le contexte de l'agent.

## 📖 Cours approfondi
**Modèle mental : la « mémoire » d'un agent, c'est TOI qui la construis — le modèle n'a que le contexte de l'appel courant, et gérer ce qui y entre est le vrai travail.** Tu le sais depuis le jour 197 : un LLM n'a aucune mémoire persistante. Pour un agent qui itère, cela pose un problème AIGU : l'historique (objectif + toutes les actions et observations) grossit à chaque tour, et il doit tenir dans la fenêtre de contexte tout en gardant l'information utile. La gestion de l'état d'un agent est un problème d'INGÉNIERIE DU CONTEXTE, pas une propriété du modèle.

Les types d'état d'un agent, à distinguer :
1. **L'état de travail (court terme)** : l'historique de la session courante (actions, observations). Il croît vite. Problème central : quand il dépasse le budget de contexte, que garder ? Stratégies — tronquer les vieux tours, RÉSUMER l'historique ancien (un appel LLM qui condense « voici ce qui a été fait et appris »), ou garder l'objectif + les N derniers tours + un résumé du milieu.
2. **La mémoire persistante (long terme)** : ce qui survit entre les sessions — préférences, faits appris, résultats précédents. Stockée par TON code (fichier, base) et réinjectée au démarrage. C'est ce qui fait qu'un agent « se souvient » d'une session à l'autre — mécaniquement, c'est de la lecture/écriture que tu orchestres.
3. **L'état structuré vs le contexte brut** : plutôt que tout garder en texte, un agent mûr maintient un ÉTAT structuré (objectif, sous-tâches accomplies, faits établis, prochaine étape) mis à jour à chaque tour — plus compact et moins sujet à la dérive d'objectif (jour 275) que l'historique brut.

Le trade-off central : plus tu gardes de contexte, plus l'agent est « informé » mais plus il coûte cher (tokens, jour 200) et plus il risque le « lost in the middle » (l'information noyée est mal utilisée). Moins tu gardes, moins il coûte mais plus il risque d'oublier une étape. Gérer la mémoire d'un agent, c'est arbitrer en permanence entre COÛT, COMPLÉTUDE et FIABILITÉ — et le faire explicitement (une stratégie de gestion du contexte) plutôt que de laisser l'historique grossir jusqu'au débordement.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : ajouter une gestion de mémoire/état à ton agent, avec gestion de la fenêtre de contexte.

**Exemple simple** : la mémoire persistante la plus simple est un fichier JSON `memoire.json` lu au démarrage et écrit à la fin — l'agent « se souvient » de la session précédente parce que TON code recharge ce fichier.

**Raisonnement pas-à-pas** : maintenir un état structuré compact plutôt que l'historique brut, résumer quand ça déborde, persister ce qui doit survivre.

**Implémentation** :
```python
class EtatAgent:
    objectif: str
    sous_taches_faites: list[str]      # état structuré, pas historique brut
    faits_etablis: list[str]           # ce qui a été appris
    derniers_tours: list[str]          # N derniers (détail récent)

def gerer_contexte(etat: EtatAgent, budget_tokens=6000) -> str:
    contexte = format_etat(etat)
    if compter_tokens(contexte) > budget_tokens:      # débordement
        etat.faits_etablis = [resumer(etat.faits_etablis)]  # RÉSUMER l'ancien
        etat.derniers_tours = etat.derniers_tours[-3:]      # tronquer le récent
    return format_etat(etat)

# Persistance entre sessions :
def charger_memoire(): return json.loads(Path("memoire.json").read_text()) if ... else {}
def sauver_memoire(faits): Path("memoire.json").write_text(json.dumps(faits))
```

→ (a) de TON code qui gère ce qui entre dans le contexte (le modèle n'a pas de mémoire) ; (b) plus compact, moins sujet à la dérive d'objectif, garde l'essentiel ; (c) coût (tokens) vs complétude vs fiabilité (« lost in the middle »).

## 🏢 Cas métier
La gestion du contexte est LE problème d'ingénierie des agents en production : un agent support qui traite une conversation de 30 tours doit garder l'objectif et les faits clés sans exploser le budget de tokens (coût) ni noyer l'information (fiabilité). Les équipes qui maintiennent un état structuré et résument intelligemment ont des agents fiables et abordables ; celles qui laissent l'historique brut grossir ont des agents qui deviennent chers et confus au fil de la session. « Context engineering » est devenu un intitulé de poste — c'est exactement cette compétence.

## 🎤 Question d'entretien
**« Comment gères-tu la mémoire et le contexte d'un agent ? »** → Le modèle n'a pas de mémoire : c'est mon code qui gère ce qui entre dans le contexte. Je distingue l'état de travail (court terme, qui croît — je maintiens un ÉTAT STRUCTURÉ compact : objectif, sous-tâches faites, faits établis, N derniers tours, plutôt que l'historique brut) et la mémoire persistante (long terme, stockée et réinjectée entre sessions). Quand ça déborde, je résume l'ancien et tronque le récent. Le trade-off central : coût (tokens) vs complétude vs fiabilité (lost in the middle) — je l'arbitre explicitement, je ne laisse pas l'historique grossir jusqu'au débordement.
