## 🎯 Objectif du jour
Régler et valider.

## 📖 Cours approfondi
**Modèle mental : régler les hyperparamètres, c'est CHERCHER dans un espace de configurations — mais sans validation propre, on OPTIMISE le bruit (on choisit la config qui a eu de la chance sur un découpage) ; la validation finale sur un jeu de test JAMAIS utilisé pour régler quoi que ce soit est le seul chiffre honnête à rapporter.** Après le feature engineering (le gros des gains), l'optimisation des hyperparamètres apporte les derniers pourcents — à condition de ne pas se piéger en optimisant sur les mauvaises données. C'est le jour où la discipline anti-surapprentissage (jour 166) et anti-leakage (jour 157) se combinent au réglage.

Les concepts, depuis les fondations :
1. **Hyperparamètres vs paramètres** : les paramètres sont appris par `fit` (les coefficients) ; les HYPERPARAMÈTRES sont fixés AVANT l'entraînement et contrôlent le modèle (profondeur d'arbre, régularisation `C`, nombre d'arbres). Les régler, c'est choisir la meilleure configuration.
2. **La recherche (grid/random search)** : `GridSearchCV` teste toutes les combinaisons d'une grille ; `RandomizedSearchCV` en échantillonne au hasard (plus efficace sur de grands espaces). Chaque configuration est évaluée en VALIDATION CROISÉE — jamais sur un seul split.
3. **Le piège de l'optimisation sur le test** : si on règle les hyperparamètres en regardant le jeu de TEST, on l'a « utilisé » pour décider, donc il n'est plus une mesure honnête de généralisation (une forme de leakage). La parade : régler sur la validation croisée (dans le dev set), et ne toucher au TEST final qu'UNE fois, à la toute fin, pour l'évaluation qu'on rapporte.
4. **La sur-optimisation** : tester des centaines de configurations et garder la meilleure, c'est risquer de choisir celle qui a eu de la CHANCE sur les folds — le score de validation devient optimiste. On préfère une recherche raisonnable, on regarde la stabilité (écart-type), et on garde un test final vierge comme juge de paix.

La hiérarchie des gains : le feature engineering (jour 178) rapporte généralement le plus, l'optimisation des hyperparamètres les derniers pourcents. Passer des jours à régler un modèle sur des features pauvres est une erreur de priorité. Et le chiffre qu'on RAPPORTE est toujours celui du test final intouché, pas le meilleur score de validation obtenu pendant la recherche (qui est optimiste par construction).

La règle du jour : **règle les hyperparamètres par recherche en validation croisée (grid/random search), sans jamais toucher au test ; le chiffre honnête est celui du jeu de test final, utilisé UNE seule fois. L'optimisation apporte les derniers pourcents — après les features — et sur-optimiser sur la validation, c'est optimiser le bruit**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : régler les hyperparamètres par recherche en CV, puis valider une fois sur le test final.

**Exemple simple** : la séparation des rôles — on RÈGLE sur la validation croisée (dans le dev set) et on ÉVALUE une seule fois sur le test final. Le test n'entre JAMAIS dans le réglage, sinon le chiffre rapporté est optimiste.

**Raisonnement pas-à-pas** : définir une grille raisonnable → GridSearchCV/RandomizedSearchCV sur le dev set (CV) → prendre la meilleure config → l'évaluer UNE fois sur le test final intouché → rapporter ce chiffre.

**Implémentation** :
```python
from sklearn.model_selection import RandomizedSearchCV
from sklearn.metrics import roc_auc_score

grille = {
    "clf__n_estimators": [200, 400, 600],
    "clf__max_depth": [4, 8, 12, None],
    "clf__min_samples_leaf": [1, 5, 20],
}
recherche = RandomizedSearchCV(pipe, grille, n_iter=20, cv=5,
    scoring="roc_auc", random_state=42).fit(X_dev, y_dev)   # réglage sur le DEV (CV)
print("meilleure config :", recherche.best_params_)
print("AUC validation   :", recherche.best_score_)          # OPTIMISTE (issu de la recherche)

# Évaluation HONNÊTE : le test final, touché UNE seule fois
auc_test = roc_auc_score(y_test, recherche.predict_proba(X_test)[:, 1])
print("AUC test final   :", auc_test)                        # LE chiffre à rapporter
```

**Mini-quiz** : (a) Différence entre paramètre et hyperparamètre ? (b) Pourquoi ne pas régler les hyperparamètres sur le test ? (c) Quel chiffre rapporte-t-on à la fin ?
→ (a) les paramètres sont appris par fit (coefficients) ; les hyperparamètres sont fixés avant et contrôlent le modèle (profondeur, régularisation) ; (b) régler en regardant le test l'« utilise » pour décider — il n'est plus une mesure honnête de généralisation (leakage) ; (c) l'AUC du jeu de test final, touché une seule fois — pas le meilleur score de validation, qui est optimiste par construction.

**Variante** : compare le meilleur score de validation (issu de la recherche) au score du test final. Le test est souvent un peu plus bas : c'est normal (la recherche a optimisé sur la validation). Rapporter le test, pas la validation, est ce qui rend ton chiffre honnête.

## 🏢 Cas métier
L'optimisation des hyperparamètres est utile mais surestimée par les débutants, qui y passent des jours pour quelques pourcents alors que le feature engineering aurait rapporté davantage — une erreur de priorité fréquente. Plus grave, régler les hyperparamètres en regardant le test (ou sur-optimiser sur la validation) donne des scores optimistes qui ne tiennent pas en production. Les data scientists rigoureux règlent en validation croisée, gardent un test final vierge touché une seule fois, et rapportent CE chiffre. En entreprise et en compétition, la séparation stricte dev/test et la sobriété de la recherche sont ce qui distingue un score fiable d'un score gonflé. Savoir régler proprement (recherche en CV, test final intouché) et connaître la hiérarchie des gains (features d'abord) est une compétence de méthode valorisée.

## 🎤 Question d'entretien
**« Comment règles-tu les hyperparamètres sans te tromper toi-même ? »** → Par une recherche (grid ou random search) évaluée en VALIDATION CROISÉE sur le dev set, jamais sur le test. Les hyperparamètres (profondeur, régularisation, nombre d'arbres) sont fixés avant l'entraînement et contrôlent le modèle ; je cherche la meilleure config par CV. Le piège est de régler en regardant le TEST : je l'aurais alors « utilisé » pour décider, et il ne mesurerait plus honnêtement la généralisation (une forme de leakage). Je garde donc le test final VIERGE et je ne le touche qu'UNE fois, à la fin, pour l'évaluation que je rapporte — pas le meilleur score de validation, qui est optimiste par construction (j'ai choisi la config qui a eu de la chance sur les folds). Enfin, je connais la hiérarchie des gains : le feature engineering rapporte plus que le réglage, donc je n'optimise les hyperparamètres qu'après les features, sobrement.
