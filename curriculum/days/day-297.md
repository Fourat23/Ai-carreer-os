## 🎯 Objectif du jour
Rendre l'IA observable.

## 📖 Cours approfondi
**Modèle mental : rendre une app IA OBSERVABLE, c'est pouvoir répondre à « que s'est-il passé pour CETTE requête ? » longtemps après — sans observabilité, un système IA non déterministe est une boîte noire où le débogage devient impossible.** Un système classique est déjà dur à déboguer à distance ; un système IA l'est PLUS car il est non déterministe (jour 199), fait des appels externes coûteux, et enchaîne des étapes (retrieval, génération, agents). L'observabilité — logs structurés, traçabilité, corrélation — est ce qui transforme « ça a mal répondu une fois » en « voici exactement la question, les chunks récupérés, le prompt envoyé, la réponse, le coût, à telle heure ».

Les trois piliers, appliqués à l'IA :
1. **Les logs structurés** : pas des `print` en texte libre mais des événements structurés (JSON) avec des champs exploitables — timestamp, type d'événement, durée, tokens, coût, statut. Structurés = REQUÊTABLES (« montre-moi toutes les requêtes qui ont coûté > 0,05 € hier »), ce que des logs texte ne permettent pas.
2. **La corrélation (correlation id)** : un identifiant unique attaché à une requête utilisateur et propagé à travers TOUTES les étapes (retrieval, génération, appels d'outils, workers asynchrones). Avec lui, tu peux reconstituer le PARCOURS COMPLET d'une session — crucial dans un flux événementiel (jour 290) où les étapes sont éclatées. Sans corrélation, tu as des logs isolés impossibles à raccorder.
3. **La traçabilité d'une session complète** : pouvoir REJOUER mentalement (ou réellement) ce qui s'est passé — la question posée, les chunks récupérés avec leurs scores, le prompt exact envoyé au LLM, la réponse, les citations, les guardrails déclenchés, le coût, la latence par étape. C'est ce qui rend un incident DIAGNOSTICABLE (« le retrieval a ramené les mauvais chunks » vs « la génération a mal utilisé les bons chunks » — le tri du jour 225, rendu possible a posteriori par les logs).

Ce qui est SPÉCIFIQUE à l'IA : logger les éléments propres au LLM — le prompt (ou son hash, pour la privacy, jour 296), les tokens in/out, le coût, le modèle, la température, les scores de retrieval, les jugements de guardrails. Ces champs sont ce qui permet de déboguer, de suivre les coûts (jour 285) et de détecter les dérives. Une app IA sans ces logs est indébuggable en production — et l'observabilité est exactement ce qui distingue un prototype (« ça marchait sur ma machine ») d'un système de production (« je peux te dire ce qui s'est passé pour la requête de 14h32 »).

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : logs structurés avec correlation id sur DocQA, traçabilité d'une session complète.

**Exemple simple** : le correlation id en une idée — générer un `req_id` à l'arrivée d'une requête et l'inclure dans CHAQUE log de son traitement. Filtrer les logs par ce `req_id` reconstitue tout le parcours.

**Raisonnement pas-à-pas** : générer un id par requête, le propager, logger des événements structurés à chaque étape avec les champs IA, puis reconstituer une session.

**Implémentation** :
```python
import uuid, json, time

def traiter_requete(question, user):
    req_id = str(uuid.uuid4())                          # CORRELATION id
    def log(evt, **champs):
        print(json.dumps({"req_id": req_id, "ts": time.time(),
                          "evt": evt, "user": hash(user), **champs}))  # STRUCTURÉ
    log("requete_recue", question_hash=hash(question))   # privacy : hash (j.296)
    chunks = retrieve(question)
    log("retrieval", n=len(chunks), scores=[c.score for c in chunks],
        latence_ms=...)
    reponse = generer(question, chunks)
    log("generation", tokens_in=..., tokens_out=..., cout=..., modele=...,
        citations=len(reponse.citations), latence_ms=...)
    log("reponse_envoyee", refus=reponse.est_refus)
    return reponse
# Traçabilité : filtrer les logs par req_id → parcours complet reconstituable
```

**Mini-quiz** : (a) Pourquoi des logs STRUCTURÉS plutôt que du texte ? (b) À quoi sert le correlation id ? (c) Quels champs SPÉCIFIQUES à l'IA faut-il logger ?
→ (a) ils sont requêtables (« toutes les requêtes > 0,05 € ») ; (b) à raccorder toutes les étapes d'une requête en un parcours complet, surtout en flux éclaté ; (c) prompt (ou hash), tokens in/out, coût, modèle, température, scores de retrieval, guardrails déclenchés.

**Variante** : provoque une mauvaise réponse, puis DIAGNOSTIQUE-la uniquement à partir des logs (sans re-tester) — le retrieval a-t-il ramené les bons chunks (scores) ? la génération les a-t-elle bien utilisés ? Si tes logs permettent ce diagnostic a posteriori, ton observabilité est réussie.

## ⚠️ Erreurs fréquentes
- Logs en texte libre : impossibles à requêter — structurés (JSON) pour pouvoir filtrer/agréger.
- Pas de correlation id : les logs des différentes étapes sont isolés et impossibles à raccorder, surtout en flux éventementiel.
- Oublier les champs spécifiques IA (tokens, coût, scores, prompt) : sans eux, on ne peut ni déboguer ni suivre les coûts ni détecter les dérives.
- Logger le prompt complet avec données personnelles : privacy — hash ou masquage (jour 296), surtout en production.

## 🏢 Cas métier
L'observabilité est ce qui sépare un prototype d'un système de production : quand un utilisateur signale « l'assistant a donné une mauvaise réponse hier », l'équipe qui a des logs structurés avec correlation id reconstitue la session complète (question, chunks, prompt, réponse, coût) et diagnostique en minutes ; celle qui n'a que des `print` texte ne peut rien reconstituer et reste aveugle. Pour une app IA, c'est encore plus critique (non-déterminisme, coûts, étapes multiples). Le poste de « LLM observability / AI reliability engineer » existe précisément pour ça. Savoir instrumenter une app IA — logs structurés, corrélation, champs LLM — est une compétence de production directement recherchée.

## 🎤 Question d'entretien
**« Comment rends-tu une application IA observable en production ? »** → Trois piliers appliqués à l'IA : des logs STRUCTURÉS (JSON requêtable, pas du texte) avec les champs spécifiques LLM (prompt ou hash, tokens in/out, coût, modèle, température, scores de retrieval, guardrails) ; un CORRELATION ID généré par requête et propagé à toutes les étapes (retrieval, génération, workers asynchrones) pour reconstituer le parcours complet — crucial en flux éclaté ; et la traçabilité d'une session complète, qui rend un incident diagnosticable a posteriori (le retrieval a-t-il ramené les bons chunks, ou la génération les a-t-elle mal utilisés ?). Sans ça, un système IA non déterministe est une boîte noire indébuggable. C'est ce qui distingue un prototype d'un système de production.
