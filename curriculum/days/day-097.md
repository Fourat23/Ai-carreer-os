## 🎯 Objectif du jour
Factoriser les appels réseau.

## 📖 Cours approfondi
**Modèle mental : centraliser les appels réseau dans un seul module `api.ts`, c'est créer une FRONTIÈRE unique entre ton application et le réseau — un seul endroit qui connaît l'URL de base, les en-têtes, le parsing JSON et la traduction des erreurs HTTP en erreurs applicatives.** Sans cette frontière, chaque composant fait son `fetch` à sa façon : URL en dur répétée, statut HTTP parfois vérifié parfois non, erreurs gérées différemment partout. Le jour où l'API change (nouvelle URL de base, en-tête d'auth), tu modifies dix composants. Avec un module api, tu modifies UN fichier.

Ce que la centralisation apporte concrètement :
1. **Une seule configuration** : l'URL de base, les en-têtes communs (Content-Type, plus tard le token d'auth) définis une fois.
2. **Un parsing et une vérification uniformes** : chaque appel vérifie `response.ok`, parse le JSON, et transforme un statut d'erreur en une erreur TYPÉE que le front sait afficher — au lieu de laisser chaque composant redécouvrir que `fetch` ne rejette PAS sur un 404 (piège classique : `fetch` ne lève une erreur que sur panne réseau, pas sur un statut 4xx/5xx).
3. **Des fonctions métier lisibles** : `api.getLivres()`, `api.creerLivre(x)` — les composants expriment l'intention, pas la mécanique HTTP. C'est le clean code (mois 2) appliqué au réseau : une couche qui NOMME les opérations.

La gestion d'erreur centralisée suit la même logique que côté serveur (mois 3) : **un seul endroit décide comment une erreur réseau devient un message pour l'utilisateur**. On distingue les familles — erreur réseau (pas de connexion), erreur client (4xx : mauvaise requête, non trouvé), erreur serveur (5xx : bug back-end) — et on les traduit en messages ou comportements adaptés (réessayer, corriger la saisie, signaler un bug). Le composant, lui, reçoit soit des données, soit une erreur claire ; il n'a plus à connaître les codes HTTP.

La règle du jour : **le réseau est un détail d'infrastructure qui vit dans une seule couche ; le reste de l'app parle à cette couche, pas au réseau**. C'est la version front du principe de séparation des responsabilités.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : un module `api.ts` typé et centralisé qui branche ton front sur LivreAPI.

**Exemple simple** : le cœur du module est une fonction `request` qui vérifie `res.ok` et parse — `if (!res.ok) throw new ApiError(res.status)`. Tout le module se construit autour de ce garde-fou, car `fetch` ne rejette PAS sur un 404.

**Raisonnement pas-à-pas** : une fonction `request` privée qui gère URL de base + en-têtes + `res.ok` + erreur typée → des fonctions métier typées qui l'utilisent → les composants n'appellent que ces fonctions métier.

**Solution** :
```tsx
const BASE = import.meta.env.VITE_API_URL ?? 'http://localhost:3000';

export class ApiError extends Error {
  constructor(public status: number, message: string) { super(message); }
}

async function request<T>(chemin: string, options?: RequestInit): Promise<T> {
  let res: Response;
  try { res = await fetch(BASE + chemin, {
    headers: { 'Content-Type': 'application/json' }, ...options });
  } catch { throw new ApiError(0, 'Réseau indisponible'); }        // panne réseau
  if (!res.ok) throw new ApiError(res.status,                       // fetch NE rejette PAS sur 4xx/5xx
    res.status === 404 ? 'Ressource introuvable' : 'Erreur serveur');
  return res.status === 204 ? (undefined as T) : res.json();
}

export const api = {                                               // fonctions métier NOMMÉES
  getLivres: () => request<Livre[]>('/livres'),
  getLivre: (id: number) => request<Livre>(`/livres/${id}`),
  creerLivre: (l: NouveauLivre) =>
    request<Livre>('/livres', { method: 'POST', body: JSON.stringify(l) }),
};
```

**Mini-quiz** : (a) `fetch` lève-t-il une erreur sur un statut 404 ? (b) Pourquoi centraliser l'URL de base ? (c) Que gagne un composant à appeler `api.getLivres()` plutôt qu'un `fetch` direct ?
→ (a) non — il ne rejette que sur panne réseau ; il faut vérifier `res.ok` soi-même ; (b) un seul point à changer si l'API bouge, pas dix composants ; (c) il exprime l'intention, ignore la mécanique HTTP, et bénéficie du parsing/erreur uniformes.

**Variante** : ajoute une fonction `majLivre` (PUT) et `supprimerLivre` (DELETE) — tu obtiens le client complet dont BiblioApp aura besoin (jour 114), déjà typé et robuste.

## 🏢 Cas métier
Le module api centralisé est un standard de toute base de code front sérieuse : sans lui, une équipe se retrouve avec des `fetch` dispersés, des URL en dur, et le fameux bug « le 404 n'est pas géré » (parce que `fetch` ne rejette pas dessus). Le jour où l'API passe en HTTPS, change de domaine ou ajoute une authentification, la couche api absorbe le changement en un seul fichier. Les revues de code front rejettent systématiquement un `fetch` en dur dans un composant : c'est le signe d'un couplage au réseau qu'on sait coûteux. Savoir construire cette couche prouve que tu penses architecture, pas juste « faire marcher l'appel ».

## 🎤 Question d'entretien
**« Comment organises-tu les appels réseau dans une app front ? »** → Je centralise tout dans une couche `api.ts` : une frontière unique entre l'app et le réseau. Elle connaît l'URL de base et les en-têtes, vérifie `response.ok` (car `fetch` ne rejette PAS sur un 404 — seulement sur panne réseau), parse le JSON, et traduit les statuts d'erreur en erreurs typées que le front sait afficher. Les composants n'appellent que des fonctions métier nommées (`api.getLivres()`), sans connaître les codes HTTP. Bénéfice : si l'API change (URL, auth), je modifie un seul fichier ; et la gestion d'erreur est uniforme au lieu d'être réinventée dans chaque composant.
