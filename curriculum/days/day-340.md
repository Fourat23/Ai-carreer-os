# Jour 340 — Polish GitHub

> **Mois 12** · **Semaine 49** · Compétence : **Communication technique** · Difficulté : Intermédiaire/5 · Durée : 4.5 h

[← Dashboard](../../) · [Semaine 49](../week-49.md) · [Mois 12](../month-12.md) · [Correction](../solutions/day-340-solution.md)

## 🎯 Objectif du jour
Soigner les repos.

## 📖 Cours approfondi
**Modèle mental : polir tes 7 repos GitHub, c'est soigner la PREMIÈRE IMPRESSION de chacun — un recruteur juge la qualité de ton travail à la propreté de tes dépôts, avant même de lire une ligne de code.** Tu as des projets ; maintenant tu rends chaque dépôt PROFESSIONNEL : description, topics, README à jour, licence, et un README de profil GitHub qui accueille le visiteur. Un GitHub soigné signale le professionnalisme ; un GitHub en désordre (repos sans description, READMEs « TODO », commits « fix ») dévalue même un bon travail.

Les éléments de polish par repo :
1. **La description et les topics** : chaque repo a une description d'une phrase (ce qu'il fait) et des topics (tags : python, rag, llm...) — ils rendent le repo trouvable et compréhensible en un coup d'œil, dans la liste des repos comme dans les recherches.
2. **Le README à jour** : chaque repo a un README qui vaut (le README exemplaire du jour 337 pour DocSense ; une version proportionnée pour les autres). Un repo sans README, ou avec un README obsolète, signale l'abandon.
3. **La licence** : une licence (MIT typiquement) rend le projet réutilisable et signale que tu comprends les standards open-source. Un repo sans licence est juridiquement flou.
4. **Le README de profil GitHub** : le README spécial (repo à ton nom d'utilisateur) qui s'affiche sur ta page de profil — il accueille le visiteur, résume qui tu es (dev IA), et met en avant tes projets clés. C'est ta page d'accueil de développeur.

Pourquoi le polish GitHub compte : GitHub est le portfolio de facto d'un développeur, et un recruteur y regarde AVANT l'entretien. La propreté des dépôts est un PROXY de la qualité de ton travail — un GitHub soigné (descriptions, READMEs, licences, profil accueillant) signale le professionnalisme et le soin ; un GitHub en désordre suggère la négligence, même sur du bon code. Le polish ne prend qu'une journée mais change la première impression de TOUS tes projets. « Mes 7 repos sont polis, avec descriptions, READMEs et un profil GitHub accueillant » est ce qui fait qu'un recruteur qui tombe sur ton GitHub a immédiatement une bonne impression — l'inverse d'un GitHub qui donne envie de fermer l'onglet. C'est une compétence de présentation de soi qui, pour un coût faible, a un impact élevé sur la perception.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : polir les 7 repos (description, topics, README, licence) + README de profil GitHub.

**Exemple simple** : le minimum vital par repo — une description d'une phrase + 3-5 topics + un README qui explique quoi/pourquoi/comment lancer. Sans ça, le repo semble abandonné.

**Raisonnement pas-à-pas** : passer chaque repo au standard (description, topics, README, licence), puis créer le README de profil.

**La checklist de polish** :
```
Pour CHAQUE repo (× 7) :
  - description d'une phrase (ce que fait le projet)
  - topics/tags (python, rag, llm, fastapi... — trouvable et lisible)
  - README à jour (exemplaire pour DocSense j.337 ; proportionné pour les autres)
  - licence (MIT typiquement — réutilisable, standard open-source)
README de profil GitHub (repo à ton nom d'utilisateur) :
  - qui tu es (dev IA / AI Engineer), tes projets clés épinglés, comment te contacter
  - c'est ta PAGE D'ACCUEIL de développeur
```

**Mini-quiz** : (a) Pourquoi un recruteur juge-t-il ton travail à la propreté de tes repos ? (b) Que signale un repo sans README ou sans licence ? (c) À quoi sert le README de profil GitHub ?
→ (a) la propreté des dépôts est un PROXY de la qualité du travail ; GitHub est le portfolio de facto ; (b) l'abandon (pas de README) et un flou juridique (pas de licence) — négligence ; (c) c'est ta page d'accueil de développeur — elle accueille le visiteur et met en avant tes projets.

**Variante** : ouvre ton GitHub comme si tu étais un recruteur qui te découvre — la première impression est-elle « pro » ou « en désordre » ? Chaque repo sans description ou README est un point de négligence à corriger.

## ⚠️ Erreurs fréquentes
- Repos sans description ni topics : invisibles et incompréhensibles en un coup d'œil — chaque repo en a.
- READMEs obsolètes ou « TODO » : signalent l'abandon — les mettre à jour, proportionnés au projet.
- Pas de licence : flou juridique, projet non réutilisable — MIT typiquement.
- Pas de README de profil : la page d'accueil GitHub est vide — c'est ta vitrine, la soigner.

## 🏢 Cas métier
GitHub est le portfolio de facto d'un développeur, et les recruteurs techniques y regardent AVANT et PENDANT le processus de recrutement : un GitHub soigné (repos avec descriptions, READMEs de qualité, licences, profil accueillant) fait une excellente première impression et signale le professionnalisme ; un GitHub en désordre (repos sans description, READMEs vides, commits « asdf ») dévalue même du bon travail et donne envie de fermer l'onglet. Le polish ne prend qu'une journée mais change la première impression de TOUS les projets à la fois — un ratio impact/effort exceptionnel. Pour un candidat, un GitHub poli est ce qui transforme « des repos qui existent » en « un portfolio professionnel » — et c'est souvent ce qui fait la différence entre un profil qu'on creuse et un profil qu'on écarte.

Un repo sans README signale l'abandon, un GitHub en désordre dévalue même du bon code. Le polish prend une journée mais change la première impression de tous mes projets — un ratio impact/effort exceptionnel. Un GitHub poli transforme « des repos qui existent » en « un portfolio professionnel ».
