## 🎯 Objectif du jour
Distinguer fonctions pures et effets de bord, pratiquer l'immutabilité (spread, patterns de mise à jour), et restructurer un programme en cœur pur + coquille impure.

## 📖 Cours approfondi
**Concepts abordés :** Fonction pure (2 critères) · Effets de bord · Pourquoi pur = testable + cachable + prévisible · Immutabilité : patterns objet/tableau · Copie superficielle vs profonde · Architecture cœur pur / coquille impure.

Une fonction **pure** : (1) même entrée → même sortie, TOUJOURS ; (2) aucun **effet de bord** (ne modifie rien dehors : pas d'écriture fichier, pas de console.log, pas de mutation d'argument, pas de Math.random ni Date.now dedans).

Pourquoi c'est précieux — tu as déjà TOUT vécu :
- **Testable** : appelle, compare, fini (ta facture du jour 9 : le calcul se teste, l'affichage se regarde).
- **Cachable** : ton memoriser du jour 22 ne marche QUE sur du pur.
- **Prévisible** : pas de « ça marche chez moi » — rien de caché n'influence le résultat.

**L'immutabilité** est la discipline jumelle : ne jamais MODIFIER les données reçues, retourner des VERSIONS NEUVES. Les patterns à automatiser :
```js
{ ...obj, prix: 20 }                    // objet : changer un champ
{ ...obj, stats: { ...obj.stats, pv: 50 } }  // imbriqué : spread à CHAQUE niveau
[...arr, x]  /  arr.filter(...)          // ajouter / retirer
arr.map(o => o.id === id ? { ...o, done: true } : o)  // modifier UN élément
```
Le spread est SUPERFICIEL (un niveau) — tu l'as vu au jour 23 avec le catalogue : les objets imbriqués exigent un spread par niveau.

**L'architecture qui en découle** (le vrai sujet du jour) : un **cœur pur** (toute la logique : calculs, décisions, transformations — massivement testable) entouré d'une **coquille impure** (lecture fichier, affichage, horloge, aléatoire — le minimum vital aux frontières). Ton journal du jour 12 avait déjà cette forme (charger/sauvegarder vs logique). React (mois 4) l'impose, les tests (mois 4) la récompensent, l'hexagonal (mois 10) la généralise. Aujourd'hui : tu la pratiques consciemment.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : rendre `subirDegats` PURE (l'original du jour 10 mutait le personnage).

**Raisonnement** : au lieu de modifier, retourner un NOUVEAU personnage. Bénéfice : historique et undo gratuits.

**Solution & explication** :
```js
const subirDegats = (perso, n) => ({ ...perso, pv: Math.max(0, perso.pv - n) });
const p0 = { nom: "Kael", pv: 100, pvMax: 100 };
const p1 = subirDegats(p0, 30); // p1.pv = 70
console.log(p0.pv);             // 100 → INTACT
```
La fonction ne touche pas `perso` : elle construit une copie avec le pv modifié. Comme `p0` n'a pas bougé, on peut garder TOUT l'historique des états.

**Variante — undo gratuit** :
```js
const etats = [p0, p1];
etats.push(subirDegats(etats.at(-1), 20)); // nouvel état
etats.pop();                                // annuler = revenir en arrière
```
Impossible avec la version mutante : c'est la démonstration concrète de ce que l'immutabilité achète.

## 🎤 Question d'entretien
**Mise en situation : « Voici une fonction `ajouterTache(liste, texte)` qui fait `liste.push({texte, date: Date.now()})` puis renvoie `liste`. Pourquoi est-elle DIFFICILE à tester, et comment la rends-tu pure ? »**

*Ce que la question évalue :* la distinction fonction pure / effet de bord et la pratique de l'immutabilité — sur un cas concret de code impur à diagnostiquer.

**Réponse attendue :** deux problèmes. (1) Elle MUTE son argument (`push` modifie la `liste` de l'appelant) : effet de bord, comportement dépendant de l'extérieur. (2) Elle lit `Date.now()` : sa sortie n'est pas déterministe, donc un test ne peut pas prédire le résultat. Pour la rendre pure : retourner une NOUVELLE liste sans muster l'entrée (`return [...liste, { texte, date }]`), et INJECTER la date en paramètre (`ajouterTache(liste, texte, date)`) au lieu de la lire dans la fonction. Ainsi mêmes entrées → même sortie, sans effet de bord.

**Débutant / correct / excellent :** débutant = ne voit ni la mutation ni le non-déterminisme ; correct = identifie les deux et corrige (spread + date injectée) ; excellent = généralise (« isoler les effets aux bords, garder un cœur pur ») et explique pourquoi une fonction pure est triviale à tester.

**Relance possible :** « pourquoi une fonction pure est-elle plus facile à tester ? » → mêmes entrées → même sortie, sans montage ni horloge : on compare simplement la sortie à l'attendu.

**À éviter :** muter l'argument avec `push` ; lire l'horloge/le hasard au cœur de la logique ; croire que renvoyer la liste suffit alors qu'on l'a mutée.

**Formulation orale naturelle :** « Elle mute son argument avec `push` et lit `Date.now()`, donc elle est imprévisible : je renvoie une nouvelle liste avec le spread et j'injecte la date en paramètre — mêmes entrées, même sortie, testable. »

## 🧠 À retenir
- Fonction pure : même entrée → même sortie, zéro effet de bord → testable, cachable, prévisible.
- Immutabilité : retourner du neuf (`{ ...obj, cle: val }`) au lieu de muter ; spread à CHAQUE niveau imbriqué.
- Architecture cœur pur (logique) / coquille impure (I/O, affichage) : undo, rejeu et tests en découlent.
