## 🎯 Objectif du jour
Fixer le retrieval final.

## 📖 Cours approfondi
**Modèle mental : consolider un pipeline de retrieval, c'est le figer en UNE configuration par défaut + UN mode dégradé, chacun justifié par l'ablation.** La semaine 36 a empilé et MESURÉ quatre étages (lexical, vectoriel, hybride RRF, reranking). Le tableau d'ablation (jour 249) et le budget latence (jour 250) ont produit les chiffres ; aujourd'hui tu transformes ces chiffres en DÉCISION opérationnelle stable — la configuration de retrieval finale que le mois d'évaluation (semaine 37+) prendra comme référence.

La consolidation d'un système à plusieurs régimes a une spécificité par rapport à celle du jour 244 : tu ne figes pas UNE config, tu figes une POLITIQUE. Concrètement :
1. **La config par défaut** : hybride + reranking (qualité maximale mesurée : 24/26), pour l'usage interactif où ~1,1 s de p95 est toléré.
2. **Le mode dégradé** : hybride seul (22/26, mais p95 < 500 ms), activé sous contrainte de latence ou de budget — un PARAMÈTRE, jamais un fork de code (la leçon du jour 249).
3. **La règle de bascule** : QUI décide du mode, et sur quel critère observable (budget latence dépassé ? pic de charge ? appel API sans reranking pour un batch offline ?). Une politique sans règle de déclenchement est deux configs qui dorment.
4. **La justification traçable** : chaque choix pointe vers sa ligne d'ablation. « Reranking par défaut : +2 questions dont les 2 identifiants critiques, pour +900 ms tolérés en interactif — ablation jour 249 ». La config sans renvoi redevient un dogme.

Et la clôture méthodologique : cette config de retrieval est maintenant un COMPOSANT figé. Le mois d'évaluation ne va plus la bricoler — il va la MESURER de bout en bout (retrieval + génération) et attaquer ce qui reste, qui n'est probablement PAS le retrieval (rappel de la découverte des jours 244 et 249 : les synthèses résistent à tous les étages de retrieval). Consolider, c'est aussi savoir dire « cette partie est finie, le problème est ailleurs ».

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : la politique de retrieval (défaut + dégradé + bascule), justifiée et figée.

**Raisonnement** : compiler l'ablation et le budget en une politique à deux régimes, écrire la règle de bascule, taguer.

**La politique (le livrable)** :
```json
{
  "version": "retrieval-v2", "fige_le": "2026-XX-XX",
  "defaut": {
    "pipeline": ["hybride_rrf", "rerank_cross_encoder"],
    "k_moteur": 20, "k_final": 3,
    "qualite": "24/26 top-3", "p95_ms": 1100,
    "justif": "ablation j.249 : +2 vs hybride (dont 2 identifiants critiques) ; latence tenue au budget j.250"
  },
  "degrade": {
    "pipeline": ["hybride_rrf"],
    "qualite": "22/26 top-3", "p95_ms": 480,
    "justif": "perd 2 questions non critiques ; ÷2,3 sur la latence"
  },
  "bascule": "mode dégradé si budget latence < 500 ms OU traitement batch offline (le reranking coûte ×2, inutile hors interactif)",
  "fige": "le retrieval est un composant CLOS ; le mois d'éval mesure, ne bricole plus"
}
```

**Vérification de cohérence** :
```
1. Les deux régimes tournent et donnent les scores annoncés (re-passe rapide).
2. La bascule est un paramètre testé (force le mode dégradé, vérifie la latence).
3. Le harnais du jour 221 passe dans les DEUX modes.
4. Le manifeste d'index (jour 242) pointe vers retrieval-v2.
```

**Explication** : figer une POLITIQUE (deux régimes + règle) plutôt qu'une config unique est ce qui distingue un système de production d'un prototype — les vrais systèmes ont toujours un mode dégradé. **Variante** : ajoute un 3e régime « lexical seul » pour les requêtes 100 % identifiants (codes, références) détectées à l'entrée — un routage par TYPE de requête, avant-goût des agents (semaine 40).

## 🏢 Cas métier
Les systèmes de production sérieux ont TOUJOURS un mode dégradé : quand la charge explose ou qu'un service tiers ralentit, on sacrifie de la qualité pour rester disponible, par une bascule PRÉVUE — pas par une panne. Un RAG qui n'a que son mode « qualité maximale » tombe en entier au premier pic. Arriver en entretien avec « mon retrieval a un mode nominal et un mode dégradé, avec une règle de bascule » démontre une pensée de fiabilité que peu de juniors ont — c'est le vocabulaire des équipes SRE.

## 🎤 Question d'entretien
**« Ton pipeline de retrieval est optimisé : comment le figes-tu pour la suite ? »** → En une politique à deux régimes, pas une config unique : un mode par défaut (hybride + rerank, qualité max) et un mode dégradé (hybride seul, latence ÷2), chacun justifié par l'ablation, avec une règle de bascule sur critère observable (budget latence, batch offline). Le tout est un paramètre, jamais un fork. Et je déclare le retrieval CLOS : le mois d'évaluation le mesure de bout en bout, il ne le bricole plus — les problèmes restants sont ailleurs.
