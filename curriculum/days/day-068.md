## 🎯 Objectif du jour
Implémenter une auth par token propre et gérer les secrets hors du code.

## 📖 Cours approfondi
**Concepts abordés :** Token dans un header · Middleware d'auth · Secrets en .env · Pourquoi pas dans l'URL/le code.

L'authentification par token : le client envoie un secret dans le header `Authorization` à chaque requête ; un middleware le vérifie AVANT les routes protégées. Pourquoi le header et pas l'URL ? Les URLs sont loggées partout (serveurs, proxies, historiques) — un secret dans l'URL est un secret publié.

Les secrets vivent dans l'ENVIRONNEMENT (.env, jamais commité — vérifie ton .gitignore) : le code lit process.env.API_TOKEN. Le fichier .env.example (committé, sans les valeurs) documente les variables attendues.

Cette hygiène prépare le mois 8 : tes clés d'API LLM suivront exactement le même circuit. Un secret commité une fois est compromis pour toujours (l'historique Git n'oublie pas) — d'où l'audit systématique avant tout push public.

**Modèle mental : l'authentification par token, c'est le client qui envoie un secret dans le header `Authorization` À CHAQUE requête (HTTP est sans état, jour 50), et un MIDDLEWARE qui le vérifie AVANT les routes protégées. Pourquoi le header et pas l'URL ? Parce que les URLs sont LOGGÉES partout — serveurs, proxies, historiques de navigateur — donc un secret dans l'URL est un secret PUBLIÉ. Et les secrets vivent dans l'ENVIRONNEMENT (`.env`, jamais commité), jamais en dur dans le code.** Protéger les routes d'écriture de LivreAPI, c'est appliquer l'hygiène de secrets qui resservira pour tes clés d'API LLM (mois 8).

Pourquoi une authentification, et pourquoi par token. HTTP est sans état : le serveur ne « se souvient » de personne d'une requête à l'autre. Pour savoir QUI fait une requête, le client doit donc PROUVER son identité à CHAQUE appel — en joignant un token (un secret prouvant qu'il est autorisé). Le token est vérifié par le serveur avant de laisser passer vers une route sensible. C'est la conséquence directe du caractère sans état : l'auth se rejoue à chaque requête.

Le header Authorization, depuis les fondations. Le token voyage dans le header `Authorization: Bearer <token>`, PAS dans l'URL. Raison cruciale : les URLs sont enregistrées partout (logs de serveurs, de proxies, historique du navigateur, referers) — un secret dans une URL fuit dans tous ces journaux. Un header n'est pas loggé par défaut. C'est une règle de sécurité absolue : un secret ne va JAMAIS dans une URL.

Le middleware d'authentification, depuis les fondations. Un middleware (jour 53) placé AVANT les routes protégées lit le header `Authorization`, vérifie le token, et : soit il attache l'identité à `req` et appelle `next()` ; soit il répond 401 (non authentifié) et court-circuite. L'ORDRE compte : le middleware d'auth doit s'exécuter avant les routes qu'il protège. On protège typiquement les routes d'ÉCRITURE (POST/PUT/DELETE), en laissant éventuellement les lectures publiques.

Les secrets dans l'environnement, depuis les fondations. Un secret (token, clé d'API, mot de passe de base) ne vit JAMAIS dans le code (il serait publié dans Git, visible par tous). Il vit dans une variable d'ENVIRONNEMENT, lue via `process.env`, chargée depuis un fichier `.env` qui est GITIGNORÉ (jamais commité). Un fichier `.env.example` (commité, SANS les valeurs) documente les variables attendues. Cette hygiène prépare exactement la gestion des clés d'API LLM du mois 8.

La différence 401 vs autres. Sans token ou token invalide → 401 (non authentifié, jour 50). À distinguer de 403 (authentifié mais pas le droit). Un token présent mais faux reste un 401 : le serveur ne reconnaît pas l'identité.

Limites et compromis. Un token statique partagé est simple mais limité (pas d'expiration, pas d'identité par utilisateur) — les vrais systèmes utilisent des tokens signés (JWT) avec expiration, ou des sessions. Le token dans le header suppose HTTPS (sinon il transite en clair, jour 71). Et gérer les secrets en `.env` est le minimum ; en production, on utilise un gestionnaire de secrets dédié.

La règle du jour : **authentifie par token dans le header `Authorization` (jamais dans l'URL, qui est loggée partout), vérifié par un MIDDLEWARE placé avant les routes protégées (401 si absent/invalide). Range les secrets dans l'ENVIRONNEMENT (`.env` gitignored, `.env.example` commité), jamais en dur dans le code — l'hygiène qui resservira pour tes clés LLM.**

**Gérer un secret pour de vrai (fondation V24).** Un secret (mot de passe, token, clé d'API, clé privée) a un cycle de vie : il est **créé**, **stocké** dans un coffre (jamais en clair dans le code, une image, un log ou une ConfigMap), **injecté** au démarrage (variable d'environnement ou fichier monté, référencé et non copié), **utilisé** avec le **moindre privilège** (une clé ne peut que ce dont le service a besoin), et surtout **tourné** régulièrement. Deux gestes à ne jamais confondre : la **révocation** (invalider un credential — il devient inutilisable, même s'il a fuité) et la **rotation** (le remplacer par un nouveau). Face à une fuite, l'ordre correct est **révocation → rotation → redéploiement → audit** : on coupe d'abord, on remplace ensuite, on redéploie avec la nouvelle valeur, puis on comprend l'étendue. Le réflexe « je change le secret » (rotation) sans révoquer l'ancien laisse une fenêtre exploitable.

**Ce qui rend un secret « fuité ».** Dès qu'un secret apparaît dans un endroit non prévu — un commit Git (même supprimé ensuite : il reste dans l'historique), un log de CI (`echo $TOKEN`), une image de conteneur, une capture d'écran, un message — il doit être considéré comme **compromis**. On ne « fait pas comme si » : on le révoque. C'est pour cela qu'un dépôt sérieux a une **détection de secret** en pré-commit et en CI, et que les logs sont **masqués/rédigés**.

### Que faire dans ce cas ? (fuite de secret)

1. **Symptômes** : une clé/token apparaît dans un commit, un log, une image, un ticket.
2. **Première action** : **révoquer** le secret immédiatement (le rendre inutilisable). Ne PAS commencer par « le retirer du code » — le retirer ne le dé-compromet pas.
3. **À ne pas faire** : réécrire l'historique Git en pensant que « ni vu ni connu » ; garder le secret « le temps de », le poster dans un chat pour « demander de l'aide ».
4. **Collecte de preuves** : où le secret a-t-il fuité, depuis quand, qui/quoi a pu le lire, quelles ressources il ouvre.
5. **Confinement** : révocation faite, restreindre les accès de l'identité concernée.
6. **Correction** : **rotation** (nouveau secret), stockage dans un coffre, référence au lieu de valeur, purge des traces (logs, historique si possible).
7. **Validation** : le service fonctionne avec le nouveau secret ; l'ancien ne fonctionne plus.
8. **Communication** : informer l'équipe et, si des données ont pu être touchées, les personnes concernées — factuel, sans minimiser.
9. **Prévention** : détection de secret en pré-commit/CI, masquage des logs, moindre privilège, rotation planifiée. Un **post-mortem sans blâme** cherche la cause systémique (pourquoi le secret pouvait-il être en clair ?), pas un coupable.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : protéger les routes d'écriture de LivreAPI par un middleware d'auth token, avec le secret en `.env`.

**Exemple simple** : header vs URL. `Authorization: Bearer abc123` (header, non loggé) est sûr ; `POST /livres?token=abc123` (URL) publie le secret dans tous les logs et historiques. Le token va TOUJOURS dans le header.

**Raisonnement pas-à-pas** : (1) le secret vit dans `.env` (gitignored), lu via `process.env` ; (2) un middleware lit le header `Authorization`, compare le token ; (3) absent/invalide → 401 ; (4) le middleware est placé AVANT les routes d'écriture.

**Implémentation** :
```ts
import 'dotenv/config';
// .env (gitignored) :  API_TOKEN=un-secret-long-et-aleatoire
// .env.example (commité) :  API_TOKEN=
const TOKEN = process.env.API_TOKEN;                 // jamais en dur dans le code

// MIDDLEWARE d'auth : vérifie AVANT les routes protégées
function authRequise(req, res, next) {
  const header = req.get('Authorization') ?? '';
  const token = header.startsWith('Bearer ') ? header.slice(7) : null;
  if (!token || token !== TOKEN) {
    return res.status(401).json({ message: 'authentification requise' });   // 401
  }
  next();                                            // token valide -> on continue
}

// Lectures publiques, ÉCRITURES protégées (ordre : middleware AVANT la route)
app.get('/livres', listerLivres);                    // public
app.post('/livres', authRequise, creerLivre);        // protégé
app.delete('/livres/:id', authRequise, supprimerLivre);
```
Sans token → 401, mauvais token → 401, bon token → succès. Le secret vit dans `.env` (gitignored, avec un `.env.example` commité), jamais dans le code ni dans l'URL. Un audit de l'historique Git doit confirmer qu'aucun secret n'a jamais été commité.

## ⚠️ Erreurs fréquentes
- Token dans l'URL : fuite dans les logs, proxies et historiques — un secret publié.
- Secret en dur dans le code : publié dans Git, visible par tous.
- .env non gitignored ou secret déjà présent dans l'historique Git : la fuite persiste même après suppression.
- Middleware d'auth placé après la route, ou protégeant les mauvaises routes : la protection ne s'applique pas.

## 🏢 Cas métier
L'authentification et la gestion des secrets sont des fondamentaux de sécurité que TOUTE application exposée doit maîtriser, et leurs défaillances sont parmi les causes les plus fréquentes de brèches. Un secret commité dans Git (clé d'API, mot de passe de base) est une fuite classique et coûteuse — les dépôts publics sont scannés en continu par des bots qui exploitent les clés exposées en minutes ; même dans un dépôt privé, un secret dans l'historique reste une bombe. Le token dans l'URL qui fuit dans les logs est un autre cas réel. Les équipes matures imposent : secrets hors du code (variables d'environnement, gestionnaires de secrets comme Vault ou les secrets managés du cloud), tokens dans les headers, vérification par middleware, et scan de l'historique Git. Cette hygiène est directement transférable aux clés d'API LLM (mois 8), qui coûtent de l'argent réel si elles fuient. Savoir implémenter une auth par token propre, ranger les secrets dans l'environnement et vérifier qu'aucun n'a fuité dans Git est un attendu de base — et « où mets-tu tes secrets ? » est une question d'entretien fréquente.

## 🎤 Question d'entretien
**« Comment gères-tu l'authentification et les secrets d'une API ? »** → Pour l'authentification : comme HTTP est sans état, le client doit prouver son identité à chaque requête en joignant un token dans le header `Authorization: Bearer <token>` — JAMAIS dans l'URL, parce que les URLs sont loggées partout (serveurs, proxies, historique navigateur), donc un secret dans l'URL est publié. Un middleware placé AVANT les routes protégées lit le header, vérifie le token, et répond 401 s'il est absent ou invalide, sinon laisse passer. Je protège typiquement les routes d'écriture (POST/PUT/DELETE) en laissant éventuellement les lectures publiques. Pour les secrets : ils ne vivent JAMAIS dans le code — ils seraient publiés dans Git. Je les range dans des variables d'environnement, chargées depuis un fichier `.env` qui est gitignored, avec un `.env.example` commité (sans les valeurs) qui documente les variables attendues. Je vérifie aussi l'historique Git pour confirmer qu'aucun secret n'a jamais été commité. Cette hygiène est exactement celle que j'appliquerai à mes clés d'API LLM. **Relance possible** : « un token statique partagé suffit-il en production ? » → non : il n'a ni expiration ni identité par utilisateur ; en vrai on utilise des tokens signés (JWT) avec expiration ou des sessions, et le token suppose HTTPS pour ne pas transiter en clair.
