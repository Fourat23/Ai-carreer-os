## 🎯 Objectif du jour
Enrichir le retrieval.

## 📖 Cours approfondi
**Modèle mental : la similarité trouve ce qui RESSEMBLE, les métadonnées délimitent OÙ chercher.** « Que dit le contrat 2025 sur les pénalités ? » : la similarité seule remontera les passages sur les pénalités... de tous les contrats, 2023 inclus — et le meilleur score peut venir du mauvais document. Le filtrage par métadonnées ajoute la dimension que le vectoriel ignore : chercher la similarité DANS un sous-ensemble (ce document, cette section, ce type, cette date).

Mécanique : **filtrer d'abord, chercher ensuite**. On restreint les candidats par prédicat exact (`source == "contrat-2025.pdf"`, `type == "md"`, `section commence par "Sécurité"`), PUIS on calcule les similarités sur ce sous-ensemble. L'inverse (chercher large puis filtrer le top-k) est un piège : si les 3 meilleurs chunks globaux viennent du mauvais document, le filtre après coup te laisse zéro résultat alors que le bon document contenait des passages corrects — au rang 12 global mais au rang 1 de SON sous-ensemble.

Les métadonnées exploitables, tu les as posées aux jours 216 et 222 (source, type, page, section) — l'investissement paie aujourd'hui. Deux voies d'utilisation :
1. **Explicite** : l'utilisateur (ou ton code) précise le périmètre — un paramètre `--source` de plus dans la CLI.
2. **Inférée** : détecter le périmètre DANS la question (« dans le guide RH... » → filtre sur guide-rh). Puissant mais fragile — commence par l'explicite, l'inférence viendra avec les agents.

C'est aussi ta première marche vers les vector DB : le filtrage par métadonnées est LEUR fonctionnalité vedette (et coûteuse à bien faire à grande échelle) — l'implémenter à la main sur ton index JSON te fait comprendre exactement ce que tu achèteras demain.

## 🧭 Exemple guidé

**Énoncé** : filtrage par métadonnées + test prouvant qu'il change les résultats.

**Raisonnement** : implémenter filtre-puis-cherche, exposer dans la CLI, et construire LE cas de test où le filtre fait la différence.

**Implémentation** :
```python
def top_k_filtre(question: str, k=3, **filtres) -> list[tuple[float, dict]]:
    # filtres : source="guide-rh.md", type="pdf", section_prefixe="Sécurité"...
    candidats = [i for i, c in enumerate(chunks) if respecte(c["meta"], filtres)]
    if not candidats:
        return []                        # périmètre vide : à signaler, pas à masquer
    sous_matrice = M_norm[candidats]      # la matrice du jour 219, restreinte
    scores = sous_matrice @ embed(question)
    meilleurs = np.argsort(scores)[::-1][:k]
    return [(float(scores[j]), chunks[candidats[j]]) for j in meilleurs]

# CLI : rag ask "les pénalités ?" --source contrat-2025.pdf
```

**Le test qui prouve (à construire exprès)** :
```
1. Trouve une question dont la réponse existe dans DEUX documents avec des
   valeurs différentes (ex. : « délai de préavis » dans contrat-2023 et 2025).
2. Sans filtre → observe quel document gagne le top-k (souvent le mauvais).
3. Avec --source contrat-2025 → la réponse vient du bon, citations à l'appui.
4. Filtre sur une source inexistante → message clair « périmètre vide »,
   PAS un refus générique (l'utilisateur doit comprendre POURQUOI).
```

**Explication** : le cas « deux documents, deux valeurs » est le scénario réel (versions, années, produits) qui justifie le filtrage — sans lui, ton test ne prouve rien. **Variante** : mesure le bonus latence — filtrer d'abord RÉDUIT la matrice à multiplier : le filtrage est aussi une optimisation, note le chiffre.

## ⚠️ Erreurs fréquentes
- Filtrer le top-k après la recherche globale : le piège classique — résultats vides alors que la réponse existe dans le périmètre.
- Des filtres en substring flou (source contient « contrat ») quand l'utilisateur attend un match exact : définis la sémantique de chaque filtre.
- Ne pas distinguer « périmètre vide » de « rien de pertinent » : deux messages différents, deux actions utilisateur différentes.
- Construire le test avec une question qui n'existe que dans UN document : le filtre semblera marcher sans rien prouver.

## 🏢 Cas métier
Cas d'entreprise omniprésent : la base documentaire contient les politiques 2023, 2024 ET 2025 (l'historique est légalement conservé). Sans filtrage, l'assistant mélange les années — c'est LE bug qui fait perdre la confiance des utilisateurs en une démo. Le filtre par date/version de document est la première demande de tout déploiement réel, et tu sauras dire pourquoi il doit s'appliquer AVANT la similarité.

## 🎤 Question d'entretien
**« À quoi servent les métadonnées dans un RAG, au-delà des citations ? »** → À délimiter le périmètre de recherche : filtrer par prédicat exact (document, type, section, date) PUIS chercher la similarité dans le sous-ensemble. L'ordre compte : filtrer après coup peut vider le top-k alors que le bon document contenait la réponse — au mauvais rang global mais au premier rang de son périmètre. C'est aussi la fonctionnalité clé qu'on achète avec une vector DB.
