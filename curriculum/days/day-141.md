## 🎯 Objectif du jour
Choisir la source et les questions.

## 📖 Cours approfondi
**Modèle mental : cadrer un projet data, c'est choisir une SOURCE et formuler les 3 QUESTIONS auxquelles le tableau de bord répondra AVANT d'écrire une ligne de pipeline — parce que ce sont les questions qui DICTENT les données à extraire, les transformations à faire et les visualisations à produire. Sans questions, on extrait tout, on transforme au hasard, et on ne répond à rien.** DataPulse (Projet 4) est ton pipeline ETL + dashboard de bout en bout. Le réflexe débutant est de plonger dans les données et de « voir ce qu'on trouve » ; le réflexe professionnel est de partir des QUESTIONS et de remonter vers les données nécessaires.

Les trois décisions du cadrage :
1. **La source** : une source publique RÉELLE (données ouvertes, une API) — réelle parce qu'une donnée propre et jouet ne prouve rien et n'apprend rien. Critères de choix : accessible (tu peux l'extraire), assez riche pour porter 3 questions intéressantes, et pas trop volumineuse pour rester maîtrisable. Vérifie AVANT de t'engager qu'elle contient bien les colonnes qui répondront à tes questions.
2. **Les 3 questions** : des questions ANALYTIQUES précises et répondables avec la source (« comment le nombre de X évolue-t-il par mois ? », « quels sont les 5 Y les plus Z ? », « quelle est la répartition de W ? »). Chaque question doit être assez concrète pour dicter une agrégation (jour 130/137) et une visualisation (jour 145). Une question vague (« que disent les données ? ») ne guide rien.
3. **Le backlog** : la décomposition en incréments livrables qui suivent le pipeline — extract (142) → transform (143) → load (144) → dashboard (145) → doc (146). Chaque jour du projet produit un livrable vérifiable qui s'accroche au précédent.

Pourquoi les questions d'abord : elles sont le CONTRAT du projet. Elles déterminent quelles colonnes extraire (pas besoin de tout), quelles transformations sont nécessaires (celles qui préparent les réponses), et quelles visualisations construire (une par question). Un projet qui part des données sans questions produit un dashboard encombré qui ne répond à rien de précis — le défaut le plus courant des projets data de portfolio.

La règle du jour : **choisis une source réelle, formule 3 questions analytiques précises qu'elle peut réellement répondre, et laisse ces questions dicter tout le pipeline ; décompose en incréments livrables**. Le cadrage transforme « j'ai des données » en « je réponds à des questions » — la différence entre un tas de graphiques et une analyse.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : cadrer DataPulse — choisir une source publique, définir les 3 questions du dashboard, écrire le backlog.

**Exemple simple** : une bonne question dicte tout — « quelle est l'évolution mensuelle du nombre de vélos en libre-service ? » impose la colonne date (à extraire), une agrégation par mois (transform/groupby) et un graphique en ligne (dashboard). Une question précise EST une spécification.

**Raisonnement pas-à-pas** : vérifier que la source contient les colonnes voulues → formuler 3 questions répondables → pour chacune, tracer la donnée nécessaire → décomposer en incréments.

**Cadrage** :
```
SOURCE : [données publiques réelles, ex. open data transport] — vérifiée : contient date, station, valeur.

LES 3 QUESTIONS (chacune dicte donnée + agrégation + visualisation) :
  Q1 (évolution)   : "Comment le trafic évolue-t-il par mois ?"
                     → colonne date ; groupby mois (SUM) ; graphique en LIGNE
  Q2 (comparaison) : "Quelles sont les 5 stations les plus fréquentées ?"
                     → colonne station ; groupby + top 5 ; graphique en BARRES
  Q3 (répartition) : "Comment se répartit la fréquentation par jour de semaine ?"
                     → dérivée jour-de-semaine ; groupby ; HISTOGRAMME/barres

BACKLOG (incréments livrables, jours 142-146) :
  1. Extract (ingestion source + erreurs)   2. Transform (nettoyage + rapport qualité)
  3. Load (schéma + transactionnel)          4. Dashboard (3 graphiques = 3 réponses)
  5. README + ADR + démo
```

**Mini-quiz** : (a) Pourquoi formuler les questions AVANT de coder ? (b) Pourquoi une source réelle plutôt que jouet ? (c) Qu'est-ce qui rend une question exploitable ?
→ (a) elles dictent quelles données extraire, quelles transformations et quelles visualisations — sans elles, on extrait tout et on ne répond à rien ; (b) une donnée jouet propre ne prouve rien et n'apprend pas à gérer le réel (sale, manquant, volumineux) ; (c) être assez précise pour imposer une agrégation et une visualisation (pas « que disent les données ? »).

**Variante** : pour chacune de tes 3 questions, écris d'avance la forme du résultat (un tableau à telles colonnes, un type de graphique) — si tu ne peux pas, la question est trop vague et ne guidera pas ton pipeline.

## ⚠️ Erreurs fréquentes
- Partir des données sans questions : dashboard fourre-tout qui ne répond à rien de précis.
- Questions vagues (« que disent les données ? ») : elles ne dictent aucune agrégation ni visualisation.
- Source jouet propre : ne prouve rien et n'apprend pas à gérer le réel (sale, manquant, volumineux).
- Ne pas vérifier que la source contient les colonnes nécessaires : le projet cale à l'extraction.

## 🏢 Cas métier
Le cadrage par les questions est ce qui distingue un projet data qui a de la valeur d'un « dashboard fourre-tout » : en entreprise, un projet analytique commence par la question métier (« pourquoi le churn augmente-t-il ? ») et remonte vers les données nécessaires, jamais l'inverse. Un dashboard construit sans questions précises est encombré de graphiques que personne ne sait interpréter, et ne débloque aucune décision. Pour un portfolio, un projet DataPulse dont les 3 questions sont claires et dont chaque visualisation répond à l'une d'elles se comprend et se défend immédiatement — un recruteur voit la démarche analytique, pas juste la technique. Savoir partir des questions est une compétence d'analyste autant que d'ingénieur, et le socle de tout le projet.
