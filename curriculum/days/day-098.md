### Synthèse de la semaine
La semaine 14 a posé les fondations de React : penser en composants purs et props typées (jour 92), gérer l'état local sans le muter (93), afficher conditionnellement et mapper des listes avec des keys stables (94), consommer une API avec ses 3 états et un nettoyage d'effet (95), maîtriser les formulaires contrôlés validés (96), et centraliser le réseau dans une couche api robuste (97). Le fil rouge : **l'UI est une fonction pure du state ; on ne manipule jamais le DOM, on change le state et React recalcule l'écran**. Les deux disciplines qui reviennent partout : l'IMMUTABILITÉ (remplacer, pas muter) et la MACHINE À ÉTATS (chargement/erreur/données, toujours les trois). Tu as maintenant de quoi construire une vraie app front branchée sur ton API — ce que fera BiblioApp (Projet 3).

### Plan de remédiation (si un critère échoue)
- **State muté** (l'UI ne bouge pas après un changement) : rejoue le jour 93 — React compare les RÉFÉRENCES ; spread pour ajouter, map+spread pour modifier, filter pour retirer. C'est la cause n°1 des bugs front des débutants.
- **Effet mal maîtrisé** (dépendances oubliées, pas de nettoyage) : reprends le jour 95 — dépendances = tout ce que l'effet lit ; nettoyage = ignorer les réponses tardives. Un fetch a toujours 3 états.
- **key = index** : reviens au jour 94 — une key doit être une identité stable issue des données, sinon React apparie les mauvais éléments.
- **fetch en dur dans les composants** : centralise (jour 97) — vérifie res.ok (fetch ne rejette pas sur 404), types d'erreur, URL de base unique. Sans cette couche, BiblioApp deviendra vite ingérable.
- **Formulaire non contrôlé ou envoi non protégé** : rejoue le jour 96 — value depuis le state, validation dérivée, bouton désactivé pendant l'envoi.

### Questions d'entretien de la semaine
1. **« Pourquoi ne mute-t-on jamais le state en React ? »** Attendu : React re-rend en comparant les références ; muter ne change pas la référence donc ne re-rend pas ; l'immutabilité rend le state prévisible.
2. **« À quoi sert le tableau de dépendances de useEffect ? »** Attendu : dire quand l'effet se ré-exécute ; une dépendance oubliée = stale closure (valeur périmée) ; sans nettoyage, setState sur composant démonté.
3. **« Contrôlé vs non contrôlé : quelle différence ? »** Attendu : contrôlé = valeur dans le state (source de vérité), permet validation directe et pré-remplissage ; non contrôlé = valeur dans le DOM.
4. **« Pourquoi une couche api centralisée ? »** Attendu : une frontière unique (URL de base, en-têtes, res.ok, erreurs typées) ; fetch ne rejette pas sur 4xx/5xx ; un changement d'API ne touche qu'un fichier.
5. **« Que sont les 3 états d'un chargement de données ? »** Attendu : chargement, erreur, données — toujours les trois, un seul rendu à la fois, jamais 'données' sans données.
