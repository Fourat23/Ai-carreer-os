## 🎯 Objectif du jour
Écrire de vrais tests unitaires.

## 📖 Cours approfondi
**Modèle mental : un test unitaire FIGE un comportement attendu, et sa valeur se PROUVE en le faisant rougir — un test qui ne peut jamais échouer ne teste rien.** Écrire un test, ce n'est pas « vérifier que ça marche une fois » : c'est décrire, en code exécutable, ce que ta fonction DOIT faire, de sorte que toute régression future casse le test au lieu de casser la production silencieusement. Le test est un filet de sécurité ET une documentation vivante du comportement attendu.

L'anatomie d'un bon test unitaire (schéma AAA) :
1. **Arrange** : préparer les données d'entrée et le contexte.
2. **Act** : appeler la fonction testée UNE fois.
3. **Assert** : vérifier que la sortie est celle attendue — une assertion claire, focalisée sur UN comportement.

Un test unitaire vise une UNITÉ isolée (une fonction de validation, un calcul, un filtre) — pas toute l'app. Il doit être : RAPIDE (des millisecondes, on en lance des centaines), DÉTERMINISTE (même entrée → même résultat, sans dépendre du réseau ou de l'horloge — d'où les mocks, jour 108), et LISIBLE (son nom décrit le comportement : « rejette un email sans @ »).

Le geste qui distingue un vrai test d'un test décoratif : **le faire ROUGIR volontairement**. Écris le test, sabote le code (change un `>` en `>=`, retourne `null`) et VÉRIFIE que le test échoue. Un test qui reste vert alors que tu as cassé le code ne protège de rien — c'est un faux sentiment de sécurité, pire que pas de test. On teste les cas NORMAUX, les cas LIMITES (vide, zéro, négatif, très grand) et les cas d'ERREUR (entrée invalide) — c'est aux limites que les bugs se cachent.

La règle du jour : **un test prouve sa valeur par sa capacité à échouer quand le code est faux**. Couvrir la logique métier (validation, calculs, filtres) par des tests qui rougissent quand on les sabote transforme « je crois que ça marche » en « je peux prouver que ça marche, et je serai alerté si ça casse ».

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire 10+ tests sur une logique métier et prouver qu'ils rougissent.

**Exemple simple** : un test AAA minimal — `test('rejette un email sans @', () => { expect(valider('bob')).toBe(false); })`. Un comportement nommé, un appel, une assertion. Dix tests, c'est dix fois cette structure sur des cas différents.

**Raisonnement pas-à-pas** : lister les comportements (normaux + limites + erreurs) → un test AAA par comportement → lancer (vert) → SABOTER le code → vérifier que ça rougit → réparer.

**Solution** :
```ts
import { describe, test, expect } from 'vitest';
import { validerLivre, filtrerParTitre } from './metier';

describe('validerLivre', () => {
  test('accepte un livre complet', () => expect(validerLivre({ titre: 'A', auteur: 'B' }).ok).toBe(true));
  test('rejette un titre vide', () => expect(validerLivre({ titre: '', auteur: 'B' }).ok).toBe(false));
  test('rejette des espaces seuls (cas limite)', () => expect(validerLivre({ titre: '   ', auteur: 'B' }).ok).toBe(false));
});
describe('filtrerParTitre', () => {
  const livres = [{ titre: 'React' }, { titre: 'Rust' }];
  test('filtre insensible à la casse', () => expect(filtrerParTitre(livres, 'r').length).toBe(2));
  test('liste vide si aucun match', () => expect(filtrerParTitre(livres, 'zzz')).toEqual([]));
});
// PREUVE : change 'titre.trim()' en 'titre' dans validerLivre → le test des espaces DOIT rougir.
```

**Mini-quiz** : (a) Que prouve le fait de saboter le code volontairement ? (b) Pourquoi un test doit-il être déterministe ? (c) Où se cachent le plus souvent les bugs ?
→ (a) que le test peut vraiment échouer, donc qu'il protège d'une régression ; (b) sinon il rougit/verdit au hasard (réseau, horloge), on ne peut pas s'y fier ; (c) aux cas limites (vide, zéro, espaces, très grand) et d'erreur.

**Variante** : pour chaque fonction, ajoute un test de cas limite auquel tu n'avais pas pensé (chaîne très longue, caractères spéciaux) — c'est souvent là qu'un vrai bug apparaît.

## 🏢 Cas métier
Les tests unitaires sont le socle de la confiance en entreprise : ils permettent de refactorer et de livrer sans peur, car une régression casse un test avant d'atteindre la production. Le contre-exemple classique est le test « décoratif » qui ne peut pas échouer (il teste que `2+2===4` sans toucher au code métier, ou il n'a pas d'assertion réelle) — il gonfle la couverture sans rien protéger. Les équipes sérieuses vérifient qu'un test ROUGIT quand on casse le code (parfois via le « mutation testing »). Savoir écrire des tests qui échouent utilement, en couvrant les cas limites, est une compétence directement évaluée et un prérequis pour travailler sur une base de code partagée.

## 🎤 Question d'entretien
**« Qu'est-ce qui fait un bon test unitaire ? »** → Il fige UN comportement attendu (schéma Arrange-Act-Assert), il est rapide, déterministe (même entrée → même résultat, sans dépendre du réseau ou de l'horloge) et lisible (son nom décrit le comportement). Surtout, sa valeur se prouve par sa capacité à ROUGIR : j'écris le test, je sabote volontairement le code, et je vérifie qu'il échoue — un test qui reste vert quand le code est cassé ne protège de rien, c'est pire que pas de test. Je couvre les cas normaux, limites (vide, zéro, négatif) et d'erreur, parce que c'est aux limites que les bugs se cachent. Un test unitaire vise une unité isolée ; ses dépendances externes sont mockées pour rester déterministe.
