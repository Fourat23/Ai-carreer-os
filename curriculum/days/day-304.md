## 🎯 Objectif du jour
Concevoir les données.

## 📖 Cours approfondi
**Modèle mental : le modèle de données est le squelette invisible de DocSense — mal conçu, il contraint tout le reste ; bien conçu, il rend les fonctionnalités naturelles.** Avant de coder les features, tu conçois COMMENT les données sont structurées et reliées : documents, chunks, évaluations, sessions. C'est un exercice de modélisation (tes acquis SQL/database-modeling du mois 5) appliqué à une app IA, avec ses entités spécifiques (chunks vectorisés, résultats d'évaluation, historique de conversation).

Les entités de DocSense et leurs relations :
1. **Document** : un fichier ingéré — source, format, date d'ingestion, hash (pour l'idempotence, jour 223), métadonnées. C'est l'unité que l'utilisateur uploade.
2. **Chunk** : un morceau de document — texte, position, métadonnées (section, page), et le vecteur d'embedding. Relation : un document a plusieurs chunks (1-N). L'identité stable du chunk (hash contenu+source) permet la ré-indexation sans doublons.
3. **Évaluation** : un résultat de mesure — question du golden set, réponse produite, scores (rappel@k, fidélité, exactitude), version du système, date. Relation : liée à une version d'index/config. C'est ce qui permet de suivre la qualité dans le temps (dashboard, jour 318).
4. **Session** : une conversation — historique des questions/réponses, correlation id (jour 297), coût cumulé. Relation : une session a plusieurs échanges. C'est ce qui porte le multi-tours et la traçabilité.

Les décisions de modélisation à justifier :
- **Où vivent les vecteurs** : dans la vector DB (Chroma) séparément, ou avec les chunks ? Le lien entre un chunk (métadonnées, texte) et son vecteur doit être clair (un id partagé).
- **La normalisation vs la dénormalisation** : faut-il dupliquer certaines données pour la performance (ex. le texte du chunk stocké avec l'évaluation pour l'auditer sans jointure) ? Un arbitrage classique (mois 5).
- **Le versioning** : le modèle doit porter la version de l'index/config (jour 242) pour que les évaluations soient comparables et l'index reconstructible.

Pourquoi ça compte : le modèle de données détermine ce qui sera FACILE ou PÉNIBLE à faire ensuite. Vouloir un dashboard de qualité par version (jour 318) est trivial si l'évaluation porte sa version, impossible sinon. Concevoir le modèle en pensant aux fonctionnalités À VENIR (dashboard, ré-indexation, multi-tours, audit) évite de se retrouver bloqué. Un modèle de données justifié est aussi un artefact que les recruteurs data/backend savent lire — il révèle si tu penses en structures durables.

## ⚠️ Erreurs fréquentes
- Un modèle qui ne porte pas le versioning : le dashboard de qualité par version (jour 318) devient impossible — anticiper les fonctionnalités.
- Ids de chunks instables : la ré-indexation crée des doublons — un id = hash(contenu+source) assure l'idempotence (jour 223).
- Vecteurs et chunks mal reliés : sans id partagé clair, retrouver le texte d'un vecteur devient un casse-tête.
- Tout normaliser par dogme : parfois dupliquer (le texte du chunk dans l'audit d'évaluation) évite des jointures coûteuses — arbitrer selon l'usage.

## 🏢 Cas métier
Le modèle de données est ce qui détermine la vélocité future d'un projet : un modèle qui a anticipé les fonctionnalités (versioning des évaluations, id stables pour la ré-indexation, correlation id pour la traçabilité) rend les features suivantes naturelles ; un modèle bâclé force des migrations douloureuses et des contorsions. En entreprise, les modèles de données mal conçus au départ sont la source n°1 de dette technique structurelle — coûteuse et durable. Un ingénieur qui conçoit un modèle justifié, pensé pour les fonctionnalités à venir, démontre une compétence de conception que les recruteurs data/backend savent immédiatement évaluer — et pour DocSense, c'est ce qui rend le build des 7 semaines suivantes fluide.
