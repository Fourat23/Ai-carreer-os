## 🎯 Objectif du jour
Consolider le style fonctionnel typé : fonctions pures typées, composition, immutabilité avec readonly.

## 📖 Cours approfondi
**Concepts abordés :** Fonctions pures typées · readonly / as const · compose/pipe typés · FP vs POO : le choix.

Typer les fonctions d'ordre supérieur révèle leur logique profonde : `compose<A, B, C>(f: (b: B) => C, g: (a: A) => B): (a: A) => C` dit exactement la contrainte de composition — la sortie de g doit nourrir l'entrée de f. Si les types ne s'emboîtent pas, la composition n'a pas de sens, et le compilateur le dit AVANT l'exécution.

`readonly` et `as const` font vérifier l'immutabilité (jour 26) par le compilateur : muter un `readonly string[]` est une erreur de compilation. La discipline devient un contrat outillé.

C'est le pattern général de TypeScript : transformer tes conventions (pureté, immutabilité, contrats) en règles VÉRIFIÉES mécaniquement.

**Modèle mental : typer les fonctions d'ordre supérieur transforme tes CONVENTIONS (pureté, immutabilité, composition) en CONTRATS vérifiés par le compilateur. `compose<A, B, C>(f: (b: B) => C, g: (a: A) => B)` DIT que la sortie de g doit nourrir l'entrée de f — si les types ne s'emboîtent pas, la composition n'a pas de sens, et tsc le refuse avant l'exécution. `readonly` fait de l'immutabilité une règle mécanique : muter devient une erreur de compilation, pas une discipline qu'on espère tenir.** La programmation fonctionnelle typée, c'est rendre le pipeline de données PROUVÉ correct dans ses assemblages.

Pourquoi la FP typée est puissante. En JavaScript, la pureté et l'immutabilité sont des CONVENTIONS : rien n'empêche de muter un tableau censé être constant, ou de composer deux fonctions dont les types ne collent pas — le bug n'apparaît qu'à l'exécution. Le typage transforme ces intentions en garde-fous : le compilateur vérifie que les compositions s'emboîtent et que rien ne mute ce qui est `readonly`. On passe d'une discipline personnelle à une garantie outillée.

Les briques, depuis les fondations. Une **fonction pure typée** : sa signature promet une sortie déterministe pour des entrées données, sans effet de bord — testable en isolation. La **composition** (`compose`/`pipe`) enchaîne des transformations : `pipe(nettoyer, valider, formater)` lit le pipeline dans l'ordre. Le générique `pipe<A, B, C>` garantit que chaque étape reçoit le type que la précédente produit. L'**immutabilité** avec `readonly`/`as const` : `readonly string[]` interdit `push`/`pop` à la compilation ; `as const` fige un littéral en type le plus précis (et immuable).

La différence FP vs POO, pour choisir. La POO regroupe état + comportements dans des objets (jour 38) ; la FP sépare les DONNÉES (immuables) des TRANSFORMATIONS (fonctions pures). Un pipeline de données pur est plus facile à raisonner (pas d'état caché), à tester (entrée → sortie) et à paralléliser. La POO brille pour modéliser un domaine avec état encapsulé et polymorphisme. Ce ne sont pas des rivales : on choisit selon le problème, et TS supporte les deux.

L'apport concret du typage sur la composition. Sans types, `compose(f, g)` peut assembler deux fonctions incompatibles silencieusement (le bug surgit à l'appel). Avec `compose<A, B, C>`, le compilateur EXIGE que `g: A → B` et `f: B → C` : impossible de mal brancher le pipeline. Le typage n'est pas décoratif ici — il attrape une classe entière d'erreurs d'assemblage.

Limites et compromis. Les génériques de `compose`/`pipe` variadiques (nombre d'étapes variable) sont NOTABLEMENT difficiles à typer parfaitement — d'où les surcharges dans les bibliothèques (Ramda, fp-ts). Un générique trop lâche perd le type au milieu du pipeline (retombe à `any`), un trop strict devient illisible. L'immutabilité par copie a un coût mémoire (nouveaux objets) rarement problématique mais réel sur de très gros volumes. Et la FP poussée à l'extrême (point-free, monades) peut nuire à la lisibilité pour une équipe non familière.

La règle du jour : **type tes fonctions d'ordre supérieur pour transformer pureté et immutabilité en contrats vérifiés — compose/pipe génériques qui garantissent l'emboîtement des étapes, readonly qui interdit la mutation à la compilation. Choisis FP (données + transformations pures) ou POO (état encapsulé + polymorphisme) selon le problème, sans dogme.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire un `pipe` typé générique et un mini-pipeline de traitement 100 % pur, où le compilateur garantit l'emboîtement des étapes et interdit la mutation.

**Exemple simple** : la valeur du typage sur pipe. `pipe(doubler, versChaine)` doit refuser `pipe(versChaine, doubler)` si `doubler` attend un nombre mais reçoit une chaîne — le compilateur attrape le mauvais branchement avant l'exécution.

**Raisonnement pas-à-pas** : (1) je type `pipe` pour que chaque étape reçoive le type produit par la précédente ; (2) j'écris des transformations PURES (pas d'effet de bord) ; (3) je marque les données `readonly` pour que le compilateur interdise toute mutation ; (4) je vérifie que réordonner mal les étapes provoque une erreur de compilation.

**Implémentation** :
```ts
// pipe typé à 3 étapes : chaque sortie nourrit l'entrée suivante
function pipe<A, B, C>(f: (a: A) => B, g: (b: B) => C): (a: A) => C {
  return (a: A) => g(f(a));
}

// transformations PURES et typées
const doubler = (n: number): number => n * 2;
const versLabel = (n: number): string => `valeur=${n}`;

const traiter = pipe(doubler, versLabel);
console.log(traiter(21));         // "valeur=42"
// pipe(versLabel, doubler)       // ❌ tsc : string non assignable à number

// immutabilité vérifiée : le compilateur interdit la mutation
function total(readonlyLignes: readonly number[]): number {
  // readonlyLignes.push(0);      // ❌ tsc : push n'existe pas sur readonly[]
  return readonlyLignes.reduce((s, x) => s + x, 0);   // lecture pure
}
console.log(total([10, 20, 12]));  // 42
```
Le mauvais ordre des étapes et la tentative de mutation sont TOUS DEUX attrapés à la compilation : la convention est devenue un contrat.

- Imposer la FP partout par dogme là où la POO (état encapsulé) serait plus claire.

## 🏢 Cas métier
Le style fonctionnel typé domine le traitement de données moderne, du front (transformations d'état immuables dans React/Redux) au back (pipelines ETL, transformation de flux). Sa valeur en entreprise : des transformations PURES et immuables sont prévisibles (pas d'état caché qui surprend), testables unitairement (entrée → sortie, sans montage de fixtures), et sûres à composer et paralléliser. Le typage ajoute la garantie que les pipelines s'assemblent correctement — une classe d'erreurs éliminée avant tout test. Concrètement, savoir écrire des fonctions pures typées, composer proprement et exploiter `readonly` est directement valorisé sur les postes front (gestion d'état immuable) et data (pipelines) ; et savoir ARBITRER FP vs POO selon le problème, plutôt que d'imposer un dogme, est un signe de maturité que les leads recherchent.

## 🎤 Question d'entretien
**« Qu'apporte le typage à la programmation fonctionnelle, et quand choisis-tu FP plutôt que POO ? »** → Le typage transforme les CONVENTIONS de la FP en contrats vérifiés. La pureté et l'immutabilité, en JS, ne sont qu'une discipline ; en TS, `readonly` fait de la mutation une erreur de compilation, et un `compose`/`pipe` générique garantit que chaque étape reçoit le type produit par la précédente — impossible d'assembler un pipeline incompatible, le bug d'branchement est attrapé avant l'exécution. Pour le choix FP vs POO : la FP sépare les données immuables des transformations pures, idéale pour les pipelines de données faciles à raisonner et à tester (entrée → sortie, pas d'état caché) ; la POO regroupe état et comportements, idéale pour modéliser un domaine avec encapsulation et polymorphisme. Ce ne sont pas des rivales : je choisis selon le problème, et TypeScript supporte les deux. **Relance possible** : « pourquoi les compose variadiques sont-ils durs à typer ? » → parce qu'un nombre variable d'étapes exige des surcharges génériques ; trop lâche, le type se perd au milieu (retour à any), d'où les surcharges des bibliothèques comme fp-ts.
