## 🎯 Objectif du jour
Consolider en refactorant une API vers une structure propre, testée, documentée.

## 📖 Cours approfondi
**Concepts abordés :** Refactoring guidé · Séparation des couches · Tests comme filet · Dette technique.

Refactorer = améliorer la STRUCTURE sans changer le COMPORTEMENT. La garantie que le comportement n'a pas changé, ce sont les tests : d'abord verrouiller par des tests ce qui marche, ensuite seulement restructurer, en relançant les tests à chaque étape. Refactorer sans filet, c'est casser en croyant améliorer.

La méthode : par PETITES étapes (extraire une fonction, déplacer un module, renommer) — jamais de « grande réécriture » qui te laisse trois jours avec un système cassé. Chaque étape laisse le système fonctionnel et committable.

La dette technique se documente : ce qui reste imparfait, pourquoi c'est accepté, et le signal qui obligera à payer la dette. Une dette CONSCIENTE est une décision de gestion ; une dette ignorée est une bombe.

**Modèle mental : refactorer, c'est améliorer la STRUCTURE d'un code SANS changer son COMPORTEMENT — et la garantie que le comportement n'a pas changé, ce sont les TESTS. La méthode : d'abord VERROUILLER par des tests ce qui marche, ensuite SEULEMENT restructurer, en relançant les tests à chaque étape. Refactorer sans filet, c'est casser en croyant améliorer. Et on procède par PETITES étapes committables (extraire une fonction, déplacer un module, renommer), jamais par « grande réécriture » qui laisse trois jours avec un système cassé.** Consolider le mois 3, c'est prendre ton API la plus faible et la porter à une structure propre, testée, documentée — sous filet.

Pourquoi refactorer, et pourquoi sous tests. Le code accumule de la DETTE : à force d'ajouts rapides, la structure se dégrade (logique dans les routes, erreurs dupliquées, config en dur). Refactorer paie cette dette pour retrouver de la vélocité. Mais toucher à la structure risque de casser le comportement — sauf si des tests le VERROUILLENT d'abord. Les tests transforment le refactoring d'un pari (« j'espère ne rien casser ») en une opération sûre (« les tests confirment que le comportement est identique »). Sans tests, on ne refactore pas : on réécrit à l'aveugle.

La méthode des petites étapes, depuis les fondations. On ne fait JAMAIS une « grande réécriture » (big-bang) : elle laisse le système cassé pendant des jours, cumule les changements, et devient impossible à déboguer. On procède par PETITES étapes, chacune laissant le système FONCTIONNEL et COMMITTABLE : extraire une fonction, déplacer un module, renommer, centraliser les erreurs. Après chaque étape, on relance les tests. Un historique de petites étapes vertes est traçable et réversible ; un big-bang est un saut dans le vide.

Ce qu'on refactore dans une API, depuis les fondations. Les cibles typiques : SÉPARER les couches (sortir la logique des routes vers les services, jour 53), CENTRALISER les erreurs (un middleware unique, jour 54), SORTIR la config (secrets et paramètres en variables d'environnement, jour 68), NOMMER clairement (jour 40). Chaque amélioration réduit le couplage et clarifie les responsabilités, sans changer ce que l'API FAIT.

La dette technique, à documenter. La dette est ce qui reste imparfait après le refactoring : ce qu'on n'a pas eu le temps de traiter, un compromis assumé, un TODO justifié. On la DOCUMENTE (quoi, pourquoi accepté, quel signal déclencherait son paiement) plutôt que de la laisser invisible. Documenter la dette, c'est la rendre gérable au lieu de subie.

Limites et compromis. Refactorer sans tests est dangereux — mais écrire les tests d'abord a un coût (temps) qu'on est tenté de zapper : c'est justement là que le refactoring échoue. Tout refactorer d'un coup est un anti-pattern (big-bang) ; améliorer par petites étapes est plus lent mais sûr. Et il faut savoir S'ARRÊTER : refactorer à l'infini (« encore un peu plus propre ») a un rendement décroissant — on vise « assez propre pour la suite », pas la perfection.

La règle du jour : **refactore = améliorer la structure SANS changer le comportement, garanti par des tests écrits AVANT ; procède par PETITES étapes committables (jamais un big-bang), en relançant les tests à chaque fois ; cible les couches, les erreurs centralisées, la config sortie ; et DOCUMENTE la dette restante (quoi, pourquoi, signal de paiement).**

---

**La dette technique en détail — la mesurer, l'arbitrer, la rembourser.** Le refactoring paie une dette ; encore faut-il savoir laquelle. La *dette technique* est l'écart entre le code tel qu'il est et le code qu'il faudrait pour rester modifiable à coût raisonnable. Modèle mental : comme une dette financière, elle a un PRINCIPAL (le travail de remise en état) et des INTÉRÊTS (le surcoût payé à CHAQUE modification tant qu'elle n'est pas remboursée). Conséquence directe : une dette dans un code qu'on ne touche jamais coûte presque rien ; la même dette dans un code modifié chaque semaine coûte énormément. On ne rembourse donc pas la dette « la plus laide » mais celle dont les INTÉRÊTS sont les plus élevés.

**Quatre origines (matrice de Fowler)** : dette VOLONTAIRE et prudente (« on livre vite, on nettoiera » — un choix assumé et écrit) opposée à INVOLONTAIRE et imprudente (« on ne savait pas mieux » — ignorance) ; et dette DÉLIBÉRÉE opposée à celle par NÉGLIGENCE. La dette volontaire, documentée avec son signal de paiement, est saine ; la dette involontaire accumulée en silence est le vrai danger.

**Cinq natures** : dette de CODE (duplication, fonctions trop longues, couplage fort — les *code smells*, symptômes d'un problème plus profond), de TESTS (couverture absente → refactoring impossible sous filet, jour 69), d'ARCHITECTURE (frontières floues entre modules — la plus chère à rembourser), de DOCUMENTATION (le savoir vit dans les têtes, perdu au départ d'une personne), d'INFRASTRUCTURE (dépendances périmées, environnement reconstruit à la main). Distinguer aussi la dette LOCALE (contenue dans un module, remboursable seule et sans risque) de la dette SYSTÉMIQUE (elle traverse tout le système — remboursement coûteux et risqué, souvent via un *strangler* progressif, jour 85).

**La gérer plutôt que la subir.** On tient un REGISTRE DE DETTE (un backlog dédié, pas des TODO éparpillés) : chaque entrée note l'emplacement, l'intérêt payé (à quelle fréquence ce code fait mal), le coût de remboursement estimé et le signal déclencheur. On PRIORISE par **impact × risque × effort** : rembourser d'abord la dette à fort intérêt sur un code modifié souvent, jamais la dette « laide mais stable ». Au quotidien, la règle du BOY-SCOUT (« laisse le code plus propre que tu ne l'as trouvé ») rembourse la dette locale par petites touches, sans projet dédié. Contre-exemple classique : réécrire entièrement un module « parce qu'il est moche » alors qu'il est stable et jamais modifié — c'est dépenser du principal sans aucun intérêt à récupérer.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : refactorer une route qui contient toute la logique vers une structure en couches, sous protection d'un test écrit AVANT.

**Exemple simple** : le filet d'abord. Avant de toucher à une route qui fait tout (validation + SQL + réponse), j'écris un test d'intégration qui verrouille son comportement actuel. Ensuite je restructure : si le test reste vert, le comportement n'a pas changé. Sans ce test, je refactore à l'aveugle.

**Raisonnement pas-à-pas** : (1) j'écris un test qui verrouille le comportement ACTUEL ; (2) j'extrais la logique de la route vers un service (petite étape) ; (3) je relance le test (vert = comportement inchangé) ; (4) je commit ; (5) étape suivante (centraliser les erreurs, sortir la config), test à chaque fois.

**Avant / Après** :
```ts
// AVANT : tout dans la route (intestable sans serveur, dupliqué)
app.post('/livres', (req, res) => {
  if (!req.body.titre) return res.status(400).json({ e: 'titre' });   // validation
  const info = db.prepare('INSERT INTO livres (titre) VALUES (?)').run(req.body.titre); // SQL
  res.status(201).json({ id: info.lastInsertRowid });                 // réponse
});
```
```ts
// 1. TEST écrit AVANT (verrouille le comportement)
test('POST /livres crée et renvoie 201', async () => {
  const r = await fetch(url, { method: 'POST', headers: h, body: '{"titre":"X"}' });
  assert.equal(r.status, 201);
});

// 2. APRÈS : couches séparées (petite étape, test toujours vert)
const serviceLivres = {
  creer: (titre: string) => {
    if (!titre?.trim()) throw new ErreurValidation('titre requis');   // logique -> service
    return dataLivres.inserer(titre.trim());                          // SQL -> data
  },
};
app.post('/livres', (req, res) => {
  const cree = serviceLivres.creer(req.body.titre);   // la route ne fait que traduire
  res.status(201).json(cree);
});
// erreurs centralisées (middleware), config en .env : étapes suivantes, test à chaque fois
```
Le test écrit AVANT garantit que le comportement est identique après restructuration ; les petites étapes committables rendent le refactoring sûr et réversible ; la dette restante (ex. « validation encore manuelle ») est documentée.

## ⚠️ Erreurs fréquentes
- Refactorer sans tests : on casse le comportement en croyant l'améliorer, régressions silencieuses.
- Big-bang (tout réécrire d'un coup) : système cassé pendant des jours, impossible à déboguer, souvent abandonné.
- Ne pas commiter les petites étapes : perte de la traçabilité et de la réversibilité.
- Laisser la dette restante invisible au lieu de la documenter : elle est subie au lieu d'être gérée.

## 🏢 Cas métier
Le refactoring sous tests est une compétence quotidienne et à fort enjeu en entreprise : le code vit des années, s'alourdit de dette, et doit être régulièrement assaini pour rester modifiable. Un développeur qui refactore SANS tests introduit des régressions silencieuses — il « améliore » et casse en même temps, ce qui érode la confiance de l'équipe. Un développeur qui verrouille par des tests puis avance par petites étapes committables améliore le code en toute sécurité, et son historique raconte une progression maîtrisée. Le big-bang (« je réécris tout ») est un anti-pattern classique qui échoue souvent : des semaines sans livrer, un système cassé, un abandon fréquent. Les équipes matures refactorent en continu, par petites touches, protégées par une suite de tests, et gèrent la dette technique explicitement (backlog de dette, règle du boy-scout « laisse le code plus propre que tu ne l'as trouvé »). Savoir refactorer sous filet et documenter la dette est un signal de maturité directement évalué — et « comment refactores-tu un code legacy sans le casser ? » est une question d'entretien fréquente.

## 🎤 Question d'entretien
**« Comment refactores-tu un code existant sans casser son comportement ? »** → La règle absolue : je ne refactore JAMAIS sans filet. Refactorer, c'est améliorer la STRUCTURE sans changer le COMPORTEMENT, et la seule garantie que le comportement n'a pas changé, ce sont les tests. Donc je commence par VERROUILLER par des tests ce qui marche aujourd'hui — même du code que je vais restructurer, j'écris d'abord un test qui capture son comportement actuel. Ensuite seulement je restructure, par PETITES étapes committables : extraire une fonction, sortir la logique d'une route vers un service, centraliser les erreurs, sortir la config en environnement — et je relance les tests à CHAQUE étape. Si un test casse, je sais exactement quelle petite étape l'a cassé. Je ne fais jamais de « grande réécriture » big-bang, qui laisse le système cassé pendant des jours et devient impossible à déboguer. Enfin, je DOCUMENTE la dette restante : ce qui reste imparfait, pourquoi c'est accepté, et quel signal déclencherait son paiement. **Relance possible** : « et si le code legacy n'a aucun test ? » → j'écris d'abord des tests de caractérisation qui capturent le comportement actuel (même bizarre), pour créer le filet ; ensuite je refactore. On ne peut pas refactorer sûrement du code non testé sans d'abord le rendre testable.
