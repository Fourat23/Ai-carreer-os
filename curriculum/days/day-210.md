## 🔁 Revue hebdomadaire

**Thème de la semaine :** Prompt engineering, structured outputs, function calling + revue mensuelle 7

### Bilan
Le prompt comme spécification, pas comme incantation : rôle, contraintes, exemples, format de sortie imposé et VALIDÉ par le code. La semaine ferme le mois 7 : revue mensuelle 7 en fin de semaine.

### Test pratique
90 min : construis un extracteur d'informations (texte libre → JSON strict : personnes, dates, montants) — prompt versionné, schéma validé côté code, 10 cas de test dont 3 pièges, taux de réussite mesuré.

### Test théorique
Pourquoi 'réponds en JSON' ne suffit pas ; few-shot : quand ça aide vraiment ; pourquoi versionner ses prompts ; que faire quand la sortie ne parse pas (stratégies) ; system vs user prompt ?

### Mini-projet / livrable
Bibliothèque perso de 5 patterns de prompts testés (extraction, classification, résumé contraint, réécriture, critique) avec leurs cas de test.

### Checklist
- [ ] Sorties TOUJOURS validées par le code
- [ ] Prompts dans des fichiers versionnés, pas en dur
- [ ] Chaque pattern a ses cas de test
- [ ] Retry avec message d'erreur en cas de parse fail
- [ ] Revue mensuelle 7 faite

### Critères de passage à la semaine suivante
- [ ] Extracteur ≥ 8/10 cas réussis
- [ ] 5 patterns documentés et testés
- [ ] Auto-éval llm ≥ 3
- [ ] Revue mensuelle 7 complétée

### Exercice de réflexion architecturale
Ton extracteur est appelé 10 000 fois/jour. Où mets-tu la validation, le retry, le fallback, le log des échecs ? Dessine le composant 'appel LLM robuste' réutilisable.

### Synthèse de la semaine
La semaine 30 a fait passer du LLM « qu'on interroge » au LLM « qui fait un travail FIABLE dans une application ». Compétences réellement évaluées :
- **Prompt engineering sérieux (jour 204)** : structurer un prompt (rôle, tâche, contraintes, format), être explicite, itérer méthodiquement plutôt qu'espérer.
- **Structured outputs (jour 205)** : forcer une sortie MACHINE-lisible (JSON conforme à un schéma) pour brancher le LLM à du code fiable.
- **Few-shot et patterns de prompts (jour 206)** : montrer des exemples pour guider le format et le raisonnement ; les patterns récurrents.
- **Function calling / tool use (jour 207)** : laisser le modèle DÉCIDER d'appeler des outils/fonctions ; le LLM comme orchestrateur, pas comme oracle.
- **Intégration dans une app (jour 208)** : brancher tout cela dans une vraie application (entrée utilisateur → prompt → sortie structurée → action).
- **Consolidation + revue mensuelle 7 (jour 209)** : synthèse du mois LLM.

Le fil rouge : **un LLM utile en production produit des sorties STRUCTURÉES et vérifiables, guidé par un prompt explicite (et du few-shot), et peut APPELER des outils — on l'intègre comme un composant fiable, pas comme une boîte magique.**

### Grille de notation
**Test théorique (réponds sans notes) :**
1. Quels sont les éléments d'un bon prompt structuré (au moins 4) ?
2. Pourquoi forcer une sortie JSON conforme à un schéma plutôt qu'un texte libre ?
3. Qu'apporte le few-shot par rapport à une simple consigne (zero-shot) ?
4. Qu'est-ce que le function calling / tool use, et pourquoi dit-on que le LLM ORCHESTRE ?
5. Dans une app, que fais-tu si le LLM renvoie un JSON invalide ou hors schéma ?

**Exercice pratique (45-60 min) :** construis un mini-composant « extracteur » : à partir d'un texte libre (ex. un email), le LLM renvoie un JSON STRUCTURÉ conforme à un schéma (`{expéditeur, intention, urgence, action}`) ; ajoute 2 exemples few-shot, VALIDE la sortie contre le schéma côté code, et gère le cas « sortie non conforme » (re-demande ou erreur propre). Bonus : expose une « fonction » (ex. `chercherClient`) que le modèle peut décider d'appeler.

**Grille de notation (/100, critères observables) :**
| Critère observable | Points |
|---|---|
| Prompt structuré (rôle/tâche/contraintes/format) explicite | /15 |
| Sortie JSON conforme à un schéma, VALIDÉE côté code | /25 |
| Cas « sortie non conforme » géré proprement (pas de crash) | /15 |
| Few-shot pertinent qui améliore la fiabilité (démontré) | /15 |
| Function/tool call correctement déclaré et déclenché | /20 |
| Composant intégrable (entrée → prompt → sortie structurée → action) | /10 |

**Seuils :** **≥ 80 = acquis** · **50-79 = fragile** · **< 50 = insuffisant**.

### Plan de remédiation (si un critère échoue)
**Diagnostic — erreur → compétence :**
| Symptôme observé | Compétence à retravailler |
|---|---|
| Prompt vague (« résume ça ») sans rôle/format/contraintes | Prompt engineering (jour 204) |
| Parse un texte libre à la main au lieu d'exiger du JSON | Structured outputs (jour 205) |
| Sortie instable faute d'exemples | Few-shot (jour 206) |
| Fait tout faire au LLM au lieu de lui donner des outils | Function calling / tool use (jour 207) |
| Le code plante quand la sortie n'est pas conforme | Intégration robuste / validation (jour 208) |

**Remédiation conditionnelle selon le score :**
- **< 50** : rejoue les jours 204-208 ; refais l'extracteur en exigeant un JSON validé côté code.
- **50-79** : cible la faiblesse (souvent la validation de sortie ou le tool use) ; ajoute la gestion du cas non conforme.
- **≥ 80** : avance vers la mise en production/robustesse ; garde le réflexe « sortie structurée + validée ».

**Exercices de rattrapage ciblés :**
- *Structured output* : impose un schéma JSON strict et rejette/repose la question si la sortie ne le respecte pas.
- *Few-shot* : compare la stabilité d'une tâche zero-shot vs 3-shot sur 5 entrées.
- *Tool use* : déclare une fonction `convertirDevise(montant, de, vers)` et laisse le modèle décider de l'appeler.

**Décision :** *Continuer* vers les prompts en production (semaine 31) si ≥ 80 · *Consolider* si 50-79 · *Reprendre les jours 204-208* si < 50.

**Preuves / livrables attendus :** le composant extracteur (prompt + schéma + validation + gestion du cas non conforme), un exemple de sortie JSON valide, et le cas échéant la déclaration d'un outil appelable.

### Questions d'entretien de la semaine
1. **« Comment fiabilises-tu la sortie d'un LLM pour la brancher à du code ? »** Attendu : exiger une sortie STRUCTURÉE (JSON conforme à un schéma), la VALIDER côté code, et gérer le cas non conforme (re-demande/erreur propre) — jamais parser du texte libre à la main.
2. **« Zero-shot ou few-shot : comment choisis-tu ? »** Attendu : few-shot quand le format/raisonnement doit être guidé et que zero-shot est instable ; on montre 2-3 exemples représentatifs — au prix de tokens supplémentaires.
3. **« Qu'est-ce que le function calling / tool use ? »** Attendu : le modèle décide d'appeler des fonctions/outils déclarés (recherche, calcul, API) ; il ORCHESTRE et délègue au lieu de tout inventer, ce qui augmente fiabilité et actionnabilité.
4. **« Un prompt vague vs un bon prompt : qu'est-ce qui change ? »** Attendu : un bon prompt est explicite (rôle, tâche, contraintes, format attendu, éventuels exemples) et itéré ; il réduit l'ambiguïté et la variance des réponses.
5. **« Le LLM renvoie un JSON invalide en production : que fais-tu ? »** Attendu : validation systématique contre le schéma, stratégie de reprise (re-prompt avec l'erreur), valeurs de repli, et jamais de confiance aveugle à la sortie.
