## 🎯 Objectif du jour

## 📖 Cours approfondi
**Concepts abordés :** Injection · Auth cassée · Exposition de données · Rate limiting · Secrets · HTTPS.

L'OWASP Top 10 recense les failles web les plus exploitées. Les 4 qui te concernent immédiatement : l'INJECTION (SQL — ta défense : le paramétrage), l'AUTH CASSÉE (tokens absents/faibles/mal vérifiés), l'EXPOSITION DE DONNÉES (renvoyer trop : mots de passe hashés, emails d'autres utilisateurs, stack traces), et la MAUVAISE CONFIGURATION (secrets commités, CORS en *, messages d'erreur bavards).

La posture qui change tout : ATTAQUER son propre système. Tu ne sais pas si ton API est sûre tant que tu n'as pas essayé de la casser — c'est l'état d'esprit que tu appliqueras aux systèmes LLM au mois 9 (prompt injection).

Pourquoi la sécurité est une propriété transversale. Un développeur qui pense « je sécuriserai à la fin » a déjà perdu : une faille peut vivre dans n'importe quelle entrée non validée, n'importe quelle réponse trop bavarde, n'importe quel secret mal rangé. La sécurité se vérifie à CHAQUE point du système, pas dans un module « sécurité » ajouté après coup. Et elle ne se PROUVE que par l'attaque : croire son app sûre sans l'avoir attaquée est l'erreur fondamentale.

Les quatre familles OWASP qui te concernent, depuis les fondations. **L'INJECTION** (SQL surtout) : entrée interprétée comme du code — ta défense est le paramétrage (jour 57). **L'AUTHENTIFICATION CASSÉE** : tokens absents, faibles, ou mal vérifiés, routes protégées qui ne le sont pas vraiment (jour 68). **L'EXPOSITION DE DONNÉES** : renvoyer TROP — mots de passe hashés, emails d'autres utilisateurs, stack traces internes (jour 54) ; on ne renvoie que le NÉCESSAIRE. **La MAUVAISE CONFIGURATION** : secrets commités dans Git, CORS ouvert à `*`, messages d'erreur bavards qui renseignent l'attaquant, dépendances non à jour.

La posture de l'attaquant, depuis les fondations. La seule façon de savoir si une API est sûre est d'essayer de la CASSER : envoyer une injection et vérifier qu'elle échoue, appeler une route protégée sans token, demander les données d'un autre utilisateur, provoquer une erreur et lire la réponse (fuit-elle des détails internes ?). Cet état d'esprit — supposer que tout est attaquable jusqu'à preuve du contraire — est ce qui distingue un système sécurisé d'un système « pas encore attaqué ».

Le rate limiting, une défense simple. Limiter le nombre de requêtes par client et par fenêtre de temps protège contre le brute-force (deviner un token/mot de passe) et l'abus (déni de service applicatif). Un rate limiting même simple (compteur par IP) élève significativement le coût d'une attaque.

Limites et compromis. La sécurité est un CONTINUUM, jamais « terminée » : on réduit la surface d'attaque, on ne l'annule pas. Trop de restrictions nuisent à l'usage (rate limit trop bas, validation trop stricte) ; le bon niveau protège sans bloquer les usages légitimes. Et l'audit maison ne remplace pas un audit professionnel — mais l'état d'esprit d'attaquant est la base indispensable.

La règle du jour : **traite la sécurité comme une propriété à vérifier PARTOUT (chaque entrée, réponse, config), et PROUVE-la en attaquant ton propre système. Audite les quatre familles OWASP qui te concernent — injection (paramétrage), auth cassée (tokens vérifiés), exposition (ne renvoyer que le nécessaire), mauvaise config (secrets hors du code) — corrige de vraies failles, et ajoute un rate limiting.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : auditer une route de ton API selon OWASP en l'ATTAQUANT, puis corriger une faille d'exposition de données.

**Exemple simple** : la faille d'exposition. `GET /membres/1` qui renvoie `{ id, nom, email, motDePasseHash }` EXPOSE le hash du mot de passe — inutile au client, précieux pour un attaquant. La correction : ne renvoyer que les champs NÉCESSAIRES.

**Raisonnement pas-à-pas** : (1) j'ATTAQUE chaque famille : injection (déjà paramétré ?), auth (route protégée sans token ?), exposition (la réponse fuit-elle ?), config (secrets, erreurs bavardes ?) ; (2) je repère une faille réelle ; (3) je la corrige et je PROUVE la correction ; (4) j'ajoute un rate limiting simple.

**Implémentation (audit + corrections)** :
```ts
// 1. EXPOSITION : ne renvoyer que le nécessaire (pas le hash, pas d'autres emails)
app.get('/membres/:id', (req, res) => {
  const m = dataMembres.parId(Number(req.params.id));
  if (!m) return res.status(404).json({ message: 'introuvable' });
  const { motDePasseHash, ...public } = m;      // on RETIRE le champ sensible
  res.json(public);                             // on ne renvoie que le nécessaire
});

// 2. MAUVAISE CONFIG : erreurs non bavardes (pas de stack au client, jour 54)
// 3. INJECTION : requêtes paramétrées partout (jour 57) -> vérifié par relecture

// 4. RATE LIMITING simple : limiter le brute-force et l'abus
const hits = new Map<string, { n: number; t: number }>();
function rateLimit(req, res, next) {
  const ip = req.ip, now = Date.now();
  const e = hits.get(ip) ?? { n: 0, t: now };
  if (now - e.t > 60000) { e.n = 0; e.t = now; }   // fenêtre d'1 min
  e.n++; hits.set(ip, e);
  if (e.n > 100) return res.status(429).json({ message: 'trop de requêtes' }); // 429
  next();
}
app.use(rateLimit);
```
L'audit par l'attaque révèle la fuite du hash (corrigée en ne renvoyant que le nécessaire), confirme le paramétrage anti-injection, et le rate limiting (429 au-delà de la limite) élève le coût d'un brute-force.

## ⚠️ Erreurs fréquentes
- Croire son app sûre sans l'avoir attaquée : la sécurité ne se suppose pas, elle se prouve.
- Messages d'erreur qui fuient des infos internes (stack, requête, chemins) : renseignent l'attaquant.
- Exposer trop de données par défaut (hash, emails d'autres, champs internes) faute de choisir ce qu'on renvoie.
- Secrets commités ou CORS ouvert à * : mauvaise configuration exploitable.

## 🏢 Cas métier
La sécurité web est un enjeu critique et permanent : les failles OWASP (injection, auth cassée, exposition de données, mauvaise configuration) sont responsables de la majorité des brèches réelles — fuites de données personnelles, vols de comptes, compromissions de bases. Le coût d'une brèche (financier, réputationnel, légal avec le RGPD) est énorme, et la plupart des failles exploitées sont connues et évitables. La posture « attaquer son propre système » est exactement celle des équipes de sécurité (pentest, red team) et des programmes de bug bounty. En entreprise, la sécurité est une responsabilité partagée par tous les développeurs, pas seulement une équipe dédiée : chacun doit valider les entrées, ne pas exposer de données superflues, garder les secrets hors du code. Savoir auditer une API selon OWASP, attaquer son propre code et corriger de vraies failles est une compétence directement valorisée — et l'état d'esprit d'attaquant se transfère aux systèmes LLM (injection de prompt, mois 8). « Comment sécurises-tu une API ? » est une question d'entretien back de plus en plus fréquente.

## 🎤 Question d'entretien
**« Comment abordes-tu la sécurité d'une API ? »** → Je traite la sécurité comme une PROPRIÉTÉ à vérifier partout, pas comme une feature ajoutée à la fin : une faille peut vivre dans n'importe quelle entrée, réponse ou config. Et je pars du principe que je ne SAIS pas si mon API est sûre tant que je ne l'ai pas ATTAQUÉE. Concrètement, j'audite les quatre familles OWASP qui me concernent. L'INJECTION : je vérifie que tout le SQL est paramétré (zéro concaténation). L'AUTHENTIFICATION CASSÉE : j'appelle mes routes protégées sans token pour confirmer qu'elles refusent bien. L'EXPOSITION DE DONNÉES : je vérifie que mes réponses ne renvoient que le nécessaire — jamais un hash de mot de passe, l'email d'un autre utilisateur, ou une stack trace. La MAUVAISE CONFIGURATION : secrets hors du code (.env gitignored), CORS restreint, messages d'erreur non bavards. Puis je corrige les vraies failles trouvées et je le prouve. J'ajoute aussi un rate limiting pour freiner le brute-force et l'abus (429 au-delà de la limite). **Relance possible** : « quelle faille as-tu réellement trouvée chez toi ? » → typiquement une exposition — un endpoint qui renvoyait l'objet complet, hash inclus ; je l'ai corrigé en ne renvoyant que les champs publics. Ça m'a appris qu'on fuit des données par défaut si on ne choisit pas explicitement ce qu'on renvoie.
