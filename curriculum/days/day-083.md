## 📖 Cours approfondi
**Concepts abordés :** Auto-évaluation · Identification des lacunes · Consolidation · Projection mois 4-6.

Un bilan trimestriel n'est pas une formalité : c'est le mécanisme qui transforme l'expérience en compétence CONSCIENTE. La méthode : relire ses notes anciennes (la distance révèle la progression invisible au quotidien), réévaluer chaque compétence avec le test dur (« puis-je le produire SEUL + l'expliquer ? »), nommer les 3 lacunes prioritaires et leur affecter un créneau concret.

Le piège de l'auto-évaluation : la familiarité se déguise en maîtrise. Avoir VU la récursion 20 fois n'est pas savoir l'ÉCRIRE — seul le test de production compte. Sous-évaluer est aussi une erreur : compare-toi au toi du jour 1, pas à un senior.

Le portfolio se vérifie MAINTENANT, pas au mois 12 : un recruteur peut tomber sur ton GitHub aujourd'hui. Chaque repo doit être propre en continu.

**Modèle mental : un bilan n'est pas une formalité — c'est le mécanisme qui transforme l'EXPÉRIENCE en compétence CONSCIENTE. La méthode : relire ses notes anciennes (la distance révèle la progression invisible au quotidien), réévaluer chaque compétence avec le TEST DUR (« puis-je le PRODUIRE seul + l'EXPLIQUER ? »), nommer les 3 lacunes prioritaires et leur affecter un créneau concret. Le piège central : la FAMILIARITÉ se déguise en maîtrise — avoir VU la récursion 20 fois n'est pas savoir l'ÉCRIRE.** Consolider le mois 3 et préparer le trimestre 2, c'est faire un point d'honnêteté qui dirige la suite.

Pourquoi un bilan structuré. L'apprentissage quotidien est une accumulation dont on ne perçoit pas la progression : on avance sans mesurer le chemin. Un bilan périodique prend du RECUL — il compare l'état actuel à l'état passé (d'où relire ses notes anciennes), révélant une progression réelle mais invisible au jour le jour. Et il identifie ce qui n'est PAS encore acquis, transformant une impression vague en un plan de rattrapage précis. Sans bilan, on progresse à l'aveugle et on répète ses lacunes.

Le test dur de la maîtrise, depuis les fondations. La question qui ne ment pas : « puis-je le PRODUIRE seul (sans aide, sans notes) ET l'EXPLIQUER à voix haute ? ». C'est le critère de tout ce parcours (jour 48). Reconnaître un concept, l'avoir lu, l'avoir vu résolu — rien de tout cela n'est la maîtrise. Seule la PRODUCTION autonome + l'EXPLICATION prouvent qu'un savoir est disponible. Appliquer ce test à chaque compétence donne une évaluation honnête, pas complaisante.

Le piège de la familiarité, depuis les fondations. La FAMILIARITÉ (« je connais ça, je l'ai vu souvent ») se déguise en MAÎTRISE (« je sais le faire »). C'est le biais d'auto-évaluation le plus courant et le plus trompeur : avoir vu vingt fois une solution crée un sentiment de compétence qui s'effondre dès qu'on doit produire seul. L'antidote est le test dur : ne pas se demander « est-ce que ça me parle ? » mais « est-ce que je peux le refaire seul MAINTENANT ? ». Sous-évaluer est l'erreur inverse (se comparer à un expert au lieu du soi d'il y a trois mois) — l'honnêteté va dans les deux sens.

Le plan de rattrapage, depuis les fondations. Une lacune identifiée sans plan reste une lacune. On nomme les 3 lacunes PRIORITAIRES (pas dix, pour rester actionnable) et on leur affecte un CRÉNEAU DATÉ concret. Une lacune avec une date de traitement devient un rendez-vous ; une lacune vague (« il faudrait que je revoie… ») ne se traite jamais.

La préparation du trimestre 2, depuis les fondations. Trois mois de fondations (terminal, Git, algorithmique, structures, TypeScript, API REST sécurisée et testée, SQL, React) constituent déjà un profil full-stack junior. La suite (data et ML, mois 4-6) s'APPUIE sur ces fondations : projeter ce qui vient, c'est voir la continuité (une API du mois 3 + de la donnée du mois 4 = les briques du RAG du mois 8) et aborder la data avec des bases consolidées, pas fuir en avant.

Limites et compromis. Un bilan honnête est INCONFORTABLE (il révèle les lacunes) : c'est justement ce qui le rend utile. Trop de lacunes listées paralyse — d'où le focus sur 3 prioritaires. Et le bilan ne remplace pas l'action : c'est un outil de direction, pas une fin. L'IA peut aider en faisant passer un examen blanc, mais l'auto-évaluation honnête reste un exercice personnel.

La règle du jour : **fais un bilan qui transforme l'expérience en compétence consciente : relis tes notes anciennes (la distance révèle la progression), réévalue chaque compétence par le TEST DUR (produire seul + expliquer), déjoue le piège familiarité ≠ maîtrise, et affecte un créneau DATÉ à tes 3 lacunes prioritaires. Projette le trimestre 2 (data/ML) comme un appui sur ces fondations.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : réévaluer honnêtement une compétence avec le test dur et transformer une lacune en rendez-vous daté.

**Exemple simple** : familiarité vs maîtrise. « La récursion ? Oui, je connais » (familiarité) ≠ « je viens d'écrire seul un parcours d'arbre récursif et de l'expliquer » (maîtrise). Le test dur tranche : est-ce que je peux le PRODUIRE seul MAINTENANT ?

**Raisonnement pas-à-pas** : (1) pour chaque compétence, j'applique le test « produire seul + expliquer » ; (2) je note honnêtement (pas ce qui me parle, ce que je peux refaire) ; (3) je repère les 3 lacunes prioritaires ; (4) je leur donne un créneau daté.

**Protocole de bilan** :
```text
RELECTURE : mes notes des jours 1, 30, 60 -> quelle distance parcourue ?

TEST DUR par compétence (0-3) : "puis-je le PRODUIRE seul + l'EXPLIQUER ?"
  - API REST sécurisée      : 3 (LivreAPI faite seul, défendable à l'oral)
  - Transactions SQL        : 2 (fait avec un rappel, à consolider)
  - Rebase Git              : 1 (compris mais pas fluide sans notes)   <- LACUNE
  - Tests d'intégration     : 2
  - Lecture de code inconnu : 1                                        <- LACUNE
  ... (déjouer familiarité != maîtrise : noter ce qu'on REFAIT, pas ce qui "parle")

3 LACUNES PRIORITAIRES -> CRÉNEAU DATÉ (un rendez-vous, pas un vœu) :
  1. Rebase Git          -> samedi matin : refaire l'exercice du jour 73 seul
  2. Lecture de code     -> mercredi soir : cartographier un repo open-source
  3. Transactions SQL    -> jeudi : réécrire l'emprunt transactionnel de mémoire

PROJECTION trimestre 2 : mes API (mois 3) + la donnée (mois 4) = briques du RAG (mois 8).
```
Le test dur donne une évaluation honnête (produire seul, pas « ça me parle »), le piège familiarité≠maîtrise est déjoué, et chaque lacune devient un rendez-vous daté — un plan actionnable, pas une liste de bonnes intentions.

## 🏢 Cas métier
La capacité à s'auto-évaluer honnêtement et à diriger son apprentissage est une méta-compétence décisive pour une carrière tech, où l'on doit apprendre en continu. Le piège « familiarité ≠ maîtrise » explique pourquoi tant de développeurs surestiment leurs compétences (le biais de Dunning-Kruger) : avoir lu sur un sujet crée un sentiment de maîtrise trompeur. Les développeurs qui progressent le plus vite sont ceux qui appliquent le test dur (« puis-je le faire seul ? »), identifient leurs lacunes sans complaisance, et les traitent avec un plan concret. En entreprise, cette lucidité est ce qui permet de dire « je ne sais pas encore, mais voici comment je vais apprendre » — une réponse d'entretien bien plus solide qu'un bluff. Le bilan structuré (relire, réévaluer, planifier le rattrapage) est aussi ce qui permet de PRÉPARER une transition — ici vers la data/ML — en consolidant les fondations plutôt qu'en accumulant des lacunes. Un candidat qui connaît honnêtement ses forces et ses axes de progression, et qui sait diriger son apprentissage, inspire confiance : c'est un profil qui grandira dans l'équipe.
