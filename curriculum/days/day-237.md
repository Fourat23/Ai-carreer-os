## 🎯 Objectif du jour
Préparer le mois 9.

## 📖 Cours approfondi
**Modèle mental : le bilan transforme quatre semaines de travail en trois actifs — un état des lieux, un backlog, un jeu d'évaluation.** DocQA fonctionne : interface, multi-tours, prompt optimisé, cas limites définis. Avant d'attaquer le mois 9 (évaluation systématique et amélioration mesurée), une journée pour consolider — pas par cérémonie, mais parce que le mois 9 sera exactement aussi bon que le golden set qui l'alimente.

Les trois livrables :
1. **Le bilan chiffré** : la trajectoire du mois (v0 : 9/15 → post-optimisation : 13/15), les décisions prises (6 décisions du jour 227 + ADR-006 + 4 familles du jour 236), les limites assumées, les coûts réels (ton log du jour 214 les a accumulés — combien a coûté le mois d'API ?). Un lecteur doit comprendre où en est le système SANS te parler.
2. **Le backlog priorisé par les données** : chaque amélioration candidate reliée à sa preuve (chunking structurel ← 6 échecs du jour 226 ; hybride ← les échecs « vocabulaire » ; reranking ← les échecs de rang). Le mois 9 exécutera ce backlog dans l'ordre — les jours 239-248 sont déjà alignés dessus.
3. **Le golden set complet** : les 30 questions du cadrage (jour 232), maintenant TOUTES écrites, avec réponse attendue, type, source de vérité (document + passage), et difficulté. Règles d'or : des questions issues du BESOIN (pas des capacités actuelles), des types équilibrés, les cas difficiles du jour 236 inclus, et — crucial — le golden set est FIGÉ : on ne le retouche plus en cours d'évaluation, sinon les comparaisons v1/v2 ne valent rien. C'est ton jeu de test au sens du mois 6 : il ne sert qu'à évaluer, jamais à développer.

Ce triptyque (état, backlog, golden set) est exactement ce qu'un lead demande à la fin d'un cycle : où on en est, quoi faire ensuite, comment on saura que ça s'améliore.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : bilan + backlog priorisé + golden set de 30 questions figé.

**Raisonnement** : le bilan compile l'existant (rien ne s'invente), le backlog relie chaque amélioration à sa preuve, le golden set opérationnalise le cadrage.

**Format du golden set (le livrable central)** :
```json
{
  "version": "1.0", "fige_le": "2026-XX-XX",
  "questions": [
    {
      "id": "gs-01", "type": "factuelle", "difficulte": "facile",
      "question": "Quel est le délai de rétractation ?",
      "reponse_attendue": "14 jours",
      "source_verite": {"doc": "guide-client.md", "section": "§4"},
      "verdicts": ["reponse_ok", "citation_ok", "chunk_dans_topk"]
    },
    { "id": "gs-27", "type": "hors_corpus", "difficulte": "dure",
      "question": "Et en Belgique ?",
      "reponse_attendue": "REFUS", "source_verite": null, ... }
  ]
}
```

**Le backlog priorisé (extrait type)** :
```
1. Chunking par structure   ← preuve : 6/10 échecs j.226 (chunks coupés)
   → jour 240, mesuré sur golden set au jour 241
2. k et seuil de refus      ← preuve : 3 échecs de rang récupérés à k=5
   → re-test golden set (décision j.227 « sous surveillance »)
3. Hybride lexical/vectoriel ← preuve : 2 échecs « vocabulaire »
   → jours 245-246
```

**Explication** : le champ `source_verite` de chaque question rend le verdict « bon chunk dans top-k » automatisable — c'est lui qui transformera ton évaluation manuelle en script au mois 9. **Variante** : passe le golden set UNE fois sur le système actuel — c'est ta baseline v1 officielle, celle que toutes les améliorations du mois 9 devront battre.

## ⚠️ Erreurs fréquentes
- Écrire les questions du golden set en regardant ce que le système réussit : biais fatal — elles viennent du besoin et du cadrage, pas des capacités.
- Un golden set sans sources de vérité : les verdicts resteront manuels et coûteux — c'est source_verite qui permet le script du mois 9.
- Un backlog par intuition (« le reranking c'est bien ») : chaque ligne cite sa preuve ou elle sort du backlog.
- Retoucher le golden set après l'avoir figé : chaque retouche invalide toutes les comparaisons passées — version 1.0, point.

## 🏢 Cas métier
« Comment tu sais que ton RAG s'améliore ? » : question posée dans TOUS les entretiens AI engineer depuis 2024. La réponse faible : « les réponses ont l'air meilleures ». La tienne : « golden set de 30 questions typées, figé, avec source de vérité par question ; baseline chiffrée ; chaque changement re-passe le set ». Les équipes sérieuses fonctionnent exactement comme ça — arriver avec la pratique déjà installée vaut des mois d'onboarding.

## 🎤 Question d'entretien
**« Comment construis-tu un jeu d'évaluation pour un RAG ? »** → 30 questions issues du besoin réel, typées (factuelle, reformulée, synthèse, hors corpus, ambiguë — les difficiles incluses), chacune avec réponse attendue ET source de vérité (document + passage, pour automatiser le verdict retrieval). Le set est FIGÉ : on ne le retouche pas en cours d'évaluation, il ne sert jamais au développement — c'est la discipline train/test du ML, appliquée au RAG.
