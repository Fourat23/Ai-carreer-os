## 📖 Cours approfondi
**Modèle mental : une migration réussie est un échange d'implémentations sous comportement constant — et tu as un avantage rare : une référence EXACTE.** L'ADR-006 (jour 230) a fixé la décision et ses raisons (filtrage natif, persistance, collections) ; aujourd'hui tu l'exécutes. Chroma remplace ton index JSON + brute force derrière le MÊME contrat de module (`search`, jour 221) — et ta brute force devient l'instrument de VALIDATION de la migration.

Ce que Chroma t'apporte concrètement : une **collection** persistante (les vecteurs vivent hors de la RAM de ton process), les **métadonnées et filtres `where`** natifs (ton filtrage du jour 229, géré par la base), et l'API `query` qui encapsule le top-k. Ce que tu dois savoir : à ton échelle, Chroma fait aussi de la recherche exacte ou quasi-exacte — les écarts éventuels avec ta brute force viennent surtout de DÉTAILS d'implémentation : métrique de distance configurée à la CRÉATION de la collection (cosine vs L2 — vérifie-la, c'est le piège n°1), normalisation, et gestion des ids.

Le protocole de migration professionnelle :
1. **Adapter derrière l'interface** : `search.py` gagne un backend Chroma ; le contrat (entrées/sorties, scores) ne bouge pas ; le reste du pipeline ignore le changement.
2. **Double-run de validation** : les 30 questions du golden set passées sur les DEUX backends — les top-k doivent coïncider (mêmes chunks, scores cohérents). Chaque écart s'explique avant de continuer.
3. **Parité fonctionnelle** : la ré-ingestion idempotente (jour 223 — les ids stables paient : `upsert` sur ton chunk_id) et le filtrage (jour 229 → `where`) fonctionnent à l'identique.
4. **Bascule et trace** : la brute force reste dans le code (backend de référence, activable pour diagnostiquer), et l'ADR-006 est annotée : migration faite, écarts observés, temps passé.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : migrer search vers Chroma, valider par double-run contre la brute force.

**Raisonnement** : créer la collection avec la BONNE métrique, ingérer avec les ids existants, valider sur le golden set, basculer.

**Implémentation** :
```python
import chromadb
client = chromadb.PersistentClient(path="./chroma")
col = client.get_or_create_collection(
    "docqa", metadata={"hnsw:space": "cosine"})   # LA ligne critique : cosine !

# Ingestion : tes chunk_id stables (jour 223) rendent l'upsert idempotent
col.upsert(
    ids=[c["id"] for c in chunks],
    embeddings=[c["vecteur"] for c in chunks],     # TES embeddings existants
    documents=[c["texte"] for c in chunks],
    metadatas=[c["meta"] for c in chunks],
)

def top_k_chroma(question, k=3, **filtres):
    r = col.query(query_embeddings=[embed(question)], n_results=k,
                  where=filtres or None)            # le filtrage du jour 229, natif
    return list(zip(r["distances"][0], r["documents"][0], r["metadatas"][0]))
```

**Le double-run (la vraie journée de travail)** :
```
Pour les 30 questions du golden set :
  top-3 brute force vs top-3 Chroma →
  - mêmes chunks, même ordre : ✓
  - mêmes chunks, ordre permuté sur scores quasi égaux : acceptable, noté
  - chunks DIFFÉRENTS : STOP — suspects habituels : métrique L2 par défaut,
    embeddings re-générés au lieu de réutilisés, distance vs similarité
    (Chroma renvoie une DISTANCE : similarité ≈ 1 - distance en cosine)
Résultat attendu : ~30/30 concordants après correction des pièges.
```

**Explication** : réutiliser TES embeddings (plutôt que laisser Chroma en générer avec SON modèle par défaut) est le deuxième piège classique — sinon tu compares deux espaces différents (jour 218 : un espace = un modèle). **Variante** : chronomètre les deux backends sur 100 requêtes — à ton échelle Chroma ne sera pas forcément plus rapide que NumPy : la migration s'est faite pour les FONCTIONNALITÉS (persistance, where, échelle future), pas la vitesse — sache le dire.

## ⚠️ Erreurs fréquentes
- Métrique par défaut (L2) au lieu de cosine à la création de la collection : top-k différents, diagnostic laborieux — LA cause n°1 d'écart.
- Laisser Chroma générer ses embeddings au lieu de fournir les tiens : deux modèles, deux espaces, résultats incomparables.
- Confondre distance et similarité dans les scores exposés au reste du pipeline (le seuil de refus du jour 227 casserait en silence).
- Supprimer la brute force après la bascule : c'est ta référence exacte de diagnostic — elle reste, désactivée par défaut.

## 🏢 Cas métier
Les migrations d'infrastructure de retrieval (JSON → Chroma, Chroma → pgvector, un fournisseur → un autre) sont des opérations courantes et redoutées : sans jeu de validation, l'équipe découvre les régressions par les plaintes utilisateurs. Ta méthode — référence exacte + golden set + double-run — est le protocole pro en miniature. « J'ai migré en validant chaque résultat contre ma référence » est une phrase d'entretien qui sent le vécu.

Pièges classiques : la métrique de distance à la création de la collection (cosine vs L2), réutiliser les MÊMES embeddings (un espace = un modèle), et distance vs similarité dans les scores. L'ancien backend reste comme référence de diagnostic.
