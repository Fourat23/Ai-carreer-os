## 🎯 Objectif du jour
Écrire un serveur http natif AVANT Express pour ne pas traiter le framework en boîte noire.

## 📖 Cours approfondi
**Concepts abordés :** Module http natif · req/res · Routing manuel · Parsing du corps · Pourquoi Express.

Sous Express il y a le module http de Node : un serveur = une fonction qui reçoit (req, res) et ÉCRIT une réponse. Tout ce qu'Express automatise, tu peux le faire à la main : router (un switch sur method + url), parser le corps (accumuler les chunks du flux entrant), répondre (statut + headers + res.end).

L'exercice du jour a un but précis : éprouver la FRICTION. Parser le JSON à la main, router à la main, gérer les erreurs à la main — pour que demain, chaque facilité d'Express (express.json(), app.get, les middlewares) soit comprise comme une automatisation de quelque chose que tu SAIS faire, pas comme de la magie.

C'est un principe d'apprentissage général : une couche basse comprise une fois = toutes les abstractions au-dessus démystifiées.

### Exercice principal
Serveur natif (sans Express) : GET /ping → pong, POST /echo → renvoie le JSON reçu. Constate la friction. Puis réécris-le en Express en 10 lignes.

## 📦 Livrable attendu
server-natif.ts + version Express + notes sur ce qu'Express automatise.

## ✅ Critères de validation
- [ ] Le serveur natif répond correctement à GET /ping et POST /echo
- [ ] Le corps du POST est parsé chunk par chunk (compris, pas copié)
- [ ] La liste de frictions est écrite : chaque friction est associée à ce qu'Express automatise

## ⚠️ Erreurs fréquentes
- Oublier res.end (réponse jamais terminée).
- Ne pas gérer les chunks du corps.

## 🏢 Cas métier
Cas typique : appeler un LLM (POST + header d'auth + corps JSON + streaming), exposer ton système RAG comme une API (`POST /questions`), ou consommer une API tierce — comprendre HTTP, c'est comprendre comment les systèmes IA se parlent.

## 🎤 Question d'entretien
**« Décris le trajet d'une requête HTTP et le rôle des statuts. »** → DNS → TCP → TLS → HTTP ; requête (méthode + URL + headers + corps) / réponse (statut + corps) ; sans état ; 2xx succès, 4xx faute client, 5xx faute serveur ; idempotence de GET/PUT/DELETE pour les retries.

## 🚀 Pourquoi ça comptera plus tard
- **En architecture** : toute intégration système passe par des APIs — comprendre HTTP en profondeur, c'est comprendre comment les systèmes se parlent.
- **En IA/LLM** : appeler un LLM, C'EST une requête HTTP (headers d'auth, corps JSON, streaming, statuts d'erreur) ; ton RAG est une API qui appelle des APIs.
- **En entretien** : « que se passe-t-il quand tu tapes une URL » et « design une API pour X » sont des classiques absolus.
