## 🎯 Objectif du jour

## 📖 Cours approfondi
**Modèle mental : tester un projet réel, ce n'est PAS tout couvrir — c'est protéger les PARCOURS CRITIQUES (ceux dont la casse coûte le plus) avec le bon type de test pour chaque chose. On ne vise pas 100 % de couverture, on vise la confiance là où elle compte.** BiblioApp a maintenant une logique (validation, recherche/filtres) et des composants (formulaires, listes, CRUD). Les tester tous à l'identique serait du gaspillage ; les tester INTELLIGEMMENT, c'est appliquer à chaque chose le test adapté, sur les parcours qui comptent vraiment.

La stratégie de test d'un projet (la « pyramide » appliquée) :
1. **Logique métier → tests unitaires** (jour 106) : la validation d'un livre, la composition des filtres (jour 115), les calculs. Rapides, nombreux, ils couvrent les cas limites. C'est la base de la pyramide.
2. **Composants → tests de comportement** (jour 107) : le formulaire affiche ses erreurs, la liste rend les résultats, la suppression demande confirmation. Testés par rôle/label/texte, pas par implémentation.
3. **Flux critiques → tests d'intégration** (jour 108) : « créer un livre → il apparaît dans la liste », « supprimer → il disparaît », avec l'api MOCKÉE. Ces tests attrapent les bugs d'ASSEMBLAGE entre formulaire, api et affichage — les plus coûteux.

Comment choisir QUOI tester en priorité : les parcours dont l'échec fait le plus mal. Pour BiblioApp : créer un livre (cœur métier), supprimer (destructeur — un bug ici perd des données), rechercher (le plus utilisé). Un bug sur ces parcours ruine l'app ; un bug sur un détail cosmétique, non. Tester d'abord le critique donne le maximum de confiance pour l'effort.

Les tests protègent aussi le POLISH à venir (jour 117) et tout refactor futur : une suite verte te dit que tes changements n'ont rien cassé. C'est ce qui rend un projet MODIFIABLE sans peur — la vraie valeur d'une suite de tests.

La règle du jour : **couvre les parcours critiques avec le type de test adapté (unitaire pour la logique, comportement pour les composants, intégration pour les flux) ; vise la confiance, pas le pourcentage**. Une suite qui rougit quand un parcours critique casse vaut plus que 100 % de couverture de code trivial.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : une suite de tests verte couvrant les parcours critiques de BiblioApp.

**Exemple simple** : le test d'intégration le plus rentable — le flux de création. `remplir le formulaire → cliquer Ajouter → le livre apparaît dans la liste`. Un seul test qui traverse formulaire + api mockée + affichage, et attrape les bugs d'assemblage.

**Raisonnement pas-à-pas** : lister les parcours critiques (créer, supprimer, rechercher) → tester la logique en unitaire, les composants en comportement, les flux en intégration → prouver que chaque test rougit sur une régression.

**Solution** :
```tsx
// 1. UNITAIRE — logique de filtres (jour 115), cas limites
test('combine texte ET disponibilité', () => {
  expect(filtrer(livres, { q: 'react', dispoSeule: true })).toHaveLength(1);
});
// 2. COMPORTEMENT — le composant confirme avant de supprimer (jour 107)
test('demande confirmation avant suppression', async () => {
  const onSuppr = vi.fn(); vi.spyOn(window, 'confirm').mockReturnValue(false);
  render(<CarteLivre livre={livre} onSupprimer={onSuppr} />);
  await userEvent.click(screen.getByRole('button', { name: /supprimer/i }));
  expect(onSuppr).not.toHaveBeenCalled();                    // annulé → aucune suppression
});
// 3. INTÉGRATION — flux critique créer (jour 108), api mockée
test('créer un livre l\'ajoute à la liste', async () => {
  vi.mocked(api.creerLivre).mockResolvedValue({ id: 9, titre: 'Vue', auteur: 'Evan' });
  render(<BiblioApp />);
  await userEvent.type(screen.getByLabelText(/titre/i), 'Vue');
  await userEvent.click(screen.getByRole('button', { name: /ajouter/i }));
  expect(await screen.findByText('Vue')).toBeVisible();      // assemblage form → api → liste
});
```

**Mini-quiz** : (a) Vise-t-on 100 % de couverture ? (b) Quel type de test pour un flux « créer → apparaît dans la liste » ? (c) Comment choisir quoi tester en priorité ?
→ (a) non — on vise la CONFIANCE sur les parcours critiques, pas le pourcentage ; (b) un test d'intégration (api mockée) qui traverse formulaire → api → affichage ; (c) les parcours dont l'échec coûte le plus (créer, supprimer, rechercher).

**Variante** : sabote la logique de filtres (inverse un `&&` en `||`) et vérifie que le test unitaire correspondant rougit — la preuve que ta suite protège vraiment le parcours de recherche.

## 🏢 Cas métier
Une suite de tests bien ciblée est ce qui rend un projet MODIFIABLE en confiance : les équipes livrent et refactorent sans peur parce qu'une régression sur un parcours critique casse un test avant la production. Le contre-exemple coûteux est la course au « 100 % de couverture » qui teste massivement du code trivial (getters, rendu statique) tout en laissant les vrais flux (créer, supprimer) non couverts — beaucoup d'effort, peu de protection. Les équipes matures raisonnent en parcours critiques et en pyramide (beaucoup d'unitaires rapides, quelques intégrations ciblées). Pour un portfolio, une suite verte qui couvre les flux critiques de BiblioApp est un signal fort : elle prouve que tu sais rendre un projet fiable, pas seulement fonctionnel.

## 🎤 Question d'entretien
**« Comment décides-tu quoi tester dans un projet ? »** → Je ne vise pas 100 % de couverture, je vise la CONFIANCE sur les PARCOURS CRITIQUES — ceux dont l'échec coûte le plus (pour BiblioApp : créer, supprimer, rechercher). J'applique à chaque chose le bon type de test : unitaire pour la logique métier (validation, filtres, cas limites), comportement pour les composants (par rôle/label, pas l'implémentation), intégration pour les flux (créer → apparaît dans la liste, api mockée) car ils attrapent les bugs d'assemblage, les plus coûteux. C'est la pyramide : beaucoup d'unitaires rapides, quelques intégrations ciblées. Une suite qui rougit quand un parcours critique casse vaut bien plus que 100 % de couverture de code trivial — et c'est ce qui rend le projet modifiable sans peur.
