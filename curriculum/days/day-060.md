Et le CONTRAT d'API s'écrit AVANT le code — c'est une promesse que Postman vérifiera ; coder d'abord et documenter ensuite produit des APIs incohérentes.** Concevoir LivreAPI, c'est modéliser les données, promettre un contrat, et planifier les tests — tout ce qui rend le code ensuite fluide.

Pourquoi les données d'abord. Le schéma est la fondation : tout le reste (requêtes, endpoints, logique) en dépend. Un mauvais schéma se paie à chaque requête (jointures tortueuses), à chaque évolution (migration risquée) et en bugs de cohérence. Poser d'abord un bon modèle — normalisé (jour 58), avec les bonnes relations — rend l'API naturelle à construire. C'est le prolongement de « concevoir les types avant le code » (jour 44), au niveau de la base.

La table de liaison, un pattern à reconnaître. Une relation « plusieurs-à-plusieurs » (un membre emprunte plusieurs livres, un livre est emprunté par plusieurs membres au fil du temps) ne se modélise pas par une clé étrangère simple : il faut une TABLE DE LIAISON `emprunts(id, livre_id, membre_id, date_emprunt, date_retour)` qui relie les deux ET porte ses propres attributs (les dates). Ce pattern est PARTOUT : inscriptions (étudiant × cours), participations (personne × événement), lignes de commande (commande × produit). Le reconnaître est un réflexe de modélisation.

Le contrat avant le code, depuis les fondations. On écrit le CONTRAT d'API — endpoints, verbes, statuts, corps, erreurs (le design REST du jour 51) — AVANT d'implémenter. C'est une PROMESSE : « voici comment mon API se comportera ». Promettre d'abord FORCE la cohérence (on conçoit l'ensemble avant les détails) ; coder d'abord et documenter ensuite produit des incohérences (chaque endpoint inventé au fil de l'eau). Postman (jour 59) VÉRIFIERA que le code tient la promesse.

La robustesse du modèle : anticiper UNE évolution probable. La question à se poser systématiquement : « et si un livre a plusieurs auteurs ? ». Si la réponse casse le schéma (auteur stocké comme un champ unique du livre), il faut une table de liaison de plus (`livre_auteurs`). Anticiper UNE évolution probable est du bon design ; en anticiper dix (chaque cas hypothétique) est de la sur-ingénierie. Le juste milieu : un modèle qui encaisse les évolutions RÉALISTES sans se noyer dans les improbables.

Le backlog en jalons démontrables. Comme au jour 44 : « CRUD livres fonctionne », « emprunt/retour avec règle de disponibilité » — des jalons vérifiables, pas « avancer sur LivreAPI ». Le progrès se mesure, la procrastination se voit.

Limites et compromis. Sur-modéliser (anticiper tous les cas hypothétiques) alourdit inutilement ; sous-modéliser (ignorer une relation évidente comme les emprunts) condamne l'API. Le contrat écrit d'avance a un coût (conception avant code) largement rentabilisé par la cohérence. Et un modèle n'est jamais figé : il s'ajuste, mais partir d'un bon socle évite les refontes douloureuses.

La règle du jour : **conçois les DONNÉES d'abord (schéma normalisé, emprunts = table de liaison qui porte ses dates), écris le CONTRAT d'API avant le code (une promesse que Postman vérifiera), anticipe UNE évolution probable (« et si plusieurs auteurs ? ») sans sur-concevoir, et découpe en jalons démontrables.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : modéliser la relation membre–livre (emprunts) et esquisser le contrat d'API correspondant, avant tout code.

**Exemple simple** : pourquoi une table de liaison. Stocker « qui a emprunté » dans un champ du livre échoue : un livre a un HISTORIQUE d'emprunts (plusieurs membres au fil du temps), chacun avec ses dates. La table `emprunts` relie livre + membre ET porte les dates — c'est le pattern plusieurs-à-plusieurs avec attributs.

**Raisonnement pas-à-pas** : (1) j'identifie les entités (livres, auteurs, membres) ; (2) je repère la relation plusieurs-à-plusieurs (emprunts) → table de liaison ; (3) je teste la robustesse (« plusieurs auteurs ? » → table de liaison `livre_auteurs`) ; (4) j'écris le contrat d'API (endpoints, statuts, dont le 409 du double emprunt) avant de coder.

**Modèle + contrat (avant code)** :
```sql
-- Table de LIAISON : relie membre + livre ET porte ses propres données (dates)
CREATE TABLE emprunts (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  livre_id     INTEGER NOT NULL REFERENCES livres(id),
  membre_id    INTEGER NOT NULL REFERENCES membres(id),
  date_emprunt TEXT NOT NULL,
  date_retour  TEXT                         -- NULL tant que non rendu
);
-- "Un livre a plusieurs auteurs" -> autre table de liaison
CREATE TABLE livre_auteurs (
  livre_id  INTEGER NOT NULL REFERENCES livres(id),
  auteur_id INTEGER NOT NULL REFERENCES auteurs(id),
  PRIMARY KEY (livre_id, auteur_id)
);
```
```text
CONTRAT D'API (promesse vérifiée par Postman au jour 59) :
GET    /livres            -> 200 [ ... ]        (recherche/pagination en query)
POST   /livres            -> 201 | 400
POST   /livres/{id}/emprunter -> 201 | 409 (déjà emprunté) | 404
POST   /emprunts/{id}/rendre  -> 200 | 404
GET    /membres/{id}/emprunts -> 200 [ ... ]
```
La table de liaison porte les dates, le modèle encaisse « plusieurs auteurs », et le contrat (avec le 409 du double emprunt) est promis AVANT le code — cohérent et vérifiable.

## 🏢 Cas métier
Le cadrage d'un projet — modéliser les données, promettre un contrat, planifier les tests avant de coder — est ce qui distingue un projet livrable d'un projet qui s'enlise. En entreprise, la phase de conception (schéma, contrat d'API, découpage) est souvent revue collectivement AVANT l'implémentation, précisément parce que corriger un mauvais schéma ou un contrat incohérent une fois le code écrit coûte très cher (migrations, réécriture, clients cassés). Le pattern de la table de liaison est omniprésent dans les modèles de données réels (e-commerce, réseaux sociaux, réservation) : le reconnaître évite des schémas bancals. Écrire le contrat d'API d'avance permet aux équipes front et back de travailler EN PARALLÈLE (le front code contre le contrat pendant que le back l'implémente) — un gain de temps majeur. Pour un portfolio, un projet dont la conception (modèle + contrat + plan de tests) est explicite et cohérente démontre une maturité d'ingénieur, pas seulement de codeur.

## 🎤 Question d'entretien
**« Comment cadres-tu un projet d'API avant d'écrire du code ? »** → Je commence par les DONNÉES, parce que le schéma est la fondation dont dépendent les requêtes, les endpoints et la logique — un mauvais schéma condamne l'API à des jointures tortueuses et des incohérences pendant des années. Je modélise les entités et je repère les relations : pour une bibliothèque, les emprunts sont une relation plusieurs-à-plusieurs entre membres et livres, donc une TABLE DE LIAISON qui relie les deux ET porte ses propres données (dates d'emprunt et de retour) — un pattern qu'on retrouve partout (inscriptions, lignes de commande). Ensuite j'écris le CONTRAT d'API avant le code : endpoints, verbes, statuts (dont le 409 pour un double emprunt), corps, erreurs. C'est une promesse qui force la cohérence et que Postman vérifiera ensuite. Enfin je découpe en jalons démontrables. **Relance possible** : « pourquoi le contrat d'abord plutôt que coder puis documenter ? » → parce que promettre d'abord force à concevoir l'ensemble de façon cohérente, et permet aux équipes front et back de travailler en parallèle contre le même contrat ; documenter après coup produit des APIs incohérentes.
