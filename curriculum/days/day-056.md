### Synthèse de la semaine
La semaine 8 a ouvert le mois 3 et posé le socle du développement backend. HTTP en profondeur (jour 50) : un protocole sans état où chaque requête est autonome, les méthodes portent une sémantique, l'idempotence sécurise les retries, et les statuts sont un langage (401 « non authentifié » vs 403 « interdit »). REST design (jour 51) : des ressources (noms pluriels), les verbes HTTP pour les actions, une API PRÉVISIBLE qui se devine sans doc. Node natif puis Express (jour 52) : éprouver la friction du bas niveau (req/res, chunks, res.end) pour démystifier ce que le framework automatise. Express en couches (jour 53) : middlewares en chaîne (l'ordre = l'exécution) et séparation routes/services/data qui rend la logique testable sans serveur. Validation et erreurs centralisées (jour 54) : toute entrée est hostile jusqu'à validation, l'opérationnel (400/404) se distingue du bug (500 générique sans fuite), on prouve la robustesse en attaquant l'API. SQL (jour 55) : le déclaratif, JOIN, GROUP BY, la distinction WHERE/HAVING. Le fil rouge : **construire une API, c'est comprendre le protocole (HTTP), concevoir un contrat cohérent (REST), structurer proprement (couches, middlewares), se défendre (validation, erreurs sans fuite) et savoir interroger ses données (SQL).** Tu entres dans la suite du mois 3 (SQLite branché, modélisation, Projet 2 LivreAPI) avec les fondations d'un vrai backend.

### Plan de remédiation (si un critère échoue)
- **HTTP flou (statuts, idempotence)** : rejoue le jour 50 — sans-état, méthodes sémantiques, distinction 401/403, idempotence pour les retries.
- **API non prévisible / verbes dans l'URL** : jour 51 — ressources au pluriel, verbes HTTP pour les actions, statuts par cas, cohérence.
- **Express en boîte noire** : jour 52 — réécris un serveur natif (req/res, chunks, res.end) pour voir ce que le framework automatise.
- **Logique dans les routes** : jour 53 — sépare routes/services/data, teste la logique des services sans serveur ; maîtrise la chaîne de middlewares (ordre, next).
- **API fragile / fuite d'erreurs** : jour 54 — valide toute entrée (400 + liste), centralise les erreurs (opérationnel vs bug), n'expose jamais la stack ; attaque ta propre API.
- **SQL confus (WHERE/HAVING, JOIN)** : jour 55 — WHERE filtre les lignes avant, HAVING les groupes après ; INNER vs LEFT ; paramètre les valeurs.

### Questions d'entretien de la semaine
1. **« HTTP est sans état : qu'est-ce que ça implique, et 401 vs 403 ? »** Attendu : requête autonome, état transporté par token, scalabilité ; 401 non authentifié, 403 interdit ; idempotence pour les retries.
2. **« Conçois une API REST : quelles règles ? »** Attendu : ressources au pluriel, verbes HTTP pour les actions (jamais dans l'URL), statuts par cas, query string pour raffiner, prévisibilité.
3. **« Qu'est-ce qu'Express fait pour toi par rapport au module http ? »** Attendu : routing, parsing du corps (chunks), réponse (res.end) ; le framework automatise ce qu'on fait à la main.
4. **« Comment structures-tu une API et gères-tu les middlewares ? »** Attendu : 3 couches (routes/services/data), logique testable hors des routes ; chaîne de middlewares, ordre = exécution, next obligatoire.
5. **« Comment rends-tu une API robuste, et différence WHERE/HAVING en SQL ? »** Attendu : entrée hostile jusqu'à validation, erreurs centralisées sans fuite ; WHERE filtre les lignes avant, HAVING les groupes après.
