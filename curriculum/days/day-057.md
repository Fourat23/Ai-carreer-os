## 📖 Cours approfondi
**Concepts abordés :** better-sqlite3 / node:sqlite · Requêtes paramétrées · Schéma/init versionné · Injection SQL et prévention · Couche data isolée.

L'injection SQL est la faille historique n°1 : si tu CONCATÈNES l'entrée utilisateur dans ta requête (`"SELECT * WHERE nom = '" + input + "'"`), un input malin (`' OR 1=1 --`) devient du code SQL exécuté. Vol de données, destruction de tables : tout devient possible.

La défense est simple et absolue : les requêtes PARAMÉTRÉES. `SELECT * WHERE nom = ?` + la valeur passée séparément — le moteur traite l'entrée comme une DONNÉE, jamais comme du code. Règle à vie : zéro concaténation de SQL, sans exception.

La couche data isolée (un module qui contient TOUT le SQL) prépare la suite : le jour où SQLite devient PostgreSQL, un seul fichier change. C'est ton interface Store du projet 1, appliquée à une vraie base.

**Modèle mental : l'injection SQL, la faille n°1 de l'histoire du web, vient d'une seule erreur — CONCATÉNER l'entrée utilisateur dans une requête. `"SELECT * WHERE nom = '" + input + "'"` laisse un input malin (`' OR 1=1 --`) devenir du CODE SQL exécuté. La défense est simple et ABSOLUE : les requêtes PARAMÉTRÉES (`WHERE nom = ?` + la valeur passée séparément) SÉPARENT le code SQL des données — l'entrée ne peut plus JAMAIS être interprétée comme du code. Règle à vie : zéro concaténation de SQL, sans exception.** Brancher une vraie base, c'est aussi isoler tout le SQL dans une couche data (ton interface Store du Projet 1, appliquée à SQLite).

Pourquoi l'injection existe, depuis les fondations. Une requête concaténée MÉLANGE deux choses de natures différentes : le CODE (la structure de la requête) et les DONNÉES (les valeurs fournies par l'utilisateur). Le moteur reçoit une seule chaîne et ne peut pas savoir où finit ton code et où commencent les données de l'utilisateur — donc si l'utilisateur écrit du SQL, le moteur l'EXÉCUTE. `' OR 1=1 --` transforme un `WHERE nom = '...'` en condition toujours vraie (fuite de toutes les lignes) ; d'autres charges détruisent des tables. C'est la porte ouverte au vol et à la destruction de données.

Comment le paramétrage ferme la porte. Une requête paramétrée envoie la STRUCTURE (`WHERE nom = ?`) et les VALEURS SÉPARÉMENT au moteur. Celui-ci compile d'abord la structure, PUIS insère les valeurs en les traitant STRICTEMENT comme des données — jamais comme du code. Même si l'utilisateur envoie `' OR 1=1 --`, cette chaîne est cherchée LITTÉRALEMENT comme un nom, pas exécutée. La séparation code/données est la défense, et elle est totale : il n'y a pas de « paramétrage partiel » — soit tout est paramétré, soit une faille subsiste.

La différence concaténation vs paramétrage, à ne jamais oublier. Concaténer (`+ input +`) mélange code et données → faille. Paramétrer (`?` + valeur) sépare code et données → sûr. Il n'y a pas de compromis ni d'exception « pour aller vite » : une seule requête concaténée avec une entrée utilisateur suffit à compromettre toute la base. Le réflexe pris au jour 55 devient ici une règle de sécurité absolue.

La couche data isolée, depuis les fondations. Tout le SQL vit dans UN module (la couche data) : les services ne voient que des fonctions (`trouverParId`, `inserer`), jamais du SQL. Bénéfice double : la sécurité se contrôle en un seul endroit (on relit un fichier pour vérifier « zéro concaténation »), et la migration devient triviale — le jour où SQLite devient PostgreSQL, un seul fichier change. C'est exactement l'interface `Store` du Projet 1 (jour 44), appliquée à une vraie base : l'inversion de dépendance protège ET découple.

Le schéma versionné. Le schéma (`init.sql`) est VERSIONNÉ dans Git : n'importe qui peut recréer la base à l'identique. Un schéma non versionné rend la base irreproductible (« ça marche sur ma machine ») — un anti-pattern.

Limites et compromis. Le paramétrage protège les VALEURS, pas les identifiants dynamiques (noms de colonnes/tables) qui, eux, exigent une liste blanche. SQLite est parfait pour apprendre et pour de petites applications, mais mono-fichier et limité en concurrence (d'où PostgreSQL en production). Et isoler la couche data ajoute une indirection justifiée dès qu'on veut tester ou migrer.

La règle du jour : **zéro concaténation de SQL, JAMAIS — les requêtes paramétrées (`?` + valeur) séparent code et données et sont LA défense contre l'injection. Isole tout le SQL dans une couche data (sécurité contrôlée en un point, migration triviale) et versionne ton schéma. Prouve que l'injection échoue en l'essayant.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : migrer une requête concaténée (vulnérable) vers une requête paramétrée (sûre), et prouver qu'une injection échoue.

**Exemple simple** : l'attaque qui marche vs qui échoue. Sur `"... WHERE nom = '" + input + "'"` avec `input = "' OR 1=1 --"`, la requête devient `WHERE nom = '' OR 1=1 --'` → TOUTES les lignes fuient. Sur `WHERE nom = ?` avec la même entrée, le moteur cherche LITTÉRALEMENT un nom égal à `' OR 1=1 --` → zéro ligne. La séparation code/données neutralise l'attaque.

**Raisonnement pas-à-pas** : (1) je repère toute concaténation de SQL ; (2) je la remplace par un `?` et je passe la valeur séparément ; (3) j'isole le SQL dans la couche data ; (4) je TENTE l'injection et je constate qu'elle échoue.

**Implémentation (better-sqlite3)** :
```ts
import Database from 'better-sqlite3';
const db = new Database('citations.db');

// ❌ VULNÉRABLE : concaténation -> injection possible
function chercherVulnerable(nom: string) {
  return db.prepare(`SELECT * FROM auteurs WHERE nom = '${nom}'`).all();  // NE JAMAIS FAIRE
}

// ✅ SÛR : requête paramétrée -> code et données séparés
const dataAuteurs = {
  chercherParNom: (nom: string) =>
    db.prepare('SELECT * FROM auteurs WHERE nom = ?').all(nom),   // le ? est une DONNÉE
  inserer: (nom: string) =>
    db.prepare('INSERT INTO auteurs (nom) VALUES (?)').run(nom),
};

// PREUVE que l'injection échoue
const attaque = "' OR 1=1 --";
console.log(dataAuteurs.chercherParNom(attaque).length);  // 0 : cherché littéralement, pas exécuté
```

**Le schéma versionné (init.sql, dans Git)** :
```sql
CREATE TABLE IF NOT EXISTS auteurs (
  id   INTEGER PRIMARY KEY AUTOINCREMENT,
  nom  TEXT NOT NULL
);
```
Le paramétrage neutralise l'injection (l'entrée reste une donnée), tout le SQL est dans la couche data (relisible d'un coup pour vérifier « zéro concaténation »), et le schéma versionné rend la base reproductible.

## ⚠️ Erreurs fréquentes
- Concaténer des chaînes dans le SQL : faille d'injection béante, même « juste pour un champ ».
- Schéma non versionné : base irreproductible (« ça marche sur ma machine »).
- Croire que le paramétrage protège les identifiants dynamiques (colonnes/tables) : eux exigent une liste blanche.
- Laisser du SQL dans les services au lieu de l'isoler en couche data : sécurité incontrôlable et migration douloureuse.

## 🏢 Cas métier
L'injection SQL figure depuis des décennies au sommet des classements de vulnérabilités (OWASP Top 10) et reste responsable de fuites de données massives et coûteuses — vol de comptes, exfiltration de bases entières, destruction de données. Sa prévention est pourtant simple et bien connue : les requêtes paramétrées, systématiquement. C'est précisément pour ça que concaténer une entrée utilisateur dans une requête est un red flag ÉLIMINATOIRE en revue de code et en entretien back : ça révèle une méconnaissance d'un risque de sécurité fondamental. Les équipes matures interdisent la concaténation de SQL par convention (et par linters), isolent l'accès aux données dans une couche dédiée (contrôle et audit facilités), et versionnent leurs schémas (migrations reproductibles). Savoir expliquer POURQUOI le paramétrage protège (séparation code/données) et le PROUVER en tentant une injection démontre une compréhension de sécurité que les recruteurs valorisent hautement.

## 🎤 Question d'entretien
**« Qu'est-ce qu'une injection SQL et comment t'en protèges-tu ? »** → L'injection vient d'une seule erreur : concaténer l'entrée utilisateur dans la requête, par exemple `"SELECT * WHERE nom = '" + input + "'"`. Le problème de fond est que la requête MÉLANGE alors le code SQL et les données : le moteur reçoit une seule chaîne et ne sait pas où finit mon code et où commencent les données de l'utilisateur, donc si celui-ci envoie `' OR 1=1 --`, le moteur l'EXÉCUTE — fuite de toutes les lignes, voire destruction de tables. La défense est simple et absolue : les requêtes PARAMÉTRÉES. J'écris `WHERE nom = ?` et je passe la valeur séparément ; le moteur compile la structure PUIS insère la valeur en la traitant STRICTEMENT comme une donnée, jamais comme du code. Même `' OR 1=1 --` est alors cherché littéralement comme un nom, pas exécuté. La règle à vie : zéro concaténation de SQL, sans exception, et j'isole tout le SQL dans une couche data pour contrôler ça en un seul endroit et pouvoir migrer facilement. Je le PROUVE en tentant l'injection et en constatant qu'elle échoue. **Relance possible** : « le paramétrage protège-t-il tout ? » → non : il protège les valeurs, mais pas les identifiants dynamiques comme un nom de colonne, qui exigent une liste blanche — un point que beaucoup ignorent.
