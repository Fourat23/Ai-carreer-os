## 🎯 Objectif du jour
Concevoir des modules à interfaces claires, comprendre couplage/cohésion, préparer la pensée architecturale.

## 📖 Cours approfondi
**Concepts abordés :** Module et interface · Couplage faible / cohésion forte · Cacher l'implémentation · API design (contrat) · Dépendances.

Deux mesures gouvernent la qualité d'un découpage en modules : le COUPLAGE (à quel point les modules dépendent les uns des autres — à minimiser) et la COHÉSION (à quel point le contenu d'un module va ensemble — à maximiser). Le symptôme du couplage fort : changer une chose oblige à toucher cinq fichiers.

Un bon module CACHE son implémentation derrière une interface minimale : le reste du monde connaît le contrat (les fonctions exposées), jamais les détails (la structure interne, la lib utilisée). Ton interface Store (jour 44), ton module api.ts : même principe. Ce qui est caché peut changer librement ; ce qui est exposé est un engagement.

Le graphe de dépendances rend le design VISIBLE : les flèches doivent aller dans un sens (vers le bas, vers le stable), jamais en cercle (A→B→A = les deux modules n'en sont qu'un, déguisé).

**Modèle mental : deux mesures gouvernent la qualité d'un découpage en modules — le COUPLAGE (à quel point les modules dépendent les uns des autres : à MINIMISER) et la COHÉSION (à quel point le contenu d'un module va ensemble : à MAXIMISER). Le symptôme du couplage fort : changer UNE chose oblige à toucher CINQ fichiers. Un bon module CACHE son implémentation derrière une interface MINIMALE : le reste du monde connaît le contrat (les fonctions exposées), jamais les détails (structure interne, lib utilisée) — donc ce qui est caché peut CHANGER librement.** Concevoir des modules à interfaces propres, c'est le raisonnement architectural, préparé par ton interface Store (jour 44) et ton module api.ts (jour 88).

Pourquoi couplage et cohésion gouvernent tout. Un système est un ensemble de modules. Sa MODIFIABILITÉ — sa capacité à évoluer sans tout casser — dépend de deux choses : combien les modules dépendent les uns des autres (couplage), et combien chaque module est cohérent (cohésion). Fort couplage = un changement se propage partout (fragile). Faible cohésion = un module fait dix choses sans rapport (illisible, difficile à réutiliser). L'objectif : couplage FAIBLE, cohésion FORTE — des modules autonomes qui font chacun UNE chose.

Le couplage, depuis les fondations. Le couplage mesure les DÉPENDANCES entre modules. Symptôme du couplage fort : changer l'implémentation d'un module oblige à modifier plusieurs autres (« je change ça, et cinq fichiers cassent »). On le RÉDUIT en faisant dépendre les modules de CONTRATS (interfaces) plutôt que d'implémentations (jour 38, 44) : le module A connaît l'INTERFACE de B, pas ses détails, donc B peut changer sans casser A. Le couplage faible localise les changements.

La cohésion, depuis les fondations. La cohésion mesure à quel point le contenu d'un module VA ENSEMBLE. Cohésion forte = un module a UNE responsabilité claire (« la gestion des emprunts »), tout ce qu'il contient sert ce but. Cohésion faible = un module fourre-tout (« utils » qui contient dix fonctions sans rapport). La cohésion forte rend un module compréhensible, testable et réutilisable d'un bloc.

Cacher l'implémentation, depuis les fondations. Un bon module expose une INTERFACE MINIMALE (les fonctions nécessaires) et CACHE tout le reste (sa structure interne, la bibliothèque qu'il utilise, ses détails). Le reste du système ne connaît que le contrat. Bénéfice décisif : ce qui est caché peut CHANGER sans impact — remplacer la lib interne, réorganiser la structure, optimiser, sans toucher les modules qui l'utilisent. C'est exactement ton interface Store (jour 44) et ton module api.ts (jour 88, l'Adapter).

Les dépendances et leurs pièges. Le graphe de dépendances (qui dépend de qui) révèle la structure. Un piège grave : les DÉPENDANCES CIRCULAIRES (A dépend de B qui dépend de A) — elles empêchent de comprendre, tester ou réutiliser un module isolément, et signalent une mauvaise séparation des responsabilités. On les élimine en repensant les responsabilités ou en introduisant une abstraction.

Limites et compromis. Trop de modules (sur-découpage) crée de l'indirection inutile ; trop peu (modules géants) crée du couplage interne. Le bon grain dépend du contexte. Cacher l'implémentation ajoute une interface (un peu de cérémonie) justifiée quand l'implémentation peut varier ou doit être isolée. Et réduire le couplage à zéro est impossible (les modules doivent bien communiquer) — l'objectif est de MINIMISER et de rendre les dépendances explicites et acycliques.

La règle du jour : **vise un couplage FAIBLE (les modules dépendent de contrats, pas d'implémentations — un changement reste localisé) et une cohésion FORTE (chaque module fait UNE chose). Cache l'implémentation derrière une interface minimale pour qu'elle puisse changer librement. Élimine les dépendances circulaires. Le test : changer l'implémentation d'un module ne doit casser aucun autre.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : réduire le couplage d'un module en le cachant derrière une interface minimale, et vérifier qu'en changer l'implémentation ne casse rien.

**Exemple simple** : le test du couplage. Si je change l'implémentation d'un module (la lib de base de données) et que cinq autres fichiers cassent, le couplage est fort. S'ils dépendent d'une INTERFACE (`Store`), je change l'implémentation derrière, zéro fichier casse. Objectif : zéro.

**Raisonnement pas-à-pas** : (1) je repère un module dont l'implémentation « fuit » (les autres dépendent de ses détails) ; (2) je définis une interface minimale (le contrat) ; (3) les autres modules dépendent du contrat ; (4) je change l'implémentation → rien ne casse.

**Avant / Après** :
```ts
// AVANT : couplage FORT — le service dépend des détails de SQLite (better-sqlite3)
import Database from 'better-sqlite3';
const db = new Database('livres.db');
function listerLivres() {
  return db.prepare('SELECT * FROM livres').all();   // le service connaît le SQL et la lib
}
// changer de base (SQLite -> Postgres) casse TOUS les modules qui font ça.
```
```ts
// APRÈS : couplage FAIBLE — interface minimale, implémentation cachée
interface LivresRepo {                       // le CONTRAT (ce que les autres connaissent)
  tous(): Livre[];
  parId(id: number): Livre | undefined;
}

// implémentation SQLite CACHÉE derrière le contrat
const livresSqlite: LivresRepo = {
  tous: () => db.prepare('SELECT * FROM livres').all() as Livre[],
  parId: (id) => db.prepare('SELECT * FROM livres WHERE id = ?').get(id) as Livre,
};

// le service ne dépend que du CONTRAT LivresRepo, jamais de SQLite
function creerServiceLivres(repo: LivresRepo) {
  return { lister: () => repo.tous() };      // changer l'implémentation du repo ne casse rien ici
}
```
Le service dépend de l'interface `LivresRepo`, pas de SQLite : remplacer l'implémentation (Postgres, mock de test) ne touche AUCUN module qui l'utilise. Couplage faible, implémentation cachée, changement localisé — le test « zéro casse » est réussi.

## ⚠️ Erreurs fréquentes
- Modules qui exposent tout (pas d'encapsulation) : les autres dépendent de détails internes, couplage fort.
- Dépendances circulaires (A→B→A) : impossible de tester/réutiliser un module isolément.
- Module fourre-tout (« utils ») à faible cohésion : dix responsabilités sans rapport.
- Sur-découper en trop de petits modules : indirection inutile ; le bon grain dépend du contexte.

## 🏢 Cas métier
La modularité (couplage faible, cohésion forte, implémentations cachées) est ce qui détermine si un système reste MODIFIABLE à mesure qu'il grandit — l'enjeu central de l'architecture logicielle en entreprise. Un système à fort couplage devient une « boule de boue » : chaque changement casse des choses ailleurs, la peur de toucher au code s'installe, la vélocité s'effondre. Un système modulaire (modules cohérents dépendant de contrats) évolue par touches localisées, se teste par morceaux (on remplace un module par un mock), et permet à plusieurs équipes de travailler en parallèle sur des modules différents. Cacher l'implémentation derrière des interfaces est le principe qui permet de changer de base de données, de fournisseur ou de bibliothèque sans réécrire le métier — la valeur business directe d'une bonne conception. Les dépendances circulaires sont un signal d'alarme repéré en revue d'architecture. Savoir raisonner en couplage/cohésion, concevoir des interfaces minimales et dessiner un graphe de dépendances propre est exactement ce qu'on attend d'un développeur qui monte en séniorité — et « qu'est-ce qu'un bon module ? » ou « comment réduis-tu le couplage ? » sont des questions d'entretien d'architecture.

## 🎤 Question d'entretien
**« Qu'est-ce qui fait un bon découpage en modules, et comment réduis-tu le couplage ? »** → Deux mesures gouvernent la qualité d'un découpage : le COUPLAGE (à quel point les modules dépendent les uns des autres, à minimiser) et la COHÉSION (à quel point le contenu d'un module va ensemble, à maximiser). Je vise couplage faible, cohésion forte : des modules autonomes qui font chacun UNE chose. Le symptôme du couplage fort, c'est « je change une chose et cinq fichiers cassent ». Je le réduis en faisant dépendre les modules de CONTRATS (interfaces) plutôt que d'implémentations : le module qui utilise la base dépend d'une interface `LivresRepo`, pas de SQLite directement — donc je peux changer l'implémentation (Postgres, un mock de test) sans toucher les modules qui l'utilisent. C'est le principe de cacher l'implémentation derrière une interface minimale : ce qui est caché peut changer librement. Mon test concret : changer l'implémentation d'un module ne doit casser AUCUN autre — objectif zéro. J'évite aussi les dépendances circulaires (A dépend de B qui dépend de A), qui empêchent de tester ou réutiliser un module isolément. **Relance possible** : « peut-on avoir un couplage nul ? » → non, les modules doivent bien communiquer ; l'objectif n'est pas zéro couplage mais de le MINIMISER et de le rendre explicite et acyclique — dépendre d'interfaces stables plutôt que de détails changeants.
