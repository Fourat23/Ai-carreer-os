## 🎯 Objectif du jour
Souder le retrieval avancé.

## 📖 Cours approfondi
**Modèle mental : consolider, c'est transformer trois expériences en UNE configuration de référence — figée, justifiée, rejouable.** Cette semaine a produit trois verdicts : la stratégie de chunking (jour 241), la discipline de versioning (jour 242), le modèle d'embedding (jour 243). Isolément, ce sont des tableaux ; ensemble, ils définissent TA configuration de retrieval v1 — celle que l'hybride et le reranking (semaine prochaine) devront BATTRE.

Le travail de consolidation a trois faces :
1. **La configuration de référence** : un fichier unique (`configs/retrieval-v1.json`) qui fixe tout — chunking (stratégie + params), modèle d'embedding, k, seuil de refus, collection active — avec, pour CHAQUE choix, une ligne de justification pointant vers son tableau (« structurel : +2 top-3 global, jour 241 »). La config sans justification redevient de la magie en trois semaines.
2. **La baseline officielle** : le harnais complet passé UNE fois sur cette config — scores par type, latence p50, coût par requête — enregistrés dans le manifeste (jour 242). C'est le CHIFFRE À BATTRE : toute amélioration future (hybride, reranking) se mesurera contre lui, pas contre un souvenir.
3. **La dette d'expérimentation, listée** : ce que tu n'as PAS testé (chunking sémantique, k>5, autres modèles) et POURQUOI c'est acceptable de ne pas l'avoir fait maintenant (coût/bénéfice attendu, données manquantes). Une limite listée est un choix ; une limite ignorée est une surprise future.

Ce triptyque config/baseline/dette est le geste de fin d'itération des équipes ML matures — tu le retrouveras sous d'autres noms (model card, experiment tracking). L'exécuter proprement sur TON système, avec TES chiffres, vaut tous les tutoriels de MLflow.

**La configuration justifiée** :

```json
{
  "version": "retrieval-v1", "fige_le": "2026-XX-XX",
  "chunking":  {"strategie": "structurel", "max_tk": 600, "min_tk": 80,
                "justif": "19/24 vs 17/24 fixe-400 (j.241) ; perd 1 synthèse, assumé"},
  "embedding": {"modele": "titulaire", 
                "justif": "challenger +1/24 pour ×4,5 prix : refusé (j.243)"},
  "k": 3,
  "k_justif": "k=5 récupérait 3 échecs (j.226) MAIS +40% tokens de contexte ;
               re-décision après reranking (j.248) qui changera l'arbitrage",
  "seuil_refus": 0.45,
  "collection": "docqa-v4"
}
```

**La baseline officielle (harnais complet)** :
```
retrieval-v1 — baseline du 2026-XX-XX
  top-3 :      19/24 (factuelles 11/12, reformulées 5/6, synthèses 3/6)
  refus :      3/3 hors-corpus refusées, 0 refus injustifié
  latence p50: 380 ms (embed 80 + search 15 + génération 285)
  coût/question : 0,0038 €
Dette d'expérimentation :
  - chunking sémantique : non testé (coût d'implémentation vs +espéré faible
    tant que les échecs « frontières » sont rares : 1/24)
  - k > 5 : non testé (explosion contexte ; attendre le reranking)
  - synthèses à 3/6 : AUCUNE stratégie testée ne les améliore →
    hypothèse : problème de GÉNÉRATION multi-chunks, pas de retrieval (à
    vérifier au jour 254 avec les métriques séparées)
```

**Explication** : la ligne « synthèses : aucune stratégie ne les améliore » est le genre d'observation TRANSVERSALE que seule la consolidation révèle — trois tableaux séparés ne la montraient pas. **Variante** : tague le commit (`retrieval-v1`) — quand l'hybride et le reranking seront passés, un diff entre tags racontera l'histoire complète de l'amélioration.

## ⚠️ Erreurs fréquentes
- Consolider en recopiant les conclusions sans les chiffres : « structurel car meilleur » ne permet aucune ré-évaluation — le renvoi au tableau, si.
- Une baseline partielle (qualité sans latence ni coût) : l'hybride et le reranking DÉGRADENT la latence — sans baseline latence, impossible d'arbitrer la semaine prochaine.
- Cacher la dette d'expérimentation : les synthèses à 3/6 non résolues sont une info CRUCIALE pour la suite, pas une honte à masquer.
- Différer la consolidation (« je le ferai après l'hybride ») : chaque expérience de plus rend la compilation plus floue — on fige à chaque palier.

## 🏢 Cas métier
Dans les équipes ML, la fin d'une itération sans consolidation produit le syndrome « on avait mesuré ça quelque part » : trois mois plus tard, personne ne retrouve pourquoi k=3 ni quel tableau justifiait le chunking. La config justifiée + baseline versionnée est ce qui permet à un NOUVEAU venu (ou à toi dans 6 mois) de reprendre le système sans archéologie. C'est aussi, très exactement, ce qu'un manager technique te demandera de produire à chaque fin de sprint ML.

## 🎤 Question d'entretien
**« Ton retrieval est configuré : comment gardes-tu la trace du pourquoi ? »** → Une configuration de référence versionnée où CHAQUE paramètre porte sa justification chiffrée (renvoi au tableau d'expérience), une baseline officielle mesurée sur le harnais complet (le chiffre à battre pour toute amélioration), et une dette d'expérimentation explicite — ce que je n'ai pas testé et pourquoi c'est un choix, pas un oubli. Toute amélioration future se compare à la baseline, jamais à un souvenir.
