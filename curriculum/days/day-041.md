# Jour 41 — Debugging méthodique : la compétence qu'on n'enseigne jamais

## 🎯 Objectif du jour
Adopter une méthode de debug systématique : reproduire → isoler → hypothèse → prouver → corriger.

## 📖 Cours approfondi
**Concepts abordés :** Reproduire fiablement · Bissection · console.log stratégique / debugger · Lire une stack trace · Rubber duck.

Le debugging méthodique remplace la loterie par un processus : (1) REPRODUIRE de façon fiable — sans ça, impossible de valider un fix ; (2) LIRE le message d'erreur en entier — il donne souvent ligne et cause ; (3) ISOLER par bissection — couper le code en deux, vérifier au milieu, éliminer une moitié (la recherche binaire appliquée au debug) ; (4) formuler UNE hypothèse falsifiable ; (5) la PROUVER par une observation (log, breakpoint) avant de corriger ; (6) corriger la CAUSE, pas le symptôme, puis re-reproduire.

Les familles de bugs à connaître : référence partagée (deux choses changent ensemble), off-by-one (bornes de boucle), type inattendu (NaN qui se propage), async (l'ordre d'exécution n'est pas celui du code), état périmé. Chaque famille a sa signature — les reconnaître accélère le diagnostic.

## ✍️ Pratique autonome

### Exercice principal
Un programme à 5 bugs (fourni en correction : logique, typage, référence partagée, off-by-one, async). Trouve-les avec la MÉTHODE, en documentant symptôme→hypothèse→preuve→fix.

## 📦 Livrable attendu
Journal de debug des 5 bugs + ta méthode personnelle écrite.

## ✅ Critères de validation
- [ ] Les 5 bugs trouvés avec, pour chacun : symptôme → hypothèse → preuve → correction documentés
- [ ] Aucune correction "au hasard" (chaque fix découle d'une hypothèse prouvée)
- [ ] Ta méthode personnelle de debug est écrite et affichée près de ton écran

## ⚠️ Erreurs fréquentes
- Corriger un symptôme sans la cause (le bug revient).
- Ne pas lire le message d'erreur en entier.

## 🚀 Pourquoi ça comptera plus tard
- **En architecture** : tests, gestion d'erreurs et refactoring sont ce qui rend une architecture VIVABLE — sans eux, tout design s'effondre à la première évolution.
- **En IA** : tester un composant qui appelle un LLM (mock, replay, éval — mois 11) est une extension directe des tests d'aujourd'hui.
- **En entretien** : la qualité de ton code sous pression (nommage, découpage, cas limites) est évaluée dans CHAQUE exercice, même quand on ne le dit pas.
