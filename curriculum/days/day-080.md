## 🎯 Objectif du jour
Comprendre le caching (les 2 problèmes difficiles), mesurer et optimiser une API.

## 📖 Cours approfondi
**Concepts abordés :** Cache (in-memory, HTTP) · Invalidation · Les 2 hard problems du cache · Profiling · N+1 queries.

Règle n°1 de la performance : MESURER avant d'optimiser. L'intuition se trompe presque toujours sur l'emplacement du goulot — profile d'abord (temps par endpoint, requêtes SQL exécutées), optimise ensuite, re-mesure pour prouver le gain.

Le problème N+1 est le bug de performance le plus courant des APIs : afficher 50 emprunts en faisant 1 requête pour la liste + 50 requêtes pour les livres associés = 51 allers-retours. La correction : UN JOIN (ou une requête batch WHERE id IN (...)). Symptôme : le nombre de requêtes SQL croît avec la taille de la liste.

Le CACHE échange de la fraîcheur contre de la vitesse : garder en mémoire un résultat coûteux et le resservir. Ses deux problèmes difficiles (célèbres) : l'INVALIDATION (quand la donnée sous-jacente change, le cache ment) et le nommage des clés. Ton LRU du jour 30 est exactement l'outil.

**Modèle mental : la règle n°1 de la performance est MESURER AVANT d'optimiser — l'intuition se trompe presque toujours sur l'emplacement du goulot d'étranglement. On PROFILE d'abord (temps par endpoint, requêtes SQL exécutées), on optimise ENSUITE, on re-mesure pour PROUVER le gain. Le bug de perf le plus courant des API est le N+1 (1 requête pour la liste + N requêtes pour les éléments associés), corrigé par un JOIN ou un batch. Et le CACHE échange de la FRAÎCHEUR contre de la VITESSE — ses deux problèmes réputés difficiles : l'INVALIDATION (quand purger) et le NOMMAGE.** Optimiser, c'est mesurer, corriger la vraie cause, et re-mesurer — jamais deviner.

Pourquoi mesurer avant d'optimiser. « Optimiser sans mesurer, c'est deviner. » L'intuition sur l'emplacement d'un goulot est presque toujours FAUSSE : on optimise un code qu'on croit lent alors que le vrai coût est ailleurs (une requête SQL, un aller-retour réseau). Le résultat : du temps perdu, du code compliqué inutilement, et le problème toujours là. La démarche rigoureuse : PROFILER (mesurer où le temps passe réellement), identifier le VRAI goulot, l'optimiser, puis RE-MESURER pour prouver le gain (et vérifier qu'on n'a pas déplacé le problème). C'est la méthode scientifique appliquée à la performance.

Le problème N+1, depuis les fondations. C'est LE bug de perf classique des API : pour afficher 50 emprunts avec leur livre, on fait 1 requête pour la liste des emprunts, PUIS 1 requête par emprunt pour récupérer son livre = 51 requêtes. Symptôme caractéristique : le nombre de requêtes SQL CROÎT avec la taille de la liste. La correction : UN JOIN (récupérer emprunts + livres en une requête) ou une requête BATCH (`WHERE livre_id IN (...)`). Passer de 51 requêtes à 1 ou 2 transforme radicalement la latence.

Le cache, depuis les fondations. Un cache STOCKE le résultat d'un calcul/d'une requête coûteuse pour le RÉUTILISER sans le refaire : il échange de la FRAÎCHEUR (le résultat caché peut être périmé) contre de la VITESSE (réponse immédiate). Il n'accélère que ce qui est lu SOUVENT et change PEU. Le cache LRU (jour 30) est un exemple ; un cache HTTP en est un autre. Le cache est puissant mais introduit un nouveau risque : servir des données PÉRIMÉES.

Les deux problèmes difficiles du cache. Une célèbre boutade dit qu'il n'y a que deux problèmes difficiles en informatique : l'invalidation de cache et le nommage. **L'INVALIDATION** : QUAND purger une entrée cachée pour ne pas servir du périmé ? Trop tôt, le cache ne sert à rien ; trop tard, on sert des données fausses. **Le NOMMAGE** (la clé de cache) : comment identifier de façon unique et correcte ce qui est caché ? Une mauvaise clé sert la mauvaise donnée. Un cache SANS stratégie d'invalidation est un piège qui sert des données périmées silencieusement.

La différence optimiser au hasard vs par mesure. Optimiser AU HASARD (« ça a l'air lent, je vais cacher ça »), c'est traiter un symptôme supposé — souvent inutile, parfois nuisible (cache mal invalidé). Optimiser PAR MESURE, c'est traiter la vraie cause identifiée (le N+1 mesuré, la requête sans index profilée). La mesure transforme l'optimisation d'un pari en une opération ciblée.

Limites et compromis. Optimiser trop tôt (avant d'avoir un problème mesuré) est de la sur-ingénierie (« premature optimization »). Le cache ajoute de la complexité (invalidation) qui ne se justifie que sur un vrai goulot de lecture. Un index accélère les lectures mais ralentit les écritures (jour 58). Chaque optimisation est un compromis à mesurer, pas un gain gratuit.

La règle du jour : **MESURE avant d'optimiser (l'intuition se trompe), corrige la VRAIE cause, re-mesure pour prouver le gain. Le N+1 (requêtes qui croissent avec la liste) se corrige par JOIN/batch. Le cache échange fraîcheur contre vitesse — n'accélère que le lu-souvent/change-peu, et exige une stratégie d'INVALIDATION explicite.**

---

**Mesurer rigoureusement — de la BASELINE aux percentiles.** « Mesurer avant d'optimiser » suppose de savoir QUOI mesurer et COMMENT. Le protocole professionnel : (1) établir une BASELINE — une mesure de référence de l'état actuel, dans des conditions REPRODUCTIBLES, AVANT de rien changer ; sans baseline, « c'est plus rapide » ne veut rien dire. (2) Formuler une HYPOTHÈSE explicite (« le goulot est la requête sans index sur `titre` ») : on optimise pour tester une hypothèse, pas au hasard. (3) PROFILER pour la valider — un profileur montre où le temps passe réellement, et révèle le *hot path* (le chemin de code le plus emprunté / le plus coûteux), là où un gain compte vraiment. (4) Changer UNE seule chose, puis RE-MESURER contre la baseline pour prouver le gain et vérifier qu'on n'a pas juste déplacé le problème. Un *benchmark* n'a de valeur que s'il est reproductible : même jeu de données, même machine au repos, plusieurs itérations.

**Latence, débit et percentiles.** Deux métriques distinctes : la LATENCE (temps d'UNE requête) et le DÉBIT (*throughput* : requêtes servies par seconde) — on ne les optimise pas pareil. Surtout, la latence ne se résume JAMAIS à une moyenne, qui cache les pics : on lit la distribution en PERCENTILES — p50 (la médiane, l'expérience typique), p95 et p99 (la *tail latency*, les 5 % / 1 % d'utilisateurs les plus lents). Un p50 à 20 ms avec un p99 à 3 s décrit un système qui « marche en moyenne » mais punit régulièrement de vrais utilisateurs. On fixe donc les objectifs sur les percentiles, pas sur la moyenne.

**Où est le goulot ? CPU / I/O / mémoire.** Un traitement lent est *CPU-bound* (le processeur calcule sans cesse — un tri, une sérialisation lourde), *I/O-bound* (il ATTEND le disque, le réseau, la base — le cas le plus fréquent d'une API) ou *memory-bound* (limité par les accès et allocations mémoire). Le remède diffère radicalement : optimiser l'algorithme ou paralléliser pour du CPU-bound ; batcher, cacher ou rendre asynchrone pour de l'I/O-bound. Identifier la nature du *bound* AVANT d'agir évite d'optimiser dans le vide. À surveiller aussi : les ALLOCATIONS inutiles (créer des objets dans une boucle chaude) et la FUITE MÉMOIRE (*memory leak* — de la mémoire jamais libérée : un cache sans borne, un écouteur jamais retiré — dont le symptôme est une consommation qui monte sans redescendre jusqu'au crash). Enfin le *cold start* : la toute première requête après démarrage paie l'initialisation (connexions, compilation JIT) et n'est PAS représentative — on l'exclut de la baseline.

**Défendre le gain : budget et régression.** Une optimisation n'est acquise que si elle est PROTÉGÉE. Un BUDGET DE PERFORMANCE fixe une limite explicite (« le p95 de `/livres` reste < 200 ms »). Une RÉGRESSION DE PERFORMANCE, c'est ce budget dépassé par un changement ultérieur : on la détecte en RE-MESURANT contre la baseline à chaque évolution (idéalement en CI), pas en attendant les plaintes. Contre-exemple classique — la *premature optimization* : complexifier un code FROID (jamais sur le hot path) pour un gain que personne ne mesurera ; on paie la lisibilité sans rien gagner. La règle de validation d'une optimisation : une baseline existe, la mesure est reproductible, le comportement fonctionnel est préservé (mêmes résultats), et le compromis (lisibilité, mémoire, complexité) est documenté.

**Mettre à l'échelle dans le cloud (fondation V22).** Quand la charge augmente, deux voies : la **scalabilité verticale** (une machine plus grosse — simple, mais plafonnée et créant un SPOF) et la **scalabilité horizontale** (plus d'instances derrière un load balancer — sans plafond dur, et redondante par nature). L'**autoscaling** ajuste automatiquement le nombre d'instances selon une métrique (CPU, requêtes) : on paie pour la charge réelle plutôt que pour le pire cas. La scalabilité horizontale est le socle de la haute disponibilité (jour 79) : plus d'une instance = tolérance à la panne ET capacité extensible.

**Stateless vs stateful : le prérequis du scaling.** Un service **stateless** ne garde aucun état local entre deux requêtes : n'importe quelle instance peut traiter n'importe quelle requête, donc on en ajoute/retire librement. Un service **stateful** garde un état local (session en mémoire, fichier local) : ajouter une instance casse la cohérence (une requête tombe sur une instance qui « ne connaît pas » l'utilisateur). La règle : **externaliser l'état** (cache/base partagés — le cache du jour, justement) pour rendre le service stateless AVANT d'activer l'autoscaling. Un service stateful derrière un autoscaling est un anti-pattern que le Cloud Topology Lab signale.

**Le compromis coût / performance / complexité.** Plus de capacité coûte plus cher ; l'autoscaling et le multi-zone ajoutent de la complexité d'exploitation. **Sur-dimensionner** (10 instances pour un trafic marginal) gaspille ; **sous-dimensionner** (une instance unique en production) crée une coupure au premier incident. Le bon dimensionnement se MESURE, il ne se devine pas — et tout chiffre de coût reste ici un ordre de grandeur pédagogique, jamais une estimation contractuelle.

---

**Scaling et choix du compute (fondation V25).** Deux façons de grandir : le **scaling vertical** (une machine plus grosse — simple mais plafonné et SPOF) et le **scaling horizontal** (plus d'instances — sans limite théorique, mais exige des instances **stateless** : aucun état local, l'état va dans une base/cache partagé). L'**autoscaling** ajoute/retire des instances selon la charge ; il n'a de sens que sur du stateless, derrière un **load balancer** (L4 pour la performance brute TCP, L7 pour le routage applicatif HTTP) avec health checks.

**Quand choisir VM, container ou serverless ?** La **VM** (EC2 / Azure VM) donne le contrôle total de l'OS — legacy, GPU, logiciels spécifiques — au prix d'une exploitation lourde. Le **container** (ECS/EKS, AKS/Container Apps) offre portabilité et densité pour une charge continue avec autoscaling. Le **serverless** (Lambda / Azure Functions) élimine la gestion de serveurs et se paie à l'usage (scale-to-zero) : idéal pour l'événementiel et les pics irréguliers, inadapté à une charge constante intensive (une VM/container y est souvent moins chère). La question n'est jamais « lequel est le meilleur » mais « lequel pour CETTE charge et CES contraintes ».

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : identifier et corriger un problème N+1 par la MESURE, puis ajouter un cache avec stratégie d'invalidation.

**Exemple simple** : le N+1 en chiffres. Afficher 50 emprunts avec leur livre : version naïve = 1 + 50 = 51 requêtes SQL. Version JOIN = 1 requête. On MESURE les deux (nombre de requêtes, temps) pour PROUVER le gain, au lieu de supposer.

**Raisonnement pas-à-pas** : (1) je MESURE (compter les requêtes SQL, chronométrer) pour trouver le vrai goulot ; (2) je repère le N+1 (requêtes qui croissent avec la liste) ; (3) je corrige par un JOIN ; (4) je RE-MESURE pour prouver le gain ; (5) j'ajoute un cache seulement là où c'est lu souvent et change peu, avec invalidation.

**Avant / Après (N+1)** :
```ts
// AVANT : N+1 — 1 requête liste + 1 par emprunt (mesuré : 51 requêtes pour 50 emprunts)
const emprunts = db.prepare('SELECT * FROM emprunts').all();
for (const e of emprunts) {
  e.livre = db.prepare('SELECT * FROM livres WHERE id = ?').get(e.livre_id);  // +1 par tour !
}
```
```ts
// APRÈS : un seul JOIN (mesuré : 1 requête) — gain PROUVÉ par la mesure
const emprunts = db.prepare(`
  SELECT e.*, l.titre AS livre_titre
  FROM emprunts e JOIN livres l ON l.id = e.livre_id
`).all();
// re-mesurer : nombre de requêtes 51 -> 1, latence divisée d'autant.
```
```ts
// CACHE avec stratégie d'INVALIDATION explicite (sur une lecture coûteuse et stable)
const cache = new Map<string, { data: unknown; expire: number }>();
function statsAvecCache() {
  const hit = cache.get('stats');
  if (hit && hit.expire > Date.now()) return hit.data;   // frais -> on sert le cache
  const data = calculerStatsCouteux();                   // sinon on recalcule
  cache.set('stats', { data, expire: Date.now() + 60_000 });  // INVALIDATION : TTL 60 s
  return data;
}
// invalidation aussi à l'écriture : cache.delete('stats') quand les données changent.
```
Le N+1 est trouvé PAR LA MESURE (51 requêtes) et corrigé par un JOIN (1 requête), gain re-mesuré ; le cache n'est ajouté que sur une lecture coûteuse et stable, avec une stratégie d'invalidation explicite (TTL + purge à l'écriture) — jamais un cache « au hasard » qui servirait du périmé.

## ⚠️ Erreurs fréquentes
- Optimiser au hasard sans profiler : on traite un goulot supposé, souvent le mauvais.
- Laisser un N+1 (requêtes qui croissent avec la liste) : latence qui explose à l'échelle.
- Cache sans stratégie d'invalidation : des données périmées sont servies silencieusement.
- Optimisation prématurée : compliquer le code avant d'avoir un problème mesuré.

## 🏢 Cas métier
La performance est un enjeu direct d'expérience utilisateur et de coût en entreprise : une API lente fait fuir les utilisateurs et alourdit la facture d'infrastructure. Le problème N+1 est l'un des plus fréquents et des plus coûteux en production — il passe inaperçu en développement (avec peu de données) puis fait exploser la latence à l'échelle réelle ; le détecter et le corriger par un JOIN ou un chargement groupé est une optimisation classique, souvent la première qu'on cherche sur une API lente. La règle « mesurer avant d'optimiser » évite le piège de l'optimisation prématurée qui complique le code sans gain, et le contre-piège d'optimiser le mauvais endroit. Le cache est un levier de performance majeur (il fait la différence entre une réponse en millisecondes et en secondes) mais ses deux problèmes difficiles (invalidation, nommage) causent des bugs redoutables de données périmées servies aux utilisateurs. Savoir profiler, reconnaître un N+1, et cacher avec une stratégie d'invalidation explicite est une compétence directement valorisée, et « comment optimiserais-tu cette API lente ? » est une question d'entretien fréquente qui teste la démarche (mesurer d'abord) autant que les techniques.

## 🎤 Question d'entretien
**« Comment optimises-tu une API lente ? »** → Ma première règle : MESURER avant d'optimiser, parce que l'intuition se trompe presque toujours sur l'emplacement du goulot. Je profile — temps par endpoint, nombre de requêtes SQL exécutées — pour trouver le VRAI goulot, je l'optimise, puis je RE-MESURE pour prouver le gain et vérifier que je n'ai pas déplacé le problème. Optimiser sans mesurer, c'est deviner. Le coupable le plus fréquent sur une API est le problème N+1 : afficher 50 emprunts avec leur livre en faisant 1 requête pour la liste + 50 requêtes pour les livres = 51 requêtes ; le symptôme est que le nombre de requêtes CROÎT avec la taille de la liste. Je le corrige par un JOIN ou une requête batch, ce qui passe de 51 requêtes à 1 ou 2. Ensuite seulement, si une lecture reste coûteuse ET stable, j'ajoute un CACHE — qui échange de la fraîcheur contre de la vitesse, donc uniquement là où les données sont lues souvent et changent peu, et TOUJOURS avec une stratégie d'invalidation explicite (un TTL, et une purge quand les données changent). **Relance possible** : « quels sont les pièges du cache ? » → ses deux problèmes difficiles : l'invalidation (quand purger — trop tôt le cache est inutile, trop tard on sert du périmé) et le nommage de la clé (une mauvaise clé sert la mauvaise donnée) ; un cache sans stratégie d'invalidation sert des données périmées silencieusement, ce qui est pire qu'un cache absent.
