## 🎯 Objectif du jour
Implémenter le socle : base SQLite + endpoints CRUD livres.

## 📖 Cours approfondi
**Concepts abordés :** Schéma · CRUD sur base · Couches · Paramétrage.

L'implémentation d'un socle suit un ordre précis : le schéma d'abord (init.sql exécutable — la base se reconstruit d'une commande), la couche data ensuite (toutes les requêtes paramétrées, isolées dans leur module), les routes enfin (traduction HTTP pure). Chaque étage se teste avant de monter le suivant.

Les statuts se choisissent avec précision dès maintenant : 201 + l'objet créé (avec son id) sur un POST réussi, 200 + l'objet sur un GET, 404 net sur un id inconnu, 400 détaillé sur une entrée invalide. Les corriger après coup casse les clients — les choisir bien d'emblée est gratuit.

Le réflexe pro : après chaque endpoint, LE tester immédiatement dans Postman (cas nominal + un cas d'erreur), pas « à la fin ».

**Modèle mental : on construit le socle d'une API dans un ORDRE précis, de bas en haut — le SCHÉMA d'abord (un `init.sql` exécutable qui reconstruit la base d'une commande), la couche DATA ensuite (toutes les requêtes paramétrées, isolées dans leur module), les ROUTES enfin (traduction HTTP pure). Chaque étage se teste AVANT de monter le suivant, si bien qu'un bug est toujours localisé à l'étage qu'on vient d'ajouter.** Ce n'est pas TaskFlow (jour 45, stockage JSON en mémoire) : c'est une vraie base relationnelle branchée derrière une structure en couches — le passage du prototype au socle crédible.

Pourquoi construire de bas en haut. Si l'on code les routes avant d'avoir un schéma et une couche data fiables, chaque bug peut venir de trois endroits à la fois (SQL, logique, HTTP) — impossible à isoler. En posant d'abord le schéma reconstructible, puis la couche data testée en isolation, puis les routes, chaque nouvel étage repose sur un socle DÉJÀ vérifié : le débogage reste local. C'est le « walking skeleton » (jour 45) appliqué à une base SQL.

Le schéma reconstructible, depuis les fondations. `init.sql` contient les `CREATE TABLE` (avec clés primaires, types, contraintes `NOT NULL`, clés étrangères) et se rejoue d'une commande : n'importe qui — toi demain, un collègue, la CI — reconstruit une base identique de zéro. Un schéma versionné rend le projet REPRODUCTIBLE ; un schéma qui n'existe que « dans la base de mon poste » est irreproductible (« ça marche chez moi »).

Le choix des statuts, dès maintenant. Les statuts HTTP (jour 50) se décident À LA CONCEPTION, pas après : 201 + l'objet créé (avec son id) sur un POST réussi, 200 + l'objet sur un GET, 204 sur un DELETE, 404 net sur un id inconnu, 400 détaillé sur une entrée invalide. Les corriger après coup CASSE les clients qui en dépendent ; les choisir bien d'emblée est gratuit. Chaque endpoint suit le même squelette : VALIDER l'entrée → INTERROGER (en paramétré) → répondre le STATUT correct.

La différence avec TaskFlow. TaskFlow persistait en JSON via une interface `Store` ; ici la couche data parle à SQLite en requêtes paramétrées (jour 57), et la structure routes/services/data (jour 53) est réelle. Le contrat conçu au jour 60 se concrétise : chaque endpoint promis est implémenté, testable via Postman.

Limites et compromis. Un CRUD complet est répétitif (add/list/get/update/delete se ressemblent) : la tentation de dupliquer est réelle — factoriser la couche data aide, mais sur un projet d'apprentissage la clarté prime sur l'abstraction prématurée. Et un socle « qui marche » n'est pas « fini » : la sécurité (jours 67-68), les tests (jour 65) et la doc (jour 66) viendront le durcir.

La règle du jour : **construis le socle de bas en haut (schéma reconstructible → couche data paramétrée → routes), teste chaque étage avant le suivant, choisis les statuts à la conception (201/200/204/400/404), et fais que `init.sql` reconstruise la base d'une seule commande. Chaque endpoint : valider → interroger (paramétré) → statut correct.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : implémenter l'endpoint `POST /livres` de bout en bout (schéma → couche data paramétrée → route), avec le bon statut.

**Exemple simple** : le squelette d'un endpoint. Trois gestes invariables — VALIDER (l'entrée est-elle correcte ? sinon 400), INTERROGER (la couche data, en paramétré), RÉPONDRE (201 + l'objet créé avec son id). Tous les endpoints suivent ce moule.

**Raisonnement pas-à-pas** : (1) le schéma définit la table `livres` (init.sql, rejouable) ; (2) la couche data expose `inserer`/`tous` en requêtes paramétrées ; (3) la route valide, appelle la couche data, renvoie 201 + l'objet ; (4) une entrée invalide → 400 avant tout accès base.

**Implémentation** :
```sql
-- init.sql : reconstruit la base d'une commande (sqlite3 livres.db < init.sql)
CREATE TABLE IF NOT EXISTS livres (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  titre     TEXT NOT NULL,
  auteur_id INTEGER REFERENCES auteurs(id),
  genre     TEXT,
  disponible INTEGER NOT NULL DEFAULT 1
);
```
```ts
// COUCHE DATA : SQL isolé, requêtes PARAMÉTRÉES (jour 57)
const dataLivres = {
  inserer: (titre: string, genre: string) =>
    db.prepare('INSERT INTO livres (titre, genre) VALUES (?, ?)').run(titre, genre),
  parId: (id: number) =>
    db.prepare('SELECT * FROM livres WHERE id = ?').get(id),
};

// ROUTE : valider -> interroger -> statut correct
app.post('/livres', (req, res) => {
  const { titre, genre } = req.body;
  if (typeof titre !== 'string' || !titre.trim())
    return res.status(400).json({ erreurs: ['titre requis'] });   // 400 AVANT la base
  const info = dataLivres.inserer(titre.trim(), genre ?? null);
  const cree = dataLivres.parId(Number(info.lastInsertRowid));
  res.status(201).json(cree);                                     // 201 + l'objet CRÉÉ (avec id)
});
```
Le schéma se rejoue d'une commande, la couche data isole le SQL paramétré, et la route suit valider → interroger → 201. Un GET sur un id inconnu renverra 404 ; une entrée invalide, 400 — décidés dès la conception.

## ⚠️ Erreurs fréquentes
- Statuts incorrects (200 pour une création ou une erreur) : casse les clients et détruit le langage des statuts.
- Validation oubliée sur POST/PUT : une entrée invalide atteint la base au lieu d'un 400 net.
- Schéma non reconstructible (base créée à la main) : projet irreproductible.
- SQL non paramétré ou éparpillé hors de la couche data : faille d'injection et migration difficile.

## 🏢 Cas métier
Construire une API sur une vraie base relationnelle, avec un schéma versionné et une structure en couches, est le pain quotidien du développement backend en entreprise. Le schéma reconstructible (init.sql, puis les migrations) est ce qui permet à une équipe de partager une base cohérente, de monter des environnements de test jetables, et à la CI de tourner sur une base propre — sans lui, chaque poste diverge et les bugs « ça marche chez moi » prolifèrent. Le choix rigoureux des statuts dès la conception est ce qui rend l'API consommable par les autres équipes (front, mobile) sans surprises. Un développeur qui livre un CRUD sur base avec statuts corrects, requêtes paramétrées et couche data isolée démontre exactement le socle attendu d'un profil back junior. LivreAPI, construit proprement, devient une pièce de portfolio que le recruteur peut cloner, reconstruire d'une commande et inspecter.

## 🎤 Question d'entretien
**« Comment implémentes-tu proprement le socle CRUD d'une API sur base de données ? »** → Je construis de bas en haut. D'abord le SCHÉMA dans un `init.sql` versionné qui reconstruit la base d'une seule commande — c'est ce qui rend le projet reproductible par un collègue ou la CI. Ensuite la couche DATA : tout le SQL y est isolé et PARAMÉTRÉ (jamais de concaténation, pour éviter l'injection). Enfin les ROUTES, qui ne font que traduire le HTTP : chaque endpoint suit le même squelette — VALIDER l'entrée (sinon 400 avant tout accès base), INTERROGER la couche data, répondre le STATUT correct. Je choisis les statuts à la conception : 201 + l'objet créé avec son id sur un POST, 200 sur un GET, 204 sur un DELETE, 404 sur un id inconnu, 400 détaillé sur une entrée invalide — parce que les corriger après coup casse les clients. Chaque étage se teste avant de monter le suivant, donc un bug reste localisé. **Relance possible** : « pourquoi renvoyer l'objet créé et pas juste un 201 vide ? » → parce que le client a besoin de l'id généré par la base pour les opérations suivantes (le lire, le modifier, le supprimer) ; renvoyer l'objet complet lui évite un aller-retour et rend l'API plus pratique à consommer.
