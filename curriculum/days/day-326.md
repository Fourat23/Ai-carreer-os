## 🎯 Objectif du jour
Automatiser la qualité.

## 📖 Cours approfondi
**Modèle mental : la CI complète automatise la qualité de DocSense — lint, tests unitaires et éval smoke tournent à chaque push, de sorte qu'aucun changement cassant ne passe inaperçu.** Tu as posé une CI vide au jour 307 ; ici tu la RENDS complète : elle vérifie maintenant réellement le code (lint), la logique (tests unitaires) et même la qualité IA (éval smoke en mode replay/mock). Une CI complète est le filet de sécurité qui protège les dernières semaines de build — chaque commit est validé automatiquement, la régression est impossible à merger sans la voir.

Les trois niveaux de vérification de la CI :
1. **Le lint** : la qualité de forme du code (style, erreurs évidentes, imports inutilisés). Rapide, il maintient la cohérence et attrape les erreurs triviales avant qu'elles n'atteignent la revue.
2. **Les tests unitaires** : la logique du cœur (le RAG, les workflows, le refus). Grâce à l'architecture hexagonale (jour 310), le cœur se teste avec des stubs — rapide, déterministe, gratuit. La CI lance ces tests à chaque push : une régression de logique est attrapée immédiatement.
3. **L'éval smoke (en mode replay/mock)** : le point spécifique à l'IA. Une évaluation LÉGÈRE (quelques questions du golden set) tourne en CI, mais avec les appels LLM MOCKÉS ou REJOUÉS (jour 327) — pas de vrais appels (coûteux, lents, non déterministes) dans la CI. Le smoke test vérifie que le pipeline complet ne casse pas (l'ingestion tourne, le retrieval retourne des chunks, la génération produit un format valide), sans mesurer la qualité fine (qui se fait avec le harnais complet, hors CI).

Pourquoi la CI complète est le filet des dernières semaines : le mois 12 est intense (fonctionnalités, sécurité, polish) ; sans CI, une amélioration peut casser silencieusement le RAG core ou un workflow, et on le découvre trop tard. Avec une CI complète, chaque commit est vérifié sur les trois niveaux — impossible de merger du code qui casse le lint, les tests ou le pipeline. C'est le principe « rendre la qualité automatique » (jour 307) porté à maturité. Et une CI qui inclut une éval smoke IA est un signal de sophistication : peu de projets testent leur pipeline LLM en CI. « Ma CI lint, teste, et vérifie que le pipeline IA tourne, à chaque commit » démontre une culture de qualité de production rare sur un projet de portfolio.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : la CI GitHub Actions complète de DocSense — lint + tests unitaires + éval smoke (replay/mock).

**Exemple simple** : l'éval smoke en une idée — lancer 3 questions du golden set avec les appels LLM MOCKÉS (réponses enregistrées), et vérifier que le pipeline produit un résultat au bon format. On teste que ça TOURNE, pas la qualité fine.

**Raisonnement pas-à-pas** : ajouter les trois niveaux au workflow CI, mocker les appels LLM pour l'éval smoke (rapide, déterministe, gratuit).

**Le workflow CI** :
```yaml
# .github/workflows/ci.yml — à chaque push :
jobs:
  qualite:
    - lint (ruff/flake8)                          # qualité de forme
    - tests unitaires (cœur avec stubs, j.310)    # logique, rapide/gratuit
    - éval smoke : 3 questions golden, appels LLM MOCKÉS (j.327)
        → vérifie que le pipeline TOURNE (ingestion→retrieval→génération, format OK)
        → PAS de vrais appels LLM (coûteux, lents, non déterministes) en CI
# La CI passe au ROUGE si lint, tests OU smoke échouent → régression bloquée
```

**Mini-quiz** : (a) Pourquoi mocker les appels LLM dans l'éval smoke de la CI ? (b) Que vérifie une éval smoke vs le harnais complet ? (c) Que garantit une CI complète pour les dernières semaines ?
→ (a) les vrais appels sont coûteux, lents et non déterministes — inadaptés à une CI qui tourne à chaque push ; (b) le smoke vérifie que le pipeline TOURNE (format valide), le harnais complet mesure la qualité fine (hors CI) ; (c) chaque commit est vérifié sur 3 niveaux — impossible de merger une régression sans la voir.

**Variante** : casse volontairement le pipeline (change un format de sortie) et pousse — l'éval smoke doit passer au ROUGE. Une CI qui ne détecte pas un pipeline cassé n'est pas un filet.

## 🏢 Cas métier
Une CI complète qui inclut une vérification du pipeline IA est un standard de production rare sur les projets IA : la plupart testent le code classique mais laissent le pipeline LLM non testé (« c'est non déterministe, on ne peut pas tester »), et découvrent les régressions en production. Les équipes matures mockent/rejouent les appels LLM pour tester que le pipeline TOURNE (format, enchaînement) en CI, tout en gardant l'évaluation de qualité fine hors CI. Pour DocSense, une CI qui lint, teste et vérifie le pipeline à chaque commit protège les semaines intenses du mois 12 et signale une culture de qualité de production. « Ma CI teste même mon pipeline LLM, en mode mock » est un signal de sophistication qui distingue un projet de portfolio.

## 🎤 Question d'entretien
**« Comment testes-tu du code qui appelle un LLM en CI ? »** → Je mocke ou rejoue les appels LLM : les vrais appels sont coûteux, lents et non déterministes — inadaptés à une CI qui tourne à chaque push. Ma CI complète a trois niveaux : lint (forme), tests unitaires (logique du cœur, testable avec stubs grâce à l'hexagonal), et éval smoke (quelques questions du golden set avec appels LLM MOCKÉS, pour vérifier que le pipeline TOURNE — ingestion → retrieval → génération, format valide — sans mesurer la qualité fine qui se fait hors CI). Chaque commit est ainsi vérifié sur trois niveaux, impossible de merger une régression sans la voir. Peu de projets testent leur pipeline LLM en CI — c'est un signal de maturité.
