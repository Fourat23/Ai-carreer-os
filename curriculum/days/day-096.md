## 🎯 Objectif du jour
Maîtriser les formulaires contrôlés.

## 📖 Cours approfondi
**Modèle mental : dans un formulaire contrôlé, le state React est la SOURCE DE VÉRITÉ et le champ HTML n'en est que le reflet — la valeur affichée EST le state, pas l'inverse.** Un `<input>` non contrôlé garde sa propre valeur dans le DOM ; tu dois aller la lire. Un input CONTRÔLÉ tire sa valeur du state (`value={x}`) et renvoie chaque frappe au state (`onChange`). Le state pilote l'affichage ; le DOM ne fait qu'obéir. C'est le prolongement direct de « l'UI est une fonction du state » (jour 93) appliqué à la saisie.

Le cycle d'un champ contrôlé :
1. `value={valeur}` : le champ AFFICHE le state.
2. `onChange={e => setValeur(e.target.value)}` : chaque frappe MET À JOUR le state.
3. Le nouveau state re-rend le champ avec la nouvelle valeur. La boucle est fermée : à aucun moment le DOM n'est « en avance » sur le state.

Pourquoi cette contrainte est un avantage : parce que le state contient TOUJOURS la valeur actuelle, tu peux valider en direct, désactiver le bouton d'envoi tant que c'est invalide, formater à la volée, et pré-remplir un formulaire d'édition (jour 114) en initialisant le state. La validation devient une fonction PURE du state : `erreurs = valider(form)`, recalculée à chaque frappe — pas un contrôle éparpillé.

Les deux règles qui font un formulaire professionnel :
- **La validation affiche des erreurs UTILES au bon moment** : pas « champ invalide » mais « l'email doit contenir @ » ; idéalement après que l'utilisateur a quitté le champ (blur), pas à la première lettre tapée.
- **La soumission empêche l'envoi invalide** : `e.preventDefault()` (sinon la page recharge), on valide, et on ne poste que si tout est bon ; pendant l'envoi, on désactive le bouton (état « en cours ») pour éviter le double-clic.

La bascule par rapport à un formulaire HTML classique : tu ne « lis pas le DOM à la soumission », tu as déjà tout dans le state à chaque instant.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : un formulaire d'ajout de livre contrôlé, validé en direct, qui poste vers l'API.

**Exemple simple** : un seul champ contrôlé — `<input value={titre} onChange={e => setTitre(e.target.value)} />`. La valeur vient du state, chaque frappe y retourne. Tout formulaire n'est que la répétition de ce cycle par champ.

**Raisonnement pas-à-pas** : un state par champ (ou un state-objet) → une validation dérivée pure → un bouton désactivé si invalide → une soumission qui preventDefault, revalide et poste.

**Solution** :
```tsx
function AjoutLivre({ onCreer }: { onCreer: (l: NouveauLivre) => Promise<void> }) {
  const [form, setForm] = useState({ titre: '', auteur: '' });
  const [envoi, setEnvoi] = useState(false);
  const maj = (champ: string) => (e: React.ChangeEvent<HTMLInputElement>) =>
    setForm((f) => ({ ...f, [champ]: e.target.value }));           // maj immuable

  const erreurs = {                                                 // validation DÉRIVÉE (pure)
    titre: form.titre.trim() ? '' : 'Le titre est requis',
    auteur: form.auteur.trim() ? '' : "L'auteur est requis",
  };
  const valide = !erreurs.titre && !erreurs.auteur;

  const soumettre = async (e: React.FormEvent) => {
    e.preventDefault();                                             // pas de rechargement
    if (!valide) return;
    setEnvoi(true);
    try { await onCreer(form); setForm({ titre: '', auteur: '' }); }
    finally { setEnvoi(false); }                                    // bouton réactivé quoi qu'il arrive
  };

  return (
    <form onSubmit={soumettre}>
      <input value={form.titre} onChange={maj('titre')} />
      {erreurs.titre && <span className="err">{erreurs.titre}</span>}
      <button disabled={!valide || envoi}>{envoi ? 'Envoi...' : 'Ajouter'}</button>
    </form>
  );
}
```

**Mini-quiz** : (a) Où vit la valeur d'un champ contrôlé ? (b) Pourquoi `e.preventDefault()` à la soumission ? (c) Pourquoi la validation est-elle dérivée et non stockée en state ?
→ (a) dans le state React (le champ n'en est que le reflet) ; (b) sinon le navigateur recharge la page et perd le state ; (c) elle se recalcule à chaque frappe à partir du form — la stocker créerait une source de vérité redondante à resynchroniser (jour 93).

**Variante** : n'affiche l'erreur d'un champ qu'après un `onBlur` (champ quitté) — l'utilisateur n'est pas harcelé dès la première lettre, une UX bien plus soignée.

## 🏢 Cas métier
Les formulaires sont partout (inscription, paiement, recherche, back-office) et sont la première source de frustration utilisateur quand ils sont mal faits : validation qui hurle dès la première lettre, bouton d'envoi cliquable deux fois qui crée un doublon, page qui recharge et perd la saisie. Un formulaire contrôlé bien construit — validation dérivée, bouton désactivé pendant l'envoi, erreurs utiles au bon moment — règle tout cela. C'est un livrable que les recruteurs demandent explicitement (« code-moi un formulaire d'inscription validé ») parce qu'il condense state, validation, async et UX.

## 🎤 Question d'entretien
**« Quelle est la différence entre un champ contrôlé et non contrôlé, et lequel préfères-tu ? »** → Un champ CONTRÔLÉ tire sa valeur du state React (`value={x}`) et la met à jour à chaque frappe (`onChange`) : le state est la source de vérité, le DOM n'est qu'un reflet. Un champ NON contrôlé garde sa valeur dans le DOM et je dois aller la lire. Je préfère contrôlé par défaut : parce que le state contient toujours la valeur, je peux valider en direct, désactiver l'envoi tant que c'est invalide, formater à la volée et pré-remplir un formulaire d'édition. La validation devient une fonction pure du state, recalculée à chaque frappe.
