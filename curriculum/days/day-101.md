## 🎯 Objectif du jour
Utiliser Context sans sur-ingénierie.

## 📖 Cours approfondi
**Modèle mental : Context est un CANAL DE DIFFUSION pour un état GLOBAL et STABLE (le thème, l'utilisateur connecté, la langue) — pas un remplacement des props, et surtout pas un endroit pour un état qui change souvent.** Tu sais lever l'état (jour 100) ; mais quand une donnée est lue par BEAUCOUP de composants à des profondeurs variées (le thème de toute l'app, l'utilisateur connecté partout), la faire descendre en props traverse dix niveaux qui ne l'utilisent pas : le props drilling. Context résout précisément ce cas — il rend une valeur disponible à tout un sous-arbre SANS la passer manuellement de parent en enfant.

Les trois pièces de Context :
1. **Le `createContext`** : déclare le canal et sa valeur par défaut.
2. **Le `Provider`** : enveloppe un sous-arbre et y injecte la valeur courante (souvent un state + son setter).
3. **Le `useContext`** : n'importe quel composant du sous-arbre lit la valeur, quelle que soit sa profondeur, sans props intermédiaires.

Mais Context a un COÛT qu'il faut connaître : **quand la valeur du Provider change, TOUS les composants qui la consomment se re-rendent**. C'est pourquoi Context convient à un état qui change RAREMENT (thème, utilisateur) et devient un piège pour un état qui change souvent (la valeur d'un champ, la position de la souris) — il déclencherait des re-rendus massifs (jour 102). Context n'est pas non plus un gestionnaire d'état : c'est un mécanisme de TRANSPORT.

La règle qui évite la sur-ingénierie : **Context quand une donnée est vraiment globale et stable ET que le props drilling devient douloureux — sinon, des props suffisent**. Le réflexe débutant « tout mettre en Context pour éviter les props » est une erreur : les props sont explicites et locales (faciles à suivre), Context est implicite et global (plus difficile à tracer). On paie Context en lisibilité et en re-rendus ; on ne l'utilise que quand le bénéfice (éliminer un vrai props drilling) dépasse ce coût.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : un thème clair/sombre partagé via Context, avec la justification du choix.

**Exemple simple** : le hook de consommation typé — `const { theme, toggle } = useContext(ThemeContext)`. N'importe quel composant du sous-arbre y accède sans qu'aucun parent n'ait passé de prop. C'est exactement ce que Context fait gagner.

**Raisonnement pas-à-pas** : créer le contexte → un Provider qui détient le state → des consommateurs qui lisent, quelle que soit leur profondeur → vérifier que la donnée est bien globale ET stable.

**Solution** :
```tsx
type ThemeCtx = { theme: 'clair' | 'sombre'; toggle: () => void };
const ThemeContext = createContext<ThemeCtx | null>(null);

function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<'clair' | 'sombre'>('clair');
  const toggle = () => setTheme((t) => (t === 'clair' ? 'sombre' : 'clair'));
  return <ThemeContext.Provider value={{ theme, toggle }}>{children}</ThemeContext.Provider>;
}

function useTheme() {                                    // hook custom : accès sûr
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme doit être utilisé dans un ThemeProvider');
  return ctx;
}
// N'importe où DANS le Provider, à n'importe quelle profondeur :
function BoutonTheme() { const { theme, toggle } = useTheme(); return <button onClick={toggle}>{theme}</button>; }
```

**Mini-quiz** : (a) Que se passe-t-il pour les consommateurs quand la valeur du Provider change ? (b) Context convient-il à la valeur d'un champ de saisie ? (c) Context remplace-t-il les props ?
→ (a) ils se re-rendent tous — d'où Context pour un état STABLE ; (b) non, ça change trop souvent, re-rendus massifs — garde-le local ; (c) non, c'est un transport pour un état global ; les props restent le défaut pour le local.

**Variante** : ajoute un garde-fou (le hook `useTheme` qui lève une erreur hors Provider) — il transforme une erreur silencieuse (valeur par défaut inattendue) en message clair, un réflexe de robustesse.

## 🏢 Cas métier
Context est utilisé dans presque toutes les apps React pour un petit nombre de valeurs vraiment globales : thème, utilisateur authentifié, langue, notifications. Le problème récurrent en entreprise est l'ABUS de Context — des équipes y mettent des états qui changent souvent, provoquant des re-rendus en cascade et des bugs de performance difficiles à diagnostiquer (jour 102). Les revues de code front vérifient qu'un Context est justifié (donnée globale + stable) et non un raccourci pour éviter de réfléchir au placement de l'état. Savoir QUAND ne PAS utiliser Context est aussi valorisé que savoir l'utiliser — c'est le signe d'un jugement d'architecture mûr.

## 🎤 Question d'entretien
**« Quand utilises-tu Context, et quels sont ses pièges ? »** → J'utilise Context pour un état vraiment GLOBAL et STABLE (thème, utilisateur connecté, langue) quand le passer en props provoquerait du props drilling sur plusieurs niveaux. Context est un mécanisme de TRANSPORT, pas un gestionnaire d'état. Son piège principal : quand la valeur du Provider change, TOUS ses consommateurs se re-rendent — donc il est inadapté à un état qui change souvent (valeur de champ, position souris), qui déclencherait des re-rendus massifs. Le réflexe « tout mettre en Context » est une erreur : les props sont explicites et locales, Context est implicite et global. Je ne paie ce coût que quand il élimine un vrai props drilling.
