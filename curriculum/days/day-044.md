## 📖 Cours approfondi
**Concepts abordés :** Lecture de spec · Types avant code · Interface Store · Découpage en jalons.

Concevoir les types AVANT le code force à comprendre le domaine : quelles entités (Task), quels états possibles (union littérale de statuts), quelles opérations (le contrat Store). Un modèle clair rend l'implémentation évidente ; un modèle flou la rend tortueuse.

L'interface `Store` est ta première INVERSION DE DÉPENDANCE consciente : la logique métier dépend d'un CONTRAT (save/load/all), pas d'une implémentation (JSON, SQLite). Le jour où le stockage change, un seul fichier change. C'est le principe qui structurera l'architecture hexagonale du mois 10 — à petite échelle dès aujourd'hui.

Le backlog en jalons DÉMONTRABLES (« add + list fonctionnent ») plutôt qu'en activités floues (« avancer sur le CLI ») rend le progrès mesurable et la procrastination visible.

**Modèle mental : concevoir les TYPES avant d'écrire la moindre logique force à comprendre le DOMAINE — quelles entités, quels états possibles, quelles opérations. Et l'interface `Store` est ta première INVERSION DE DÉPENDANCE consciente : la logique métier dépend d'un CONTRAT (save/load/all), pas d'une implémentation (JSON, SQLite). Le jour où le stockage change, UN SEUL fichier change. Un modèle clair rend l'implémentation évidente ; un modèle flou la rend tortueuse.** Ce jour ne code pas TaskFlow : il en pose les fondations pour que le reste coule de source.

Pourquoi concevoir avant de coder. La tentation est de « commencer à coder » tout de suite. Mais sans modèle du domaine, on découvre les incohérences en cours de route, on refactore sans cesse, on empile les cas particuliers. Poser d'abord les types (Task, statuts, opérations) OBLIGE à répondre aux vraies questions — un statut peut-il être vide ? une tâche a-t-elle une priorité obligatoire ? — avant qu'elles ne deviennent des bugs. Le type est un plan qui révèle les décisions cachées.

L'inversion de dépendance, depuis les fondations. Normalement, la logique métier « dépend » du stockage : elle appelle directement des fonctions de lecture/écriture de fichier. Problème : changer de stockage oblige à réécrire la logique. L'inversion consiste à faire dépendre la logique d'une ABSTRACTION — une interface `Store { save(); load(); all() }` — et à fournir une IMPLÉMENTATION concrète (JsonStore) séparément. La logique ne connaît QUE le contrat ; l'implémentation est branchée « par le dehors ». C'est le D de SOLID, et le germe de l'architecture hexagonale (ports & adapters) du mois 10, appliqué ici à petite échelle.

La différence contrat vs implémentation. Le CONTRAT (`interface Store`) décrit CE QU'ON PEUT FAIRE (sauver une tâche, tout charger) sans dire COMMENT. L'IMPLÉMENTATION (JsonStore, plus tard SqliteStore) dit COMMENT (fichier JSON, base SQL). Programmer contre le contrat rend le COMMENT interchangeable. C'est exactement l'interface `Notifieur` du jour 38, appliquée à la persistance : le polymorphisme au service du découplage.

Le backlog en jalons DÉMONTRABLES. « Avancer sur le CLI » n'est pas un jalon : on ne peut pas le cocher. « add + list fonctionnent de bout en bout » en est un : il est vérifiable. Découper en jalons démontrables rend le progrès mesurable et la procrastination visible — chaque jalon est une preuve, pas une intention.

Limites et compromis. Sur-concevoir les types (abstractions prématurées pour des besoins hypothétiques) est aussi néfaste que sous-concevoir (`any` partout) : le bon niveau est « assez précis pour interdire l'incohérence, assez souple pour évoluer ». L'inversion de dépendance a un coût (une interface de plus) qui ne se justifie que si l'implémentation peut réellement varier — ici oui (JSON → SQLite est explicitement prévu). Enfin, un modèle n'est jamais figé : il s'ajustera au contact du code, et c'est normal.

La règle du jour : **conçois les types AVANT la logique pour comprendre le domaine, et fais dépendre ta logique d'un CONTRAT (interface Store) pas d'une implémentation — c'est l'inversion de dépendance, qui rend le stockage interchangeable (un seul fichier change). Découpe en jalons démontrables, pas en activités floues.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : concevoir l'interface `Store` et les types de TaskFlow de sorte que passer de JSON à SQLite ne change QU'UN fichier.

**Exemple simple** : le test de l'inversion réussie. Si je demande « combien de fichiers changent pour migrer vers SQLite ? » et que la réponse est UN (la nouvelle implémentation), la conception est bonne. Si c'est « toute la logique », l'inversion a échoué.

**Raisonnement pas-à-pas** : (1) je modélise l'entité `Task` et ses états (statut en union littérale) ; (2) je définis le CONTRAT `Store` (ce qu'on peut faire, pas comment) ; (3) la logique métier ne dépendra QUE de `Store` ; (4) l'implémentation concrète (JsonStore) sera fournie séparément — interchangeable.

**Conception (types.ts)** :
```ts
type Statut = 'todo' | 'doing' | 'done';
type Priorite = 'basse' | 'moyenne' | 'haute';

interface Task {
  readonly id: number;
  titre: string;
  statut: Statut;
  priorite: Priorite;
  creeLe: string;   // ISO
}

// Le CONTRAT : ce qu'on peut faire, sans dire COMMENT (fichier ? base ?)
interface Store {
  all(): Task[];
  save(taches: Task[]): void;
  load(): Task[];
}

// La logique métier dépend de l'ABSTRACTION Store, jamais d'un fichier
function ajouterTache(store: Store, titre: string, priorite: Priorite): Task {
  const taches = store.load();
  const id = taches.length ? Math.max(...taches.map(t => t.id)) + 1 : 1;  // max+1
  const t: Task = { id, titre, statut: 'todo', priorite, creeLe: new Date().toISOString() };
  store.save([...taches, t]);   // immuable : nouvelle liste
  return t;
}
// Demain, SqliteStore implements Store -> ajouterTache N'EST PAS touchée.
```
La logique parle au contrat `Store` ; l'implémentation (JSON aujourd'hui, SQLite demain) est branchée par le dehors. Un seul fichier changera.

## ⚠️ Erreurs fréquentes
- Types trop rigides (impossibles à faire évoluer) ou trop lâches (any qui annule le bénéfice de la conception).
- Jalons non démontrables (« avancer sur le CLI ») qui masquent la procrastination.
- Faire dépendre la logique d'un fichier concret au lieu du contrat Store : l'inversion échoue, la migration touchera tout.
- Sur-concevoir des abstractions pour des besoins hypothétiques : l'interface ne se justifie que si l'implémentation varie réellement (ici oui).

## 🏢 Cas métier
L'inversion de dépendance est un pilier de l'architecture logicielle professionnelle : les applications testables et évolutives font dépendre leur cœur métier d'INTERFACES (dépôts, passerelles, services) plutôt que de détails d'infrastructure (base précise, API tierce, système de fichiers). Bénéfices concrets : on peut TESTER la logique avec une fausse implémentation (un Store en mémoire) sans base réelle, CHANGER de fournisseur (SQLite → PostgreSQL → cloud) sans réécrire le métier, et FAIRE ÉVOLUER l'infrastructure indépendamment. C'est le fondement de l'architecture hexagonale (ports & adapters) très demandée sur les postes back. Concevoir une interface Store pour TaskFlow, même petit, démontre en entretien que tu penses découplage et testabilité — et un backlog en jalons démontrables prouve que tu sais planifier un projet, pas seulement coder.

## 🎤 Question d'entretien
**« Comment conçois-tu une application pour que changer de base de données ne casse pas la logique métier ? »** → J'applique l'inversion de dépendance : la logique métier ne dépend pas d'une implémentation de stockage, mais d'un CONTRAT abstrait — une interface, par exemple `Store { load(); save(); all() }`. La logique parle uniquement à ce contrat ; l'implémentation concrète (un JsonStore, plus tard un SqliteStore ou un PostgresStore) est fournie séparément et branchée « par le dehors ». Résultat : migrer de JSON à SQLite ne change QU'UN fichier — la nouvelle implémentation — sans toucher au métier. C'est le D de SOLID et le principe de l'architecture hexagonale (ports & adapters). Ça rend aussi le métier TESTABLE : je lui injecte un Store en mémoire pour les tests, sans base réelle. En amont, je conçois les TYPES avant la logique, parce que modéliser le domaine (entités, états en union littérale, opérations) fait émerger les décisions avant qu'elles ne deviennent des bugs. **Relance possible** : « quand cette abstraction n'en vaut-elle pas la peine ? » → quand l'implémentation ne variera jamais : ajouter une interface pour un stockage unique et définitif est de la sur-ingénierie. Ici, JSON → SQLite est explicitement prévu, donc elle se justifie.
