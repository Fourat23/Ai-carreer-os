## 🎯 Objectif du jour
Créer des features utiles.

## 📖 Cours approfondi
**Modèle mental : souvent, de meilleures FEATURES battent un meilleur modèle — transformer les données brutes en variables porteuses de SIGNAL (ratios, agrégats, décompositions de dates, encodages métier) apporte plus qu'un algorithme sophistiqué sur des features pauvres. Chaque feature créée est une HYPOTHÈSE métier, testée par la mesure sur la validation.** Le feature engineering est le levier le plus rentable du ML tabulaire : c'est là que la connaissance du DOMAINE se transforme en performance, bien plus que dans le choix de l'algorithme.

Ce que le feature engineering apporte, depuis les fondations :
1. **Rendre le signal ACCESSIBLE au modèle** : un modèle ne « voit » que ses features. Une date brute (« 2024-03-15 ») est peu utile ; en extraire le jour de semaine, le mois, ou « jours depuis le dernier achat » crée des variables qui portent un signal réel. Un modèle linéaire ne captera « prix par m² » que si tu crées le ratio ; il ne l'invente pas.
2. **Encoder la connaissance métier** : « les clients qui contactent le support 3+ fois par mois sont à risque » devient une feature `contacts_support_par_mois`. Chaque feature est une hypothèse sur ce qui explique la cible — c'est du raisonnement métier, pas du calcul aveugle.
3. **Les transformations courantes** : ratios et différences (prix/surface, revenus − dépenses), agrégats (moyenne d'achats par client), décomposition temporelle (jour/mois/saison, ancienneté), binning (regrouper l'âge en tranches), interactions (croiser deux features). Chacune expose une facette du signal.
4. **La mesure comme juge** : une feature n'est utile que si elle AMÉLIORE la validation. On tient un JOURNAL des tentatives et de leurs effets — certaines hypothèses métier séduisantes n'apportent rien, d'autres inattendues aident. Seule la mesure tranche.

Le piège majeur — le leakage par les features : créer une feature à partir d'information non disponible au moment de la prédiction (une agrégation calculée sur tout le dataset test compris, une feature qui encode la cible) donne des gains illusoires (jour 157). Toute feature doit être calculable avec l'information disponible AU MOMENT de la prédiction, et son calcul appris sur le train seul.

La règle du jour : **crée des features qui rendent le signal accessible et encodent la connaissance métier (ratios, agrégats, dates, interactions), traite chacune comme une hypothèse testée sur la validation, et vérifie l'absence de leakage. De meilleures features battent souvent un meilleur modèle**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : améliorer un modèle UNIQUEMENT par les features, avec un journal des tentatives et effets.

**Exemple simple** : une feature qui expose le signal — sur des données immobilières, créer `prix_au_m2 = prix / surface` donne au modèle un ratio qu'il ne pouvait pas déduire d'une combinaison linéaire de prix et surface. Une hypothèse métier, une variable.

**Raisonnement pas-à-pas** : partir d'un modèle fixe → créer une feature (hypothèse métier) → mesurer l'effet sur la validation → journaliser → garder si ça aide, jeter sinon → vérifier l'absence de leakage.

**Implémentation** :
```python
from sklearn.model_selection import cross_val_score

def score(df):   # modèle FIXE : seules les features changent
    return cross_val_score(model, df, y, cv=5, scoring="roc_auc").mean()

base = score(X)                                  # référence

# Hypothèse 1 : le rythme de contact au support signale le risque
X1 = X.assign(contacts_par_mois=X["contacts"] / X["anciennete_mois"].clip(lower=1))
print("contacts/mois:", score(X1) - base)         # gain mesuré sur la validation

# Hypothèse 2 : décomposer la date d'inscription
X2 = X1.assign(mois_inscription=pd.to_datetime(X["date_insc"]).dt.month)
print("+ mois inscription:", score(X2) - base)

# JOURNAL : hypothèse -> effet (gardée si gain, jetée sinon). Vérifier : pas de leakage
# (chaque feature calculable avec l'info disponible AU MOMENT de la prédiction).
```

**Mini-quiz** : (a) Pourquoi une bonne feature peut-elle battre un meilleur modèle ? (b) Qu'est-ce qu'une feature au fond ? (c) Comment sait-on qu'une feature est utile ?
→ (a) un modèle ne voit que ses features ; rendre le signal accessible (un ratio, un agrégat) apporte souvent plus qu'un algorithme sophistiqué sur des features pauvres ; (b) une hypothèse métier sur ce qui explique la cible, encodée en variable ; (c) elle améliore la VALIDATION — on mesure, on journalise ; certaines hypothèses séduisantes n'apportent rien.

**Variante** : crée une feature à partir d'une agrégation calculée sur TOUT le dataset (test compris) et observe le gain « magique » — puis recalcule-la proprement (train seul). Tu vois le leakage par les features et pourquoi chaque feature doit être calculée sur le train uniquement.

## 🏢 Cas métier
Le feature engineering est le levier le plus rentable du ML tabulaire en entreprise : dans la plupart des projets et compétitions, les gains décisifs viennent de features intelligentes issues de la connaissance métier, bien plus que du choix d'algorithme (une bonne feature sur une régression logistique bat souvent une forêt sur des features brutes). C'est là que la collaboration avec les experts métier (SME) paie : ils savent quels signaux comptent (« un client qui change de forfait deux fois en trois mois est à risque »). Les data scientists qui traitent chaque feature comme une hypothèse testée et journalisée, en se méfiant du leakage, obtiennent des gains fiables ; ceux qui empilent des algorithmes sur des features pauvres stagnent. C'est une compétence cœur, directement valorisée.
