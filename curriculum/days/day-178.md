## 🎯 Objectif du jour
Améliorer par les features.

## 📖 Cours approfondi
**Modèle mental : sur un vrai projet, les gains décisifs viennent surtout des FEATURES dérivées justifiées par le métier — chaque feature est une hypothèse (« les clients qui contactent souvent le support churnent plus ») MESURÉE en validation, et l'anti-leakage se vérifie à CHAQUE ajout, car une feature qui fuit donne un gain illusoire.** C'est le jour 169 (feature engineering conceptuel) appliqué à ChurnScope avec la contrainte du réel : sur un modèle déjà comparé (jour 177), on cherche les gains là où ils sont les plus rentables — les features — en gardant une rigueur absolue anti-leakage.

La démarche appliquée, depuis les acquis :
1. **Partir des hypothèses métier ET de l'analyse d'erreurs** : quelles features pourraient porter du signal sur le churn ? Le rythme de contact au support, la baisse récente d'usage, l'ancienneté, les changements de forfait. L'analyse d'erreurs (jour 167) oriente : si le modèle rate les nouveaux clients, créer des features sur eux.
2. **Créer, mesurer, journaliser** : chaque feature est ajoutée, son effet MESURÉ sur la validation croisée (le modèle et le protocole restent fixes), et le résultat journalisé (gardée si gain, jetée sinon). Certaines hypothèses séduisantes n'apportent rien ; seule la mesure tranche.
3. **La vigilance anti-leakage RENFORCÉE** : sur un vrai projet, le leakage par les features est le danger n°1. Une feature comme « nombre de jours depuis la résiliation » ENCODE la cible (elle n'existe que si le client a churné) — gain magique, modèle inutilisable. Chaque feature doit être calculable avec l'information disponible À LA DATE D'OBSERVATION, et son calcul appris sur le train seul (via Pipeline).
4. **Les features temporelles et agrégées** : sur des données clients, les features les plus puissantes sont souvent des agrégats sur une fenêtre temporelle (achats des 30 derniers jours, tendance d'usage) — mais ce sont AUSSI les plus à risque de leakage (attention à la fenêtre : ne pas inclure d'information postérieure à la date d'observation).

Ce qui fait la valeur de cette étape : sur un projet tabulaire réel, le feature engineering rapporte généralement PLUS que le choix ou le réglage du modèle. C'est là que la connaissance métier se transforme en performance, et où un data scientist attentif se distingue. Mais la contrepartie est la rigueur : chaque gain doit être mesuré ET vérifié sans leakage, sinon on construit une illusion.

La règle du jour : **crée des features dérivées justifiées par le métier et l'analyse d'erreurs, mesure chaque gain sur la validation, journalise, et vérifie l'absence de leakage à chaque ajout (feature calculable à la date d'observation, sur le train seul). Sur un projet réel, les features rapportent plus que le modèle — mais un gain non vérifié est souvent un leakage**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : ajouter des features dérivées justifiées à ChurnScope, mesurer l'impact, vérifier l'anti-leakage.

**Exemple simple** : une feature métier mesurée — « baisse d'usage récente » = usage des 30 derniers jours / usage des 30 précédents. Hypothèse : une chute annonce le départ. On l'ajoute, on mesure sur la validation, on garde si gain. Et on vérifie : la fenêtre n'inclut aucune donnée postérieure à la date d'observation.

**Raisonnement pas-à-pas** : formuler l'hypothèse métier → créer la feature dans le Pipeline → mesurer le gain en CV → journaliser → vérifier l'absence de leakage temporel.

**Implémentation** :
```python
from sklearn.model_selection import cross_val_score

def auc(df):   # modèle et protocole FIXES ; seules les features changent
    return cross_val_score(pipe, df, y_dev, cv=5, scoring="roc_auc").mean()

base = auc(X_dev)

# Hypothèse 1 : rythme de contact au support (métier) — calculable à la date d'observation
X1 = X_dev.assign(contacts_par_mois=X_dev["contacts_90j"] / 3)
print("contacts/mois :", round(auc(X1) - base, 4))

# Hypothèse 2 : baisse d'usage récente (fenêtre AVANT la date d'observation -> pas de leakage)
X2 = X1.assign(baisse_usage=X_dev["usage_30j"] / X_dev["usage_30j_prec"].clip(lower=1))
print("+ baisse usage :", round(auc(X2) - base, 4))

# JOURNAL : hypothèse -> gain -> gardée/jetée. VÉRIF : aucune feature postérieure à l'observation.
```

**Mini-quiz** : (a) D'où viennent les meilleures features sur un projet réel ? (b) Comment vérifie-t-on qu'une feature ne fuit pas ? (c) Pourquoi mesurer chaque feature sur la validation ?
→ (a) de la connaissance métier et de l'analyse d'erreurs (quelles sous-populations ratées) ; les agrégats temporels sont puissants mais risqués ; (b) elle doit être calculable avec l'information disponible À LA DATE D'OBSERVATION, sans inclure de donnée postérieure, et calculée sur le train seul ; (c) certaines hypothèses séduisantes n'apportent rien, et un gain non mesuré (ou dû à un leakage) est une illusion.

**Variante** : ajoute volontairement une feature « jours depuis résiliation » (qui encode la cible) et regarde l'AUC exploser à ~1,0. Puis retire-la. C'est le leakage le plus dangereux d'un projet churn : une feature qui n'existe QUE parce que le client a déjà churné.

## 🏢 Cas métier
Sur les projets de churn (et le ML tabulaire en général), le feature engineering est l'étape à plus fort impact ET le principal nid à leakage. Les gains décisifs viennent de features métier (baisse d'usage, rythme de contact, changements de forfait) que la connaissance du domaine suggère et que l'analyse d'erreurs oriente. Mais les projets churn sont truffés de fuites : des features comme « raison de résiliation » ou « date de fin de contrat » encodent la cible et donnent des modèles « parfaits » et inutilisables. Les data scientists qui créent des features justifiées, mesurent chaque gain et vérifient la disponibilité temporelle de chaque feature livrent des modèles fiables ; ceux qui ajoutent des features sans vérifier le leakage produisent des illusions démasquées en production. Cette rigueur (gains mesurés + anti-leakage temporel) est exactement ce qui est valorisé sur un projet ML réel.

## 🎤 Question d'entretien
**« Sur un projet réel, où cherches-tu les gains, et quel est le danger principal ? »** → Sur du tabulaire, les gains décisifs viennent surtout du FEATURE ENGINEERING, plus que du choix ou du réglage du modèle : des features dérivées justifiées par le métier (baisse d'usage récente, rythme de contact au support) et orientées par l'analyse d'erreurs (quelles sous-populations le modèle rate). Chaque feature est une hypothèse que je mesure sur la validation croisée et que je journalise (gardée si gain, jetée sinon). Le danger principal est le LEAKAGE par les features : sur un projet churn, une feature comme « jours depuis la résiliation » encode la cible et donne un modèle « parfait » mais inutilisable. Je vérifie donc à chaque ajout que la feature est calculable avec l'information disponible À LA DATE D'OBSERVATION (sans inclure de donnée postérieure) et calculée sur le train seul via le Pipeline.
