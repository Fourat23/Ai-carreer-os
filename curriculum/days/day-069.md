# Jour 69 — Consolidation mois 3 : refactor complet d'une API

## 🎯 Objectif du jour
Consolider en refactorant une API vers une structure propre, testée, documentée.

## 📖 Cours approfondi
**Concepts abordés :** Refactoring guidé · Séparation des couches · Tests comme filet · Dette technique.

Refactorer = améliorer la STRUCTURE sans changer le COMPORTEMENT. La garantie que le comportement n'a pas changé, ce sont les tests : d'abord verrouiller par des tests ce qui marche, ensuite seulement restructurer, en relançant les tests à chaque étape. Refactorer sans filet, c'est casser en croyant améliorer.

La méthode : par PETITES étapes (extraire une fonction, déplacer un module, renommer) — jamais de « grande réécriture » qui te laisse trois jours avec un système cassé. Chaque étape laisse le système fonctionnel et committable.

La dette technique se documente : ce qui reste imparfait, pourquoi c'est accepté, et le signal qui obligera à payer la dette. Une dette CONSCIENTE est une décision de gestion ; une dette ignorée est une bombe.

## ✍️ Pratique autonome
> **D'abord sans IA.** Tente seul au moins 30 minutes. Ne copie-colle jamais une réponse d'IA : lis, ferme, réécris de mémoire.

### Exercice principal
Prends ton API la plus faible (citations ou LivreAPI) et refactore-la : couches nettes, erreurs centralisées, tests, config par env. Documente la dette avant/après.

## 📦 Livrable attendu
API refactorée + notes sur la dette technique adressée.

## ✅ Critères de validation
- [ ] Le refactor est couvert par des tests écrits AVANT (et toujours verts après)
- [ ] Historique : plusieurs petites étapes commitées, jamais un big-bang
- [ ] La dette restante est documentée (quoi, pourquoi accepté, signal de paiement)

## ⚠️ Erreurs fréquentes
- Refactorer sans tests (on casse en croyant améliorer).
- Tout refaire au lieu d'améliorer par petites étapes.

## 🤖 Consigne d'utilisation de l'IA
Le refactoring est un raisonnement de conception — seul, avec tes tests comme filet.

## 🎤 Question d'entretien
**« Comment testes-tu ce code, et comment sais-tu qu'un test est utile ? »** → Arrange/Act/Assert sur la logique pure ; un test doit pouvoir ÉCHOUER (on sabote pour le prouver) ; isoler l'extérieur par des mocks ; tester les cas limites et d'erreur, pas seulement le chemin heureux.

## 🚀 Pourquoi ça comptera plus tard
- **En architecture** : tests, gestion d'erreurs et refactoring sont ce qui rend une architecture VIVABLE — sans eux, tout design s'effondre à la première évolution.
- **En IA** : tester un composant qui appelle un LLM (mock, replay, éval — mois 11) est une extension directe des tests d'aujourd'hui.
- **En entretien** : la qualité de ton code sous pression (nommage, découpage, cas limites) est évaluée dans CHAQUE exercice, même quand on ne le dit pas.
