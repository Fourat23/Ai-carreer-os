# Jour 108 — Mocks et tests d'intégration

[← Dashboard](../../) · [Semaine 16](../week-16.md) · [Mois 4](../month-04.md) · [Correction](../solutions/day-108-solution.md)

## 🎯 Objectif du jour
Isoler les dépendances externes.

## 📖 Cours approfondi
**Modèle mental : un MOCK remplace une dépendance que tu ne contrôles pas (l'API, l'horloge, le hasard) pour rendre ton test ISOLÉ et DÉTERMINISTE ; un test d'INTÉGRATION vérifie que plusieurs pièces marchent ENSEMBLE. La règle : mock ce que tu ne possèdes pas, teste en vrai ce que tu possèdes.** Un test unitaire doit être déterministe (jour 106) — or un vrai appel réseau ne l'est pas (lent, faillible, dépend d'un serveur). Le mock résout cela : tu remplaces `fetch` par une fonction qui renvoie une réponse contrôlée, et ton test vérifie comment TON code réagit à cette réponse — sans jamais toucher le réseau.

Ce qu'un mock permet de tester proprement :
1. **Le cas de succès** : l'API renvoie des données → l'UI les affiche.
2. **Le cas d'erreur** : l'API renvoie un 500 → l'UI montre l'erreur. Ce cas est presque IMPOSSIBLE à tester avec une vraie API (comment forcer un 500 à la demande ?) mais TRIVIAL avec un mock. C'est un des grands intérêts du mock : provoquer les cas rares.
3. **Le cas limite** : réponse vide, réseau lent, timeout — tous simulables.

Le test d'INTÉGRATION monte d'un cran : au lieu de tester une unité isolée, il vérifie un FLUX complet — par exemple « l'utilisateur remplit le formulaire → l'appel API (mocké) part avec les bonnes données → l'UI affiche la confirmation ». Il teste la COLLABORATION entre le formulaire, la couche api et l'affichage. On mocke toujours la frontière externe (le réseau), mais on laisse collaborer TOUT ton code interne — c'est là que se cachent les bugs d'assemblage qu'un test unitaire ne voit pas.

Le piège du mock : **trop mocker rend le test inutile**. Si tu mockes ton propre code (la fonction que tu veux justement tester), tu ne testes plus rien — tu vérifies que ton mock renvoie ce que tu lui as dit de renvoyer. La ligne est nette : mocke la FRONTIÈRE EXTERNE (réseau, temps, aléatoire), jamais la logique interne que le test est censé couvrir.

La règle du jour : **mocke la frontière, teste l'intégration de ton code ; les cas d'erreur rares deviennent testables, et les bugs d'assemblage remontent**.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : mocker les appels API et écrire un test d'intégration d'un flux complet.

**Exemple simple** : mocker la couche api pour un cas d'erreur impossible à provoquer autrement — `vi.mock('./api'); vi.mocked(api.getLivres).mockRejectedValue(new ApiError(500, 'boom'));`. Ton test vérifie alors que l'UI affiche l'erreur.

**Raisonnement pas-à-pas** : mocker la frontière réseau (api) → tester le succès, l'erreur et le vide → puis un test d'intégration du flux formulaire → api mockée → UI.

**Solution** :
```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { api } from './api';
vi.mock('./api');                                          // on mocke la FRONTIÈRE externe

test('affiche l\'erreur quand l\'API échoue', async () => {
  vi.mocked(api.getLivres).mockRejectedValue(new Error('500')); // cas rare, trivial à simuler
  render(<Catalogue />);
  expect(await screen.findByText(/erreur/i)).toBeVisible();
});

test('intégration : créer un livre affiche la confirmation', async () => {
  vi.mocked(api.creerLivre).mockResolvedValue({ id: 1, titre: 'React', auteur: 'Dan' });
  render(<AjoutLivre />);
  await userEvent.type(screen.getByLabelText(/titre/i), 'React');
  await userEvent.type(screen.getByLabelText(/auteur/i), 'Dan');
  await userEvent.click(screen.getByRole('button', { name: /ajouter/i }));
  expect(api.creerLivre).toHaveBeenCalledWith({ titre: 'React', auteur: 'Dan' }); // bonnes données
  expect(await screen.findByText(/ajouté/i)).toBeVisible();                        // UI mise à jour
});
```

**Mini-quiz** : (a) Que faut-il mocker, et que faut-il laisser réel ? (b) Pourquoi un mock rend-il testable un cas d'erreur 500 ? (c) Que se passe-t-il si on mocke le code qu'on veut tester ?
→ (a) mocker la frontière externe (réseau, temps) ; laisser réel ton code interne ; (b) on force la réponse voulue sans dépendre d'un vrai serveur ; (c) on ne teste plus rien — juste que le mock renvoie ce qu'on lui a dit.

**Variante** : ajoute un test du cas « réponse vide » (`mockResolvedValue([])`) et vérifie l'état vide de l'UI — un flux souvent oublié qui casse en production.

## ⚠️ Erreurs fréquentes
- Sur-mocker jusqu'à mocker le code testé : le test ne vérifie plus que la config des mocks.
- Faire de vrais appels réseau dans les tests : lents, non déterministes, cas d'erreur intestables.
- Ne tester que le succès : les cas 500/timeout/vide, pourtant faciles à mocker, cassent en production.
- Oublier de vérifier les DONNÉES envoyées à l'api (toHaveBeenCalledWith) : on rate les bugs de format d'assemblage.

## 🏢 Cas métier
Les mocks et tests d'intégration sont ce qui rend une suite de tests à la fois rapide, fiable et utile en entreprise : mocker le réseau permet de tester les cas d'erreur (500, timeout, réponse vide) qu'on ne peut pas provoquer avec un vrai serveur, et les tests d'intégration attrapent les bugs d'ASSEMBLAGE (le formulaire envoie le mauvais format à l'api) que les tests unitaires ratent. L'anti-pattern coûteux, courant chez les débutants, est le sur-mock : mocker tellement de choses que le test ne vérifie plus que la configuration des mocks. Les équipes matures mockent uniquement la frontière externe. Savoir où placer cette frontière est un jugement de test directement valorisé.

## 🎤 Question d'entretien
**« Quand et quoi mockes-tu dans tes tests ? »** → Je mocke ce que je ne CONTRÔLE pas et qui rend le test non déterministe : le réseau (l'API), l'horloge, l'aléatoire. Ça me permet de tester proprement les cas de succès, mais surtout les cas d'ERREUR rares (un 500, un timeout, une réponse vide) que je ne peux pas provoquer avec un vrai serveur. En revanche, je ne mocke JAMAIS le code que le test est censé couvrir — sinon je ne teste plus rien. Un test d'INTÉGRATION monte d'un cran : il mocke la frontière réseau mais laisse collaborer tout mon code interne (formulaire → api → UI), ce qui attrape les bugs d'assemblage qu'un test unitaire ne voit pas. La règle : mock la frontière externe, teste en vrai ce que tu possèdes.
