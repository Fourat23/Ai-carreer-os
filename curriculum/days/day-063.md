### Test pratique
75 min : remplace le stockage mémoire de ton API citations par SQLite — schéma, script d'initialisation, requêtes PARAMÉTRÉES partout. Puis, sur une base fournie (livres/auteurs/emprunts) : dix requêtes — SELECT filtrés, JOIN sur deux puis trois tables, GROUP BY + COUNT, tri, LIMIT, une sous-requête. Termine en tentant une injection SQL sur ta propre API et montre pourquoi elle échoue.

### Test théorique
Clé primaire vs clé étrangère ; 1NF/2NF/3NF en une phrase chacune ; ce que fait un index et ce qu'il coûte à l'écriture ; différence WHERE/HAVING ; ACID, les quatre lettres avec un exemple chacune ; pourquoi une requête paramétrée empêche l'injection alors qu'un échappement manuel ne suffit pas ; quand dénormaliser, et ce qu'on accepte de perdre en le faisant.

### Synthèse de la semaine
La semaine 9 a fait passer d'une API en mémoire à une vraie application backend sur base de données. Le branchement SQLite (jour 57) : les requêtes PARAMÉTRÉES qui séparent code et données — LA défense contre l'injection — et la couche data isolée (l'interface Store appliquée à une vraie base). La modélisation (jour 58) : normaliser pour une source de vérité, indexer les colonnes filtrées/jointes souvent (compromis lecture/écriture), et les transactions ACID pour l'atomicité. Postman avancé (jour 59) : une collection = doc vivante + suite de tests + démo, qui vérifie statut ET forme. Le cadrage du Projet 2 (jour 60) : données d'abord (table de liaison pour les emprunts), contrat d'API avant le code. Puis la construction du socle de LivreAPI : schéma reconstructible → couche data paramétrée → routes, statuts choisis à la conception (jour 61) ; et la logique métier — règle dans le service, emprunt transactionnel, 409 sur conflit, JOIN pour les données liées (jour 62). Le fil rouge : **une vraie API backend se construit de bas en haut sur un modèle solide — sécurité (paramétrage), intégrité (normalisation, transactions), et logique métier au bon endroit (service).** LivreAPI a un socle crédible ; les semaines suivantes le durciront (recherche, tests, sécurité, doc).

### Plan de remédiation (si un critère échoue)
- **SQL concaténé / injection possible** : rejoue le jour 57 — zéro concaténation, requêtes paramétrées partout, couche data isolée ; prouve l'échec de l'injection.
- **Redondance / index injustifiés / pas de transaction** : jour 58 — normalise (une source de vérité), justifie chaque index, enveloppe les opérations liées dans une transaction.
- **Postman superficiel** : jour 59 — teste la FORME du corps, pas juste le statut ; variables d'environnement ; scénario enchaîné.
- **Modèle bancal / contrat après le code** : jour 60 — données d'abord (table de liaison pour les emprunts), contrat d'API avant l'implémentation.
- **Socle désordonné / statuts flous** : jour 61 — schéma reconstructible → data paramétrée → routes, statuts choisis à la conception (201/200/204/400/404).
- **Logique dans la route / pas d'atomicité / mauvais statut** : jour 62 — règle dans le service, emprunt transactionnel (rollback), 409 sur conflit.
