## 🎯 Objectif du jour

## 📖 Cours approfondi
**Modèle mental : le README est la VITRINE de ton projet final — un recruteur y passe 30 à 90 secondes et décide s'il creuse ; il doit comprendre le problème, voir une démo, lire les chiffres, et pouvoir lancer en 5 minutes.** Tu as fini de construire DocSense (v1.0 gelé) ; maintenant tu le rends VENDABLE. Le README exemplaire est le document le plus rentable de ton portfolio : il transforme un dépôt de code en une pièce qui capte l'attention et donne envie de creuser.

Les composants d'un README qui vend :
1. **Le problème (en 2 phrases, en premier)** : pas « DocSense utilise Chroma et FTS5 » (la stack) mais « trouver l'information exacte dans un gros corpus est lent et les assistants inventent ; DocSense répond en citant ses sources et refuse quand il ne sait pas ». Le POURQUOI avant le COMMENT — un recruteur doit comprendre la valeur en 10 secondes.
2. **Une démo visuelle (GIF)** : une image vaut mille lignes — un GIF de DocSense en action (question → réponse citée → refus honnête) montre instantanément que ça marche. C'est ce qui capte dans les premières secondes.
3. **Les chiffres d'évaluation** : le rapport qualité (jour 334) résumé — « exactitude 0,92 sur 40 questions, sécurité 15/15, réponses citées vérifiables ». Les chiffres prouvent la qualité et te distinguent des projets sans évaluation.
4. **L'installation en 5 minutes** : grâce au Docker (jour 320), « git clone + docker compose up » — un recruteur peut le faire tourner. Une installation simple prouve la livrabilité.
5. **Les limites honnêtes** : ce que DocSense ne fait pas (le hors-scope, jour 302). L'honnêteté sur les limites CRÉDIBILISE le reste — un README sans limites est suspect.

Pourquoi le README est le document le plus rentable : c'est l'INTERFACE entre ton travail et le marché. Un excellent projet avec un README illisible est invisible ; un bon projet avec un README exemplaire capte l'attention. Le recruteur ne lit pas ton code en premier — il lit ton README, et décide en 90 secondes. Un README qui commence par le problème, montre une démo, prouve par les chiffres et se lance en 5 minutes est ce qui te fait passer le premier filtre. C'est aussi la synthèse de tout ton projet en une page — savoir présenter DocSense de façon lisible et convaincante est une compétence de communication technique aussi importante que le code lui-même.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : le README exemplaire de DocSense — problème, démo GIF, archi, chiffres, install 5 min, limites.

**Exemple simple** : la première ligne teste tout — si elle dit la STACK (« app RAG avec Chroma »), c'est raté ; si elle dit le PROBLÈME et la valeur (« réponses sourcées sur vos documents, refus honnête quand l'info manque »), c'est gagné.

**Raisonnement pas-à-pas** : écrire pour un recruteur pressé — problème d'abord, preuve visuelle, chiffres, install, limites — puis tester avec un regard neuf.

**Structure du README** :
```markdown
# DocSense
> [1 phrase : le problème + la valeur]
[GIF de démo : question → réponse citée → refus honnête]
## Le problème (2 phrases)
## Ce que fait DocSense (les fonctionnalités clés, orientées valeur)
## Résultats (chiffres du rapport qualité j.334) : exactitude 0,92, sécurité 15/15...
## Installation (5 min) : git clone + docker compose up (j.320)
## Architecture (schéma + lien vers les ADR)
## Limites honnêtes (le hors-scope, j.302)
```

**Mini-quiz** : (a) Par quoi commence un README qui vend ? (b) Pourquoi un GIF de démo ? (c) Pourquoi les limites honnêtes crédibilisent-elles ?
→ (a) le problème et la valeur (le pourquoi), pas la stack ; (b) une image montre instantanément que ça marche, capte dans les premières secondes ; (c) un README sans limites est suspect ; l'honnêteté sur ce qui ne marche pas donne confiance dans le reste.

**Variante** : fais lire ton README à quelqu'un qui ne connaît pas DocSense et chronomètre — comprend-il le problème, la valeur et comment lancer en 90 secondes ? Ses questions sont tes trous à combler.
