## 🎯 Objectif du jour
Approfondir Linux : scripts shell, permissions, variables d'environnement, processus — le socle du DevOps à venir.

## 📖 Cours approfondi
**Concepts abordés :** Scripts bash · chmod/permissions · Variables d'environnement · Processus (ps, kill) · Pipes avancés.

Un script shell encode un savoir-faire répétable : la séquence de commandes que tu tapes à la main devient un outil fiable. Les fondamentaux : `set -e` (le script s'arrête à la première erreur au lieu de continuer aveuglément), les codes de sortie vérifiés, les messages d'étape clairs.

Les PERMISSIONS Unix (lecture/écriture/exécution × propriétaire/groupe/autres) : `chmod +x script.sh` rend exécutable. Les VARIABLES D'ENVIRONNEMENT sont l'interface de configuration universelle : un script qui lit $DB_PATH tourne partout sans modification — c'est exactement le contrat que la CI et Docker (mois 11) attendent.

Les PROCESSUS : ps liste, kill termine proprement (SIGTERM) ou brutalement (SIGKILL), & lance en arrière-plan. Comprendre « mon serveur est un processus qui écoute un port » démystifie la moitié des problèmes de déploiement.

**Modèle mental : un script shell ENCODE un savoir-faire répétable — la séquence de commandes que tu tapes à la main devient un OUTIL fiable, versionnable, partageable. Les fondamentaux qui le rendent robuste : `set -e` (le script s'arrête à la première erreur au lieu de continuer aveuglément), les codes de sortie vérifiés, et la CONFIGURATION lue depuis l'ENVIRONNEMENT (jamais en dur). Un script qui lit `$DB_PATH` tourne partout sans modification — c'est exactement le contrat que la CI et Docker exigeront (mois 11).** Automatiser le lancement d'un projet, c'est poser le germe du DevOps.

Pourquoi automatiser avec un script. Refaire à la main une séquence (installer, initialiser la base, démarrer) est lent, source d'oublis, et non reproductible — chacun le fait « à sa façon ». Un script CAPTURE cette séquence une fois pour toutes : il devient la source de vérité du « comment lancer ce projet », exécutable par n'importe qui (y compris une machine de CI) de façon identique. C'est le premier pas vers l'automatisation qui structure tout le DevOps.

Les fondamentaux d'un script robuste, depuis les fondations. **`set -e`** : sans lui, un script continue après une erreur (installer échoue, mais on démarre quand même sur un état cassé) ; avec lui, il s'arrête net à la première commande qui échoue. **Les codes de sortie** : chaque commande renvoie 0 (succès) ou non-zéro (échec) ; les vérifier permet de réagir. **Les messages d'étape clairs** (`echo`) : un script muet est indébogable ; un script qui annonce chaque étape et son statut est traçable.

Les permissions Unix, depuis les fondations. Le modèle : trois droits (lecture r, écriture w, exécution x) × trois catégories (propriétaire, groupe, autres). `chmod +x script.sh` ajoute le droit d'exécution — sans lui, le script ne se lance pas. Comprendre les permissions, c'est comprendre pourquoi « permission denied » arrive et comment y remédier proprement (sans tout mettre en 777, qui est un anti-pattern de sécurité).

Les variables d'environnement, l'interface de config universelle. Un script qui lit sa configuration depuis l'environnement (`$DB_PATH`, `$PORT`, `$API_TOKEN`) tourne PARTOUT sans modification : en local, en CI, en conteneur Docker. C'est le même contrat que les secrets du jour 68, généralisé : le code/script lit l'environnement, l'environnement fournit les valeurs selon le contexte. Coder les valeurs en dur enchaîne le script à une seule machine.

Les processus, depuis les fondations. Un programme qui tourne est un PROCESSUS ; `ps` les liste, `kill` en arrête un (par son identifiant). Comprendre les processus, c'est savoir qu'un serveur « déjà lancé » occupe un port, comment le retrouver et l'arrêter — des gestes quotidiens du développement et de l'exploitation.

Limites et compromis. Un script shell est parfait pour l'automatisation locale et la CI simple, mais devient vite illisible pour de la logique complexe (là on passe à un vrai langage). `set -e` a des subtilités (certaines constructions l'ignorent) — d'où l'intérêt de vérifier explicitement les étapes critiques. Et un script non idempotent (qui casse s'il est relancé) est un piège : viser la ré-exécutabilité.

La règle du jour : **un script encode un savoir-faire répétable et versionnable. Rends-le robuste (`set -e`, codes de sortie vérifiés, messages clairs), lis la CONFIGURATION depuis l'environnement (jamais en dur, pour tourner partout), et maîtrise permissions (`chmod +x`) et processus (`ps`/`kill`). C'est le germe de la CI et de Docker (mois 11).**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire un `setup.sh` robuste qui lance un projet de zéro (install → init base → démarrage), avec `set -e`, config par environnement et messages clairs.

**Exemple simple** : sans `set -e` vs avec. Sans lui, si `npm install` échoue, le script continue et tente de démarrer sur des dépendances manquantes → erreur obscure plus loin. Avec `set -e`, il s'arrête NET à l'install ratée, avec un message clair — le problème est localisé.

**Raisonnement pas-à-pas** : (1) `set -e` en tête (arrêt à la première erreur) ; (2) lire la config depuis l'environnement avec valeurs par défaut ; (3) chaque étape annoncée par un `echo` ; (4) rendre le script exécutable (`chmod +x`).

**Implémentation (setup.sh)** :
```bash
#!/usr/bin/env bash
set -euo pipefail                 # -e : stop à la 1re erreur ; -u : variable non définie = erreur

DB_PATH="${DB_PATH:-./livres.db}"   # CONFIG depuis l'environnement, défaut si absent
PORT="${PORT:-3000}"

echo "[1/3] Installation des dépendances..."
npm install

echo "[2/3] Initialisation de la base ($DB_PATH)..."
sqlite3 "$DB_PATH" < init.sql       # reconstruit la base (jour 61)

echo "[3/3] Démarrage sur le port $PORT..."
PORT="$PORT" npm start
```
```bash
chmod +x setup.sh          # sans le droit x, "permission denied"
DB_PATH=/tmp/test.db PORT=4000 ./setup.sh   # config injectée par l'environnement
```
Le script encode le lancement complet, `set -e` arrête à la première erreur (une dépendance manquante → message clair, pas un démarrage sur état cassé), et la config vient de l'environnement — ce même script tournerait en CI sans modification.

## ⚠️ Erreurs fréquentes
- Secrets ou chemins en dur dans le script : il ne tourne que sur une machine et fuit potentiellement des secrets.
- Pas de set -e : le script continue après une erreur, sur un état cassé, jusqu'à une erreur obscure plus loin.
- chmod 777 pour « régler » un permission denied : ouvre tous les droits à tous (faille) — utiliser chmod +x.
- Script non idempotent qui casse s'il est relancé : viser la ré-exécutabilité.

## 🏢 Cas métier
L'automatisation par scripts est le socle du DevOps et une compétence transférable très valorisée. En entreprise, tout ce qui est fait à la main plus d'une fois finit scripté : le setup d'un projet, le déploiement, les sauvegardes, les tâches de maintenance. Un script robuste (avec `set -e`, config par environnement, messages clairs) est fiable et reproductible, là où une procédure manuelle est lente et source d'erreurs. La configuration par variables d'environnement est le contrat universel de la CI et des conteneurs (Docker, Kubernetes) : le même artefact tourne en dev, staging et prod, seule l'environnement change (twelve-factor app). Comprendre les permissions Unix évite les erreurs de déploiement (« permission denied ») et les failles (`chmod 777` qui ouvre tout). Comprendre les processus est quotidien (un port déjà occupé, un serveur à arrêter). Ces compétences Linux/shell sont un prérequis du DevOps du mois 11 (CI/CD, Docker) et une base attendue de tout développeur back — un script de setup propre dans un dépôt est aussi un signal de rigueur pour un recruteur.

## 🎤 Question d'entretien
**« Comment écris-tu un script d'automatisation robuste, et pourquoi lire la config depuis l'environnement ? »** → Un script encode un savoir-faire répétable, donc je le rends fiable. Je mets `set -e` en tête pour qu'il s'arrête à la PREMIÈRE erreur au lieu de continuer aveuglément sur un état cassé — sans ça, une install ratée mènerait à un démarrage qui échoue plus loin avec une erreur obscure. J'ajoute `-u` (variable non définie = erreur) et `pipefail`, je vérifie les codes de sortie des étapes critiques, et j'annonce chaque étape par un message clair pour que le script soit traçable. Surtout, je lis la CONFIGURATION depuis l'environnement (`$DB_PATH`, `$PORT`) avec des valeurs par défaut, jamais en dur : ainsi le MÊME script tourne en local, en CI et dans un conteneur Docker — seule l'environnement change. C'est le contrat de la « twelve-factor app » et exactement ce que la CI exige. Je rends le script exécutable avec `chmod +x` (le droit x du modèle de permissions Unix). **Relance possible** : « ce script pourrait-il tourner en CI sans modification ? » → oui, si toute sa config vient de l'environnement et qu'il est idempotent (ré-exécutable sans casser) : c'est justement le critère qui distingue un script d'automatisation d'une suite de commandes tapées à la main.
