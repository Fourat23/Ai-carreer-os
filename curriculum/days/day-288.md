## 🎯 Objectif du jour
Séparer le cœur des détails.

## 📖 Cours approfondi
**Modèle mental : la clean architecture sépare ce qui NE CHANGE PAS (les règles métier, le cœur) de ce qui change souvent (les détails techniques — UI, base de données, APIs) — pour que les détails puissent changer SANS toucher au cœur.** Après un mois d'agents et de workflows, tu prends de la hauteur : comment STRUCTURER une application IA pour qu'elle dure et évolue ? La clean architecture répond par une règle de DÉPENDANCE : le cœur (la logique métier) ne dépend de RIEN ; les détails dépendent du cœur, jamais l'inverse. Ton pipeline RAG ne doit pas « savoir » qu'il utilise Chroma ou OpenAI — ce sont des détails interchangeables.

Le principe fondamental — l'inversion de dépendance :
1. **Le cœur (domaine)** : les règles métier de DocQA — qu'est-ce qu'une question, un chunk, une réponse citée, une évaluation. Du code pur, sans import de framework, sans SQL, sans appel HTTP. C'est ce qui a de la VALEUR et qui change lentement (ta logique de RAG, tes règles de refus).
2. **Les détails (infrastructure)** : Chroma, l'API LLM, le système de fichiers, l'UI. Ils changent souvent (nouveau vector store, nouveau modèle) et ne devraient JAMAIS contaminer le cœur.
3. **La règle de dépendance** : les flèches de dépendance pointent vers le cœur. Le cœur définit des INTERFACES (« j'ai besoin d'un moyen de stocker des vecteurs ») ; l'infrastructure les IMPLÉMENTE (« voici l'adaptateur Chroma »). Changer de vector store = écrire un nouvel adaptateur, sans toucher au cœur.

Pourquoi ça compte pour une app IA en particulier : le monde des LLM change VITE (modèles, vector stores, frameworks se remplacent tous les mois). Une architecture où le modèle ou le vector store est enchevêtré dans toute la codebase rend chaque changement douloureux et risqué. Une architecture propre où ils sont des détails derrière des interfaces rend l'évolution triviale — tu remplaces un adaptateur, tes tests du cœur passent toujours. C'est la différence entre une app IA qui survit 3 ans et une qu'il faut réécrire à chaque évolution de l'écosystème.

L'exercice du jour est une CARTOGRAPHIE : dans DocQA, identifier ce qui est cœur (règles métier RAG, logique d'évaluation, politique de refus) et ce qui est détail (Chroma, l'API LLM, l'UI, le stockage). Cette distinction est le préalable au refactoring hexagonal de demain (jour 289).

## 🏢 Cas métier
Le monde des LLM évolue à une vitesse folle : le modèle « meilleur » change tous les mois, les vector stores se multiplient, les frameworks apparaissent et disparaissent. Les apps IA dont le cœur métier est enchevêtré avec un SDK spécifique doivent être partiellement réécrites à chaque évolution — un coût récurrent énorme. Celles construites en clean architecture remplacent un adaptateur en une journée, cœur et tests intacts. « Notre logique métier ne connaît pas notre vector store — on a migré de Chroma à pgvector en changeant un fichier » est un retour d'expérience qui prouve une maturité d'architecture directement valorisée, surtout dans un domaine aussi mouvant que l'IA.

## 🎤 Question d'entretien
**« Comment structures-tu une application IA pour qu'elle résiste aux changements d'écosystème ? »** → Clean architecture : je sépare le cœur (règles métier — logique RAG, refus, évaluation, modèle du domaine — du code pur sans framework) des détails (vector store, API LLM, UI — qui changent souvent). La règle de dépendance : le cœur définit des interfaces, les détails les implémentent ; les dépendances pointent vers le cœur, jamais l'inverse. Changer de vector store = un nouvel adaptateur, cœur et tests intacts. C'est crucial en IA car l'écosystème (modèles, stores) change tous les mois — l'app propre évolue en remplaçant un adaptateur, l'app enchevêtrée se réécrit.
