## 🎯 Objectif du jour
Comprendre et appliquer les architectures 3-tiers et MVC, socle de toute application web.

## 📖 Cours approfondi
**Concepts abordés :** 3-tiers (présentation/logique/données) · MVC · Séparation des responsabilités · Où va quoi · Frontières.

Le 3-TIERS découpe toute application en trois couches : PRÉSENTATION (l'UI — afficher et saisir), LOGIQUE (les règles métier — décider), DONNÉES (persister). La règle : chaque couche ne parle qu'à sa voisine, et la logique ne sait ni COMMENT elle est affichée ni OÙ elle est stockée.

MVC organise la présentation : le Modèle (les données et leur logique), la Vue (le rendu), le Contrôleur (reçoit les actions, orchestre). Tu l'as pratiqué sans le nommer : tes routes Express sont des contrôleurs, tes services le modèle.

Pourquoi ces découpages comptent : chaque couche évolue, se teste et se remplace INDÉPENDAMMENT. Changer l'UI ne touche pas les règles ; migrer la base ne touche pas l'UI. Toute architecture plus avancée (hexagonale, mois 10) est un raffinement de cette idée : isoler ce qui change pour des raisons différentes.

**Modèle mental : le 3-TIERS découpe TOUTE application en trois couches — PRÉSENTATION (l'UI : afficher et saisir), LOGIQUE (les règles métier : décider), DONNÉES (persister) — avec une règle stricte : chaque couche ne parle qu'à sa VOISINE, et la logique ne sait NI comment elle est affichée NI où elle est stockée. MVC organise la couche présentation : le Modèle (données + leur logique), la Vue (le rendu), le Contrôleur (reçoit les actions, orchestre). Tu l'appliques sans le nommer depuis le mois 3 : tes routes Express sont des contrôleurs, tes services le modèle.** Structurer une application, c'est décider OÙ VA QUOI, et tracer des FRONTIÈRES nettes.

Pourquoi séparer en couches. Une application mélange trois préoccupations très différentes : montrer/saisir (présentation), décider (logique métier), retenir (données). Les MÉLANGER (logique métier dans l'UI, SQL dans une route) rend le tout rigide : impossible de changer l'affichage sans risquer la logique, impossible de tester le métier sans lancer l'UI, impossible de changer de base sans réécrire les règles. Séparer en COUCHES permet à chacune d'ÉVOLUER, de se TESTER et de se REMPLACER indépendamment. C'est la structure fondamentale de toute application web.

Le 3-tiers, depuis les fondations. **PRÉSENTATION** : ce qui affiche et reçoit les saisies (un front React, ou les routes d'une API qui parlent HTTP). **LOGIQUE** : les règles métier — décider (« emprunter est-il permis ? »). **DONNÉES** : la persistance (SQL, fichiers). La règle d'or : chaque couche ne parle qu'à sa VOISINE (présentation → logique → données), et la logique est INDÉPENDANTE de la présentation (elle ne sait pas si c'est du web ou du CLI) et de la persistance (elle ne sait pas si c'est SQLite ou Postgres). Cette indépendance est ce qui rend les couches interchangeables (l'inversion de dépendance, jour 44).

MVC, depuis les fondations. MVC organise la PRÉSENTATION (et parfois plus). Le **Modèle** : les données et leur logique. La **Vue** : le rendu (ce que voit l'utilisateur). Le **Contrôleur** : reçoit les actions de l'utilisateur, orchestre le modèle et choisit la vue. Tu l'as pratiqué sans le nommer : dans ton API Express, les ROUTES sont des contrôleurs (reçoivent la requête, orchestrent), les SERVICES sont le modèle (la logique), et la réponse JSON est la vue. MVC et 3-tiers ne s'opposent pas : MVC structure souvent la couche présentation d'une architecture 3-tiers.

La différence « où va quoi », depuis les fondations. La compétence pratique est de savoir PLACER chaque chose : une nouvelle RÈGLE MÉTIER va dans la logique (le service), pas dans la route ni la base ; une nouvelle VUE va dans la présentation ; un changement de stockage va dans la couche données, sans toucher le reste. Une frontière FLOUE (tout communique avec tout) détruit le bénéfice ; une frontière NETTE localise chaque type de changement.

Limites et compromis. Le découpage en couches ajoute de la structure (plus de fichiers, indirection) justifiée dès qu'une application dépasse le script jetable — pour un tout petit outil, c'est excessif. Les couches ne doivent pas devenir des silos qui se recopient les données (over-engineering). Et il existe d'autres découpages (par fonctionnalité, hexagonal) : le 3-tiers/MVC est un socle éprouvé, pas la seule voie.

La règle du jour : **structure toute application en couches — présentation (afficher/saisir), logique (décider), données (persister) — où chaque couche ne parle qu'à sa voisine et la logique est indépendante de l'affichage et du stockage. MVC organise la présentation (tes routes = contrôleurs, tes services = modèle). Sache OÙ VA QUOI : règle métier → logique, vue → présentation, stockage → données.**

**Ce 3-tiers DÉPLOYÉ dans le cloud (fondation V22).** Les trois couches deviennent trois familles de ressources : la PRÉSENTATION derrière un point d'entrée public (un `load-balancer` en façade), la LOGIQUE dans du compute privé (machines virtuelles, conteneurs ou fonctions), les DONNÉES dans un service de stockage/base managé, en réseau privé. La règle « chaque couche ne parle qu'à sa voisine » devient une règle RÉSEAU : seul le load balancer est exposé, l'API vit dans un `subnet` privé, et la base n'est JAMAIS accessible publiquement — on n'y accède que depuis l'API. Une base exposée sur Internet est l'anti-pattern cloud le plus grave.

**Modèles de service et responsabilité partagée.** On loue le cloud à des niveaux différents : IaaS (on gère l'OS et au-dessus — machines virtuelles), PaaS (on ne gère que l'application — la plateforme s'occupe de l'OS et du runtime), SaaS (on consomme un logiciel fini), FaaS/serverless (on ne fournit que des fonctions, la plateforme gère l'exécution et la mise à l'échelle). Plus on monte (IaaS → SaaS), plus le fournisseur prend en charge — c'est la **responsabilité partagée** : le fournisseur sécurise l'infrastructure, mais TA configuration (accès public, secrets, permissions) reste TA responsabilité. Un bucket de stockage ouvert au monde n'est pas une faille du fournisseur, c'est une erreur de config.

**Région et zone de disponibilité.** Une **région** est une zone géographique (proximité des utilisateurs, contraintes légales de résidence des données) ; une **zone de disponibilité** est un datacenter isolé à l'intérieur d'une région. Répartir les instances sur plusieurs zones protège d'une panne locale sans changer de région. On y revient en haute disponibilité (jour 79).

**Cartographie déterministe (Cloud Topology Lab).** Le laboratoire local permet d'ANALYSER une telle topologie : il repère une base exposée, un flux public sans TLS, une couche mal séparée — sans provisionner quoi que ce soit. C'est un simulateur pédagogique, pas une console cloud : aucun appel réel, aucun coût, aucune isolation OS prétendue.

---

**Du concept au fournisseur : lire une architecture cloud (fondation V25).** Les couches (présentation/logique/données) restent vraies dans le cloud ; ce qui change, c'est QUI opère quoi. Le **modèle de responsabilité partagée** trace la frontière : le fournisseur gère le socle (matériel, hyperviseur, réseau physique, services managés), toi la configuration, les identités, les données. Plus tu montes en managé (IaaS → PaaS → SaaS), plus tu délègues — mais tu restes TOUJOURS responsable de tes accès et de tes données.

**Identité d'abord (IAM).** Avant le réseau, on gouverne QUI peut agir sur QUOI. L'**IAM** applique le **moindre privilège** : une identité (utilisateur, rôle, identité managée) ne reçoit que les actions strictement nécessaires. Côté AWS : IAM (users, rôles, policies) + STS pour des credentials temporaires. Côté Azure : Microsoft Entra ID + Azure RBAC (attribution de rôle sur un scope) + managed identity pour éviter les secrets applicatifs. Modèle proche, mécanique différente — on raisonne les DIFFÉRENCES, pas une simple équivalence.

**Périmètre et réseau.** Un compte AWS (ou une subscription Azure) isole facturation et gouvernance ; côté Azure, le **resource group** regroupe des ressources au cycle de vie commun (sans équivalent direct AWS). Une **région** est une zone géographique ; une **availability zone** (AZ) est un datacenter isolé au sein d'une région — répartir sur plusieurs AZ, c'est survivre à la panne d'un datacenter. Le réseau privé se déclare : un **VPC** (AWS) ou un **VNet** (Azure) découpé en **subnets** publics (exposés) et privés (base, backend), avec CIDR disjoints et security groups/NSG comme pare-feu.

Le **Cloud Architecture Lab** te fait charger une architecture (AWS ou Azure), l'analyser (IAM, réseau, disponibilité, coût) et comparer un état problématique à un état sain — en déterministe, local, sans aucun appel fournisseur.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : cartographier une fonctionnalité selon le 3-tiers et décider où placer une nouvelle règle métier, une nouvelle vue, un changement de base.

**Exemple simple** : où va quoi. Nouvelle règle « un membre ne peut pas emprunter plus de 5 livres » → couche LOGIQUE (service), pas la route ni la base. Nouvelle vue « liste des retards » → PRÉSENTATION. Passer de SQLite à Postgres → couche DONNÉES seulement. Chaque changement a UNE couche d'accueil.

**Raisonnement pas-à-pas** : (1) j'assigne chaque fichier à sa couche ; (2) je repère les violations (logique dans la route, SQL dans la présentation) ; (3) pour chaque évolution, je détermine sa couche d'accueil ; (4) je vérifie que la logique ne dépend ni de l'affichage ni du stockage.

**Cartographie 3-tiers de LivreAPI** :
```text
PRÉSENTATION (parle HTTP)        LOGIQUE (décide)              DONNÉES (persiste)
  routes/livres.ts        -->     services/livres.ts     -->   data/livres.ts
  routes/emprunts.ts      -->     services/emprunts.ts   -->   data/emprunts.ts
  (extrait params,               (règle : disponible ?         (SQL paramétré,
   renvoie le statut)             limite d'emprunts)           SQLite)

  Règle : chaque couche ne parle qu'à sa VOISINE (flèches ->).
  La LOGIQUE ne connaît ni HTTP (présentation) ni SQL (données) :
    - le service reçoit des paramètres simples, pas req/res ;
    - le service appelle un contrat de données (jour 76), pas du SQL brut.
```
```ts
// MVC dans Express : la route est un CONTRÔLEUR, le service le MODÈLE, le JSON la VUE
app.post('/emprunts', (req, res) => {              // CONTRÔLEUR : reçoit l'action
  const emprunt = serviceEmprunts.emprunter(       // MODÈLE : décide (règle métier)
    Number(req.body.livreId), Number(req.body.membreId));
  res.status(201).json(emprunt);                   // VUE : le rendu (JSON)
});
```
Chaque changement a sa couche : une règle va dans le service (logique), une vue dans la présentation, un changement de base dans la couche données — sans que rien d'autre ne bouge. Les frontières nettes localisent l'évolution.

## ⚠️ Erreurs fréquentes
- Logique métier dans la présentation (route/vue) ou la couche données : intestable, dupliquée, couplée.
- Frontières floues (tout communique avec tout) : le bénéfice des couches disparaît.
- Faire connaître à la logique les détails de HTTP (req/res) ou du SQL : elle n'est plus indépendante ni testable seule.
- Sur-structurer un tout petit outil : les couches se justifient dès qu'on dépasse le script jetable.

## 🏢 Cas métier
L'architecture en couches (3-tiers, MVC) est le socle de la quasi-totalité des applications web d'entreprise, des frameworks (Rails, Django, Spring, Angular) aux applications maison. Sa valeur est la MODIFIABILITÉ et la TESTABILITÉ : séparer présentation, logique et données permet de changer l'interface sans toucher au métier, de tester les règles sans lancer l'UI, de migrer la base sans réécrire la logique, et de faire travailler des équipes différentes sur des couches différentes (front, back, data). À l'inverse, une application où les couches sont mélangées (logique métier dans les vues, SQL dans les contrôleurs) devient rigide et fragile — le cauchemar de maintenance classique. Savoir cartographier une application selon le 3-tiers, placer correctement chaque responsabilité et justifier les frontières est une compétence d'architecture attendue dès qu'on dépasse le rôle de junior pur. « Où mettrais-tu telle logique ? », « comment structures-tu une application ? » et « qu'est-ce que MVC ? » sont des questions d'entretien très fréquentes, et une réponse claire (couches, frontières, où va quoi) démontre une pensée structurée.

## 🎤 Question d'entretien
**« Comment structures-tu une application, et qu'est-ce que MVC ? »** → Je pense en COUCHES. Le 3-tiers découpe toute application en trois : la PRÉSENTATION (afficher et saisir — un front, ou les routes d'une API qui parlent HTTP), la LOGIQUE (les règles métier, décider), et les DONNÉES (persister). Cette indépendance est ce qui permet de changer l'UI ou la base sans réécrire le métier, et de tester les règles sans lancer l'UI. MVC organise la couche présentation : le Modèle (les données et leur logique), la Vue (le rendu), le Contrôleur (reçoit les actions, orchestre). Je l'ai pratiqué sans le nommer dans mon API Express : les routes sont des contrôleurs, les services le modèle, la réponse JSON la vue. La compétence pratique, c'est de savoir OÙ VA QUOI : une nouvelle règle métier va dans le service, une nouvelle vue dans la présentation, un changement de base dans la couche données. **Relance possible** : « et si la logique métier se retrouve dans une route ou une vue ? » → c'est le code smell classique : intestable sans lancer l'UI, dupliqué, et couplé à HTTP ou à l'affichage ; je l'extrais dans la couche logique pour rétablir des frontières nettes.
