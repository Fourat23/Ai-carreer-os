## 🎯 Objectif du jour
Penser en composants et props.

## 📖 Cours approfondi
**Modèle mental : un composant React est une FONCTION PURE qui prend des props et renvoie du JSX — l'UI est le RÉSULTAT d'un calcul, pas une suite d'ordres donnés au DOM.** C'est le renversement le plus important à intégrer. En JavaScript vanilla (ou jQuery), tu écrivais des instructions IMPÉRATIVES : « crée un élément, ajoute-le, change son texte, retire cette classe ». En React, tu écris une fonction DÉCLARATIVE : « pour ces props, voici à quoi l'UI doit ressembler » — et React se charge de faire correspondre le DOM à ta description. Tu ne touches plus le DOM à la main.

Les trois notions du jour :
1. **Le composant** : une fonction qui renvoie du JSX. Son nom commence par une MAJUSCULE (React distingue `<Carte/>`, ton composant, de `<div/>`, une balise HTML). Elle doit être PURE : mêmes props → même rendu, sans effet de bord.
2. **Les props** : les ARGUMENTS du composant, en lecture seule. Un composant ne modifie JAMAIS ses props — il les reçoit et les affiche. C'est le flux de données unidirectionnel : les données descendent du parent vers l'enfant.
3. **Le JSX** : une syntaxe qui ressemble à du HTML mais EST du JavaScript. `className` (pas `class`), `{expression}` pour injecter une valeur, un seul élément racine (ou un Fragment `<>...</>`). Le JSX est compilé en appels de fonction — ce n'est pas une chaîne de caractères.

La règle qui gouverne tout le mois : **penser en composants, c'est décomposer une interface en petites fonctions réutilisables et typées, chacune responsable d'un morceau**. Une bonne décomposition rend l'UI lisible (chaque composant tient dans la tête), réutilisable (la même Carte pour tous les produits) et testable. C'est exactement la modularité du clean code (mois 2) appliquée à l'écran.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : décomposer une carte de livre en composants typés, à partir de props.

**Exemple simple** : un composant minimal — `function Badge({ texte }: { texte: string }) { return <span className="badge">{texte}</span>; }`. Une fonction, une prop typée, du JSX. Tout le reste n'est que composition de briques comme celle-ci.

**Raisonnement pas-à-pas** : repérer les blocs répétés d'une maquette → en faire des composants → typer leurs props → les composer dans un parent.

**Solution** :
```tsx
type Livre = { id: number; titre: string; auteur: string; dispo: boolean };

function Badge({ dispo }: { dispo: boolean }) {
  return <span className={dispo ? 'ok' : 'ko'}>{dispo ? 'Dispo' : 'Emprunté'}</span>;
}

function CarteLivre({ livre }: { livre: Livre }) {   // props en lecture seule
  return (
    <article className="carte">
      <h3>{livre.titre}</h3>
      <p>{livre.auteur}</p>
      <Badge dispo={livre.dispo} />   {/* composition : un composant dans un autre */}
    </article>
  );
}

function Liste({ livres }: { livres: Livre[] }) {
  return <div>{livres.map((l) => <CarteLivre key={l.id} livre={l} />)}</div>;
}
```

**Mini-quiz** (réponds sans regarder) : (a) Pourquoi le nom d'un composant commence-t-il par une majuscule ? (b) Un composant peut-il modifier ses props ? (c) Pourquoi `className` et pas `class` ?
→ (a) pour que React le distingue d'une balise HTML native ; (b) non, les props sont en lecture seule (flux unidirectionnel) ; (c) `class` est un mot réservé de JavaScript, le JSX étant du JS.

**Variante** : ajoute une prop `onEmprunter` (une fonction) passée du parent à la Carte, et un bouton qui l'appelle — tu prépares la remontée d'événements du jour 100.

## ⚠️ Erreurs fréquentes
- Un composant géant qui fait tout : illisible et non réutilisable — découpe en briques nommées d'après leur rôle.
- Muter les props (les props sont en lecture seule) : casse le flux unidirectionnel et provoque des bugs invisibles.
- Oublier la majuscule sur le nom du composant : React le prend pour une balise HTML et ne le rend pas.
- Typer les props avec any : on perd toute la sécurité de TypeScript, qui est justement l'intérêt de typer un front.

## 🏢 Cas métier
Toute interface d'entreprise moderne (tableau de bord, e-commerce, back-office) est un arbre de composants React ou équivalent. Les équipes qui décomposent proprement — une Carte réutilisée partout, des props typées — livrent vite et cassent rarement ; celles qui empilent du JSX monolithique de 400 lignes passent leur temps à débugger des régressions. Savoir découper une maquette en composants réutilisables est la compétence front n°1 attendue d'un développeur, et le typage des props (TypeScript) est ce qui distingue un front professionnel d'un prototype fragile.

## 🎤 Question d'entretien
**« Qu'est-ce qu'un composant React, et pourquoi dit-on qu'il doit être 'pur' ? »** → Un composant est une fonction qui reçoit des props et renvoie du JSX décrivant l'UI. « Pur » signifie : mêmes props → même rendu, sans effet de bord ni mutation de ses props. Cette pureté est ce qui permet à React de re-rendre de façon fiable et prévisible — il peut appeler la fonction quand il veut sans surprise. Le corollaire : les données descendent du parent vers l'enfant (flux unidirectionnel), et un composant ne modifie jamais ce qu'il reçoit.
