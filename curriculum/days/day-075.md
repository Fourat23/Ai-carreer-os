# Jour 75 — Lecture de code existant : la compétence sous-estimée

> **Mois 3** · **Semaine 11** · Compétence : **Software engineering** · Difficulté : Intermédiaire/5 · Durée : 4.5 h

[← Dashboard](../../) · [Semaine 11](../week-11.md) · [Mois 3](../month-03.md) · [Correction](../solutions/day-075-solution.md)

## 🎯 Objectif du jour
Apprendre à lire et comprendre un codebase inconnu — ce que tu feras 80% du temps en poste.

## 📖 Cours approfondi
**Concepts abordés :** Stratégie de lecture · Point d'entrée · Suivre un flux · Cartographier sans tout lire · Poser des questions au code.

En poste, tu liras 5 à 10 fois plus de code que tu n'en écriras — et personne n'enseigne à lire. La stratégie : ne JAMAIS lire linéairement. (1) Trouver le point d'entrée (package.json → main/scripts, le fichier qui démarre tout). (2) Cartographier les grandes zones (les dossiers racontent l'architecture). (3) Choisir UN flux utilisateur et le suivre de bout en bout, en notant les fonctions traversées. (4) Formuler des hypothèses (« ce module doit faire X ») et les VÉRIFIER — lire avec une question, jamais en spectateur.

Les outils du lecteur : la recherche globale (où cette fonction est-elle appelée ?), le go-to-definition, git log sur un fichier (son histoire raconte ses douleurs), les tests (la documentation d'usage la plus fiable).

Accepter l'inconfort : on comprend un codebase à 30%, puis 50%, jamais 100% d'emblée. L'objectif est de savoir OÙ intervenir, pas de tout savoir.

**Leçon(s) de fond à lire/relire :**
- [Clean code](/doc/lessons/clean-code)
- [Tester son code](/doc/lessons/testing-foundations)

## ✍️ Pratique autonome
> **D'abord sans IA.** Tente seul au moins 30 minutes. Ne copie-colle jamais une réponse d'IA : lis, ferme, réécris de mémoire.

### Exercice principal
Clone un projet open-source simple (ex: un petit utilitaire Node populaire). Sans le lancer d'abord : trouve le point d'entrée, cartographie l'architecture, trace un flux complet. Écris ce que tu as compris AVANT de vérifier.

## 📦 Livrable attendu
Une note de compréhension d'un codebase inconnu (architecture + un flux tracé).

## ✅ Critères de validation
- [ ] Point d'entrée et architecture du repo inconnu identifiés et documentés
- [ ] Un flux complet tracé (liste des fonctions traversées, dans l'ordre)
- [ ] Tes hypothèses écrites AVANT vérification, avec le verdict (justes/fausses)

## ⚠️ Erreurs fréquentes
- Vouloir tout lire (paralysie).
- Lire sans hypothèse (errance).

## 🔗 Ressources
- N'importe quel repo Node bien noté et de taille modeste

## 🤖 Consigne d'utilisation de l'IA
Lis SEUL d'abord : demander à l'IA de résumer le code te prive de la compétence n°1 du métier.

## 🎤 Question d'entretien
**« Comment testes-tu ce code, et comment sais-tu qu'un test est utile ? »** → Arrange/Act/Assert sur la logique pure ; un test doit pouvoir ÉCHOUER (on sabote pour le prouver) ; isoler l'extérieur par des mocks ; tester les cas limites et d'erreur, pas seulement le chemin heureux.

## 🧠 À retenir
- Concepts clés du jour : Stratégie de lecture, Point d'entrée, Suivre un flux, Cartographier sans tout lire, Poser des questions au code.
- Approfondis via la leçon de fond : Clean code, Tester son code.
- Je dois pouvoir REFAIRE l'exercice seul demain et l'EXPLIQUER à l'oral — sinon ce n'est pas encore acquis.

## 🚀 Pourquoi ça comptera plus tard
- **En architecture** : tests, gestion d'erreurs et refactoring sont ce qui rend une architecture VIVABLE — sans eux, tout design s'effondre à la première évolution.
- **En IA** : tester un composant qui appelle un LLM (mock, replay, éval — mois 11) est une extension directe des tests d'aujourd'hui.
- **En entretien** : la qualité de ton code sous pression (nommage, découpage, cas limites) est évaluée dans CHAQUE exercice, même quand on ne le dit pas.
