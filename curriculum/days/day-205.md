## 🎯 Objectif du jour
Forcer et valider le JSON.

## 📖 Cours approfondi
**Modèle mental : le LLM propose, ton code dispose.** Dès qu'une sortie LLM alimente du CODE (parsing, base de données, affichage), la règle change : plus question d'accepter du texte libre. On impose un contrat — un schéma JSON strict — et on VALIDE côté code, systématiquement. La confiance ne se demande pas au modèle, elle s'obtient par la validation.

L'architecture d'un extracteur robuste :
1. **Le prompt-contrat** : schéma exact, types, champs obligatoires, et la convention d'absence (« si l'info n'est pas dans le texte : null » — JAMAIS deviner). Température 0.
2. **La validation côté code** : parse le JSON, vérifie le schéma (Pydantic en Python, Zod en TS — tes acquis du mois 5 resservent), vérifie les invariants métier (une date au futur pour une facture passée = rejet).
3. **Le retry intelligent** : en cas d'échec de parse/validation, on ne réessaie pas bêtement — on renvoie l'ERREUR PRÉCISE au modèle (« ton JSON a échoué : champ montant manquant ») et on lui redemande. Une à deux fois, puis échec propre et loggé.
4. **L'échec assumé** : un extracteur qui échoue proprement sur 3 % des cas vaut mieux qu'un qui invente sur 3 % des cas — l'erreur silencieuse est le pire scénario.

Ce pattern (contrat → validation → retry → échec propre) est LE pont entre le monde probabiliste du LLM et le monde déterministe de ton code. Tu le réutiliseras dans chaque app LLM de ta carrière.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : extracteur texte libre → JSON validé (exemple : demandes de congés).

**Raisonnement** : définir le schéma d'abord, le prompt ensuite, la boucle de validation autour.

**Squelette** :
```python
from pydantic import BaseModel, ValidationError
class Conge(BaseModel):
    employe: str
    date_debut: str          # ISO 8601
    date_fin: str
    motif: str | None        # null si absent — pas deviné

def extraire(texte: str, essais=2) -> Conge | None:
    erreur = ""
    for _ in range(essais):
        brut = appel_llm(PROMPT.format(texte=texte, erreur=erreur), temp=0)
        try:
            return Conge.model_validate_json(brut)
        except ValidationError as e:
            erreur = f"Ton JSON précédent a échoué : {e}. Corrige."
    log_echec(texte)
    return None               # échec PROPRE, pas d'invention
```

**Explication** : le renvoi de l'erreur au modèle rend le retry intelligent — le taux de succès au 2e essai est spectaculairement meilleur qu'un simple re-run. **Variante** : teste sur 10 textes dont 3 pièges (info manquante, deux demandes dans un texte, texte hors sujet) et mesure ton taux de succès/échec propre/invention.

## ⚠️ Erreurs fréquentes
- Valider seulement « c'est du JSON » : un JSON bien formé peut contenir un montant inventé — les invariants métier sont le 2e étage obligatoire.
- Retry aveugle (re-run sans renvoyer l'erreur) : tu rejoues la même loterie au lieu de guider la correction.
- Laisser le modèle deviner les champs manquants au lieu d'imposer null : l'invention silencieuse entre en base.
- Oublier le cas « texte hors sujet » : l'extracteur doit savoir dire « rien à extraire ».

## 🏢 Cas métier
Cas réel type : extraire les données de bons de commande reçus par email vers l'ERP. Sans validation stricte, UNE hallucination de montant passée en base coûte plus cher que tout le projet. Le pattern contrat/validation/retry est la différence entre un POC et un système qu'un directeur financier accepte de brancher.

## 🎤 Question d'entretien
**« Comment fiabilises-tu une sortie JSON de LLM ? »** → Contrat strict dans le prompt (schéma, null si absent), température 0, validation côté code (Pydantic/Zod + invariants métier), retry en renvoyant l'erreur précise au modèle, et échec propre loggé au-delà. Le principe : ne jamais faire confiance à la sortie — la valider.
