## 🎯 Objectif du jour
Poser les fondations.

## 📖 Cours approfondi
**Modèle mental : poser les fondations (repo structuré + CI verte) AVANT toute fonctionnalité, c'est installer le filet de sécurité avant de marcher sur le fil — une CI qui passe sur un projet vide garantit que chaque futur commit sera vérifié automatiquement.** Le dernier jour de cadrage établit l'infrastructure du build : un repo bien structuré (selon l'architecture hexagonale du jour 303), et une CI (intégration continue) qui tourne dès le départ, même sur un projet quasi vide. Commencer par les fondations plutôt que par les features est un choix d'ingénieur mûr : on rend la qualité AUTOMATIQUE avant d'écrire le code qui en aura besoin.

Les éléments des fondations :
1. **La structure du repo** : les dossiers reflètent l'architecture (cœur/domaine, adapters, tests, docs/adr) — hexagonal dès le départ (jour 289). Une structure claire dès le début évite le refactoring douloureux d'un projet qui a grossi en vrac. Le README, la SPEC, l'ARCHITECTURE et les ADR (jours 302-306) y trouvent leur place.
2. **La CI vide qui passe** : un pipeline (GitHub Actions) qui, à chaque push, lance le lint et les tests — même s'il n'y a presque rien à tester au départ. Pourquoi « vide » ? Parce que mettre en place la CI sur un projet vide est FACILE (rien ne casse), alors que l'ajouter tard sur un gros projet est pénible (tout casse d'un coup). Une CI verte dès le jour 1 signifie que chaque fonctionnalité future arrivera dans un environnement où la vérification est déjà automatique — impossible de merger du code cassé sans le voir.
3. **La relecture critique de la SPEC à J+2** : avec 2 jours de recul, relire la SPEC révèle les angles morts (un cas d'usage oublié, un hors-scope trop optimiste). Le recul court est un outil de qualité gratuit.

Pourquoi commencer par les fondations paie : un projet sans CI accumule silencieusement des régressions (un commit casse un test, personne ne le voit, la dette s'installe) ; un projet avec CI dès le départ maintient sa qualité en continu (chaque commit est vérifié). C'est le principe « rendre le bon comportement automatique » — au lieu de compter sur la discipline (lancer les tests à la main, qu'on oublie), on l'automatise. Et une CI verte dès le premier jour est un signal de professionnalisme immédiatement visible sur un repo : un recruteur qui voit une CI verte sait que le projet a une culture de qualité.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : repo DocSense structuré + CI GitHub Actions verte sur projet quasi vide + relecture SPEC.

**Exemple simple** : la CI minimale qui a de la valeur — un workflow qui, à chaque push, installe les dépendances et lance `lint` + `test`, même si test ne contient qu'un seul test trivial. Le point n'est pas ce qu'elle teste aujourd'hui, mais qu'elle TOURNE dès aujourd'hui.

**Raisonnement pas-à-pas** : structurer le repo selon l'architecture hexagonale, mettre la CI en place tant que c'est facile (projet vide), relire la SPEC avec du recul.

**Les fondations** :
```
Structure du repo (hexagonal) :
  docsense/
    domaine/       # cœur : logique RAG, refus, éval (sans framework)
    adapters/      # détails : vector DB, LLM, stockage
    tests/         # tests du cœur (avec stubs)
  docs/
    SPEC.md · ARCHITECTURE.md · adr/ADR-00X.md
  README.md · .gitignore (secrets exclus !) · pyproject/requirements
.github/workflows/ci.yml :
  à chaque push → installer deps → lint → tests (même 1 test trivial)
  → badge vert sur le repo
Relecture SPEC à J+2 : un cas d'usage oublié ? un hors-scope trop optimiste ?
```

**Mini-quiz** : (a) Pourquoi mettre la CI en place sur un projet VIDE ? (b) Que garantit une CI verte dès le jour 1 ? (c) Pourquoi relire la SPEC à J+2 ?
→ (a) c'est facile quand rien ne casse ; l'ajouter tard sur un gros projet est pénible ; (b) chaque futur commit arrive dans un environnement où la vérification est automatique — impossible de merger du cassé sans le voir ; (c) le recul court révèle les angles morts (cas d'usage oublié, hors-scope optimiste).

**Variante** : casse volontairement un test et pousse — la CI doit PASSER AU ROUGE. Une CI qui ne détecte pas un test cassé n'est pas un filet de sécurité. Vérifie qu'elle protège vraiment.

## 🏢 Cas métier
Commencer par les fondations (repo structuré + CI) est une pratique d'ingénieur expérimenté qui paie sur toute la durée du projet : une CI installée dès le départ maintient la qualité en continu (chaque commit vérifié), alors qu'une CI ajoutée tard sur un projet mûr est un chantier douloureux (des dizaines de tests à réparer d'un coup, une intégration complexe). En entreprise, les projets qui démarrent sans CI accumulent une dette de qualité invisible qui explose plus tard. Un repo avec une CI verte dès le premier commit signale immédiatement une culture de qualité — un recruteur qui voit le badge vert et une structure claire sait qu'il a affaire à quelqu'un qui rend la qualité automatique plutôt que de compter sur la discipline. Pour DocSense, c'est le filet qui protégera les 7 semaines de build.

## 🎤 Question d'entretien
**« Par quoi commences-tu un nouveau projet, avant les fonctionnalités ? »** → Par les fondations : un repo structuré selon l'architecture (hexagonal — cœur/adapters/tests/docs) et une CI qui passe dès le projet vide. Je mets la CI en place tôt parce que c'est FACILE quand rien ne casse, alors que l'ajouter tard sur un gros projet est pénible ; et une CI verte dès le jour 1 garantit que chaque commit futur arrive dans un environnement où lint et tests sont automatiques — impossible de merger du cassé sans le voir. C'est le principe « rendre le bon comportement automatique » plutôt que compter sur la discipline. Et je relis la SPEC à J+2 : le recul court révèle les angles morts.
