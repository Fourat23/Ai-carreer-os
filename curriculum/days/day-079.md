## 🎯 Objectif du jour
Rendre une application observable : logs structurés, métriques, correlation id — indispensable en production.

## 📖 Cours approfondi
**Concepts abordés :** Logs structurés (JSON) · Niveaux de log · Métriques · Traces / correlation id · Que logger, que ne jamais logger.

L'observabilité répond à UNE question : « que s'est-il passé en production ? » — sans elle, tu es aveugle. Trois piliers : les LOGS (des événements horodatés — ce qui s'est passé), les MÉTRIQUES (des agrégats — combien, à quelle vitesse), les TRACES (le parcours d'UNE requête à travers le système).

Les logs STRUCTURÉS (JSON : {timestamp, level, message, requestId, ...}) sont interrogeables mécaniquement, là où le texte libre exige des yeux humains. Les NIVEAUX (debug/info/warn/error) permettent de filtrer. Le CORRELATION ID — un identifiant unique généré à l'entrée de chaque requête et propagé partout — relie tous les logs d'une même requête : c'est lui qui permet de « rejouer » une session.

Ce qu'on ne logge JAMAIS : mots de passe, tokens, données personnelles sensibles. Un log est une base de données que tout le monde lit.

**Modèle mental : l'observabilité répond à UNE question — « que s'est-il passé en production ? ». Sans elle, tu es AVEUGLE : un bug survient chez un utilisateur, et tu n'as aucune trace pour comprendre. Trois piliers : les LOGS (des événements horodatés — ce qui s'est passé), les MÉTRIQUES (des agrégats — combien, à quelle vitesse), les TRACES (le parcours d'UNE requête à travers le système). Les logs STRUCTURÉS (JSON) sont interrogeables mécaniquement, et le CORRELATION ID relie tous les logs d'une même requête. La règle qui protège : on log assez pour déboguer, JAMAIS de secrets ni de données personnelles.** Rendre une application observable, c'est se donner les yeux pour la production.

Pourquoi l'observabilité est vitale. En développement, quand un bug survient, tu as le débogueur, les logs, la reproduction. En PRODUCTION, tu n'as RIEN de tout ça : le bug est arrivé chez un utilisateur, il y a des heures, tu ne peux pas reproduire. Ta seule fenêtre sur ce qui s'est passé, ce sont les données que l'application a émises PENDANT l'incident. Sans observabilité, un incident de production est un mystère insoluble ; avec, il devient une enquête possible. C'est la différence entre voler à vue et voler aux instruments.

Les trois piliers, depuis les fondations. **Les LOGS** : des événements horodatés (« requête reçue », « emprunt créé », « erreur X ») — ils racontent CE QUI s'est passé, événement par événement. **Les MÉTRIQUES** : des agrégats numériques (nombre de requêtes, latence moyenne, taux d'erreur) — ils disent COMBIEN et À QUELLE VITESSE, pour repérer les tendances et les anomalies. **Les TRACES** : le parcours d'UNE requête à travers les composants du système — elles montrent OÙ le temps est passé et OÙ ça a cassé, pour une requête donnée. Les trois sont complémentaires : logs pour le détail, métriques pour la tendance, traces pour le parcours.

Les logs structurés, depuis les fondations. Un log en TEXTE LIBRE (« erreur lors de l'emprunt du livre 42 par le membre 7 ») est lisible par un humain mais INGREPABLE mécaniquement à grande échelle. Un log STRUCTURÉ (JSON : `{ timestamp, level, message, requestId, livreId, membreId }`) est INTERROGEABLE — on peut filtrer tous les logs `level=error`, tous ceux d'un `requestId`, agréger par `livreId`. À l'échelle de milliers de requêtes, seul le structuré permet de retrouver l'aiguille dans la botte de foin.

Le correlation id, depuis les fondations. Un identifiant unique généré à l'ENTRÉE de chaque requête et propagé dans TOUS ses logs. Bénéfice décisif : on peut RECONSTITUER tout ce qui s'est passé pour UNE requête précise en filtrant sur son `requestId` — même si mille requêtes s'entrelacent dans les logs. Sans corrélation, les logs sont un enchevêtrement illisible ; avec, chaque requête a son fil traçable.

Les niveaux et la règle de sécurité. Les NIVEAUX (debug/info/warn/error) permettent de filtrer selon la gravité (tout en dev, seulement warn/error en prod). La règle absolue : on ne LOG JAMAIS de secrets (tokens, mots de passe) ni de données personnelles sensibles — les logs sont stockés, consultés, parfois exfiltrés ; un secret dans un log est un secret fuité (jour 68).

Limites et compromis. Trop de logs coûtent (stockage, bruit qui noie l'essentiel) ; trop peu aveuglent — le bon niveau log les événements utiles au débogage. Les métriques et traces ont un coût de mise en place ; on commence simple (logs structurés + correlation id + quelques métriques). Et logger des données sensibles est un risque de conformité (RGPD) autant que de sécurité.

La règle du jour : **rends l'application observable pour répondre à « que s'est-il passé en prod ? » — logs structurés (JSON, interrogeables) avec niveaux et CORRELATION ID (reconstituer une requête), métriques (agrégats), traces (parcours). Log assez pour déboguer, JAMAIS de secrets ni de données personnelles.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : ajouter des logs structurés avec correlation id à une API, de sorte qu'on puisse reconstituer une session complète depuis les seuls logs.

**Exemple simple** : texte libre vs structuré. `console.log('emprunt échoué')` n'est pas filtrable. `{ level: 'error', requestId: 'abc', event: 'emprunt_refuse', livreId: 42 }` permet de filtrer tous les `error`, de suivre le `requestId` abc, d'agréger par `livreId`. Le structuré est interrogeable.

**Raisonnement pas-à-pas** : (1) un middleware génère un correlation id à l'entrée de CHAQUE requête ; (2) tous les logs de cette requête portent ce même id ; (3) les logs sont en JSON avec un niveau ; (4) aucun secret ni donnée personnelle n'est loggé.

**Implémentation** :
```ts
import { randomUUID } from 'node:crypto';

function log(niveau: string, requestId: string, event: string, extra: object = {}) {
  // log STRUCTURÉ (JSON) : interrogeable mécaniquement
  console.log(JSON.stringify({ timestamp: new Date().toISOString(), niveau, requestId, event, ...extra }));
}

// MIDDLEWARE : un correlation id par requête, propagé dans tous ses logs
app.use((req, res, next) => {
  req.requestId = randomUUID();                       // id unique à l'ENTRÉE
  log('info', req.requestId, 'requete_recue', { methode: req.method, chemin: req.path });
  res.on('finish', () =>
    log('info', req.requestId, 'requete_terminee', { statut: res.statusCode }));
  next();
});

app.post('/emprunts', (req, res) => {
  try {
    const e = serviceEmprunts.emprunter(req.body.livreId, req.body.membreId);
    log('info', req.requestId, 'emprunt_cree', { livreId: req.body.livreId }); // PAS de données perso
    res.status(201).json(e);
  } catch (err) {
    log('error', req.requestId, 'emprunt_refuse', { livreId: req.body.livreId, raison: err.message });
    res.status(409).json({ message: err.message });
  }
});
```
En filtrant les logs sur un `requestId`, on reconstitue toute la vie d'une requête (reçue → emprunt refusé → terminée en 409) même au milieu de milliers d'autres. Les logs sont structurés (interrogeables), avec niveaux, et ne contiennent aucun secret ni donnée personnelle.

## ⚠️ Erreurs fréquentes
- Logs en texte libre non structuré : ingrepables à grande échelle, il faut des yeux humains.
- Logger des secrets/mots de passe/tokens ou des données personnelles : fuite et non-conformité RGPD.
- Pas de correlation id : impossible de reconstituer une requête au milieu de milliers d'autres.
- Trop de logs sans niveaux : le bruit noie l'essentiel et coûte en stockage.

## 🏢 Cas métier
L'observabilité est ce qui rend une application EXPLOITABLE en production, et son absence est une cause majeure d'incidents non résolus et de temps de rétablissement (MTTR) élevés. Quand un service tombe ou se dégrade à 3 h du matin, l'équipe d'astreinte n'a que les logs, les métriques et les traces pour comprendre et corriger — sans elles, elle est aveugle et l'incident s'éternise. Les logs structurés avec correlation id permettent de reconstituer le parcours d'une requête problématique parmi des millions ; les métriques (latence, taux d'erreur) déclenchent les alertes avant que les utilisateurs ne se plaignent ; les traces localisent le composant lent dans une architecture distribuée. Les plateformes d'observabilité (Datadog, Grafana, ELK, OpenTelemetry) sont un marché entier. La règle de ne jamais logger de secrets ni de données personnelles est aussi une exigence de conformité (RGPD) et de sécurité. Savoir instrumenter une application (logs structurés, correlation id, métriques de base) et raisonner sur ce qu'il faut logger est une compétence directement valorisée pour tout rôle back ou DevOps — et « comment débogues-tu un problème en production ? » repose entièrement sur l'observabilité.

## 🎤 Question d'entretien
**« Comment rends-tu une application débogable en production ? »** → Par l'observabilité, qui répond à la question « que s'est-il passé en prod ? » — parce qu'en production, contrairement au dev, je n'ai ni débogueur ni reproduction : ma seule fenêtre, ce sont les données que l'application a émises pendant l'incident. Je m'appuie sur trois piliers. Les LOGS : des événements horodatés, que je rends STRUCTURÉS en JSON pour qu'ils soient interrogeables — je peux filtrer par niveau, par requête, agréger par champ, ce que du texte libre ne permet pas à grande échelle. Les MÉTRIQUES : des agrégats comme la latence et le taux d'erreur, pour repérer les tendances et déclencher des alertes. Les TRACES : le parcours d'une requête à travers le système. L'élément clé pour déboguer, c'est le CORRELATION ID : un identifiant unique généré à l'entrée de chaque requête et propagé dans tous ses logs — il me permet de reconstituer toute la vie d'une requête précise, même noyée dans des milliers d'autres. Et une règle absolue : je ne logge JAMAIS de secrets ni de données personnelles, parce que les logs sont stockés et consultés — c'est autant une question de sécurité que de conformité RGPD. **Relance possible** : « quelle est la différence entre logs, métriques et traces ? » → les logs disent CE QUI s'est passé (détail événementiel), les métriques COMBIEN et à quelle vitesse (agrégats pour les tendances/alertes), les traces OÙ le temps est passé pour UNE requête ; ils sont complémentaires, pas interchangeables.
