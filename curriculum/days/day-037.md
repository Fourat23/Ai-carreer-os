## 🎯 Objectif du jour
Modéliser avec interfaces et unions, contraindre par littéraux, écrire des fonctions génériques.

## 📖 Cours approfondi
**Concepts abordés :** interface vs type · Union / intersection · Types littéraux · Génériques <T> · Narrowing.

Les types avancés font du compilateur un garde du corps : une union littérale `type Statut = 'panier' | 'payee' | 'expediee'` transforme une simple string en contrat — la typo 'payé' devient une erreur de compilation, et un switch sur le statut peut être vérifié exhaustif.

`interface` décrit la forme d'un objet (extensible), `type` crée des alias et des unions. Le narrowing : TypeScript AFFINE le type dans les branches (`if (typeof x === 'string')` → x est string dedans).

Les génériques `<T>` écrivent UNE logique valable pour tous les types sans perdre le typage : `premier<T>(arr: T[], p: (x: T) => boolean)` fonctionne sur des nombres comme des Commandes, et le résultat est du bon type. C'est le mécanisme derrière Array, Map, Promise.

**Modèle mental : les types avancés servent à rendre les états ILLÉGAUX IMPOSSIBLES à représenter. Une union littérale `type Statut = 'panier' | 'payee' | 'expediee'` transforme une simple chaîne en CONTRAT vérifié : la faute de frappe `'payé'` devient une erreur de compilation, et un `switch` sur le statut peut être prouvé EXHAUSTIF. Un générique `<T>` écrit UNE logique valable pour tous les types sans perdre le typage. Le but n'est pas d'annoter plus : c'est de modéliser le domaine si précisément que le compilateur refuse les valeurs absurdes.** Bien typé, le domaine se documente et se protège lui-même.

Pourquoi ces outils existent. Avec les types de base, on peut encore écrire des non-sens acceptés : un statut `"livré"` mal orthographié, un objet auquel il manque un champ, une fonction `premier` recopiée pour chaque type. Les types avancés ferment ces trous : les unions littérales bornent les valeurs possibles, les interfaces imposent la forme des objets, les génériques éliminent la duplication tout en gardant la vérification. C'est le passage de « le code compile » à « le code ne PEUT pas être dans un état incohérent ».

Comment ils fonctionnent, depuis les fondations. Une **interface** décrit la FORME d'un objet (ses propriétés et leurs types), extensible et implémentable. Un **type alias** nomme n'importe quel type, y compris les UNIONS (`A | B` : l'un OU l'autre) et intersections (`A & B` : les deux à la fois). Les **types littéraux** font d'une valeur constante un type (`'payee'` est un type qui n'accepte que cette chaîne) ; leur union borne un ensemble fini. Le **narrowing** est le mécanisme par lequel le compilateur AFFINE le type dans une branche : après `if (typeof x === 'string')`, `x` est `string` à l'intérieur. Un **générique** `premier<T>(arr: T[], p: (x: T) => boolean): T | undefined` paramètre le type : appelé sur des `number[]` il renvoie `number | undefined`, sur des `Commande[]` il renvoie `Commande | undefined` — une seule implémentation, typage préservé.

La différence interface vs type, souvent demandée. `interface` est privilégiée pour les objets extensibles (elle supporte la fusion de déclarations et l'`implements`). `type` est indispensable pour les unions, intersections, alias de primitives et types calculés. En pratique : interface pour la forme d'un objet, type pour tout le reste (surtout les unions). Les deux se recouvrent largement pour les objets simples.

Le bénéfice décisif : l'exhaustivité vérifiée. Sur une union littérale, un `switch` couvrant tous les cas permet au compilateur de PROUVER qu'aucun cas n'est oublié (via un cas `default` typé `never`). Ajouter un statut demain provoque une erreur de compilation partout où il faut le gérer — le compilateur devient ta checklist de refactoring.

Limites et compromis. Sur/sous-contraindre un générique nuit : `<T>` trop libre n'apporte rien, `<T extends { id: number }>` peut être nécessaire pour accéder à `.id`. Les types trop élaborés (conditionnels, mappés imbriqués) deviennent illisibles — la sophistication doit servir la clarté, pas l'exhiber. Et le typage reste effacé à l'exécution : il ne valide pas les données réelles (d'où la validation runtime, jour 54).

La règle du jour : **modélise le domaine pour rendre les états illégaux irreprésentables — unions littérales pour borner les valeurs, interfaces pour les formes, génériques pour une logique réutilisable typée. Vise l'exhaustivité vérifiée par le compilateur, sans sur-typer au point de nuire à la lisibilité.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : modéliser une commande e-commerce avec un statut en union littérale, puis écrire une fonction générique `premier<T>` réutilisable.

**Exemple simple** : le statut. Écrit `statut: string`, la valeur `'payé'` (accent, faute) passe silencieusement. Écrit `statut: 'panier' | 'payee' | 'expediee'`, cette même faute devient une erreur de compilation — le type EST le garde-fou.

**Raisonnement pas-à-pas** : (1) je décris les formes avec des interfaces ; (2) je borne le statut par une union littérale ; (3) j'écris un `switch` exhaustif dont le `default: never` PROUVE qu'aucun cas n'est oublié ; (4) j'extrais la logique « trouver le premier élément qui satisfait un prédicat » en une fonction générique valable pour tout type.

**Implémentation** :
```ts
type Statut = 'panier' | 'payee' | 'expediee';

interface Produit { id: number; nom: string; prix: number; }
interface LigneCommande { produit: Produit; quantite: number; }
interface Commande { id: number; lignes: LigneCommande[]; statut: Statut; }

function messageStatut(c: Commande): string {
  switch (c.statut) {
    case 'panier':   return 'En cours de constitution';
    case 'payee':    return 'Paiement reçu';
    case 'expediee': return 'Colis expédié';
    default:
      const _exhaustif: never = c.statut;   // erreur de compil si un statut est oublié
      return _exhaustif;
  }
}

// Générique : UNE implémentation, typage préservé pour tout T
function premier<T>(arr: T[], p: (x: T) => boolean): T | undefined {
  for (const x of arr) if (p(x)) return x;
  return undefined;
}

const n = premier([1, 2, 3, 4], x => x % 2 === 0);        // number | undefined -> 2
const commandes: Commande[] = [];
const c = premier(commandes, cmd => cmd.statut === 'payee'); // Commande | undefined
```
Ajoute demain `'remboursee'` à `Statut` : le `switch` ne compile plus tant que tu ne l'as pas géré. Le compilateur t'a listé le travail.

## ⚠️ Erreurs fréquentes
- Laisser le statut en `string` au lieu d'une union littérale : une faute de frappe passe sans être détectée.
- Oublier l'exhaustivité (pas de default:never) : un cas non géré ne déclenche aucune erreur à l'ajout d'un statut.
- Générique sur- ou sous-contraint : `<T>` trop libre n'apporte rien ; sans `extends`, impossible d'accéder à une propriété commune.
- Croire que le typage valide les données réelles : il est effacé à l'exécution ; les données externes exigent une validation runtime (jour 54).

## 🏢 Cas métier
La modélisation par types précis est ce qui distingue une base de code robuste d'une base fragile en entreprise. Un domaine métier (commande, paiement, abonnement) modélisé par des unions littérales et des interfaces strictes rend des CLASSES ENTIÈRES de bugs impossibles : on ne peut pas mettre un statut invalide, oublier un champ obligatoire, ni ignorer un nouveau cas sans que le compilateur ne le signale. Les états illégaux irreprésentables, c'est moins de tests défensifs à écrire et moins d'incidents en production. Les génériques, eux, fondent les bibliothèques réutilisables (une fonction de tri, un client d'API typé) sans sacrifier la sécurité. Concrètement, savoir modéliser un domaine avec unions et interfaces, et écrire une fonction générique correctement contrainte, est exactement ce qu'un lead cherche dans une revue de code — et une source fréquente de questions d'entretien front/back TypeScript.

## 🎤 Question d'entretien
**« Comment utiliserais-tu le système de types pour empêcher un statut de commande invalide, et qu'apporte un type générique ? »** → Je remplace `statut: string` par une union littérale `'panier' | 'payee' | 'expediee'` : dès lors, une valeur mal orthographiée devient une erreur de compilation — le type est le garde-fou. Mieux, un `switch` sur ce statut avec un cas `default` typé `never` me donne l'EXHAUSTIVITÉ vérifiée : si j'ajoute un statut demain, le code ne compile plus tant que je ne l'ai pas traité, donc le compilateur me sert de checklist de refactoring. C'est le principe « rendre les états illégaux irreprésentables ». Pour le générique : `premier<T>(arr: T[], p: (x: T) => boolean): T | undefined` écrit UNE seule logique valable pour tous les types en préservant le typage — sur des nombres il renvoie `number | undefined`, sur des commandes `Commande | undefined`, sans `any` ni duplication. C'est le mécanisme derrière `Array`, `Map`, `Promise`. **Relance possible** : « et si le générique doit accéder à une propriété commune ? » → je le CONTRAINS : `<T extends { id: number }>` autorise `x.id` tout en restant générique — sur/sous-contraindre est le principal piège des génériques.
