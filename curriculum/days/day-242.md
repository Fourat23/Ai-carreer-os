## 🎯 Objectif du jour
Gérer les reconstructions.

## 📖 Cours approfondi
**Modèle mental : un index est un ARTEFACT COMPILÉ — comme un binaire, il doit toujours pouvoir être reconstruit depuis ses sources et sa recette.** Ton index n'est plus un fichier : c'est le produit de quatre ingrédients — les documents (version du corpus), la stratégie de chunking (et ses paramètres), le modèle d'embedding, et le code du pipeline. Change UN ingrédient et l'index devient un autre index. Sans traçabilité, tu obtiens l'index-mystère : « celui-là marche mieux, mais on ne sait plus comment il a été construit » — l'équivalent RAG du binaire sans source.

Le versioning minimal viable :
1. **Un manifeste par index** : `{version, date, corpus_hash (ou liste doc+hash), chunking: {strategie, params}, embedding_model, code_version (commit)}` — écrit à la construction, stocké AVEC l'index (métadonnées de collection Chroma, ou fichier à côté). Ton embryon du jour 218 (modèle + date + n) devient complet.
2. **La reconstruction scriptée** : `rag build --config configs/v3.json` reconstruit l'index à l'identique depuis les sources. Le test de vérité : reconstruire et comparer (mêmes n_chunks, échantillon de vecteurs identiques). C'est la reproductibilité du jour 181, appliquée aux index.
3. **La règle d'invalidation** : quel changement invalide quoi. Corpus modifié → ré-ingestion incrémentale (jour 223, remplacement par source). Chunking ou modèle d'embedding changé → reconstruction TOTALE (tous les vecteurs sont issus de la recette) — et c'est là que ton chiffrage du jour 228 (coût de ré-ingestion) devient une contrainte de conception : changer de modèle d'embedding n'est pas un hotfix, c'est une MIGRATION planifiée.
4. **La migration propre** : construire le nouvel index EN PARALLÈLE (collection v4 à côté de v3), valider sur le golden set (le double-run du jour 239 — même protocole, nouvelle variable), basculer, garder v3 le temps d'un rollback possible. Jamais de reconstruction « sur place » : un index en cours de reconstruction est un index qui ment.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : manifeste, reconstruction scriptée, et une migration blanche complète.

**Raisonnement** : le manifeste d'abord (traçabilité), le script ensuite (reproductibilité), la migration blanche enfin (la procédure vécue une fois AVANT d'en avoir besoin).

**Le manifeste** :
```json
{
  "index_version": "v3",
  "construit_le": "2026-XX-XX",
  "corpus": {"n_docs": 12, "hash_global": "a3f9...",
              "docs": [{"source": "guide.md", "hash": "7c21..."}]},
  "chunking": {"strategie": "structurel", "max_tk": 600, "min_tk": 80},
  "embedding": {"modele": "voyage-3", "dim": 1024},
  "code": "commit 4be2a1f",
  "golden_set_score": "19/24 top-3"     ← le score de validation VOYAGE avec l'index
}
```

**La migration blanche (l'exercice central)** :
```
Scénario joué : « on passe du chunking fixe-400 au structurel » (tu as les deux !)
1. rag build --config structurel.json → collection docqa-v4 (v3 intacte)
2. Golden set sur v4 → score attendu (19/24, jour 241) : la validation
3. Bascule : le pipeline pointe vers v4 (UN paramètre de config)
4. Test de rollback : re-pointe vers v3, vérifie le harnais (jour 221), re-bascule
5. Journal de migration : quoi, pourquoi, scores avant/après, durée, coût
```

**Explication** : embarquer le score golden set DANS le manifeste lie chaque version d'index à sa qualité mesurée — l'historique des manifestes raconte l'évolution du système. **Variante** : provoque l'incident évité — modifie un document SANS ré-ingérer, et écris le check qui le détecte (hash du corpus vs manifeste : « index désynchronisé du corpus ») ; branche-le dans `rag status`.

## 🏢 Cas métier
Incident réel type : une équipe améliore son prompt pendant des semaines sur un index construit avec un vieux chunking, sans le savoir — les scores stagnent mystérieusement, jusqu'à ce que quelqu'un demande « il date de quand, cet index ? ». Personne ne sait. Reconstruction : +11 points de rappel, trois semaines perdues. Le manifeste coûte 15 lignes de JSON ; l'index-mystère coûte des sprints.

## 🎤 Question d'entretien
**« Que versionnes-tu dans un système RAG, et qu'est-ce qui invalide quoi ? »** → L'index est un artefact compilé de quatre sources : corpus, stratégie de chunking, modèle d'embedding, code. Chaque index porte un manifeste (versions + hashs + score de validation) et se reconstruit par script. Corpus modifié → ré-ingestion incrémentale ; chunking ou embedding changé → reconstruction totale, traitée comme une migration : nouvel index en parallèle, validation golden set, bascule par config, rollback possible.
