## 🎯 Objectif du jour
Faire de Postman un outil de test d'API sérieux : variables d'environnement, tests automatiques, scénarios.

## 📖 Cours approfondi
**Concepts abordés :** Collections structurées · Variables d'environnement · Tests JS dans Postman · Scénarios enchaînés.

Une collection Postman bien construite est trois choses à la fois : une DOCUMENTATION vivante (chaque requête montre l'usage réel), une SUITE DE TESTS (les assertions vérifient statut et forme de réponse à chaque exécution), et un OUTIL DE DÉMO (un recruteur importe, lance, tout passe).

Les variables d'environnement ({{baseUrl}}, {{token}}) rendent la collection portable : même collection en local et en prod. Les tests s'écrivent en JS dans l'onglet Tests : vérifier le statut ne suffit pas — vérifie aussi la FORME du corps (les champs attendus existent, les types sont bons).

Le scénario enchaîné (create → read → update → delete, en passant l'id créé aux requêtes suivantes via les variables) teste un FLUX réel, pas des endpoints isolés.

## ⚠️ Erreurs fréquentes
- Collection non exportée/versionnée.
- Tests qui ne vérifient que le statut, pas le corps.

## 🏢 Cas métier
Cas typique : appeler un LLM (POST + header d'auth + corps JSON + streaming), exposer ton système RAG comme une API (`POST /questions`), ou consommer une API tierce — comprendre HTTP, c'est comprendre comment les systèmes IA se parlent.

## 🎤 Question d'entretien
**« Décris le trajet d'une requête HTTP et le rôle des statuts. »** → DNS → TCP → TLS → HTTP ; requête (méthode + URL + headers + corps) / réponse (statut + corps) ; sans état ; 2xx succès, 4xx faute client, 5xx faute serveur ; idempotence de GET/PUT/DELETE pour les retries.
