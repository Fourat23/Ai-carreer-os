La documentation d'une API a un critère unique : un inconnu peut-il la tester en 5 minutes ? Le README répond dans l'ordre aux questions du lecteur : c'est quoi → comment lancer → comment tester (importer la collection) → comment c'est construit (architecture) → quelles limites.

La démo enregistrée (2 min, écran + voix) est un multiplicateur : elle prouve que ça marche sans rien installer, et elle t'entraîne à PRÉSENTER — la compétence du mois 12, commencée maintenant. Règle : scénario écrit, une répétition, une prise.

L'ADR n°2 (validation à la main vs librairie) capture un arbitrage réel : à ta taille, la validation manuelle est pédagogique et suffisante ; en équipe sur 30 endpoints, une librairie de schémas gagne. Savoir dire OÙ la bascule se produit, c'est exactement ce qu'on attend d'un ingénieur.

**Modèle mental : la documentation d'une API a un critère UNIQUE — un inconnu peut-il la tester en 5 minutes ? Le README répond dans l'ORDRE aux questions du lecteur : c'est quoi → comment lancer → comment tester (importer la collection) → comment c'est construit (architecture) → quelles limites. La collection Postman EST la doc vivante (clone → import → lance → tout passe), et la démo enregistrée (2 min, écran + voix) est un MULTIPLICATEUR : elle prouve que ça marche sans rien installer, et elle t'entraîne à PRÉSENTER.** Finaliser LivreAPI, c'est le rendre utilisable et compréhensible par quelqu'un qui n'a pas ta tête.

Pourquoi la doc décide de la visibilité d'un projet. Un projet dont personne ne sait l'installer, l'utiliser ni comprendre l'architecture est INVISIBLE — le meilleur code reste inexploité. La documentation n'est pas un supplément : c'est ce qui transforme un tas de code en projet UTILISABLE par d'autres (recruteur, collègue, toi dans six mois). Le critère opérationnel « un inconnu opérationnel en 5 minutes » rend la qualité de la doc MESURABLE : il suffit de tester ses propres instructions sur un clone frais.

Le README, dans l'ordre du lecteur. Le lecteur arrive avec des questions, dans un ordre précis : QU'EST-CE que c'est (une phrase claire) → COMMENT LE LANCER (commandes exactes, prérequis) → COMMENT LE TESTER (importer la collection Postman, exemples d'appels) → COMMENT C'EST CONSTRUIT (l'architecture en couches, le schéma) → QUELLES LIMITES (ce que ça ne fait pas, la dette assumée). Répondre dans CET ordre, c'est écrire pour le lecteur, pas pour soi.

La collection Postman comme doc vivante. Contrairement à une doc figée qui se périme, une collection exportée et versionnée est EXÉCUTABLE : on la clone, on l'importe, on lance — et tout passe. Elle documente l'usage réel (URLs, corps, headers) et prouve que l'API fonctionne, en un geste. C'est le prolongement direct du jour 59.

La démo enregistrée, un multiplicateur. Une démo de 2 minutes (partage d'écran + voix) prouve que ça marche SANS que le lecteur installe quoi que ce soit, et — bénéfice caché — elle t'ENTRAÎNE à présenter ton travail, la compétence du mois 12 commencée dès maintenant. La méthode : un scénario écrit, une répétition, une prise propre.

L'ADR n°2, un arbitrage réel. Un Architecture Decision Record capture une décision structurante : ici « validation à la main vs librairie » (jour 54). Il documente le contexte, les options, la décision, ses conséquences, et le POINT DE BASCULE (ce qui ferait passer à une librairie de validation). L'ADR prouve, comme au jour 47, que tu arbitres consciemment.

Limites et compromis. Un README trop long dilue l'essentiel, trop court n'aide pas — viser l'utilisabilité en 5 minutes calibre la longueur. Une démo se répète (mais pas dix fois : une prise correcte suffit). Documenter chaque détail est contre-productif ; on documente ce qui aide le lecteur à démarrer et à comprendre les décisions.

La règle du jour : **vise le critère « un inconnu teste l'API en 5 minutes » : README dans l'ordre du lecteur (quoi → lancer → tester → construit → limites), collection Postman comme doc vivante et exécutable, démo 2 min enregistrée (preuve + entraînement à présenter), et un ADR qui trace une décision structurante. Teste ta doc sur un clone frais.**

---

**La carte de la documentation technique professionnelle.** Le README et l'ADR ne sont que deux documents d'une famille plus large que tu croiseras en entreprise. La compétence n'est pas de tous les écrire, mais de choisir **le bon document, pour la bonne audience, au bon niveau de détail, au bon moment** — et de savoir quand NE PAS en écrire. Trois familles :

- **Décision** — pourquoi le système est ainsi. L'**ADR** *acte* une décision prise (immuable : on la remplace par un nouvel ADR) ; le **RFC** la *propose* et se discute *avant* de s'engager ; le **decision log** indexe ces décisions ; le **changelog** liste, pour les utilisateurs, ce qui a changé entre versions. Ne confonds pas : changelog = *ce qui a changé* ; decision log = *ce qui a été décidé et pourquoi*.
- **Conception** — comment le système est structuré, du plus haut au plus bas : **HSD** (High-Level Solution Design — quelle solution et pourquoi, convention de ce cours, cf. ADR-017) → **HLD** (architecture des composants, souvent avec le modèle **C4** : contexte → conteneurs → composants) → **LLD** (l'intérieur d'un composant : schéma de tables, algorithme) → **TSD** (le contrat d'implémentation, avec critères d'acceptation). Le **contrat d'API** fige ce qu'une API promet à ses consommateurs et précède l'implémentation.
- **Exploitation** — faire vivre le système en production. Le **runbook** donne la procédure exécutable (démarrer, diagnostiquer, *rollback*) pour l'astreinte à 3 h du matin ; le **playbook** orchestre une *famille* de situations ; le **post-mortem sans blâme** analyse un incident à froid (cause racine / *RCA*, actions), en cherchant le système fautif, pas un coupable.

L'erreur fréquente est la SUR-documentation : produire un HLD que personne ne lit au lieu d'un README clair. La bonne question : « quel est le PLUS PETIT document qui répond à la question de mon lecteur ? » On écrit un document quand son absence coûte (un inconnu bloqué, une décision reperdue, une astreinte sans procédure), et la doc **vit avec le code** — une doc jamais mise à jour ment. Modèles réutilisables de chaque document (but, audience, quand l'écrire/le mettre à jour, quand ne pas l'utiliser, différences, squelette à copier) : voir la référence [Documentation technique — modèles réutilisables](/doc/methodology/documentation-technique).

**Raisonnement pas-à-pas** : (1) j'écris le README dans l'ordre des questions du lecteur ; (2) j'exporte la collection Postman (doc vivante) ; (3) j'enregistre une démo de 2 min ; (4) je teste tout sur un clone frais.

**Structure (README.md)** :
```md
# LivreAPI — API REST de gestion d'une bibliothèque
Une API de prêt de livres (CRUD, emprunts, recherche), sur Node/Express + SQLite.

## Lancer (prérequis : Node 20+)
\`\`\`bash
npm install
sqlite3 livres.db < init.sql     # reconstruit la base d'une commande
cp .env.example .env             # renseigner API_TOKEN
npm start                        # http://localhost:3000
\`\`\`

## Tester en 2 minutes
Importer \`postman/LivreAPI.json\` dans Postman -> "Run collection" : tout passe.

## Architecture
routes -> services (logique métier) -> data (SQL paramétré). Schéma : voir \`init.sql\`.
Décisions : voir \`docs/adr/\`.

## Limites connues
Pagination par OFFSET (curseur prévu si volume) ; auth par token simple (jours 67-68).
```
```md
# docs/adr/002-validation-manuelle-vs-librairie.md
## Contexte : valider les entrées de LivreAPI.
## Options : (a) validation à la main (zéro dépendance, explicite) ;
##           (b) librairie (Zod/Joi : concise, schémas réutilisables).
## Décision : validation à la main pour la v1 (apprentissage, peu de champs).
## Point de bascule : passer à une librairie si le nombre de schémas explose.
```
Le README répond dans l'ordre du lecteur, la collection prouve l'API en un clic, l'ADR trace la décision, et le test sur clone frais valide le critère « 5 minutes ».

## ⚠️ Erreurs fréquentes
- Collection non versionnée : la doc vivante disparaît avec le poste de l'auteur.
- README qui suppose un contexte absent (prérequis non dits, chemins codés en dur) : l'inconnu bloque.
- README dans l'ordre de l'auteur et jamais testé sur un clone frais.
- ADR réduit à une phrase, sans point de bascule : la décision paraît subie.

## 🏢 Cas métier
La documentation est ce qui détermine si un projet est ADOPTÉ ou ignoré, en entreprise comme en open-source. Un service interne sans README utilisable coûte du temps à chaque nouvel arrivant et à chaque équipe qui veut l'intégrer ; un projet open-source sans documentation claire n'a pas d'utilisateurs, quel que soit son code. Le critère « opérationnel en 5 minutes » est concret : les projets qui le respectent sont adoptés, les autres non. La collection Postman comme doc vivante et exécutable est une pratique standard pour les API (avec OpenAPI/Swagger), car elle ne peut pas se périmer sans qu'on le remarque. Pour un portfolio, la documentation est décisive : un recruteur qui clone LivreAPI juge d'abord le README (peut-il lancer et tester ?), et une démo de 2 minutes lui prouve le résultat sans installation. Savoir documenter pour un lecteur précis, et s'entraîner à présenter via une démo, sont des compétences de communication technique directement évaluées — et la présentation orale d'un projet est un exercice d'entretien fréquent.

## 🎤 Question d'entretien
**« Comment documentes-tu un projet pour qu'il soit vraiment utilisable par quelqu'un d'autre ? »** → Je vise un critère unique et mesurable : un inconnu peut-il tester l'API en 5 minutes ? Pour ça, mon README répond dans l'ORDRE des questions du lecteur — c'est quoi, comment le lancer (commandes exactes, prérequis), comment le tester (importer la collection Postman), comment c'est construit (l'architecture en couches), et quelles sont les limites connues. J'écris pour le lecteur, pas pour moi. La collection Postman est ma doc VIVANTE : exécutable, versionnée, elle prouve que l'API marche en un clic et ne se périme pas sans qu'on le voie. J'ajoute une démo de 2 minutes (écran + voix) qui prouve le résultat sans que le lecteur installe quoi que ce soit — et qui m'entraîne à présenter. Et je trace les décisions structurantes dans des ADR, par exemple « validation à la main vs librairie », avec le point de bascule. Le test décisif : je clone mon propre dépôt dans un dossier vierge et je suis mes instructions ; si je bloque, un recruteur bloquera. **Relance possible** : « qu'est-ce qui distingue un bon README d'un mauvais ? » → un bon README répond aux questions du lecteur dans son ordre et est testé sur un clone frais ; un mauvais décrit le projet dans l'ordre de l'auteur, suppose un contexte absent, et n'a jamais été vérifié par un tiers.
