## 🎯 Objectif du jour
L'alternative sobre aux agents.

## 📖 Cours approfondi
**Modèle mental : un workflow, c'est un agent dont TU as figé le plan — tu échanges l'autonomie contre la prévisibilité, et c'est presque toujours un bon échange.** Le jour 278 t'a appris à préférer le workflow ; aujourd'hui tu le CONSTRUIS. Un workflow explicite décompose la tâche en étapes FIXES que ton code orchestre ; le LLM fait le travail cognitif DANS chaque étape (classer, extraire, résumer), mais ne décide jamais du FLUX. Le chemin est écrit dans ton code, pas choisi par le modèle à l'exécution.

Ce que tu gagnes en figeant le plan :
1. **La prévisibilité** : le nombre d'appels LLM est CONNU d'avance (une étape = un appel, éventuellement quelques branches) — donc le coût et la latence sont bornés et estimables AVANT de lancer (jour 285). Un agent, lui, décide du nombre de tours à l'exécution.
2. **La fiabilité** : pas de boucle, pas de dérive d'objectif, pas de mauvais choix de flux — les trois modes d'échec des agents (jour 275) DISPARAISSENT car il n'y a plus de décision de flux à mal prendre. Restent seulement les erreurs DANS les étapes (une classification erronée), bien plus faciles à tester et corriger.
3. **La testabilité** : chaque étape a une entrée et une sortie connues → tu peux la tester en isolation (le golden set par étape), et le flux global est déterministe donc reproductible.

Le prix : la flexibilité. Un workflow ne s'adapte pas à un cas imprévu que son plan ne couvre pas — d'où le routage (jour 282) qui ajoute des branches pour les variations PRÉVUES. Mais pour la vaste majorité des tâches (flux connu avec du raisonnement dans les étapes), c'est exactement ce qu'il faut.

L'exercice du jour incarne la doctrine : transformer ton vérificateur de documentation (fait en AGENT au jour 276) en WORKFLOW explicite — étapes fixes : lister → lire chaque doc → extraire les affirmations → comparer par paires → rapporter. Puis COMPARER les deux versions sur coût, latence et fiabilité. Le plus souvent, le workflow gagne sur les trois — et cette comparaison chiffrée est LA preuve qui fonde ta doctrine du jour 278.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : transformer ton vérificateur (agent, jour 276) en workflow explicite, et comparer.

**Exemple simple** : le workflow le plus simple est une CHAÎNE — étape1 puis étape2 puis étape3, chaque sortie nourrit la suivante. Pas de boucle, pas de décision de flux : `rapport = comparer(extraire(lire(lister())))`.

**Raisonnement pas-à-pas** : figer les étapes que l'agent découvrait, orchestrer en code, mesurer coût/latence/fiabilité contre la version agent.

**Implémentation** :
```python
def verificateur_workflow(dossier: str) -> Rapport:
    docs = lister_docs(dossier)                        # étape 1 : déterministe
    affirmations = {}
    for doc in docs:
        affirmations[doc] = extraire_affirmations(lire(doc))  # étape 2 : LLM par doc
    conflits = []
    for a, b in paires(affirmations):                  # étape 3 : comparaison
        conflits += detecter_conflits_llm(a, b)         # LLM par paire
    return rapport(conflits)                            # étape 4 : déterministe
# Nombre d'appels LLM CONNU : len(docs) + C(len(docs), 2) — estimable AVANT
```

**La comparaison (le livrable)** :
```
                    agent (j.276)      workflow (aujourd'hui)
appels LLM          variable (5-15)    connu (docs + paires)
coût                imprévisible       estimable avant
latence             variable           bornée
fiabilité           modes d'échec      pas de dérive/boucle possible
mêmes contradictions trouvées ?         → vérifie : rappel identique ou meilleur ?
```

**Mini-quiz** : (a) Qui décide du flux dans un workflow ? (b) Lesquels des 3 modes d'échec d'agent disparaissent ? (c) Que perd-on en figeant le plan ?
→ (a) TON code (le plan est fixe), le LLM ne fait que le travail cognitif des étapes ; (b) les trois (boucle, dérive, mauvais choix de flux) — il n'y a plus de décision de flux ; (c) la flexibilité face aux cas imprévus non couverts par le plan.

**Variante** : mesure le coût réel des deux versions sur le même dossier de docs — combien d'appels chacune, pour quel résultat ? Le workflow fait-il aussi bien pour moins cher ? C'est la preuve chiffrée de ta doctrine.

## 🏢 Cas métier
La bascule agent → workflow est l'une des optimisations les plus rentables des équipes IA : un système reformulé en workflow explicite devient estimable en coût, testable étape par étape, et débarrassé des comportements erratiques — souvent pour un résultat équivalent ou meilleur. « Nous avons remplacé notre agent par un workflow à étapes fixes : coût divisé par trois, latence prévisible, plus de boucles en production » est un retour d'expérience classique et valorisé. Savoir faire cette transformation, et la CHIFFRER, est une compétence d'optimisation directement utile.

## 🎤 Question d'entretien
**« Qu'est-ce qu'un workflow explicite et quand le préfères-tu à un agent ? »** → Un workflow décompose la tâche en étapes FIXES orchestrées par mon code ; le LLM fait le travail cognitif dans chaque étape mais ne décide jamais du flux. Je le préfère dès que le flux est connu (la vaste majorité des cas) : le coût et la latence deviennent estimables AVANT de lancer, les trois modes d'échec d'agent disparaissent (plus de décision de flux à mal prendre), et chaque étape est testable en isolation. Je perds la flexibilité face aux cas imprévus — que je récupère avec du routage si nécessaire. Souvent, un workflow fait aussi bien qu'un agent pour bien moins cher, et je peux le prouver.
