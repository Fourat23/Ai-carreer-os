## 🎯 Objectif du jour
Faire de Postman un outil de test d'API sérieux : variables d'environnement, tests automatiques, scénarios.

## 📖 Cours approfondi
**Concepts abordés :** Collections structurées · Variables d'environnement · Tests JS dans Postman · Scénarios enchaînés.

Une collection Postman bien construite est trois choses à la fois : une DOCUMENTATION vivante (chaque requête montre l'usage réel), une SUITE DE TESTS (les assertions vérifient statut et forme de réponse à chaque exécution), et un OUTIL DE DÉMO (un recruteur importe, lance, tout passe).

Les variables d'environnement ({{baseUrl}}, {{token}}) rendent la collection portable : même collection en local et en prod. Les tests s'écrivent en JS dans l'onglet Tests : vérifier le statut ne suffit pas — vérifie aussi la FORME du corps (les champs attendus existent, les types sont bons).

Le scénario enchaîné (create → read → update → delete, en passant l'id créé aux requêtes suivantes via les variables) teste un FLUX réel, pas des endpoints isolés.

**Modèle mental : une collection Postman bien construite est TROIS choses à la fois — une DOCUMENTATION vivante (chaque requête montre l'usage réel de l'API), une SUITE DE TESTS (des assertions vérifient statut ET forme de réponse à chaque exécution), et un OUTIL DE DÉMO (un recruteur importe la collection, la lance, tout passe). Les variables d'environnement la rendent portable, et un scénario enchaîné (create → read → update → delete, en passant l'id créé aux requêtes suivantes) teste un FLUX réel, pas des endpoints isolés.** Tester une API, ce n'est pas vérifier des statuts un par un à la main : c'est automatiser un flux réutilisable.

Pourquoi outiller ses tests d'API. Vérifier une API à la main (envoyer une requête, lire la réponse à l'œil) ne passe pas à l'échelle et n'est pas reproductible : on oublie des cas, on ne rejoue pas après chaque changement. Une collection de tests automatisés VÉRIFIE l'API à chaque exécution, documente son usage, et sert de filet contre les régressions. C'est le pont entre « j'ai testé une fois » et « je peux prouver que ça marche, à tout moment ».

Les trois rôles, depuis les fondations. **Documentation vivante** : chaque requête de la collection montre un appel réel (URL, headers, corps), toujours à jour puisqu'exécutable — contrairement à une doc figée qui se périme. **Suite de tests** : dans l'onglet Tests (JavaScript), on écrit des assertions — pas seulement sur le STATUT (200, 201), mais aussi sur la FORME du corps (les champs attendus existent, les types sont bons). **Outil de démo** : la collection exportée et versionnée permet à quiconque (recruteur, collègue) de l'importer et de tout lancer d'un clic.

Les variables d'environnement, depuis les fondations. `{{baseUrl}}`, `{{token}}` rendent la collection PORTABLE : la même collection s'exécute en local (`baseUrl = localhost:3000`) et en prod, en changeant juste l'environnement. Sans variables, on duplique l'URL partout et on ne peut pas basculer d'un environnement à l'autre. C'est le principe « une seule source » appliqué aux tests d'API.

La différence tester le statut seul vs le corps aussi. Vérifier UNIQUEMENT le statut (`200 OK`) est insuffisant : une API peut renvoyer 200 avec un corps vide, malformé ou faux. Un bon test vérifie AUSSI la forme de la réponse — que les champs attendus sont présents, du bon type, avec les bonnes valeurs. C'est la différence entre « l'API a répondu » et « l'API a répondu CORRECTEMENT ».

Le scénario enchaîné, depuis les fondations. Tester des endpoints isolés ne prouve pas qu'un FLUX fonctionne. Un scénario create → read → update → delete enchaîne les requêtes en passant l'id créé (capturé dans une variable) aux suivantes : il teste le cycle de vie réel d'une ressource, comme un utilisateur l'exercerait. C'est un test d'intégration du flux, pas juste des unités.

Limites et compromis. Postman est excellent pour les tests d'API manuels et automatisés à petite/moyenne échelle et pour la démo, mais pour l'intégration continue on préfère souvent du code de test versionné (ou Newman, le runner CLI de Postman). Trop de tests fragiles (couplés à des valeurs exactes changeantes) deviennent un fardeau. Le bon équilibre : tester le contrat (statut + forme + valeurs clés), pas chaque détail volatil.

La règle du jour : **fais de Postman un outil sérieux — variables d'environnement pour la portabilité, tests qui vérifient le STATUT ET la FORME du corps (pas juste le statut), et un scénario enchaîné (CRUD) qui teste un flux réel. Exporte et versionne la collection : c'est à la fois doc vivante, suite de tests et démo.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire un test Postman qui vérifie le statut ET la forme du corps, puis enchaîner un flux create → read en passant l'id.

**Exemple simple** : statut seul vs statut + forme. Un test qui vérifie `status === 201` accepte une réponse 201 au corps vide. Un bon test vérifie aussi que `body.id` existe et que `body.texte` vaut ce qu'on a envoyé — « l'API a répondu CORRECTEMENT », pas juste « a répondu ».

**Raisonnement pas-à-pas** : (1) j'utilise `{{baseUrl}}` pour la portabilité ; (2) au POST, je teste le statut ET la forme, et je CAPTURE l'id créé dans une variable ; (3) au GET suivant, j'utilise cet id ; (4) le scénario complet se rejoue d'un clic.

**Tests Postman (onglet Tests, en JS)** :
```js
// POST {{baseUrl}}/citations  — créer, tester statut ET forme, capturer l'id
pm.test('201 Created', () => pm.response.to.have.status(201));
pm.test('le corps a la bonne forme', () => {
  const body = pm.response.json();
  pm.expect(body).to.have.property('id');               // champ présent
  pm.expect(body.texte).to.eql(pm.variables.get('texteEnvoye')); // bonne valeur
});
// capturer l'id créé pour la requête SUIVANTE (scénario enchaîné)
pm.environment.set('citationId', pm.response.json().id);
```
```js
// GET {{baseUrl}}/citations/{{citationId}}  — lit la ressource créée juste avant
pm.test('200 OK', () => pm.response.to.have.status(200));
pm.test('renvoie la même citation', () => {
  pm.expect(pm.response.json().id).to.eql(Number(pm.environment.get('citationId')));
});
```
Le test vérifie la FORME (pas juste le statut), `{{baseUrl}}` rend la collection portable, et l'id capturé enchaîne create → read en un flux réel — rejouable d'un clic via « Run collection ».

## ⚠️ Erreurs fréquentes
- Ne tester que le statut, pas le corps : on rate un 200 au corps vide, malformé ou faux.
- Collection non exportée/versionnée : ni reproductible ni partageable, elle vit sur une seule machine.
- URLs en dur au lieu de variables d'environnement : impossible de basculer local/prod, duplication.
- Tester des endpoints isolés sans scénario enchaîné : on ne prouve pas qu'un flux réel fonctionne.

## 🏢 Cas métier
Le test d'API outillé est une pratique quotidienne en entreprise, et une collection Postman de qualité est un artefact professionnel à plusieurs titres. Comme documentation vivante, elle permet aux équipes consommatrices (front, mobile, partenaires) de comprendre et d'essayer l'API sans harceler l'équipe back. Comme suite de tests, elle attrape les régressions à chaque modification et peut s'exécuter en intégration continue (via Newman, le runner CLI). Comme outil de démo, elle prouve en direct que l'API fonctionne. Les variables d'environnement permettent de tester local, staging et prod avec la même collection. Pour un portfolio, une collection versionnée qui teste statut ET forme et enchaîne un scénario CRUD complet démontre une rigueur de test que les recruteurs valorisent — bien plus qu'une API « qui marche quand je clique ». Savoir écrire des assertions utiles (pas juste le statut) et penser en flux réels est une compétence de qualité directement transférable au test automatisé en général.
