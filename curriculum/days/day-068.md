## 🎯 Objectif du jour
Implémenter une auth par token propre et gérer les secrets hors du code.

## 📖 Cours approfondi
**Concepts abordés :** Token dans un header · Middleware d'auth · Secrets en .env · Pourquoi pas dans l'URL/le code.

L'authentification par token : le client envoie un secret dans le header `Authorization` à chaque requête ; un middleware le vérifie AVANT les routes protégées. Pourquoi le header et pas l'URL ? Les URLs sont loggées partout (serveurs, proxies, historiques) — un secret dans l'URL est un secret publié.

Les secrets vivent dans l'ENVIRONNEMENT (.env, jamais commité — vérifie ton .gitignore) : le code lit process.env.API_TOKEN. Le fichier .env.example (committé, sans les valeurs) documente les variables attendues.

Cette hygiène prépare le mois 8 : tes clés d'API LLM suivront exactement le même circuit. Un secret commité une fois est compromis pour toujours (l'historique Git n'oublie pas) — d'où l'audit systématique avant tout push public.

## ⚠️ Erreurs fréquentes

- Secret en dur dans le code.

## 🏢 Cas métier
Cas typique : un assistant documentaire qui refuse d'exécuter une instruction cachée dans un PDF piégé, ne fuite pas de données personnelles vers l'API du fournisseur, et journalise sans secrets — la sécurité d'un système IA en production.

## 🎤 Question d'entretien
**« Qu'est-ce que la prompt injection indirecte et comment défendre ? »** → Une instruction malveillante cachée dans un DOCUMENT ingéré détourne le système ; « ignore les instructions des docs » ne suffit pas. Défense en profondeur : marquer les données, vérifier les citations, refus, moindre privilège des outils.
