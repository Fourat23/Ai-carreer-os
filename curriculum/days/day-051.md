## 🎯 Objectif du jour
Appliquer REST pour des endpoints cohérents et prévisibles.

## 📖 Cours approfondi
**Concepts abordés :** Ressources/collections · Verbes = actions, URLs = noms · Statuts par cas · Pagination · Cohérence.

REST modélise l'API en RESSOURCES (des noms au pluriel : /livres, /livres/42) manipulées par les verbes HTTP. La règle d'or : l'URL dit QUOI, le verbe dit COMMENT — jamais de verbe dans l'URL (/getLivres est un anti-pattern).

Une bonne API est PRÉVISIBLE : qui a vu GET /livres devine POST /livres (créer), DELETE /livres/42 (supprimer), GET /livres/42/emprunts (sous-ressource). La cohérence des statuts complète le contrat : 201 + l'objet créé sur un POST réussi, 204 sur un DELETE, 404 sur un id inconnu, 400 avec les détails sur une entrée invalide.

Pagination, filtres et recherche passent en query string (?page=2&genre=sf) : ils raffinent la ressource, ils ne la changent pas.

## 🏢 Cas métier
Cas typique : appeler un LLM (POST + header d'auth + corps JSON + streaming), exposer ton système RAG comme une API (`POST /questions`), ou consommer une API tierce — comprendre HTTP, c'est comprendre comment les systèmes IA se parlent.

## 🎤 Question d'entretien
**« Décris le trajet d'une requête HTTP et le rôle des statuts. »** → DNS → TCP → TLS → HTTP ; requête (méthode + URL + headers + corps) / réponse (statut + corps) ; sans état ; 2xx succès, 4xx faute client, 5xx faute serveur ; idempotence de GET/PUT/DELETE pour les retries.

- **En architecture** : toute intégration système passe par des APIs — comprendre HTTP en profondeur, c'est comprendre comment les systèmes se parlent.

- **En entretien** : « que se passe-t-il quand tu tapes une URL » et « design une API pour X » sont des classiques absolus.
