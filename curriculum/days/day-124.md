## 📖 Cours approfondi
**Modèle mental : pytest fait du test une simple FONCTION qui commence par `test_` et contient un `assert` — pas de framework verbeux ni de classes obligatoires ; sa valeur se prouve, comme tout test, en le faisant ROUGIR, et les FIXTURES fournissent un contexte réutilisable sans dupliquer le setup.** Tu connais les principes du test (jour 106, en JS) : figer un comportement, couvrir les cas limites, prouver qu'un test peut échouer. pytest est l'outil qui rend cela minimal et agréable en Python — au point que l'absence de cérémonie est sa force.

Ce qui rend pytest distinctif :
1. **La simplicité radicale** : une fonction `def test_ajoute_une_note():` avec un `assert resultat == attendu`. pytest DÉCOUVRE automatiquement les fichiers `test_*.py` et les fonctions `test_*`. Pas de `expect().toBe()` — juste `assert`, et pytest affiche intelligemment pourquoi l'assertion a échoué (les valeurs comparées).
2. **Les fixtures** : une fonction décorée `@pytest.fixture` qui prépare un contexte (des données, un fichier temporaire, une base en mémoire) et le fournit aux tests qui la demandent en PARAMÈTRE. C'est l'injection de dépendances du test : le setup est écrit UNE fois et réutilisé, sans le dupliquer dans chaque test. `tmp_path` (fixture intégrée) donne un dossier temporaire propre par test.
3. **La paramétrisation** : `@pytest.mark.parametrize` exécute le MÊME test sur plusieurs jeux d'entrées/sorties — une table de cas plutôt que dix fonctions copiées. Idéal pour couvrir les cas limites d'une fonction de validation.
4. **Le rougissement, toujours** : le principe du jour 106 reste vrai — un test qui ne peut pas échouer ne teste rien. On sabote le code pour vérifier que le test rougit.

La règle du jour : **écris des tests `test_*` minimalistes avec `assert`, factorise le setup en fixtures, couvre les cas limites par paramétrisation, et prouve chaque test en le faisant rougir**. pytest récompense le test parce qu'il est sans friction — et une suite verte sur ta CLI et tes fonctions est ce qui te permet de refactorer ton Python en confiance, exactement comme au front.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : installer pytest, écrire 10+ tests sur la CLI `notes` et ses fonctions, prouver le rougissement.

**Exemple simple** : le test pytest minimal — `def test_ajoute_incremente_id():\n    assert ajouter([], "a")[0]["id"] == 1`. Une fonction `test_`, un `assert`. pytest la découvre et l'exécute sans configuration.

**Raisonnement pas-à-pas** : tester la logique métier pure (facile, sans I/O) → utiliser une fixture `tmp_path` pour tester le stockage sans polluer le disque → paramétrer les cas limites → saboter pour prouver le rougissement.

**Implémentation** :
```python
import json, pytest
from notes.metier import ajouter, chercher
from notes.stockage import charger, sauver

# 1. Logique pure — cas normaux et limites
def test_ajoute_incremente_id():
    assert ajouter([], "a")[0]["id"] == 1

@pytest.mark.parametrize("mot, attendu", [   # une table de cas, pas 3 fonctions
    ("react", 1), ("REACT", 1), ("zzz", 0),
])
def test_cherche_insensible_casse(mot, attendu):
    notes = [{"id": 1, "texte": "React"}]
    assert len(chercher(notes, mot)) == attendu

# 2. Stockage — fixture tmp_path : dossier temporaire propre par test
def test_sauver_puis_charger(tmp_path):
    fichier = tmp_path / "notes.json"
    sauver(fichier, [{"id": 1, "texte": "a"}])
    assert charger(fichier) == [{"id": 1, "texte": "a"}]   # aller-retour

def test_charger_fichier_absent(tmp_path):
    assert charger(tmp_path / "absent.json") == []          # cas prévu (jour 122)
# PREUVE : change `len(notes) + 1` en `len(notes)` dans ajouter → test_ajoute rougit.
```

**Mini-quiz** : (a) Comment pytest sait-il quelles fonctions sont des tests ? (b) À quoi sert la fixture `tmp_path` ? (c) Que fait `@pytest.mark.parametrize` ?
→ (a) il découvre les fichiers `test_*.py` et les fonctions `test_*` automatiquement ; (b) fournir un dossier temporaire propre par test, pour tester l'I/O sans polluer le disque ; (c) exécuter le même test sur plusieurs jeux d'entrées/sorties (table de cas).

**Variante** : écris une fixture personnalisée `@pytest.fixture` qui renvoie un jeu de notes de départ, et réutilise-la dans plusieurs tests — tu factorises le setup au lieu de le recopier dans chaque fonction.

## ⚠️ Erreurs fréquentes
- Tester en écrivant/lisant de vrais fichiers du projet : tests non déterministes et polluants — utiliser `tmp_path`.
- Dupliquer le même setup dans chaque test au lieu d'une fixture : maintenance lourde.
- Copier dix fonctions pour dix cas au lieu de `parametrize` : bruit et oublis.
- Ne pas vérifier le rougissement : une suite verte qui ne peut pas échouer donne un faux sentiment de sécurité.

## 🏢 Cas métier
pytest est le standard de fait des tests Python en entreprise, précisément parce que sa simplicité (fonction + `assert`) supprime la friction qui décourage d'écrire des tests. Les fixtures permettent de tester du code qui touche des fichiers, des bases ou des API sans dupliquer le setup ni polluer l'environnement — `tmp_path` pour un fichier jetable, une fixture de base en mémoire pour un test d'intégration. Dans les projets data, une suite pytest verte est ce qui permet de refactorer un pipeline sans craindre de casser une transformation silencieusement. Une suite de tests bien faite est directement lisible dans un repo et signale un développeur qui livre du code fiable — un critère que les recruteurs et les équipes vérifient systématiquement.

## 🎤 Question d'entretien
**« Comment testes-tu en Python avec pytest ? »** → Un test est une fonction `test_*` avec un simple `assert` ; pytest découvre automatiquement les fichiers et fonctions de test, et affiche intelligemment pourquoi une assertion échoue. Pour le code qui touche l'I/O, j'utilise des FIXTURES — des fonctions `@pytest.fixture` qui préparent un contexte réutilisable (par exemple `tmp_path` pour un fichier temporaire propre par test), demandées en paramètre : le setup est écrit une fois, pas dupliqué. Pour couvrir les cas limites, je paramètre avec `@pytest.mark.parametrize` — une table de cas plutôt que dix fonctions copiées. Et comme tout test, la valeur se prouve en le faisant rougir : je sabote le code pour vérifier que le test échoue. Une suite verte me permet de refactorer en confiance.
