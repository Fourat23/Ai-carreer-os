## 🔁 Revue hebdomadaire

**Thème de la semaine :** REST design, Node.js, premiers serveurs, Express

### Bilan
Tu passes de consommateur d'API à producteur. D'abord le module http natif (pour comprendre), puis Express (pour produire).

### Test pratique
75 min : serveur Express avec routes GET /livres, GET /livres/:id, POST /livres (validation titre requis), DELETE /livres/:id — données en mémoire, statuts corrects, testé via Postman.

### Test théorique
Les 6 contraintes REST (au moins 4 de tête) ; pourquoi GET ne doit pas modifier l'état ; qu'est-ce qu'un middleware Express ; où mettre la validation ; que renvoyer sur un POST réussi ?

### Mini-projet / livrable

### Exercice de réflexion architecturale

### Synthèse de la semaine
La semaine 10 a porté LivreAPI de « socle qui marche » à « projet crédible et sécurisé ». Recherche, pagination et filtres (jour 64) : raffiner une collection en query string, avec le piège d'OFFSET (curseur sur gros volume) et le % de LIKE sur la valeur paramétrée. Tests d'intégration (jour 65) : vérifier le système assemblé (HTTP → service → base) sur une base de test isolée, pour attraper les bugs de câblage que l'unitaire ne voit pas. Documentation (jour 66) : le critère « un inconnu teste en 5 minutes », README dans l'ordre du lecteur, collection comme doc vivante, démo enregistrée, ADR. Sécurité OWASP (jour 67) : la sécurité comme propriété à vérifier partout, PROUVÉE en attaquant son propre système (injection, auth, exposition, config). Auth par token et secrets (jour 68) : token dans le header (jamais l'URL), middleware de vérification, secrets en .env gitignored. Refactoring (jour 69) : améliorer la structure sans changer le comportement, garanti par des tests écrits avant, par petites étapes. Le fil rouge : **un projet crédible n'est pas seulement fonctionnel — il est testé (câblage vérifié), documenté (utilisable par un inconnu), sécurisé (attaqué par son auteur) et maintenable (refactorable sous filet).** LivreAPI est désormais une vraie 2e pièce de portfolio.

### Plan de remédiation (si un critère échoue)
- **OFFSET coûteux / SQL concaténé dans la recherche** : rejoue le jour 64 — % de LIKE sur la valeur paramétrée, curseur sur gros volume, filtres présents seulement.
- **Tests superficiels / sur base de dev** : jour 65 — base de test isolée réinitialisée, vérifier réponse ET état, cibler les règles métier (409) et cas d'erreur.
- **Doc inutilisable** : jour 66 — critère « 5 minutes » testé sur clone frais, README dans l'ordre du lecteur, collection vivante, ADR avec point de bascule.
- **Sécurité supposée, non prouvée** : jour 67 — attaque tes propres API (4 familles OWASP), corrige de vraies failles, ajoute un rate limiting.
- **Token dans l'URL / secret en dur** : jour 68 — token dans le header, middleware avant les routes protégées, secrets en .env gitignored, audit de l'historique Git.
- **Refactor à l'aveugle / big-bang** : jour 69 — tests écrits AVANT, petites étapes committables, dette documentée.

### Questions d'entretien de la semaine
1. **« Comment paginerais-tu un million de lignes ? »** Attendu : piège d'OFFSET (lit et jette), pagination par curseur (WHERE id > dernierIdVu), index ; LIKE non indexable → full-text.
2. **« Différence entre test unitaire et test d'intégration ? »** Attendu : isolé (logique) vs assemblé (câblage, HTTP → base) ; base de test isolée, cibler les règles métier.
3. **« Qu'est-ce qui rend un projet utilisable par un inconnu ? »** Attendu : critère « 5 minutes », README dans l'ordre du lecteur, collection vivante, démo, ADR ; testé sur clone frais.
4. **« Comment sécurises-tu une API ? »** Attendu : sécurité comme propriété vérifiée partout, attaquer son propre système, 4 familles OWASP, rate limiting.
5. **« Comment refactores-tu sans casser, et où mets-tu tes secrets ? »** Attendu : tests d'abord + petites étapes + dette documentée ; token dans le header, secrets en .env hors du code.
