**Concepts abordés :** Full-stack assemblé · CRUD complet UI · États edge · Le flux complet compris.

Le full-stack assemblé est le moment de vérité : peux-tu suivre UNE donnée sur tout le trajet ? Clic « ajouter » → événement React → validation → fetch POST → route Express → service (règle métier) → requête SQL paramétrée → réponse 201 → mise à jour immuable du state → re-render. Si un maillon reste flou, c'est LÀ que tu dois creuser — la magie est interdite.

Les états EDGE font la différence : la liste vide (un message utile, pas une page blanche), l'erreur réseau (un message + possibilité de réessayer), le chargement (un indicateur). Un utilisateur passe 5% du temps dans ces états, mais c'est là que se joue la perception de qualité.

Pourquoi le full-stack assemblé est le moment de vérité. Chaque couche a été apprise séparément (React, fetch, Express, services, SQL) ; les ASSEMBLER teste si tu comprends vraiment comment elles s'articulent. Le critère : peux-tu tracer une donnée du clic jusqu'à la base et retour, en nommant chaque maillon ? Si oui, tu as une compréhension RÉELLE et non magique de ton système. Si un maillon est flou (« ça marche mais je ne sais pas comment »), c'est le signal exact d'où creuser. La magie interdite, c'est le refus de l'acceptation passive.

Le trajet complet d'une donnée, depuis les fondations. Suivre un clic « ajouter un livre » : (1) l'utilisateur clique → (2) un événement React déclenche un handler → (3) validation côté front → (4) `fetch` POST via api.ts → (5) la route Express reçoit → (6) le service applique la règle métier → (7) la couche data fait un INSERT paramétré → (8) la base répond → (9) la route renvoie 201 + l'objet → (10) le front met à jour le state de façon IMMUABLE → (11) React re-rend la liste. Onze maillons, chacun une compétence des trois mois. Savoir les nommer, c'est posséder son système.

Les états edge, depuis les fondations. Un utilisateur passe ~5 % de son temps dans les états « edge » (limites), mais leur soin fait 50 % de la qualité perçue. La liste VIDE : afficher « Aucun livre, ajoutez-en un » plutôt qu'une page blanche déroutante. L'ERREUR réseau : un message clair + un bouton réessayer, pas un plantage silencieux. Le CHARGEMENT : un indicateur, pas un gel. Une app qui néglige ces états paraît cassée ; une app qui les soigne paraît finie et professionnelle.

La différence « ça marche » vs « je comprends ». Un full-stack qui « marche » sans qu'on sache pourquoi est fragile : au premier bug, on est perdu. Un full-stack qu'on COMPREND à chaque couche est débogable, modifiable, et défendable en entretien. Le CRUD complet de bout en bout (liste, détail, ajout, édition, suppression, recherche) exerce tous les maillons et prouve la compréhension.

La valeur de preuve, depuis les fondations. Un mini full-stack qui tourne de bout en bout, que tu comprends à chaque couche, est la PREUVE CONCRÈTE de tes trois premiers mois : tu construis, sécurises, testes, documentes et CONNECTES une application complète. Limites et compromis. Un mini full-stack local n'est pas déployé (le déploiement viendra) ni au niveau portfolio (le Projet 3 le fera) — mais il SOUDE les acquis. Soigner tous les états edge prend du temps, justifié par la qualité perçue. Et « comprendre chaque couche » est un idéal — l'important est de ne laisser AUCUN maillon en « magie » sur son propre système.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : tracer le trajet complet d'un ajout de livre à travers le full-stack, et soigner les états edge.

**Exemple simple** : un état edge soigné. Liste vide → « Aucun livre pour l'instant, ajoutez-en un ! » (utile) plutôt qu'une page blanche (déroutante). L'utilisateur comprend l'état au lieu de croire à un bug.

**Raisonnement pas-à-pas** : (1) je trace le clic jusqu'à la base et retour, en nommant chaque maillon ; (2) je m'assure qu'aucun maillon n'est « magique » ; (3) je soigne les trois états edge (vide, erreur, chargement) ; (4) je vérifie le CRUD complet de bout en bout.

**Le trajet complet (annoté) + états edge** :
```tsx
function AjoutLivre({ onAjoute }: { onAjoute: (l: Livre) => void }) {
  const [erreur, setErreur] = useState<string | null>(null);
  async function soumettre(titre: string) {
    if (!titre.trim()) return setErreur('titre requis');   // (3) validation FRONT
    try {
      const cree = await api.creerLivre(titre);            // (4) fetch POST via api.ts
      //   -> (5) route Express -> (6) service (règle) -> (7) INSERT paramétré
      //   -> (8) base -> (9) réponse 201 + objet
      onAjoute(cree);                                       // (10) MAJ immuable du state (parent)
      setErreur(null);                                       // (11) React re-rend la liste
    } catch (e) {
      setErreur('réseau indisponible, réessayez');          // état EDGE : erreur AFFICHÉE
    }
  }
  return <form>{/* ... */}{erreur && <p className="err">{erreur}</p>}</form>;
}

function Liste({ livres, loading }: { livres: Livre[]; loading: boolean }) {
  if (loading) return <p>Chargement…</p>;                    // état EDGE : chargement
  if (livres.length === 0) return <p>Aucun livre, ajoutez-en un !</p>;  // état EDGE : vide (pas de page blanche)
  return <ul>{livres.map(l => <li key={l.id}>{l.titre}</li>)}</ul>;    // état DATA
}
```
Chaque maillon du trajet est nommé (clic → validation → fetch → route → service → SQL → réponse → state immuable → re-render), aucun n'est « magique », et les trois états edge (vide, erreur, chargement) sont soignés — ce qui transforme une démo fragile en une app qui paraît finie et qu'on comprend de bout en bout.

## 🎤 Question d'entretien
**« Explique-moi ce qui se passe, techniquement, quand un utilisateur ajoute un livre dans ton app full-stack. »** → Je peux tracer toute la donnée sur son trajet, sans aucun maillon magique. L'utilisateur clique « ajouter » : ça déclenche un événement React qui appelle mon handler. Je valide d'abord côté front (titre non vide). Puis j'appelle l'API via mon module `api.ts` : un `fetch` POST. Côté back, la route Express reçoit la requête, le service applique la règle métier, et la couche data fait un INSERT paramétré dans SQLite. La base répond, la route renvoie 201 avec l'objet créé (qui contient l'id généré). De retour côté front, je mets à jour le state de façon IMMUABLE — une nouvelle liste avec le livre ajouté — ce qui fait re-rendre React, et le nouveau livre apparaît. C'est onze maillons, chacun une compétence de mes trois mois, et je sais nommer chacun : c'est ça, comprendre son système plutôt que subir de la magie. Je soigne aussi les états edge — liste vide avec un message utile, erreur réseau affichée avec un bouton réessayer, indicateur de chargement — parce que c'est ce qui fait qu'une app paraît finie. **Relance possible** : « et si le livre n'apparaît pas après l'ajout ? » → je remonte le trajet maillon par maillon : la réponse 201 est-elle arrivée (onglet réseau) ? ai-je bien fait une mise à jour IMMUABLE du state (une mutation ne re-rendrait pas) ? — le fait de connaître chaque maillon rend le débogage systématique au lieu d'aléatoire.
