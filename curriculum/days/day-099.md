## 🎯 Objectif du jour
Naviguer entre plusieurs vues.

## 📖 Cours approfondi
**Modèle mental : l'URL est un ÉTAT — partageable, bookmarkable, et piloté par le bouton retour du navigateur. Le routing mappe cet état-URL à l'arbre de composants affiché.** Sans routing, ton app est un seul écran dont l'état vit uniquement en mémoire : impossible de partager un lien vers « la fiche du livre 42 », le bouton retour quitte le site, et rafraîchir remet tout à zéro. Le routing règle cela en faisant de l'URL la source de vérité de « quelle vue est affichée ».

Les notions clés d'un routeur (React Router) :
1. **Les routes** : une correspondance entre un motif d'URL et un composant. `/livres` → `<Liste/>`, `/livres/:id` → `<Detail/>`, `*` → `<PageIntrouvable/>`. Le routeur regarde l'URL et rend le composant correspondant.
2. **Les paramètres d'URL** : `:id` est une variable lue par le composant (`useParams`). L'URL `/livres/42` transporte l'identifiant : la fiche sait quel livre charger à partir de l'URL, pas d'un state interne. L'URL EST le paramètre.
3. **La navigation** : un `<Link to="/livres/42">` (pas un `<a href>` qui rechargerait la page et perdrait le state) ; une navigation programmatique (`useNavigate`) après une action (« créer » → aller vers la fiche créée).
4. **Le 404** : une route attrape-tout (`*`) pour les URL inconnues — une app pro ne montre jamais un écran blanc sur une mauvaise URL.

La règle du jour : **une vue navigable a une URL, et cette URL suffit à la reconstruire**. Le test : si je copie l'URL d'une fiche et l'ouvre dans un onglet neuf, je dois retomber sur la même fiche. Si oui, ton état de navigation est bien dans l'URL ; sinon, il est piégé en mémoire et l'app n'est pas vraiment navigable. C'est le même principe que côté API (mois 3) : une ressource a une adresse stable.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : ajouter le routing (liste / détail / édition + 404) à ton app, avec des URL propres.

**Exemple simple** : une route paramétrée et sa lecture — `<Route path="/livres/:id" element={<Detail/>} />`, et dans Detail : `const { id } = useParams()`. L'URL transporte l'identifiant ; le composant le lit. C'est tout le principe.

**Raisonnement pas-à-pas** : déclarer les routes (dont le 404) → naviguer avec Link → lire les paramètres avec useParams → charger la ressource à partir de l'URL.

**Solution** :
```tsx
function App() {
  return (
    <BrowserRouter>
      <nav><Link to="/livres">Livres</Link></nav>
      <Routes>
        <Route path="/livres" element={<Liste />} />
        <Route path="/livres/:id" element={<Detail />} />
        <Route path="/livres/:id/edit" element={<Edition />} />
        <Route path="*" element={<PageIntrouvable />} />   {/* 404 : jamais d'écran blanc */}
      </Routes>
    </BrowserRouter>
  );
}

function Detail() {
  const { id } = useParams();                             // l'URL transporte l'id
  const [livre, setLivre] = useState<Livre | null>(null);
  useEffect(() => { api.getLivre(Number(id)).then(setLivre); }, [id]); // recharge si l'id change
  if (!livre) return <Spinner />;
  return <><h1>{livre.titre}</h1><Link to={`/livres/${id}/edit`}>Éditer</Link></>;
}
```

**Mini-quiz** : (a) Pourquoi `<Link>` et pas `<a href>` ? (b) Où le composant Detail lit-il l'id du livre ? (c) Que se passe-t-il sur une URL inconnue sans route `*` ?
→ (a) `<a>` recharge la page et perd tout le state ; `<Link>` change l'URL côté client sans rechargement ; (b) dans l'URL, via `useParams` — pas dans un state interne ; (c) écran blanc — d'où la route attrape-tout qui affiche un 404 propre.

**Variante** : ajoute `useNavigate` pour rediriger vers la fiche après une création (`navigate('/livres/' + nouvel.id)`) — la navigation programmatique après une action, indispensable au CRUD (jour 114).

## 🏢 Cas métier
Le routing est ce qui transforme une « page unique » en application : des URL partageables (un collègue vous envoie le lien exact d'une fiche), un bouton retour qui marche, un rafraîchissement qui retombe au bon endroit. Les apps qui gardent l'état de navigation en mémoire au lieu de l'URL frustrent les utilisateurs (impossible de partager un lien, retour qui quitte le site) et posent des problèmes de référencement. Savoir mettre l'état navigable dans l'URL — et gérer le 404 — est un attendu de base de toute SPA professionnelle, et le principe « une ressource, une URL stable » fait écho au design d'API que tu connais déjà.

## 🎤 Question d'entretien
**« Pourquoi mettre l'état de navigation dans l'URL plutôt qu'en mémoire ? »** → Parce que l'URL est un état PARTAGEABLE et bookmarkable, piloté par le bouton retour du navigateur. Si l'état de navigation vit seulement en mémoire, on ne peut pas partager un lien vers une vue précise, le bouton retour quitte le site, et rafraîchir remet tout à zéro. Avec le routing, l'URL est la source de vérité de la vue affichée : `/livres/42` suffit à reconstruire la fiche du livre 42 (lue via les paramètres d'URL). Le test : copier l'URL dans un onglet neuf doit retomber sur la même vue. J'utilise `<Link>` (pas `<a>` qui recharge) et une route attrape-tout pour un 404 propre.
