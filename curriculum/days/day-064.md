## 🎯 Objectif du jour
Ajouter recherche, pagination et filtres à LivreAPI.

## 📖 Cours approfondi
**Concepts abordés :** Recherche (LIKE) · Pagination (LIMIT/OFFSET) · Filtres combinés · Performance.

La recherche s'implémente avec LIKE (`WHERE titre LIKE '%terme%'`) — attention à la casse selon le moteur, et toujours en requête paramétrée (le % se concatène à la VALEUR, pas au SQL).

La pagination standard : LIMIT (taille de page) + OFFSET (décalage). Sa limite cachée : OFFSET 100000 force le moteur à LIRE et jeter 100 000 lignes — sur de gros volumes, on pagine par CURSEUR (WHERE id > dernierIdVu LIMIT 20). Connaître cette limite est une question d'entretien classique.

Les filtres combinables reprennent ton pattern du jour 23 côté SQL : chaque filtre absent ne contraint pas la requête. Et les colonnes cherchées/filtrées fréquemment méritent leur index (jour 58) — mesure avant/après pour le prouver.

**Modèle mental : recherche, pagination et filtres RAFFINENT une collection sans la changer — ils passent tous en query string sur un GET. La recherche se fait avec `LIKE` (le `%` se concatène à la VALEUR paramétrée, jamais au SQL). La pagination standard `LIMIT`/`OFFSET` cache un PIÈGE de performance : `OFFSET 100000` force le moteur à LIRE et JETER 100 000 lignes — sur gros volume, on pagine par CURSEUR (`WHERE id > dernierIdVu LIMIT 20`). Les filtres combinables reprennent le pattern « critère absent = ne contraint pas ».** Ajouter ces capacités, c'est rendre l'API utilisable à l'échelle tout en connaissant les limites de chaque technique.

La recherche avec LIKE, depuis les fondations. `WHERE titre LIKE ?` avec la valeur `%terme%` cherche « contient terme ». Deux points d'attention : la SENSIBILITÉ À LA CASSE dépend du moteur (SQLite est insensible pour l'ASCII par défaut sur `LIKE`, à documenter) ; et le `%` doit être ajouté à la VALEUR passée en paramètre (`'%' + terme + '%'`), PAS concaténé dans la chaîne SQL — sinon on rouvre la porte à l'injection (jour 57).

La pagination et son piège, depuis les fondations. `LIMIT n OFFSET m` renvoie n lignes après en avoir sauté m. Le problème : pour atteindre `OFFSET 100000`, le moteur doit PARCOURIR et jeter les 100 000 premières lignes à chaque requête — le coût croît avec le numéro de page. C'est acceptable sur de petits volumes, catastrophique sur de gros. La parade est la pagination par CURSEUR : au lieu d'un décalage, on garde le dernier id vu et on demande `WHERE id > dernierIdVu ORDER BY id LIMIT 20` — coût constant, car un index sur `id` permet de sauter directement. Connaître cette limite d'OFFSET est une question d'entretien classique.

Les filtres combinables, depuis les fondations. Chaque filtre (`?disponible=1&genre=sf`) est une condition ; un filtre ABSENT ne doit rien contraindre (jour 46, côté SQL cette fois). On construit dynamiquement le `WHERE` en n'ajoutant que les conditions fournies, chacune paramétrée. Le piège falsy resurgit : `disponible=0` est un filtre légitime, il faut tester la PRÉSENCE du paramètre, pas sa véracité.

La performance et les index. Une recherche/un tri sur une colonne sans index force un parcours complet. Ajouter un index sur les colonnes RÉELLEMENT recherchées/triées (titre, auteur_id) accélère les lectures — mais chaque index a un coût en écriture (jour 58), donc on le justifie par une mesure, pas par réflexe.

Limites et compromis. OFFSET est simple mais ne passe pas l'échelle (curseur pour les gros volumes, mais le curseur complique le « sauter à la page N »). LIKE `%terme%` avec joker en tête ne peut pas utiliser un index classique (recherche plein texte dédiée pour aller plus loin). Les filtres dynamiques doivent rester paramétrés — construire du SQL par concaténation pour « aller vite » rouvre l'injection.

La règle du jour : **recherche (`LIKE` avec le `%` sur la valeur paramétrée, casse documentée), pagination (`LIMIT/OFFSET` simple mais coûteux en profondeur → curseur sur gros volume), filtres combinables (critère absent = ne contraint pas, tester la présence), et index justifiés par une mesure. Tout raffine la collection en query string, sans jamais concaténer de SQL.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : implémenter `GET /livres?recherche=...&genre=...&page=...` avec recherche LIKE paramétrée, filtres combinables et pagination — puis comprendre le piège d'OFFSET.

**Exemple simple** : le piège d'OFFSET. `LIMIT 20 OFFSET 20` (page 2) est rapide ; `LIMIT 20 OFFSET 100000` (page 5000) force le moteur à lire et jeter 100 000 lignes. Même requête, coût très différent selon la profondeur — d'où le curseur sur gros volume.

**Raisonnement pas-à-pas** : (1) je construis le WHERE dynamiquement, en n'ajoutant que les filtres FOURNIS, chacun paramétré ; (2) la recherche ajoute une condition LIKE avec le `%` sur la VALEUR ; (3) la pagination ajoute LIMIT/OFFSET ; (4) je note la limite d'OFFSET et l'alternative curseur.

**Implémentation** :
```ts
function chercherLivres(opts: { recherche?: string; genre?: string; page?: number }) {
  const conditions: string[] = [];
  const params: unknown[] = [];

  if (opts.recherche !== undefined) {            // filtre PRÉSENT (pas de piège falsy)
    conditions.push('titre LIKE ?');
    params.push('%' + opts.recherche + '%');     // le % sur la VALEUR, jamais dans le SQL
  }
  if (opts.genre !== undefined) {
    conditions.push('genre = ?');
    params.push(opts.genre);
  }
  const where = conditions.length ? 'WHERE ' + conditions.join(' AND ') : '';

  const taille = 20;
  const offset = ((opts.page ?? 1) - 1) * taille;
  const sql = `SELECT * FROM livres ${where} ORDER BY id LIMIT ? OFFSET ?`;
  return db.prepare(sql).all(...params, taille, offset);
}

// PIÈGE OFFSET : à la page 5000, OFFSET 100000 lit et jette 100 000 lignes.
// Alternative CURSEUR (coût constant grâce à l'index sur id) :
function pageParCurseur(dernierIdVu: number) {
  return db.prepare('SELECT * FROM livres WHERE id > ? ORDER BY id LIMIT 20').all(dernierIdVu);
}
```
Les filtres ne contraignent que s'ils sont fournis (paramétrés), la recherche met le `%` sur la valeur, et la pagination par curseur reste rapide en profondeur là où OFFSET s'écroule. Un index sur `titre` justifié par une mesure accélère la recherche.

## ⚠️ Erreurs fréquentes
- Concaténer le terme de recherche dans le SQL (au lieu du % sur la valeur paramétrée) : faille d'injection.
- Ignorer le coût d'OFFSET en profondeur : l'API s'écroule sur les grandes pages/volumes.
- Piège falsy sur un filtre (disponible=0 confondu avec pas de filtre) : tester la présence, pas la véracité.
- Recherche/tri sans index sur gros volume : parcours complet lent.

## 🏢 Cas métier
Recherche, pagination et filtres sont des fonctionnalités que TOUTE application à données non triviales doit fournir — liste de produits, résultats de recherche, historique, catalogue. Le piège d'OFFSET est un problème de performance très réel : de nombreuses applications ralentissent dramatiquement sur les pages profondes ou les grands ensembles, et la migration vers une pagination par curseur (utilisée par les grandes API comme celles de réseaux sociaux, sous forme de « cursor »/« next token ») est une optimisation classique en production. La recherche LIKE avec joker en tête qui ne peut pas utiliser d'index mène, à l'échelle, à adopter une recherche plein texte dédiée. Et construire des filtres dynamiques SANS concaténer de SQL (donc en paramétré) est une exigence de sécurité constante. Savoir implémenter ces capacités ET connaître leurs limites (OFFSET coûteux, LIKE non indexable, index à mesurer) démontre qu'on pense performance et sécurité, pas seulement fonctionnalité — exactement ce qu'un entretien back explore avec « comment paginerais-tu un million de lignes ? ».

## 🎤 Question d'entretien
**« Comment implémentes-tu la pagination d'une API, et quelle est la limite de LIMIT/OFFSET ? »** → La pagination standard est `LIMIT n OFFSET m` : renvoyer n lignes après en avoir sauté m. Elle est simple et correcte sur de petits volumes, mais elle cache un piège : pour atteindre `OFFSET 100000`, le moteur doit PARCOURIR et jeter les 100 000 premières lignes à chaque requête — le coût croît avec la profondeur de la page. Sur de gros volumes, je passe à une pagination par CURSEUR : au lieu d'un décalage, je garde le dernier id vu et je demande `WHERE id > dernierIdVu ORDER BY id LIMIT 20` ; grâce à l'index sur `id`, le moteur saute directement, à coût constant. Le compromis du curseur : on perd le « sauter à la page N » arbitraire, mais on gagne la scalabilité (c'est ce qu'utilisent les grandes API, sous forme de next token). Pour la recherche, j'utilise `LIKE` en mettant le `%` sur la VALEUR paramétrée (jamais dans le SQL, sinon injection), et je documente la sensibilité à la casse selon le moteur. Les filtres combinables n'ajoutent au WHERE que les critères fournis, chacun paramétré, en testant leur présence pour éviter le piège falsy. **Relance possible** : « et la recherche `LIKE '%terme%'` à grande échelle ? » → le joker en tête empêche d'utiliser un index classique, donc à l'échelle je passerais à une recherche plein texte dédiée (index full-text).
