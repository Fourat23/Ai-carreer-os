## 🎯 Objectif du jour

## 📖 Cours approfondi
**Modèle mental : une décision d'architecture non écrite est une dette — l'ARCHITECTURE.md et les ADR figent le COMMENT et le POURQUOI de DocSense avant de coder, pour que les choix soient délibérés et défendables.** Après la SPEC (le quoi), tu conçois le comment : un schéma d'architecture (C4) qui montre les composants et les flux de données, et des ADR (Architecture Decision Records) qui figent les 4 décisions structurantes — stockage vectoriel, modèle LLM, stratégie de chunking, approche d'évaluation. Concevoir avant de coder évite de découvrir à mi-parcours qu'un choix implicite bloque tout.

Les deux livrables et leur rôle :
1. **ARCHITECTURE.md avec un schéma C4** : le C4 est une façon de dessiner une architecture à plusieurs niveaux de zoom (Contexte : DocSense et ses acteurs ; Conteneurs : l'app, la vector DB, l'API LLM ; Composants : ingestion, retrieval, génération, évaluation). Le schéma montre les FLUX DE DONNÉES — comment un document entre, est chunké, indexé, et comment une question devient une réponse citée. C'est la carte qui permet de raisonner sur le système AVANT de le construire, et de le présenter en entretien (jour 341).
2. **4 ADR** : chaque décision structurante devient une ADR — contexte, options considérées, décision, conséquences (positives ET négatives), conditions de révision. Tu en as déjà pratiqué (ADR-006, jour 230). Les 4 de DocSense : stockage vectoriel (Chroma vs pgvector vs autre), modèle LLM (fournisseur, taille, coût), chunking (fixe vs structurel, la config du mois 9), évaluation (golden set + métriques). Chaque ADR PROUVE que tu as arbitré, pas choisi par défaut.

Pourquoi c'est déterminant : l'architecture décidée aujourd'hui structure les 7 semaines de build. Un choix implicite mal fait (« on verra pour le stockage ») force des refactorings coûteux plus tard. Les ADR rendent les choix EXPLICITES et RÉVERSIBLES de façon contrôlée (les conditions de révision disent quand rouvrir la décision). Et en entretien, dérouler l'architecture de DocSense depuis son schéma C4 et justifier 4 décisions par des ADR est une démonstration de pensée d'architecte — exactement ce qui distingue un ingénieur d'un exécutant. Tu construis DocSense en architecture hexagonale (jour 289) dès le départ : les détails (vector DB, LLM) derrière des ports, pour qu'ils restent interchangeables.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : ARCHITECTURE.md (schéma C4 + flux) + 4 ADR pour DocSense.

**Exemple simple** : une ADR tient en 5 lignes — « Contexte : besoin de stocker les vecteurs. Options : Chroma, pgvector, fichier JSON. Décision : Chroma. Pourquoi : filtrage natif + persistance sans infra lourde. Révision si : > 1M vecteurs ou besoin multi-instances ». Décision + pourquoi + condition de sortie.

**Raisonnement pas-à-pas** : dessiner le flux de données (le cœur du schéma), puis figer chaque décision structurante en ADR avec ses options écartées.

**Structure** :
```
ARCHITECTURE.md
  Schéma C4 (Contexte → Conteneurs → Composants) :
    Contexte  : [Utilisateur] → [DocSense] → [API LLM externe]
    Conteneurs: App (cœur hexagonal) · Vector DB · Stockage documents
    Composants: ingestion → chunking → embedding → index
                question → retrieval hybride → génération citée → réponse
  Flux de données : document (entrée) → chunks → vecteurs (index) ;
                    question → embedding → top-k → prompt → réponse citée
docs/adr/
  ADR-001 stockage vectoriel   (Chroma vs pgvector vs JSON)
  ADR-002 modèle LLM           (fournisseur, taille, coût, no-training)
  ADR-003 stratégie de chunking (structurel — config mois 9)
  ADR-004 approche d'évaluation (golden set + rappel@k + fidélité)
  Chaque ADR : contexte · options · décision · conséquences (+/−) · révision si
```

**Mini-quiz** : (a) Que montre un schéma C4 qu'une liste de technos ne montre pas ? (b) Que prouve une ADR qu'un choix implicite ne prouve pas ? (c) Pourquoi décider l'architecture AVANT de coder ?
→ (a) les composants ET les flux de données à plusieurs niveaux de zoom ; (b) que tu as ARBITRÉ entre options avec un pourquoi et une condition de révision ; (c) un choix implicite mal fait force des refactorings coûteux à mi-parcours.

**Variante** : pour l'ADR la plus incertaine (souvent le modèle LLM ou le chunking), écris explicitement les conséquences NÉGATIVES assumées — une ADR sans inconvénients est un plaidoyer, pas une décision.

## 🏢 Cas métier
Les ADR sont une pratique standard des équipes d'ingénierie matures — elles répondent à la question qui hante tout projet six mois plus tard : « pourquoi on a choisi ça, déjà ? ». Sans ADR, la réponse est « c'était comme ça » et personne n'ose toucher ; avec, un nouveau venu lit, comprend, et sait quand rouvrir la décision. En entretien, « montre-moi comment tu documentes une décision d'architecture » arrive tôt — dérouler une ADR de DocSense (options, décision, conséquences négatives assumées, condition de révision) te place immédiatement dans la catégorie « pense en architecte ». Pour un projet final, avoir un ARCHITECTURE.md et 4 ADR est ce qui le fait passer de « script qui marche » à « système conçu ».
