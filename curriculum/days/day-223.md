## 🎯 Objectif du jour
Gérer les mises à jour.

## 📖 Cours approfondi
**Modèle mental : un index qui ne se met pas à jour est un instantané qui pourrit.** L'argument « fraîcheur » du jour 215 t'oblige : si le corpus change et que l'index ne suit pas, ton RAG répond depuis le passé — avec citations, donc avec une fausse crédibilité. La ré-ingestion est le mécanisme qui tient la promesse de fraîcheur, et elle a trois exigences :

1. **Pas de doublons.** Ré-ingérer naïvement duplique les chunks : le top-k se remplit de copies du même passage, évinçant les autres sources. La parade : une IDENTITÉ stable par chunk — un hash du contenu + source (`chunk_id = hash(source + texte)`) — et une écriture idempotente : même contenu → même id → pas de doublon. (L'idempotence de l'ETL du mois 6, appliquée aux vecteurs.)
2. **Les mises à jour remplacent.** Un document modifié doit voir ses ANCIENS chunks retirés et les nouveaux insérés — sinon l'index contient les deux versions et le RAG cite l'obsolète. Stratégie simple et sûre : à la ré-ingestion d'un document, supprimer tous les chunks de cette source puis réinsérer (remplacement par source, plus simple à prouver correct qu'un diff chunk à chunk).
3. **Les échecs se journalisent.** Un fichier illisible, une page vide, un appel d'embedding qui échoue : le pipeline continue (un document pourri ne doit pas bloquer les 99 autres) mais l'échec est CONSIGNÉ — journal avec source, étape, erreur, date. Le journal des échecs de retrieval (questions dont le top-k est resté sous le seuil) s'y ajoute : c'est la matière première du diagnostic du jour 226.

Le test qui prouve tout : ingérer, modifier un document, ré-ingérer, poser une question dont la réponse a CHANGÉ — la réponse doit refléter la nouvelle version, et l'index ne doit pas avoir grossi d'un doublon.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : ré-ingestion idempotente + remplacement par source + journal des échecs.

**Raisonnement** : identité de chunk d'abord, stratégie de remplacement ensuite, journal transversal, et LE test de bout en bout qui prouve la fraîcheur.

**Implémentation** :
```python
import hashlib

def chunk_id(source: str, texte: str) -> str:
    return hashlib.sha256(f"{source}::{texte}".encode()).hexdigest()[:16]

def reingerer_document(source: str, index: Index):
    try:
        nouveaux = chunker(extraire(source))
        index.supprimer_par_source(source)        # remplacement par source
        a_embedder = [c for c in nouveaux
                      if not index.a_deja(chunk_id(source, c["texte"]))]
        index.inserer(embedder(a_embedder))
    except Exception as e:
        journal.append({"source": source, "etape": "ingestion",
                        "erreur": str(e), "date": now()})   # on CONTINUE
```

**Le test de fraîcheur (obligatoire)** :
```
1. Ingère le corpus, note n_chunks. Pose Q : « quel est le délai de X ? » → « 30 jours ».
2. Modifie le document : 30 → 45 jours. Ré-ingère.
3. Repose Q → la réponse DOIT dire 45 jours.
4. Vérifie : n_chunks n'a pas gonflé (pas de doublons), et l'ancienne
   version n'apparaît dans aucun top-k.
5. Glisse un fichier corrompu dans le corpus → ré-ingestion complète OK,
   1 entrée au journal, les autres documents à jour.
```

**Explication** : le remplacement par source est volontairement plus brutal qu'un diff fin — il re-paie l'embedding du document modifié, mais il est PROUVABLE (aucun état hybride possible). À ton échelle, la simplicité prouvable bat l'optimisation. **Variante** : ajoute `rag status` qui affiche n_chunks, par source, date de dernière ingestion, échecs récents — le tableau de bord de santé de ton index.

## ⚠️ Erreurs fréquentes
- Ré-ingérer en ajoutant (append) : les doublons squattent le top-k et l'obsolète cohabite avec le neuf — le pire des deux mondes.
- Un diff fin chunk-à-chunk « pour économiser » : compliqué à prouver correct, sources d'états hybrides — à ton échelle, remplace par source.
- try/except qui avale les erreurs SANS journal : le document illisible disparaît silencieusement du corpus et personne ne le saura.
- Tester seulement l'ajout de documents, jamais la MODIFICATION : c'est la modification qui casse les index naïfs.

## 🏢 Cas métier
Incident RAG classique en entreprise : le support cite une ancienne politique de remboursement des mois après sa mise à jour — les deux versions coexistaient dans l'index, et le retrieval remontait l'ancienne (mieux formulée pour la question). Coût : des clients remboursés à l'ancienne grille + un audit. La ré-ingestion par remplacement et le test de fraîcheur sont exactement ce qui l'aurait évité.

## 🎤 Question d'entretien
**« Comment gères-tu les mises à jour de documents dans un RAG ? »** → Identité stable par chunk (hash contenu+source) pour l'idempotence, remplacement par source à la ré-ingestion (les anciens chunks partent, aucun état hybride), journal des échecs pour que le pipeline continue sans perdre l'information, et un test de fraîcheur bout-en-bout : modifier un document, ré-ingérer, vérifier que la réponse change et que l'index n'a pas gonflé.
