## 🎯 Objectif du jour
Consommer une API avec les 3 états async.

## 📖 Cours approfondi
**Modèle mental : un effet (`useEffect`) SYNCHRONISE ton composant avec un système EXTÉRIEUR à React (une API, un timer, un abonnement) — ce n'est pas « du code qui tourne après le rendu », c'est un pont vers le monde hors React, avec un nettoyage obligatoire.** Le rendu d'un composant doit rester PUR (jour 92) : il calcule du JSX, sans effet de bord. Mais une vraie app doit parler au monde extérieur — chercher des données, poser un timer. `useEffect` est l'endroit prévu pour ces effets de bord, exécutés APRÈS le rendu, sans polluer la pureté.

Les trois pièces d'un effet :
1. **La fonction d'effet** : ce qui parle à l'extérieur (le fetch, l'abonnement).
2. **Le tableau de dépendances** : quand l'effet doit-il se ré-exécuter ? `[]` = une seule fois au montage ; `[id]` = à chaque changement d'`id`. Une dépendance oubliée = un effet qui utilise une valeur périmée (bug de « stale closure »).
3. **Le nettoyage** (la fonction retournée) : annuler ce que l'effet a lancé (abonnement, timer, requête). Sans lui, un composant démonté qui reçoit une réponse tardive provoque un warning « setState sur composant démonté » et des fuites.

Le fetch impose sa discipline : **un appel réseau a TOUJOURS trois états** — chargement, erreur, données — et on ne peut jamais afficher « données » sans données. On modélise ces trois états dans un seul state (une machine à états, jour 93) et on en rend exactement un à la fois. C'est la même rigueur que côté API (mois 3, les 3 réponses possibles) vue depuis le client.

La règle du jour : **le rendu décrit l'UI pour un state donné ; l'effet va chercher les données qui remplissent ce state, et nettoie derrière lui**. La bascule mentale par rapport à JS vanilla : tu ne fais plus « au clic, fetch puis manipule le DOM » ; tu fais « l'effet remplit le state, le state produit l'UI ». Le nombre de `useEffect` que tu écris doit rester petit : beaucoup de choses qu'on croit être des effets sont en fait des valeurs dérivées (jour 93).

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : charger une liste depuis une API avec ses 3 états, une dépendance correcte et un nettoyage.

**Exemple simple** : la machine à 3 états en un seul state — `useState<{ s: 'load' | 'err' | 'ok'; data?: Livre[] }>({ s: 'load' })`. On ne peut JAMAIS être en 'ok' sans `data` : le typage l'interdit presque.

**Raisonnement pas-à-pas** : un state qui encode les 3 états → un effet qui fetch et le met à jour → un nettoyage qui ignore une réponse tardive → un rendu qui affiche l'état courant.

**Solution** :
```tsx
function Livres({ url }: { url: string }) {
  const [etat, setEtat] = useState<{ s: 'load' | 'err' | 'ok'; data?: Livre[] }>({ s: 'load' });

  useEffect(() => {
    let annule = false;                                  // garde-fou de nettoyage
    setEtat({ s: 'load' });
    fetch(url)
      .then((r) => { if (!r.ok) throw new Error(String(r.status)); return r.json(); })
      .then((data) => { if (!annule) setEtat({ s: 'ok', data }); })
      .catch(() => { if (!annule) setEtat({ s: 'err' }); });
    return () => { annule = true; };                     // NETTOYAGE : ignore la réponse tardive
  }, [url]);                                             // DÉPENDANCE : re-fetch si l'url change

  if (etat.s === 'load') return <Spinner />;
  if (etat.s === 'err') return <p>Erreur de chargement <button>réessayer</button></p>;
  return <ul>{etat.data!.map((l) => <li key={l.id}>{l.titre}</li>)}</ul>;
}
```

**Mini-quiz** : (a) Que se passe-t-il si on oublie `url` dans les dépendances ? (b) À quoi sert le drapeau `annule` ? (c) Peut-on afficher l'état 'ok' sans données ?
→ (a) l'effet garde la première url (stale closure), ne re-fetch pas quand elle change ; (b) à ignorer une réponse arrivant après le démontage/changement, évitant un setState sur composant démonté ; (c) non, le state encode data avec 'ok' — la machine à états l'empêche.

**Variante** : rends le bouton « réessayer » fonctionnel en ajoutant un state `essai` incrémenté au clic et mis dans les dépendances — tu déclenches un re-fetch propre sans dupliquer la logique.

## ⚠️ Erreurs fréquentes
- Dépendances incomplètes : stale closure, l'effet utilise une valeur périmée — inclure tout ce que l'effet lit.
- Pas de nettoyage : setState sur composant démonté, warning et fuite quand une réponse arrive tard.
- Ne gérer que le cas heureux : pas d'état d'erreur ni de chargement — l'app casse sur réseau lent ou API en panne.
- Transformer en effet ce qui est une valeur dérivée : un useEffect inutile qui recopie une donnée calculable (jour 93).

## 🏢 Cas métier
Les fuites et warnings « setState sur composant démonté » sont un problème réel : un utilisateur navigue vite entre deux pages, la première reçoit sa réponse API après avoir disparu, et l'app plante ou fuit. Le nettoyage d'effet règle exactement ce cas. Et la discipline des 3 états est ce qui distingue une app qui « marche sur ma machine » (réseau rapide, jamais d'erreur) d'une app robuste en conditions réelles (réseau lent, API en panne). Les recruteurs testent précisément cela : « montre-moi comment tu charges des données » — la bonne réponse inclut chargement, erreur ET nettoyage, pas juste le cas heureux.

## 🎤 Question d'entretien
**« Explique `useEffect` : à quoi sert-il et quels sont ses pièges ? »** → `useEffect` sert à SYNCHRONISER le composant avec un système extérieur (API, timer, abonnement) — les effets de bord qui n'ont pas leur place dans le rendu, qui doit rester pur. Trois pièges : (1) le tableau de dépendances — en oublier une donne une « stale closure » qui utilise une valeur périmée ; (2) l'absence de nettoyage — un composant démonté qui reçoit une réponse tardive provoque un warning et des fuites, d'où la fonction de nettoyage retournée ; (3) l'over-use — beaucoup de « données qu'on va chercher » sont en fait des valeurs dérivées qui n'ont pas besoin d'effet. Et tout fetch a trois états à rendre : chargement, erreur, données.
