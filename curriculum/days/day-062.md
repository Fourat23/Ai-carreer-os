## 🎯 Objectif du jour
Implémenter les relations (auteurs, emprunts) et la logique métier d'emprunt/retour.

## 📖 Cours approfondi
**Concepts abordés :** JOIN dans l'API · Logique métier · Règles (disponibilité) · Transactions.

La logique MÉTIER est ce qui distingue une vraie API d'un CRUD généré : « on ne peut emprunter qu'un livre disponible » est une RÈGLE, et les règles vivent dans la couche service (pas dans les routes, pas dans la base seule).

L'emprunt est une opération à étapes multiples (vérifier la disponibilité → créer l'emprunt → marquer indisponible) : c'est exactement le cas d'usage des TRANSACTIONS du jour 58. Sans elle, une panne au milieu laisse un livre fantôme. Le conflit métier (déjà emprunté) mérite son statut précis : 409 Conflict — pas 400, pas 500.

Les JOIN entrent dans l'API : GET /livres/42 ramène le livre AVEC son auteur (un JOIN), pas un id opaque que le client devrait résoudre par une seconde requête.

**Modèle mental : la LOGIQUE MÉTIER est ce qui distingue une vraie API d'un CRUD généré. « On ne peut emprunter qu'un livre DISPONIBLE » est une RÈGLE, et les règles vivent dans la couche SERVICE — pas dans les routes (qui ne font que traduire le HTTP), pas dans la base seule. Et comme l'emprunt est une opération à ÉTAPES MULTIPLES (vérifier la disponibilité → créer l'emprunt → marquer indisponible), c'est le cas d'usage exact des TRANSACTIONS : sans elle, une panne au milieu laisse un livre fantôme, ni vraiment emprunté ni vraiment disponible.** Implémenter l'emprunt, c'est placer la règle au bon endroit et garantir l'atomicité.

Pourquoi la règle métier vit dans le service. Si « pas de double emprunt » est écrit dans la route, elle est intestable sans serveur et se duplique à chaque endroit qui emprunte. Dans la base seule (une contrainte), elle est difficile à exprimer et à faire remonter proprement au client. Dans le SERVICE (jour 53), elle est testable en isolation, réutilisable, et le bon statut peut être renvoyé. La couche service est le siège des DÉCISIONS métier ; les routes traduisent, la data persiste.

La transaction pour une opération multi-étapes, depuis les fondations. Emprunter, c'est : (1) vérifier que le livre est disponible ; (2) créer la ligne d'emprunt ; (3) marquer le livre indisponible. Ces trois étapes doivent réussir ENSEMBLE ou aucune (atomicité, jour 58) : si une panne survient après (2) mais avant (3), on aurait un emprunt enregistré ET un livre encore marqué disponible — un état incohérent qui autoriserait un double emprunt. La transaction enveloppe les trois étapes ; en cas d'échec, un ROLLBACK annule tout.

Le statut du conflit métier, une nuance à connaître. Tenter d'emprunter un livre déjà emprunté n'est ni une erreur de saisie (400) ni un bug serveur (500) : c'est un CONFLIT avec l'état actuel de la ressource → **409 Conflict**. Choisir 409 plutôt que 400 ou 500 est un signe de maîtrise des statuts : le client comprend que sa requête était bien formée mais que l'état ne le permet pas.

Les JOIN entrent dans l'API. Ramener « un livre avec son auteur » ou « les emprunts d'un membre avec les titres » se fait par des JOIN (jour 55) dans la couche data : `GET /livres/42` peut renvoyer le livre ET le nom de son auteur en une requête, plutôt que de forcer le client à faire deux appels. Le JOIN assemble les données liées côté base, là où c'est efficace.

Limites et compromis. Placer TOUTE la logique dans le service peut créer des services volumineux — on les découpe par domaine si besoin. Les transactions ont un coût (verrous) : on les garde ciblées sur les opérations réellement liées. Et exprimer une règle à la fois dans le service ET comme contrainte base (défense en profondeur) est parfois justifié, au prix d'une duplication assumée.

La règle du jour : **place la logique métier dans le SERVICE (testable, réutilisable, pas dans les routes), enveloppe les opérations multi-étapes (emprunt : vérifier → créer → marquer) dans une TRANSACTION pour l'atomicité, renvoie 409 sur un conflit métier (double emprunt), et utilise les JOIN pour ramener les données liées.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : implémenter `POST /livres/:id/emprunter` avec la règle « livre disponible ? » dans le service, une transaction atomique, et le statut 409 en cas de conflit.

**Exemple simple** : où vit la règle. La ROUTE reçoit la requête et renvoie le statut ; le SERVICE décide (« disponible ? sinon conflit ») ; la DATA exécute la transaction. La décision métier est dans le service, isolée et testable.

**Raisonnement pas-à-pas** : (1) le service vérifie la disponibilité (règle métier) ; (2) si indisponible → il signale un conflit → la route renvoie 409 ; (3) sinon, une TRANSACTION crée l'emprunt ET marque le livre indisponible atomiquement ; (4) une panne au milieu → rollback, aucun état à moitié fait.

**Implémentation** :
```ts
class ConflitMetier extends Error {}

// COUCHE DATA : la transaction rend les étapes atomiques (jour 58)
const emprunterTx = db.transaction((livreId: number, membreId: number) => {
  const livre = db.prepare('SELECT disponible FROM livres WHERE id = ?').get(livreId);
  if (!livre) throw new Error('livre introuvable');
  if (livre.disponible === 0) throw new ConflitMetier('livre déjà emprunté');   // règle
  db.prepare('INSERT INTO emprunts (livre_id, membre_id, date_emprunt) VALUES (?, ?, ?)')
    .run(livreId, membreId, new Date().toISOString());
  db.prepare('UPDATE livres SET disponible = 0 WHERE id = ?').run(livreId);
  // si une étape échoue -> ROLLBACK : jamais un emprunt sans livre marqué indisponible
});

// ROUTE : traduit le HTTP, mappe le conflit métier sur 409
app.post('/livres/:id/emprunter', (req, res) => {
  try {
    emprunterTx(Number(req.params.id), req.body.membreId);
    res.status(201).json({ message: 'emprunté' });
  } catch (e) {
    if (e instanceof ConflitMetier) return res.status(409).json({ message: e.message }); // 409 !
    throw e;   // vrai bug -> middleware d'erreurs (500 générique)
  }
});

// JOIN : ramener le livre AVEC son auteur en une requête
const livreAvecAuteur = (id: number) => db.prepare(
  'SELECT l.*, a.nom AS auteur FROM livres l LEFT JOIN auteurs a ON a.id = l.auteur_id WHERE l.id = ?'
).get(id);
```
La règle « disponible ? » vit dans la transaction du service, l'opération est atomique (rollback si échec), le double emprunt renvoie 409 (pas 400 ni 500), et le JOIN ramène l'auteur en une requête.

## ⚠️ Erreurs fréquentes
- Emprunter un livre déjà emprunté (règle non vérifiée ou vérifiée hors transaction → race condition).
- Pas de transaction : une panne au milieu laisse un emprunt sans livre marqué indisponible (état incohérent).
- Mauvais statut : 400 ou 500 pour un double emprunt au lieu de 409 Conflict.
- Règle métier dans la route au lieu du service : intestable et dupliquée.

## 🏢 Cas métier
La logique métier et l'intégrité transactionnelle sont le cœur de valeur de tout système d'entreprise sérieux — e-commerce, réservation, banque, gestion de stock. La règle « on ne vend pas un produit en rupture », « on ne réserve pas un siège déjà pris », « on ne débite pas sans créditer » est exactement l'analogue du double emprunt, et son absence cause des incidents coûteux (survente, double réservation, argent perdu). Placer ces règles dans une couche service testable, et envelopper les opérations liées dans des transactions atomiques, est ce qui distingue un système fiable d'un système qui « marche jusqu'à la première panne au mauvais moment ». Le choix du statut 409 pour un conflit métier est un détail qui signale la maîtrise. En entretien back, « où mets-tu la logique métier ? » et « comment garantis-tu qu'une opération à plusieurs étapes ne laisse pas d'état incohérent ? » sont des questions directes, et savoir répondre couche service + transaction + 409 démontre un vrai niveau.

## 🎤 Question d'entretien
**« Comment implémentes-tu une opération métier comme "emprunter un livre" de façon fiable ? »** → Je sépare les responsabilités. La ROUTE ne fait que traduire le HTTP ; la RÈGLE métier (« on ne peut emprunter qu'un livre disponible ») vit dans la couche SERVICE, où elle est testable en isolation et réutilisable. Comme l'emprunt est une opération à plusieurs étapes — vérifier la disponibilité, créer la ligne d'emprunt, marquer le livre indisponible — je l'enveloppe dans une TRANSACTION : les trois réussissent ensemble ou un rollback annule tout. Sans ça, une panne entre la création de l'emprunt et le marquage laisserait un état incohérent, autorisant un double emprunt. Pour le conflit « livre déjà emprunté », je renvoie 409 Conflict — pas 400 (la requête est bien formée) ni 500 (ce n'est pas un bug) : c'est un conflit avec l'état de la ressource. Et je ramène les données liées (le livre avec son auteur) par un JOIN, en une requête. **Relance possible** : « et si tu voulais une défense supplémentaire contre le double emprunt ? » → j'ajouterais une contrainte au niveau base (par exemple une règle d'unicité sur les emprunts actifs) en défense en profondeur : la règle dans le service pour l'expérience et le bon statut, la contrainte base comme filet ultime contre une race condition.
