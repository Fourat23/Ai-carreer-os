## 🎯 Objectif du jour
Écrire un serveur http natif AVANT Express pour ne pas traiter le framework en boîte noire.

## 📖 Cours approfondi
**Concepts abordés :** Module http natif · req/res · Routing manuel · Parsing du corps · Pourquoi Express.

Sous Express il y a le module http de Node : un serveur = une fonction qui reçoit (req, res) et ÉCRIT une réponse. Tout ce qu'Express automatise, tu peux le faire à la main : router (un switch sur method + url), parser le corps (accumuler les chunks du flux entrant), répondre (statut + headers + res.end).

L'exercice du jour a un but précis : éprouver la FRICTION. Parser le JSON à la main, router à la main, gérer les erreurs à la main — pour que demain, chaque facilité d'Express (express.json(), app.get, les middlewares) soit comprise comme une automatisation de quelque chose que tu SAIS faire, pas comme de la magie.

C'est un principe d'apprentissage général : une couche basse comprise une fois = toutes les abstractions au-dessus démystifiées.

**Modèle mental : sous Express, il y a le module `http` de Node — un serveur n'est qu'une fonction qui reçoit `(req, res)` et ÉCRIT une réponse. Tout ce qu'Express automatise, tu peux le faire à la main : router (un `switch` sur méthode + URL), parser le corps (accumuler les morceaux du flux entrant), répondre (statut + headers + `res.end`). Écrire d'abord un serveur natif a un but précis : ÉPROUVER LA FRICTION, pour que demain chaque facilité d'Express soit comprise comme l'automatisation de quelque chose que tu SAIS faire — pas comme de la magie.** Une couche basse comprise une fois démystifie toutes les abstractions au-dessus.

Pourquoi passer par le natif avant le framework. La tentation est d'apprendre Express directement. Mais utiliser un framework sans comprendre ce qu'il fait, c'est dépendre d'une boîte noire : au premier comportement inattendu (un corps non parsé, un middleware dans le mauvais ordre), on est perdu. Écrire le serveur natif révèle CE QU'EXPRESS FAIT POUR TOI : le routing, le parsing, la gestion des réponses. Ensuite, Express n'est plus magique — c'est un raccourci dont tu connais le travail sous-jacent.

Ce que fait le module http, depuis les fondations. `http.createServer((req, res) => { ... })` : à chaque requête, la fonction reçoit `req` (méthode, URL, headers, et le corps comme un FLUX) et `res` (pour écrire la réponse). **Router à la main** : un `switch`/`if` sur `req.method` et `req.url` pour diriger vers le bon traitement. **Parser le corps** : le corps arrive par MORCEAUX (chunks) sur un flux ; il faut les accumuler (`req.on('data', ...)`) puis les assembler à la fin (`req.on('end', ...)`) et `JSON.parse`. **Répondre** : `res.writeHead(statut, headers)` puis `res.end(corps)` — oublier `res.end` laisse la requête PENDANTE (le client attend indéfiniment).

La différence natif vs Express. En natif, tu écris explicitement le routing, le parsing et la gestion des réponses — c'est verbeux et répétitif. Express fournit `app.get('/ping', ...)` (routing déclaratif), `express.json()` (parsing automatique du corps), `res.json()` (réponse JSON en une ligne), et la CHAÎNE de middlewares (jour 53). Express ne fait rien de magique : il AUTOMATISE ce que tu viens de faire à la main.

Le principe d'apprentissage général. Comprendre une couche basse une seule fois rend transparentes toutes les couches au-dessus. C'est vrai ici (http → Express), mais aussi partout : comprendre comment fonctionne une abstraction (un ORM sur SQL, un framework front sur le DOM) permet de la maîtriser au lieu de la subir. Le natif n'est pas du temps perdu — c'est l'investissement qui rend le framework limpide.

Limites et compromis. Le serveur natif est instructif mais IMPRATICABLE en vrai : routing verbeux, parsing manuel fragile, aucune gestion d'erreurs structurée. C'est exactement pourquoi les frameworks existent — on ne code pas une API de production en http natif. L'objectif du jour est la COMPRÉHENSION, pas la production : on écrit le natif pour le comprendre, puis on passe à Express pour travailler.

La règle du jour : **écris un serveur http natif AVANT Express pour éprouver la friction (routing, parsing des chunks, res.end) et comprendre ce qu'un framework automatise. Une couche basse comprise démystifie l'abstraction au-dessus — Express n'est plus magique, c'est un raccourci dont tu connais le travail.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : écrire un serveur http natif (GET `/ping` → `pong`, POST `/echo` → renvoie le JSON reçu), constater la friction, puis mesurer ce qu'Express automatise.

**Exemple simple** : la friction du parsing. En natif, lire le corps d'un POST demande d'accumuler les morceaux d'un flux et de les assembler — plusieurs lignes. En Express, `express.json()` le fait, et `req.body` est prêt. C'est CETTE friction qu'Express supprime.

**Raisonnement pas-à-pas** : (1) je crée le serveur avec `(req, res)` ; (2) je route à la main sur `method` + `url` ; (3) pour le POST, j'accumule les chunks puis j'assemble et je parse ; (4) je réponds avec `writeHead` + `end` (sans oublier `end`).

**Serveur natif** :
```ts
import { createServer } from 'node:http';

const serveur = createServer((req, res) => {
  // ROUTING à la main : switch sur méthode + url
  if (req.method === 'GET' && req.url === '/ping') {
    res.writeHead(200, { 'Content-Type': 'text/plain' });
    res.end('pong');                       // sans res.end -> requête pendante !
    return;
  }
  if (req.method === 'POST' && req.url === '/echo') {
    // PARSING du corps : accumuler les chunks du flux
    let brut = '';
    req.on('data', chunk => { brut += chunk; });
    req.on('end', () => {
      try {
        const json = JSON.parse(brut);
        res.writeHead(200, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify(json));      // renvoie ce qu'on a reçu
      } catch {
        res.writeHead(400); res.end('JSON invalide');
      }
    });
    return;
  }
  res.writeHead(404); res.end('Not Found');   // route inconnue
});
serveur.listen(3000);
```

**Le même service en Express** (ce qui est automatisé) :
```ts
import express from 'express';
const app = express();
app.use(express.json());                       // parsing du corps : AUTOMATIQUE
app.get('/ping', (_req, res) => res.send('pong'));         // routing déclaratif
app.post('/echo', (req, res) => res.json(req.body));       // req.body prêt, res.json
app.listen(3000);
```
Le natif expose la friction (routing manuel, chunks, res.end) ; Express l'automatise exactement. Le framework n'est plus une boîte noire.

## ⚠️ Erreurs fréquentes
- Oublier res.end : la réponse n'est jamais terminée, la requête reste pendante.
- Ne pas gérer les chunks du corps : lire req comme une valeur au lieu d'un flux accumulé.
- Traiter Express en boîte noire sans comprendre ce qu'il automatise : blocage au premier comportement inattendu.
- Croire que le serveur natif est fait pour la production : il est instructif mais impraticable (verbeux, fragile).

## 🏢 Cas métier
Comprendre la couche http native sous Express a une valeur pratique directe en entreprise, même si personne n'écrit d'API de production en http natif. Quand un comportement inattendu survient — un corps de requête vide alors qu'on attend du JSON, un middleware qui ne s'exécute pas, un streaming à gérer, une réponse qui ne se termine pas — c'est la compréhension de la couche basse (req/res, flux, chunks, res.end) qui permet de diagnostiquer, là où un développeur qui traite Express en boîte noire reste bloqué. C'est aussi ce qui permet de comprendre les frameworks concurrents (Fastify, Koa) : ils automatisent la même couche http différemment. Le principe « comprendre une couche pour maîtriser l'abstraction au-dessus » se généralise à toute la stack (un ORM sur SQL, React sur le DOM). En entretien, savoir expliquer ce qu'Express fait « pour toi » distingue celui qui comprend de celui qui applique des recettes.

## 🎤 Question d'entretien
**« Qu'est-ce qu'Express fait concrètement pour toi par rapport au module http de Node ? »** → Au niveau du module `http`, un serveur est une simple fonction `(req, res)` : je dois tout faire à la main. Le ROUTING : un `switch` sur `req.method` et `req.url` pour diriger chaque requête. Le PARSING du corps : le corps arrive par morceaux sur un flux, je dois accumuler les chunks puis les assembler et les parser. La RÉPONSE : `res.writeHead(statut, headers)` puis `res.end` — et si j'oublie `res.end`, la requête reste pendante. Express AUTOMATISE exactement ça : `app.get('/ping', ...)` remplace le routing manuel, `express.json()` parse le corps et me donne `req.body` prêt, `res.json()` répond en une ligne, et la chaîne de middlewares structure le traitement. Le point important est qu'Express ne fait rien de magique : il fait ce que je viens de décrire, en plus concis. J'écris le natif d'abord justement pour que le framework ne soit pas une boîte noire — quand un corps n'est pas parsé ou une réponse ne part pas, je sais où regarder. **Relance possible** : « pourquoi ne pas rester en http natif alors ? » → parce que le natif est instructif mais impraticable en vrai : routing verbeux, parsing fragile, aucune gestion d'erreurs structurée — c'est précisément pourquoi les frameworks existent.
