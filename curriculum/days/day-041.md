# Jour 41 — Debugging méthodique : la compétence qu'on n'enseigne jamais

## 🎯 Objectif du jour
Adopter une méthode de debug systématique : reproduire → isoler → hypothèse → prouver → corriger.

## 📖 Cours approfondi
**Concepts abordés :** Reproduire fiablement · Bissection · console.log stratégique / debugger · Lire une stack trace · Rubber duck.

Le debugging méthodique remplace la loterie par un processus : (1) REPRODUIRE de façon fiable — sans ça, impossible de valider un fix ; (2) LIRE le message d'erreur en entier — il donne souvent ligne et cause ; (3) ISOLER par bissection — couper le code en deux, vérifier au milieu, éliminer une moitié (la recherche binaire appliquée au debug) ; (4) formuler UNE hypothèse falsifiable ; (5) la PROUVER par une observation (log, breakpoint) avant de corriger ; (6) corriger la CAUSE, pas le symptôme, puis re-reproduire.

Les familles de bugs à connaître : référence partagée (deux choses changent ensemble), off-by-one (bornes de boucle), type inattendu (NaN qui se propage), async (l'ordre d'exécution n'est pas celui du code), état périmé. Chaque famille a sa signature — les reconnaître accélère le diagnostic.

**Modèle mental : déboguer n'est PAS modifier du code au hasard jusqu'à ce que « ça marche » — c'est une enquête scientifique. On REPRODUIT le bug de façon fiable, on ISOLE la zone coupable par bissection, on formule UNE hypothèse FALSIFIABLE, on la PROUVE par une observation, puis on corrige la CAUSE (pas le symptôme) et on re-reproduit pour valider. Le débogueur méthodique bat le devineur pressé à tous les coups, parce qu'il élimine des possibilités au lieu d'en espérer une.** Changer du code sans hypothèse, c'est jouer à la loterie ; suivre la méthode, c'est converger.

Pourquoi une méthode est nécessaire. Face à un bug, la tentation est de modifier « ce qui a l'air suspect » et de relancer. Sur un bug simple, on a parfois de la chance ; sur un bug subtil (référence partagée, async, off-by-one), on tourne en rond des heures, on introduit de NOUVEAUX bugs, et on ne comprend jamais la cause — donc il reviendra. La méthode remplace la chance par une convergence garantie : chaque étape RÉDUIT l'espace des causes possibles.

Les six étapes, depuis les fondations. (1) **Reproduire fiablement** : sans un cas qui déclenche le bug à volonté, impossible de savoir si un fix marche. C'est le prérequis absolu. (2) **Lire le message d'erreur EN ENTIER** : la stack trace donne souvent le fichier, la ligne et la nature — l'ignorer, c'est jeter la carte au trésor. (3) **Isoler par bissection** : couper le parcours en deux, vérifier l'état au milieu (log/breakpoint), et éliminer la moitié saine — la recherche binaire (jour 16) appliquée au débogage, qui localise en O(log n) étapes. (4) **Formuler UNE hypothèse falsifiable** : « la liste est mutée à l'étape X » — précise, testable. (5) **La prouver par observation** AVANT de corriger : un log ou un breakpoint confirme ou infirme. (6) **Corriger la cause** puis re-reproduire : le symptôme peut disparaître alors que la cause demeure.

La différence corriger la cause vs le symptôme. Un `if (valeur == null) valeur = 0` qui masque un `null` inattendu FAIT DISPARAÎTRE le crash mais laisse la vraie question ouverte (pourquoi est-ce null ?) — le bug ressurgira ailleurs. Corriger la cause, c'est remonter à l'origine du `null`. Le symptôme est ce qu'on voit ; la cause est ce qui le produit.

Les familles de bugs et leur signature. **Référence partagée** : deux variables pointent le même objet, modifier l'une change l'autre (copie superficielle vs profonde). **Off-by-one** : bornes de boucle (`<` vs `<=`, index 0 vs 1). **Type inattendu** : un `NaN` ou `undefined` qui se propage silencieusement. **Async** : l'ordre d'exécution n'est pas celui de lecture du code (une valeur lue avant d'être résolue). **État périmé** : une donnée mise en cache non rafraîchie. Reconnaître la signature accélère le diagnostic.

Limites et compromis. La méthode a un coût d'installation (reproduire prend parfois du temps) qui décourage sur un bug « évident » — mais c'est justement sur les bugs non évidents qu'elle fait gagner des heures. Le `console.log` stratégique suffit souvent ; le débogueur pas-à-pas (breakpoints, inspection) est plus puissant pour l'état complexe et l'async. Le « rubber duck » (expliquer le bug à voix haute, même à un canard) révèle souvent la faille dans le raisonnement avant tout outil.

La règle du jour : **ne modifie JAMAIS au hasard. Reproduis d'abord, lis l'erreur en entier, isole par bissection, formule une hypothèse falsifiable, prouve-la par observation, corrige la CAUSE, re-reproduis. Reconnais les familles de bugs à leur signature — c'est ce qui transforme une chasse aléatoire en enquête qui converge.**

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : débusquer un bug de RÉFÉRENCE PARTAGÉE avec la méthode, au lieu de patcher au hasard.

**Exemple simple** : le symptôme déroutant.
```ts
const modele = { tags: [] as string[] };
function creerTache(titre: string) {
  const t = { titre, tags: modele.tags };   // BUG : même référence partagée !
  return t;
}
const a = creerTache('A');
const b = creerTache('B');
a.tags.push('urgent');
console.log(b.tags);   // ['urgent'] ?!  b n'a jamais reçu 'urgent'
```

**Raisonnement pas-à-pas (la méthode)** : (1) REPRODUIRE : le cas ci-dessus déclenche le bug à coup sûr. (2) SYMPTÔME : modifier `a.tags` change `b.tags`. (3) HYPOTHÈSE falsifiable : « `a.tags` et `b.tags` sont le MÊME tableau en mémoire ». (4) PROUVER par observation : `console.log(a.tags === b.tags)` → `true` → hypothèse CONFIRMÉE. (5) CAUSE : `tags: modele.tags` copie la RÉFÉRENCE, pas le contenu. (6) FIX de la cause + re-reproduire.

**Correction (cause traitée)** :
```ts
function creerTache(titre: string) {
  const t = { titre, tags: [...modele.tags] };   // copie du CONTENU, plus de partage
  return t;
}
const a = creerTache('A'), b = creerTache('B');
console.log(a.tags === b.tags);   // false -> références distinctes
a.tags.push('urgent');
console.log(b.tags);              // [] -> b intact, bug résolu à la CAUSE
```
Le réflexe naïf aurait été de « réinitialiser `b.tags` » (patch du symptôme) — le partage serait resté et le bug réapparu ailleurs. La méthode a mené à la cause en une hypothèse prouvée.

## ⚠️ Erreurs fréquentes
- Modifier du code au hasard sans hypothèse : on introduit de nouveaux bugs et on ne comprend jamais la cause.
- Corriger le symptôme (valeur par défaut qui masque un null) au lieu de la cause : le bug revient ailleurs.
- Ne pas lire le message d'erreur en entier : on ignore la ligne et la nature déjà fournies.
- Ne pas reproduire avant de corriger : impossible de savoir si le fix marche vraiment.

## 🏢 Cas métier
Le débogage méthodique est une compétence quotidienne et sous-estimée : un développeur passe une part énorme de son temps non à écrire, mais à COMPRENDRE pourquoi quelque chose ne marche pas — en dev, en pré-prod, et sous pression lors d'un incident en production. Face à un bug critique qui coûte de l'argent à chaque minute, celui qui modifie au hasard aggrave souvent la situation (nouveaux bugs, régressions) ; celui qui reproduit, isole et prouve une hypothèse converge et documente la cause racine (post-mortem). Les familles de bugs (référence partagée, async, état périmé) reviennent constamment dans le code réel. C'est aussi un signal d'entretien fort : « raconte comment tu as débogué un problème difficile » teste précisément si tu as une MÉTHODE ou si tu tâtonnes — et les équipes matures pratiquent le rubber duck et les post-mortems sans blâme.

## 🎤 Question d'entretien
**« Raconte comment tu t'y prends pour déboguer un problème difficile. »** → Je ne modifie jamais au hasard : je traite le bug comme une enquête. D'abord je le REPRODUIS de façon fiable — sans ça, impossible de valider un fix. Je lis le message d'erreur EN ENTIER (la stack trace donne souvent la ligne et la cause). J'ISOLE par bissection : je coupe le parcours en deux, j'observe l'état au milieu avec un log ou un breakpoint, et j'élimine la moitié saine — c'est la recherche binaire appliquée au débogage. Puis je formule UNE hypothèse falsifiable (« la liste est mutée ici ») et je la PROUVE par observation AVANT de toucher au code. Enfin je corrige la CAUSE, pas le symptôme — masquer un null par une valeur par défaut fait disparaître le crash mais laisse le bug ressurgir ailleurs — et je re-reproduis pour valider. Je m'appuie aussi sur les signatures des familles de bugs : référence partagée, off-by-one, async, type inattendu, état périmé. **Relance possible** : « et si tu bloques complètement ? » → le rubber duck : j'explique le bug ligne à ligne à voix haute (à un collègue ou littéralement à un canard) ; verbaliser révèle presque toujours la faille dans mon raisonnement.
