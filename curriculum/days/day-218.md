## 🎯 Objectif du jour
Vectoriser les chunks.

## 📖 Cours approfondi
**Modèle mental : l'embedding donne une adresse GPS au sens.** Tu l'as vu au jour 191 : un modèle d'embedding transforme un texte en vecteur (des centaines de dimensions) tel que deux textes proches par le SENS ont des vecteurs proches par la GÉOMÉTRIE — « congés payés » et « vacances » voisins, « congés payés » et « recette de tarte » lointains. Aujourd'hui ce concept devient l'infrastructure de ton RAG : chaque chunk reçoit son adresse, et chercher = trouver les adresses proches de celle de la question.

Les décisions d'ingénierie du jour :
1. **Un seul modèle d'embedding pour tout** : les vecteurs de deux modèles différents vivent dans des espaces INCOMPATIBLES — embedder les chunks avec un modèle et les questions avec un autre = similarités absurdes. Le nom du modèle se stocke AVEC l'index (tu comprendras pourquoi au versioning, jour 242).
2. **Le stockage : JSON suffit.** Pour quelques centaines/milliers de chunks, un fichier `[{id, texte, source, position, vecteur}, ...]` est parfait. La vector DB (jour 239) résoudra des problèmes que tu n'as PAS encore — et tu sauras lesquels, puisque tu auras vécu sans.
3. **Les appels se font par batch** (l'API accepte plusieurs textes par requête) : moins de round-trips, moins cher, plus rapide. Et l'ingestion est REPRENABLE : si elle plante au chunk 800/1000, on ne repaie pas les 800 premiers (sauvegarde incrémentale ou reprise sur ids manquants).
4. **Vérification immédiate** : avant de construire la recherche (demain), un test de santé — l'embedding de « congés » est-il plus proche de ton chunk RH que de ton chunk technique ? Trois sondages à la main valident que l'espace fonctionne.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : embedder tous les chunks et les stocker, ingestion reprenable.

**Raisonnement** : batch + reprise + vérification — les trois gestes qui distinguent l'ingestion sérieuse du script jetable.

**Implémentation** :
```python
import json, pathlib
INDEX = pathlib.Path("index.json")

def ingerer(chunks: list[dict], batch=50):
    fait = {c["id"] for c in json.loads(INDEX.read_text())} if INDEX.exists() else set()
    restants = [c for c in chunks if c["id"] not in fait]      # REPRISE
    for lot in batches(restants, batch):
        vecteurs = api_embeddings([c["texte"] for c in lot])    # 1 appel / 50 chunks
        for c, v in zip(lot, vecteurs):
            c["vecteur"] = v
        sauvegarder_incremental(lot)                            # après CHAQUE lot
    # métadonnées d'index : modèle d'embedding, date, nb de chunks
    sauver_meta({"modele": MODELE_EMBED, "date": now(), "n": len(chunks)})
```

**Vérification de santé** :
```
embedde 3 mini-requêtes dont tu connais le chunk-cible → pour chacune,
affiche les 3 chunks aux vecteurs les plus proches (cosinus rapide, même
naïf) → la cible est-elle dedans ? Si non : STOP, débugge avant demain.
```

**Explication** : la reprise sur ids manquants transforme un plantage réseau en non-événement ; les métadonnées d'index (modèle, date) sont 3 lignes qui t'éviteront un bug infernal le jour où tu changeras de modèle. **Variante** : chronomètre et chiffre l'ingestion complète (n appels, tokens, coût, durée) — première ligne de ton futur budget RAG.

## ⚠️ Erreurs fréquentes
- Embedder question et chunks avec des modèles différents : l'erreur silencieuse la plus coûteuse du RAG — rien ne plante, tout est faux.
- Ingestion non reprenable : le plantage au chunk 800 coûte 800 chunks re-payés.
- Oublier de stocker le texte avec le vecteur : un vecteur seul est inutilisable pour la génération.
- Sauter le test de santé : tu découvriras demain, empilé sur la logique de recherche, que l'espace était cassé aujourd'hui.

## 🏢 Cas métier
Bug classique en production RAG : après une migration, les NOUVEAUX documents sont embeddés avec un nouveau modèle, les anciens vecteurs restent — l'index devient un espace hybride où les similarités ne veulent plus rien dire, et les résultats se dégradent mystérieusement. Diagnostic impossible sans métadonnées d'index. Ta règle « un espace = un modèle, noté dans les métadonnées » est exactement ce qui l'évite.

## 🎤 Question d'entretien
**« Comment structures-tu l'ingestion des embeddings d'un RAG ? »** → Un seul modèle d'embedding pour chunks ET requêtes (espaces incompatibles sinon), noté dans les métadonnées de l'index ; appels par batch ; ingestion reprenable (sauvegarde incrémentale, reprise sur ids manquants) ; stockage simple tant que le volume le permet (JSON pour des milliers de chunks) ; et un test de santé avant de construire au-dessus — trois requêtes dont je connais la cible.
