## 📖 Cours approfondi
**Modèle mental : une API LLM est une fonction très chère et non déterministe.** L'appel est banal techniquement (HTTP POST, JSON), mais ses propriétés sont inhabituelles : chaque appel coûte de l'argent, met des secondes à répondre, et peut renvoyer autre chose que la dernière fois. On code donc dès le premier jour comme pour un composant faillible.

Anatomie d'un appel propre :
- **Le system prompt** : le rôle et les règles, séparés du message utilisateur. C'est une SPÉCIFICATION, pas une formule magique.
- **Les messages** : l'historique explicite `[{role, content}, ...]` — c'est TOI qui construis la « mémoire » en réinjectant les tours précédents.
- **Les paramètres** : `model`, `max_tokens` (plafond de sortie = plafond de coût), `temperature` (demain).
- **Le streaming** : la réponse arrive token par token ; indispensable en UX (l'utilisateur voit la réponse naître au lieu de fixer un spinner 8 secondes).

Et les règles d'hygiène non négociables : la clé API vit en `.env` (JAMAIS dans le code, JAMAIS committée — tu connais la chanson depuis le mois 4), les erreurs sont attrapées (réseau, rate limit 429, timeout), et chaque appel logge son usage de tokens. Un script d'appel LLM sans gestion d'erreur n'est pas « presque fini » : il n'est pas commencé.

## 🧭 Exemple guidé
*Étudie ce pas-à-pas, puis FERME-le et attaque la pratique autonome de mémoire.*

**Énoncé** : un script d'appel à l'API Claude, propre dès la v1.

**Raisonnement** : séparer configuration (env), construction de l'appel (system + messages + params) et gestion des issues (réponse, erreur, usage).

**Squelette (Python)** :
```python
import os, anthropic
client = anthropic.Anthropic()          # lit ANTHROPIC_API_KEY depuis l'env
try:
    reponse = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=500,                  # plafond de sortie = plafond de coût
        system="Tu es un assistant concis. Réponds en 3 phrases maximum.",
        messages=[{"role": "user", "content": "Explique le streaming HTTP."}],
    )
    print(reponse.content[0].text)
    print(f"tokens: in={reponse.usage.input_tokens} out={reponse.usage.output_tokens}")
except anthropic.APIStatusError as e:
    print(f"Erreur API {e.status_code} — à gérer, pas à ignorer")
```

**Explication** : le system prompt contraint le comportement, max_tokens borne la dépense, usage logge la consommation réelle. **Variante** : passe en streaming (`client.messages.stream(...)`) et affiche les tokens au fil de l'eau — compare le ressenti utilisateur.

## 🎤 Question d'entretien
**« Que mets-tu dans le system prompt vs le message utilisateur ? »** → Le system prompt porte le rôle, les règles et le format attendus — la spécification stable, versionnée. Le message utilisateur porte la demande variable. Séparer les deux rend le comportement testable et le prompt réutilisable.
