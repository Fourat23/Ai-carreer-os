## 📖 Cours approfondi
**Modèle mental : documenter DataPulse, c'est PROUVER la valeur du pipeline à un lecteur extérieur — un README qui part des QUESTIONS et montre les RÉPONSES, une ADR qui fige un arbitrage technique réel, une démo qui prouve la reproductibilité. C'est l'interface entre ton travail data et le recruteur, et pour un projet de PIPELINE, elle a ses spécificités : le « rejouable en une commande » et le rapport de qualité sont au cœur.** DataPulse fonctionne (jours 141-145) ; aujourd'hui tu le rends présentable en deux minutes à quelqu'un qui ne l'a jamais vu. Contrairement à un projet d'app (front), un projet data se vend sur ses QUESTIONS, ses RÉPONSES et sa REPRODUCTIBILITÉ.

Les livrables et leur rôle propre à un projet data :
1. **Le README orienté questions** : il commence par le PROBLÈME et les 3 QUESTIONS (pas par « DataPulse utilise pandas et SQLite »), montre les RÉPONSES (les 3 visualisations, ou un aperçu), explique comment lancer en UNE commande (`python -m datapulse`), et inclut le rapport de qualité (ce qui a été fait aux données). Un recruteur data lit d'abord : quelles questions, quelles réponses, est-ce reproductible ?
2. **L'ADR n°4 : « SQLite vs PostgreSQL »** : une décision d'architecture RÉELLE de DataPulse, figée avec son pourquoi. SQLite (choisi) pour un projet local, mono-utilisateur, sans serveur à administrer ; PostgreSQL (écarté) aurait apporté la concurrence et la montée en charge, inutiles ici. Documenter cet arbitrage montre que tu as CHOISI en connaissance de cause, pas par défaut — et que tu connais les conditions où l'autre choix s'imposerait.
3. **La démo de 2 minutes** : elle prouve la REPRODUCTIBILITÉ — lancer la commande unique, voir le pipeline s'exécuter (extract → transform → load), puis montrer le dashboard répondant aux 3 questions. Pour un pipeline, la démo clé est « je relance tout d'une commande et j'obtiens le résultat », pas juste « voici de jolis graphiques ».

Le test du regard neuf, version data : quelqu'un qui n'a jamais vu DataPulse comprend-il, via le README et la démo, QUELLES questions le projet répond, QUELLES réponses il donne, comment le RELANCER, et POURQUOI tu as fait tes choix techniques — sans te parler ? Si oui, ton projet data est vendable.

La règle du jour : **un README qui part des questions et prouve les réponses + un rapport de qualité + une ADR sur un vrai arbitrage (SQLite vs Postgres) + une démo qui prouve la reproductibilité en une commande ; le tout pour un lecteur extérieur pressé**. Un projet data non documenté et non reproductible n'existe pas pour un recruteur.


## 🏢 Cas métier
Pour un projet data, la documentation et la reproductibilité sont ce qui transforme un notebook oublié en pièce de portfolio défendable : un recruteur data évalue en priorité si le projet répond à des questions claires, si les décisions de traitement sont tracées (rapport de qualité), et si le pipeline est reproductible (une commande) — bien avant la sophistication technique. Un projet sans README orienté questions est illisible ; un pipeline qui n'est pas rejouable n'inspire pas confiance ; une absence d'ADR suggère des choix par défaut plutôt qu'arbitrés. L'ADR SQLite vs Postgres est particulièrement parlante car elle montre qu'on connaît les conditions de chaque choix. À compétence égale, le projet data dont on comprend les questions, les réponses et la reproductibilité en deux minutes obtient l'entretien.
